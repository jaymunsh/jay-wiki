# 오목 웹앱 구현 계획

## 1. 목표

`qwen-test` 폴더 안에 외부 CDN 없이 실행할 수 있는 HTML 기반 오목 웹앱을 구현한다.

1차 목표는 완성도 높은 싱글플레이 게임이다. 다만 규칙 엔진과 게임 상태를 UI에서 분리해, 이후 Node.js WebSocket 서버와 최대 5개 방을 지원하는 멀티플레이로 확장할 수 있어야 한다.

## 2. 규칙 정책

### 기본 규칙: 표준 렌주룰

- 15x15 보드
- 흑 선공
- 흑의 3-3 금지
- 흑의 4-4 금지
- 흑의 장목(6목 이상) 금지
- 흑은 정확히 5목일 때 승리
- 백은 5목 이상이면 승리
- 백에게는 표준 렌주룰상 33·44·장목 금지를 적용하지 않는다.
- 흑의 금수 착수는 실행하지 않고, 착수 전에 금수 위치를 표시한다.

### 선택 가능한 변형 규칙

옵션에서 다음 규칙을 선택할 수 있도록 구조만 먼저 마련한다.

- 자유 오목: 33·44·장목 제한 없음
- 양쪽 33 제한 변형: 흑과 백 모두 33을 제한

양쪽 33 제한은 표준 렌주룰이 아니라 변형 규칙이므로, 기본값으로 사용하지 않는다. 규칙 표시 영역에 현재 선택된 규칙을 명시한다.

### 판정 주의사항

흑 33은 단순히 돌 3개가 연속된 것만 세면 안 된다.

- 열린 3
- 끊어진 3
- 가장자리와 모서리
- 4-4와 동시에 발생하는 경우
- 착수 직후 5목이 되는 경우
- 이미 금수인 방향을 이용한 위협

을 구분해야 한다. 정확한 렌주 판정은 독립 규칙 엔진과 테스트로 검증한다.

## 4. 핵심 데이터 모델

```js
GameState = {
  roomId: null,
  players: {
    black: { id: 'human', name: 'Player' },
    white: { id: 'bot', name: 'Ornith Bot' }
  },
  board: [],
  turn: 'black',
  moveHistory: [],
  clocks: {
    mode: 'unlimited',
    blackRemainingMs: null,
    whiteRemainingMs: null
  },
  ruleSet: 'renju',
  gameStatus: 'ready',
  chatMessages: []
}
```

규칙 엔진은 DOM에 의존하지 않는 순수 모듈로 작성한다.

필수 함수:

- `isLegalMove(board, position, player, ruleSet)`
- `getForbiddenMoves(board, player, ruleSet)`
- `checkWin(board, position, player, ruleSet)`
- `checkDraw(board)`
- `applyMove(state, position)`
- `undoMove(state)`

## 5. 화면 구성

### 데스크톱

- 전체 레이아웃은 게임 영역 2/3, 진행 패널 1/3
- 게임 영역: 오목판, 좌표, 마지막 착수 강조, 금수 위치 표시
- 진행 패널: 방 상태, 닉네임, 색상, 현재 턴, 타이머, 수순, 채팅, 액션 버튼

### 필수 UI

- 규칙 프리셋 표시
- 닉네임과 돌 색상
- 현재 턴 및 마지막 착수
- 남은 시간
- 착수 기록
- 채팅방 형태의 로그 패널
- 무르기
- 기권
- 재시작
- 옵션
- 봇 난이도 선택
- 제한 시간 선택

### 모바일

- 보드가 화면 폭을 우선 사용
- 진행 패널은 보드 아래에 배치하거나 접이식 drawer로 표시
- 버튼은 엄지손가락으로 누르기 쉬운 크기로 구성

## 6. 시간 설정

1차 구현에서는 다음을 지원한다.

- 무제한
- 1분
- 3분
- 5분
- 10분

게임 상태에는 양쪽의 남은 시간을 별도로 저장한다. 시간 감소는 실제 게임 상태와 분리된 타이머 모듈에서 처리하며, 게임이 끝나면 타이머를 정지한다.

추후 확장:

- 수마다 제한 시간
- Fischer 방식
- Byo-yomi
- 멀티플레이 서버 기준 시간 동기화

## 7. 봇 난이도

봇은 `getBotMove(state, difficulty)` 형태의 교체 가능한 인터페이스로 작성한다.

- 하: 즉시 승리 수와 즉시 방어 수, 중앙 선호
- 중: 주변 후보 수를 평가하고 공격·방어 점수 비교
- 상: 열린 2·3·4와 상대 위협을 분석하고 얕은 탐색 수행
- 최상: 후보 수 제한, 위협 수 우선 탐색, 얕은 minimax와 transposition cache 적용

봇 계산이 UI를 멈추게 하지 않도록 구조상 Web Worker로 이동할 수 있게 한다. 1차 버전에서는 단순화된 탐색으로 먼저 완성한다.

## 8. 구현 단계

### 단계 1: 규칙 엔진

- 보드 생성과 착수
- 차례 관리
- 승리·무승부
- 흑 33·44·장목 금수
- 자유 오목 및 양쪽 33 변형 규칙의 확장 지점

### 단계 2: 규칙 테스트

다음 테스트를 먼저 작성하고 통과시킨다.

- 빈 보드에서 흑 선공
- 점유 칸 착수 거부
- 흑의 정확한 5목 승리
- 백의 5목 이상 승리
- 흑 장목 금지
- 흑 44 금지
- 흑 33 금지
- 열린 3과 끊어진 3 구분
- 가장자리·모서리 판정
- 자유 오목에서는 금수 해제
- 양쪽 33 변형에서는 백 33도 제한
- 무승부

### 단계 3: 보드 UI

- Canvas 또는 SVG 기반 보드
- 반응형 크기 조절
- 클릭 착수
- 마지막 착수 표시
- 금수 표시
- 승리 라인 표시

### 단계 4: 게임 컨트롤

- 무르기
- 기권
- 재시작
- 규칙 프리셋
- 제한 시간
- 수순 기록

### 단계 5: 봇

- 4단계 난이도
- 즉시 승리·방어
- 후보 수 평가
- 게임 종료 후 재시작

### 단계 6: UI 완성

- 2/3 대 1/3 레이아웃
- 플레이어 카드
- 채팅 패널
- 옵션 모달
- 모바일 대응
- 빈 상태·승리·패배·기권 화면

### 단계 7: 멀티플레이 확장 기반

실제 WebSocket 서버는 구현하지 않는다. 대신 다음 상태와 인터페이스를 보존한다.

- `roomId`
- `players`
- `chatMessages`
- 서버에서 검증할 수 있는 move payload
- 게임 상태 직렬화·복원
- 클라이언트 입력과 게임 엔진의 분리

## 9. 검증 방법

Qwen Code는 각 단계마다 실제 명령을 실행하고 결과를 출력해야 한다.

```bash
node --test
```

추가로 다음을 확인한다.

```bash
node --check src/main.js
python3 -m http.server 4173
```

정적 서버 실행 후 브라우저에서 `http://localhost:4173`을 열어 착수, 금수, 승리, 봇, 타이머, 무르기, 기권, 재시작을 수동 확인한다.
