# 저장소에 적어 두면 AI 코딩 도구가 덜 묻는다

AI 코딩 도구를 팀 저장소에 들이면 비슷한 설명을 반복하게 된다. 프로젝트의 구조, 검증 순서, 변경하면 안 되는 영역을 매번 대화에 붙여 넣는 방식은 누락과 해석 차이를 만든다. 이때 저장소 안의 지침 파일은 대화를 대신하는 만능 규칙집이 아니라, 도구가 작업 맥락을 읽을 수 있게 하는 출발점이다. GitHub 공식 문서는 저장소 전용 지침을 “프로젝트를 이해하고 변경 사항을 빌드·테스트·검증하는 방법”을 전달하는 수단으로 설명한다([공식 문서](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/add-custom-instructions/add-repository-instructions)).

## 먼저 반복되는 문제를 고른다

좋은 지침은 제품 이름보다 저장소에서 반복되는 판단을 적는다. 예를 들어 모든 변경에 적용되는 테스트 순서, 특정 디렉터리에서만 필요한 생성 규칙, 에이전트가 작업할 때 지켜야 할 파일 경계를 분리한다. “항상 이 명령을 실행했다”처럼 확인하지 않은 경험을 사실로 쓰면 지침 자체가 새로운 오류의 출발점이 된다. 실제로 실행해 확인한 절차와 아직 확인하지 않은 제안을 문장부터 나누어 두는 편이 안전하다.

## 규칙을 둘 위치를 선택한다

세 위치는 이름만 다른 복사본이 아니다. 적용 범위와 처리 주체가 다르므로 가장 넓은 규칙부터 작게 좁혀 간다.

| 종류 | 대표 경로 | 적용 범위와 역할 |
|---|---|---|
| 저장소 공통 지침 | `.github/copilot-instructions.md` | 저장소 맥락의 모든 요청에 적용할 공통 개요·검증 원칙을 둔다. |
| 경로별 지침 | `.github/instructions/NAME.instructions.md` | `applyTo` 글롭과 맞는 파일에만 적용한다. 공통 지침과 함께 사용될 수 있다. |
| 에이전트 지침 | 저장소 어디든 `AGENTS.md` | AI 에이전트의 작업 규칙이다. 디렉터리 트리에서 가장 가까운 파일이 우선한다. |

공통 지침 파일의 경로와 경로별 파일의 이름 형식은 공식 문서에 명시돼 있다. 경로별 지침은 GitHub.com의 cloud agent와 code review에서만 지원된다고 안내되므로, 다른 IDE나 도구까지 같은 동작을 보장한다고 확대하면 안 된다([지원 범위와 경로](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/add-custom-instructions/add-repository-instructions)). `AGENTS.md`는 에이전트가 읽을 규칙을 저장소 어디에 둘 수 있게 하지만, 그 파일이 모든 채팅 제품에서 자동으로 적용된다고 단정할 근거는 별도로 확인해야 한다.

## 작은 공통 지침부터 쓴다

아래는 실제 저장소 설정이 아닌 교육용 예시다. 명령은 해당 프로젝트에 존재하고 사전 조건을 확인한 뒤에만 실행한다.

```markdown
Project working notes (교육용 예시)

이 저장소는 API 서버와 웹 클라이언트를 함께 관리한다.

작업 전:
- 변경 범위를 먼저 설명하고 generated/ 아래 파일은 직접 편집하지 않는다.
- 의존성과 런타임 버전은 README와 설정 파일에서 확인한다.

검증 순서:
- 실제로 정의된 포맷터와 정적 검사부터 실행한다.
- 변경 영역에 맞는 테스트를 실행하고, 실행하지 못한 검사는 이유를 남긴다.

완료 조건:
- 변경 파일과 테스트 결과를 요약한다.
- 확인하지 않은 배포·성능·호환성은 성공했다고 쓰지 않는다.
```

이 예시는 프로젝트 개요, 검증 절차, 변경 범위를 드러내지만 특정 저장소의 실행 성공을 주장하지 않는다. 프로젝트 전체에 공통인 안전 규칙은 공통 파일에, `docs/`나 `infra/`처럼 문법과 검증법이 달라지는 영역은 경로별 파일에 둔다. 에이전트가 반드시 확인해야 할 계획·파일 보존 규칙처럼 제품 기능보다 작업 방식에 가까운 내용은 가까운 `AGENTS.md`로 분리할 수 있다.

## 참고됐는지와 지켜졌는지를 나눈다

파일을 저장하면 지침이 사용 가능해지고, Copilot Chat에서는 저장소를 대화에 첨부해 맥락으로 사용할 수 있다. 답변 상단의 References를 펼쳐 `.github/copilot-instructions.md`가 표시되는지 확인하는 것이 공식 문서가 제시하는 확인 방법이다([사용 확인 방법](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/add-custom-instructions/add-repository-instructions)). 이 표시는 파일이 참고 목록에 들어갔다는 증거이지, 답변이 모든 지침을 정확히 따랐다는 증명은 아니다. 결과물의 변경 범위, 테스트 로그, 미실행 항목을 별도로 검토해야 한다.

지침이 충돌할 때의 우선순위도 기록해 둔다. 공식 문서는 개인 지침, 저장소 지침, 조직 지침 순으로 우선순위를 설명하면서도 관련 지침이 함께 제공될 수 있다고 한다. 따라서 같은 대상을 서로 다르게 요구하는 문장을 여러 파일에 복사하기보다, 공통 원칙은 한곳에 두고 예외만 좁은 범위에 적는다. Code review에서 저장소 지침을 사용할지 여부는 설정에서 켜고 끌 수 있고 기본값이 활성화라는 별도 조건도 있다.

## 도입 체크리스트와 한계

도입할 때는 다음을 순서대로 확인한다.

1. 공통 지침에 프로젝트 목적, 금지할 변경 범위, 실제로 확인한 검증 순서를 적는다.
2. 경로별 파일의 `applyTo`가 의도한 파일만 가리키는지 작은 샘플로 확인한다.
3. 답변 References에 지침 파일이 나타나는지 확인하고, 결과 diff와 검증 로그를 사람이 대조한다.
4. 지침 변경을 pull request로 검토하고, 현재 작업 브랜치의 파일이 사용되는지 확인한다.

지침은 입력 맥락을 보태지만 잘못된 명령을 실행 가능하게 만들거나 코드 품질을 자동 보증하지 않는다. 개인·저장소·조직 지침이 충돌하면 결과가 달라질 수 있고, GitHub.com의 기능별 지원 범위도 다르다. 긴 문서에 모든 예외를 쌓기보다 규칙을 작게 유지하고 검증 가능한 문장만 남겨야 한다. 처음에는 모든 작업에 공통인 변경 범위와 검증 원칙을 `copilot-instructions.md`에 정리하고, 반복해서 충돌하는 영역만 경로별 지침으로 분리한 뒤, 에이전트 전용 절차를 가까운 `AGENTS.md`로 옮기는 순서가 실행 가능하다.
