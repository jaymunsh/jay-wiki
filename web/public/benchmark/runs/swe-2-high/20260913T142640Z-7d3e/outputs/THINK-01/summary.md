# 복구 판단 메모: 되돌리기 명령이 있어도 복구는 자동이 아니다

## 결론 먼저

`kubectl rollout undo` 같은 되돌리기 명령이 존재한다는 사실만으로 안전한 복구는 보장되지 않는다. Deployment의 롤백은 Pod 템플릿만 이전 revision으로 되돌릴 뿐이며, 진행 실패는 감지해 보고할 뿐 자동으로 되돌리지 않는다. GitHub의 2018년 장애 사례는 복구의 어려움이 명령 실행이 아니라 데이터 정합성 판단과 대량 복원 시간에 있었음을 보여준다.

## 사례 타임라인(UTC)

2018년 10월 GitHub 장애에서 미국 동부·서부 데이터베이스에 서로 다른 쓰기가 남았다. 서부는 약 40분간 쓰기를 받았고 동부에도 미복제 쓰기가 수초 있어 단순 복귀가 불가능했다.

| 시각(UTC) | 사건 |
|---|---|
| 10/21 23:19 | 추가 쓰기 감축을 위해 webhook 전달·Pages 빌드 일시 중지 |
| 10/22 00:05 | 백업 복원·양쪽 복제본 동기화·토폴로지 복귀 계획 수립 |
| 10/22 00:41 | 영향 MySQL 클러스터 백업 절차 진행 상황 관찰 |
| 10/22 06:51 | 일부 동부 클러스터 복원 완료, 대형 클러스터는 복원 진행 중 |

GitHub는 데이터 무결성을 복구 시간·사용성보다 우선했고, 그 대가로 대륙 간 호출 지연 탓에 많은 사용자가 서비스를 쓰기 어려웠다. 백업은 4시간마다 원격 저장소에 보관됐지만 테라바이트급 전송·압축 해제·체크섬·적재에 시간이 걸렸고, 절차를 매일 시험했어도 전체 클러스터 재구축은 처음이었다.

## 상태 복구와 데이터 정합성은 다르다

Deployment가 되돌리는 대상은 Pod 템플릿이다. 스케일링은 새 revision도 만들지 않고, 롤백해도 데이터베이스 쓰기·스키마·파일 데이터는 건드리지 않는다. `ProgressDeadlineExceeded`가 보고돼도 Kubernetes는 상태 조건을 기록할 뿐 자동 롤백하지 않는다(상위 오케스트레이터가 조건을 보고 행동할 수 있다). GitHub 사례의 쟁점이었던 양방향 쓰기 병합 문제는 컨테이너 배포 도구의 롤백 범위 밖이다.

## 복구 판단 체크리스트

- [ ] 되돌릴 대상이 무엇인지 확인했는가(Pod 템플릿인가, 데이터인가)
- [ ] 이력이 살아 있는가(`revisionHistoryLimit`, paused 여부)
- [ ] 실패가 진행 지연인지 데이터 손상인지 구분했는가
- [ ] 복구 비용(전송·복원 시간)과 우선순위(무결성 vs 사용성)를 합의했는가
- [ ] 복구 후 검증 기준을 미리 정했는가

## 후속 개선 제안

아래는 이 메모 작성자의 제안이며 자료의 보장이 아니다. 실제 담당자·기한·성과 수치는 채우지 않았다.

| 제안 | 담당 역할 | 우선순위 | 완료 확인 기준 |
|---|---|---|---|
| 롤백 가능 조건(이력 보존·paused 절차) 런북화 | 플랫폼 운영 | 높음 | 모의 롤백 절차가 문서대로 재현됨 |
| 복구 우선순위 기준(무결성/시간) 사전 합의 | 서비스 소유자 | 높음 | 장애 시나리오별 판단 기준 문서 존재 |
| 백업 복원 시간 측정·기록 | 데이터 저장소 담당 | 중간 | 전체 복원 리허설 소요 시간이 기록됨 |
