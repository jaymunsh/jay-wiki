# AMBIG-03 assumptions — 정책 명세서(v2.3) 해석과 판단

## 발견한 모순과 해석

**§3 "최초 호출 포함 최대 3회" vs §7 "일시 오류: 성공할 때까지 재시도"** — 두 조항이 직접 충돌한다. 나는 다음과 같이 해석했다.

- §3을 구체적 수치 규칙으로 우선 적용해 **최대 3회 시도**로 제한한다.
- §7의 "성공할 때까지"는 "§3의 한도 내에서 계속 재시도한다"는 의도로 읽는다(§7 표의 실질 역할은 종료 조건 요약).
- 근거: §7을 문자 그대로 적용하면 무한 재시도가 되어 §3·§7의 '대기 총합 5초' 규칙이 무의미해진다. 문서 전체가 모순 없이 성립하려면 §3이 상한 규칙이어야 한다. 또한 §3이 "횟수"를 전담하는 조항이고 §7은 조건별 동작의 요약표이므로, 구체 조항을 우선하는 문서 해석 원칙을 따랐다.
- 이 해석이 틀렸다면 대안은 "§7 우선 = 사실상 대기 5초까지 무제한"이다. 이 경우도 대기 총합 5초 조항이 상한으로 작동하므로, 본 구현은 어느 해석에서도 5초 대기 상한을 지킨다.

## 명세 그대로 따른 사항

- **오류 분류(§2)**: 상태 코드 없는 오류(네트워크 단절·타임아웃 추정)와 5xx, 429는 일시 오류 → 재시도. 나머지 4xx(401/403 포함)는 영구 오류 → 즉시 실패. "한도 초과"는 별도 상태가 명시되지 않아 4xx 계열로 포함했다.
- **백오프(§4)**: 첫 대기 200ms, 매번 2배, 상한 2,000ms, 지터 없음.
- **횟수(§3)**: 최초 호출 포함 최대 3회.
- **대기 총합(§7)**: 누적 대기가 5초를 넘을 대기는 수행하지 않고 중단·실패 반환. (기본값 조합에서는 200+400=600ms로 실제로 도달하지 않지만 규칙은 구현함.)
- **멱등성(§5)**: 호출마다 `crypto.randomUUID()`로 멱등 키를 하나 생성해 모든 시도에 동일하게 사용한다. `fn`이 인자를 받으면 키를 전달하고, 받지 않는 `fn`도 호출은 동일하게 동작한다. 명세상 "포함"의 실제 전달 수단이 `fn`의 계약에 의존하므로 이 방법을 택했다.
- **관측(§6)**: 재시도마다 `retry.attempt`·`retry.reason`을, 최종 실패 시 `retry.exhausted`를 기록한다. 출력 수단은 명세에 없어 구조화된 JSON 로그(console)를 기본으로 하고, `log` 콜백 옵션으로 수집기를 주입할 수 있게 했다.
- **§8 예외 사항**: 정산 배치는 이 정책의 적용 대상이 아니므로 본 함수에 별도 분기를 두지 않았다(적용 주체가 호출자 측 판단이기 때문).

## 명세에 없어 내가 정한 것

- 실패 시 마지막 오류를 래핑하지 않고 그대로 throw — 호출자가 원본 오류를 진단할 수 있어야 하므로.
- `fn` 비함수 인자 → `TypeError`.
