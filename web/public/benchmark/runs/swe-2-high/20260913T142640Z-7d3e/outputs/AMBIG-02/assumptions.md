# AMBIG-02 assumptions — 재시도 래퍼의 판단과 근거

명세는 "외부 API 호출이 실패하면 재시도한다"와 "성공 시 반환값을 그대로 돌려준다"만 정한다. 아래는 내가 채운 정책과 근거다.

## 결정 사항

1. **최대 시도 횟수 = 3 (최초 호출 포함)**
   - 근거: 무한 재시도는 장애 중인 API를 더 압박하고 호출자를 무한 대기시킨다. 외부 API 래퍼의 통상 기본값인 3회를 택했다.

2. **재시도 가능 오류의 분류**
   - 네트워크 수준 실패(상태 코드가 없는 오류)와 HTTP 408/409/425/429/5xx는 일시적 → 재시도.
   - 그 외 4xx(400/401/403/404/422 등)는 요청 자체의 문제로 보고 즉시 실패 반환.
   - 오류 객체에 `retryable: boolean` 속성이 있으면 그 값을 우선한다.
   - 근거: 인증 실패·잘못된 요청에 대한 재시도는 지연만 늘리고 의미가 없다. 429는 일시 과부하 신호이므로 재시도 대상에 포함했다.

3. **지수 백오프 + 상한 + 지터**
   - 첫 대기 200ms, 매번 2배, 상한 2,000ms. ±20% 지터를 더한다.
   - 근거: 즉시 재시도는 장애 회복 시간을 주지 못하고, 고정 간격 동시 재시도는 thundering herd를 만든다. 지터는 여러 클라이언트의 재시도 동기화를 분산한다.

4. **실패 시 동작**
   - 모든 시도가 실패하면 마지막 오류를 그대로 throw한다(래핑하지 않음).
   - 근거: 호출자가 원본 오류의 상태 코드·메시지를 그대로 진단에 쓸 수 있어야 한다.

5. **성공 반환**
   - `fn()`의 resolve 값을 변형 없이 그대로 반환한다.

6. **옵션 노출**
   - 정책 값은 기본값으로 채우되 두 번째 인자로 재정의 가능하게 했다.
   - 근거: 명세가 시그니처 `callWithRetry(fn)`를 요구하므로 첫 인자 계약은 유지하고, 실제 사용에서 튜닝이 필요할 때를 위해 선택적 두 번째 인자를 추가했다.

7. **비함수 인자·잘못된 옵션**
   - `fn`이 함수가 아니면 `TypeError`, `maxAttempts`가 양의 정수가 아니면 `RangeError`.
   - 근거: 프로그래머 실수와 외부 API 실패를 구분해 즉시 드러내는 편이 디버깅에 유리하다.

## 명세에 없어서 하지 않은 것

- 타임아웃 강제(개별 호출의 취소/시간 제한): 명세가 요구하지 않으며 AbortController 계약이 `fn`에 의존하므로 추가하지 않았다.
- 서킷 브레이커·멱등 키 부착: 정책 범위 밖으로 판단.
