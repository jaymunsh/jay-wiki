# AI 코딩 도구에 매번 같은 규칙을 설명하지 않으려면

## 반복 설명의 비용

AI 코딩 도구를 팀에 도입하면 처음에는 모두가 같은 대화를 반복한다. "테스트는 이렇게 돌립니다", "이 디렉터리는 건드리지 마세요", "커밋 전에 린트를 확인하세요" 같은 말을 세션마다 다시 입력해야 한다. 규칙이 사람의 기억과 채팅 기록에만 남아 있으면 도구는 매번 빈 상태에서 시작한다.

저장소에 규칙을 파일로 적어 두면 이 반복을 줄일 수 있다. GitHub Copilot의 저장소 사용자 지정 지침처럼, 파일이 요청에 자동으로 포함되도록 설계된 기능을 쓰는 방식이다. 핵심 질문은 "무엇을 적을까"보다 먼저 "어디에 둘 것인가"다.

## 규칙을 둘 위치 세 가지

[GitHub 문서](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/add-custom-instructions/add-repository-instructions)는 저장소 지침을 세 유형으로 나눈다. 역할과 위치, 적용 범위가 다르므로 비교해 고르면 된다.

| 유형 | 위치 | 역할 | 적용 범위 |
|---|---|---|---|
| 저장소 공통 지침 | `.github/copilot-instructions.md` | 프로젝트 전체 맥락 | 해당 저장소의 모든 요청 |
| 경로별 지침 | `.github/instructions/NAME.instructions.md` | 특정 파일 종류의 규칙 | `applyTo` glob에 맞는 파일을 다루는 요청 |
| AGENTS.md | 저장소 어디든, 여러 개 가능 | AI 에이전트용 지침 | 디렉터리 트리에서 가장 가까운 파일이 우선 |

경로별 지침은 파일 앞부분의 frontmatter에서 `applyTo: "app/models/**/*.rb"`처럼 glob로 대상을 지정한다. 대상 파일과 공통 지침이 둘 다 해당하면 둘 다 함께 쓰인다. AGENTS.md 대신 루트에 `CLAUDE.md`나 `GEMINI.md` 하나를 두는 선택지도 문서에 나온다.

주의할 점은 지원 범위다. 경로별 지침은 문서 기준으로 GitHub.com의 Copilot cloud agent와 code review에서만 지원된다. 같은 구조가 모든 AI 도구에서 보장되는 것은 아니므로, 쓰는 도구의 문서에서 지원 여부를 확인해야 한다.

## 저장소 공통 지침의 작은 예시

공통 지침에는 무엇을 적을까. 문서가 생성용 프롬프트에서 권장하는 내용은 저장소가 무엇을 하는지, 빌드·검증 절차, 프로젝트 구조다. "2페이지를 넘지 않고 특정 작업에만 해당하지 않게"라는 제한도 함께 제시된다. 아래는 그 취지를 옮긴 교육용 예시로, 실제 이 저장소의 설정이 아니다.

```markdown
# Project overview
결제 이력을 조회하는 내부 웹 서비스. Go 1.22 + PostgreSQL, 진입점은 cmd/server/main.go.

# Build and validate
- go test ./... 를 커밋 전에 반드시 실행한다(작성자가 이 예시 작성 시점에 실제 명령을 검증하지 않았으므로, 도입 시 각자 환경에서 확인 필요).
- db/ 마이그레이션을 바꿨다면 로컬에서 up/down을 모두 시험한다.

# Change boundaries
- internal/pricing/ 은 회계팀 승인 없이 수정하지 않는다.
- 생성 파일(gen/)은 편집하지 않고 생성 스크립트를 고친다.
```

적을 때 기준은 "첫날 온 동료에게 구두로 전할 것"이다. 검증 순서, 하면 안 되는 변경, 찾기 어려운 설정 위치가 우선이다.

## 적용됐는지 확인하는 방법

파일을 저장하면 지침은 바로 요청에 자동으로 추가된다. 실제로 참고됐는지는 Copilot Chat에서 답변 상단의 참조 목록을 펼쳐 `.github/copilot-instructions.md`가 뜨는지로 확인할 수 있다. code review에서는 head 브랜치의 지침 파일을 읽으므로 같은 PR에서 지침 변경도 시험할 수 있다.

다만 "참조에 떴다"와 "지침을 따랐다"는 다르다. 참조 표시는 파일이 요청에 포함됐다는 증거이지 답변이 규칙을 준수했다는 보장이 아니다. 준수 여부는 여전히 결과물 검토와 CI 검증으로 확인해야 한다.

## 도입 전 체크리스트와 한계

- [ ] 쓰는 도구와 기능(채팅·에이전트·리뷰)이 각 지침 유형을 지원하는지 확인했는가
- [ ] 지침에 적은 명령을 실제 환경에서 실행해 봤는가
- [ ] 여러 지침이 겹칠 때 우선순위(개인 > 저장소 > 조직)와 충돌 가능성을 검토했는가
- [ ] 참조 목록에서 파일이 실제로 읽혔는지 확인하는 절차를 팀이 아는가

한계도 있다. 지침은 프롬프트에 실리는 힌트일 뿐 강제 장치가 아니며, 오래되면 실제 절차와 어긋난다. 저장소 규칙이 길어질수록 유지비도 커진다.

## 어떤 규칙부터 분리할까

결론은 단순하다. 먼저 `.github/copilot-instructions.md` 하나에 "이 프로젝트가 무엇인지 + 검증 절차"만 적는다. 매번 반복되던 설명이 줄어드는지 확인한 뒤, 규칙이 경로나 에이전트별로 달라질 때만 `instructions/`와 AGENTS.md로 분리한다. 처음부터 세 유형을 다 만들면 관리 대상이 늘고, 쓰이지 않는 규칙은 오히려 혼란이 된다.
