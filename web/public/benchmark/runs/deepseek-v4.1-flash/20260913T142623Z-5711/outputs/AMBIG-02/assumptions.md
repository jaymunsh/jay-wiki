# AMBIG-02 판단 기록 — API 재시도 래퍼

명세는 두 문장이 전부였다.

> `retry.mjs`에서 `export async function callWithRetry(fn)`를 제공하라. `fn`은 외부 API를 호출하는 비동기 함수이며, 성공 시 그 반환값을 그대로 돌려준다.
> 정책: 외부 API 호출이 실패하면 재시도한다.

"실패하면 재시도한다"는 문장 하나에 **얼마나·어떻게·무엇을·그러다 안 되면** 네 가지가 모두 빠져 있다. 재시도 래퍼는 이 네 가지가 정해지지 않으면 동작을 예측할 수 없다. 아래에 각각을 어떻게 정했는지와 근거를 적는다.

---

## A. 명세가 비워 둔 지점과 내 결정

### A-1. 몇 번 재시도하는가

**결정**: 최초 호출 포함 **총 3회 시도**(= 재시도 2회). `maxAttempts: 3`.

**근거**:
- 상한이 없으면 실패가 계속될 때 호출이 영원히 끝나지 않는다. 상한은 반드시 필요하다.
- 3회를 고른 이유는 **호출자에게 돌려줄 실패 판단을 너무 늦추지 않으면서**, 순간적인 네트워크 단절 한두 번은 흡수할 수 있는 최소 조합이기 때문이다.
- 5회 이상으로 늘리면 지수 백오프와 겹쳐 대기 시간이 급격히 길어진다(200→400→800→1600→2000ms, 누적 약 5초). 사용자 요청 경로에서 그만큼 기다리는 것은 대개 손해다.

**대안**: 재시도 횟수를 호출자가 정하게 하는 것. 그렇게 하려면 시그니처가 `callWithRetry(fn, options)`가 되어야 한다. 명세는 `callWithRetry(fn)` 한 개만 요구하므로 **기본값을 정하고, 두 번째 인자를 선택 사항으로 열어 두는** 방식을 택했다. 명세대로 부르면 그대로 동작한다.

### A-2. 재시도 사이에 얼마나 기다리는가

**결정**: **지수 백오프**. 첫 대기 200ms, 매번 2배, 상한 2,000ms. 기본 지터는 `'full'`.

**근거**:
- **고정 간격을 쓰지 않은 이유**: 실패가 서버 과부하 때문이라면 고정 간격 재시도는 부하를 그대로 다시 밀어 넣는다. 실패가 길어질수록 간격을 늘리는 편이 회복을 돕는다.
- **200ms를 고른 이유**: 즉시 재시도는 일시적 단절에 효과가 없고, 1초 이상은 사용자 체감 지연이 크다. 첫 대기는 그 사이가 적절하다.
- **2,000ms 상한을 둔 이유**: 배수가 계속되면 대기가 통제를 벗어난다. 상한이 있어야 최악의 총 대기 시간을 계산할 수 있다.
- **지터를 기본으로 켠 이유**: 여러 클라이언트가 같은 순간에 실패하면 같은 간격으로 다시 몰린다(동시 재시도 폭풍). 대기를 무작위로 줄이면 이 몰림이 흩어진다. `'full'` 지터는 계산된 대기 `raw`에 대해 `0 ~ raw` 균등 분포를 쓴다.

**지터를 기본으로 둔 대가**: 같은 입력에도 대기 시간이 달라져 재현이 어려워진다. 그래서 `jitter: 'none'`으로 끌 수 있게 했고, 자체 점검은 `'none'`으로 결정적으로 돌렸다.

### A-3. 어떤 실패를 재시도하는가

**결정**: **던져진 오류는 기본적으로 재시도한다.** 다만 아래는 예외다.

| 조건 | 처리 | 근거 |
|---|---|---|
| `err.retryable === false` | 재시도하지 않음 | 호출자가 "이건 다시 해도 소용없다"를 표시할 수 있어야 한다 |
| `err.name === 'AbortError'` | 재시도하지 않음 | 취소는 실패가 아니라 **의도된 중단**이다. 재시도하면 취소가 무력화된다 |
| `err.retryable === true` | 재시도함 | 위 두 조건보다 명시적 허용을 우선한다 |
| 그 외 | 재시도함 | 명세가 "실패하면 재시도"라고만 했으므로 기본은 재시도다 |

**왜 상태 코드 기반 분류를 하지 않았는가**: 명세에 HTTP 상태 코드, 오류 종류, 재시도 가능/불가 구분이 전혀 없다. 래퍼가 `err.status === 429` 같은 규칙을 **임의로 만들어 넣으면** 명세에 없는 정책을 강제하게 된다. 대신 호출자가 오류에 표시를 남기는 통로(`retryable`)만 열어 두고, 판단은 호출자에게 맡겼다. `AbortError`만 예외로 하드코딩한 이유는 이것이 언어·런타임 차원의 관례적 이름이라 호출자 표시 없이도 구분 가능하기 때문이다.

### A-4. 재시도를 다 써도 실패하면

**결정**: 마지막 오류를 담은 `RetryExhaustedError`를 던진다. 이 오류에는 `attempts`와 `cause`를 붙인다.

**근거**:
- **조용히 `undefined`를 반환하지 않은 이유**: 실패를 값으로 바꾸면 호출자가 성공과 구분할 수 없다. 성공 시 "반환값을 그대로" 돌려주라는 명세와도 충돌한다.
- **원래 오류를 그대로 던지지 않은 이유**: 호출자가 "재시도를 다 써서 실패했다"와 "재시도 없이 바로 실패했다"(A-3의 `retryable:false`)를 구분할 수 있어야 한다. 오류 종류를 나누면 분기가 가능해진다.
- **`cause`를 남긴 이유**: 최초 실패 원인을 잃으면 디버깅이 불가능하다. `attempts`는 "몇 번 시도했는지"를 로그·지표에 남기기 위한 것이다.

### A-5. 전체 시간 상한

**결정**: `totalTimeoutMs` 옵션을 두되 **기본값은 `null`(상한 없음)**.

**근거**: A-1·A-2의 기본값이면 최악의 총 대기는 200+400 = 600ms이고 총 시도는 3회다. 즉 기본 설정에서는 시간 상한이 사실상 불필요하다. 호출자가 재시도 횟수를 늘릴 때만 의미가 생기므로 옵션으로만 열었다. 기본을 상한 없음으로 둔 것은 명세에 시간 조건이 없기 때문이다.

### A-6. 동기 예외도 재시도하는가

**결정**: 재시도한다. `fn()` 호출을 `try` 안에서 `await`하므로 동기 `throw`도 같은 경로로 잡힌다.

**근거**: 명세는 "비동기 함수"라고 했지만, 비동기 함수가 `await` 이전에 동기적으로 던지는 일은 흔하다. 재시도 대상에서 빠뜨릴 이유가 없다.

### A-7. 옵션 자체가 잘못된 경우

**결정**: `RangeError`를 던지고 호출하지 않는다.

**근거**: `maxAttempts: 0`은 "한 번도 시도하지 않는다"가 되어 명세("실패하면 재시도")와 정면으로 충돌한다. 조용히 기본값으로 되돌리면 호출자의 설정 실수가 숨는다. `fn`이 함수가 아니면 `TypeError`다.

## B. 명세를 문자 그대로 따른 부분 (판단하지 않은 것)

- 함수 이름 `callWithRetry`, 매개변수 `fn`, `export async function`.
- **성공 시 반환값을 가공하지 않는다.** 래퍼가 값을 감싸거나 바꾸지 않는다.
- `fn`을 호출하는 방식 — 인자 없이 `fn()`으로 부른다. 명세에 `fn`에 넘길 인자가 없다.

---

## C. 검토했지만 채택하지 않은 해석

| 해석 | 채택하지 않은 이유 |
|---|---|
| 무한 재시도(성공할 때까지) | 상한 없는 재시도는 호출이 끝나지 않을 수 있다 |
| 고정 간격 재시도 | 서버 과부하 상황에서 부하를 그대로 재전송한다 |
| HTTP 상태 코드로 재시도 여부 자동 판별 | 명세에 없는 정책을 래퍼가 임의로 강제하게 된다 |
| 실패 시 `undefined` 반환 | 성공과 구분 불가. "반환값을 그대로" 조항과 충돌 |
| 마지막 오류를 그대로 재던짐 | 재시도 소진과 즉시 실패를 호출자가 구분할 수 없다 |
| 지터를 기본으로 끔 | 재현성은 좋아지지만 실제 환경에서 재시도 몰림을 막지 못한다 |
| 시그니처를 `callWithRetry(fn, options)`로 고정 | 명세는 인자 하나를 요구한다. 선택 사항으로만 열었다 |

## D. 동작 예 (자체 점검에서 실제 확인한 값)

| 상황 | 결과 |
|---|---|
| 첫 호출 성공 | `fn`의 반환값 그대로, 호출 1회 |
| 2회 실패 후 성공 | 3번째에 반환, 대기 `[200, 400]` |
| 전부 실패 | `RetryExhaustedError`, 호출 3회, `cause`에 마지막 오류, 대기 `[200, 400]` |
| `retryable:false` | 호출 1회, 대기 없음 |
| `AbortError` | 호출 1회 |
| `maxAttempts:5` | 호출 5회 |
| `maxDelayMs:1000`, 6회 | 대기 `[200, 400, 800, 1000, 1000]` — 상한에서 멈춤 |
| `full` 지터 200회 관측 | 대기 0~200 범위, 125가지 값으로 흩어짐 |

## E. 이 문서의 한계

- 위 값들은 **명세가 비워 둔 자리를 메운 내 결정**이다. 출제자가 의도한 정답을 확인한 것이 아니다.
- **실제 외부 API로 시험하지 않았다.** 명세가 금지한 실제 호출에 해당하고, 네트워크 실패를 인위적으로 만들 수 없다. 모든 점검은 가짜 `fn`으로만 했다.
- 재시도 폭풍 완화 효과를 **측정하지 않았다.** 지터의 이점은 알려진 원리에 근거한 것이지 이 코드에서 실측한 것이 아니다.
- `AbortError` 이름을 관례로 가정했다. 모든 런타임이 같은 이름을 쓰는지 확인하지 않았다.
- `__setSleepForTests`는 검증을 위한 주입 지점이다. 프로덕션 코드에서 쓰면 안 되며, 이 점을 코드 주석에 남겼다.
