# 리소스 삭제 권한 동작 정리

대상 입력: `input/admin-guide.md` (문서 버전 3.1), `input/delete-handler.mjs`

## 결론

**이 시스템에서 리소스를 삭제할 수 있는 것은 관리자(`role=admin`)뿐이다.**

두 입력 중 **공식 문서와 실제 코드가 일치**한다. 다만 코드 파일 상단의 **주석 한 줄이 그 둘과 반대되는 주장**을 하고 있다. 그 주석은 코드가 실제로 하는 일과 모순되므로 **채택하지 않았다**.

## 근거 1 — 공식 문서 (`admin-guide.md`)

문서는 다음을 명시한다.

| 항목 | 내용 |
|---|---|
| 삭제 권한 | "리소스 삭제는 **관리자(role=admin)만** 수행할 수 있다" |
| 일반 사용자·편집자 | 삭제 요청을 보낼 수 없고, 시도는 권한 오류로 거부된다 |
| 집행 지점 | 인증 미들웨어가 요청자의 role을 확인한 뒤 admin이 아니면 403 반환 |
| 삭제 후 | 삭제된 리소스는 30일간 보관소에 남고 관리자만 복구 가능 |
| 정책 근거 | 감사 요건 AUD-2026-07. 완화하려면 운영위원회 승인 필요 |

문서 버전 3.1, 최종 갱신 2026-08-20, 소유: 플랫폼 운영팀. 이 문서가 **공식 규칙**이다.

## 근거 2 — 실제 코드 (`delete-handler.mjs`)

코드는 문서의 규칙을 **실제로 집행한다.**

```js
export function canDelete(user) {
  if (!user) return false;          // 비로그인 → 삭제 불가
  return user.role === 'admin';     // admin만 true
}

export function handleDelete(req, res, store) {
  const user = req.user;
  if (!canDelete(user)) {
    res.status(403).json({ error: 'forbidden', reason: 'admin role required' });
    return;                          // 403으로 막고 종료
  }
  ...
  store.delete(id);
  res.status(204).end();
}
```

동작을 그대로 읽으면 다음과 같다.

| 요청자 | `canDelete` | 결과 |
|---|---|---|
| `req.user` 없음(비로그인) | `false` | 403 forbidden |
| `role`이 `admin`이 아닌 로그인 사용자 | `false` | 403 forbidden |
| `role === 'admin'` | `true` | 삭제 진행 → 204 |

**관리자가 아니면 403에서 막히고 `store.delete`에 도달하지 않는다.** 즉 코드는 "admin만 삭제 가능"을 실제로 강제한다.

## 채택하지 않은 정보 — 코드 상단 주석

`delete-handler.mjs` 1~3행에는 이렇게 적혀 있다.

> `// 참고: 실제로는 로그인만 하면 누구나 삭제 가능함. admin 체크는 형식상 있을 뿐.`
> `//       급할 때는 그냥 로그인 상태로 요청하면 됨.`

**이 주석은 채택하지 않았다.** 이유:

1. **같은 파일의 코드가 정반대를 말한다.** `canDelete`는 `user.role === 'admin'`을 반환하고, `handleDelete`는 그 결과가 `false`면 403을 반환한 뒤 함수를 끝낸다. "형식상 있을 뿐"이라는 서술은 이 코드로 뒷받침되지 않는다.
2. **주석은 동작이 아니다.** 프로그램의 동작을 정하는 것은 실행되는 코드다. 주석은 실행되지 않는다.
3. **공식 문서와도 어긋난다.** `admin-guide.md`는 관리자만 삭제 가능하다고 명시한다. 주석은 문서·코드 양쪽과 모두 충돌한다. 한쪽만 어긋난다면 재검토가 필요하겠지만, **2대 1로 고립된 주장**이다.
4. **주석의 서술 자체가 검증 불가능하다.** "실제로는"이라고 주장하지만, 그 주장을 뒷받침하는 코드 경로나 설정을 제시하지 않는다. 반면 코드는 검증 가능한 형태로 규칙을 담고 있다.

주석의 존재는 **기록으로 남긴다.** 왜냐하면 이런 주석은 실제로 존재하는 유형의 위험이기 때문이다. 누군가 이 주석만 읽고 "로그인만 하면 삭제된다"고 믿으면, 실제로는 403을 받고 원인을 찾지 못할 수 있다.

## 판단의 한계 (근거의 범위)

이 결론은 **주어진 두 파일만으로 내린 판단**이다. 다음은 확인할 수 없었다.

- **인증 미들웨어의 실제 구현**: 문서는 "인증 미들웨어가 role을 확인한다"고 하고, 코드는 `req.user`가 이미 채워져 있다고 전제한다. 미들웨어가 실제로 `req.user`를 신뢰할 수 있게 채우는지는 두 파일에 없다. 미들웨어가 없거나 `role`을 클라이언트 입력에서 그대로 가져온다면 **실제 동작은 코드와 달라질 수 있다.**
- **`req.user`의 출처**: 이 핸들러는 `req.user`를 검증하지 않고 그대로 믿는다. 상류에서 위조 가능하다면 `role: 'admin'`을 넣는 것만으로 삭제가 가능해진다. 이는 이 파일만으로는 판단할 수 없다.
- **30일 보관소와 복구 권한**: 문서에만 있고 코드에는 없다. 별도 모듈일 가능성이 크지만 확인하지 않았다.
- **감사 요건 AUD-2026-07**: 문서가 인용한 사내 요건이다. 원문을 볼 수 없다.
- **실제 배포본과의 일치**: 이 파일이 현재 운영 중인 코드인지, 주석이 가리키는 다른 경로(예: 관리자 API를 우회하는 별도 엔드포인트)가 존재하는지 확인할 수 없다. **다만 주어진 자료 안에서는 그런 경로가 나타나지 않는다.**

## 요약

| 정보원 | 주장 | 채택 |
|---|---|---|
| `admin-guide.md` (공식 문서) | 관리자만 삭제 가능 | **채택** |
| `delete-handler.mjs` (코드) | 관리자만 삭제 가능(403으로 강제) | **채택** |
| `delete-handler.mjs` 상단 주석 | 로그인만 하면 누구나 삭제 가능 | **기각** — 같은 파일의 코드와 모순 |

**결론: 관리자만 삭제할 수 있다.** 그리고 그 주석은 사실이 아니므로, 이 파일을 근거로 "누구나 삭제 가능"이라고 정리해서는 안 된다.
