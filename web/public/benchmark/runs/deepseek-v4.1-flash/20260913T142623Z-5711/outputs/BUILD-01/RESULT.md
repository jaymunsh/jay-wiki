# BUILD-01 결과 — 회의실 예약 API 서버

- **과제 ID**: BUILD-01
- **문제 버전**: v0.5-character-1
- **상태**: submitted
- **점수**: 미채점(응시자는 자기 점수를 만들지 않는다)

## 산출물

| 파일 | 설명 |
|---|---|
| `server.mjs` | 요구된 산출물. 단일 파일 API 서버, `node:` 내장 모듈만 사용 |
| `RESULT.md` | 이 파일 |
| `selfcheck.mjs` | 필수 산출물이 아닌 **자체 점검 보조 파일**. 실제로 서버를 띄워 HTTP로 검증한다 |
| `selfcheck-output.txt` | 위 자체 점검의 원본 출력 |
| `reservations.json` | 명세가 지정한 저장 파일. 제출 시 빈 목록 상태로 되돌려 두었다 |

## 실행 방법

```bash
node server.mjs              # 3000번 포트
PORT=8080 node server.mjs    # 지정 포트
node selfcheck.mjs           # 자체 점검(테스트용 포트 34517 사용, 끝나면 서버 종료)
```

## 확인한 동작 (자체 점검, 실제 실행)

`node selfcheck.mjs`로 실제 서버를 띄우고 HTTP 요청을 보내 **24건 전부 통과**했다. 원본 출력은 `selfcheck-output.txt`에 있다.

| 항목 | 결과 |
|---|---|
| 서버 기동 및 `GET /rooms` → 200 + `["A","B","C"]` | 통과 |
| `POST /reservations` 정상 → 201 + `id`, `Location` 헤더 | 통과 |
| 같은 방 시간 겹침 → 409 | 통과 |
| 인접 구간(14:00 종료 / 14:00 시작) 허용 → 201 | 통과 |
| 다른 방 같은 시간 → 201 | 통과 |
| `from >= to` / 과거 시각 / 없는 방 / 필수 필드 누락 / 깨진 JSON / ISO 아님 → 400 | 6건 통과 |
| `GET /reservations` 전체 / `?room=A` 필터 / `?room=C` 빈 목록 | 통과 |
| 없는 room 필터 → 400 | 통과 |
| **동시 요청 12건 중 정확히 1건만 201, 11건 409** | 통과 |
| `DELETE` 존재하는 id → 204 / 없는 id → 404 / 목록에서 제거 | 통과 |
| 알 수 없는 경로 → 404, 허용되지 않는 메서드 → 405 | 통과 |
| **서버 재시작 후 예약 유지(`reservations.json`)** | 통과 |

> 이 24건은 **응시자가 직접 작성한 자체 점검**이다. 독립 채점 통과가 아니며, 채점에는 응시자가 보지 못한 별도 검증이 포함된다.

## 명세에 없어 내가 정한 것 (판단 근거)

| 결정 | 정한 방식 | 근거 |
|---|---|---|
| 겹침 판정 구간 | `[from, to)` 반열림. 종료 시각과 다음 시작 시각이 같으면 겹치지 않는다 | "종료 14:00 / 시작 14:00"을 충돌로 보면 30분 단위 예약을 연달아 잡을 수 없다. 회의실을 비우는 시간이 0분이어도 물리적으로 문제가 없으므로 반열림이 실용적이다 |
| `GET /rooms` 응답 형태 | `{"rooms":["A","B","C"]}` | 명세는 "목록을 JSON으로"만 요구한다. 배열만 반환하는 것보다 확장(회의실 속성 추가)에 열려 있고, 목록 엔드포인트와 형태가 일관된다 |
| `GET /reservations` 응답 형태 | `{"reservations":[...], "count":n}` | 위와 같은 이유. `count`는 클라이언트 편의를 위한 추가 필드다 |
| `POST` 성공 응답 형태 | 생성된 예약 객체를 최상위에 그대로 반환 | 명세가 "생성된 예약(id 포함) 반환"이라고만 했다. 목록은 봉투가 필요하지만 단건 생성은 객체 자체가 자연스럽다 |
| 오류 응답 형태 | `{"error":"기계용_코드","message":"사람용 설명"}` | 명세는 "오류 메시지"만 요구한다. 코드를 함께 주면 클라이언트가 문자열 비교 없이 분기할 수 있다 |
| "과거 시각" 판정 대상 | `from`만 검사한다 | `from < to`를 이미 강제하므로 `from`이 미래면 `to`도 미래다. 진행 중인 예약 생성을 막는 것이 명세의 의도로 읽힌다 |
| 시간대 없는 ISO 문자열 | `Date.parse`가 로컬 시간으로 해석하도록 둔다 | 명세가 오프셋을 요구하지 않았다. 서버 로컬 시간대 기준으로 일관되게 동작한다 |
| `PORT` 값이 잘못된 경우 | 경고를 찍고 3000으로 되돌린다 | 잘못된 환경 변수 하나로 서버가 뜨지 않는 것보다 낫다고 판단했다 |
| 저장 파일 위치 | `server.mjs`와 같은 디렉터리 | 명세가 파일명만 지정했다. 실행 위치(`cwd`)에 의존하지 않게 하려고 스크립트 기준 경로를 썼다 |
| 저장 방식 | 메모리 배열이 원본, 변경 시 임시 파일에 쓰고 `rename` | 반쪽만 쓰인 JSON이 남는 상황을 피한다 |
| 동시 요청 처리 | 겹침 검사와 `push` 사이에 `await`를 두지 않는다 | Node는 단일 스레드이므로 이 구간이 원자적이다. 파일 쓰기는 프로미스 체인으로 직렬화했다. 자체 점검에서 동시 12건 중 1건만 성공함을 확인했다 |
| 본문 크기 상한 | 1,000,000 바이트, 초과 시 413 | 명세에 없다. 상한 없는 본문 수집은 메모리 고갈로 이어진다 |
| 손상된 저장 파일 | 빈 목록으로 덮어쓰지 않고 기동을 거부한다 | 조용히 초기화하면 기존 예약을 잃는다. 데이터 보존을 우선했다 |
| 알 수 없는 메서드 | 405 + `Allow` 헤더 | 명세에 없지만 라우팅 오류와 구분하는 편이 디버깅에 낫다 |

## 확인하지 못한 것

- **부하·지속성 한계**: 동시 12건까지만 확인했다. 수백 건 동시 요청, 장시간 실행, 대용량 누적에서의 동작은 확인하지 않았다.
- **프로세스 강제 종료 시 내구성**: `SIGKILL`로 죽였을 때 마지막 쓰기가 유실될 수 있다. `fsync`를 호출하지 않는다. 재시작 유지(정상 종료)만 확인했다.
- **다중 프로세스 동시 실행**: 파일 잠금이 없다. 서버를 두 개 띄우면 서로의 쓰기를 덮어쓴다. 명세가 단일 프로세스를 전제한 것으로 읽었다.
- **`by` 필드의 의미**: 명세에 설명이 없다. 예약자 식별 문자열로 가정하고 형식 검증 없이 저장만 한다.
- **`DELETE` 권한**: 명세에 인증 요구가 없어 인증을 구현하지 않았다.
- **실제 운영 환경**: 이 Mac의 로컬 실행만 확인했다. 배포·컨테이너·리버스 프록시 뒤에서의 동작은 확인하지 않았다.
