# 되돌리기 명령이 있다고 안전한 복구는 아니다

## 결론

되돌리기 명령의 존재는 안전한 복구를 보장하지 않는다. Kubernetes Deployment의 롤백은 Pod template 부분만 이전으로 되돌린다. 그동안 데이터베이스에 쓰인 내용은 되돌아가지 않는다. GitHub의 2018년 10월 21일 장애에서는 오히려 되돌리기보다 데이터 무결성을 먼저 세우는 선택이 필요했다. 두 자료는 서로 다른 시스템의 사례이며, GitHub 사례가 Kubernetes Deployment로 복구됐다는 근거는 자료에 없다.

## 배포 상태 복구와 데이터 정합성의 차이

Deployment를 되돌리면 Pod template만 이전 상태로 간다. 이미지와 설정이 되돌아갈 뿐, 애플리케이션이 그동안 쓴 데이터는 그대로 남는다. 그래서 배포가 정상으로 보여도 데이터가 어긋나 있을 수 있다. 되돌리기는 배포 상태를 고치는 수단이지 데이터를 고치는 수단이 아니다.

GitHub 사례는 이 차이를 보여 준다. 장애 시점에 미국 동부와 서부 데이터베이스에 서로 다른 쓰기가 남았고, 서부는 약 40분 동안 애플리케이션 쓰기를 받았다. 단순히 한쪽으로 되돌리는 것으로 끝나지 않았다. GitHub는 데이터 무결성을 복구 시간과 사용성보다 우선했고, 대륙 간 호출 지연 때문에 많은 사용자가 서비스를 쓰기 어려웠다.

또 하나 구분할 것이 있다. 진행 실패를 감지하는 것과 자동으로 되돌아가는 것은 다르다. Kubernetes는 멈춘 Deployment에 `ProgressDeadlineExceeded` 조건을 보고할 뿐이고, 되돌리기 같은 조치는 상위 오케스트레이터가 맡는다. paused 상태의 Deployment는 resume 전까지 되돌릴 수 없다는 제약도 있다.

## 복구 판단 체크리스트

- [ ] 되돌리기 대상이 Pod template인지 데이터인지 구분했는가
- [ ] 되돌릴 revision이 남아 있는가 (`.spec.revisionHistoryLimit`이 0이 아닌가)
- [ ] Deployment가 paused 상태가 아닌가
- [ ] 되돌린 뒤 데이터 정합성을 따로 확인할 계획이 있는가
- [ ] 되돌리기로 해결되지 않을 때의 다음 수단을 정했는가

## 후속 개선 제안

아래는 자료를 읽고 정리한 제안이며 실제 담당자·기한·성과가 아니다. 완료 여부는 각 항목의 확인 기준으로 판단한다.

| 제안 | 담당 역할 | 우선순위 | 완료 확인 기준 |
|---|---|---|---|
| 배포 롤백과 데이터 복구를 다른 절차로 문서화 | 릴리스 담당 | 높음 | 두 절차가 각각 런북에 존재 |
| 전체 클러스터 재구축 리허설 수행 | 인프라 담당 | 높음 | 리허설 1회 수행 기록 존재 |
| 되돌리기 후 데이터 정합성 점검 항목 추가 | 서비스 담당 | 중간 | 체크리스트에 항목 반영 |
| 백업 복구 소요 시간 측정 | 인프라 담당 | 중간 | 측정값 기록 존재 |
