# 매번 같은 규칙을 설명하지 않으려면: 저장소에 무엇을 적어야 할까

## 문제: 규칙이 저장소 밖에 있다

AI 코딩 도구를 팀 저장소에 들이면 첫 주에 같은 대화를 반복하게 된다. 빌드 명령, 테스트 실행 순서, 손대면 안 되는 디렉터리, 커밋 전 확인 절차를 매번 다시 설명한다. 도구가 부족해서가 아니라 그 규칙이 저장소 안에 적혀 있지 않기 때문이다. 설명을 반복하는 비용은 두 번 지불된다. 사람이 타이핑하는 시간이 먼저 들고, 규칙이 조금씩 다르게 전달되어 결과물이 달라지는 비용이 나중에 든다.

사람에게는 온보딩 문서와 코드 리뷰가 이 역할을 한다. AI 도구에는 지침 파일이 같은 역할을 하되, 요청마다 자동으로 참조된다는 점이 다르다. 그래서 물음은 "무엇을 적을까"보다 "어디에 적을까"가 먼저다. 규칙마다 적용 범위가 다르고, 적용 범위가 다르면 두는 위치도 달라야 한다.

## 규칙을 둘 위치: 세 가지 지침

GitHub Copilot 문서는 저장소 지침을 세 종류로 나눈다. 아래 표는 그 문서가 설명하는 구분이다. 다른 AI 도구가 같은 파일 이름과 위치를 똑같이 지원한다는 보장은 아니므로, 도구를 고를 때는 해당 도구의 문서를 따로 확인해야 한다.

| 지침 종류 | 두는 위치 | 적용 범위 | 함께 적용될 때 |
|---|---|---|---|
| 저장소 공통 지침 | `.github/copilot-instructions.md` | 저장소 맥락의 모든 요청 | 저장소당 하나 |
| 경로별 지침 | `.github/instructions/` 아래 `NAME.instructions.md` | `applyTo` 글롭과 일치하는 파일을 다루는 요청 | 공통 지침이 있으면 둘 다 사용 |
| 에이전트 지침 | 저장소 어디든 `AGENTS.md` | AI 에이전트 작업 | 디렉터리 트리에서 가장 가까운 파일이 우선 |

경로별 지침은 파일 이름이 `.instructions.md`로 끝나야 하고, 머리말 블록에 `applyTo` 글롭을 적는다. 여러 패턴은 쉼표로 구분한다. 특정 기능에는 읽히지 않게 하려면 머리말에 `excludeAgent`를 넣는다. 다만 경로별 지침은 쓸 수 있는 기능이 제한적이라는 점도 함께 봐야 한다.

에이전트 지침은 성격이 다르다. 저장소 전체에 하나만 두는 공통 지침과 달리 여러 개를 둘 수 있고, 작업 중인 파일에서 디렉터리 트리를 따라 가장 가까운 파일이 우선한다. 그래서 "루트에는 공통 규칙, 특정 모듈에는 그 모듈의 규칙"처럼 층을 나누기에 적합하다.

## 짧은 저장소 공통 지침 예시

아래는 형식을 보여 주기 위한 교육용 예시다. 이 저장소의 실제 설정이 아니며, 명령 이름과 순서는 팀이 직접 확인한 값으로 바꿔 넣어야 한다. 확인하지 않은 명령을 검증 완료라고 적으면 안 된다.

```markdown
프로젝트 개요
- 사내 결제 API를 제공하는 서비스다. 진입점은 src/server.js, 테스트는 test/ 아래에 있다.
- 런타임 버전은 .tool-versions에 고정한다.

검증 절차
- 변경을 올리기 전에 아래 순서를 지킨다.
  1. 의존성 설치
  2. 린트
  3. 단위 테스트
  4. 변경한 경로에 해당하는 통합 테스트

변경 범위
- 마이그레이션 파일은 승인 없이 수정하지 않는다.
- 생성된 코드는 직접 편집하지 않는다.
- 공개 API 응답 형식을 바꾸면 변경 이력을 남긴다.
```

세 부분이 모두 들어가야 한다. 프로젝트 개요는 탐색 시간을 줄이고, 검증 절차는 실패한 빌드를 줄이며, 변경 범위는 되돌리기 어려운 수정을 막는다. 검증 절차를 적을 때는 "테스트를 돌린다" 같은 문장 대신 실행 순서와 선행 조건을 적어야 한다. 순서가 있는 절차는 번호 목록으로, 서로 독립적인 항목은 목록으로 나눈다. 지침 사이의 공백은 무시되므로 한 줄씩 쓰든 빈 줄로 나누든 내용은 같다.

## 적용 확인: 참조와 준수는 다르다

지침 파일은 저장하면 바로 쓰인다. 요청마다 자동으로 붙고, 채팅 응답 위쪽의 참조 목록을 펼치면 지침 파일이 올라와 있는지 확인할 수 있다. 도구가 지침을 읽었는지 확인하는 가장 간단한 방법이다.

여기서 한 가지를 구분해야 한다. 참조되었다는 사실은 준수를 보장하지 않는다. 참조 목록에 파일이 보여도 모델이 그 규칙을 모두 따랐다는 뜻은 아니다. 여러 종류의 지침이 동시에 적용될 수 있고, 개인 지침이 저장소 지침보다 우선하며, 그다음이 조직 지침 순서다. 서로 충돌하는 지침을 함께 두면 응답 품질이 떨어진다. 결국 준수 여부는 참조 목록이 아니라 결과물을 검토해야 알 수 있다.

## 도입 체크리스트와 한계

도입할 때 확인할 항목은 다섯 개면 충분하다.

- [ ] 저장소 전체에 해당하는 규칙과 경로별로 다른 규칙을 구분했는가
- [ ] 지침에 적은 빌드·테스트 명령을 실제로 한 번 실행해 확인했는가
- [ ] 서로 충돌하는 지침이 없는가
- [ ] 지침 파일이 답변의 참조 목록에 실제로 나타나는가
- [ ] 지침을 바꾼 뒤 결과물이 달라졌는지 확인했는가

한계도 분명하다. 지침은 요청에서 차지하는 몫이 있으므로 길수록 유리하지 않다. 도구별 지원 범위가 다르고, 경로별 지침은 쓸 수 있는 기능이 제한적이다. 다만 지침 파일은 코드 리뷰에서 병합 대상 브랜치가 아니라 변경 브랜치에서 읽히므로, 지침 수정을 같은 방식으로 시험해 볼 수 있다는 점은 장점이다.

## 무엇부터 분리할까

결론은 하나다. 빌드와 테스트처럼 실패가 곧바로 드러나는 규칙부터 저장소 공통 지침으로 옮긴다. 그다음 디렉터리마다 다른 규칙을 경로별 지침으로 분리하고, 에이전트 전용 작업 방식은 에이전트 지침에 남긴다. 처음부터 완성본을 쓰려 하지 말고, 반복해서 설명하던 문장 하나를 옮기는 데서 시작하면 된다. 한 번 옮겨 둔 규칙은 다음 사람과 다음 도구가 다시 묻지 않는다.
