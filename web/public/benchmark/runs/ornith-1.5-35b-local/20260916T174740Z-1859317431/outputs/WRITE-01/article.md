# 작업 규칙을 저장소에 담아두기: 매번 설명하지 않는 방법

코드를 작성하거나 수정할 때마다 같은 내용을 반복해 설명하다 보면 시간은 물론 집중력도 떨어진다. 새로운 참여자가 오면 다시 처음부터 설명해야 하고, 이전 대화의 맥락은 언제나 놓친다. 이 문제는 사람이든 에이전트든 마찬가지다. 답은 사람을 다시 부르지 않고도 맥락을 전하는 데 있다. 저장소 안에 작업 규칙을 넣어두는 것이다.

## 규칙을 둘 위치 고르기

하나의 저장소에 모든 요청이 같은 맥락으로 처리되길 바란다면, 저장소 전체에 적용되는 공통 지침이 필요하다. 보통은 `.github` 디렉터리에 `copilot-instructions.md` 파일을 놓는다. 저장소 상단에서 한 번만 정해두면, 그 저장소를 대상으로 하는 모든 요청에 자동으로 반영된다.

특정 종류 파일만 따로 다뤄야 한다면 이야기가 달라진다. 예를 들어 테스트 코드와 프로덕션 코드는 요구하는 규칙이 확연히 다르다. 이런 때는 `.github/instructions` 디렉터리에 `NAME.instructions.md` 파일을 만들고, 파일 상단에 `applyTo`로 적용 대상을 지정한다. 여기에 글로브 문법을 쓰면 된다. 파일명은 반드시 `.instructions.md`로 끝나야 한다.

경로 지정 파일은 작업 중인 파일의 경로가 일치할 때만 적용된다. 예를 들어 TypeScript 파일 전체에 한해 특정 규칙을 걸려면 `applyTo`에 해당 확장자를 여러 개 나열한다. 특정 하위 디렉터리에만 적용하려면 경로 앞에 디렉터리 이름을 붙인다. 원하면 특정 에이전트나 기능에만 적용 범위를 좁힐 수도 있다. frontmatter에 `excludeAgent`를 넣어 cloud agent나 code review 중 하나를 제외할 수 있다. 이를 붙이지 않으면 두 기능 모두 지침을 사용한다.

이런 경로 지정 파일은 공통 지침과 만났을 때 함께 동작한다. 저장소 공통 지침 파일도 함께 있으면 두 파일의 내용을 모두 사용한다. 둘이 서로 떨어지지 않고 합쳐진다는 뜻이다.

에이전트를 대상으로 한 지침은 좀 더 유연하다. `AGENTS.md` 파일을 저장소 안 어디에든 둘 수 있고, 에이전트가 작업을 시작할 때 디렉터리 트리상 가장 가까운 `AGENTS.md`가 우선권을 가진다. 저장소 루트에 `CLAUDE.md`나 `GEMINI.md` 하나를 두는 방식도 가능하다.

이렇게 세 유형의 지침을 두면 저장소 요청에 맥락이 자동으로 붙는다. 실제 동작하는지 확인하고 싶다면 대화형 도구에서 지침 파일을 담은 저장소를 첨부해 대화를 시작하면 된다. 그러면 지침이 응답에 참조로 붙어 나온다. 참고 목록을 펼쳐 지침 파일이 보이는지 보면 된다.

## 교육용 예시: 짧은 공통 지침

아래 내용은 실제 저장소를 대신하지 않는 교육용 예시다. 실제 저장소 파일이 아니라 참고용으로 쓴 짧은 문단이다.

```markdown
이 저장소는 소규모 웹 서비스다.

- 메인 언어는 TypeScript고, 실행 환경은 Node.js 20을 쓴다.
- 변경을 넣기 전에 항상 `npm install` 후 `npm test`를 먼저 돈다.
- 로컬 변경 전 `git stash`로 작업 상태를 정리한다.
- 주석은 코드 목적을 설명하는 용도로만 쓴다.
```

이런 짧은 문단 몇 개만으로도 새 맥락이 크게 달라진다. 파일을 하나 만들면 그 내용이 저장소 전체 요청에 자동으로 붙는다.

## 참조로 나타나는 것과 준수하는 것의 차이

규칙을 넣었다 해서 반드시 지켜진다는 보장은 없다. 저장소에 파일을 넣으면 그 내용은 저장소를 대상으로 하는 요청에 자동으로 추가된다. 하지만 그것이 응답에 반영돼 있다는 증거는 따로 확인해야 한다.

예를 들어 대화형 도구에서는 지침 파일이 참조 목록에 나오는지로 알 수 있다. 응답 상단의 참조 목록을 펼치고, 지침 파일이 거기 포함되어 있는지 확인하는 방식이다. 참조로 나타났다는 것과 실제 그 지침을 준수했다는 것은 같은 말이 아니다.

우선순위도 함께 생각해둘 일이다. 여러 지침이 동시에 적용될 수 있는데, 보통 개인 지침이 가장 높고 저장소 지침이 그 다음, 조직 지침이 마지막이다. 서로 다른 지침이 충돌하면 품질이 흔들릴 수 있으니, 충돌하는 지침은 피하는 게 좋다.

지침을 처음부터 직접 쓰기가 부담스럽다면, 저장소를 스캔하게 해 만든 뒤 그 내용을 검토하는 방법도 있다. 이때는 문서 길이를 2 페이지 안으로 제한하는 등 기본적인 틀을 함께 지정하면 좋다. 만든 뒤에도 실제 저장소에 반영됐는지 다시 한 번 살펴봐야 한다.

또한 지침은 파일을 저장하는 순간 사용 가능해진다. 하지만 특정 기능에서는 기본적으로 켜져 있어도 별도로 끌 수 있다. 예를 들어 코드 리뷰 기능은 기본적으로 켜져 있지만, 저장소 설정에서 끌 수 있다.

## 시작 전 확인할 체크리스트

- 공통 지침은 `.github/copilot-instructions.md`에 놓았는가.
- 경로별 지침은 `.github/instructions` 아래에 두고 `applyTo`로 대상을 지정했는가.
- 에이전트 지침이 필요하면 `AGENTS.md`를 원하는 위치에 두었는가.
- 지침이 참조 목록에 나오는지, 우선순위는 어떤 순서인지 확인했는가.
- 충돌할 수 있는 중복 지침은 없는지 살폈는가.

## 한계와 결론

이 방식의 한계도 분명하다. 규칙을 넣었다고 모든 요청이 자동으로 준수되는 것은 아니다. 참조로 나타났는지 따로 확인해야 하고, 우선순위와 기능별 기본 설정까지 고려해야 한다. 또한 지침은 저장소를 대상으로 한 요청에 국한된다. 저장소 바깥 맥락이나 도구 자체의 설정은 별개다.

그래도 방향은 명확하다. 매번 반복하는 설명을 저장소 안에 담아두면 맥락이 사라지지 않는다. 공통 지침으로 시작하고, 필요하면 경로별·에이전트 지침으로 세부화한다. 넣은 뒤는 참조 목록과 우선순위로 확인한다. 이 한 번의 작업이 다음부터의 모든 요청을 가볍게 만든다.
