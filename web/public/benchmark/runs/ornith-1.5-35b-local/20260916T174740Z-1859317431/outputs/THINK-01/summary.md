# 장애 복구 판단 메모 — 되돌리기 명령이 안전한 복구를 보장하지 않는다

두 입력 자료는 서로 다른 시스템을 설명한다. `deployment.md`는 배포 롤백의 공식 문서이고, `incident.md`는 GitHub 자체 발행 데이터베이스 장애 브리프다. “되돌리기 명령이 있다는 사실만으로 안전한 복구가 보장되는가?”에 답한다. 한쪽으로 다른 쪽 근거를 옮겨 붙이면 안 된다.

## 결론

결론부터 말하면 보장하지 않는다. 되돌리기 명령의 존재는 복구 절차의 가능성을 알릴 뿐, 데이터를 안전하게 되돌렸다는 보장을 주지 않는다. Kubernetes에서는 롤백이 Pod 템플릿의 Revision만 되돌리고 애플리케이션이 쓴 데이터는 복원하지 않는다. GitHub 10월 21일 장애는 이 데이터 정합성 문제로 맞부딪쳤다. 단순히 한쪽으로 되돌리면 별도로 쓴 쓰기가 사라져 복구가 성립하지 않는다.

또한 이 GitHub 장애를 Kubernetes Deployment로 돌릴 근거도 없다. `incident.md`는 GitHub가 Kubernetes Deployment를 사용했다고 명시하지 않는다. 데이터베이스 백업 복원과 대륙 간 복제는 Kubernetes 롤백과 다른 절차다. 두 시스템을 같은 사건으로 섞으면 복구 판단이 왜곡된다.

## 배포 복구와 데이터 정합성

Kubernetes 롤백의 한계를 먼저 짚는다. Deployment Revision은 Pod 템플릿(`.spec.template`)이 바뀔 때만 생성되고, 복제본 수를 조절하는 스케일링은 Revision을 만들지 않는다. 따라서 롤백이 되돌리는 것은 오직 Pod 템플릿 부분이고 애플리케이션 데이터는 건드리지 않는다. “`kubectl rollout undo`가 있으니 데이터도 함께 돌아갈 것”이라는 추정은 문서 내용과 맞지 않는다.

상태 조건도 자동 복구가 아니다. `progressDeadlineSeconds`를 넘겨 `ProgressDeadlineExceeded` 조건이 뜨면 Kubernetes는 그 조건을 보고 끝낸다. 실제 롤백은 더 높은 오케스트레이터가 판단해 수행한다. rollback 경로가 막힌 경우도 있다. `revisionHistoryLimit`을 0으로 하면 역사가 전부 정리돼 롤백이 불가능해진다. 롤아웃을 일시중지한 상태에서는 먼저 재개하기 전까지 롤백할 수 없다.

이것들은 모두 “명령이 있다”와 “복구가 안전하다”는 다른 문제라는 점을 보여준다.

## 복구 체크리스트

- [ ] 되돌리기 전에 현재 Revision과 백업 시점을 확인한다
- [ ] 롤백이 Pod 템플릿만 되돌린다는 점을 분명히 하고, 애플리케이션 데이터는 별도 절차로 복구한다
- [ ] `revisionHistoryLimit`이 0은 아닌지, 되돌릴 이전 ReplicaSet이 남아있는지 확인한다
- [ ] 롤아웃이 일시중지되어 있으면 먼저 재개한다
- [ ] `ProgressDeadlineExceeded`는 조건일 뿐이므로 더 높은 오케스트레이터의 행동을 따로 확인한다
- [ ] 데이터베이스 사건이면 데이터베이스 백업 복원 절차로 접근하고, Kubernetes 롤백과 섞지 않는다
- [ ] 복구 후 사용성·지연·복제 동기화 상태를 재확인한다
