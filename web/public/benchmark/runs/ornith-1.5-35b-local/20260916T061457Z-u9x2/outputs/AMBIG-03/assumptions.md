# AMBIG-03 assumptions — 재시도 정책 명세서 구현 근거

- case_version: v0.5-character-1
- 과제: `export async function fetchWithPolicy(fn)` 구현 + 판단 근거 문서화
- 고정 입력: `cases/v0.5-character/input/ambig03-spec.md` (v2.3, SHA-256 `f5829aec…9625`)

명세서를 그대로 따른다. 그중 §3("최대 3회 시도")과 §7("일시 오류는 성공할 때까지 재시도")는 **의도적으로 모순**된다. 아래는 그 밖의 누락·모순 부분에 내린 판단과 근거다.

## 1. §3과 §7 모순 해결: "최대 3회"를 우선하되 5초 한도는 안전장치로 병용
- **판단**: 일시 오류 재시도는 **최대 3회(초시도 포함)**를 원칙로 하되, §7의 "최대 대기 총합 5초 초과"가 우선하면 그 전에 중단한다. §7의 "성공할 때까지 재시도"는 3회 한도·5초 한도 안에서 해석한다.
- **근거**: 출제자 메모에 "명세의 누락·모순이 의도적"이라고 명시되어, 모순을 그대로 두지 않고 판단으로 정리해야 한다. 구체적 규칙(3회)이 일반적 진술("성공할 때까지")보다 우선한다는 해석 관례(특수·일반 → 특수 우선)를 따른다. 동시에 §7의 5초 한도는 안전상한으로 남겨 둘 적용한다.
- **참고**: 3회 재시도의 백오프 대기(200+400=600ms)는 5초를 훨씬 밑돕으므로, 실제 실행에서는 5초 한도가 먼저 닿지 않는다. 5초 한도는 maxAttempts를 크게 잡은 경우에에만 실 동작으로 드러난다.

## 2. 일시/영구 분류는 HTTP 상태코드로
- **판단**: `fn`이 던지는 오류의 `status`로 분류한다. `status≥500`·`429`·상태 없는 오류(네트워크/타임아웃)는 일시(재시도), `401`·`403`·`429` 외의 `4xx`는 영구(재시도 안 함).
- **근거**: §2가 용어를 상태코드 수준으로 정의한다("5xx 응답", "401/403", "4xx 중 429 제외"). 상태코드로 판단하는 것이 명세 용어에 가장 직접적으로 맞는다.
- **429 처리**: §2는 영구를 "4xx 중 429 제외"로 정의하므로 429는 영구가 아니라 일시로 재시도한다. 명시적 제외이므로 우선 적용.

## 3. 백오프: 첫 200ms, 2배 증가, 2000ms 상한, 지터 없음 (§4)
- **판단**: `200·2^(n-1)`, 2000ms 상한. 지터 기본 off.
- **근거**: §4가 수치를 명시한다. 지터는 "사용하지 않는다"로 쓰였으나 기본 off로 하고 옵션으로만 제공(명세의 문자적 요구 준수 + 유연성).

## 4. 멱등 키는 래퍼가 생성해 모든 시도에 동일 전달 (§5)
- **판단**: `fetchWithPolicy` 호출 1회당 멱등 키 1개를 생성하고, 재시도마다 **같은 키**를 `fn({ idempotencyKey })`로 전달.
- **근거**: §5는 "재시도 대상 호출은 반드시 멱등 키를 포함"하고 "같은 주문의 재시도는 새 결제를 만들지 않는다"고 한다. 같은 키 재사용이 요구사항이다. 키 생성 책임은 래퍼가 가져서 재시도 일관성을 보장한다.

## 5. 관측: 재시도는 로그, 최종 실패는 exhausted 이벤트 (§6)
- **판단**: 각 재시도는 `onRetry(attempt, reason)`로 `retry.attempt`·`retry.reason`을 남기고, 최종 실패(영구 오류 포함)는 `onExhausted(error)`로 `retry.exhausted`를 발행한다.
- **근거**: §6이 재시도 로그와 최종 실패 이벤트를 구분한다. 영구 오류도 "최봉 실패"이므로 exhausted를 발행한다. 기본 구현은 콘솔 발행으로 대체(이벤트 소스는 주입 가능).

## 6. 시그니처는 `fetchWithPolicy(fn)` 유지, 튜닝은 두 번째 옵션으로
- **판단**: 핵심 시그니처 `fetchWithPolicy(fn)`을 그대로 두고, `maxAttempts`·`backoffBase`·`backoffCap`·`jitter`·`maxTotalWaitMs`·`idempotencyKey`·`sleep`·`classify`·`onRetry`·`onExhausted`를 options로 주입 가능하게 한다.
- **근거**: 과제 시그니처를 준수하면서, 명세의 수치적 요구를 기본값으로 넣고 테스트용 훅(sleep, onRetry, onExhausted)를 뒷걸림 없이 제공한다.

## 확인하지 않은 것
- **실제 네트워크 지연**: 주입한 `sleep`으로 백오프·5초 한만 검증. 실시간 setTimeout 대기 미검증.
- **한도 초과(429 외)의 상태코드**: §2의 "한도 초과"가 어떤 코드로 오는지 불명확. 429만 일시로 명시 처리, 다른 한도 오류는 상태코드에 따라 분류에 위임.
- **정산 배치 작업 예외 (§8)**: 이 정책의 적용 제외 항목이지만 `fetchWithPolicy` 구현 범위外的. 별도 스케줄러가 관리하므로 다루지 않았다.
- **`retry.exhausted`의 실제 이벤트 소스(이미터 등)**: 기본은 콘솔. 실제 시스템 이벤트 발행처는 주입 의존.
