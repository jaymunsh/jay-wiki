# 매번 설명하지 않는 저장소: AI 코딩 도구에 작업 규칙을 적는 법

팀에 AI 코딩 도구가 들어오면 같은 설명이 반복된다. 빌드 전에 무엇을 깔아야 하는지, 테스트는 어떤 순서로 도는지, 이 디렉터리의 코드는 어떤 약속을 따르는지 매번 채팅으로 알려준다. 설명이 사람마다 조금씩 달라서 도구가 엉뚱한 명령을 돌리기도 한다. 답은 작업 규칙을 저장소 안 문서로 옮기는 것이다. 한 번 적어 두면 도구가 매 요청에 그 문서를 읽는다.

## 세 종류의 지침을 한 표로 이해한다

[GitHub 공식 문서](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/add-custom-instructions/add-repository-instructions)는 저장소 지침을 세 종류로 나눈다. 역할과 두는 곳, 적용 범위가 다르므로 고르기 전에 표로 정리한다.

| 종류 | 두는 곳 | 적용 범위 |
|---|---|---|
| 저장소 공통 지침 | `.github/copilot-instructions.md` | 저장소 안 모든 요청 |
| 경로별 지침 | `.github/instructions` 아래 `이름.instructions.md` | 경로가 맞는 파일 작업에만 |
| 에이전트 지침 | 저장소 안 어디든 `AGENTS.md` | AI 에이전트 작업, 가까운 파일 우선 |

경로별 지침 파일은 맨 앞에 `applyTo`를 적어 glob으로 대상을 정한다. 저장소 공통 지침과 경로별 지침이 함께 맞으면 두 문서가 같이 쓰인다. 에이전트 지침은 디렉터리 트리에서 가장 가까운 파일이 우선하고, 루트의 `CLAUDE.md`나 `GEMINI.md`를 대신 쓸 수도 있다. 제품별 지원 범위를 모든 AI 도구의 공통 보장으로 넓혀 읽지 않는다. 경로별 지침은 GitHub.com에서 클라우드 에이전트와 코드 리뷰에만 지원된다는 제약을 먼저 확인한다.

## 규칙을 둘 위치를 고른다

기준은 간단하다. 저장소 전체에 통하는 약속은 공통 지침에, 특정 디렉터리에만 통하는 약속은 경로별 지침에, 에이전트의 작업 방식 자체는 에이전트 지침에 둔다. 예를 들어 빌드·테스트·검증 절차와 변경 범위는 공통 지침에 적는다. 결제 모듈처럼 별도 규칙이 있는 디렉터리는 경로별 지침으로 분리한다. 서로 겹치는 내용을 두 곳에 복사하지 않는다. 겹치면 나중에 한쪽만 고쳐서 어긋난다. 여러 지침이 한 요청에 같이 적용될 수 있고, 개인 지침이 가장 우선하고 저장소 지침이 다음이며 조직 지침이 마지막이라는 순서도 알아둔다. 충돌이 걱정되면 지침을 끄고 품질을 비교해 본다.

## 작은 공통 지침 예시를 쓴다

아래는 교육용 예시이며 실제 이 저장소의 설정이 아니다. 프로젝트 개요와 검증 절차, 변경 범위가 드러나도록 짧게 쓴다. 빌드 명령은 확인하지 않았으므로 검증 완료라고 쓰지 않는다.

```markdown
**프로젝트 개요**
이 저장소는 주문 관리 웹 API이다. Python 3.12를 사용한다.

**검증 절차**
1. 의존성을 설치한다.
2. 단위 테스트를 실행한다.
3. 린터를 실행한다.

**변경 범위**
- API 동작을 바꾸는 변경은 `api/`와 테스트를 함께 고친다.
- 스키마 변경은 마이그레이션 파일을 포함한다.
- 항상 테스트를 먼저 돌리고 실패하면 빌드 문제를 의심한다.
```

예시가 길어지면 도구가 다 읽지 않거나 중요한 줄을 놓친다. 생성 도구 기준으로 2페이지를 넘지 않고 특정 작업 전용 내용을 넣지 않는다는 제한을 참고한다. 공백은 무시되므로 가독성을 위해 빈 줄로 나눈다.

## 참고됐는지 확인하고 준수를 구분한다

채팅 응답 위의 참조 목록을 펼쳐 지침 파일이 들어 있는지 본다. 파일이 참조에 나타나면 도구가 읽었다는 뜻이다. 그러나 읽었다는 것과 지켰다는 것은 다르다. 참조는 입력에 포함됐다는 기록일 뿐, 답이 규칙을 따랐는지는 사람이 본문에서 확인한다. 코드 리뷰는 기본적으로 지침을 사용하며 저장소 설정에서 끌 수 있다. 리뷰할 때는 base 브랜치가 아니라 변경이 담긴 head 브랜치의 지침을 읽으므로, 지침 수정과 코드 수정을 같은 풀 리퀘스트에서 함께 시험할 수 있다.

## 도입 체크리스트와 한계를 남긴다

- [ ] 공통 지침에 개요·검증 절차·변경 범위를 적었는가
- [ ] 경로별 지침의 `applyTo`가 의도한 파일에만 맞는가
- [ ] 채팅 참조 목록에 지침 파일이 나타나는가
- [ ] 규칙을 어긴 답이 나오면 지침 문장을 고쳤는가
- [ ] 특정 도구의 제약(경로별 지침 지원 범위 등)을 팀에 공유했는가

한계도 적어 둔다. 지침은 보장서가 아니라 입력이다. 도구가 지침과 다른 답을 낼 수 있고, 개인 지침이 저장소 지침보다 우선한다. 제품별 지원 내용은 그 제품에서만 확인된 사실로 둔다.

공통 지침부터 분리한다. 검증 절차와 변경 범위처럼 매번 반복되는 설명을 먼저 옮기면 효과가 바로 보인다. 다음으로 규칙이 다른 디렉터리만 경로별 지침으로 떼어낸다. 이 순서면 설명 반복이 줄고, 남은 어긋남은 지침 문장을 고치는 일로 바뀐다.
