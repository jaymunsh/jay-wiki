# 되돌리기 명령이 있어도 복구는 판단이 필요하다

결론부터 적는다. 되돌리기 명령이 있다는 사실만으로 안전한 복구가 보장되지 않는다. Kubernetes의 롤백은 Pod 템플릿만 되돌리고, GitHub 사례는 데이터 정합성을 지키느라 복구에 오랜 시간이 걸렸다. 복구 수단은 명령의 존재가 아니라 상태 확인과 판단으로 완성된다. 아래는 장애 대응 회의에서 읽는 판단 메모이며, 후속 조치는 제안이다.

## 실제 사례 타임라인으로 본다

GitHub의 2018년 10월 장애 브리프를 UTC로 정리한다. 이 사례가 Kubernetes로 운영됐다는 근거는 자료에 없으므로, 두 시스템을 같은 사건으로 섞지 않는다.

| 시각(UTC) | 일어난 일 |
|---|---|
| 10월 21일 23:19 | 추가 쓰기를 줄이려고 webhook 전달과 Pages 빌드를 멈춤 |
| 10월 22일 00:05 | 백업 복원·복제본 동기화·토폴로지 복귀·대기 작업 재개 계획 수립 |
| 10월 22일 00:41 | 영향받은 MySQL 클러스터 백업 절차 진행 중 관찰 |
| 10월 22일 06:51 | 일부 동부 클러스터 복원 완료 후 서부 새 데이터 복제 시작, 큰 클러스터는 복원 중 |

동부와 서부 데이터베이스에 서로 다른 쓰기가 남아 단순히 한쪽으로 되돌릴 수 없는 상태였다. 서부는 약 40분 동안 애플리케이션 쓰기를 받았고, 동부에도 복제되지 않은 수초 분량의 쓰기가 있었다. GitHub는 데이터 무결성을 복구 시간과 사용성보다 우선했고, 대륙 간 호출 지연으로 많은 사용자가 불편을 겪었다. 백업은 4시간마다 만들어 원격 저장소에 있었고, 테라바이트급 전송·압축 해제·체크섬·준비·적재에 시간이 필요했다. 복구 절차는 최소 매일 시험했지만 전체 클러스터를 백업에서 완전히 재구축한 것은 처음이었다.

## 배포 상태 복구와 데이터 정합성은 다르다

Kubernetes Deployment의 롤백은 Pod 템플릿 부분만 되돌린다. 리비전은 템플릿이 바뀔 때만 생기고, 스케일 변경은 리비전을 만들지 않는다. 이력 보관 제한을 0으로 두면 롤백할 수 없고, 멈춘 Deployment는 resume하기 전에는 되돌릴 수 없다. 기한을 넘긴 진행 실패는 상태로 보고될 뿐 자동 롤백이 일어나지 않는다. 즉 Deployment 롤백은 배포 상태(어떤 Pod 템플릿이 도는가)를 되돌리는 수단이며, 데이터베이스 쓰기까지 이전 상태로 복원하지 않는다. GitHub 사례처럼 쓰기가 엇갈린 상황에서는 되돌리기 명령 하나로 끝날 일이 아니다. 정합성 판단이 먼저이고, 명령은 그 다음이다.

## 복구 판단 체크리스트

- [ ] 지금 멈춘 것이 새 Pod인지, 기존 Pod도 영향받는지 확인했는가
- [ ] 돌아갈 리비전이 이력에 남아 있는지, 보관 제한을 확인했는가
- [ ] 되돌리기가 Pod 템플릿만 되돌린다는 점을 전제로 판단했는가
- [ ] 데이터 정합성 문제를 배포 롤백으로 덮으려 하지 않는가
- [ ] 되돌린 뒤 복제본 숫자와 조건을 숫자로 확인했는가
- [ ] 멈춤 상태라면 resume을 먼저 고려했는가

## 후속 개선 제안

아래는 제안이며 확정된 담당자·기한·성과가 아니다. 완료 기준만 적는다.

| 제안 | 우선순위 | 역할 | 완료 기준 |
|---|---|---|---|
| 변경 사유 기록 남기기 | 높음 | 릴리스 담당 | 이력에서 변경 내용을 알 수 있음 |
| 보관 제한 값 점검 | 높음 | 플랫폼 담당 | 롤백 가능 세대 수가 문서화됨 |
| 전체 복구 훈련 | 중간 | 대응 팀 | 백업에서 재구축을 끝까지 해봄 |
| 기한 초과 알림 연결 | 중간 | 관측 담당 | 상태 보고가 사람에게 닿음 |
