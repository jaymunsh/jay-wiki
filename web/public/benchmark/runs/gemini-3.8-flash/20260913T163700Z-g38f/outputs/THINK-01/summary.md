# 배포 복구 메커니즘과 데이터 정합성 보장의 한계: 장애 복구 의사결정 메모

## 1. 핵심 결론: 되돌리기 명령만으로 안전한 복구가 보장되지 않는 이유

시스템에 '되돌리기(롤백)' 명령이 있다는 사실이 안전하고 완전한 복구를 보장하지 않는다. Kubernetes Deployment 롤백(`kubectl rollout undo`)은 Pod 템플릿(이미지, 환경변수 등) 명세만 이전으로 되돌릴 뿐이며, 이미 데이터베이스나 스토리지에 기록된 데이터 불일치를 복원해주지 못한다.

또한 리비전 보관 한도(`revisionHistoryLimit`) 초과, 워크로드의 Paused 상태, 데드라인(`ProgressDeadlineExceeded`) 시의 자동 롤백 부재 등 컨트롤러 수준의 제약도 존재한다. 데이터 영속성을 수반하는 분산 시스템 장애에서는 단순 배포 롤백이 쓰기 분기를 심화시키거나 유실을 초래할 수 있으므로, 배포 롤백과 데이터 정합성 복구는 명확히 분리하여 판단해야 한다.

## 2. GitHub 장애 대응 타임라인 (UTC)

다음은 2018년 10월 21일 발생한 GitHub의 데이터베이스 분기 장애 대응 사례 요약이다. 본 사례는 Kubernetes와 무관한 별도의 데이터 인프라 장애이며, 단순 롤백이 불가했던 대표적인 분산 정합성 문제의 전형이다.

| 일시 (UTC) | 대응 단계 | 내용 및 운영 판단 |
| :--- | :--- | :--- |
| 10월 21일 23:19 | 쓰기 억제 | webhook 전달과 GitHub Pages 빌드를 일시 중지하여 불일치 확산 방지 |
| 10월 22일 00:05 | 계획 수립 | 백업 복원, 양쪽 복제본 동기화, 토폴로지 복귀 및 대기 작업 재개 계획 |
| 10월 22일 00:41 | 복원 진행 | 영향받은 MySQL 클러스터 백업 복원 절차 진행 관찰 |
| 10월 22일 06:51 | 복제 개시 | 일부 동부 클러스터 복원 완료 및 서부 새 데이터 복제 개시 (대형 클러스터는 복원 중) |

미국 동부와 서부 DB에 서로 다른 쓰기가 남았고, 서부가 약 40분간 쓰기를 받는 동안 동부에도 미복제 쓰기가 있었다. 단순히 동부로 되돌리면 서부의 쓰기가 유실되므로 단순 되돌리기는 불가했다. GitHub는 복구 시간이나 사용성보다 '데이터 무결성'을 최우선으로 선택했다.

## 3. 배포 상태 복구와 데이터 정합성의 차이

배포 도구의 복구와 데이터 계층의 정합성은 완전히 다른 영역이다.

1. **상태 복구의 국소성**: Deployment 롤백은 Pod 템플릿만 과거 ReplicaSet으로 치환한다. DB 스키마 변경이나 파괴적 데이터 쓰기가 발생한 경우, 앱 코드만 이전으로 내리면 스키마 비호환으로 2차 장애가 발생한다.
2. **컨트롤러 자동화의 한계**: Kubernetes는 진행 지연 시 `ProgressDeadlineExceeded` 조건만 기록할 뿐 자동 롤백하지 않는다. 감지와 복구 실행 사이에는 엔지니어의 판단이 개입된다.
3. **복구 소요 시간의 비대칭성**: 배포 롤백은 수십 초 내에 끝나지만, 테라바이트급 DB 백업 복원은 매일 시험했더라도 원격 전송, 압축 해제, 체크섬, 적재로 수 시간이 걸릴 수 있다.

## 4. 복구 판단 체크리스트

장애 발생 시 롤백 전 다음 항목을 점검한다.

- `[ ]` **데이터 쓰기 분기 여부**: 잘못된 쓰기나 양방향 쓰기 분기가 발생했는가? (발생 시 즉시 비동기 쓰기 차단)
- `[ ]` **스키마 하위 호환성**: 배포를 이전 Pod 템플릿으로 되돌렸을 때 현재 DB 스키마와 호환되는가?
- `[ ]` **배포 상태 제약**: 대상이 Paused 상태가 아니며 대상 ReplicaSet이 남아 있는가?
- `[ ]` **우선순위 합의**: 가용성 즉시 재개와 데이터 무결성 보장 중 조직이 우선할 가치가 정의되었는가?
