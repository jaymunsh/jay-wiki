# AMBIG-02 판단 근거 문서 (assumptions.md)

본 문서는 `retry.mjs` 구현 과정에서 "외부 API 호출이 실패하면 재시도한다"라는 단 한 줄의 극도로 모호한 정책 명세에 대해 내린 기술적 의사결정과 판단 근거를 기술한다.

---

## 1. 최대 재시도 횟수(Max Retries)의 한도 설정

- **모호점**: 재시도 횟수 상한이 명시되지 않음.
- **판단**: **최대 재시도 횟수를 기본 3회(최초 시도 1회 + 재시도 3회 = 총 4회 실행)**로 제한하고, 옵션(`maxRetries`)으로 조정 가능하게 설계.
- **근거**: 무한 재시도는 API 서버 장애 시 클라이언트 스레드/이벤트루프를 점유하여 시스템 마비를 초래하고, 외부 서버에 재시도 폭풍(Retry Storm) 및 DoS 효과를 야기하므로 유한한 상한(산업 표준인 3회)이 반드시 필요함.

---

## 2. 지수 백오프(Exponential Backoff) 및 대기 시간

- **모호점**: 재시도 간의 시간 간격(대기 시간)이 명시되지 않음.
- **판단**: **초기 대기 100ms, 지수 백오프 계수 2(100ms -> 200ms -> 400ms)** 적용.
- **근거**: 즉각적인 재시도(Immediate retry)는 일시적인 네트워크 순단이나 서버 순간 부하를 완화하지 못하고 오히려 장애를 가중시킴. 지수 백오프를 통해 원격 서비스의 일시적 회복 시간을 확보함.

---

## 3. 재시도 대상 에러(Retryable)와 비재시도 에러의 분류

- **모호점**: 모든 에러에 대해 무조건 재시도할 것인지 여부.
- **판단**:
  1. 클라이언트 오류인 HTTP 4xx(400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found 등)는 재시도해도 성공할 가능성이 없으므로 **즉시 실패(Non-retryable)** 처리.
  2. 단, 클라이언트 오류 중 408(Request Timeout) 및 429(Too Many Requests)와 서버 오류인 5xx, 일반 네트워크 예외는 일시적 장애로 간주하여 **재시도 대상(Retryable)**으로 처리.
- **근거**: 잘못된 요청 본문이나 권한 부재로 인한 실패를 반복 호출하는 것은 무의미한 지연과 자원 낭비를 유발하기 때문임.

---

## 4. 최종 실패 시 예외 전파

- **모호점**: 재시도 횟수를 모두 소진했을 때의 반환값 또는 예외 형태.
- **판단**: 마지막 시도에서 발생한 원본 에러(`lastError`)를 그대로 `throw`하여 상위 호출자에게 전파.
- **근거**: 원본 에러의 스택 트레이스와 에러 메시지를 훼손하지 않아야 상위 애플리케이션에서 정확한 장애 원인 파악 및 로깅이 가능함.
