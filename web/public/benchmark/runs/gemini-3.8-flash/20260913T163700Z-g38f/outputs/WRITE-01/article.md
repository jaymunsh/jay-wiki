# AI 코딩 도구에 저장소 작업 규칙을 전달하는 실무 가이드: 반복 프롬프트에서 벗어나는 법

## 1. 매번 반복되는 규칙 설명이라는 병목

팀 저장소에 AI 코딩 도구를 도입할 때 개발자가 가장 먼저 겪는 피로는 매 대화마다 동일한 맥락을 반복 설명해야 한다는 점이다. "우리 팀은 탭 대신 공백 2칸을 쓴다", "API 응답 타입은 반드시 별도 파일에 선언한다", "커밋 전 특정 테스트를 실행해야 한다" 같은 기본 규칙을 매 요청에 붙여넣다 보면, AI 도구가 주는 생산성보다 맥락 전달 비용이 더 커진다.

이 문제를 해결하기 위해 현대 AI 코딩 도구는 대화창 바깥의 저장소 자체에 작업 규칙을 선언해두고, AI가 코드를 작성하거나 리뷰할 때 이를 자동으로 읽어 들이는 방식을 제공한다. 하지만 규칙을 무턱대고 적어둔다고 해서 모든 도구가 알아서 해석하는 것은 아니다. 규칙이 적용되는 범위와 위치, 각 파일 포맷의 특성을 정확히 이해하고 구조화해야 실질적인 협업 효율을 얻을 수 있다.

## 2. 작업 규칙을 둘 위치와 파일별 특성 비교

저장소 규칙을 정의할 때는 규칙의 영향 범위와 작업 주체에 맞춰 적절한 위치를 선택해야 한다.

| 구분 | 주요 대상 파일 경로 | 적용 대상 및 지원 범위 | 주요 특징 및 한계 |
|---|---|---|---|
| **저장소 공통 지침** | `.github/copilot-instructions.md` | 저장소 전체 작업 (채팅, 코드 생성 등) | 루트 기준 기본 지침으로 동작하며, 모든 요청에 자동으로 추가됨 |
| **경로별 지침** | `.github/instructions/NAME.instructions.md` | `applyTo` 글로브(glob)에 매칭되는 특정 경로 | 프론트매터로 대상 파일을 한정하며, 클라우드 에이전트 및 코드 리뷰 등 특정 환경에 적용됨 |
| **에이전트 지침** | `AGENTS.md` (또는 `CLAUDE.md`, `GEMINI.md`) | AI 코딩 에이전트 (자율 작업 도구) | 트리 상 가장 가까운 디렉터리의 파일이 우선하며, 도구 생태계별 지원 방식이 다름 |

주의할 점은 특정 플랫폼 문서의 설정 경로가 모든 AI 코딩 도구에서 동일하게 동작한다는 보장은 없다는 사실이다. 예컨대 `.github/copilot-instructions.md`는 특정 서비스 생태계의 표준 경로이며, 다른 도구는 `AGENTS.md`나 자체 설정 파일을 우선 탐색할 수 있다. 팀의 주력 도구 조합에 맞춰 기본 진입점을 구성해야 한다.

## 3. 저장소 공통 지침 작성 예시

저장소 공통 지침은 프로젝트 개요, 변경 범위, 검증 절차를 명확한 구조로 작성하는 것이 좋다. 다음은 교육용으로 구성한 가상의 공통 지침 예시다. (실제 운영 저장소의 설정이 아닌 이해를 돕기 위한 예시 구조다.)

```markdown
[프로젝트 공통 작업 지침 예시]
1. 프로젝트 개요
- 본 프로젝트는 TypeScript 기반 REST API 서비스입니다.
- 함수형 프로그래밍 스타일을 지향하며 불변성을 유지합니다.

2. 작업 및 변경 범위
- 신규 엔드포인트 추가 시 `src/routes/` 및 `src/controllers/` 하위만 수정합니다.
- 데이터베이스 스키마(`src/models/`)는 별도 승인 없이 변경하지 않습니다.

3. 검증 절차
- 코드 작성 후 타입 검사 및 단위 테스트를 통과해야 합니다.
- 실행 명령 예시: `npm run type-check`, `npm test`
- 주의: 확인되지 않은 빌드 명령을 검증 완료로 간주하지 마십시오.
```

지침 파일은 자연어 마크다운으로 작성되며, 지침 사이의 공백 줄바꿈은 모델 해석에 방해가 되지 않으므로 단락을 명확히 분리하는 것이 바람직하다.

## 4. 적용 확인 방법과 준수 보장의 간극

지침 파일을 저장소에 저장했다고 해서 작업이 끝난 것은 아니다. 실제로 AI 도구가 이 지침을 읽고 있는지 확인해야 한다.

Copilot Chat 환경에서는 답변 상단의 참고 자료(References) 목록을 펼쳐 `.github/copilot-instructions.md` 파일이 포함되어 있는지 확인할 수 있다. 지침 파일이 목록에 나타난다면 해당 문서가 프롬프트 컨텍스트에 정상 주입되었음을 뜻한다.

그러나 가장 중요한 기술적 사실은 **"참고되었다는 사실(Reference 포함)"과 "지침을 완벽히 준수한다는 것"은 별개의 문제**라는 점이다. LLM은 확률적으로 텍스트를 생성하므로 지침이 주입되더라도 복잡한 제약이나 상충 지시가 있으면 일부 규칙을 누락할 가능성이 항상 존재한다. 또한 개인 지침, 저장소 지침, 조직 지침 간 우선순위 충돌 시 의도와 다른 응답이 나올 수 있다. 지침 파일은 '강제 장치'가 아니라 '확률을 높이는 맥락 주입기'로 이해해야 한다.

## 5. 저장소 규칙 도입 체크리스트와 적용 한계

팀 저장소에 규칙 파일을 배포하기 전에 점검할 핵심 체크리스트는 다음과 같다.

- [ ] **단일 책임과 길이 통제**: 핵심 린트, 테스트, 아키텍처 원칙만 담았는가?
- [ ] **경로와 파일명 정확성**: 도구가 인식하는 올바른 위치(`.github/copilot-instructions.md` 또는 `AGENTS.md`)에 배치되었는가?
- [ ] **상충 지시 배제**: 개인 설정이나 다른 프롬프트와 충돌하는 표현이 없는가?
- [ ] **실제 검증 프로세스 연계**: 지침에 적힌 테스트 명령이 실제로 동작하는 최신 명령인가?

지침은 파일 접근 권한을 운영체제 수준에서 차단하지 못하며, 모델의 파괴적 변경을 완전히 막아주지 못한다. 엄격한 품질 통제는 CI 파이프라인의 자동화된 테스트와 린터에 맡겨야 한다.

## 6. 어떤 규칙부터 분리해야 하는가

규칙 파일을 처음 도입할 때 코딩 스타일부터 배포 정책까지 수백 줄을 한 번에 작성하면 모델의 주의 집중이 분산된다.

가장 먼저 분리할 규칙은 **"AI가 가장 자주 틀리는 프로젝트 고유 컨벤션 3가지"**다. 디렉터리 명명 규칙, 예외 처리 형식, 단위 테스트 실행 명령처럼 프로젝트마다 달라 실수를 유발하는 최소 규칙부터 공통 지침 파일에 단문으로 정리하는 것에서 출발해야 한다.
