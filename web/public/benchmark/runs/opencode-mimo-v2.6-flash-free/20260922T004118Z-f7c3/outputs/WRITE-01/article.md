# 매번 같은 작업 규칙을 설명하지 않으려면 저장소에 무엇을 적을까

AI 코딩 도구를 팀 저장소에 도입하면 가장 먼저 부딪히는 문제가 있다. "우리 팀은 이렇게 검증한다", "이 폴더는 건드리지 않는다" 같은 규칙을 매 대화마다 다시 설명해야 하는 것이다. 이 글은 저장소에 어떤 지침 파일을, 어느 위치에, 어떤 내용으로 적어야 이 반복을 줄일 수 있는지 정리한다. 판단 근거는 GitHub이 공개한 저장소 사용자 지침 문서를 기준으로 삼았다.

## 반복 설명이 비용이 되는 이유

지침이 대화 안에만 존재하면 다음 세션이나 다른 동료의 도구 사용에서는 그 규칙이 사라진다. 검증 순서를 몇 번이고 다시 말하게 되고, 도구는 검증 없이 제안을 내뱉기 쉽다. 반복되는 설명은 작성자에게도, 응답 품질의 일관성에도 비용이 된다. 그래서 규칙을 대화가 아니라 저장소 소유물로 옮기는 방향이 유효하다. 저장소에 고정된 지침은 저장 즉시 요청에 반영되며([사용 조건 확인](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/add-custom-instructions/add-repository-instructions)) 개인이 기억하지 않아도 된다.

## 규칙을 둘 세 곳을 먼저 고른다

같은 목적이지만 파일 위치와 적용 범위가 다르므로, 먼저 아래 표처럼 나눈다. 표의 내용은 GitHub Copilot 문서 기준이며, 다른 AI 도구가 같은 경로·범위를 똑같이 지원한다는 일반화는 하지 않는다.

| 지침 유형 | 파일 위치 | 적용 범위 |
|---|---|---|
| 저장소 공통 지침 | `.github/copilot-instructions.md` | 저장소 맥락의 모든 요청 |
| 경로별 지침 | `.github/instructions/NAME.instructions.md` (`applyTo` glob) | 지정 경로의 파일과 관련된 요청 |
| 에이전트 지침 | 저장소 안 아무 곳의 `AGENTS.md` | AI 에이전트가 사용, 트리에서 가장 가까운 파일 우선 |

선택 기준은 간단하다. 팀 전체가 지켜야 하는 검증 절차·변경 범위는 공통 지침에, 특정 디렉터리에만 적용되는 규칙(예: 스키마 폴더 전용 규칙)은 경로별 지침에 둔다. 에이전트가 자주 읽는 컨텍스트는 `AGENTS.md`가 더 가까운 위치에서 우선한다. 경로별 지침과 공통 지침이 같은 요청에 걸리면 둘 다 사용되므로, 목적에 맞게 분리하는 편이 관리에 낫다. 경로별 지침의 현재 지원 범위는 문서에 제한이 적혀 있으므로, 도입 전에 우리 팀이 쓰는 기능에서 실제로 받는지 확인해야 한다.

## 짧게 시작하는 공통 지침 예시

길이보다 "개요·검증·변경 범위"의 삼 구조가 있는지가 중요하다.아래는 교육용 예시이며 이 글을 쓰는 저장소의 실제 설정이 아니다. 아래 명령 문자열은 검증되지 않았으므로, 실제 저장소에 넣기 전에 자기 환경에서 실행해 확인해야 한다.

```markdown
# 저장소 공통 지침 (교육용 예시)

## 프로젝트 개요
- TypeScript 기반 웹 서비스. 운영 코드는 `src/`, 읽기 전용 아카이브는 `legacy/`.

## 검증 절차
- 변경 후 `npm run lint`, `npm test` 순서로 실행한다.
- (이 예시의 명령은 검증되지 않은 문자열이다.)

## 변경 범위
- DB 스키마와 배포 설정이 포함되는 PR은 설명에 별도 섹션을 남긴다.
- `legacy/` 변경은 이견이 없으면 하지 않는다.
```

이 정도 분량에서 시작하면 유지 부담이 적고, 검증 절차와 변경 범위가 함께 드러나 도구가 "무엇을 바꿔도 되는지"를 먼저 알게 된다.

## 참고됐다고 준수까지 보장되지는 않는다

적용이 됐는지는 응답 상단의 참고 목록에서 지침 파일이 링크되는지로 확인한다. 파일이 참고 목록에 나타나면 그 응답에 지침이 덧붙여진 것이다. 다만 여기서 구분할 것이 있다. **참고됐다는 사실과 지침 준수가 보장된 것은 다르다.** 참고 목록은 사용 여부를 보여줄 뿐, 모델이 지침의 모든 문장을 따랐는지는 보장하지 않는다. 우선순위 규칙(개인 지침이 가장 높고 저장소, 조직 순) 때문에 다른 지침과 충돌하면 결과가 달라질 수 있으며, 문서도 충돌을 피하라고 권한다. 따라서 도입 직후에는 다음을 점검한다.

- [ ] 파일이 정해진 위치에 실제로 존재하는가
- [ ] 개요·검증 절차·변경 범위가 각각 한 문단 이상 있는가
- [ ] 개인·조직 지침과 충돌하는 문장이 없는가
- [ ] 채팅 응답의 참고 목록에 파일이 나타나는지 확인했는가
- [ ] 코드 리뷰에서의 사용 여부 설정이 팀 합의와 일치하는가

적용 한계도 함께 적어 둔다. 지침은 제품 기능에 따라 적용 범위가 다르고, 문서 스냅샷의 설명과 실제 최신 동작이 어긋날 수 있다. 지침 파일이 응답에 포함된다고 프로젝트 규율이 자동으로 지켜지는 것도 아니다. 최종 판단은 코드 리뷰에서 사람이 한다.

## 무엇부터 분리할까

지금 바로 실행할 수 있는 순서는 다음과 같다. 이번 주에 한 개의 PR로 `.github/copilot-instructions.md` 초안을 만들고, 검증 절차 문단을 가장 먼저 채운 뒤, 참고 목록에 나타나는지 확인한다. 다음 회차에서 규칙이 폴더별로 갈리는 항목(예: 마이그레이션 파일 전용 규칙)만 경로별 지침으로 꺼내고, 팀·조직이 함께 지키는 규칙은 마지막에 정리한다. 검증 절차가 공통 지침에 들어가는 순간부터 매 대화 설명이 줄어들기 시작한다.
