# 장애 복구 판단 메모: 되돌리기 명령이 곧 안전을 보장하지 않는다

## 결론

**롤백 명령이 있다는 사실만으로 안전한 복구는 보장되지 않는다.** Kubernetes의 Deployment 롤백은 Pod 템플릿(이미지·라벨 등)만 이전 revision으로 되돌릴 뿐 데이터베이스의 쓰기는 복원하지 않는다. GitHub의 2018년 10월 21일 장애처럼 양쪽 데이터베이스에 서로 다른 쓰기가 남은 상황에서는 워크로드를 되돌려도 데이터 정합성 문제는 그대로 남는다. 복구 판단은 "명령이 있는가"가 아니라, 무엇이 깨졌는지(배포 상태 vs 데이터), 이전 revision이 남아 있는지, 롤백 이후 상태를 확인할 수 있는지를 순서대로 확인하는 과정이다.

## 실제 사례 타임라인 (UTC)

| 시각 (UTC) | 조치 |
|---|---|
| 10월 21일 23:19 | webhook 전달과 GitHub Pages 빌드 일시 중지(메타데이터 쓰기 절감) |
| 10월 22일 00:05 | 백업 복원, 양쪽 복제본 동기화, 안정 토폴로지 복귀, 대기 작업 재개 계획 수립 |
| 10월 22일 00:41 | 영향받은 MySQL 클러스터의 백업 절차 진행 상황 관찰 |
| 10월 22일 06:51 | 일부 동부 클러스터 복원 완료 후 서부 새 데이터 복제 시작, 더 큰 클러스터는 복원 중 |

서부 데이터베이스는 약 40분간 애플리케이션 쓰기를 받았고, 동부에도 서부로 복제되지 않은 수초 분량의 쓰기가 남아 단순히 동부로 되돌리는 선택지는 없었다.

## 배포 상태 복구와 데이터 정합성의 차이

Deployment 롤백의 대상은 `.spec.template`뿐이며, 롤백 시 되돌아가는 것도 템플릿 부분이다. revision은 템플릿이 바뀔 때만 만들어지고 스케일링은 revision을 만들지 않는다. 진행이 멈춘 배포에 `ProgressDeadlineExceeded`가 뜨면 Kubernetes는 상태 보고 외 아무것도 하지 않으므로 자동 롤백도 없다. 일시정지된 Deployment는 resume하기 전에 롤백할 수 없고, `revisionHistoryLimit`이 0이면 히스토리가 사라져 롤백 자체가 불가능하다.

반면 데이터 정합성은 다른 층의 문제다. GitHub 사례의 선택은 백업 복원과 복제 동기화였고, 배포 워크로드를 되돌리는 행위와 겹치지 않는다. "롤백 명령이 있다"는 워크로드 템플릿을 복구할 가능성만 말해 주고, DB 쓰기 충돌을 해소해 주지는 않는다.

## 복구 판단 체크리스트

1. 변경된 것이 템플릿인지 스케일링인지 확인한다(스케일링만으로는 revision이 없다).
2. `kubectl rollout history`로 목표 revision의 존재와 `revisionHistoryLimit` 보관 상태를 확인한다.
3. paused 여부를 확인하고, paused라면 resume부터 한다.
4. 롤백 후 `kubectl rollout status`와 `kubectl get deployment`로 완료·가용 상태를 확인한다.
5. 데이터 계층은 백업 시각·복제 지연·쓰기 충돌을 별도로 확인한다(배포 롤백으로 해결되지 않는다).
6. `ProgressDeadlineExceeded`는 자동 조치 신호가 아니라 판독 신호임을 상기한다.

| 제안 | 담당 역할 | 우선순위(제안) | 완료 확인 기준 |

| 복구 판단 체크리스트를 회의 절차에 편입 | 플랫폼 엔지니어링 | 높음 | 회의에서 체크리스트 사용 여부 검토 |

| 진행 기한 초과 알림·대응 규칙 문서화 | 플랫폼 엔지니어링 | 중간 | 조건별 대응 절차 문서 확인 |
