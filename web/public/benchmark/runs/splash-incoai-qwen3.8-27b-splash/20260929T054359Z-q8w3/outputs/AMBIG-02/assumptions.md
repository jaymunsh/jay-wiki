# AMBIG-02 — 판단 근거 (assumptions)

명세는 한 문장뿐이다: **"외부 API 호출이 실패하면 재시도한다."**
횟수·대기·"실패"의 정의·성공 시 반환 — 전부 미정의다. 아래는 그 각 지점에서 정한 값과 이유.

## 1. 재시도 횟수 — 3회(초기 1 + 재시도 2), 상한
- **판단**: `maxAttempts = 3`(총 호출 3회). 이후엔 더 재시도하지 않고 마지막 오류로 reject.
- **근거**: 명세에 횟수가 없다. "실패하면 재시도"를 **무제한**으로 읽으면 영속 장애 시 영원히 막힌다(호출자 hang). 유한 상한이 안전한 기본값이며, 3회는 재시도 래퍼에서 흔한 기본치. `options.maxAttempts`로 덮어 쓸 수 있게 해 두어(예: 5) 의사결정 밖으로 노출.

## 2. 대기(backoff) — 지수 200ms, 상한 2000ms, 지터 없음
- **판단**: 재시도 사이 대기 = `min(200 * 2^(n-1), 2000)`ms (200→400→800…). 지터 없음.
- **근거**: 명세가 대기를 안 정했다. 짧은 지수 백오프는 "하늘을 울리지 않으면서" 재시도하는 표준. 지터는 동시 재시도 폭주를 막는 데 쓰이나, 단일 호출 래퍼라 생략.

## 3. "실패"의 정의 — `fn`이 reject(throw)하는 경우
- **판단**: `fn`이 **reject**하면 실패→재시도, **resolve**하면 성공→그 값을 그대로 반환.
- **근거**: `fn`이 무엇을 반환지는 명세가 안 준다(HTTP status 객체인지, 값인지). 상태 분류를 할 재료가 없으므로, **Promise 결과(resolve/reject)** 만으로 성공/실패를 정한다. HTTP 상태 기반 분류는 AMBIG-03(명세가 status를 전제한 경우)에 해당한다.
- **의존성**: `fn`은 인자 없이 호출한다(`fn()`). 요청 자체는 `fn`이 클로저로 닫고 있다고 가정.

## 4. 안전장치 — 총 대기 시간 예산
- **판단**: 누적 대기가 `maxTotalWaitMs`(기본 30s)를 넘으면 조기 중단 후 reject.
- **근거**: 3회 상한+2000ms 백오프만으로도 총 대기 ≤ ~600ms라 실제로는 발동하지 않지만, 큰 `maxAttempts`를 사용자가 세어도 hang을 막는 2차 안전장치.

## 5. 성공 시 반환 / 최종 실패 시
- 성공: `fn`의 반환값을 **그대로** 반환(명세 지정).
- 최종 실패: **마지막 오류로 reject**(`await`에서 throw). "반환"을 resolve 값이 아닌 reject로 처리.

## 6. 확장
- 시그니처는 `callWithRetry(fn)`을 유지하되 선택적 2번째 인자 `options`로 기본값 덮어쓰기를 허용(명세의 단일 인자 계약과 충돌 없음).

## 명세가 정해준 것
"실패하면 재시도한다", "성공 시 그 반환값을 그대로 돌려준다".
