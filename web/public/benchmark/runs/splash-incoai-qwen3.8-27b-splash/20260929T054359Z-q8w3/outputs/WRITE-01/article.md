# 매번 같은 규칙을 설명하지 않으려면, 저장소에 무엇을 적어야 할까

## 반복되는 설명이 문제다

팀에 AI 코딩 도구를 하나만 들어와도 같은 말이 반복된다. "프로젝트 구조가?", "테스트는 이 명령으로", "여긴 건드리지 마". 매번 같은 문장을 붙여넣는다면 그 문장은 채팅창이 아니라 저장소에 있어야 한다. 쓰면 팀원과 도구가 매 세션 같은 전제를 공유한다. 핵심은 "무엇을"이 아니라 "어디에"다. 모든 규칙을 한 파일에 끼우면 관련 없는 작업에도 섞이고 길어져 핵심이 묻힌다. 같은 문장이라도 두는 위치에 따라 읽히는 요청의 범위와 우선순위가 달라지므로, 규칙의 성격에 따라 파일을 나누는 것이 이 글의 출발점이다.

## 규칙을 둘 세 가지 위치

GitHub Copilot 문서는 저장소 지시를 세 종류로 구분한다(공식 문서). 아래 표는 파일·위치, 적용 범위, 성격이다.

| 구분 | 파일과 위치 | 적용 범위 | 성격 |
|---|---|---|---|
| 저장소 전체 | `.github/copilot-instructions.md` | 모든 요청 | 항상 읽히는 공통 규칙 |
| 경로별 | `.github/instructions/` `NAME.instructions.md`(frontmatter `applyTo`) | 해당 glob 매칭 파일 | 영역별 규칙 |
| 에이전트 | 어디서나 `AGENTS.md`(가장 가까운 파일 우선), 또는 루트 `CLAUDE.md`·`GEMINI.md` | AI 에이전트 작업 | 도구 독립 컨벤션 |

"전체"와 "경로별"은 충돌이 아니라 겹쳐 읽힌다. 매칭된 경로 파일 작업 시 저장소 전체 지시도 함께 존재하면 두 지시가 모두 사용된다. `AGENTS.md`는 성격이 다르다. 어디에나 두고 가장 가까운 파일이 우선하며, 특정 벤더가 아닌 여러 도구가 따르는 컨벤션이다. 다만 파일명을 통일하는 것은 컨벤션일 뿐, 모든 도구가 지원하는 것은 아니다. 제품별 지원은 문서 표를 개별로 확인하라. 경로별 지시 파일은 `.github/instructions` 하위에 두고 파일명이 `.instructions.md`로 끝나야 하며, frontmatter의 `applyTo`에 glob 패턴으로 적용 대상을 지정한다. 여러 패턴은 쉼표로 나열할 수 있다.

## 작은 작성 예시

실제 모양을 교육용 예시로 본다. 아래는 이 저장소 설정이 아니라, "개요·검증·범위" 세 축이 드러나는 예시다.

```markdown
# 프로젝트 개요
- 결제 웹 백엔드. Python 3.12, FastAPI, PostgreSQL.
- `src/` 도메인, `migrations/` 스키마, `tests/` pytest.

# 변경을 검증하는 절차
- 코드 변경 후: `make lint && make test`
- 스키마를 건드리면 `migrations/`에 새 파일 추가, `make migrate-check` 실행.
- 위 명령은 문서 작성 시점에 저장소에서 확인한 것이다.

# 변경 범위
- `src/legacy/`는 유지보수만. 신규 기능 금지.
- 공개 API 응답 스키마 변경 금지.
```

개요는 방향을, 검증 절차는 "성공적으로 빌드·테스트하는 순서"를, 변경 범위는 안 건드릴 영역을 고정한다. 문서도 같은 방향을 권한다. 저장소가 하는 일의 요약, 언어·프레임워크·런타임, bootstrap·build·test·run·lint 순서와 도구 버전을 쓰라고 한다. 한 가지만 분명히 하자. 예시의 `make` 명령은 예시용이지 실제 이 저장소 명령이 아니다. "실행해 봤다"고 단언하기 전엔 명령을 한 번 돌려야 한다. 확인하지 않은 명령을 "검증 완료"처럼 쓰면 도구는 잘못된 전제로 작업한다.

## 적용을 확인하는 방법

저장소에 올려도 끝이 아니다. Copilot Chat의 응답 상단 references 목록을 펼치면 이번 응답에 쓴 파일이 나열되고, `.github/copilot-instructions.md`가 있는지가 "읽혔는가"의 확인점이다. 참고 파일은 클릭해 열리기도 한다.

여기서 구별할 것이 있다. references에 파일이 나온다는 것은 근거로 참조됐다는 뜻이지, 지시를 정확히 지켰다는 보장은 아니다. "참고했다"와 "준수했다"는 다르다. 지시가 길거나 충돌하면 어떤 선택을 했는지 diff를 직접 검토해야 한다. 문서도 충돌 지시 피하기를 권하고, 품질이 걱정되면 저장소 지시를 일시 끄도록 한다. Copilot code review는 이 토글이 기본 켜져 있고, base가 아닌 head 브랜치 지시를 읽으니 같은 pull request 안에서 지시 변경을 시험할 수 있다. 지시 파일은 저장하는 순간 다음 요청부터 자동 반영되므로, 수정 효과를 바로 참고 목록에서 확인하기 쉽습니다.

## 도입 시 확인할 것

- 지시 파일의 이름과 위치가 쓰는 도구가 실제로 읽는 것인지. (파일명·경로는 제품마다 다름)
- 공통 규칙과 경로 규칙을 나눠, 모든 요청에 매번 읽히는 지시가 짧게 유지되는지.
- 지시끼리, 지시와 개인/조직 설정끼리 충돌하는 곳이 없는지.
- 검증 명령을 실제로 한 번 실행해 문서가 지금의 저장소와 일치하는지.
- 응답 references에서 파일이 참조되고, 결과 diff가 지시대로 나오는지.

한계도 함께 적는다. 지시는 계약이 아니라 파일 저장 시 즉시 요청에 합쳐지는 것이다. 길어지면 핵심이 희석되고, 충돌이 생기고, 어떤 부분을 반영할지 예측이 어려워진다. 전체·경로별·에이전트 지시가 한 요청에 동시에 걸리고, 개인 지시가 조직 지시보다 우선하기도 한다. "적혔으니 무조건 따른다"가 아니라, "어떤 우선순위로 읽히는지 아는 것"이 한계의 핵심이다. 개인·저장소·조직 지시가 동시에 걸리면 의도와 다르게 우선순위에 가려질 수 있으니, 적용 우선순위를 문서에 미리 적어 두면 혼란을 줄입니다.

## 어떤 규칙부터 분리할까

한 파일의 규칙을 바로 나누면 안 된다. 우선 잘 안 바뀌는 "전역 공통"만 `.github/copilot-instructions.md`로 빼고, 개요·검증 절차·"절대 건드리지 말 것" 세 가지만 남긴다. 특정 디렉터리에서만 유효한 규칙은 `applyTo`로 매칭하는 경로별 파일로 옮긴다. `migrations/**`의 스키마 규칙, `src/legacy/**`의 신규 기능 금지처럼. 도구에 따라 다르고 디렉터리별 세분이 필요한 규칙은 가까운 `AGENTS.md`로 내려 보내라. 순서는 항상 같다. 공통은 짧게, 영역은 좁게, 도구차는 깊게. 전역에서 "항상/절대"만 남기고 나머지를 아래로 내린 뒤, references와 실제 diff로 각 단계가 먹는지 확인한다. 이 순서만 지키면 매번 같은 설명을 다시 쓰지 않게 된다.
