# 롤백 명령이 있는 것은 안전 복구를 보장하지 않는다

## 결론

Kubernetes Deployment의 `rollout undo`는 Deployment의 Pod 템플릿만 되돌린다. 데이터베이스나 저장소처럼 애플리케이션이 롤아웃 중 쓴 지속 데이터에는 손을 대지 않는다. 그래서 데이터에 발산된 쓰기가 남은 장애에서는, 롤백이 아니라 백업 복원과 재동기화가 실제 복구 경로가 된다. GitHub의 2018-10-21 장애는 정확히 이 경로를 택했고, 복구 시간과 사용성을 희생하며 데이터 무결성을 먼저 지켰다. 핵심은 두 가지를 구분하는 것이다. 앱의 배포 상태를 되돌리는 것과, 데이터 상태를 되돌리는 것은 서로 다른 작업이고, 어느 쪽을 우선할지는 응답자의 판단이다.

## 실제 대응 순서 (UTC)

아래는 사건 브리프(SRC-INCIDENT)의 시각을 그대로 옮긴 것이다. 이 사건은 GitHub 내부 데이터베이스 장애로, Kubernetes와 무관한 별개의 시스템이다.

| 시각 (UTC) | 조치 |
|---|---|
| 10-21 23:19 | 메타데이터 쓰기를 줄이고자 webhook 전달과 GitHub Pages 빌드를 일시 중지 |
| 10-22 00:05 | 백업 복원, 양쪽 복제본 동기화, 안정 토폴로지로 복귀, 대기 작업 재개 계획 수립 |
| 10-22 00:41 | 영향받은 MySQL 클러스터의 백업 절차 진행 상황 관찰 |
| 10-22 06:51 | 일부 동부 클러스터는 복원 완료 후 서부의 새 데이터 복제 시작. 더 큰 클러스터는 복원 중 |

서부에는 약 40분, 동부에는 서부로 복제되지 않은 수초 분량의 쓰기가 남아 있어, 단순히 동부로 되돌리는 것은 불가능했다.

## 배포 상태 복원과 데이터 무결성의 차이

- **롤백의 범위**: 이전 리비전으로의 롤백은 Deployment의 Pod 템플릿 부분만 되돌린다. 템플릿을 제외한 데이터는 그대로 남는다. (SRC-DEPLOY)
- **리비전 생성 조건**: 롤아웃이 트리거되고 새 리비전이 생기는 것은 Pod 템플릿이 바뀔 때만이다. 스테이징만 변경하면 리비전은 생기지 않는다.
- **자동 롤백 없음**: 롤아웃이 시간 한도를 지나면 컨트롤러는 `ProgressDeadlineExceeded` 상태만 보고하고 계속 재시도한다. 롤백은 더 높은 수준의 오케스트레이터나 사람이 한다.
- **데이터 문제는 롤백 밖**: 두 지역에 발산된 DB 쓰기를 롤백이 지우지 못했기에, 실제 복구는 백업 복원과 양방향 복제 동기화로 진행됐다.

즉 롤백 명령은 "앱 배포 상태" 회복 수단이고, "데이터 상태" 회복은 백업·동기화·조정의 별도 경로로 보장해야 한다.

## 복구 결정 체크리스트

롤백을 실행하기 전에 다음을 순서대로 확인한다.

- [ ] 장애가 앱 배포 상태에 있는가, 데이터에 있는가
- [ ] 데이터베이스·큐 등 외부 시스템으로의 쓰기가 아직 흐르는가. 흐르면 먼저 쓰기 원천 차단
- [ ] 마지막으로 알려진 안정 리비전은 어느 것인가 (`rollout history`로 확인)
- [ ] 롤백 대상 리비전이 지속 데이터에 영향을 주는가. 템플릿만 건드려도 데이터는 별도 확인
- [ ] 최근 백업이 존재하는가. 간격과 보관 위치를 확인
- [ ] 양방향 데이터 동기화는 끝났는가. 어느 쪽 데이터를 정본으로 삼는가
- [ ] 허용 가능한 가용성·복구 시간의 범위를 미리 정했는가
- [ ] 복구 후 검증 방법이 있는가 (체크섬, 대조 작업)

## 개선 제안 (제안이며, 구체 담당자·기한 없음)

| 방향 | 담당 역할 (제안) | 우선순위 | 완료 기준 |
|---|---|---|---|
| 전체 클러스터 규모 백업 복원 훈련 | SRE | 높음 | 전체 복원 1회 이상 실제 실행, 소요 시간 기록 |
| 백업 간격 축소 및 RPO 문서화 | SRE / DBA | 높음 | 백업 간격 명시, RPO 측정·공개 |
| 무결성과 가용성 우선순위 사전 합의 | 사령관 / 엔지니어링 매니저 | 높음 | 우선순위 규칙을 장애 런북에 기록 |
| 롤백 자동화와 데이터 복구 자동화 분리 | 플랫폼 엔지니어링 | 중간 | 앱 롤백은 원커맨드, 데이터 복구는 별도 승인 절차 |
| 대륙 간 복제 지연 경보 | DBA | 중간 | 지연 임계값 경보 설정, 런북에 포함 |

위 표는 개선 방향의 제안으로, GitHub가 실제로 완료한 업무가 아니다. 구체적 인력 배치는 존재하지 않는다.
