# AMBIG-03 — 판단 근거 (assumptions)

고정 입력 `input/ambig03-spec.md` (v2.3) 재시도 정책 명세서. SHA-256 `f5829ae…89625` — sources.json(AMBIG03-SPEC)과 **일치** 확인.
핵심은 **명세 자체에 심어진 모순**과, status 기반 분류·함수 계약의 해석이다.

## 1. 핵심 모순: "최대 3회"(§3) vs "성공할 때까지"(§7)
- **§3**: "일시 오류에 대해서만 재시도하며, **최초 호출 포함 최대 3회** 시도한다."
- **§7(종료 조건 표)**: "일시 오류 | **성공할 때까지** 재시도."
- → 둘은 충돌한다: §3은 3회로 단속하고, §7은 회수 없이 성공을 향해 간다.
- **판단**: **§3의 숫자 상한(3회)이 우선**한다.
- **근거**:
  1. §3은 **구체적·강력한 수치**(hard cap)이고, §7의 "성공할 때까지"는 그 상한을 잊은 **개요적 표현**이다. 둘이 충돌하면 구체적 수치 조항이 우세한 게 표준 해석.
  2. 무한 재시도는 영속 장애·비용·서버 과부하를 부른다. "성공할 때까지"를 문자 그대로 따르면 안전 장치가 사실상 §7의 "최대 대기 총합 5초"뿐인데, 3회 상한이 있으므로 그 5초는 3회(최대 대기 600ms)에선 **실제로 발동하지 않는다** — 즉 3회 상한이 1차, 5초가 2차 방어.
  3. §3은 **결제 게이트웨이**라는 멱등·비용 민감 문맥(§1,§5)이라, 횟수 제한이 의도된 설계로 읽힌다.
- **해석**: "성공할 때까지"를 "**(상한 안에서) 성공할 때까지**"로 한정. 성공하면 즉시 반환, 없으면 **3회**에서 종료.

## 2. 오류 분류 (§2 용어)
- **일시(재시도)**: 네트워크 단절, 타임아웃, 5xx, **429**(§2가 429를 영구에서 제외).
- **영구(즉시 실패, 재시도 안 함)**: 401/403, 429를 뺀 4xx, 한도 초과.
- status가 없으면(네트워크/타임아웃) → **일시**로 간주(§2의 "네트워크 단절, 타임아웃"에 해당).

## 3. `fn` 계약 가정 (명세가 shape을 안 줌)
- `fn`은 **reject 시 오류가 `.status`**를, 또는 **resolve 시 응답이 `.status`**를 가진다고 가정.
- status가 2xx/3xx → 성공(return value). 429/5xx(또는 resolve된 5xx) → 재시도. 401/403/기타 4xx → 영구, 즉시 throw.
- status도 네트워크 마커도 없으면 → **일시**(3회 상한으로 단속). ← AMBIG-02와 달리 status를 전제한 게 §2/§7이 HTTP 응답을 전제했기 때문.

## 4. 대기·종료·관측 (§4,§6,§7)
- 백오프: 첫 200ms, 매번 2배, **상한 2000ms, 지터 없음**(§4). 3회라 실제 대기 = 200+400.
- 종료: 성공→반환 / 영구→즉시 throw / **3회 도달**(§3)→throw / **총 대기 5초**(§7)→throw. (3회 상한 때문에 5초는 2차 방어.)
- 관측: 재시도 시 `retry.attempt`,`retry.reason`; **최종 실패 시 `retry.exhausted`** emit. 영구·일시-고갈 어느 쪽 최종 실패든 emit하되 reason으로 구분(§6 "최종 실패 시"에 충실).
- §8(정산 배치 제외)는 이 함수 대상 밖 → 구현 생략.

## 5. 최종 실패 표면화
- "호출자에게 실패를 **반환**"(§3/§7) → **마지막 오류로 reject**(`await`에서 throw)로 처리.
