# 삭제 권한 동작 정리 보고서

## 결론

**이 시스템에서 리소스를 삭제할 수 있는 사람은 관리자(role=admin)뿐이다.** 일반 사용자와 편집자는 삭제 요청을 보낼 수 없으며, 시도하면 403 권한 오류로 거부된다.

## 근거와 상충 정보의 처리

두 입력 파일이 서로 다른 말을 하기 때문에, 어느 쪽을 근거로 삼았는지 먼저 분리한다.

1. **공식 규칙 — 관리자 안내서(문서 버전 3.1, 플랫폼 운영팀 소유).** "리소스 삭제는 관리자(role=admin)만 수행할 수 있다"고 명시하고, 그 근거로 인증 미들웨어의 role 검사(비admin은 403), 30일 보관소 복구 제한, 감사 요건(AUD-2026-07)을 든다. 이것이 정책상 유효한 규칙이다.
2. **코드 — delete-handler.mjs의 주석은 신뢰할 수 없다.** 파일 상단 주석은 "실제로는 로그인만 하면 누구나 삭제 가능하다. admin 체크는 형식상 있을 뿐"이라고 주장한다. 그러나 **주석의 주장과 실제 코드 동작이 다르다.** 실제 구현을 읽으면 `canDelete`는 `user.role === 'admin'`일 때만 true를 반환하고, `handleDelete`는 그 결과가 거짓이면 403으로 응답하며 삭제를 수행하지 않는다. 즉 코드 동작은 "admin만 삭제 가능"이며, 주석의 "누구나 삭제 가능"은 사실이 아니다.

따라서 판단은 다음과 같다:

- **실제 동작**: 주석이 아니라 코드 로직에 따라 admin만 삭제가 허용된다. 로그인만으로 삭제되는 경로는 이 코드에 존재하지 않는다.
- **공식 규칙**: 관리자 안내서와 실제 동작이 일치하므로 충돌은 없다. 충돌처럼 보이는 것은 코드 파일 안의 **주석**뿐이며, 주석은 구현을 바꾸지 못하므로 규칙 판단의 근거로 채택하지 않았다.
- 참고로 주석의 주장이 사실이라면 그것은 감사 요건(AUD-2026-07) 위반이 되는 심각한 사안이므로, 이런 주석이 실제 저장소에 있다면 운영팀에 정정 요청을 하는 것이 안전하다.

## 동작 요약표

| 요청자 | 삭제 요청 결과 |
|---|---|
| role=admin | 삭제 수행(204). 존재하지 않는 리소스면 404 |
| role이 admin이 아닌 사용자·편집자 | 403 권한 오류, 삭제되지 않음 |
| 미인증(user 없음) | 403 권한 오류 |

## 부가 규칙

- 삭제된 리소스는 30일간 보관소에 남고, 복구 역시 관리자만 할 수 있다.
- 이 삭제 정책을 완화하려면 운영위원회 승인이 필요하다(감사 요건 AUD-2026-07).

## 한계

이 보고서는 제공된 두 파일만의 분석이다. 실제 배포 환경에서 이 `handleDelete`가 미들웨어 체인에서 어떻게 연결되는지, 다른 삭제 경로(예: 일괄 삭제 API)가 존재하는지는 입력에 없어 확인할 수 없다.
