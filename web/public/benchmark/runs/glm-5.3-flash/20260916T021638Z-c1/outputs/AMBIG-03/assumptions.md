# AMBIG-03 assumptions.md — 명세 해석 판단과 근거

대상: 재시도 정책 명세서 v2.3(ambig03-spec.md, SHA-256 f5829aee…, 검증 일치).

## 1. 명세의 모순 — §3(최대 3회)과 §7(성공할 때까지 재시도) 충돌. **§3을 우선 적용해 최초 포함 총 3회로 제한.**

근거: 두 조항이 직접 충돌할 때 더 구체적이고 수치로 정의된 조항(§3 "최초 호출 포함 최대 3회 시도")이 의도를 더 정확히 표현한다고 판단했다. §7의 "성공할 때까지"는 §7 자신의 다른 조건(최대 대기 총합 5초 초과 시 중단, 최대 횟수 소진)과도 맞지 않아, 유한 상태로 정리해야 하는 의도로 읽었다. 무한 재시도는 결제 게이트웨이 연동 모듈(§1 적용 범위)에서 사용자 대기와 중복 처리 위험을 키운다. 이 충돌을 명세 소유자에게 확인해야 한다는 점도 유지보수 관점에서 명시한다.

## 2. 오류 분류 방법 — **오류 객체의 `status` 속성 기준**

§2가 일시/영구 오류를 HTTP 상태 중심으로 정의하므로, `fn`이 던지는 오류 객체에 `status` 숫자가 있으면 그 값으로 판별한다(5xx·429 → 일시, 401/403·그 외 4xx → 영구). `status`가 없으면 네트워크 단절·타임아웃으로 간주해 일시 오류로 재시도한다. 근거: `fn`은 네트워크 호출을 흉내 내는 함수라는 전제이고, 상태 코드가 없는 throw를 모두 영구 오류로 보면 단절·타임아웃을 재시도하지 못해 명세 목적(§1 일시 실패 흡수)에 어긋난다.

## 3. 대기 총합 5초의 계산 기준 — **대기 시간만 누적(호출 소요 시간 제외)**

§7의 "최대 대기 총합 5초"를 재시도 사이의 sleep 합계로 해석했다. 근거: 조항 제목이 "대기 간격" 계열의 문맥이고, 호출 응답 시간은 서버 사정이라 클라이언트 정책으로 통제할 대상이 아니라고 본다. 반대 해석(경과 시간 전체)도 가능하다는 점을 명시한다.

## 4. 5초 초과 시의 반환 — **원인 오류를 cause로 남기고 실패를 throw**

§7은 "중단하고 실패 반환"이라고만 한다. 재시도 한도 소진과 대기 예산 초과를 구분할 수 있도록, 소진 시에는 마지막 오류에 `retryExhausted` 마커를 붙여 throw하고, 대기 예산 초과 시에는 새 오류에 `cause`로 원인을 붙여 throw한다. §6의 `retry.exhausted` 이벤트 개념을 코드 환경에서 표현한 것으로, 실제 로그 인프라는 이 구현 범위 밖이다.

## 5. 관측 로그(§6) — **onAttempt 콜백으로 대체**

`retry.attempt`/`retry.reason` 로그와 `retry.exhausted` 이벤트 발행은 구현 환경에 로거가 정의돼 있지 않아, 선택적 `onAttempt` 콜백으로 대체하고 기본 동작은 무음으로 뒀다. 근거: 라이브러리가 로깅 백엔드를 강제하지 않는 것이 안전하다.

## 6. 멱등 키(§5) — **래퍼가 아니라 호출자의 책임으로 분리**

§5는 "재시도 대상 호출은 반드시 멱등 키를 포함한다"고 요구하는데, 이는 호출 페이로드의 조건이지 래퍼 함수의 동작이 아니다. `fn` 안에서 멱등 키를 담도록 하는 책임은 호출자에 있고, 래퍼는 이를 강제하지 않는다. 근거: 래퍼가 임의의 멱등 키를 생성·주입하면 같은 주문 재시도 식별(§5의 취지)을 오히려 깰 수 있다.

## 7. 확정하지 않은 것

- 정산 배치 작업 예외(§8)는 이 함수의 호출 정책 문제라 코드로 반영하지 않았다.
- 타임아웃 값 자체는 명세에 없어 구현하지 않았다.
