# 매번 같은 작업 규칙을 설명하지 않으려면, 저장소에 무엇을 적어야 할까

AI 코딩 도구를 팀 저장소에 도입하면 반복되는 문제가 하나 생긴다. "이 프로젝트에서는 테스트를 이렇게 돌린다", "이 폴더 코드는 이렇게 다뤄달라"는 규칙을 매 대화마다 다시 설명해야 하는 것이다. 해결책은 규칙을 대화가 아니라 저장소 파일에 두는 것이다. 이 글은 규칙을 어디에 어떻게 두는지, GitHub 공식 문서가 설명하는 세 가지 위치를 중심으로 정리한다.

## 규칙을 둘 세 가지 위치

공식 문서는 저장소 안에 규칙을 두는 방법을 세 가지로 구분한다. 적용 범위가 다르므로 목적에 맞는 위치를 골라야 한다.

| 구분 | 파일과 위치 | 적용 범위 |
|---|---|---|
| 저장소 공통 지침 | `.github/copilot-instructions.md` | 저장소 맥락의 모든 요청 |
| 경로별 지침 | `.github/instructions/NAME.instructions.md` (`applyTo` glob 지정) | 지정 경로에 속한 파일의 요청 |
| 에이전트 지침 | 저장소 어디든 `AGENTS.md` (또는 루트의 `CLAUDE.md`, `GEMINI.md`) | AI 에이전트 작업. 디렉터리 트리에서 가장 가까운 파일이 우선 |

저장소 공통 지침과 경로별 지침이 모두 있고 경로가 겹치면 두 파일의 내용이 함께 사용된다. 즉 공통 지침에 전역 규칙을, 경로별 지침에 폴더 특수 규칙을 나눠 적는 구성이 자연스럽다. [공식 문서](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/add-custom-instructions/add-repository-instructions)의 39~53행이 이 세 유형의 정의이고, 49행이 동시 적용 조건이다.

경로별 지침은 현재 GitHub.com에서 클라우드 에이전트와 코드 리뷰 기능에서만 지원된다는 점(165행)도 알아둘 필요가 있다. 제품별 지원 범위를 모든 AI 도구의 공통 보장으로 확장해 설명하지 않는 것이 중요하다. `AGENTS.md`처럼 여러 도구가 읽도록 만들어진 규약도 있지만, 각 도구의 실제 지원 여부는 도구별로 확인해야 한다.

## 작은 작성 예시

공통 지침 파일에는 "에이전트가 매번 찾아보게 될 것"을 적는다. 공식 문서의 생성 프롬프트가 제안하는 항목은 저장소 요약, 사용 언어·프레임워크, 빌드·테스트·검증 절차 등이다(90~107행). 아래는 그 구성을 참고해 만든 **교육용 예시**이며, 실제 특정 저장소의 설정이 아니다. 적기 전에 명령을 실제로 실행해 확인해야 한다는 원칙(101행)도 예시에 반영했다.

```markdown
# 프로젝트 개요
- 이 저장소는 JSON 설정 파일을 읽어 리포트를 만드는 Node.js CLI 도구다.

# 검증 절차
- 변경 후에는 반드시 `npm test`를 실행한다. (검증된 명령만 적는다)
- 빌드는 `npm run build`이며 Node 20 이상이 필요하다.

# 변경 범위
- `src/core/` 아래 파일은 공개 API이므로 함수 시그니처를 바꾸지 않는다.
- 새 의존성을 추가하기 전에 팀 리뷰를 받는다.
```

지침은 2페이지 이내로 유지하고, 특정 작업에만 맞는 내용을 넣지 않는다는 제한도 공식 문서가 명시한다(84~85행). 짧고 범용적일수록 여러 요청에서 재사용된다.

## 참조됐는지 확인하는 방법과 한계

챗 응답 위쪽의 참조 목록을 펼쳐 `.github/copilot-instructions.md`가 포함됐는지 확인하면, 이번 답변에 지침이 실제로 쓰였는지 알 수 있다(227행). 다만 "참조됐다"와 "지침을 지켰다"는 다르다. 지침은 모델에 추가 맥락으로 제공될 뿐이고 준수를 보장하지 않는다. 지침 파일이 참조 목록에 없는데 답이 저장소 규칙을 따랐다면, 우연히 일치한 것일 수 있다.

우선순위도 알아둬야 한다. 개인 지침이 최우선, 그다음 저장소 지침, 조직 지침이 마지막이며, 관련된 모든 지침이 함께 제공된다(234행). 서로 충돌하는 지침 세트를 두지 않는 것이 품질 면에서 권장된다(235행).

## 도입 시 확인할 체크리스트

- [ ] 규칙 파일을 저장소에 커밋했는가 — 팀원과 에이전트가 같은 파일을 읽도록 한다.
- [ ] 적힌 빌드·테스트 명령을 실제로 실행해 확인했는가 — 확인되지 않은 명령을 검증된 것처럼 쓰지 않는다.
- [ ] 저장소 공통과 경로별 내용이 충돌하지 않는가 — 같은 주제를 두 파일에서 반대로 쓰지 않는다.
- [ ] 챗 응답의 참조 목록에 지침 파일이 뜨는지 한 번 확인했는가.
- [ ] 지침이 2페이지 이내이고 특정 작업 전용 내용이 아닌가.

적용 한계도 분명히 하자. 지침은 응답 품질을 높이는 보조 수단이지 강제 장치가 아니며, 경로별 지침처럼 기능별로 지원 범위가 다른 부분이 있다. 준수 여부가 중요한 규칙은 리뷰·CI 같은 검증 절차로 뒷받침해야 한다.

## 첫 규칙부터 분리하기

무엇부터 옮길지 고민된다면 "매 대화에서 반복해서 설명하는 것"부터 분리한다. 실전 순서는 이렇다. 첫째, 빌드·테스트·검증 명령을 확인하고 공통 지침에 적는다. 둘째, 폴더마다 다른 관행(코딩 규약, 금지 사항)을 경로별 지침이나 `AGENTS.md`로 옮긴다. 셋째, 챗에서 참조 목록으로 적용 여부를 눈으로 확인하고, 지침만으로 부족한 규칙은 검증 절차로 보강한다. 규칙이 대화가 아니라 저장소에 살게 되는 순간, 새로 온 사람도 에이전트도 같은 문서에서 출발하게 된다.
