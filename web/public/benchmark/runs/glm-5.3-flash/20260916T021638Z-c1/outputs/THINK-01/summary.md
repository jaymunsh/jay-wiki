# 복구 판단 메모 — 되돌리기 명령만으로 안전한 복구인가

## 결론

**아니요. 되돌리기 명령의 존재만으로 안전한 복구가 보장되지 않는다.** 이유는 두 가지다. 첫째, Kubernetes Deployment의 rollback은 Pod template만 되돌리므로 애플리케이션 데이터는 복원하지 않는다. 둘째, 2018년 10월 GitHub 장애 사례가 보여주듯, 두 데이터베이스에 서로 다른 쓰기가 남아 있으면 "이전 상태로 되돌린다"는 단일 정답 자체가 성립하지 않는다. 복구 판단은 되돌리기 명령이 아니라 데이터 정합성 검토에서 출발해야 한다.

## 실제 사례 타임라인 (UTC, SRC-INCIDENT 기준)

| 시각 (UTC) | 내용 |
|---|---|
| 2018-10-21 ~23:19 이전 | 미국 동부·서부 데이터베이스에 서로 다른 쓰기 발생. 서부는 약 40분간 쓰기 수용, 동부에도 미복제 수초 분량의 쓰기 |
| 10-21 23:19 | webhook 전달과 GitHub Pages 빌드를 일시 중지해 추가 메타데이터 쓰기 억제 |
| 10-22 00:05 | 백업 복원, 복제본 동기화, 토폴로지 복귀, 대기 작업 재개 계획 수립 |
| 10-22 00:41 | 영향받은 MySQL 클러스터의 백업 절차 진행 상황 관찰 |
| 10-22 06:51 | 일부 동부 클러스터가 복원을 마치고 서부의 새 데이터를 복제하기 시작 |

GitHub는 이 상황에서 **데이터 무결성을 복구 시간과 사용성보다 우선**했고, 그 대가로 대륙 간 DB 호출 지연으로 많은 사용자가 서비스를 쓰기 어려웠다. 즉 "빨리 되돌리기"와 "데이터를 지키기"가 충돌했고, 사례는 후자를 골랐다.

## 배포 상태 복구와 데이터 정합성의 차이

Kubernetes 문서가 말하는 rollback의 범위는 좁다. 리비전은 Pod template(`.spec.template`)이 바뀔 때만 만들어지고, 롤백은 "Deployment의 Pod template 부분만" 되돌린다. 데이터베이스의 쓰기는 이 범위에 없다. 또한 revisionHistoryLimit을 0으로 두면 롤백 자체가 불가능해지고, paused 상태에서는 재개 전까지 롤백할 수 없다. 진행 실패(ProgressDeadlineExceeded)를 컨트롤러가 감지해 새 ReplicaSet 확장을 멈추는 것은 있지만 자동으로 이전 버전을 되돌리지는 않는다.

GitHub 사례는 이 두 체계가 다른 시스템이었음을 보여준다. 해당 장애는 MySQL 데이터 정합성 문제였고, 브리프는 "GitHub가 Kubernetes Deployment로 이 장애를 복구했다"는 근거가 없음을 명시한다. 두 자료를 같은 사건으로 섞으면 안 된다. Kubernetes 롤백은 무상태 워크로드의 배포 버전 관리 도구이고, GitHub 사례의 복구는 백업 복원과 복제본 동기화를 동반한 데이터 정합성 복구였다.

## 복구 판단 체크리스트

- [ ] 되돌릴 대상이 무엇인지 분리했다 — 배포 버전(Pod template)인지 애플리케이션 데이터인지.
- [ ] 되돌리기로 사라지는 쓰기가 있는지 확인했다 — 분기·복제 지연으로 양쪽에 남은 쓰기 조사.
- [ ] 롤백 이력이 남아 있는지 확인했다 — revisionHistoryLimit=0이면 롤백 불가.
- [ ] paused 상태가 아닌지 확인했다 — 재개 전까지 롤백이 진행되지 않는다.
- [ ] 데이터 정합성이 걸리면 복구 시간·사용성과 우선순위를 명시적으로 정했다 — GitHub 사례처럼 그 선택의 비용도 함께 기록.
- [ ] 백업 복구 절차가 시험된 것과 전체 클러스터 재구축이 시험된 것을 구분했다 — 사례에서는 매일 시험해도 전체 재구축은 처음이었다.

## 후속 개선 제안 (제안이며 실제 담당자·기한·성과가 아님)

| 제안 | 담당 역할 | 우선순위 | 완료 기준 |
|---|---|---|---|
| Deployment 리비전 보존 한도 점검 절차 마련 | 플랫폼 운영 | 상 | 모든 운영 Deployment의 revisionHistoryLimit 값이 문서화되고 0이 아님이 확인됨 |
| 데이터 정합성 분기 대응 절차 수립 | 데이터베이스 운영 | 상 | 양쪽 복제본 쓰기 조사 절차와 판정 기준이 런북에 반영됨 |
| 전체 클러스터 백업 재구축 리허설 | 인프라 운영 | 중 | 리허설 1회 수행 후 소요 시간이 기록됨 |
| 장애 시 쓰기 일시 중지 항목 목록화 | 서비스 개발 | 중 | webhook·빌드처럼 중지 가능한 쓰기 원천 목록이 준비됨 |
| 롤백과 데이터 복구를 분리한 런북 보급 | SRE | 중 | 배포 롤백 런북과 데이터 복구 런북이 별도 문서로 존재함 |

## 출처

- SRC-DEPLOY: Kubernetes 공식 Deployment 문서 고정 스냅샷(이 메모의 deployment.md 입력). 세부 근거는 facts.json 참조.
- SRC-INCIDENT: GitHub October 21 post-incident analysis를 요약한 사실 브리프(incident.md 입력).
