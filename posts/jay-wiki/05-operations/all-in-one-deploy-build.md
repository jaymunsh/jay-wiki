## 결론 — 나가는 문은 둘이고, 큰 문은 머지 하나다

코드가 바뀌었으면 develop 을 main 에 머지한다. 그 한 번이 테스트부터 글 반영까지 사람 없이 간다. 코드가 안 바뀌고 글만 고쳤으면 머지도 필요 없다 — 로컬 /sync 옆문으로 글만 지나간다. 이 글은 그 두 문이 각각 무엇을 지나가는지, 왜 이 모양이 됐는지를 그린다.

## 출발점 — 머지가 끝나도 사람 손이 넷 남아 있었다

배포는 처음부터 「develop 을 main 에 머지하는 행동 하나」로 좁혀 뒀다. 그런데 머지가 끝나도 운영이 다 갱신되지 않았다. 넷이 사람 손에 남아 있었고, 넷이 남은 이유가 다 달랐다 — 공통점은 하나, **실패했을 때 되돌아오는 길이 앱 롤백과 달랐다**는 것이다.

| 사람 손 | 왜 파이프라인 밖이었나 |
|---|---|
| 관측 스택 Helm | 파이프라인이 Helm 을 안 불렀다. 저장소와 운영의 values 가 갈라져 있으면 upgrade 가 운영을 되돌려 버린다 |
| 블로그 발행 | 관리자 로그인에 TOTP 가 필요했다. 기계에 씨앗을 주면 2FA 가 1FA 가 된다 |
| 빈 탭 삭제 | 시드가 upsert 라 지우지 않았고, 삭제는 되돌릴 수 없는 동작이다 |
| 데이터 계층 Helm | 설치 후 한 번도 upgrade 한 적이 없었다. 파드가 아니라 데이터가 걸려 있다 |

사람이 기억해야 하는 절차는 언젠가 반드시 빠진다. 실제로 빠져서 알림이 35일 죽은 사고가 있었다. 그래서 넷을 없애기로 했는데, 전부 한 번에 밀어 넣지 않고 **각각 되돌릴 길이 생겼을 때만** 옮겼다.

## 전체 그림 — 머지 한 번이 지나가는 큰 덩어리

~~~mermaid
flowchart TB
    T[테스트 - GitHub 러너] --> B[이미지 빌드 - GHCR]
    B --> R[miniPC self-hosted 러너]
    R --> H[Helm - 관측 스택, 데이터 계층은 조건부]
    H --> O[앱 롤아웃 - SHA 태그]
    O --> P[PostgreSQL 백업 - 콘텐츠 쓰기 직전]
    P --> C[콘텐츠 - 위키 시드와 블로그 발행 Job]
    C --> S[스모크 - 공개 화면과 404 확인]
    S --> N[텔레그램 통보]
~~~

구조에서 중요한 것은 둘이다.

**deploy 잡은 miniPC 안에서 돈다.** self-hosted 러너가 클러스터와 같은 기계에 있어서 kubectl 과 helm 이 그냥 붙는다. 바깥에서 클러스터를 여는 문을 만들 필요가 없었다.

**콘텐츠는 러너가 API 를 직접 때리지 않는다.** 러너는 클러스터 안에 일회성 Job 을 띄우고, 그 Job 이 내부 경로에 쓴다. 인증은 관리자 로그인이 아니라 클러스터 안에서만 여는 machine token 하나다 — 그 경계는 gitops-wiki-content-sync-boundary 에 있다. 실패하면 이미지 캡처 기반 롤백이 돌고, 콘텐츠를 쓰기 직전의 DB 백업이 글을 덮는다. 단계 하나하나의 순서와 규칙은 deploy-rules-and-harness 에 있다.

## 셋을 옮긴 순서 — 무엇을 갖추고 나서 옮겼나

경계의 기준은 「할 수 있느냐」가 아니라 「실패했을 때 되돌릴 수 있느냐」다. 그래서 셋은 한 판이 아니라 세 판에 나눠 들어왔고, 판마다 갖춘 것이 다르다.

**1차(2026-08-15) — 관측 스택 Helm.** 올리기 전에 저장소 values 와 운영에 걸린 values 를 키 단위로 대조해, 올려도 의도한 변경만 적용된다는 것을 확인하고 넣었다. Helm 은 리비전이 있어 helm rollback 으로 되감긴다. 릴리스 지형은 helm-releases-and-boundary 에 있다.

**2차 — 1차에서 어긋난 것만 고치는 작은 판.** 자동화를 더 넣지 않았다. 고치는 배포와 새로 넣는 배포를 섞으면 무엇이 고쳐졌는지 가릴 수 없게 된다.

**3차(2026-08-16) — 남은 셋.** 각각 이렇게 갖췄다.

- **빈 탭 삭제** — 가드를 클라이언트가 아니라 서버가 쥔다. 글이 든 탭은 409 로 거부하고(클라이언트가 세어 보내면 그 사이에 글이 들어와도 모른다), 한 번에 둘까지만 지운다. 삭제는 되돌릴 수 없으므로 지울 수 있는 대상 자체를 잃을 것이 없는 빈 탭으로 좁혔다.
- **데이터 계층 Helm** — 올리기 전에 helm get manifest(지금 올라간 실물)와 --dry-run 렌더를 대조해 한 줄도 다르지 않다는 것을 확인하고 들어갔다. 결과는 REVISION 1 → 2, 파드 재시작 0. 비밀번호는 GitHub Secrets 에 따로 두지 않고 그 릴리스가 지금 쓰는 클러스터 Secret 에서 읽어 그대로 되돌려 넣는다 — 따로 둔 값이 어긋나는 순간 upgrade 가 비밀번호를 갈아 버리고 디스크의 데이터는 옛 비밀번호 그대로라 앱이 통째로 끊긴다.
- **블로그 발행** — 켜기 전에 복구 리허설을 했다. 백업을 뜨고, 운영 글 하나의 본문을 일부러 26자로 망가뜨려 화면이 깨진 것을 확인하고, 백업에서 되돌렸다 — 9305자 복구, 2.4초, 댓글·태그·id 그대로. 그리고 그 리허설에서 복구 스크립트의 버그가 실제로 나왔다. 되돌리는 길이 있다는 문서와 되돌려 봤다는 사실의 차이가 버그 하나만큼 실재했다. 백업 체계 자체는 postgres-backup-restore 에 있다.

이 순서와 기준을 정한 결정 기록은 deploy-automation-boundary 에 있다.

## /sync — 배포를 안 하고 가는 옆문

글만 고쳤는데 십수 분짜리 배포 한 판을 다 돌릴 이유가 없다. 그래서 작은 문을 따로 냈다. 로컬 개발 서버에서만 열리는 /sync 페이지에 버튼 여섯이 있다 — 차이 확인, 위키·블로그 내려받기, 위키·블로그·전체 반영. 로직은 scripts/content-ops.mjs 한 곳에 있고, 페이지의 버튼과 터미널 실행이 같은 함수를 부른다.

**배포와 별개인 이유는 지나가는 것이 다르기 때문이다.** 배포는 코드·이미지·매니페스트·글을 전부 내보내는 한 판이고, 이 문은 글만 지나간다. 되돌릴 지점도 다르다 — 파이프라인은 DB 백업을 뜨고, 이 문은 쓰기 전에 지금 운영에 있는 글을 파일로 받아 둔다. 대신 약하다. 삭제는 이 사본으로 못 되돌리므로, 탭을 지우는 일이면 배포로 한다.

~~**여기서는 사람이 TOTP 를 친다.** 파이프라인의 내부 경로는 클러스터 안에서만 열려 있어 노트북에서 못 부른다. 그래서 옆문은 관리자 API 를 타고, 그 길은 사람이 6자리를 넣는 길이다. 파이프라인이 TOTP 를 안 쓰는 것과 모순이 아니다 — 기계가 클러스터 안에서 쓰는 문과 사람이 바깥에서 쓰는 문의 **경계가 다른 것**이다.~~

**2026-09-02 에 이 경계가 옮겨졌다.** 위 문단은 그때까지의 사실이라 취소선으로 남긴다. 지금은 사람도 그 내부 문을 쓴다 — 발행 스크립트가 ssh 로 클러스터에 들어가 토큰을 그 자리에서 읽고 포트를 노트북까지 끌어온다. 토큰은 파일로 안 남기고 그 프로세스의 메모리에만 둔다.

**틀린 것은 「못 부른다」였지 경계 자체가 아니었다.** 내부 경로가 클러스터 안에서만 열려 있다는 사실은 그대로다. 바뀐 것은 노트북이 이미 ssh 로 그 안에 들어갈 수 있었다는 점을 안 쓰고 있었다는 것이다. 열쇠를 이미 들고 있으면서 문이 없다고 적어 둔 셈이다.

그래서 블로그 글은 이제 TOTP 를 안 쓴다. 위키는 여전히 옆문이 관리자 API 를 타고, 사람이 6자리를 넣는다.

안전장치는 셋이다. 운영에서는 페이지도 API 도 404 이고 그 404 를 배포 스모크가 매번 확인한다 — 열려 있으면 인증 없이 글을 쓰는 문이 되기 때문이다. 실행할 수 있는 동작은 정해진 여섯 개뿐이다. 그리고 web/public 에 새 그림 파일이 있으면 반영을 막고 배포를 시킨다 — 그림은 web 컨테이너 이미지 안에 있어서, 글만 올리면 본문은 바뀌는데 그림 자리가 깨진다.

~~셋째 안전장치는 블로그에도 걸렸다.~~ 2026-09-02 부터 블로그 그림은 MinIO 로 가고 원본은 posts/jay-blog/assets 에 남는다. 컨테이너 이미지에 안 구워지므로 막을 이유가 없어졌다. 위키 그림은 그대로 이 가드에 걸린다.

## 반복 절차가 0이지, 사람이 없어진 게 아니다

배포 후 **반복** 절차가 0이 된 것이지, 사람이 없어진 것이 아니다.

- Secret 의 실제 값 — 저장소에 없다
- Helm 릴리스의 첫 설치 — 스크립트는 없는 릴리스를 설치하지 않고 멈춘다
- 차트 버전 올리기 — 값을 바꾸는 것과 다른 작업이라 스크립트가 거부한다
- 위키 글은 여전히 두 번 머지해야 운영에 나간다 — 작업 브랜치 → develop → main

## 한계 — 앱 이미지 롤백 리허설이 아직 없다

- 앱 이미지 롤백의 실제 리허설은 아직 안 했다. 블로그 복구 리허설과 달리, 스크립트와 계획만 있는 상태다.
- 데이터 계층 Helm 과 블로그 발행의 자동 스위치는 코드가 아니라 저장소 변수다. 끄고 켜기가 설정 한 줄이라 되돌리기 쉽지만, 저장소 파일만 봐서는 지금 켜져 있는지 알 수 없다.
