- 재개편 때 검증 없이 옮겨 온 위키 51편을 저장소에 대조하면 무엇이 나오나?
- 근거는 코드·매니페스트·커밋·로컬 DB 실측만 인정하고 docs 문서와 자체 보고서는 배제했으며, 검증 보고도 근거 파일까지 직접 따라간 뒤에만 고치기로 판단했다.
- 2026-08-10에 51편의 주장 764개를 검증해 CORRECT 569 / WRONG 56 / CANNOT VERIFY 139를 얻었고, WRONG 중 1건은 검증 쪽이 틀린 것을 .github/workflows/deploy.yml 을 직접 열어 확인했다.

위키 58편 중 51편이 사실 검증을 받은 적이 없었다. 앞선 정보구조 재개편에서 검증을 거친 것은
새로 쓴 7편뿐이고, 나머지 51편은 재개편 이전 원고를 그대로 옮겨 온 것이었다. 그 51편을
전수 검증하고 나온 오류를 고쳤다.

결과 비율은 앞선 7편과 크게 달랐다. 검증을 거친 7편은 주장 76개 중 CORRECT 54 / WRONG 2 /
CANNOT VERIFY 20이었는데, 옮겨 온 51편은 주장 764개 중 CORRECT 569 / WRONG 56 /
CANNOT VERIFY 139였다. WRONG이 몰린 곳도 고르지 않았다 — DB 22, 지도 8, 거버넌스 8,
저장소 8이었고, 인프라·백업·스프링 12편은 WRONG 0이었다.

## 검증은 병렬로, 수정은 순차로 돌렸다

51편을 13그룹으로 나눠 병렬로 검증했다. 검증은 읽기만 하므로 동시에 돌아도 서로 부딪히지
않는다.

수정은 정반대였다. 위키 58편이 scripts/seed-portfolio-wiki.mjs 한 파일에 있어 여러 배치가
동시에 고치면 서로의 쓰기를 덮는다. 그래서 배치마다 순차로 돌리고 사이마다 커밋했다.

근거의 기준을 먼저 정했다. 저장소 코드, k8s 매니페스트, 스크립트, git 커밋, 로컬 DB 실측만
근거로 인정했다. docs 아래의 md 문서와 자체 보고서는 인정하지 않았다 — 문서로만 뒷받침되는
주장은 CORRECT가 아니라 CANNOT VERIFY로 내렸다. 문서도 이번에 검증하는 원고와 같은
손으로 쓰였으므로, 같은 오류를 공유할 수 있기 때문이다.

## WRONG 56건이 다 같은 틀림은 아니다

56건을 뭉뚱그리면 이 위키가 거짓투성이였다는 인상이 남지만, 갈라 보면 성격이 둘이다.
대부분은 쓸 당시에는 맞았고 그 뒤 코드가 움직여 낡은 것이다. 아래 대표 넷의 정렬 되돌림과
JetBrains Mono가 이 종류이고, 탭 19개를 12개로 재편한 것과 V13~V18 마이그레이션이 갈아 치운
스키마 수치도 같다.

소수는 쓸 당시에도 저장소와 어긋나 있었다. db-schema-erd-map은 synced_at을 "읽거나 쓰는
코드가 없다"고 적었지만 ArticleService가 저장할 때 쓰고 있었고, 그 코드(커밋 a3d312d, 7/4)는
글(8/2)보다 한 달 앞선다. nextjs-frontend-redesign이 적은 「운영 검증」 탭 소속은 그 시점에도
OPERATE였고, 같은 글의 모바일 Public Edge 순서도 CSS order 규칙이 7/10부터 지금까지 같아
처음부터 어긋났다. minipc-k3s-cloudflare의 "외부 hostname은 두 개"는 글 자신의 표(8개)와도
어긋났다.

구분이 중요한 것은 처방이 다르기 때문이다. 처음부터 틀린 것은 쓸 때 저장소에 대조했으면
막혔지만, 낡는 것은 그렇게 못 막는다. 글은 코드와 달리 낡아도 아무 신호를 내지 않는다 —
코드가 낡으면 타입 오류나 테스트 실패가 나지만 문장은 조용히 틀린 채로 남는다.
[AI가 쓴 글을 거르는 하네스](/wiki/wiki-writing-harness)의 형식 검사가 사실의 낡음을 못 잡는
것과 같은 구멍이다.

## 무엇이 틀려 있었나 — 대표 넷

**글의 뼈대가 뒤집힌 것.** 커밋 0e0563a(8/2)가 문서 목록 정렬을 sortOrder 우선으로 바꿨는데,
5009e3d(8/8)가 다시 updatedAt 내림차순으로 되돌렸고 44b915d(8/10)가 start 탭만 예외로
남겼다. 글은 8/2 시점에 멈춰 "지금은 sortOrder가 화면 순서를 결정한다"고 적고 있었다.
세부가 아니라 중심 주장 전체가 거짓이었다.

**라이선스 판단이 뒤집히는 것.** JetBrains Mono를 "CSS fallback일 뿐 파일을 배포하지
않는다"고 적었는데, 커밋 2a99853(8/3)부터 자체 호스팅이었다. 배포하지 않으면 고지 의무가
없지만 배포하면 OFL 고지 의무가 생긴다.

**실제보다 좋게 적힌 보안 서술.** MinIO root 미사용, prefix 단위 최소 권한, 공개 조회의
GetObject 권한 — 셋 다 실제와 달랐다. 실제는 계정 하나에 버킷 전체 권한이고, 기술 로고
업로드 Job은 아직 root를 쓰며, 공개 조회는 익명 읽기다. 보안 서술은 지향을 현재형으로
적는 순간 거짓이 된다.

**복사하면 안 도는 값.** 예시 assetId가 형식이 달라 404가 나고, 폐기된 ?article= 경로가
남아 있고, cloudflared에 없는 서브커맨드 validate를 안내하고 있었다. 앞선 7편 검증에서도
같은 종류가 나왔다 — 런북의 kubectl -n monitoring이 실제로는 obs였고, 그 오류는 원본
원고에 있던 것이 재작성에 그대로 옮겨진 것이었다. 검증 없는 이식은 오류도 같이 옮긴다.

## 검증도 틀린다

WRONG 56건 중 1건은 글이 아니라 검증 쪽이 틀렸다. "partner-simulator는 CI에서 pytest를
안 돌린다"고 보고됐는데, .github/workflows/deploy.yml 의 Verify partner simulator 단계가
ruff, basedpyright, pytest 셋을 다 돌리고 있었다. 고치기 전에 그 파일을 직접 열어 봐서
잡혔다.

보고를 근거 파일까지 따라가지 않았으면 멀쩡한 CI 서술을 틀린 쪽으로 고칠 뻔했다. 검증
결과도 하나의 주장이다 — 수정이라는 쓰기 작업으로 넘어가기 전에 한 번 더 원본을 확인하는
단계를 검증 자체에도 적용했다.

## 저장소 밖은 노드에 붙어야 정해진다

글 둘이 Cloudflare Tunnel의 ingress 규칙 개수를 서로 다르게 적고 있었다(8개 대 7개).
config.yml이 miniPC에만 있어 저장소만으로는 어느 쪽도 가릴 수 없었다. LAN으로 붙어 파일을
읽고, 읽기 전용이라 안전한 cloudflared tunnel --config 경로 ingress validate 로 확인했다.

결과는 hostname 6개 + 404 catch-all = 규칙 7개였다. api와 admin hostname은 죽은 채 남은
것이 아니라 삭제돼 있었다. 덤으로 그동안 저장소에서 확인할 수 없던 Traefik NodePort
30220도 이때 확정됐다.

## 고칠 때 두 가지를 지켰다

**근거가 약해지면 숫자만 갈지 않고 결론을 바꾼다.** "19개 탭 중 8개가 작성일 동률이라
created_at을 정렬에서 뺐다"는 논거는 12탭 재편 뒤 해당 탭이 하나뿐이라 무너졌다. 숫자만
12로 갈면 겉만 맞는 거짓 논증이 된다. 근거를 값의 출처 — created_at이 커밋 묶음 날짜라
집필 순서를 담지 않는다는 사실 — 로 옮겨 적었다.

**낡을 수치에는 시점을 박는다.** revision 행 수 같은 로컬 DB 값은 고쳐 놔도 다음 주에 또
틀린다. "2026-08-10 로컬 기준"을 문장에 박아, 값이 어긋나면 거짓말이 아니라 낡은 스냅샷이
되게 했다.

## 곁다리로 잡힌 것도 함께 고쳤다

- 가이드가 요구하는 방향과 반대였던 flowchart LR 7건을 전부 TB로 바꿨다.
- kind 오분류 16편을 정정했다. 14편은 「잘못 짚은 원인」 서사가 없어 postmortem에서 wiki로
  바꿨고, 2편은 본문이 후보·기각·결정의 뼈대를 따르고 있어 adr로 갔다.
- 같은 탭 안에서 겹치던 sortOrder 4쌍을 떼어 놓았다.
- CLAUDE.md의 테스트 기준선이 낡아 있었다. spring 172 / web 82로 적혀 있었는데 실측이
  186 / 100이었고, 이번에 테스트 하나를 더해 187이 됐다.

## 한계 — CANNOT VERIFY 139건은 그대로 남았다

- **CANNOT VERIFY 139건은 고치지 않았다.** 틀렸다고 증명된 것이 아니라 저장소에 대조할
  근거가 없는 것이다. 호스트 설정(cloudflared·systemd·kubelet), 노드 실측 수치, values에
  태그가 없는 버전 핀이 대부분이다. 한 글은 주장 8건 중 1건만 CORRECT였다 — 사건 서사
  전체가 저장소 밖에 있었다.
- 근거 없는 경험담 9편이 남아 있다. "처음엔 X를 의심했다" 류인데 저장소에 흔적이 없다.
- 화면은 확인하지 않았다. 58편을 전부 손댔지만 렌더 결과를 보지 않았다. mermaid 방향과
  kind 배지가 바뀌는 변경이라 브라우저에서 봐야 한다.
- 검증 자체의 정확도는 재지 않았다. 오답 1건은 우연히 잡힌 것이지 표본으로 잰 값이 아니다.
