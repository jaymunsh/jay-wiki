- 회고·로드맵 탭의 글이 무엇을 붙였는가가 아니라 왜 그렇게 했고 어디서 실패했으며 어떻게 복구했는가로 읽히게 만드는 형식이다.
- 설명하는 글과 기록하는 글을 구분하고, 날짜와 SHA와 소요 시간을 가진 기록하는 글은 작업이 끝난 뒤가 아니라 시작할 때 준비하기로 판단했다.
- 기록하는 글을 직접 쓰면서 image SHA나 row count는 사후에도 찾을 수 있지만 복구에 걸린 시간과 서비스가 돌아온 순서는 그때 재지 않으면 남지 않는다는 것을 확인했다.

기능을 많이 만들었다고 해서 좋은 포트폴리오가 되는 것은 아니다. 방문자가 알고 싶은 것은
무엇을 붙였는가보다 왜 그렇게 했고, 어디서 실패했으며, 어떻게 복구했는가다.

## 글마다 여섯 질문에 답하는 구조로 쓴다

| 항목 | 질문 |
|---|---|
| 문제 | 왜 이 작업이 필요했나 |
| 선택 | 어떤 선택지를 비교했나 |
| 실패 | 실제로 어디서 막혔나 |
| 해결 | 어떻게 고쳤나 |
| 확인 | 지금 운영 화면에서 무엇으로 볼 수 있나 |
| 보류 | 왜 아직 하지 않은 것이 있나 |

## 기능이 아니라 선택을 쓴다

CI/CD 글은 workflow 파일을 만든 이야기가 아니다. 수동 tar 배포가 반복 운영에 맞지 않았고,
Cloudflare Access SSH가 GitHub-hosted runner와 맞지 않아 miniPC self-hosted runner를 선택한 이야기다.

백업 글은 CronJob을 만든 이야기가 아니다. dump 파일 생성만으로는 백업이라 할 수 없고,
restore 리허설까지 실제로 돌린 이야기다.

## 설명하는 글과 기록하는 글은 다르다

지금 이 위키의 글은 대부분 **설명**이다. 왜 이렇게 설계했는지를 말한다.
설명은 필요하지만, 그것만으로는 운영해봤다는 증거가 되지 않는다.

**기록**은 다르다. 날짜가 있고, 커밋 SHA 나 run URL 이 있고, 걸린 시간이 있고,
무엇이 예상과 달랐는지가 있다.

| | 설명하는 글 | 기록하는 글 |
|---|---|---|
| 주어 | 이 시스템은 | 2026년 7월 9일에 나는 |
| 증거 | 구조도, 표 | image SHA, trace id, row count, 소요 시간 |
| 반증 가능성 | 낮다 | 높다. 숫자가 틀리면 바로 드러난다 |

이 구분을 세운 뒤 운영 검증 탭이 생겼고, 배송 실패 요청의 trace id나 재부팅 뒤 관찰값처럼
날짜와 숫자를 가진 글이 쌓이기 시작했다. 그래도 아직 **설명이 기록보다 많다.**
[로드맵](/wiki/roadmap-after-content)에 남은 항목이 대부분 기록하는 글인 이유다.

기록하는 글을 쓰다 보니 알게 된 것이 있다. 사후에 쓸 수 있는 기록과 그렇지 않은 기록이 나뉜다.
image SHA나 row count는 나중에도 찾을 수 있지만, 복구에 걸린 시간이나 각 서비스가 돌아온 순서는
그때 재지 않으면 영영 남지 않는다. **그래서 기록하는 글은 작업이 끝난 뒤가 아니라 시작할 때 준비하기로 했다.**

## 장애와 개선을 전부 이 형식으로 쌓는다

운영 중 생기는 장애와 개선은 모두 위 형식으로 회고·로드맵 탭에 쌓는다. 이 위키는 완성된 결과만
전시하는 곳이 아니라, 결정을 설명하는 운영 기록이 된다.
