- 로그인, 자유게시판, 채팅과 이미지 업로드가 있는 개인 서비스를 공개하기 전에 어떤 법적 공백을 닫아야 했는가?
- 고지를 잘 쓰는 일보다 수집 항목 자체를 줄이는 일이 먼저라고 보고, 열리는 기능이 없던 구글 로그인을 떼고 /privacy 처리방침을 footer에서 닿게 공개했다.
- 기능별 데이터 흐름을 표로 그려 처리방침을 작성하기 전에 이미 개인정보를 처리하고 있었다는 사실을 확인했고, 남은 공백은 P0·P1 우선순위와 완료 기준으로 구분해 남겼다.

개인 포트폴리오라는 이름이 법적 책임을 없애지는 않는다. 정적인 소개 페이지와 달리 jay-wiki는
로그인, 자유게시판, 채팅, 이미지 업로드와 운영 로그를 제공한다. 기능이 생기면 처리하는 데이터와
이용자의 권리도 생긴다.

이 글은 2026-07-15 대한민국에서 공개 운영하는 현재 저장소를 기준으로 한 기술·운영 점검이다.
법률 자문이 아니며, 서비스 범위와 법령이 바뀌면 다시 검토할 전제로 썼다.

## 먼저 실제 데이터 흐름을 확인했다

| 기능 | 처리하는 정보 | 저장 위치·기간의 현재 상태 |
|---|---|---|
| 로컬 가입 | 아이디, BCrypt 비밀번호 hash, 닉네임, 가입 시각 | PostgreSQL, 탈퇴 기능 미구현 |
| 인증 | JWT cookie | HttpOnly·Secure·SameSite=Lax, 만료 후 삭제 |
| 자유게시판 | 제목, 본문, 닉네임, 선택적 삭제 비밀번호 hash, 댓글 | PostgreSQL, 게시물별 삭제 가능 |
| 채팅 | 임시 userId, 닉네임, 메시지와 접속 상태 | Redis TTL·퇴장 정리, 공개 화면 노출 |
| 운영 관측 | 요청 metadata가 포함될 수 있는 metrics·logs·traces | Prometheus 7일, Tempo 24시간, Loki 기간 명시 필요 |
| 외부 경계 | Cloudflare 요청 처리 | 처리위탁·국외이전 여부와 사업자 정보를 정책에 명시 필요 |

가장 중요한 발견은 개인정보 처리방침을 작성하기 전에 이미 개인정보를 처리하고 있었다는 점이다.
코드가 안전해도 이용자에게 목적, 항목, 기간과 권리행사 방법을 공개하지 않으면 출시 준비가 끝난 것이 아니다.

이 표를 다시 그리면서 한 줄이 통째로 사라졌다. 구글 로그인이다. 받아 가는 항목은 가장 많은데
그것으로 열리는 기능이 없어서, 항목을 줄이는 대신 기능을 걷어냈다. 자세한 판단은
[USER 역할이 지키는 경로가 하나도 없다는 것을 나중에 알았다](/wiki/admin-user-role-boundary)에 있다.

## 남은 공백은 P0·P1 우선순위로 구분해 남겼다

| 우선순위 | 현재 공백 | 완료 기준 |
|---|---|---|
| P0 | 아동 처리 기준 없음 | 만 14세 미만 미제공 또는 법정대리인 동의 절차 중 하나 선택 |
| P0 | 게시물 권리침해 신고 경로 없음 | 개인정보·명예훼손·저작권 신고, 임시조치와 통지 절차 |
| P0 | Cloudflare 등 외부 처리자 정리 없음 | 위탁·국외이전 항목, 국가·시점·방법·보유기간 검토 |
| P1 | 로그와 backup 보유기간 불완전 | 시스템별 기간, 접근자, 파기와 복구본 반영 기준 |
| P1 | self-service 탈퇴 미구현 | 게시판 요청 없이 화면에서 직접 계정을 삭제 |
| P1 | 이미지 출처 metadata 없음 | 제작자, 원본 URL, 라이선스와 편집 내역 |

개인정보 보호법 제30조는 처리 목적, 보유 기간, 제3자 제공, 파기, 처리위탁과 정보주체 권리 등
개인정보 처리방침에 포함할 항목을 정한다. 정책은 footer와 로그인 화면에서 쉽게 찾을 수 있어야 한다.

### 닫힌 항목

**개인정보 처리방침 페이지가 생겼다.** /privacy 에 두고 footer에서 로그인 없이 닿는다(시행일 2026-08-07). 블로그는
수집 항목이 달라 따로 둔다. 처리방침을 나중에 쓰니 오히려 짧아졌다. 받는 것이 아이디, 비밀번호 hash,
닉네임, 가입 시각 넷뿐이라 적을 것이 없었다. **항목을 줄이는 일이 문서를 잘 쓰는 일보다 먼저다.**

**탈퇴·열람·정정·삭제 요청 경로도 이 페이지가 닫았다.** 처리방침이 자유게시판을 요청과 문의 창구로
공개하고, 계정 삭제는 게시판으로 요청하면 처리한다고 적었다. 남은 공백은 창구가 아니라
self-service다 — 화면에서 직접 하는 탈퇴는 아직 없고, 위 표의 P1로 남겨 둔다.

구글 OAuth 데이터 사용 고지도 목록에서 빠졌다. 고지를 잘 써서가 아니라 그 데이터를 더 받지 않기
때문이다. 규모가 이 정도인 서비스에서는 이쪽이 더 확실하게 닫는 방법이었다.

- [개인정보 보호법](https://www.law.go.kr/LSW/lsInfoP.do?lsiSeq=270351)
- [개인정보 처리방침 수립·공개 조문](https://www.law.go.kr/lsLawLinkInfo.do?chrClsCd=010202&lsJoLnkSeq=900078922)

## Google 로그인은 버튼 하나로 끝나지 않았다

처음 이 점검을 할 때 이 절의 제목은 현재형이었고, 아래에 해야 할 일이 다섯 개 적혀 있었다.
홈페이지와 처리방침 공개, 구글 데이터의 접근·사용·저장·공유 방식 설명, 동의 화면의 앱 이름과
homepage와 privacy policy를 실제 도메인과 일치시키기, 불필요한 scope 안 늘리기, 지원 창구와
도메인 소유권 검증. 구글은 운영 OAuth 앱의 공개 homepage에 기능 설명과 약관·처리방침 링크를 요구한다.

버튼은 반나절이면 붙지만 그 뒤에 붙는 의무는 반나절로 끝나지 않는다는 것이 그때의 결론이었다.

2026년 8월 6일에 다섯 개를 하는 대신 버튼을 뗐다. 그 로그인으로 열리는 기능이 없었기 때문이다.
목록을 지우려고 뗀 것이 아니라, 뗄 수 있는지 물어보니 뗄 수 있었다.

**이 절을 통째로 지우지 않고 남기는 이유가 있다.** 다음에 외부 로그인을 붙일 일이 생기면 여기 적힌
다섯 개가 그때도 그대로 따라온다. 붙이기 전에 이 목록을 먼저 읽는 편이 낫다.

- [Google OAuth 2.0 정책](https://developers.google.com/identity/protocols/oauth2/policies)
- [Google OpenID Connect 정보 항목](https://developers.google.com/identity/openid-connect/reference)

## cookie banner가 먼저 필요한 것은 아니다

현재 사이트에는 광고, 행동 추적 analytics나 마케팅 cookie가 없다. JWT는 로그인을 유지하는 필수
cookie다. 따라서 한국 사용자만을 대상으로 한 현재 범위에서는 무조건 동의 banner를
붙이는 것보다 개인정보 처리방침에 cookie 이름, 목적, 기간과 거부 시 영향을 정확히 적는 일이 우선이다.

향후 광고·분석 SDK를 추가하거나 EU 등 다른 관할의 이용자를 적극 대상으로 삼으면 별도 동의 관리와
해당 지역 규정을 다시 검토한다. banner를 설치했다는 사실만으로 개인정보 처리가 적법해지는 것은 아니다.

## 자유게시판은 삭제 버튼만으로 충분하지 않다

게시물 작성자는 타인의 개인정보, 명예를 침해하는 글이나 권리 없는 이미지를 올릴 수 있다.
정보통신망법은 사생활 침해·명예훼손 정보의 삭제 요청과 임시조치를, 저작권법은 복제·전송 중단 요청과
온라인서비스제공자의 대응 절차를 둔다.

따라서 자유게시판에 둘 운영 경계를 다음과 같이 정했다. 위 P0 표대로 아직 갖춰지지 않은 것이 있다.

- 금지 콘텐츠와 관리자 삭제 기준을 이용약관·운영정책에 공개한다.
- 게시물 URL, 권리 내용과 연락 수단을 받는 신고 창구를 둔다.
- 권리 판단이 어렵고 분쟁이 예상되면 접근을 임시 차단하고 양 당사자에게 알린다.
- 저작권 중단·재개 요청의 접수와 처리 기록을 남긴다.
- 작성 본문에 주민번호, 연락처와 같은 개인정보를 올리지 않도록 안내한다.

- [정보통신망법 제44조의2](https://www.law.go.kr/lsLawLinkInfo.do?chrClsCd=010202&lsJoLnkSeq=900628377)
- [저작권법 제102조·제103조](https://www.law.go.kr/LSW/lsInfoP.do?lsId=000798)

## 현재 기술 통제와 법적 고지는 서로 보완한다

현재 구현에는 HTTPS 공개 경계, HttpOnly·Secure cookie, BCrypt, 관리자 TOTP, ADMIN·USER 분리,
Markdown sanitization, rate limit, revision과 MinIO 참조 삭제 차단이 있다. 이는 개인정보 보호법의
안전조치 의무를 뒷받침하는 기술적 증거다.

그러나 기술 통제가 처리 목적과 보유 기간을 대신 설명해 주지는 않는다. 반대로 정책 문서를 게시했다고
접근통제와 유출 대응이 자동으로 생기지도 않는다. 법적 준비는 문구와 코드가 같은 사실을 말할 때 완성된다.

개인정보 유출을 알게 되면 어떤 정보가 언제 어떤 경위로 유출됐는지, 이용자의 대응 방법과 운영자의
조치·구제 연락처를 지체 없이 통지할 수 있어야 한다.

- [개인정보 보호법 제29조 안전조치](https://law.go.kr/LSW/lsInfoP.do?lsiSeq=270351)
- [개인정보 보호법 제34조 유출 통지](https://law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1020398739)

## 통신판매업 신고는 현재 범위에 해당하지 않는다

Saga 결제 화면은 실제 상품 판매나 금전 결제가 없는 장애 시연이다. 현재 범위에서는 통신판매업 신고,
결제 취소·환불과 전자상거래 사업자 표시를 적용할 거래가 없다. 화면에도 실제 결제가 아니라는 점을
계속 명확히 표시한다.

위치정보, 광고성 정보 전송, CCTV, 민감정보 처리도 현재 기능에 없다. 이런 기능을 추가하면 이 결론을
그대로 재사용하지 않고 별도 법률과 동의 절차를 다시 검토한다.

## 출시 판정 — 공개 정책과 권리행사 절차가 공백이다

현재 상태는 **기술적 보호조치는 여러 개 구현됐지만 공개 정책과 권리행사 절차는 출시 전 보완 필요**다.
개인 포트폴리오이므로 괜찮다고 쓰는 대신 무엇이 구현됐고 무엇이 아직 공백인지 구분한다.

법률 전문가처럼 모든 조문을 안다고 주장하는 것보다, 기능을 데이터 흐름으로 펼치고
공식 근거를 확인한 뒤 정책·코드·운영 절차를 같은 체크리스트로 관리했다는 점을 설명하는 편이 정확하다.
