사이트는 잘 열리고 백업도 돌고 있었다. 외부 요청은 터널로 받고 데이터베이스는 클러스터 안에 뒀으니, 보안도 어느 정도 정리되어 있다고 생각했다.

원래 보안을 볼 생각으로 시작한 게 아니었다. 이 프로젝트를 처음 보는 쪽에 설명할 브리프를 만드느라 구조, 돌리는 법, 왜 이렇게 설계했는지, 함정은 무엇인지를 한 파일에 적고 있었다. 그러다 답하지 못한 질문이 하나 나왔다. **그 판단을 마지막으로 검증한 게 언제였나.** 구조를 그렇게 설계한 것은 맞는데, 설계한 대로 동작하는지 확인한 기억이 없었다.

확인해 봤더니 몇 군데가 실제로 열려 있었다. 개선점을 모으는 작업이 아니라, 실제 상태를 코드와 서버에서 대조하는 작업이 됐다.

**2026년 9월 9일 정리.** 첫 점검의 수정은 9월 7일 운영에 반영했다. 이 글은 그 점검과 검증 과정을 다룬다. 이후의 보안 후속 개선과 유지보수는 [두 번째 글](/67/jaywiki-security-followup-maintenance-2026-09)로 나눴다. 취약점 수치는 당시 검사 기록이며 오늘의 재스캔 결과가 아니다.

## 점검 범위를 여덟 갈래로 잡았다

무엇을 볼지부터 적었다. 범위를 안 적고 시작하면 눈에 띄는 것만 보다가 끝난다.

| 갈래 | 무엇을 보나 |
|---|---|
| 호스트 권한 | 파일 권한, 관리자 자격 증명이 놓인 자리 |
| SSH·방화벽 | 실제 적용값. 저장소의 설정이 아니라 서버의 설정 |
| 클러스터 계정·권한 | 서비스 계정이 무엇을 할 수 있나 |
| 서비스 간 통신 | 누가 어디에 닿을 수 있나 |
| 웹 인증·입력·헤더 | 요청 제한, 본문 크기, 응답 헤더 |
| 의존성·이미지 | 라이브러리와 컨테이너를 따로 |
| 비밀정보·CI | Git 이력에 남은 것, 자동 검사의 유무 |
| 백업·복구 | 백업이 실제로 도는가 |

그리고 원칙을 하나 정했다. **고쳤다는 말은 운영에서 확인한 범위에만 쓴다.** 로컬에서 고친 것과 서버에 반영된 것을 같은 칸에 적으면, 나중에 이 글을 근거로 판단할 때 틀린다.

## 컨트롤러만 읽은 판단은 틀렸고, 진짜 빠진 자리는 회원가입이었다

처음에는 로그인 시도 제한이 비밀번호 확인 뒤 OTP 단계에만 있다고 적었다. 컨트롤러만 보면 로그인에 제한이 없어 보였기 때문이다. 그런데 호출 경로를 따라가 보니 제한은 공통 인터셉터에 있었다. 인터셉터가 로그인과 공개 시연 API에 IP별 제한을 걸고 있었고, 그 목록에서 빠진 경로는 회원가입이었다. **한 파일을 읽고 내린 결론과 호출 경로를 따라간 결론이 달랐다.** 판단을 정정하고 나니 덤으로 진짜 빠진 자리가 나온 셈이다.

제한 없는 회원가입은 계정을 대량으로 만들 수 있다는 것보다 나쁜 문제가 있다. **비밀번호 해싱은 일부러 느리게 설계된 연산이다.** 제한이 없으면 요청 자체가 CPU를 태우는 도구가 된다. 로그인에는 그 방어가 있는데 회원가입에는 없었다. 여기에 같은 제한을 걸었다.

## 웹 쪽에서 셋을 더 고쳤다

회원가입 제한 말고도 애플리케이션에서 고친 것이 셋 있다.

**요청 본문에 상한을 걸었다.** BFF가 요청과 응답을 통째로 메모리에 읽고 있었고 명시적인 타임아웃도 없었다. 헤더의 길이만 믿지 않고 실제로 읽은 바이트를 세도록 바꿨다. 상한은 백엔드가 이미 갖고 있는 업로드 제한보다 살짝 위로 잡았다. 그래야 정상 업로드는 그대로 통과하면서, 그보다 큰 것이 웹 프로세스의 메모리를 먹기 전에 끊긴다.

**변경 요청에 출처 검사를 넣고 응답 헤더를 채웠다.** 첫 수정은 `Origin`이 있으면 요청의 호스트와 대조하는 방식이었다. 헤더가 없는 서버 간 호출도 있어 누락 자체는 거부하지 않았다. 이것만으로 모든 CSRF 경로를 검증했다고 볼 수는 없다. 응답에는 콘텐츠 타입 스니핑 금지, 프레임 삽입 제한, 리퍼러 정책, 권한 정책, 그리고 최소한의 콘텐츠 보안 정책을 넣었다. 후속 수정에서는 출처의 스킴까지 대조하도록 보완했다.

**빌드 컨텍스트에서 환경 파일을 제외했다.** `.dockerignore` 가 `.env` 를 안 걸러서 이미지 빌드에 들어갈 수 있었다. 실제로 들어갔는지와 별개로, 들어갈 수 있는 경로 자체를 막았다.

## 정책이 있다는 사실과 접근이 막힌다는 사실은 달랐다

이번 점검에서 제일 값이 나온 자리다.

### 저장소가 아니라 클러스터를 열어 봤다

처음 저장소를 읽었을 때는 일부 데이터 서비스에만 접근 정책이 있는 것으로 보였다. 그런데 클러스터에 붙어 보니 Helm이 만든 정책이 더 있었다. 차트가 자기 정책을 함께 설치하기 때문이다. **파일 목록만으로 운영 설정을 설명하면 틀린다.** 저장소는 무엇을 의도했는지를 말하고, 클러스터는 무엇이 있는지를 말한다.

정책이 있다는 것으로 끝낼 수도 없었다. 규칙 내용을 열어 보니 이랬다.

```json
"ingress": [
  { "ports": [ { "port": 6379, "protocol": "TCP" } ] }
]
```

**`from` 이 없다.** 목적지 포트만 있고 접속 주체 제한이 없다. NetworkPolicy에서 `from` 이 빠진 규칙은 "이 포트는 누구에게나 연다"는 뜻이다. 정책 객체는 존재하는데 아무도 막지 않고 있었다. 검색 엔진 쪽에는 정책이 아예 없었다.

### 말로 끝내지 않고 두 방향으로 두드려 봤다

이 두 서비스를 쓸 이유가 전혀 없는 프런트엔드 파드에서 연결을 시도했다. 붙었다.

접근 대상을 필요한 백엔드로 좁힌 뒤 같은 검사를 반복했다.

```text
backend:  Redis and OpenSearch TCP access passed
frontend: [{"host":"redis...","reachable":false,"reason":"ECONNREFUSED"},
           {"host":"opensearch...","reachable":false,"reason":"ECONNREFUSED"}]
```

**두 방향을 같이 재야 변경을 설명할 수 있다.** 필요한 연결이 살아 있다는 검사만 하면 아무것도 안 막았을 때도 통과한다. 불필요한 연결이 막혔다는 검사만 하면 서비스를 죽여 놓고도 통과한다. 둘을 함께 놓아야 "좁혔고 살아 있다"가 된다.

여기서 하나를 알아 둬야 한다. **NetworkPolicy의 ingress는 여러 정책의 허용 범위를 합친다.** 전체를 허용하는 기존 규칙을 남겨 둔 채 제한적인 정책을 하나 더 얹는 것으로는 경계가 생기지 않는다. 이 성질이 뒤에서 다시 돌아온다.

## 실행 권한이 있는 곳에 무엇이 함께 있는지 봤다

관리자 화면에 오토스케일링을 시연하는 기능이 있다. 부하를 만드는 Job을 띄우고, 파드가 늘어나는 것을 보여주고, 끝나면 지운다. 그러려면 Job 생성 권한이 필요하다.

문제는 그 권한이 **애플리케이션 Secret과 같은 네임스페이스**에 있었다는 점이다. 서비스 계정에 Secret 조회 권한이 없다는 사실만으로는 충분하지 않다. **워크로드를 만들 수 있으면, 그 워크로드에 다른 리소스를 붙이는 경로까지 함께 봐야 한다.** Kubernetes 문서도 워크로드 생성 권한을 권한 상승 경로로 분류한다.

시연 Job을 별도 네임스페이스로 옮겼다. 그 네임스페이스에는 애플리케이션 Secret을 두지 않고, Restricted Pod Security와 자원 상한을 걸고, 통신 대상도 시연에 필요한 것만 남겼다. 부하 Job이 실제로 필요한 건 백엔드 한 곳과 이름 풀이뿐이다.

옮길 때 놓치기 쉬운 것이 둘 있었다. **Job을 만드는 코드만 고치면 안 된다.** 취소와 로그 조회도 같은 경계를 써야 한다. 부하 결과를 파드 로그에서 되읽는 구조라, 생성만 옮기면 결과를 못 읽는 반쪽이 된다. 그리고 앱이 만드는 Job 스펙 자체도 새 네임스페이스의 요건을 만족해야 한다. Restricted 정책은 비-root 실행, 권한 상승 금지, 커널 능력 전부 제거, 기본 seccomp 프로파일을 요구한다. 자원 상한이 걸려 있으니 요청량과 상한도 둘 다 적어야 한다. 이걸 안 넣으면 배포는 되는데 시연을 누르는 순간 Job이 거부된다.

## 호스트는 관리자 권한이 필요해서 직접 쳤다

### 읽기 전용 스크립트로 셋을 찾았다

방화벽의 최종 적용값, SSH 설정의 실제 값, Secret 저장 암호화 여부는 전부 관리자 권한이 필요한 조회다. SSH로 붙는 것과는 별개의 문이라, 이 부분은 우회하지 않았다. **읽기 전용 점검 스크립트를 만들어 내 터미널에서 직접 실행했다.** 스크립트는 설정을 변경하지 않고 비밀정보 내용도 출력하지 않는다. 관리자 비밀번호를 점검 도구나 기록에 넣는 것보다, 사람이 직접 치고 결과 파일만 남기는 쪽이 낫다고 봤다.

결과에서 셋이 나왔다. SSH가 비밀번호 로그인을 허용하고 있었다. 키가 있는데 비밀번호 경로가 함께 열려 있으면 약한 쪽이 기준이 된다. 관리자 kubeconfig 권한이 644였다. 그 머신의 다른 로컬 계정이 클러스터 관리자 자격을 읽을 수 있다는 뜻이다. 그리고 Secret 저장 암호화가 꺼져 있었다. 저장소를 통째로 가져가면 Secret이 그대로 읽힌다.

방화벽은 켜져 있었고 기본 인바운드는 거부였다. 자동 업데이트도 켜져 있었다.

### 600으로 바꾸면 배포가 끊긴다는 것을 먼저 봤다

kubeconfig 권한은 고쳐야 한다. 그런데 그냥 600으로 바꾸면 안 됐다. **배포 러너가 그 원본 파일을 읽기 때문이다.** 보안을 고치는 변경이 배포 파이프라인을 끊는다. 그래서 600이 아니라 **640으로, 소유자와 관리자 그룹만 읽도록** 제한했다. 사용자 계정에 있던 사본은 600으로 내렸다.

SSH도 같은 계산을 했다. 비밀번호 로그인과 root 로그인과 X11 전달은 껐지만 **TCP 포워딩은 남겼다.** 데이터베이스 도구가 SSH 터널로 붙기 때문이다. 전부 끄는 게 제일 안전하지만 그러면 쓰던 게 죽는다.

**권한을 가장 좁게 주는 것이 항상 정답은 아니다.** 그 파일을 지금 누가 읽고 있는지, 그 설정을 지금 무엇이 쓰고 있는지 먼저 보고 나서, 끊지 않는 범위에서 제일 좁은 값을 골라야 한다.

접속 경로를 고치는 작업이라 복구 수단도 함께 준비했다. 원본을 백업하고, 실패하면 되돌리고, SSH 설정만 reload하고 클러스터와 터널은 재시작하지 않는다. 그리고 **새 접속이 되는 것을 확인할 때까지 실행 중인 터미널을 닫지 말 것.** 원격 접속 설정을 고치는 작업에서 이건 필수다. 지금 열려 있는 세션이 마지막 복구 수단이다.

## 검사 도구가 0개 파일을 읽고 성공을 반환했다

의존성은 세 갈래를 따로 봤다. Node와 Python은 잠금 파일을, Java는 **실제 실행 JAR에 들어간 라이브러리**를 봤다. 선언된 의존성 목록과 최종 산출물이 항상 같지는 않기 때문이다.

그런데 Java 검사가 한 번 이상하게 끝났다. 도구는 성공으로 종료했고 취약점은 0건이었다. 디버그 로그를 열어 보니 이랬다.

```text
INFO  Number of language-specific files  num=0
WARN  [report] Supported files for scanner(s) not found.  scanners=[vuln]
```

**파일을 하나도 안 읽었다.** 취약점이 0건인 게 아니라 검사 대상이 0개였다. 종료 코드만 봤으면 이 결과를 「취약점 없음」으로 적었을 것이다.

JAR을 직접 읽는 방식으로 바꾸자 실제 결과가 나왔다. Critical 3, High 6, Medium 15였다. 프레임워크 구성요소를 올려서 다시 재니 0건이 됐다.

**성공한 검사와 무언가를 검사한 것은 다르다.** 0이라는 숫자는 "없다"와 "안 봤다" 양쪽에서 나온다. 그리고 두 경우의 로그가 겉으로는 똑같이 생겼다.

## 앱 검사를 통과해도 이미지 검사는 따로 남았다

웹 의존성을 올려서 경고가 0건이 됐다. 그다음 컨테이너 이미지를 검사하니 다시 경고가 나왔다.

당연한 일이다. 이미지에는 애플리케이션 라이브러리만 들어 있는 게 아니다. 운영체제 패키지와 런타임 도구가 함께 있다. **앱의 잠금 파일 검사와 배포 이미지 검사는 서로 다른 질문에 답한다.** 앞의 것은 "내가 가져다 쓴 것이 안전한가"이고, 뒤의 것은 "실제로 서버에서 도는 덩어리가 안전한가"다.

이미지에 OS 패치 단계를 넣고, 웹 런타임에서는 실행 중에 쓰지 않는 패키지 관리자를 지웠다. 그리고 다섯 이미지를 최종 설정으로 빌드해서 다시 쟀다.

| 이미지 | 최초 | 최종 | 수정본이 있는데 안 잡은 것 |
|---|---|---|---|
| 웹 | High 12 / Critical 1 | **0건** | 0 |
| Spring | 앱 의존성만 쟀었다 | **0건** | 0 |
| 파트너 시뮬레이터 | High 77 / Critical 9 | High 55 / Critical 5 | **0** |
| 결제 API | 안 쟀었다 | High 55 / Critical 5 | **0** |
| 배송 API | 안 쟀었다 | High 55 / Critical 5 | **0** |

오른쪽 끝 칸이 중요하다. Python 서비스 셋에 숫자가 크게 남았지만 **그중 고칠 수 있는 것은 0건이다.** 남은 항목의 상태가 전부 「수정본 없음」 계열이고 「수정본 있음」이 하나도 없다. 배포판이 아직 고치지 않았다는 뜻이라, OS 패치 단계가 할 수 있는 일은 이미 다 했다.

**숫자를 그대로 적고 조치 가능 여부를 옆에 두는 것이 맞다고 봤다.** 55라는 숫자만 적으면 방치처럼 보이고, 예외 파일로 지워 버리면 다음에 수정본이 나와도 안 보인다. 취약점 건수를 침해 건수처럼 쓰지 않는 것도 같은 이유다. 다음에는 수정본 제공 여부와 불필요한 패키지 제거, 기반 이미지 교체를 함께 검토해야 한다. 이미지 교체는 런타임 동작이 달라질 수 있어 첫 점검에서는 하지 않았다.

## 컨테이너를 root에서 내렸고, 검증하다 한 번 헛짚었다

다섯 이미지를 전부 비-root 사용자로 내렸다. 배포 매니페스트에도 같은 설정을 넣고, 권한 상승 금지와 커널 능력 제거를 걸었다. 웹은 클러스터 API를 부를 일이 없어서 서비스 계정 토큰도 안 붙이도록 했다.

읽기 전용 루트 파일시스템은 걸지 않았다. 자바 웹 서버가 임시 디렉터리를 만들어야 하고 파이썬 쪽도 캐시를 쓴다. 걸려면 쓰기 가능한 볼륨을 따로 붙여야 하는데, 그건 이번에 안 했다.

그리고 검증 단계에서 한 번 헛짚었다. 컨테이너를 띄우고 실행 사용자를 확인했는데 **root가 나왔다.** 원인은 이미지가 아니었다. 작업 브랜치에서 커밋한 뒤 기본 브랜치로 돌아온 상태에서 빌드해서, **보안 변경이 들어 있지 않은 예전 Dockerfile로 만든 이미지를 검사한 것이다.**

브랜치를 되돌리고 다시 빌드하니 정상이었다. 실행 사용자가 바뀌었고, 웹 서버가 6초에 기동했고, API 응답이 정상이었으며, 권한 관련 오류가 로그에 한 줄도 없었다.

**이미지 검증은 어느 브랜치에서 빌드했는지가 결과를 통째로 뒤집는다.** 특히 여러 세션이 하나의 작업 트리를 공유하는 저장소에서는, 검사 결과보다 먼저 빌드 입력이 무엇이었는지를 확인해야 한다.

## 미확인으로 남겨 둔 항목에서 진짜 결함이 나왔다

Redis 접근 정책은 점검 당시 운영 클러스터에 직접 패치했고, Helm values에도 대응 설정을 적어 뒀다. 그런데 그 values로 차트를 렌더하면 운영과 같은 정책이 나오는지는 그때 확인하지 못했다. 기록에는 그대로 「미확인」으로 남겨 뒀다.

나중에 대조해 봤다. **유지되지 않았다.** 저장소의 values로 차트를 렌더하니, 운영에 적용된 정책에 없는 항목이 하나 더 들어 있었다.

```yaml
from:
  - podSelector:
      matchLabels:
        redis-client: "true"     # 운영 정책에는 없다
  - podSelector: { 자기 자신 }
  - namespaceSelector: { 백엔드 } + podSelector: { 앱 }
```

차트는 외부 허용을 끄더라도 「같은 네임스페이스에서 특정 라벨을 단 파드는 통과」라는 항목을 **항상 끼워 넣는다.** 그리고 그걸 끄는 설정값이 없다.

앞에서 적어 둔 성질이 여기서 돌아온다. **ingress는 합집합이다.** 그 한 줄이 정책 전체를 넓힌다. 지금 그 라벨을 단 파드는 클러스터 전체에 0개라 뚫려 있지는 않다. 하지만 **다음에 이 릴리스를 Helm으로 올리는 순간, 손으로 좁혀 둔 운영 정책이 넓은 판으로 되돌아간다.** 손으로 고친 것과 저장소에 적힌 것이 갈라져 있었다는 뜻이다.

차트 정책을 끄고 표준 매니페스트로 직접 쓰는 쪽으로 옮겼다. 검색 엔진 쪽을 이미 그 방식으로 했으니 형태도 맞았다. 렌더 결과에서 정책이 사라지는 것과, 새 매니페스트가 허용하는 대상이 운영과 정확히 같은 둘인 것을 대조했다.

이 결함을 돌아와서 볼 수 있었던 건 확인 못 한 것을 확인 못 했다고 적어 뒀기 때문이다. 「적용 완료」라고만 적혀 있었으면 그 줄을 읽고 넘어갔을 것이다.

## 다음에 또 벌어지지 않도록 검사를 CI에 넣었다

한 번 점검해서 0으로 만들어도, 다음 의존성 업데이트와 설정 변경이 새 차이를 만든다. 그래서 자동 검사를 붙였다.

- Node 의존성 검사
- Python 의존성 검사
- **실제 Java JAR에 대한 취약점 검사** — 선언 목록과 최종 산출물이 같은지 확인한다
- Git 이력 전체에 대한 비밀정보 검사

마지막 것은 이번에 한 번 돌려서 후보 셋이 나왔는데, 열어 보니 문서의 예시 값과 격리된 테스트 픽스처였다. **넓은 패턴으로 무시하지 않고 정확한 지문만 예외에 적었다.** 그래야 다음에 진짜가 나오면 걸린다. 재검사에서 764개 커밋에 결과 0건이다.

이 부분은 후속 점검에서 설명을 바로잡았다. 첫 CI는 Java JAR을 검사했지만, 앞에서 수동으로 검사한 **다섯 컨테이너 이미지의 OS 패키지까지 계속 검사하는 구성은 아니었다.** 9월 8일에 이미지별 빌드·검사와 결과 보관 단계를 추가했다. 검사 대상 패키지가 0개면 실패시키고, 수정본이 있는 High·Critical 항목은 통과시키지 않도록 했다. 수정본이 없는 항목도 보고서에는 남긴다. 9월 10일 실제 GitHub 실행에서 런타임 이미지와 의존성·Secret 검사를 통과했다. 그 과정에서 발견한 HTTP 라이브러리 취약점 수정과 운영 전환·복원 검증은 [후속 기록](/70/jaywiki-security-followup-maintenance-2026-09)에 따로 정리했다.

## 고친 것과 운영에 반영한 것을 따로 적는다

다음은 **9월 7일 첫 점검 변경분**의 상태다. 후속 구현까지 운영에 들어갔다는 뜻은 아니다.

| 단계 | 상태 |
|---|---|
| 호스트 권한·SSH 설정 | 운영 반영 완료. 새 접속과 클러스터 접근으로 확인 |
| 데이터 서비스 접근 제한 | 운영 반영 완료. 양방향 검사로 확인 |
| 앱 의존성 패치 | 잠금 파일·실제 JAR 재검사 완료 |
| 앱 보안 수정 | 회원가입 제한, 본문 상한·타임아웃, 출처 검사, 보안 헤더 |
| 컨테이너 권한 축소 | 다섯 이미지 재빌드·재스캔·실행 사용자 확인. 개별 서비스 기동 검증 범위는 달랐으며 이후 배포·공개 화면 검사 통과 |
| 권한 분리 매니페스트 | 운영 반영 완료. rehearsal 네임스페이스가 생기고 백엔드 SA의 Job 생성이 그 안으로 갇혔다 |
| 회귀 검사 | 백엔드 274개, 웹 135개, 브라우저 8개 통과 |
| 운영 앱 배포 | 완료(2026-09-07). 네 잡 전부 통과, 롤백 없음 |

이 표의 목적은 하나다. **배포하지 않은 것을 반영했다고 적지 않는 것.** 권한 분리와 운영 앱 배포는 처음 이 글을 쓸 때 대기 상태였고, 배포가 끝난 뒤에 고쳤다. 권한 분리는 코드와 매니페스트가 함께 나가야 동작하므로 그때까지는 운영에 없었다.

## 배운 것

이번 점검은 Astra와 함께 진행했다. 저장소의 코드와 miniPC의 실제 설정을 오가며, 의심한 지점을 재현하고 잘못 짚은 판단을 고쳐 가는 과정에서 도움을 크게 받았다. 개인 프로젝트를 이 깊이까지 들여다볼 수 있다는 점이 인상적이었다. 아래에 남긴 판단의 근거는 그 과정에서 직접 확인한 응답과 실행 기록이다.

**정책이 있다는 것과 막힌다는 것은 다른 사실이다.** 파일이 존재하는지, 객체가 만들어졌는지는 검사하기 쉽다. 실제로 막히는지는 두드려 봐야 안다. 그리고 두 방향을 같이 재야 한다 — 필요한 것이 살아 있는지와 불필요한 것이 막혔는지 둘 다.

**0이라는 숫자는 두 가지에서 나온다.** 없어서 0일 수도 있고 안 봐서 0일 수도 있다. 검사 도구가 성공으로 끝났다는 것은 무언가를 검사했다는 뜻이 아니다. 그리고 두 경우의 출력은 겉으로 똑같이 생겼다.

**보안 수정이 운영을 끊을 수 있다.** 제일 좁은 권한이 항상 정답은 아니다. 지금 누가 그 파일을 읽고 그 설정을 쓰고 있는지 먼저 보고, 끊지 않는 범위에서 제일 좁은 값을 고른다.

**손으로 고친 것과 저장소에 적힌 것은 갈라진다.** 운영에 직접 적용해 급한 불을 끄는 건 맞지만, 그때 저장소가 같은 결과를 만드는지 대조하지 않으면 다음 배포가 조용히 되돌린다. 이번에 실제로 그런 자리가 하나 있었다.

**확인하지 못한 것은 확인하지 못했다고 적는다.** 무엇을 했는지는 저장소와 로그를 보면 대체로 복원된다. 무엇을 확인하지 못했는지는 적어 두지 않으면 영영 안 보인다. 이번에 찾은 실제 결함은 그렇게 적힌 줄에서 나왔다.

이번 기록에서 얻은 것은 안전하다는 판정이 아니다. **어느 경계를 확인했고 어느 경계를 아직 확인하지 못했는지 말할 수 있는 목록**이다.
