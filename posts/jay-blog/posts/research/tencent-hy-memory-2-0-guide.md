> **이 글의 대상**: 에이전트에 장기 기억을 붙이려는 개발자. 특히 Mem0이나 MemOS 같은 메모리 프레임워크를 쓰면서, 기억을 정리하는 데 큰 모델을 부르는 비용이 부담스러운 사람.

> **출처 및 기준일**: 1차 출처는 [Hugging Face 모델 카드](https://huggingface.co/Tencent/Hy-Memory-30B-A3B)다. 구성 요소와 프레임워크 수치는 [Let's Data Science의 10월 17일 기사](https://letsdatascience.com/news/tencent-open-sources-hy-memory-20-stack-f1fcc6c1), 지원 도구 목록은 [ifeng 보도](https://tech.ifeng.com/c/8xH3boMw0zC)를 참고했다. 공개일은 10월 16~17일이고, 판정 기준일은 10월 20일이다.

## 1. 기억은 '읽기'보다 '쓰기'가 어렵다

에이전트 기억 시스템은 보통 두 단계로 돈다. 대화나 작업이 끝나면 무엇을 남길지 정리해서 저장하고(쓰기), 다음 작업 때 관련된 것을 찾아 넣는다(읽기). 검색은 임베딩과 벡터 DB가 맡지만, 쓰기는 대개 범용 LLM이 맡는다. 무엇이 중요한지, 기존 기억과 충돌하면 어느 쪽을 믿을지, 어떤 형태로 남길지를 판단해야 하기 때문이다.

문제는 이 쓰기가 대화마다, 작업마다 일어난다는 점이다. 큰 모델로 돌리면 비싸고, 작은 범용 모델로 돌리면 엉뚱한 것을 기억한다. Hy Memory 2.0의 답은 **쓰기만 전담하는 작은 모델을 따로 학습시키는 것**이다.

## 2. 공개된 것은 모델, SDK, 앱 세 가지다

| 구성 요소 | 무엇인가 | 라이선스 |
|---|---|---|
| Hy-Memory-30B-A3B | 장기 기억 작성 모델. 전체 30B, 활성 약 3B의 MoE | Apache 2.0 |
| hy-memory SDK | 저장과 회수를 맡는 Python 프레임워크 | 기사에 명시 없음 |
| MemHub | 로컬 우선 데스크톱·CLI 앱. 여러 AI 도구의 기록을 한곳에 모은다 | 확인하지 못함 |

다루는 기억은 세 종류다.

| 종류 | 무엇을 남기나 |
|---|---|
| 대화 기억 | 사실을 시간·장소·인물이 있는 사건으로 묶고, 중복을 합치고, 충돌을 정리한다 |
| 작업 기억 | 작업 목표, 결정, 중간 결과, 그리고 적용 조건이 붙은 교훈 |
| 코드 기억 | 같은 방식을 소프트웨어 개발 작업에 적용한다 |

MemHub가 흥미롭다. Claude Code, Cursor, Codex, OpenCode, Qwen Code, DeepSeek Harness 같은 도구의 대화 기록과 작업 흔적을 사용자 허락 아래 로컬 디렉터리로 모은다. 그러면 한 도구에서 한 일을 다른 도구가 참조할 수 있다. 중국 보도에 따르면 지원 도구는 10개다. 세션이 끊기면 맥락이 사라지는 문제를 플러그인으로 풀었던 [jay-session](/14/jay-session-claude-code-plugin)과 같은 문제를, 도구 사이의 경계에서 푸는 시도다.

## 3. 작은 모델은 두 단계로 '기억 쓰는 법'을 배웠다

| 단계 | 내용 |
|---|---|
| Memory On-Policy Distillation | 학생 모델이 직접 쓴 기억 상태의 흐름에 교사 모델이 촘촘하게 지도 신호를 준다 |
| Attributed Memory RL | 기억 덩어리 단위로 기여도를 매기고, 고른 기억을 다음 창으로 넘기며 강화학습한다 |

학습에 쓰지 않은 프레임워크(EverMemOS)에서도 성능이 유지되는지를 따로 봤다. 특정 프레임워크의 형식에 맞춘 것이 아니라 기억을 쓰는 일반 능력을 배웠는지 확인하려는 설계다.

## 4. 평균은 Opus 5를 0.87점 앞섰다

모델 카드의 종합 표다. 같은 답변 모델, 같은 판정 모델, 같은 검색 설정을 두고 **기억을 쓰는 모델만 바꿔** 비교했다.

| 기억 작성 모델 | Mem0 | Hy-Memory | MemOS | EverMemOS (학습 제외) | 평균 |
|---|---|---|---|---|---|
| **Hy-Memory-30B-A3B** | **54.02** | **60.55** | **50.51** | **56.89** | **55.49** |
| Claude Opus 5 | 53.43 | 60.53 | 50.50 | 54.04 | 54.62 |
| DeepSeek V4.1 Flash | 49.73 | 60.20 | 49.17 | 55.47 | 53.64 |
| Hy3 | 45.99 | 58.06 | 50.19 | 52.30 | 51.63 |
| Qwen3.6-35B-A3B | 47.51 | 55.87 | 47.36 | 50.75 | 50.37 |
| Qwen3-30B-A3B | 39.81 | 45.67 | 45.44 | 46.57 | 44.37 |

같은 크기의 범용 모델(Qwen3-30B-A3B, 44.37)보다 11점 높다. 이 비교가 이번 공개에서 가장 설득력 있는 결과다. 같은 3B 활성 규모에서 "기억 쓰기 전용 학습"이 이만큼의 차이를 만든다는 뜻이기 때문이다.

## 5. 다만 Opus 5와의 차이는 대부분 측정 오차 수준이다

헤드라인은 "Opus 5를 넘었다"였지만, 표를 풀어 보면 이야기가 달라진다.

- **네 프레임워크 중 세 곳에서 차이가 0.6점 미만이다.** Hy-Memory 하네스에서는 0.02점, MemOS에서는 0.01점이다.
- **평균 차이의 대부분은 EverMemOS 한 곳에서 나왔다.** 이 하네스에서만 2.85점 차이가 났다.
- **모든 수치가 각 벤치마크의 고정 20% 부분 표본이다.** 표본이 작으면 0.01~0.6점 차이는 순위를 말하기 어려운 폭이다.

세부 지표에서는 Opus 5가 앞서는 곳도 많다. 대화 기억의 대표 지표인 LoCoMo를 Mem0 하네스에서 재면 Hy-Memory는 59.54, Opus 5는 69.47로 10점 가까이 뒤진다. 반대로 여행 계획(Travel SPS)처럼 작업 기억을 보는 지표에서는 Hy-Memory가 11점 이상 앞선다.

정리하면 "Opus 5보다 낫다"가 아니라 "**Opus 5와 비슷한 수준을 3B 활성으로 낸다**"가 정확하다. 비용으로 따지면 이것만으로도 충분히 큰 결과다.

프레임워크 전체의 수치도 따로 공개됐다. LoCoMo 정확도 72.6%, 질문당 토큰은 1,159개에서 703개로 39.3% 줄었다. 작업 기억(MemoryArena 여행·쇼핑) 평균은 55.31%, 코드 기억은 CodeMemoryBench 질의응답 64.2%, 작업 해결 35.6%다. 이 수치는 모델 단독 표와 설정이 달라서 직접 비교할 수 없다.

## 6. 로컬에서 띄우는 길은 넓다

3B 활성이라 개인 장비에서도 현실적인 크기다. 모델 카드가 안내하는 경로는 이렇다.

| 방법 | 내용 |
|---|---|
| vLLM | v0.31.0으로 시험. OpenAI 호환 API로 띄우고 `reasoning_effort: "no_think"`로 부른다 |
| SGLang | 서버 실행 또는 Docker |
| Transformers | pipeline이나 `AutoModelForCausalLM` |
| 양자화판 19종 | llama.cpp, Ollama, LM Studio, Jan |

기존 Mem0이나 MemOS를 쓰고 있다면, 기억을 쓰는 LLM 호출의 대상만 이 모델로 바꾸면 된다. 프레임워크를 갈아엎을 필요가 없다는 점이 도입 장벽을 낮춘다. 하드웨어 요구 사항은 모델 카드에 적혀 있지 않다.

## 7. 정리: 기억 쓰기 비용을 줄이려는 팀에게 먼저 맞는다

| 이런 경우라면 | 판단 |
|---|---|
| Mem0·MemOS의 기억 쓰기에 큰 모델을 부르고 있다 | 바꿔 볼 가치가 크다. 대상 모델만 교체하면 된다 |
| 대화 기억의 정확도가 가장 중요하다 | LoCoMo에서는 Opus 5가 10점 앞선다. 내 데이터로 비교한다 |
| 작업 기억(계획·결정 기록)을 쌓는다 | 이 모델이 상대적으로 강한 영역이다 |
| 여러 AI 도구의 기록을 한곳에 모으고 싶다 | MemHub를 시험해 본다. 성숙도는 아래 주의점을 본다 |

### 확인하지 못한 것과 주의점

- **모든 수치가 Tencent의 자체 보고다.** 독립 재현은 아직 없다.
- **MemHub의 성숙도가 불분명하다.** 한 블로그는 프로젝트 변경 기록에 "MemHub 공개 배포가 아직 없다"고 적혀 있다고 전했지만, GitHub에는 macOS·Linux용 v1.0.0 릴리스가 있다는 보고도 있다. Windows는 지원 대상이 아니라고 한다. 직접 확인하지 못했다.
- **개인정보 통제는 사용자의 몫이다.** MemHub는 여러 도구의 대화와 작업 기록을 한곳에 모은다. 로컬 우선이라고만 밝혔을 뿐, 암호화나 도구별 접근 경계에 대한 설명은 없다. 회사 코드가 오가는 도구라면 무엇이 모이는지부터 확인해야 한다.
- **커뮤니티 반응**: Hacker News나 Reddit에서 실사용 후기를 찾지 못했다. 보도는 대부분 발표 내용의 요약이었다.

## 10월 22일 수정: 다른 메모리 시스템과의 비교와 배포 상태

### 다른 메모리 시스템과 어디가 다른가

Hy Memory 2.0은 Mem0이나 Zep을 대체하는 프레임워크이기도 하고, 그 안에 넣는 기억 작성 모델이기도 하다. 많이 비교되는 시스템과 나란히 놓으면 이렇다.

| | Hy Memory 2.0 | Mem0 | Zep | Letta |
|---|---|---|---|---|
| 형태 | 프레임워크 + 전용 기억 모델 + 데스크톱 앱 | 기존 에이전트에 붙이는 메모리 API | 시간 축 지식 그래프 | 메모리가 내장된 에이전트 실행 환경 |
| 강점 | 기억 쓰기를 작은 전용 모델로 | 붙이기 쉽다 | 사실이 언제부터 언제까지 참이었는지 추적 | 에이전트를 직접 호스팅 |
| 라이선스 | 모델 Apache 2.0 | Apache 2.0 | Apache 2.0 (관리형 클라우드는 상용) | Apache 2.0 |

Tencent는 자사 프레임워크가 오픈소스 프레임워크 중 1위라고 밝혔다. 저장 공간이 입력 토큰의 6.06%로, 비교 대상의 31.9~41.2%보다 훨씬 작다는 수치도 냈다([OrcaRouter 정리](https://www.orcarouter.ai/blog/hy-memory-2-0-open-source-stack)). 다만 Zep과 Letta는 비교 대상에 없었다. 메모리 벤치마크는 업체마다 답변 모델, 판정 모델, 검색 깊이가 달라서 서로의 자체 수치를 그대로 비교하면 안 된다. Mem0도 LoCoMo 자체 보고치와 독립 측정치가 크게 다르다는 지적을 받은 적이 있다.

### 배포 상태는 아직 정리 중이다

- **MemHub는 문서대로 설치되지 않았다.** 10월 16일 기준으로 안내된 한 줄 설치의 npm 패키지 `memhub-cli`가 404였다. GitHub에는 macOS arm64와 Linux용 v1.0.0 묶음이 있지만, 변경 기록에는 "공개 릴리스 없음"이 남아 있다. 본문 주의점의 엇갈린 보고는 이 차이에서 나온 것이다. 지금 써 보려면 소스를 받아 빌드할 각오를 해야 한다.
- **양자화판 정보가 엇갈린다.** 같은 10월 16일 기사는 BF16(약 60GB)만 있고 양자화판이 없다고 적었다. 이 글을 쓴 10월 20일의 모델 카드에는 양자화판 19종이 연결돼 있었다. 그 사이에 커뮤니티가 올린 것으로 보이며, 공식판인지는 확인하지 못했다.

### 커뮤니티 반응

Hacker News와 Reddit의 토론은 여전히 찾지 못했다. GitHub 저장소가 트렌딩에 오른 정도가 확인된 반응이다. 앞의 OrcaRouter 정리는 "네 하네스 중 세 곳의 차이가 오차 범위 안이고, 우위는 남들이 아직 돌려 보지 않은 하네스 한 곳에서만 나왔다"고 평가했다. 본문 5절과 같은 결론이다.
