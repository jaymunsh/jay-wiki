GPU 견적서를 받아도 결재 문서를 쓰기 어려운 때가 있다. 장비 가격은 있는데 어떤 업무가 얼마나 나아지는지, 동시에 몇 명이 쓸 수 있는지, 문제가 생기면 누가 고치는지가 빠져 있기 때문이다. 시연 화면이 좋아 보인다는 이유만으로 구매하면 남은 일을 회사가 떠안게 된다.

이 글은 **기업이 로컬 LLM을 검토하고 공급사에 PoC와 견적을 요청하는 절차**를 제안한다. 2026년 9월 10일 확인한 공식 실행·측정 문서를 참고했다. 실제 납품 사례나 보편적인 계약 기준이 아니며, 금액·목표·기간을 넣은 사례는 가상이다. 장비·모델 후보와 예산별 활용 범위는 [예산별 구매·활용 가이드](/69/sme-local-llm-budget-30tps)에서 먼저 비교할 수 있다.

실무자가 남길 문서는 여섯 가지다. 회사 요구사항, 현재 업무 기준선, 후보 비교 결과, 3년 총비용, 인수 조건, 운영 인계서다. 이 문서들이 서로 같은 사용자 수·모델·서비스 범위를 가리켜야 견적과 실제 납품을 비교할 수 있다.

사내 문서 검색이 도입 범위에 들어간다면 [기업용 RAG 구축 가이드](/72/enterprise-rag-postgresql-pgvector-cost)의 문서·권한·갱신 조건도 붙인다. PostgreSQL·pgvector 구성, 예산별 구축 범위, 검색·답변을 구분한 검수 항목을 제공한다.

## 첫 결재는 장비 주문보다 검증 범위를 승인받는다

처음부터 전사 서비스와 모든 업무를 요구하지 않는다. 업무 하나와 사용 부서 하나를 고르고, 실제 입력·출력 사례를 모은다. 구매가 목적이 아니라면 PoC 실패도 결과다. 문서가 부족한지, 모델 품질이 부족한지, 비용이 맞지 않는지 확인하면 불필요한 발주를 줄일 수 있다.

| 단계 | 승인할 내용 | 다음 단계로 넘길 근거 |
|---|---|---|
| 사전 조사 | 대상 업무·담당자·조사 시간 | 현재 업무량과 데이터 사용 범위 |
| PoC | 대여·구축비 상한, 기간, 평가셋, 합격선 | 같은 조건의 후보별 품질·성능·비용 |
| 조건부 구매 | 정확한 BOM과 납품·인수 범위 | 합격한 구성, 반복비, 장애 대응 계획 |
| 부서 운영 | 사용자 범위·운영자·지원 계약 | 실제 업무 효과와 복구 기록 |
| 확대 | 추가 부서·모델·용량 | 기존 운영 기록에 나타난 병목 |

견적에 먼저 승인받을 금액과 전체 구축 상한을 구분한다. 대여비가 장비 구매 때 차감되는지, 실패해도 지급하는 구축비는 무엇인지, 회사에 남는 평가 결과와 산출물은 무엇인지도 적는다. 지급·검수 조건은 구매 담당자와 공급사가 실제 계약에 맞춰 확정한다.

## 요구사항은 사실·가정·미확정으로 나눈다

“직원 100명이 사용한다”는 요구만으로는 서버를 고를 수 없다. 전체 계정 수, 실제 일간 이용자, 하루 호출량, 피크 시간, 문서 길이와 출력 길이를 구분한다. 개발 에이전트는 사람이 한 번 지시해도 도구 호출 뒤 모델을 여러 번 부른다.

| 회사 입력 항목 | 조사할 값 | 확인할 담당 역할 |
|---|---|---|
| 업무 | 현재 처리 흐름, AI가 작성·추천·실행할 범위 | 업무 책임자 |
| 사용자 | 계정 수, 일간 이용자, 부서·권한, 개발자 | 업무·IT |
| 요청량 | 하루 호출, 피크 도착률, 입력·출력 길이 분포 | IT·분석 |
| 데이터 | 문서 수·GB·형식·OCR, 갱신·삭제 주기 | 문서 소유자 |
| 제한 | 외부 전송 범위, 로그 보관, 접근 허용 범위 | 회사의 보안·데이터 담당 |
| 기존 환경 | GPU·서버·RAM·저장장치·SSO·네트워크 | 인프라 |
| 예산 | 초기 상한, 월 운영 상한, 내부 인력 원가 | 구매·재무 |
| 서비스 | 허용 대기, 업무시간, 중단·복구 요구 | 업무·운영 |

각 행에 **값 / 사실·가정·미확정 / 근거 / 담당자 / 확정일**을 붙인다. 로그로 센 하루 400건은 사실이고, 앞으로 직원당 10회 사용할 것이라는 수치는 가정이다. 측정하지 않은 값에 0을 쓰지 않는다. “미측정, 1주차 기록 후 결정”으로 남긴다.

자료를 처음 모을 때에는 대표 업무와 긴 문서, 애매한 질문, 답이 없는 질문을 함께 확보한다. 잘 정리된 PDF만 공급사에 주고 실제로 많은 스캔·표·HWP를 제외하면 납품 뒤의 변환 비용이 숨겨진다. 문서별 접근 권한도 같은 샘플에 포함한다.

## 현재 방식과 대안을 같은 결과물로 비교한다

로컬 구축이 기본 답은 아니다. 현재 방식으로 계속 처리하거나, 기존 검색·업무 자동화를 개선하거나, 허용된 데이터에 외부 모델을 사용하는 안도 비교한다. 외부 서비스의 실제 요금·전송 조건은 견적 시점에 따로 확인한다. 이 글은 어느 공급사가 가장 저렴하다는 순위를 제공하지 않는다.

| 비교안 | 확보할 근거 | 빠뜨리기 쉬운 비용 |
|---|---|---|
| 기존 방식 유지 | 처리 시간, 재작업, 처리하지 못한 수요 | 반복 업무와 오류 수정 시간 |
| 검색·규칙 자동화 | 검색 성공률, 정형 작업 처리율 | 문서 정리와 시스템 연결 |
| 외부 서비스 | 같은 업무 품질, 지연, 사용량 기반 견적 | 연동·평가·지원·데이터 관리 |
| 로컬 직접 운영 | 장비 실측, 내부 인력·복구 능력 | 운영·전력·냉방·교체·업데이트 |
| 공급사 구축·지원 | 인수 시험, SLA 범위, 반복비 | 사용권·갱신비·범위 밖 작업 |

같은 작업의 사람이 검토한 최종 결과를 비교한다. 모델이 10초 만에 초안을 만들었어도 확인·수정에 10분이 걸리면 현재 업무보다 나아졌다고 할 수 없다. 중요한 업무는 평균 정확도뿐 아니라 심각한 오류 종류와 발견 가능성을 기록한다.

## 기준선과 평가셋을 먼저 고정한다

단일 부서의 시작안으로 실제 업무 1주 기록과 평가 질문 100~200개를 제안한다. 개발은 완료된 이슈 20~50개를 재구성해 범위·테스트를 준비한다. 이는 필요한 최소 표본을 보증하는 통계 기준이 아니다. 업무 종류가 많거나 오류 비용이 높으면 평가셋을 확대한다.

튜닝용 질문과 최종 평가 질문을 분리한다. 최종 평가셋을 보고 설정을 바꾸었다면 기존 점수는 개발 결과로 기록하고 새로운 평가셋으로 다시 확인한다. 확률적 결과가 큰 작업은 같은 조건으로 반복하고 평균뿐 아니라 범위와 실패 사례를 남긴다.

| 업무 | 평가 단위 | 합격 판정에 사용할 기록 |
|---|---|---|
| 규정 질의 | 질문·권한·기준일·근거 조항 | 정답, 출처, 예외 조건, 모르면 보류하는지 |
| 분류·추출 | 입력·정답 라벨·필수 필드 | 클래스별 오류, 필드 누락, 형식 실패 |
| 요약 | 원문·필수 사실 목록 | 숫자·날짜·주체 보존, 없는 사실 추가 |
| 코드 수정 | 이슈·저장소 revision·허용 범위 | 숨긴 테스트, 무관한 수정, 리뷰·재작업 시간 |
| 도구 실행 | 요청·허용 도구·상태 변화 | 잘못된 실행, 승인 준수, 중복 실행과 복구 |

규정 질의 200개 중 190개를 맞혔다면 “95%”와 함께 190/200을 적고 실패한 10개를 분류한다. 숫자·기한·금액을 잘못 말한 사례와 단순 표현 오류를 같은 비용으로 처리하지 않는다. 평가자가 둘이면 서로 다르게 판정한 항목을 조정하고 그 기준을 기록한다.

RAG가 있는 업무는 두 시험으로 나눈다. 정답 근거를 직접 주었을 때도 틀리면 생성·프롬프트 쪽 문제를 먼저 보고, 근거를 직접 주면 맞는데 검색을 거치면 틀리면 검색·전처리·권한을 확인한다. 구체적인 청킹·검색 설계는 별도 과제지만, 이 구분은 장비를 더 사야 하는지 판단하는 데 필요하다.

## 후보마다 모델과 실행 구성을 한 세트로 남긴다

품질 후보는 두세 개로 시작한다. 개발·복합 업무에서 Flash-Next를 우선 평가하더라도, 메모리와 지연 제약이 있는 회사라면 작은 후보를 함께 둔다. 공식 벤치마크 점수는 후보를 좁히는 자료로 사용하고 회사의 인수 점수로 대신하지 않는다.

| 재현 정보 | 기록할 항목 |
|---|---|
| 모델 | 저장소 URL·revision, 원본/튜닝 여부, 양자화 파일명·해시 |
| 실행 | 드라이버·엔진 버전, 컨테이너 digest, 실행 명령 |
| GPU·호스트 | 정확한 SKU·수량, RAM, PCIe·GPU 연결, offload |
| 요청 | 채팅 템플릿, system prompt, thinking, 샘플링, 출력 상한 |
| 문서 경로 | 변환·검색·임베딩 버전, 문서 snapshot, 권한 필터 |
| 도구 경로 | 에이전트·도구 버전, 저장소 상태, 실행 제한·테스트 |
| 성능 조건 | 입력·출력 분포, 요청 도착률, 동시 상한, 캐시 상태 |

설정이 다른 두 모델을 억지로 같은 토큰 수만 맞추지는 않는다. 각 모델의 정상 실행 설정을 유지한 비교와, 회사의 시간·비용 상한을 맞춘 비교를 구분한다. thinking을 끄면 품질도 바뀔 수 있으므로 빠른 설정의 품질을 따로 평가한다.

예를 들어 Flash-Next의 vLLM 공식 실행 문서에는 GPU에 따라 병렬화와 n-gram offload 조건이 다르다. 단순 VRAM 합계로 동작을 확정하지 않고, 공급사가 제안한 파일·명령으로 재현한다. [vLLM Flash-Next 실행 문서](https://recipes.vllm.ai/Qwen/Qwen3.8-Flash-Next)

## 부하는 동시 요청과 도착률을 함께 시험한다

동시 4건을 계속 실행하는 시험과 초당 일정 수의 요청이 들어오는 시험은 다르다. 전자는 제한된 동시 실행 용량을 비교하고, 후자는 요청이 쌓일 때의 대기와 실패를 본다. vLLM도 요청 도착률과 최대 동시 요청을 별도 옵션으로 구분한다. [vLLM 벤치마크 옵션](https://docs.vllm.ai/en/latest/cli/bench/serve/)

초기 시험은 입력 2K·8K·32K, 실제 업무 출력 길이, 동시 1·2·4·8건부터 제안한다. 장비 크기에 따라 구간을 조정한다. 엔진 직접 호출과 로그인·검색·게이트웨이를 포함한 실제 서비스 호출을 각각 기록한다. 실제 서비스 인수는 후자를 기준으로 한다.

| 시험 구간 | 확인할 현상 | 결과에 남길 값 |
|---|---|---|
| 단일 요청 | 기본 모델 품질과 실행 지연 | 성공 여부, 첫 답변·완료 시간 |
| 동시성 증가 | 메모리 부족·요청 간 간섭 | 요청별 생성 속도·p95 지연 |
| 실제 피크 도착률 | 큐 증가와 거절·타임아웃 | 도착·완료 요청 수, 큐 길이, 오류 |
| 긴 입력 혼합 | 짧은 요청까지 기다리는지 | 업무 유형별 지연 분포 |
| 지속 부하 | 열·전력 제한, 누수, 오류 증가 | 최소 1시간 기록과 업무일 시범 결과 |
| 장애·재시작 | 실패 처리·복구·대체 경로 | 복구 시간, 손실·중복 작업 |

초기 채팅 목표로 요청별 평균 decode 속도의 하위 5% 값 30 tok/s 이상, 읽을 수 있는 첫 답변 p95 5초 이내를 제안할 수 있다. **둘은 제안값이며 업무 책임자가 확정해야 한다.** 긴 분석과 코딩에는 작업 완료 시간·성공률을 따로 둔다. 내부 thinking의 첫 토큰 도착을 사람이 읽는 답변 시간으로 보고하지 않는다.

성공한 요청만 모아 p95를 계산하면 타임아웃이 사라져 보인다. 제출 요청 수, 성공·실패·취소 수, 실제 생성 길이, 잘린 응답을 함께 남긴다. 짧은 출력과 캐시 적중만으로 만든 최고 속도를 실제 용량으로 사용하지 않는다.

## PoC 결과표에는 실패와 미측정을 숨기지 않는다

아래는 제출 양식이다. 빈 칸 대신 “미측정”을 쓰고 시험 완료 시 결과로 교체한다. 모든 수치에 표본 수·조건·원본 로그 위치를 붙인다.

| 항목 | 후보 A | 후보 B | 합격 기준 |
|---|---|---|---|
| 정확한 모델·실행 구성 | 미확정 | 미확정 | revision·파일·설정 고정 |
| 업무 정답·근거 | 미측정 | 미측정 | 업무별 사전 합의 |
| 심각한 오류 | 미측정 | 미측정 | 허용 유형·건수 사전 합의 |
| 사람의 검토·수정 시간 | 미측정 | 미측정 | 기준선 대비 목표 개선 |
| 목표 부하의 완료 지연 | 미측정 | 미측정 | 업무별 p95·타임아웃 기준 |
| 요청 성공·실패 건수 | 미측정 | 미측정 | 전체 제출 건수 포함 |
| 최대·평균 메모리와 전력 | 미측정 | 미측정 | 실제 설치 여유 확인 |
| 재시작·백업 복구 | 미측정 | 미측정 | 회사의 복구 목표 |
| 초기비·3년 총비용 | 견적 필요 | 견적 필요 | 승인 상한 이내 |

종합점수로 모든 것을 상쇄하지 않는다. 사용권·접근 권한·필수 품질·예산처럼 통과해야 하는 조건을 먼저 정하고, 통과한 후보끼리 성능·비용·지원 편의성을 비교한다. 아래 판단은 이 글에서 제안하는 실무 규칙이다.

| 결과 | 다음 행동 |
|---|---|
| 근거를 주어도 품질 실패 | 프롬프트·모델·업무 범위 변경 후 재평가 |
| 검색할 때만 실패 | 문서 변환·검색·권한 경로 수정 |
| 품질 통과, 피크 때 지연 실패 | 큐·캐시·batch·모델 복제·장비 증설 비교 |
| 단일 요청부터 메모리 부족 | 문맥·정밀도·offload·큰 메모리 구성 비교 |
| 속도는 충분하나 검토 시간이 줄지 않음 | 사용자 흐름·결과 형식 개선 또는 도입 보류 |
| 운영자·복구 경로 없음 | 지원 범위 확보 전 운영 확대 보류 |
| 총비용 상한 초과 | 범위 축소·기존 장비·외부 대안 재비교 |

## 절감시간과 현금 절감액을 구분해 총비용을 계산한다

3년 총비용은 초기비와 36개월 반복비를 합쳐 비교한다. 내부 직원이 구축해도 투입 원가를 기록한다. 장비비와 감가상각비를 같은 총비용에 이중으로 더하지 않는다. 세무·회계 처리는 회사의 담당자가 정하며, 여기서는 도입안 비교용 계산 범위를 맞춘다.

| 비용 묶음 | 포함할 항목 |
|---|---|
| 초기 | 장비·설치, 앱·데이터 연동, 보안·권한, 교육, 검증 |
| 월 반복 | 운영 인력, 전력·냉방 또는 IDC, 사용권·지원, 백업·네트워크 |
| 비정기 | 부품 교체, 모델·인덱스 교체, 장애 대응, 추가 평가 |
| 종료·이전 | 데이터·설정 반출, 인수인계, 다른 공급사로 전환 |

**가상 상담팀 계산**을 해본다. 하루 400건, 월 20일, 건당 사람이 1분을 절약하면 월 약 133.3시간이다. 인력 원가를 시간당 3만원으로 가정하면 월 약 400만원의 시간 가치다. 채용·초과근무·외주비가 실제 줄지 않으면 이를 현금 절감액이라고 쓰지 않는다.

초기 3,000만원, 월 운영 인력 150만원, 시설·지원 50만원, 3년 교체·이전 300만원을 가정하면 3년 총비용은 **1억500만원**이다. 초기 3,000 + 반복 7,200 + 교체·이전 300의 합이다. 단위는 만원이며 시장 견적이 아니다.

동일한 월 시간 가치가 3년간 유지되면 1억4,400만원이다. 비용 대비 3,900만원이 남는 계산이지만, 여기에는 효과의 지속성과 시간 가치의 실현 가정이 들어간다. 절약이 건당 30초면 시간 가치는 절반인 7,200만원으로 내려가 비용보다 작아진다. 이 차이가 실제 시범 운영에서 검토 시간을 측정해야 하는 이유다.

최소한 보수·기준·확대 세 경우를 만든다. 이용량, 검토 시간, 월 운영비, 장애·교체비를 바꾸고 손익이 뒤집히는 조건을 적는다. 외부 서비스와 비교할 때도 같은 결과물·검토 인력·연동 비용을 포함하고 실제 사용량 견적을 받는다.

## 같은 BOM과 지원 범위로 견적을 정규화한다

BOM은 납품 부품과 소프트웨어 구성의 명세다. “96GB GPU 서버”처럼 뭉뚱그린 이름 대신 카드 SKU, CPU, RAM, 저장장치, 연결·냉각, 런타임을 적는다. 성능을 검증한 장비와 납품 장비가 다르면 다시 시험하는 조건을 붙인다.

| 공급사 답변 항목 | 비교할 내용 |
|---|---|
| 물품 | 신품·리퍼·중고, 부품별 모델·수량, 교체 가능 여부 |
| 서비스 범위 | 단순 설치, 데이터 연결, 권한 구현, 사용자 화면 중 포함 항목 |
| 설치 환경 | 입력 전원·냉각·랙·네트워크 요구, 현장 공사 비용 |
| 성능 | 정확한 모델·양자화·입력·출력·동시성, 시험 결과 원본 |
| 비용 | 부가세, 배송·설치·교육, 월·연 지원비, 갱신과 범위 밖 작업 |
| 보증 | 제조사 보증, 공급사 대응, 부품 수급, 대체 장비 |
| 운영 권한 | 관리자 계정, 구성·이미지·데이터 export, 문서 소유권 |
| 일정 | 재고·납기·설치·검수·교육 완료일 |
| 종료 | 계약 종료 후 사용 가능 범위, 데이터·설정 반출과 이전 지원 |

한 업체는 앱·검색을 포함하고 다른 업체는 서버만 포함하면 가격 합계를 바로 순위로 만들지 않는다. 제외 항목에 내부 구축 원가나 추가 견적을 넣어 같은 범위로 맞춘다. 견적 유효기간과 환율·재고 조건도 적는다.

독립 서버 두 대와 한 서버 안의 GPU 두 장은 장애 범위가 다르다. 이중 전원이나 RAID가 서버 전체 장애를 대신하지 않는다. 회사가 허용하는 중단 시간에 맞춰 대체 경로와 축소 운영 용량을 정한다.

## 사용권과 데이터 경로는 실제 제공 방식으로 확인한다

모델·추론 엔진·업무 앱·문서 변환·에이전트의 사용 조건을 각각 목록으로 만든다. 소프트웨어 이름, 버전, 라이선스 원문, 사내 사용·고객 제공 여부, 확인 담당자를 적는다. 양자화본이나 파생 모델을 사용하면 원본과 배포본의 조건을 함께 확인한다.

Flash-Next의 라이선스에는 특정 사업 형태의 별도 라이선스 조건과 내부 사용 예외가 있다. 따라서 사내 직원만 사용하는 안과 공급사가 고객에게 서비스하는 안을 같은 것으로 취급하지 않는다. 구체적인 적용 여부는 회사의 계약 담당자가 원문과 제공 구조로 확인한다. [Flash-Next 라이선스 원문](https://huggingface.co/Qwen/Qwen3.8-Flash-Next/blob/main/LICENSE)

로컬이라고 적혀 있어도 문서 OCR, 임베딩, 외부 검색, 플러그인, 오류 보고가 외부 API를 호출할 수 있다. 인수 시험에는 문서 업로드부터 답변·로그·백업까지의 데이터 경로와 외부 통신 허용 목록을 제출하도록 한다. 폐쇄망이 요구되면 모델·이미지·패키지 업데이트 경로도 포함한다.

문서 접근 통제는 검색 전에 적용되는지 확인한다. 퇴사·부서 이동으로 권한이 바뀐 뒤에도 과거 검색 캐시와 대화 링크가 문서를 노출하는지 시험한다. 삭제 요청이 원문·검색 인덱스·로그·백업 각각에 어떤 일정으로 반영되는지 회사 정책에 맞춰 기록한다.

## 인수 조건은 설치 성공보다 실제 서비스 결과로 쓴다

아래 문장은 계약서 완성본이 아니라 구매·업무·기술 담당자가 협의할 인수 조건 초안이다. 회사의 계약 형식에 맞춰 기간·책임·지급 조건을 확정한다.

> 납품 구성은 합의한 모델 revision·양자화·런타임·BOM으로 고정한다. 합의한 평가셋과 부하 조건에서 품질·지연·실패율·권한·복구 항목을 각각 통과해야 인수를 완료한다. 변경이 필요하면 변경 범위와 재시험 항목을 사전에 합의한다.

| 인수 자료 | 확인할 사항 |
|---|---|
| 구성 명세 | 실제 부품·GPU 일련번호, 모델 파일·이미지·설정 버전 |
| 품질 보고서 | 평가셋 버전, 판정 기준, 성공·실패 사례 |
| 성능 보고서 | 요청별 원본 기록, 오류 포함, 캐시·thinking 조건 |
| 복구 보고서 | 재시작·백업 복원·대체 경로 시험과 시간 |
| 운영 문서 | 설치·갱신·롤백·사용자 권한·문서 갱신 방법 |
| 접근권한 인계 | 회사 관리자 계정, 비밀값 관리, 공급사 접근 범위 |
| 교육 | 담당자가 직접 재시작·복원·권한 변경을 수행한 기록 |
| 지원 창구 | 연락 방식, 업무시간·휴일 범위, 응답과 복구의 구분 |

수리 접수에 응답하는 시간과 서비스를 복구하는 시간은 다르다. “24시간 지원”이 모니터링인지, 전화 접수인지, 현장 복구인지 확인한다. 미달 시 재시험 기간, 수정 책임, 대체안과 인수 보류 절차를 미리 정한다.

## 상담팀 검토안을 실제 문서 형태로 작성한다

다음은 3,000만원 상담팀 시나리오를 한 장의 도입 검토안으로 옮긴 예다. **효과와 성능은 목표값이며 아직 달성한 결과가 아니다.** 실제 회사에서는 문서 수량·담당자 이름·일정·운영비 단가를 채워 사용한다.

| 항목 | 작성 예시 |
|---|---|
| 도입 목적 | 상담원 20명의 상품·정책 문의 초안 작성 시간을 줄인다. 최종 발송은 상담원이 승인한다 |
| 현재 기준선 | 하루 400건. 1주간 유형별 작성·검토 시간, 잘못된 정책 안내와 재접수를 기록한다 |
| 데이터·권한 | 상품 설명과 승인된 정책 문서부터 연결. 수량·갱신 주기·고객정보 포함 여부는 1주차 확정 |
| 모델 후보 | Gemma 4 12B와 Qwen3.8-27B. 평가에 쓸 checkpoint·양자화·런타임은 기술 담당자가 고정 |
| 장비 요청 | 32GB급 독립 노드 1대안·2대안 견적 비교. 2대가 예산을 넘으면 1대부터 검증 |
| 예상 부하 | 하루 400건, 입력 4K·출력 300토큰 가정. 실제 피크를 기록하고 동시 2·4·8건 시험 |
| 초기 예산 | 장비 1,400 + 연동 900 + 운영 준비 400 + 예비비 300 = 3,000만원 상한 |
| 운영 책임 | 상담팀장: 정답·정책 갱신 승인. 기술 담당: 모델·권한·백업. 인프라 또는 공급사: 장애 복구 |
| PoC 인수 기준 | 근거 정확도 95% 이상을 제안값으로 검토, 권한 밖 문서 노출 0건, 작성·검토 시간 중앙값 20% 감소. 정책 오류·재접수 증가 여부도 확인 |
| 성능·장애 기준 | 선택한 목표 동시성에서 요청별 decode 하위 5% 30 tok/s, 첫 답변 p95 5초 이내를 시험. 장애 시 수동 상담으로 전환 |
| 미확정 항목 | 문서량·실제 피크·운영비·장비 견적·정답셋. 확정 담당자와 제출일을 붙인다 |
| 요청하는 승인 | 우선 4주 검증과 한도 내 대여·구축비. 장비 구매는 인수 기준 통과와 운영비 승인 후 집행 |

운영비도 빈칸으로 넘기지 않는다. 예를 들어 월 기술 운영비를 R, 월 시설·지원비를 S라고 두면 이 안의 3년 총비용은 `3,000만원 + 36 × (R + S) + 교체비`다. R에 내부 인력 원가를 포함한다. 절감시간은 인력 감축액으로 바로 환산하지 않고, 상담원이 추가 처리할 수 있는 업무와 함께 보고한다.

검증 일정은 다음처럼 잡을 수 있다. 데이터가 준비된 단일 부서의 제안 일정이며 복잡한 연동이면 늘린다.

| 시점 | 할 일과 남길 자료 | 다음 단계 조건 |
|---|---|---|
| 1주차 | 업무 기준선, 문서 목록·권한, 정답셋, 담당자 확정 | 데이터 사용 범위와 평가 기준 승인 |
| 2주차 | 동일 질문으로 후보 모델 비교, 실패 유형 기록 | 최소 품질 기준 통과 모델 확보 |
| 3주차 | 실제 화면 연동, 피크 부하·권한·복구 시험 | 운영 경로 전체의 성능·접근 통제 통과 |
| 4주차 | 제한된 사용자 시범 운영, 검토 시간·오류·비용 정리 | 확대·범위 축소·중단 중 하나를 결정 |

정확도 95%와 시간 20% 감소는 이 예시의 제안값이다. 계약 조항 검토나 자동 실행 업무에는 별도의 오류 허용 기준이 필요하다. 평균 점수가 높아도 심각한 정책 오류를 놓치면 합격 처리하지 않는다.

## 공개 가격을 이용해 1억원 개발팀의 결정을 끝까지 내려본다

다음은 **실제 판매 가격을 입력으로 사용한 가상 의사결정 사례**다. 고객사의 구매 결과나 직접 수행한 PoC가 아니다. 성능 합격값을 지어내지 않고, 현재 확인한 근거만으로 무엇을 승인하고 무엇을 보류할지 결정한다.

조건은 개발자 8명, 초기 상한 1억원, 그중 장비·검증 6,000만원이다. 나머지 4,000만원은 저장소·CI 연동, 인증·운영 준비, 예비비에 배정한다. 첫 목표는 사내 이슈의 패치 작성과 테스트이며 자동 배포는 범위에 없다. 품질 우선 후보는 Flash-Next, 비용·메모리 비교 후보는 Coder-Next와 27B다. 모두 이 사례의 설계 조건이다.

### 먼저 가격만으로 제외할 안을 구분한다

9월 10일 제품 페이지에서 확인한 S773은 RTX PRO 6000 Max-Q 96GB 한 장의 DELL 워크스테이션으로 40,768,500원, S849는 96GB 두 장 서버로 114,699,400원이다. S773의 기본 RAM은 16GB·SSD는 512GB라 실제 목적에 필요한 증설 견적을 추가한다. [S773 판매 구성](https://sugarcube.co.kr/v2/product_view.php?mode=server&no=773), [S849 판매 구성](https://sugarcube.co.kr/v2/product_view.php?mode=server&no=849)

| 검토안 | 확인한 비용 | 이번 단계의 결정 |
|---|---|---|
| S773 한 대 구매 | 기본 약 4,077만원 | 장비·검증 상한 안이지만 증설·성능 확인 전 구매 보류 |
| S773 두 대 구매 | 기본 합계 약 8,154만원 | 장비·검증 상한 6,000만원 초과. 이번 배분에서는 제외 |
| S849 한 대 구매 | 약 1억1,470만원 | 전체 초기 상한 1억원 초과. 이 표본은 제외 |
| 96GB 두 장 호스팅 한 달 | H863 공개 월 표시값 600만원 | 외부 시험 허용·추가비 확인 시 PoC 후보 |

호스팅 가격은 판매사 공개 목록의 무약정 표시값이다. 회사 소유 장비가 아니며 설치·사용권·세금·데이터 보관·종료 조건은 별도로 확정한다. 다른 공급사의 구성이 같은 비용이라는 뜻도 아니다. [H863 호스팅 목록](https://sugarcube.co.kr/v2/hosting.php)

### 이번 결재는 구매가 아니라 한도 있는 검증으로 정한다

결정은 **완제품 즉시 구매를 보류하고, 한 달 검증 예산 상한 1,000만원을 조건부 승인하는 안**이다. 이 1,000만원은 시장 가격이 아니라 사례의 집행 제안이다. 월 표시값 600만원을 기준으로 환경 구성·평가 인력 등 나머지 400만원 안에 들어오는지 확인하고, 초과하면 재승인한다. 검증비는 6,000만원의 일부이므로 지출 후 장비에 그대로 6,000만원을 쓸 수 없다.

외부 시험이 금지된 회사라면 호스팅 선택지는 즉시 제외하고 사내 반입 대여 견적을 받는다. 비용이 상한 안에 들어오지 않으면 기존 장비에서 작은 후보부터 시험한다. 데이터 전송 제한을 예산 때문에 바꾸지는 않는다.

### 공급사에는 세 가지 결과를 순서대로 요구한다

첫째, 계약 전에 정확한 Flash-Next 양자화 파일·revision·엔진·offload를 명시하고 제안 장비에서 적재 가능한지 확인한다. **96GB 두 장의 합계만으로 Flash-Next가 서비스된다고 약속하지 않는다.** 선택한 엔진의 실행 문서와 실제 시작·생성 기록을 요구한다.

둘째, 준비한 이슈 30개를 같은 저장소 상태와 도구·작업시간 상한으로 후보별 평가한다. 검증용 실행 설정과 평가에 사용한 설정이 같아야 한다. 테스트 성공뿐 아니라 사람이 리뷰·수정한 시간과 잘못 건드린 파일을 남긴다.

셋째, 품질을 통과한 후보만 목표 동시성에서 실행한다. 실제 호출량으로 요구 용량을 다시 계산하고, 긴 작업이 짧은 작업을 막는지 확인한다. 한 후보의 단일 요청 품질과 다른 후보의 동시성 수치를 합쳐서 합격 처리하지 않는다.

### 결과에 따라 구매와 축소를 분기한다

| 관측할 결과 | 최종 행동 |
|---|---|
| Flash-Next 적재 또는 필수 기능 실패 | 해당 구성을 구매하지 않고 엔진·양자화 또는 작은 후보 변경 |
| Flash-Next 품질 개선이 작고 수정 시간도 비슷함 | 작은 합격 후보로 납품 견적 요청 |
| Flash-Next 품질 통과, 목표 동시성 실패 | 동시 작업 제한안과 추가 장비안을 비용·대기로 비교 |
| 작은 후보도 필수 품질 실패 | 장비 구매 보류, 업무 범위와 평가 과제 재검토 |
| 합격 후보의 완제품·증설비가 남은 장비 예산 이내 | 반복비·지원·인수 조건까지 확정한 뒤 구매 요청 |
| 합격 후보가 남은 예산 초과 | 예산 증액 사유를 제출하거나 적용 범위 축소 |

현재는 PoC 결과가 없으므로 특정 모델·장비의 최종 구매 승인까지 결론 내리지 않는다. 이 사례에서 끝난 결정은 **예산을 넘는 표본 제외, 즉시 구매 보류, 검증 범위·상한·결과별 후속 행동 확정**이다. 실무에서는 모르는 성능을 확신하는 것보다 여기까지 명확히 승인받는 것이 다음 행동을 만든다.

## 검증 자료는 재구매와 장애 복구에도 쓸 수 있게 보관한다

최종 결과표와 함께 요청별 기록을 받는다. 성공한 출력만 모은 보고서는 재현에 부족하다. 다음은 공급사와 합의할 최소 기록 구조의 예다. 실제 개인정보·원문 보관 여부는 회사 정책에 맞추고, 원문 대신 통제된 샘플 ID로 연결할 수 있다.

```text
run_id, request_id, task_id, model_revision, quantization_hash
runtime_image_digest, hardware_profile, workload_profile
input_tokens, output_tokens, thinking_setting, cache_state
submitted_at, first_token_ms, first_visible_answer_ms, completed_ms
status, error_type, quality_pass, severe_error, human_review_seconds
```

성능 원본에는 요청 실패를 남기고, 품질 판정표에는 판정자와 이유를 남긴다. 모델·엔진 변경 뒤 같은 task_id를 재평가할 수 있어야 한다. 토큰 수가 같아도 토크나이저가 다를 수 있으므로 사용자 관점의 전체 작업 시간도 비교한다.

보고서의 최종 판정은 “평균 속도 우수” 대신 “선택한 workload_profile에서 필수 품질 통과, 200건 중 성공 198건·실패 2건, 실패 허용 기준 충족 여부”처럼 쓴다. 여기의 200·198·2는 **기록 형식을 설명하는 가상 숫자**이며 어떤 모델의 측정 결과도 아니다. 실제 보고에서는 표본과 원본 기록을 연결한다.

## 공급사에는 요구사항과 응답 양식을 함께 보낸다

다음 요청문은 복사해 사용할 수 있는 출발점이다. 대괄호 자리는 회사 입력란이며 발송 전에 실제 값으로 채운다.

```text
제목: [회사·업무] 로컬 LLM PoC 및 구축 견적 요청

목적: [대상 업무와 개선할 지표]
사용 범위: [계정·일간 이용자·부서·업무시간]
예상 부하: [하루 호출·피크·입력/출력 분포]
데이터: [수량·형식·갱신·권한·외부 전송 범위]
기존 환경: [보유 장비·인증·네트워크·설치 조건]
예산: [PoC 상한 / 초기 구축 상한 / 월 운영 상한]
필수 결과: [품질·지연·실패·복구 합격 기준]

제안서에는 다음을 포함해 주십시오.
1. 모델·양자화·런타임과 정확한 BOM
2. 합의한 평가셋·부하를 실행하는 PoC 방법
3. 포함/제외 작업과 회사가 준비할 사항
4. 부가세 포함 초기비·반복비·추가 비용
5. 납기·설치·교육·인수 일정
6. 보증·장애 대응·복구·대체 장비 범위
7. 관리자 권한·데이터·설정의 인계 및 종료 절차
8. 모델·앱 사용권과 제안 구성의 지원 범위
9. 미충족 요구와 대안, 재시험 조건
```

응답 항목마다 “충족 / 조건부 / 미충족”과 근거를 요청한다. 조건부이면 회사가 추가 준비할 비용·일정·인력을 반드시 적게 한다. “추후 협의”가 남은 항목은 구매 확정 전에 책임자와 확정일을 붙인다.

## 납품 뒤에는 실제 사용 기록으로 확대를 결정한다

운영 첫 달에는 업무별 이용량, 실패·재작업, 검토 시간, 비용, 장애를 매주 확인한다. 새 모델이 나왔다고 즉시 바꾸지 않고 동일 평가셋과 일부 실제 요청으로 비교한다. 이전 버전으로 되돌릴 수 있는 모델·설정·인덱스 사본을 유지한다.

| 관측 결과 | 확대 또는 수정 방향 |
|---|---|
| 품질·비용 통과, 사용량이 낮음 | 새 GPU보다 사용 흐름·교육·필요 업무 재검토 |
| 품질 통과, 피크 대기 증가 | 측정한 병목에 따라 모델 복제·큐·증설 |
| 문서 갱신 후 오류 증가 | 변환·검색·평가 데이터 갱신 절차 수정 |
| 모델 변경 후 코드 실패 증가 | 이전 버전 복귀, 에이전트·도구까지 재평가 |
| 지원 없이 운영이 멈춤 | 담당자 교차 교육·지원 범위 재설계 |
| 반복비가 예상 초과 | 호출·thinking·로그·인력별 원인 분해 |

구매에 필요한 최대한의 정보는 후보를 끝없이 나열하는 데서 나오지 않는다. **회사 요구량, 같은 조건의 측정, 정확한 견적, 책임지는 운영 범위**가 연결되어야 한다. 이 글의 양식에 회사의 값과 증거를 채우면, 무엇을 살지뿐 아니라 왜 그 구성을 선택했는지도 설명할 수 있다.
