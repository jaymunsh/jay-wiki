> **업데이트 안내 (2026년 8월 29일)** — 이 글은 2026년 8월 23일 기준 Ox Alpha 프리뷰를 정리한 글이다. 이후 정체 공개와 무료 프리뷰 종료, 최신 벤치마크는 [후속 리서치 글](/37/ox-alpha-glm-5-3-flash)에서 다룬다.

> 이 글은 2026년 8월 23일에 확인한 공개 문서와 모델 카탈로그를 기준으로 썼다. Ox Alpha는 아직 stealth preview라서 모델 ID, 가격, 한도와 제공 경로가 예고 없이 바뀔 수 있다.

Ox Alpha라는 이름이 갑자기 보이기 시작했다. **컨텍스트가 100만 토큰이고, 코딩 에이전트에 잘 맞고, OpenRouter와 OpenCode에서 무료로 쓸 수 있다**는 설명이 같이 따라온다. 그런데 막상 써 보려고 하면 이름이 세 개 나온다. `stealth/ox-alpha`, `x-preview-f-free`, `ox-alpha-free`다.

더 찜찜한 점은 누가 만든 모델인지 알 수 없다는 것이다. 벤더 블로그도, 가중치 저장소도, 공식 벤치마크도 없다. 무료라는 말만 보고 운영 저장소나 비밀이 든 프로젝트를 맡기기에는 정보가 비어 있다.

그래서 이 글은 무료로 쓸 수 있다는 사실보다 Ox Alpha가 실제로 어느 작업에서 강하고 약한지를 먼저 본다. 마지막에 OpenRouter와 OpenCode에서 시험하는 가장 짧은 경로와, 현재 프로젝트에 적용할 때의 경계를 덧붙인다.

## Ox Alpha는 어떤 모델인가

현재 공개된 자료에는 Ox Alpha의 오픈 웨이트 가중치가 없다. [OpenRouter 모델 페이지](https://openrouter.ai/stealth/ox-alpha)는 이를 **익명 제3자가 개발·운영하는 stealth 모델**이라고 설명하고, OpenRouter는 모델을 만든 곳이 아니라 요청을 전달하는 접근 계층이라고 명시한다.

따라서 지금의 Ox Alpha를 내 컴퓨터에 내려받아 실행하는 오픈소스 모델이라고 부르면 안 된다. 우리가 무료로 쓰는 것은 모델 파일이 아니라, 익명 제공자가 운영하는 추론 엔드포인트의 preview 접근권이다.

현재 카탈로그에서 확인되는 사양은 이렇다.

| 항목 | 확인된 값 |
|---|---|
| 공식 모델 ID | `stealth/ox-alpha` |
| 제작자 | 공개되지 않음. OpenRouter 표기는 `Stealth` |
| 컨텍스트 | 1,048,576 토큰 |
| 최대 출력 | 131,072 토큰 |
| 입력 | 텍스트·이미지·비디오 |
| 출력 | 텍스트 |
| 추론 | 강제. 기본 `max`, `high`·`low` 지원 |
| 도구·구조화 출력 | 카탈로그에서 지원 파라미터로 표시 |
| OpenRouter 가격 | 입력·출력 모두 $0 |

사양은 [OpenRouter 모델 API](https://openrouter.ai/api/v1/models)의 현재 응답과 [모델 페이지](https://openrouter.ai/stealth/ox-alpha)를 기준으로 했다. 이 표가 모델의 품질을 보증하는 것은 아니다. 모델 카드에 공개된 학습 데이터, 가중치, 평가 방법이 없기 때문에 "어떤 모델과 동급이다"라는 주장까지 이어 갈 근거는 아직 없다.

## 1M 컨텍스트보다 추론이 항상 켜진다는 점이 더 중요하다

100만 토큰은 눈에 잘 띄는 숫자지만, 실제 사용감은 그 숫자 하나로 결정되지 않는다. Ox Alpha는 추론이 강제되어 있고 기본 reasoning effort가 `max`다. 짧은 질문에도 답변 전에 내부 추론 토큰을 사용하므로 첫 응답이 느리거나, 단순한 작업에도 출력 비용이 커지는 것처럼 느껴질 수 있다.

OpenRouter의 API 메타데이터에는 최대 출력이 131,072토큰으로 표시된다. 이것은 한 번의 응답이 그만큼 길어질 수 있다는 뜻이지, 모든 요청이 1M 컨텍스트와 131K 출력을 실제로 안정적으로 사용할 수 있다는 뜻은 아니다. 제공자의 순간적인 용량, OpenRouter의 무료 한도, OpenCode가 요청을 구성하는 방식이 모두 영향을 준다.

코드베이스 전체를 넣는 실험을 한다면 다음을 따로 재야 한다.

| 따로 볼 것 | 왜 필요한가 |
|---|---|
| 첫 토큰까지의 시간 | 강제 추론과 큐 대기 시간이 섞인다 |
| 실제 생성 속도 | 긴 답변을 받을 때의 체감이 달라진다 |
| 입력 토큰 수 | 컨텍스트 창에 들어갔는지 확인해야 한다 |
| 추론 토큰 수 | 답변 길이만으로 비용·지연을 판단하면 안 된다 |
| 도구 호출 성공 여부 | 채팅 답변과 에이전트 작업은 다른 평가다 |

즉 "1M이라서 저장소를 전부 넣으면 된다"가 아니라, **넣을 수 있는 상한이 넓으니 어떤 구간에서 실제로 이득이 나는지 측정할 수 있다**에 가깝다.

## 공개된 성능 수치를 비교 가능한 것부터 다시 읽어보자

이번에는 한 셀에 여러 모델을 나열하지 않고, 평가별로 모델을 행에 배치했다. `Ox Alpha 대비` 열을 보면 같은 평가 안에서 누가 앞서는지 바로 확인할 수 있다.

### 10개 실무 저장소 작업 비교

[Ox Alpha 벤치마크 상세 페이지](https://oxalpha.com/ox-alpha-benchmarks)의 10개 작업 결과다. 비교 모델은 과제마다 네 번 시도했고, Ox Alpha는 과제별 한 번의 pass/fail로 기록되어 조건이 완전히 같지는 않다.

| 모델 | 평균 통과율 | Ox Alpha 대비 | 측정 방식 |
|---|---:|---:|---|
| **Ox Alpha** | **80% (8/10)** | 기준 | 10개 과제 pass/fail |
| Fable 5 | 65% | -15%p | 과제당 4회 시도 |
| GLM-5.3 | 62% | -18%p | 과제당 4회 시도 |
| Grok 4.6 | 62% | -18%p | 과제당 4회 시도 |
| GPT-5.6 Sol | 52% | -28%p | 과제당 4회 시도 |

이 표만 보면 Ox Alpha가 앞서지만, 10개 작업뿐이고 측정 방식도 비대칭이다. “Ox Alpha가 GPT-5.6 Sol보다 28%p 좋다”가 아니라, **이 작은 작업 묶음에서 28%p 높은 결과가 나왔다**고 읽어야 한다.

### 더 큰 DeepSWE 재실행 비교

같은 계열의 평가를 더 큰 표본으로 다시 실행했다는 [커뮤니티 재실행 정리](https://www.ai-primer.com/engineer/stories/ox-alpha-deepswe-retest)에서는 순서가 달라진다. 이 자료는 2차 정리이므로 확정적인 공식 점수로 보기는 어렵다.

| 모델·계열 | 보고된 점수 | Ox Alpha 대비 |
|---|---:|---:|
| Sol·Opus 계열 | 약 71~74% | +8~11%p |
| Fable 5 Medium | 약 65% | +약 2%p |
| **Ox Alpha** | **약 63%** | 기준 |

이 결과가 중요한 이유는 10개 표본의 80%를 그대로 일반화하기 어렵다는 점을 보여주기 때문이다. Ox Alpha의 실무형 성능을 하나의 고정된 점수로 쓰기보다, **작은 샘플에서 80%였지만 더 큰 재실행에서는 약 63%까지 내려온 모델**이라고 표현하는 편이 낫다.

### Kingbench 커스텀 평가 비교

[Kingbench 평가 정리](https://thegeekinsights.com/ox-alpha-ai-explained/)에서는 Ox Alpha가 80점 만점 중 70점을 얻었다. 다만 비공개·비표준 하니스라서 공식 순위표가 아니라 참고용 비교로만 봐야 한다.

| 모델 | 점수 | Ox Alpha 대비 |
|---|---:|---:|
| GLM-5.3 | 91.25% | +3.75%p |
| **Ox Alpha** | **87.5% (70/80)** | 기준 |
| Fable 5 | 약 82.5% | -약 5%p |
| Qwen 3.8 Max | 약 81.25% | -약 6.25%p |
| Opus 4.8 | 약 80% | -약 7.5%p |

반대로 [LiveCodeBench v6 단일 시도](https://www.reddit.com/r/LLMDevs/comments/1vv4h4mb/ox_alpha_livecodebench_v6/)에서는 175문제 중 49개, **Pass@1 28.0%였다**. 이 시험은 Python을 도구 없이 temperature 0으로 한 번 생성한 raw 코드 정답률이라 위의 저장소·에이전트형 결과와 직접 섞을 수 없다. [OpenRouter 운영 지표](https://openrouter.ai/stealth/ox-alpha)는 최근 3일 기준 P50 24 tok/s·지연 5.47초·Uptime 99.99%를 보여 주지만, 이것은 모델 품질이 아니라 서비스 응답 속도와 가용성이다.

숫자로 요약하면 **평가에 따라 Ox Alpha는 63~87.5% 범위에 있고, raw 코딩 한 번 생성에서는 28%였다.** 그래서 현재 공개 자료만으로는 “최고의 코딩 모델”보다, 특정 저장소 작업에서는 강한 신호를 보였지만 평가 규모와 하니스에 따라 편차가 큰 무료 preview라고 설명하는 것이 맞다.

## 성능만 놓고 내리는 결론

현재 공개 수치로 판단하면 Ox Alpha의 위치는 다음과 같다.

| 사용 상황 | 판단 | 근거 |
|---|---|---|
| 저장소를 넓게 읽고 여러 단계로 수정하는 에이전트 작업 | **시험해볼 가치가 있다** | 작은 실무형 비교에서 80%, 더 큰 재실행에서 약 63% |
| 짧은 코드 조각을 한 번에 완성하는 작업 | **기대치를 낮춰야 한다** | LiveCodeBench raw Pass@1 28% |
| 빠른 응답이 중요한 작업 | **주의해서 써야 한다** | P50 24 tok/s, 지연 5.47초, 추론 effort 기본값 `max` |
| 운영 장애 비용이 큰 핵심 업무 | **아직 주력으로 쓰기 어렵다** | 표준 공식 벤치마크 부재, 익명 제공자, preview 서비스 |

따라서 성능 결론은 “Ox Alpha가 다른 모델보다 전반적으로 좋다”가 아니다. **저장소 단위의 긴 작업에서는 유망한 신호가 있지만, 단일 코드 생성과 응답 안정성까지 포함한 종합 성능은 아직 검증되지 않았다**가 가장 정확하다. 무료라는 점을 감안하면 보조 에이전트나 코드 리뷰어로 시험할 이유는 충분하지만, 현재 기준 모델을 바로 대체할 정도의 근거는 부족하다.

### 실제로 무엇을 테스트했는가

이 비교는 알고리즘 문제를 새로 풀게 한 표가 아니다. 원문 방법론에 따르면 오픈소스 저장소에서 가져온 10개의 실제 코드 변경 작업을 대상으로 했고, 각 작업은 프로젝트 이름과 변경 요구를 조합한 식별자로 공개되어 있다. 다만 공개 페이지에서 확인할 수 있는 것은 아래 작업명과 모델별 통과 수까지다. 전체 프롬프트, 기준 커밋, 패치 평가 스크립트가 모두 공개된 표준 리더보드로 읽어서는 안 된다.

| 테스트 작업 | 작업명에서 확인되는 대상 |
|---|---|
| `anko-typed-variable-bindings` | Anko의 typed variable bindings |
| `arktype-json-schema-refs` | ArkType의 JSON Schema refs |
| `fastapi-deprecation-headers` | FastAPI의 deprecation headers |
| `helm-unified-manifest-stream` | Helm의 unified manifest stream |
| `igel-persist-feature-schema` | Igel의 persist feature schema |
| `katex-multicolumn-array-spans` | KaTeX의 multicolumn array spans |
| `meriyah-explicit-resource-decl` | Meriyah의 explicit resource declaration |
| `query-persist-restored-state` | query의 persist restored state |
| `scc-bounded-memory-spilling` | SCC의 bounded-memory spilling |
| `vulture-persistent-analysis-cache` | Vulture의 persistent analysis cache |

작업별 결과까지 펼치면 비교의 모양이 조금 달라진다. `4/4`는 비교 모델이 네 번 시도해서 네 번 통과했다는 뜻이고, `✓`와 `✕`는 Ox Alpha의 단일 pass/fail 기록이다.

| 작업 | Fable 5 | GLM-5.3 | GPT-5.6 Sol | Grok 4.6 | Ox Alpha |
|---|---:|---:|---:|---:|:---:|
| `anko` | 4/4 | 4/4 | 2/4 | 1/4 | ✓ |
| `arktype` | 2/4 | 1/4 | 3/4 | 1/4 | ✓ |
| `fastapi` | 4/4 | 3/4 | 3/4 | 4/4 | ✓ |
| `helm` | 4/4 | 4/4 | 4/4 | 4/4 | ✓ |
| `igel` | 3/4 | 3/4 | 0/4 | 4/4 | ✓ |
| `katex` | 2/4 | 4/4 | 3/4 | 4/4 | ✓ |
| `meriyah` | 1/4 | 0/4 | 0/4 | 0/4 | ✓ |
| `query` | 2/4 | 3/4 | 1/4 | 2/4 | ✓ |
| `scc` | 4/4 | 3/4 | 4/4 | 4/4 | ✕ |
| `vulture` | 0/4 | 0/4 | 1/4 | 1/4 | ✕ |

이 표에서 읽을 수 있는 구체적인 장면도 있다. Ox Alpha는 `meriyah` 작업에서 비교 모델들이 최대 1/4에 그친 상황에서도 통과했지만, `scc`에서는 네 비교 모델이 모두 적어도 3/4을 기록한 가운데 실패했다. `vulture`는 대부분의 모델이 어려워한 작업으로, Ox Alpha만의 약점이라고 보기는 어렵다. 결국 8/10이라는 평균보다 **어떤 유형의 저장소 변경에서 강했고 어디서 무너졌는지**가 실제 프로젝트에 적용할 때 더 중요한 정보다.

두 결과는 모순이라기보다 측정 대상이 다르다. 첫 번째는 실무에 가까운 작은 과제 묶음이고, 두 번째는 정해진 코딩 문제를 한 번 생성해 맞혔는지를 보는 시험이다. 에이전트가 파일을 읽고 테스트를 돌리며 여러 번 수정하는 능력과, 도구 없이 한 번에 정답 코드를 내는 능력은 같은 축의 성능이 아니다. 따라서 이 숫자만으로 "Ox Alpha가 최고다" 또는 "코딩에 약하다"고 결론내리기 어렵다.

실제 사용에서 체감되는 성능은 품질 점수 하나보다 다음 항목의 조합에 가깝다.

| 확인할 항목 | 기록할 값 |
|---|---|
| 응답 지연 | 첫 토큰까지의 시간, 전체 완료 시간 |
| 생성 효율 | 입력·출력·추론 토큰 수 |
| 에이전트 작업 | 도구 호출 성공 여부, 재시도 횟수, 테스트 통과 여부 |
| 결과 품질 | 실제 결함을 찾았는지, 제안한 수정이 재현 가능한지 |

특히 Ox Alpha는 기본 reasoning effort가 `max`이고 OpenRouter의 라우팅·무료 엔드포인트 상태에도 영향을 받는다. 같은 프롬프트라도 요청 시점과 제공 경로에 따라 지연과 결과가 달라질 수 있다. 그래서 이 모델을 평가할 때는 공개 벤치마크 숫자를 그대로 믿기보다, 같은 저장소·같은 프롬프트·같은 권한으로 기준 모델과 비교한 기록을 남기는 편이 더 유용하다.

## Ox Alpha의 핵심 사양과 무료 기간

Ox Alpha를 OpenRouter와 OpenCode에서 시험할 때 기억할 내용은 모델 자체의 다음 정보면 충분하다.

| 항목 | 확인된 내용 |
|---|---|
| 모델 ID | `stealth/ox-alpha` |
| 컨텍스트 | **1,048,576 토큰(약 1M)** |
| 최대 출력 | **131,072 토큰** |
| 입력·출력 | 텍스트·이미지·비디오 입력, 텍스트 출력 |
| 추론 | 강제 실행. 기본값 `max`, `high`·`low` 지원 |
| 도구 사용 | 도구 호출과 구조화 출력 지원 |
| 가격 | OpenRouter와 OpenCode Zen에서 현재 Free로 표시 |
| 무료 기간 | **기간 한정 preview**. 2026년 8월 23일 기준 공식 종료일은 공개되지 않음 |
| 제공자 | 익명 제3자. 오픈 웨이트나 다운로드 가능한 모델 파일은 없음 |

1M 컨텍스트와 131K 출력은 카탈로그상 상한이지, 모든 요청에서 안정적으로 보장되는 처리량은 아니다. 무료 기간도 “8월 27일까지”처럼 특정 날짜로 단정하기보다 [OpenRouter 모델 페이지](https://openrouter.ai/stealth/ox-alpha)와 [OpenCode Zen 문서](https://opencode.ai/docs/zen/)가 표시하는 최신 상태를 기준으로 확인하는 편이 안전하다.

처음 테스트할 때는 비밀정보가 없는 작은 저장소를 사용한다. 무료 모델을 시험하는 것과 코드·프롬프트가 보관되지 않는 것은 같은 의미가 아니다.

## 에이전트에 붙일 때는 무료보다 실패 격리를 먼저 준비한다

Ox Alpha는 도구 호출을 지원하는 것으로 표시되어 있어 OpenCode 같은 코딩 에이전트와 잘 맞을 가능성이 있다. 그러나 도구를 호출할 수 있다는 것과 실제 저장소 작업을 안정적으로 끝낸다는 것은 다른 주장이다. 공개된 공식 벤치마크가 없으므로 현재는 아래 정도의 실험이 적당하다.

1. 버릴 수 있는 작은 저장소에서 시작한다.
2. 읽기·수정·테스트 실행 권한을 한 번에 주지 말고 단계별로 확인한다.
3. 매 요청의 diff, 실행한 명령, 테스트 결과와 총 시간을 남긴다.
4. 같은 프롬프트를 기준 모델에도 넣어 코드 품질과 실패 유형을 비교한다.
5. 무료 한도를 다 썼을 때 다른 모델로 자동 전환할지 명시한다.

제공자 장애나 과부하 때 라우팅·fallback이 개입할 수 있으므로, 같은 모델 ID라도 요청 시점에 따라 지연과 결과가 달라질 수 있다. 비밀정보와 운영 데이터는 넣지 않고, 실제 실행 경로와 모델 정책을 확인한 뒤 사용한다.

## 정체를 맞히는 일보다 확인된 경계를 기록하는 편이 낫다

Ox Alpha를 두고 특정 연구소나 기존 모델의 변형이라는 추측이 돌고 있지만, 현재 공개된 공식 자료만으로는 확인할 수 없다. 이 글에서 안전하게 말할 수 있는 범위는 다음과 같다.

| 말할 수 있는 것 | 아직 말할 수 없는 것 |
|---|---|
| 익명 제3자가 운영하는 stealth preview다 | 어느 회사가 만들었는지 |
| OpenRouter에서 `stealth/ox-alpha`로 노출된다 | 어떤 오픈 모델을 바탕으로 했는지 |
| 1M 컨텍스트와 131K 최대 출력이 카탈로그에 표시된다 | 모든 요청에서 그 상한이 보장되는지 |
| 추론이 강제되고 도구·멀티모달 입력을 지원한다고 표시된다 | 코딩 에이전트 성능이 특정 유료 모델보다 높은지 |
| 현재 여러 경로에서 Free로 노출된다 | 이 무료 기간과 모델이 언제까지 유지되는지 |

이 표의 오른쪽을 왼쪽처럼 쓰는 순간 리서치 글이 광고 문구가 된다. 지금 Ox Alpha를 써 볼 이유는 "정체를 알아냈기 때문"이 아니라, 익명 preview가 실제 작업에서 어떤 품질과 지연을 보이는지 직접 확인할 수 있기 때문이다.

## 성능을 직접 확인하는 작은 테스트

OpenRouter의 `stealth/ox-alpha`와 OpenCode Zen의 `opencode/x-preview-f-free`에서 같은 작업을 한 번씩 실행해 보면 된다. 처음부터 복잡한 기능 구현을 맡기기보다, 현재 프로젝트의 구조·테스트·문서 상태를 읽고 문제 후보를 찾는 작업부터 시작한다.

내가 이 모델을 실제 프로젝트에 넣는다면 순서는 이렇다.

1. 작은 테스트 저장소에서 OpenRouter와 OpenCode Zen을 각각 한 번씩 호출한다.
2. 같은 작업의 diff와 테스트 결과를 비교한다.
3. API 한도와 provider 정책을 확인하기 전까지는 비밀·운영 데이터·자동 배포 권한을 주지 않는다.
4. 무료 preview가 사라져도 멈추지 않도록 fallback 모델과 수동 중단 지점을 남긴다.

성능만 놓고 보면 Ox Alpha는 **작은 실무형 에이전트 테스트에서 눈에 띄는 결과를 보였지만, 표본을 넓히거나 단일 코드 정답률로 보면 편차가 큰 모델**이다. 따라서 지금 필요한 결론은 “최고의 무료 모델”이 아니라, 무료 preview가 열려 있는 동안 현재 프로젝트에서 기준 모델과 같은 작업을 시켜 실제 성공률·소요 시간·재시도 횟수를 기록해 보는 것이다.

우선은 이 모델을 현재 프로젝트를 가볍게 점검하는 용도로 활용해볼 예정이다. 저장소 구조와 테스트·문서의 빈틈을 확인하고, 결과는 파일 경로·diff·테스트 실행으로 직접 검증할 생각이다.
