> 이 글은 2026년 8월 24일 기준으로 썼다. 앞선 두 글(Git Worktree, Pull Request)의 결론 위에 세워진 글이므로 겹치는 맥락은 짧게만 언급한다. 표기한 수치는 경험값이고 연구로 확립된 임계값이 아니다.

에이전트에게 일을 맡기기 시작하면 처음 겪는 불편이 하나 있다. **결과를 믿을 방법이 없다는 것**이다. 사람이라면 "이 부분 왜 이렇게 고쳤어요?"라고 물을 수 있지만, 에이전트의 설명은 그저 그 변경이 잘될 거라고 믿게 해주는 문장일 뿐이다.

그렇다면 남는 검증 수단은 무엇인가. diff를 사람이 정독하거나, 직접 실행해서 눈으로 확인하거나, **테스트가 통과하는지 보는 것**이다. 이 글의 주장은 단순하다. 에이전트 시대에 테스트 코드는 덜 중요해진 것이 아니라, 사람 손으로 검증하는 시간이 줄어든 만큼 **남은 검증 수단의 비중이 커졌다**는 것이다.

한 가지 미리 밝혀둔다. 이 글에서 "테스트"라고 말할 때 그 밑바닥에 있는 개념은 **기계가 pass/fail을 판정할 수 있는 장치 전반**이다. 테스트 코드는 그 대표주자일 뿐, 전부는 아니다. 왜 범위를 넓게 잡는지는 다음 절에서 설명한다.

다만 이 주장에는 정당한 반론들이 있다. 이 글 후반부에서 그 반론들도 있는 그대로 다룬다. 찬반 양쪽을 놓고 어디까지 주장할 수 있는지가 이 글의 범위다.

## 먼저 용어부터 - TDD와 테스트 코드는 다른 이야기다

"테스트" 하면 TDD(Test-Driven Development)부터 떠올리는 경우가 많은데, 이 글에서 말하는 대상은 아니다.

| 구분 | TDD | 테스트 코드 |
|---|---|---|
| 정체 | 개발 **방법론** | 개발 산출물 **자산** |
| 핵심 질문 | 테스트를 먼저 쓰고 코드를 짜는 절차가 좋은 코드를 낳는가 | 이 저장소의 변경이 올바른지 기계로 판정할 수 있는가 |
| 논쟁 여부 | 지금도 진영 논쟁이 있다 | 이 글의 대상 |

TDD의 효용(레드-그린 사이클이 설계를 개선한다 등)은 여전히 의견이 갈리는 영역이고, 이 글은 그 논쟁에 끼어들지 않는다. 다루는 것은 더 단순한 질문이다. **에이전트가 만든 변경이 올바른지 판정할 방법이 저장소 안에 있는가.**

## 테스트 코드만이 답은 아니다 - 검증 장치의 스펙트럼

도입에서 예고한 대로 범위부터 넓혀두자. 에이전트에게 필요한 것은 테스트 코드 그 자체라기보다, **기계가 pass/fail을 판정할 수 있는 장치 전반**이다. 이미 저장소 안에는 여러 층위의 판정 장치가 있다.

| 검증 장치 | 판정 비용 | 잡아내는 것 |
|---|---|---|
| 컴파일·타입 체크 | 밀리초~초 | 타입 오류, 오타 수준의 실수 |
| 린트·포맷 검사 | 초 | 규약 위반, 명백한 안티패턴 |
| 단위·통합 테스트 | 초~분 | 로직의 행위가 요구와 일치하는가 |
| E2E 테스트 | 분 | 시스템 전체가 연결돼 동작하는가 |
| 배포 후 모니터링 | 상시 | 실제 사용자 환경에서의 이상 |

이 스펙트럼에서 테스트 코드는 하나의 지점일 뿐이다. 다만 가장 넓은 범위를 합리적인 비용으로 판정해주는 중간 지점이라서 이 글의 주인공으로 삼는다. 타입 체크는 싸지만 로직의 옳음까지는 못 보고, 모니터링은 진짜 세계를 보지만 문제를 늦게 잡는다. 그 사이에서 "요구한 동작을 코드가 하는가"를 기계로 판정하는 것이 테스트다.

## 왜 더 값져졌나 - 세 가지 이유

### 1. 검증의 주체가 느리고 비싼 나에서 빠르고 싼 기계로 넘어간다

사람이 직접 개발하던 시절에는 최종 검증자가 사람이었다. 코드 리뷰, 수동 테스트, 화면을 열어보는 것. 그런데 PR 글에서 봤듯 에이전트 시대의 리뷰 관문은 비중이 이동한다. 사람이 모든 diff를 정독하기 어렵게 되면서, **사람 앞에 도착하는 변경은 이미 기계 검증을 통과한 상태여야 한다.** 그 기계 검증의 몸통이 테스트 스위트다.

비유하자면 이렇다. 사람 운전 시절에는 운전자의 눈이 안전장치였지만, 자율주행차 시대의 안전장치는 센서와 검증 소프트웨어다. 운전자가 사라지는 게 아니라 역할이 바뀌는데, 바뀐 역할을 수행하려면 센서가 없으면 아무것도 할 수 없다.

### 2. 테스트는 에이전트가 읽을 수 있는 요구사항 명세다

에이전트는 모호한 지시에 약하다. "로그인 버그 고쳐줘"라는 프롬프트로는 재현 방법도, 성공 기준도 없다. 반면 실패하는 테스트 하나는 **기계가 판정 가능한 형태의 요구사항**이다.

```typescript
// 에이전트에게 전달되는 가장 명확한 지시서
it("결제 실패 시 사용자에게 에러 메시지를 노출한다", () => {
  mockPayment.fail();
  renderCheckout();
  user.click(payButton);
  expect(screen.getByText("결제에 실패했습니다")).toBeVisible();
});
```

이 테스트가 저장소에 있으면 에이전트의 작업 순서가 명확해진다. 테스트를 실행하고, 실패를 확인하고, 통과시키는 것. 사람이 "잘 됐나?"를 감으로 판단하던 자리를 판정 함수가 대신한다. 즉 테스트 코드는 에이전트 시대에 검증 도구이기 전에 **에이전트에게 주는 지시서의 최상급 형태**가 된다.

### 3. 격리된 worktree에서 돌아오는 변경의 공통 분모가 된다

worktree 글의 결론을 다시 꺼내면, 에이전트의 산물은 자기 폴더의 브랜치 위에 격리되어 도착하고, 사람이 합침을 판단한다. 그런데 하루에 도착하는 변경이 한두 개가 아니라면 사람은 무엇을 기준으로 빠르게 걸러내는가.

PR 글에서 답을 이미 봤다. CI 1차 관문, 사람 2차 관문. 그 1차 관문이 실제로 걸러주는 힘은 전부 **테스트 스위트가 얼마나 진짜 동작을 잡아내는가**에 달려 있다. 테스트가 없는 저장소에서는 1차 관문이 비어 있으니 모든 변경이 사람에게 그대로 도착한다. 격리 구조(worktree)와 리뷰 관문(PR)을 아무리 잘 차려놔도 마지막 판정 근거가 없는 것이다.

## 판정을 실행하는 쪽 - 하네스 이야기

테스트 코드가 "무엇을 판정할까"라는 질문이라면, 짝이 되는 질문이 하나 더 있다. **누가 그 판정을 실제로 실행하고, 결과를 알려주는가.** 그 역할을 하는 실행 환경 전체를 하네스(harness)라고 부른다. 테스트 프레임워크(Jest, pytest), 러너, CI 워커, 실패 리포트까지가 하네스의 범위다.

하네스가 중요해지는 이유는 에이전트의 작동 방식에 있다. 에이전트가 저장소 안에서 접촉하는 것은 테스트 코드 자체가 아니라 **하네스의 출력**이다. `npm test`의 종료 코드, pytest가 뱉는 실패 스택 트레이스, 커버리지 리포트. 에이전트에게 이것이 유일한 감각 입력에 가깝고, 다음 수정 방향은 전부 이 출력을 읽어서 결정된다.

그래서 같은 테스트 코드라도 하네스 품질에 따라 에이전트 성능이 달라진다.

| 하네스 조건 | 왜 필요한가 |
|---|---|
| 결정적(deterministic) | flaky 테스트가 섞이면 에이전트는 원인도 아닌 실패를 고치려 해맨다 |
| 빠른 피드백 | 느린 스위트는 에이전트의 시행착오 반복 비용을 그대로 증가시킨다 |
| 실패 원인이 메시지에 드러난다 | "3개 실패"보다 "어떤 입력에서 무엇이 기대와 달랐다"가 에이전트의 다음 수를 결정한다 |
| 로컬과 CI가 같게 동작한다 | 사람은 차이를 감으로 흡수하지만 에이전트는 환경 차이에 갇힌다 |

즉 에이전트 시대에 손보아야 할 대상은 테스트 코드만이 아니라 **테스트 코드가 놓여 있는 실행 환경**까지다. 앞선 PR 글에서 CI를 "기계의 검문소"라고 불렀는데, 그 검문소의 스캐너 성능이 곧 하네스 품질이라고 보면 된다.

## 그런데 반론이 있다 - 있는 그대로

여기까지가 찬성 측 논지다. 그런데 이 주장에는 꽤 설득력 있는 반론들이 존재하고, 무시하고 넘어가면 글이 신앙 고백이 된다.

### 반론 1 - "에이전트가 테스트도 잘 짜주는데, 내가 미리 갖춰둘 필요가 있나"

가장 강한 반론이다. 에이전트에게 "수정하고 테스트도 추가해줘"라고 하면 실제로 테스트까지 만들어준다. 그렇다면 테스트가 없던 저장소에도 에이전트가 알아서 테스트를 채우지 않을까?

이 반론에는 실질적인 구멍이 하나 있다. **에이전트가 짠 테스트는 에이전트가 짠 코드를 검증한다.** 생산자와 검증자가 같은 컨텍스트에서 나오면, 오류가 테스트에 같이 스며들 가능성이 있다. 특히 위험한 형태가 이것이다. 구현이 이상하게 되어 있고, 에이전트가 그 구현에 맞춰 테스트를 짜서 통과하는 경우. 테스트는 초록불인데 동작은 틀렸다. 검증자가 생산자의 전제를 그대로 물려받은 것이다.

그렇다고 이 반론의 답을 "사람 손으로 직접 짠 테스트만 믿자"로 두면 곧 무너진다. 현실적으로 초기 기준선조차 대부분 AI 초안에서 출발할 것이기 때문이다. 진짜 경계는 **누가 타이핑했는가가 아니라 누가 승인하고 신뢰를 소유하는가**다.

- 에이전트가 짠 테스트라도 사람이 읽고 의도를 확인한 뒤 통과시켰다면, 이미 기준선 후보다
- 거기서 한 번 더, 시간이 지나며 여러 변경을 올바르게 걸러낸 경험이 쌓이면 기준선이다
- 아무 검토 없이 생성된 테스트는 몇 줄이든 기준선이 아니다. 참고 자료일 뿐이다

즉 기준선은 작성 주체로 정의되지 않고 **승인과 사용 이력으로 정의된다.** 기준선이 있으면 에이전트가 새로 짠 테스트도 그 위에서 평가할 수 있다. 기준선조차 없으면 평가할 축이 없다.

### 반론 2 - "테스트가 있으면 오히려 에이전트가 발목을 잡힌다"

이것도 사실인 부분이 많다. 실무에서 자주 겪는 현상들은 이렇다.

- 에이전트가 로직은 올바르게 고쳤는데 **깨진 테스트를 수정하느라 엉뚱한 곳까지 건드린다**
- 오래된 테스트가 옛 동작을 고정하고 있어서, 올바른 리팩토링이 "테스트 실패"로 보인다
- flaky(간헐적으로 실패하는) 테스트가 있으면 에이전트가 원인도 아닌데 그걸 고치겠다고 매달린다

세 번째 항목은 앞선 하네스 절에서 실행 환경의 문제로 언급했다. 여기서 보는 것은 같은 현상의 다른 면이다. 하네스가 아무리 좋아도 **테스트 코드 자체가 썩어 있으면** 판정 결과를 믿을 수 없다는 것. 즉 테스트는 **최신이고 신뢰할 때만 자산이고, 썩었으면 부채**다. 이 반론에 대한 실무적 답은 "테스트를 줄여라"가 아니라 다음과 같은 정리 작업이다.

| 썩은 테스트의 유형 | 처리 |
|---|---|
| 옛 동작을 고정한 테스트 | 삭제 또는 현재 의도에 맞게 갱신. 미련 없이 버린다 |
| flaky 테스트 | 원인 제거가 어려우면 우선 격리(`skip` + 이슈 등록). 에이전트 작업 경로에서 치운다 |
| 구현 세부를 검사하는 테스트 | 내부 호출 순서 같은 것을 검사하는 취약한 테스트는 행위 중심으로 재작성 |
| 느린 테스트 | 에이전트 반복 실행 시간을 잡아먹는다. 느린 것과 빠른 것을 계층으로 분리 |

### 반론 3 - "어차피 배포 환경에서 QA하면 되지 않나"

프론트엔드처럼 시각적 결과가 중요한 영역에서는 유효한 태도다. 실제로 눈으로 보는 것 이상의 검증은 드물다. 다만 이 태도가 통하는 범위에는 조건이 붙는다. **변경의 폭발 반경이 좁고, 되돌리기 쉬울 때**다. 서버 쪽 로직처럼 잘못이 사용자 데이터에 닿거나 롤백 비용이 큰 영역에서는 배포 후 발견이 최악의 검증 지점이다. 그래서 현실적인 답은 계층 분리다. 빠른 테스트가 대부분을 걷어내고, QA는 마지막 확인으로 남긴다.

## 정리 - 어디까지 주장할 수 있고 어디서 멈춰야 하나

이 글의 입장을 경계와 함께 정리하면 이렇다.

| 말할 수 있는 것 | 과하게 말하면 안 되는 것 |
|---|---|
| 검증 수단이 줄어든 환경에서 판정 장치 전반(테스트·타입 체크·하네스)의 상대 비중은 커진다 | 테스트가 없으면 에이전트를 못 쓴다 (커버할 수 있는 영역이 줄어들 뿐이다) |
| 승인되고 신뢰가 쌓인 테스트는 기준선이다. 작성 주체는 문제가 아니다 | 기준선 테스트가 항상 옳다 (썩었으면 먼저 정리해야 한다) |
| 실패하는 테스트는 에이전트에게 최고의 지시서다 | 모든 작업을 테스트 먼저로 시작해야 한다는 뜻은 아니다 |
| 하네스의 품질(결정성, 속도, 실패 메시지)이 에이전트 성능을 좌우한다 | 하네스만 고치면 된다. 판정할 테스트가 없으면 스캐너만 있는 셈이다 |
| flaky·구식 테스트는 에이전트 작업을 방해한다 | 그래서 테스트를 줄이라는 뜻은 아니다 |

실무 적용은 세 단계면 충분하다.

1. **기준선 확보**: 핵심 경로(로그인, 결제, 데이터 변조 지점)에만이라도 승인을 거친 테스트를 둔다. AI 초안이어도 사람이 검토하고 통과시키면 된다
2. **지시서 활용**: 에이전트에게 일을 맡길 때 "재현 테스트 먼저 작성 → 통과"를 프롬프트에 명시한다
3. **정리 습관화**: 에이전트가 테스트나 하네스 때문에 헤매는 경험이 생기면, 그 지점을 후보군에 올려둔다

에이전트 시대에 테스트의 의미가 바뀐 것을 한 문장으로 압축하면 이렇다. 사람에게 테스트는 **품질을 높이는 노력**이었지만, 에이전트에게는 **작업을 가능하게 하는 인터페이스**가 되었다. 노력은 밀릴 수 있지만 인터페이스가 없으면 작업 자체가 안전하게 시작되지 않는다.
