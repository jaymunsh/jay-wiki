Qwen3.8 세대가 나왔고, "27B짜리 로컬 모델이 Opus 4.6을 앞섰다"는 이야기가 같이 돌았다.
로컬에서 쓸 모델을 고르는 입장에서는 반가운 문장이지만, 이런 문장은 대개 벤더 발표를 한 번
옮긴 것이라 그대로 받으면 나중에 시간을 버린다.

그래서 지금 공개된 자료를 놓고 **확인된 것과 아직 아닌 것**을 갈라 봤다. 벤치마크 수치는 전부
모델 카드·리더보드·커뮤니티 측정을 옮긴 것이고 내가 잰 것이 아니다. 다만 마지막에
**내 M1 Max에서 한 번 돌려 본 기록**은 붙였다.

## 3.8 세대에서 받을 수 있는 것은 둘이다

| 모델 | 구조 | 라이선스 | 개인 장비 |
|---|---|---|---|
| Qwen3.8-Max | MoE 2.4T, 활성 95B | 커스텀 | 불가 |
| Qwen3.8-27B | dense 27B, 비전 포함 | Apache 2.0 | 가능 |

Max는 "Max 급 가중치를 처음 받을 수 있게 됐다"는 점에서 화제가 됐지만 2.4조 파라미터는
개인이 돌릴 대상이 아니다. 라이선스도 27B와 다르다. 매출·MAU 조건이 붙은 커스텀 라이선스라
규모가 커지면 별도 협의가 필요하다. 둘을 "오픈소스"라는 한 단어로 묶으면 안 되는 이유다.

## 27B에서 눈여겨볼 것은 파라미터 수가 아니라 층 구성이다

27B dense가 262K 토큰을 네이티브로 받는다는 것이 먼저 눈에 띄는데, 근거는 층 구성에 있다.

```
16 × (3 × (Gated DeltaNet → FFN) → 1 × (Gated Attention → FFN))
```

모든 층이 일반 어텐션이 아니다. 선형 어텐션 계열인 Gated DeltaNet 세 층마다 일반 어텐션을
한 층 끼웠다. 긴 컨텍스트에서 비용을 밀어 올리는 것은 층마다 쌓이는 KV 캐시인데, 그 층이
4분의 1로 줄어든 셈이다. 27B급에서 262K를 감당하는 값이 여기서 나온다.

긴 문서를 통째로 넣는 용도라면 이 구조가 파라미터 수보다 중요하다. 반대로 짧은 대화만
주고받을 거라면 굳이 이 모델일 이유가 줄어든다.

## 점수를 보기 전에, 무엇을 재는 것인지부터

이름이 비슷해도 재는 것이 다르다. 이 구분을 건너뛰면 표를 잘못 읽는다.

| 벤치마크 | 무엇을 재나 |
|---|---|
| DeepSWE 1.1 | 긴 호흡의 실제 개발 작업. 91개 저장소·5개 언어를 **새로 써서** 만들었고, 구현이 아니라 동작이 맞는지로 채점한다 |
| SWE-bench Pro | GitHub 이슈 해결. 1,865문제, 한 건당 평균 120줄 규모 |
| Terminal-Bench 2.1 | 터미널로 환경을 다루는 능력 전반. 개발이 가장 큰 갈래지만 과반은 아니고 과학 계산·ML도 섞인다 |
| OSWorld-Verified | 실제 데스크톱에서 GUI 작업을 끝내는 능력 |
| LiveCodeBench v6 | 최근 경진 프로그래밍 문제. 오염을 피하려 최신 문제만 쓴다 |
| SWE-MM | 화면·이미지가 낀 멀티모달 개발 과제 |
| GPQA Diamond | 대학원 수준 과학 문제. 코딩이 아니라 일반 추론 축 |

DeepSWE와 SWE-bench Pro의 차이가 특히 크다. 앞엣것은 새로 만든 문제라 외워서 풀기 어렵고,
뒤엣것은 공개 저장소의 이슈라 학습 데이터에 섞였을 수 있다.

## Opus 4.6을 앞섰다는 주장은 어디까지 확인됐나

벤더 발표는 SWE-bench Pro, QwenSWEBench, CoWorkBench, LiveCodeBench v6에서 Claude Opus 4.6 Max를
앞섰다고 적고 있다. 세대 간 상승폭도 크다.

| 항목 | 3.6-27B | 3.8-27B | 참고: Opus 4.6 |
|---|---|---|---|
| Terminal-Bench | 63.4 (2.1) | 73.0 (2.1) | 65.4 (2.0) |
| DeepSWE 1.1 | 13.3 | 42.2 | 공개 리더보드 상위에 없다 |
| OSWorld | 63.9 (Verified) | 84.3 (Verified) | 72.7 (Verified 아님) |
| SWE-bench Pro | — | 61.7 | 53.4 |
| SWE-MM | 25.7 | 38.6 | — |
| GPQA Diamond | — | 89.2 | — |

**오른쪽 열은 그대로 비교하면 안 된다.** Terminal-Bench는 2.1과 2.0이고 OSWorld는 Verified
여부가 갈린다. 버전이 다른 점수를 한 줄에 놓는 것 자체가 흔한 왜곡이라, 괄호로 남겨 뒀다.

DeepSWE가 세 배 넘게 뛴 것도 크게 보인다. 이 정도 폭이면 모델이 좋아진 것 말고도
평가셋 구성이 바뀌었거나 학습 데이터에 섞였을 가능성을 먼저 의심하는 편이 맞다.

다만 확인이 한 칸은 더 있다. datacurve의 DeepSWE와 ScaleAI의 SWE-bench Pro가 모델 카드와
같은 값을 싣고 있다고 보도된다. 점수가 재현된다는 뜻이다. 참고로 DeepSWE 리더보드의 상위는
claude-opus-5 74%, gpt-5.6-sol 73%, claude-fable-5 70%, claude-opus-4.8 59%, qwen3.8-max 57%
순이고, 27B는 상위 목록에서 확인되지 않는다.

### 비교의 바닥이 흔들린다

이 비교를 더 약하게 만드는 보도가 하나 있다. DeepSWE 팀이 SWE-bench Pro 결과를 감사했더니
Claude Opus 4.6·4.7의 통과 중 12%가 넘는 사례가 문제를 푼 것이 아니라 **git 이력에서 정답을
찾아온 것**이었다는 내용이다. 사실이라면 SWE-bench Pro 점수는 모델 간 비교의 기준이 되기
어렵고, "27B가 Opus 4.6을 앞섰다"는 문장도 그 위에 서 있는 셈이다.

여기서 내릴 결론은 어느 쪽이 낫다가 아니라 **이 축으로는 아직 못 가른다**이다.
점수가 재현되는 것과 실무에서 쓸 만한 것도 다른 문장이다.
릴리스 직후에 나온 분석 글 중 하나는 27B급의 현실을 이렇게 적었다. 작업량의 중간 대부분은
잘 처리하고 가장 어려운 10%에서 틀리며, 정말 복잡한 버그를 끝까지 고치는 비율은 대략 절반.
그 글이 권하는 운용도 명확하다. 로컬 27B로 양을 처리하고 어려운 것만 호스팅 모델로 넘겨서,
아직 검증되지 않은 모델이 단일 장애점이 되지 않게 하라는 것이다.

정리하면 "Opus 4.6급"은 **특정 코딩 벤치마크 몇 개에서 점수가 그렇다**까지가 확인된 범위다.

## 4비트로 내리면 얼마나 깎이나

커뮤니티가 여러 양자화를 같은 조건에서 비교한 자료가 있다. BF16 28.9GB를 기준으로 잰 top-1이다.

| 양자화 | 크기 | top-1 |
|---|---|---|
| BF16 (기준) | 28.9GB | 기준 |
| Q8_0 / Q6_K | 25GB 이상 | 기준과 사실상 수렴 |
| AD-IQ3_S | 13.8GB | 92.4% |
| IQ1_M | 8.5GB | 76.3% (쓰지 말라고 적혀 있다) |

읽을 점이 둘이다.

**25GB 위에서는 더 올려도 얻는 게 없다.** 64GB Mac이라면 8비트(약 28GB)가 그 구간이라,
품질을 최대로 원해도 8비트가 상한이고 그 위는 메모리만 더 쓴다.

**12~21GB 구간에서는 만든 사람에 따라 품질이 갈린다.** 같은 13.8GB급인데 KLD 기준으로 33%
차이가 났다. 4비트라는 이름표만 보고 아무 파일이나 받으면 그 차이를 그대로 먹는다는 뜻이다.
이 대역에서는 몇 비트인지만큼 누가 만들었는지가 중요하다.

일반론으로도 AWQ·GPTQ 4비트는 대부분의 평가에서 작지만 일관된 하락을 보인다.
4비트가 공짜라는 말보다는, 대체로 감당할 만한 값을 치른다는 쪽이 맞다.

## 64GB Mac에서 돌린다면

가중치만 놓고 보면 이렇다. 실제로는 KV 캐시가 위에 더 붙으므로 이 값이 바닥이다.

| 정밀도 | 가중치 | 64GB에서 |
|---|---|---|
| BF16 | 약 56GB | 사실상 불가 |
| 8비트 | 약 28GB | 가능. 품질 상한 |
| 4비트 | 약 16~18GB | 여유 있다 |

받는 경로는 셋이다.

| 경로 | 무엇 |
|---|---|
| Ollama | `qwen3.8:27b-mlx` — Apple Silicon용 MLX 네이티브 빌드 |
| LM Studio | `lmstudio-community/Qwen3.8-27B-MLX-4bit` |
| mlx-lm | `mlx-community/Qwen3.8-27B-4bit`, 3/5/6비트와 MXFP4·NVFP4도 있다 |

속도는 직접 재야 한다. 한 세대 전 3.6-27B 4비트를 M1 Max에서 잰 커뮤니티 수치가
생성 15.5 tok/s, 프롬프트 처리 67.4 tok/s, 피크 메모리 15.8GB였다. 같은 계열이니 비슷한
자리에서 시작하겠지만 이것도 남의 숫자다.

재기 전에 맞춰야 할 조건이 하나 있다. **이 모델은 thinking 모드가 기본으로 켜져 있다.**
같은 질문에도 토큰을 훨씬 많이 쓰므로, 조건을 안 맞추고 이전 모델과 비교하면 3.8이 느리다는
틀린 결론이 나온다. [Ollama와 oMLX를 같은 장비에서 비교했을 때](/7/local-llm-qwen36-ollama-omlx-benchmark)도
cache와 thinking 조건을 갈라서 재야 숫자가 설명됐다.

## 35B-A3B는 아직 소문이다

3.8 세대에서 개인적으로 기다리는 것은 27B가 아니라 이쪽이다. 총 35B에 활성 3B면 메모리는
작게 쓰면서 품질은 총량에서 나오는 구성이라, 개인 장비에서 가장 쓸모 있는 자리다.

지금 상태를 정확히 적으면 이렇다.

- 공식 발표는 **없다**
- 근거로 도는 것은 X 게시물 하나("GitHub 커밋에서 35B 총·3B 활성을 봤다")와 커뮤니티 요청 글이다
- 검색으로 확인되는 실물은 **이전 세대**뿐이다. Qwen3.6-35B-A3B와 3.5 버전은 있고, vLLM 모델
  레지스트리에도 그 둘만 있다

즉 "3.8에도 같은 자리가 나올 것"은 패턴 추론이지 근거가 아니다. 확인할 곳은 셋이다.
기사 말고 여기를 본다.

1. Hugging Face의 Qwen 조직 페이지에 해당 저장소가 생기는지
2. vLLM의 모델 레지스트리에 항목이 들어가는지
3. Qwen 공식 블로그 발표

## 심심풀이로 한 번 돌려봤다

글을 쓰고 나서 oMLX에 Qwen3.8-27B 4비트를 올려 한 번 시켜 봤다. 프롬프트는 한 줄이다.
"html에서 돌아가는 간단한 테트리스 게임 만들어볼래?"

![oMLX 실행 로그](/assets/projects/qwen3-8-27b-and-the-missing-35b-a3b/omlx-run-log.png)

| 항목 | 값 |
|---|---|
| 입력 | 231 토큰 |
| 생성 | 11,775 토큰 |
| 프리필 | 65 tok/s |
| 생성 속도 | 11 tok/s |
| TTFT | 3.57초 |
| **사고 시간** | **640.8초** |
| **전체** | **1,039.86초 (약 17분)** |

숫자를 그대로 읽으면 이렇다. 전체 17분 중 **10분 40초가 thinking**이었다. 답을 쓰기 시작하기
전에 시간의 62%를 생각하는 데 쓴 것이다. 앞에서 "thinking이 기본으로 켜져 있으니 조건을 맞추고
재라"고 적었는데, 그 말이 무슨 뜻인지 이 로그가 그대로 보여준다.

생성 속도 11 tok/s도 짚어 둘 만하다. 한 세대 전 27B를 M1 Max에서 잰 커뮤니티 수치가 15.5
tok/s였는데, 그보다 느리다. 같은 27B라도 이번 세대는 층 구성이 다르고 내 장비는 M1 Max라
최신 칩과도 다르다. **남의 숫자를 내 장비에 그대로 옮기면 안 된다는 사례가 하나 더 늘었다.**

결과물은 이렇다.

![생성된 테트리스 화면](/assets/projects/qwen3-8-27b-and-the-missing-35b-a3b/tetris-result.png)

겉보기에는 한 번에 나왔다. 점수·레벨·라인 카운터가 있고, 다음 블록 미리보기가 있고, 조작 안내에
소프트 드롭과 하드 드롭, 일시정지, 리스타트까지 들어 있다. 색상과 배경도 손대지 않은 상태다.
프롬프트 한 줄에 "간단한"이라고만 적었는데 그보다 더 만들어 왔다.

## 그런데 눌러 보니 시작 버튼이 시작을 안 했다

이 글을 올린 뒤에 다시 열어 보고서야 알았다. 첫 화면의 「시작」을 눌러도 게임이 안 돈다.
버튼 핸들러가 이렇게 쓰여 있었다.

```js
elOvBtn.addEventListener('click',()=>{
  if(over) start();      // over 는 시작 전에 false 다
  else togglePause();    // 그래서 「시작」이 일시정지 토글로 간다
});
```

게임 오버 상태에서만 start 로 간다. 처음 눌렀을 때는 일시정지가 켜지고, 한 번 더 누르면
오버레이만 사라진 채 빈 판이 남는다. 화면은 멀쩡해 보이는데 아무 일도 안 일어난다.

키보드 r 로는 시작이 됐는데, 그것도 **한글 입력 상태에서는 안 된다.** 코드가 e.key 만 보기
때문이다 — 한글로 입력하면 r 이 아니라 ㄱ 이 실려 온다.

**정지 화면만 보고 「돌아간다」고 적었던 것이 이 글의 실수다.** 스크린샷은 렌더링이 됐다는
증거지 상태 전이가 된다는 증거가 아니다. 캔버스에 격자와 블록이 그려져 있으면 눈으로는
구분이 안 된다.

## 두 줄만 고쳐서 올려 둔다

버튼 조건과 키 판정, 두 줄만 바꿨다. 로직·스타일·구조는 그대로다.

```js
if(!running||over) start(); else togglePause();   // 시작 전에도 start 로 간다
if(e.code==='KeyR'){ start(); return; }           // 한글 입력 상태에서도 먹는다
```

**[테트리스 직접 해보기 (모델이 만든 HTML, 두 줄만 고침)](/assets/projects/qwen3-8-27b-and-the-missing-35b-a3b/tetris-qwen3-8-27b.html)**

누르면 새 화면에서 돌아간다. 저장하려면 그 화면에서 다른 이름으로 저장하면 된다.
11KB짜리 파일 하나에 스타일과 로직이 다 들어 있고, 외부에서 무엇을 불러오지도 않는다.

**남은 버그 하나는 일부러 안 고쳤다.** 레벨 계산이 이렇게 되어 있다.

```js
level = lines/10|0 + 1;   //  |  가  +  보다 늦게 묶여 (lines/10) | 1 이 된다
```

10줄을 지워도 레벨이 1에 머물고, 30줄에서 3, 50줄에서 5로 튄다. 낙하 속도가 레벨을 따라가므로
체감으로는 "빨라지지 않는다". 연산자 우선순위 한 자리가 만든 차이고, 이런 것은 화면을
아무리 봐도 안 보인다.

정리하면 **겉모습은 기대 이상, 상태 전이는 아니고, 속도는 기대 이하**다. 250줄짜리 단일 파일을
17분 만에 받아 그 자리에서 열리는 것은 분명히 값이 있다. 다만 눌러 보기 전까지는 "돌아간다"고
말할 수 없다는 것을 이번에 값을 치르고 배웠다. 두 버그 다 화면에는 안 나타나는 종류다.

대화하듯 주고받아야 하는 작업이면 17분은 답답하고, 한 번 받아서 손보는 작업이면 쓸 만하다.
물론 이건 프롬프트 한 건이라 벤치마크가 아니다. 재현 조건을 갖춰 재는 것은 여전히 남아 있다.

## 그래서 지금 무엇을 할 것인가

주력을 갈아타지는 않기로 했다. 27B는 이전에 쓰던 MoE와 구조가 달라서 업그레이드가 아니라
다른 선택이고, 무엇보다 M1 Max에서 11 tok/s면 대화형으로 쓰기에는 느리다. 한 번에 던져 놓고
기다릴 수 있는 작업, 그리고 긴 문서를 통째로 넣는 작업이 이 모델의 자리라고 본다.
계속 쓴다면 4비트 대역에서 어느 저장소가 만든 것인지부터 다시 고를 것이다.

한계를 그대로 적으면, 내가 잰 것은 프롬프트 한 건뿐이라 벤치마크가 아니다. 같은 장비에서
thinking 조건까지 맞춰 여러 번 재야 어느 쪽이 나은지 말할 수 있다. 그 전까지는
확인된 것과 소문을 갈라 두는 것, 그리고 한 번 돌려 본 기록을 남기는 것까지가 전부다.
