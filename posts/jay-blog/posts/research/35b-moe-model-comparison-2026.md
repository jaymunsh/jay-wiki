35B MoE 모델을 고르려 하면 파라미터 숫자가 오히려 판단을 방해한다. Qwen3.5-35B-A3B, Qwen3.6-35B-A3B, Agents-A1, Ornith-1.5는 모두 35B 안팎이지만, 하나는 범용 멀티모달 모델이고, 하나는 코딩 에이전트에 가깝고, 하나는 환경 시뮬레이터이며, 하나는 과학 연구용 에이전트에 초점을 둔다.

더 곤란한 점은 벤치마크도 한 줄로 정리되지 않는다는 것이다. 어떤 모델은 SWE-bench 점수를 내고, 어떤 모델은 BrowseComp나 AgentWorldBench를 내고, 어떤 모델은 자기 기술보고서에만 있는 평가셋을 사용한다. 같은 35B라는 이유만으로 하나의 순위표에 욱여넣으면 모델의 장점보다 평가 방식의 차이를 비교하게 된다.

그래서 이 글은 2026년 8월 30일을 기준으로 올해 공개된 35B급 MoE 모델을 모으고, 먼저 같은 조건에 가까운 코딩 지표를 비교한 뒤, 공통 표에 들어오지 않는 모델은 각자의 대표 벤치마크로 따로 읽는다. 점수는 전부 모델 카드와 기술보고서에 공개된 수치이며, 동일 하드웨어에서 내가 다시 잰 결과는 아니다.

## 35B-A3B에서 두 숫자는 서로 다른 비용을 가리킨다

`35B-A3B`에서 앞의 35B는 모델 전체에 저장된 파라미터 수이고, 뒤의 A3B는 한 토큰을 처리할 때 활성화되는 파라미터 규모다. Qwen 계열 모델 카드에 따르면 Qwen3.5와 Qwen3.6은 35B 전체 중 약 3B를 활성화하고, 256개의 expert 가운데 8개의 routed expert와 1개의 shared expert를 사용한다. [Qwen3.5 모델 카드](https://huggingface.co/Qwen/Qwen3.5-35B-A3B)와 [Qwen3.6 모델 카드](https://huggingface.co/Qwen/Qwen3.6-35B-A3B)에 같은 구조가 적혀 있다.

이 숫자를 dense 3B 모델처럼 읽으면 안 된다.

| 구분 | 의미 |
|---|---|
| 35B total | 모델 파일에 들어 있는 전체 지식 용량과 가중치 규모 |
| 약 3B active | 한 토큰에서 실제 계산에 참여하는 부분의 규모 |
| 저장 메모리 | 대체로 35B 전체 가중치와 KV Cache를 감당해야 함 |
| 계산량 | dense 35B보다 작지만 라우팅·메모리 이동 비용이 남음 |

따라서 MoE는 계산량을 줄여 주지만 저장장치를 없애 주지는 않는다. 4비트 양자화라도 35B급 가중치는 대략 20GB 안팎이고, 긴 문맥을 쓰면 KV Cache와 런타임 버퍼가 추가된다. 16GB GPU에서 돌릴 수 있다는 말은 대개 적극적인 양자화나 CPU·RAM 오프로딩을 포함한 이야기다.

## 올해 공개된 35B급 후보는 이 여덟 가지다

아래 목록은 수많은 커뮤니티 파인튜닝을 제외하고, 공식 가중치나 공식 기술보고서가 확인되는 모델·모델 패밀리 중심으로 정리한 것이다.

| 모델 | 공개 시점 | 규모 | 주된 방향 | 공개 형태 |
|---|---:|---:|---|---|
| Qwen3.5-35B-A3B | 2026-02-24 | 35B / 3B active | 범용 멀티모달 | 공식 가중치, Apache 2.0 |
| Qwen3.6-35B-A3B | 2026-04-16 | 35B / 3B active | 코딩·에이전트 | 공식 가중치, Apache 2.0 |
| 0GM-1.0-35B-A3B | 2026-05-14 | 35B / 약 3B active | 에이전틱 코딩·툴 사용 | Qwen3.6 기반 파인튜닝, Apache 2.0 |
| Qwen-AgentWorld-35B-A3B | 2026-06-24 | 35B / 3B active | 에이전트 환경 시뮬레이션 | 공식 가중치, Apache 2.0 |
| Ornith-1.0-35B | 2026년 6월 | 35B MoE | 코딩 에이전트 | 공식 가중치, MIT |
| Agents-A1 | 2026-06-26 | 35B MoE | 검색·과학·툴 사용 에이전트 | 공식 가중치, Apache 2.0 |
| Mach-Mind-4-Flash | 2026-07-10 보고서 | 35B / 3B active | 후처리 기반 에이전틱 추론 | 기술보고서 중심 |
| Ornith-1.5-35B-A3B | 2026년 8월 | 약 35B / 3B active | 자기개선형 코딩 에이전트 | 공식 가중치, MIT |

여기서 중요한 구분이 있다. Qwen3.5, Qwen3.6, 0GM, AgentWorld, Agents-A1, Ornith는 모두 서로 완전히 다른 바닥 모델이라고 보기 어렵다. Qwen3.5 MoE 계열의 구조를 공유하거나 그 위에 후처리·파인튜닝을 얹은 모델이 많다. 따라서 아래 표는 “아키텍처 대결”이라기보다 “같은 크기대에서 어떤 학습 목표가 어떤 능력을 만들었는가”를 보는 표에 가깝다.

## 공통 코딩 벤치마크에서는 Ornith 계열이 앞선다

가장 비교하기 쉬운 축은 코딩 에이전트 벤치마크다. Qwen3.6과 Ornith의 공식 비교표에 함께 등장하는 지표를 모았다.

| 모델 | SWE-bench Verified | SWE-bench Pro | SWE-bench Multilingual | NL2Repo | ClawEval Avg |
|---|---:|---:|---:|---:|---:|
| Qwen3.5-35B-A3B | 70.0 | 44.6 | 60.3 | 20.5 | 65.4 |
| Qwen3.6-35B-A3B | 73.4 | 49.5 | 67.2 | 29.4 | 68.7 |
| Ornith-1.0-35B | 75.6 | 50.4 | 69.3 | 34.6 | 69.8 |
| Ornith-1.5-35B-A3B | **79.0** | **59.6** | **71.4** | **46.2** | **72.5** |

수치만 보면 세 가지 흐름이 보인다.

첫째, Qwen3.6은 Qwen3.5보다 코딩 에이전트 지표가 전반적으로 올라갔다. SWE-bench Verified는 70.0에서 73.4로, NL2Repo는 20.5에서 29.4로 상승했다. 둘째, Ornith-1.0은 같은 35B급이라도 코딩 특화 후처리가 점수에 직접 반영된다. 셋째, Ornith-1.5는 1.0보다 더 긴 실제 작업 흐름을 겨냥한 학습을 거쳐 다섯 지표 모두에서 앞선다.

다만 이 표를 절대 순위표로 사용하면 안 된다. [Qwen3.5 자체 모델 카드](https://huggingface.co/Qwen/Qwen3.5-35B-A3B)는 SWE-bench Verified를 69.2로 적고 있고, Qwen3.6 모델 카드의 비교표는 70.0을 사용한다. 평가 스캐폴드, 프롬프트, 수정한 문제셋, 실행 횟수가 다르기 때문이다. 0.8점 차이를 두고 어느 모델이 절대적으로 낫다고 말하지 않는 이유다.

## 에이전트와 검색 능력은 별도 지표로 봐야 한다

코딩 벤치마크에 점수를 내지 않은 모델까지 억지로 넣는 대신, 각 모델이 공개한 대표 에이전트 지표를 따로 놓았다.

| 모델 | 대표 지표 | 공개 점수 | 읽는 법 |
|---|---|---:|---|
| Qwen3.5-35B-A3B | MMLU-Pro / GPQA Diamond / IFBench / BrowseComp | 85.3 / 84.2 / 70.2 / 61.0 | 범용 지식·지시·검색의 기준선 |
| Qwen3.6-35B-A3B | MMLU-Pro / GPQA / AIME26 / ClawEval | 85.2 / 86.0 / 92.7 / 68.7 | 추론과 코딩 에이전트 쪽 개선 |
| 0GM-1.0-35B-A3B | MMLU-Pro / AIME26 / GSM-8K / MATH-500 | 77.62 / 83.33 / 96.82 / 95.80 | Qwen3.6 기반 실전 파인튜닝. 평가 범위는 제한적 |
| Qwen-AgentWorld-35B-A3B | AgentWorldBench Overall | **56.39** | 7개 에이전트 환경을 시뮬레이션하는 특화 지표 |
| Agents-A1 | IFBench / IFEval / BrowseComp | **80.61 / 94.82 / 75.51** | 장기 검색·지시·툴 사용에 초점 |
| Mach-Mind-4-Flash | AIME'26 / IFBench / BrowseComp-zh / ClawBench | **92.70 / 82.82 / 72.31 / 84.20** | 기술보고서에서 제시한 후처리 중심 결과 |
| Ornith-1.0-35B | SWE-bench Verified / NL2Repo / ClawEval | 75.6 / 34.6 / 69.8 | 코딩 에이전트 특화 결과 |
| Ornith-1.5-35B-A3B | GPQA Diamond / HLE with tools / BrowseComp / ClawEval | 89.2 / 33.4 / 67.6 / 72.5 | 추론·검색·코딩을 함께 강화한 최신 결과 |

이 표에서 굵은 숫자는 “전체 모델 중 객관적인 1위”라는 뜻이 아니다. 모델 카드가 선택한 평가셋과 실행 조건에서 나온 대표값이라는 뜻이다. 예를 들어 Agents-A1의 IFBench 80.61과 Mach-Mind의 IFBench 82.82는 같은 이름의 지표라도 보고서의 프롬프트와 실행 조건을 먼저 확인해야 한다.

## Qwen3.5는 범용 멀티모달 기준선으로 삼기 좋다

Qwen3.5-35B-A3B는 이 비교의 출발점이다. 비전 인코더를 포함한 멀티모달 모델이고, Gated Delta Network와 sparse MoE를 섞은 하이브리드 구조를 사용한다. 네이티브 문맥 길이는 262,144 토큰이며, 모델 카드에는 확장 시 약 1,010,000 토큰까지 가능하다고 적혀 있다.

장점은 범용성이다. 이미지와 텍스트를 함께 다루면서도 35B 전체를 매 토큰마다 계산하지 않고, 일반 지식·지시 이행·검색·코딩을 한 모델 안에서 처리한다. 이후 등장한 Agents-A1과 Qwen-AgentWorld도 이 계열의 구조와 체크포인트를 바탕으로 삼기 때문에, 35B MoE를 처음 이해하거나 다른 모델의 변화량을 비교할 때 기준선으로 두기 좋다.

반대로 특정 작업의 최고점을 노리는 모델은 아니다. Qwen3.5의 코딩 에이전트 점수는 Qwen3.6과 Ornith 계열보다 낮고, 환경 시뮬레이션은 AgentWorld처럼 그 목적을 위해 다시 학습된 모델에 밀린다. “모든 일을 평균 이상으로 하는 35B MoE”가 필요한 경우에 가장 자연스러운 선택이다.

## Qwen3.6은 같은 구조를 코딩과 에이전트 쪽으로 밀었다

Qwen3.6-35B-A3B는 Qwen3.5의 다음 세대 공개 가중치 모델이다. [공식 모델 카드](https://huggingface.co/Qwen/Qwen3.6-35B-A3B)는 프런트엔드 워크플로, 저장소 단위 추론, 과거 대화의 thinking context 보존을 주요 개선점으로 설명한다.

실제 수치도 이 방향과 맞는다. 공식 비교표에서 SWE-bench Verified 73.4, SWE-bench Pro 49.5, NL2Repo 29.4, ClawEval 평균 68.7을 기록한다. Qwen3.5보다 복잡한 저장소 작업과 도구를 끼운 흐름에 조금 더 맞춰진 모델이라고 읽을 수 있다.

장점은 범용성과 에이전트 사용성의 균형이다. Qwen3.5의 멀티모달·장문맥 기반을 유지하면서 coding agent와 tool calling에 더 가까워졌다. 로컬에서 하나만 받아 여러 용도로 쓰려는 경우에는 여전히 가장 안전한 기준 후보 중 하나다. 단, thinking이 켜진 상태에서는 응답 토큰 수가 늘어날 수 있어 단순 채팅의 체감 지연을 벤치마크 점수만으로 예측하면 안 된다.

## 0GM은 새 바닥 모델보다 실전형 Qwen3.6 파생 모델이다

[0GM-1.0-35B-A3B](https://0g.ai/blog/0gm-1-0-35b-a3b)는 0G가 Qwen3.6-35B-A3B를 바탕으로 에이전틱 코딩, 툴 사용, 장문맥 추론에 맞게 파인튜닝한 모델이다. 공식 발표는 35B 전체와 약 3B 활성, 256K 네이티브 문맥, Apache 2.0 라이선스를 명시한다.

이 모델의 장점은 구조 자체보다 목적이 분명하다는 데 있다. Qwen3.6을 일반 모델로 쓰는 대신, 여러 단계의 툴 호출과 코딩 작업을 바로 겨냥한다. 공식 공개 수치에서는 MMLU-Pro 77.62, AIME 2026 83.33, GSM-8K 96.82, MATH-500 95.80을 제시한다.

다만 이 숫자는 Qwen3.6과 같은 평가 파이프라인에서 완전히 통제된 비교 결과가 아니다. 공개된 평가셋 범위도 SWE-bench나 Terminal-Bench까지 넓지 않다. 따라서 0GM은 “Qwen3.6보다 무조건 똑똑한 모델”보다는 “Qwen3.6 기반의 에이전트 업무용 파생 모델”로 소개하는 편이 정확하다.

## Qwen-AgentWorld는 답변기보다 환경 시뮬레이터에 가깝다

[Qwen-AgentWorld-35B-A3B](https://github.com/QwenLM/Qwen-AgentWorld)는 일반 질문에 답하는 모델보다, 에이전트가 어떤 행동을 했을 때 다음 환경 관찰값이 어떻게 될지를 예측하는 모델이다. MCP, Search, Terminal, SWE, Android, Web, OS의 일곱 영역을 하나의 모델로 다룬다.

학습 과정도 다르다. 공식 설명은 환경 지식을 주입하는 continual pre-training, 다음 상태 예측을 활성화하는 SFT, 시뮬레이션 충실도를 높이는 RL의 세 단계로 구성된다. 기반 모델은 Qwen3.5-35B-A3B-Base다.

전용 [AgentWorldBench](https://huggingface.co/Qwen/Qwen-AgentWorld-35B-A3B)에서 Qwen-AgentWorld-35B-A3B는 전체 평균 56.39를 기록했고, 같은 표의 Qwen3.5-35B-A3B는 47.73이었다. 특히 MCP 64.79, Terminal 53.96, SWE 65.63, OS 65.92처럼 도구·환경의 상태를 예측해야 하는 영역에서 쓰임새가 뚜렷하다.

이 모델을 일반 대화 모델 순위표에 넣으면 장점을 놓치게 된다. 답변 품질보다 “에이전트가 다음에 보게 될 세계를 얼마나 그럴듯하고 일관되게 생성하는가”가 핵심이기 때문이다. 에이전트 테스트 환경을 만들거나 실제 환경과 상호작용하기 전에 시뮬레이션을 돌리는 용도라면 후보 가치가 높다.

## Ornith-1.0은 코딩 에이전트의 작업 지시까지 학습했다

[Ornith-1.0-35B](https://ornith.ai/ornith_1_0.html)는 Qwen3.5와 Gemma 4를 바탕으로 만든 에이전틱 코딩 모델이다. 일반적인 RL처럼 답만 잘 내도록 학습하는 대신, 작업을 해결하는 데 필요한 task-specific scaffold와 harness를 생성하는 능력까지 함께 학습한다.

공식 35B 결과는 Terminal-Bench 2.1 64.2, SWE-bench Verified 75.6, SWE-bench Pro 50.4, NL2Repo 34.6, ClawEval 69.8이다. 범용 지식 점수보다 저장소를 읽고, 터미널 도구를 쓰고, 여러 단계를 거쳐 패치를 완성하는 작업에 강점이 있다.

MIT 라이선스도 장점이다. 다만 “35B MoE”라는 모델 크기만 보고 범용 대화 모델로 고르면 기대와 다를 수 있다. 이 모델의 학습 목표는 처음부터 에이전틱 코딩이었고, 긴 답변을 생각한 뒤 도구를 호출하는 사용 패턴을 전제로 한다.

## Agents-A1은 여러 전문 에이전트의 능력을 한 모델에 합쳤다

[Agents-A1](https://huggingface.co/InternScience/Agents-A1)은 장기 검색, 공학, 과학 연구, 지시 이행, 툴 호출을 하나의 35B MoE 안에 통합하려는 모델이다. 공식 설명에 따르면 전체 도메인 SFT 뒤에 도메인별 teacher 모델을 만들고, multi-teacher multi-domain on-policy distillation으로 능력을 통합한다.

이 설계가 드러나는 지표가 있다. 공식 모델 카드의 비교표에서 IFBench 80.61, IFEval 94.82, BrowseComp 75.51을 기록했다. 또 HLE with tools 47.6, SciCode 44.33, MolBench-bind 56.8처럼 단순 코딩을 넘어 검색·과학·전문 작업을 섞은 평가를 제시한다.

장점은 한 영역만 잘하는 코딩 모델보다 업무 범위가 넓다는 데 있다. 브라우저 검색과 툴 호출이 필요한 리서치 에이전트, 과학 계산을 보조하는 에이전트, 여러 단계로 문제를 분해하는 시스템에 맞는다. 반대로 일반 채팅만 할 때는 이 모델이 가진 전문 에이전트 학습의 이점을 충분히 끌어내기 어렵다.

## Mach-Mind-4-Flash는 모델보다 후처리 방법이 먼저 보인다

[Mach-Mind-4-Flash 기술보고서](https://arxiv.org/abs/2607.09375)는 35B MoE와 3B 활성 파라미터를 기반으로, 대규모 사전학습보다 후처리와 에이전트 상호작용 환경을 강조한다. 여러 도메인별 RL expert를 병렬로 학습한 뒤 Multi-Teacher On-Policy Distillation으로 하나의 generalist 모델에 합치고, HMPO로 추론 과정의 길이를 줄였다고 설명한다.

보고서가 제시한 점수는 AIME'26 92.70, IFBench 82.82, Behavioral-SafetyBench 80.74, BFCL-v4 75.80, BrowseComp-zh 72.31, ClawBench 84.20이다. 특히 HMPO는 정확도 손실을 0.7 percentage point 이하로 두면서 reasoning chain을 19~46% 압축했다고 보고한다.

장점은 35B의 작은 활성 계산량으로 에이전트 추론의 효율을 노린다는 점이다. 다만 현재 확인되는 자료는 기술보고서 중심이고, 비교 가능한 공식 모델 가중치와 동일 조건의 재현 결과는 다른 후보보다 제한적이다. 따라서 본문에서는 실행 가능한 로컬 모델 후보라기보다, 35B MoE 후처리의 방향을 보여 주는 연구 사례로 분리하는 편이 안전하다.

## Ornith-1.5는 자기개선의 범위를 작업 생성까지 넓혔다

[Ornith-1.5-35B-A3B](https://ornith.ai/ornith_1_5.html)는 Ornith-1.0의 scaffold·rollout 최적화에서 한 단계 더 나아가, 학습할 task 자체와 task-specific harness, solution rollout을 함께 생성하고 개선하는 구조를 내세운다.

공식 35B 비교표에서 Terminal-Bench 2.1 67.8, SWE-bench Verified 79.0, SWE-bench Pro 59.6, SWE-bench Multilingual 71.4, NL2Repo 46.2, ClawEval 72.5를 기록했다. GPQA Diamond 89.2, HLE with tools 33.4, BrowseComp 67.6도 제시한다.

그래서 현재 후보 중에서는 코딩 에이전트에 가장 먼저 시험해 볼 모델이다. 단순 코드 완성보다 실제 저장소 작업, 테스트 실행, 도구 호출, 긴 작업 흐름의 성공률을 중요하게 본다면 1.5가 가장 설득력 있는 선택지다. 대신 응답이 reasoning model 방식으로 동작하고 35B 전체 가중치를 저장해야 하므로, 작은 GPU에서 “3B처럼 가볍게” 돌아간다고 생각하면 안 된다.

## 한 장의 순위표보다 용도별 선택표가 정확하다

공개 수치를 용도에 맞게 다시 읽으면 추천은 다음처럼 갈린다.

| 목적 | 우선 후보 | 이유 |
|---|---|---|
| 범용 멀티모달·로컬 기준선 | Qwen3.5-35B-A3B | 범용성, 비전 입력, 35B/3B 구조가 명확함 |
| 범용성과 코딩 에이전트의 균형 | Qwen3.6-35B-A3B | Qwen3.5보다 코딩·저장소·툴 사용 지표가 개선됨 |
| 에이전틱 코딩 점수 우선 | Ornith-1.5-35B-A3B | 공개된 공통 코딩 지표에서 가장 높은 결과 |
| 장기 검색·과학·전문 툴 사용 | Agents-A1 | 여러 도메인 teacher를 통합한 학습 목표 |
| 에이전트 환경을 시뮬레이션 | Qwen-AgentWorld-35B-A3B | 일곱 환경의 다음 상태 예측에 특화됨 |
| Qwen3.6 기반 실전 파인튜닝 | 0GM-1.0-35B-A3B | 툴 사용과 장문맥 코딩 업무를 직접 겨냥함 |
| 후처리·RL 연구 사례 | Mach-Mind-4-Flash | MOPD와 HMPO를 결합한 연구 방향이 뚜렷함 |
| 코딩 에이전트의 비교 기준 | Ornith-1.0-35B | 1.5와 함께 자기개선 학습의 변화량을 보기 좋음 |

## 벤치마크 점수는 모델 이름보다 평가 조건을 먼저 봐야 한다

이번 비교에서 가장 큰 결론은 “35B MoE 중 1등이 하나 있다”가 아니다. 모델이 무엇을 잘하도록 학습되었는지에 따라 점수를 읽는 축이 달라진다는 것이다.

| 벤치마크 | 측정하려는 능력 | 주의할 점 |
|---|---|---|
| SWE-bench Verified | 실제 GitHub 이슈 해결 | harness, timeout, 수정된 문제셋에 따라 달라짐 |
| SWE-bench Pro | 더 어려운 저장소·이슈 해결 | 공개·비공개 문제와 오염 가능성을 확인해야 함 |
| Terminal-Bench | 터미널 환경에서 여러 작업 수행 | 버전 2.0과 2.1을 섞으면 안 됨 |
| NL2Repo | 요구사항에서 새 저장소·코드 만들기 | 일반 코드 생성보다 긴 작업 흐름에 가까움 |
| ClawEval | 실제 사용자 분포에 가까운 에이전트 코딩 | 평가 harness와 실행 횟수 확인 필요 |
| IFBench·IFEval | 복잡한 지시를 정확히 따르는 능력 | 언어·프롬프트 구성에 민감함 |
| BrowseComp | 검색과 정보 종합 | 브라우저·검색 도구 사용 여부에 따라 달라짐 |
| AgentWorldBench | 환경 상태 예측의 형식·사실성·일관성 | 일반 채팅 점수와 직접 비교할 수 없음 |

특히 SWE-bench와 AgentWorldBench를 한 점수표에 섞으면 안 된다. 전자는 문제를 해결하는 실행 에이전트를 보고, 후자는 에이전트가 상호작용할 환경을 예측하는 모델을 본다. Qwen-AgentWorld가 코딩 에이전트 순위에서 빠졌다고 해서 약한 모델이라는 뜻이 아니라, 애초에 다른 역할을 맡은 모델이라는 뜻이다.

## 로컬 실행에서는 active parameter보다 메모리 계층이 더 중요하다

35B-A3B의 “3B 활성”은 생성 중 매 토큰의 계산량을 줄이는 데 유리하다. 하지만 모든 expert 가중치가 어딘가에 있어야 하고, 라우팅된 expert를 GPU·RAM 사이에서 이동시키는 비용이 남는다. 같은 35B-A3B라도 GPU 메모리, 시스템 RAM, PCIe 대역폭, 양자화 포맷, 런타임 지원에 따라 체감 속도가 달라진다.

실제로 고를 때는 다음 순서가 덜 위험하다.

1. 모델 전체 가중치가 내 GPU와 RAM에 들어가는지 확인한다.
2. 4비트 양자화 파일의 실제 크기와 KV Cache 여유를 함께 본다.
3. 내가 원하는 작업이 일반 대화인지, 코딩 에이전트인지, 검색·툴 사용인지 정한다.
4. 해당 작업의 벤치마크와 내 런타임에서의 실제 속도를 따로 확인한다.

긴 문맥을 쓸 때는 모델의 네이티브 문맥 길이만 보지 말고 KV Cache가 얼마나 늘어나는지도 봐야 한다. 262K를 지원한다는 문장은 “그 길이에서 충분히 빠르다”는 뜻이 아니다. 모델 카드의 최대 길이, 양자화 파일의 크기, 실제 batch와 context 설정은 서로 다른 숫자다.

## 결론은 하나의 우승자가 아니라 여덟 개의 역할이다

올해 공개된 35B급 MoE 모델은 같은 크기의 모델을 반복해서 내놓은 것이 아니다. Qwen3.5가 범용 멀티모달 기반을 만들고, Qwen3.6이 코딩과 에이전트 사용성을 밀었으며, 0GM과 Ornith는 그 기반을 특정 작업에 맞게 후처리했다. Agents-A1은 검색·과학·툴 사용을 한 모델 안에 합쳤고, Qwen-AgentWorld는 아예 에이전트가 움직일 세계를 예측하는 역할을 맡았다. Mach-Mind는 후처리 효율을 연구 주제로 끌어올렸고, Ornith-1.5는 작업과 harness를 스스로 만들어 가는 자기개선 루프를 확장했다.

그래서 선택도 이렇게 하는 편이 맞다. 하나만 받아 범용으로 쓰려면 Qwen3.6, 코딩 에이전트가 중심이면 Ornith-1.5, 검색과 과학 작업이면 Agents-A1, 에이전트 시뮬레이션이면 Qwen-AgentWorld를 먼저 본다. Qwen3.5는 여전히 비교의 기준선이고, 0GM은 Qwen3.6 기반 파생 모델의 실전성을 확인할 때, Mach-Mind는 연구 아이디어를 읽을 때 의미가 있다.

마지막으로 이 표의 숫자를 내 장비의 결과처럼 받아들이면 안 된다. 공식 점수는 모델을 소개하는 데는 충분하지만, 내 프롬프트·런타임·양자화·도구 하네스에서 같은 점수를 보장하지 않는다. 다음 단계는 같은 모델을 같은 양자화, 같은 에이전트 하네스, 같은 timeout으로 직접 재는 것이다. 그때 비로소 35B MoE의 숫자가 실제 선택으로 바뀐다.
