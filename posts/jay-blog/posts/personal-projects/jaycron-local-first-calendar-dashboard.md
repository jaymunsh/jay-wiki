일정은 Google Calendar, 할 일은 칸반, 짧은 기록은 메모, 반복할 일은 루틴에 흩어져 있었다. 도구 하나하나는 좋았지만,
오늘 무엇을 해야 하는지 확인하려면 여러 화면을 오가야 했다. Jaycron은 이 정보를 하나의 계정 서비스로 다시 만드는 대신
**한 화면에서 함께 보고, 데이터는 먼저 내 브라우저에 남기는 개인 작업 대시보드**로 시작했다.

React와 TypeScript로 만든 설치형 PWA이며 별도의 애플리케이션 백엔드는 없다. 칸반·메모·루틴은 브라우저에 즉시 저장하고,
Google Calendar는 일정이 필요할 때 연결하며, 여러 기기 사이의 이동은 Google Drive 앱 전용 공간으로 명시적으로 백업하고
복원한다.

![Jaycron 데스크톱 작업공간](/assets/projects/jaycron/jaycron-desktop.webp)

## 여러 생산성 도구를 합치는 대신 경계를 먼저 나눴다

처음부터 캘린더, Notion과 Todo 앱을 모두 대체하려고 하면 기능보다 동기화와 예외 처리의 범위가 더 빨리 커진다. 그래서
Jaycron이 직접 소유할 데이터와 외부 서비스에 맡길 데이터를 구분했다.

| 영역 | 저장 위치 | 선택한 이유 |
|---|---|---|
| 칸반 카드 | 브라우저 localStorage | 연결 없이 즉시 쓰고 오프라인에서도 관리 |
| 포스트잇 메모 | 브라우저 localStorage | 짧은 기록을 계정과 서버 없이 유지 |
| 반복 루틴 | 브라우저 localStorage | 날짜별 수행 기록을 일정과 분리 |
| 일정 | Google Calendar | 기존 일정·알림·모바일 캘린더 생태계를 그대로 사용 |
| 기기 간 백업 | Google Drive appDataFolder | 일반 Drive 파일 권한 없이 앱 데이터만 이동 |

루틴을 Calendar 일정으로 자동 생성하거나 칸반 카드를 곧바로 일정으로 바꾸지 않은 것도 같은 이유다. 한 화면에서 함께
보이더라도 각 정보의 의미와 수명은 다르다. 연결을 많이 만드는 것보다 사용자가 어느 데이터가 어디에 있는지 예측할 수 있게
하는 것을 우선했다.

## 로컬 우선 구조에 선택적 Google 연결을 더했다

Jaycron의 기본 기능은 Google에 로그인하지 않아도 동작한다. 화면에서 일어난 변경은 Zustand 상태를 거쳐 localStorage에 먼저
저장된다. Calendar와 Drive 연결은 로컬 기능을 열어 주는 필수 인증이 아니라 필요할 때 붙이는 외부 어댑터다.

~~~mermaid
flowchart TB
  A[React PWA] --> B[Zustand]
  B --> C[localStorage]
  C --> D[칸반·메모·루틴·화면 설정]
  A --> E[Google Identity Services]
  E --> F[Google Calendar API]
  E --> G[Google Drive API]
  F --> H[일정·알림·공휴일]
  G --> I[appDataFolder 백업]
~~~

Service Worker는 앱 자산을 캐시해 설치 후 오프라인 실행을 돕는다. 사용자 데이터와 앱 자산의 수명을 분리했기 때문에 새
버전의 화면을 배포하더라도 로컬 카드와 메모를 서버에서 다시 내려받을 필요가 없다.

## 월간 달력을 정보 밀도에 따라 세 단계로 만들었다

달력은 단순한 날짜 선택기에서 시작했지만, 일정 제목까지 한눈에 보고 싶다는 요구가 생겼다. 항상 큰 달력을 유지하면 칸반과
메모가 밀리고, 작게 유지하면 일정의 존재만 점으로 확인하게 된다. 그래서 달력 패널을 접기·기본·확대 세 상태로 나눴다.

- 기본 상태에서는 날짜와 일정·루틴의 존재를 작은 표시로 확인한다.
- 확대 상태에서는 날짜 셀마다 일정 제목을 최대 네 개까지 표시하고 나머지는 +N으로 요약한다.
- 패널을 접으면 얇은 경계와 다시 펼칠 수 있는 컨트롤만 남긴다.
- 월 제목을 눌러 연·월을 빠르게 이동하고, 오늘 버튼으로 현재 날짜로 돌아온다.

일정 유무에 따라 숫자의 위치가 움직이지 않도록 날짜와 하단 표시 영역의 높이를 고정했다. 일요일, 토요일, 다른 달 날짜,
선택 날짜와 오늘은 색만 다르게 사용해 같은 그리드를 유지한다. 좁은 화면에서 +N과 루틴 점이 숫자를 밀어내는 문제를 여러 번
겪으면서, 달력에서는 더 많은 정보를 넣는 것보다 **날짜 위치가 흔들리지 않는 것**이 우선이라는 기준이 생겼다.

## Google Calendar의 모델을 축소해서 다시 만들지 않았다

일정 편집기는 제목만 추가하는 작은 폼에서 시작해 시간 일정, 하루 종일 일정, 여러 날짜 일정, 색상과 알림을 다루도록
확장했다. 가능한 한 별도 Jaycron 일정 모델을 만들지 않고 Google Calendar 이벤트의 의미를 화면에 직접 반영했다.

| Calendar 정보 | Jaycron 표현 |
|---|---|
| start.dateTime / end.dateTime | 24시간제 날짜·시간 선택기 |
| start.date / end.date | 하루 종일 또는 여러 날짜 일정 |
| colorId | 일정 왼쪽 띠와 하루 종일 일정 배경색 |
| reminders.useDefault | 캘린더 기본 알림 |
| reminders.overrides | 없음·10분·30분·1시간·1일 전 알림 |
| 대한민국 공휴일 캘린더 | 읽기 전용 공휴일 표시 |

시간 선택은 15분 단위 목록을 제공하되 직접 입력도 허용한다. 종료 시간이 시작보다 앞서지 않게 보정하고, 일정 수정 상태에서는
색과 제목을 달리해 새 일정 작성과 구분한다. 삭제는 되돌릴 수 없는 Google 원격 변경이므로 로컬 카드 삭제와 달리 확인 절차를
남겼다.

## 하나의 OAuth 토큰으로 Calendar와 Drive를 연결했다

초기에는 Calendar와 Drive를 서로 다른 연결처럼 보이게 만들었다. 실제로는 두 API가 하나의 Google OAuth Access Token과 승인
흐름을 공유한다. 버튼은 기능별 진입점으로 분리하되 인증 상태는 하나로 관리하는 쪽으로 정리했다.

~~~text
https://www.googleapis.com/auth/calendar
https://www.googleapis.com/auth/drive.appdata
~~~

브라우저는 Google Identity Services에서 받은 Access Token을 Calendar와 Drive API에 직접 보낸다. Jaycron 서버를 거치지 않고,
Client Secret과 장기 Refresh Token도 사용하지 않는다. OAuth Client ID는 앱을 식별하는 공개 값이므로 배포 환경별 설정으로
분리하지만 비밀값처럼 취급하지 않는다.

토큰과 만료 시각은 브라우저에 저장해 유효한 동안 새로고침과 PWA 재실행 뒤에도 연결을 유지한다. 만료가 가까우면 아이콘으로
알리고 사용자의 클릭으로 재연결한다. 별도 백엔드가 없는 구조에서 팝업 없는 영구 로그인까지 약속하지 않는 대신, 토큰 저장과
권한의 경계를 단순하게 유지했다.

## Drive 동기화는 자동 병합보다 명시적인 백업으로 설계했다

localStorage만 사용하면 같은 브라우저에서는 편하지만 휴대폰과 노트북 사이에서 데이터가 자동으로 이동하지 않는다. 이를
해결하려고 Google Drive의 appDataFolder에 board.json과 memo.md를 저장한다.

~~~mermaid
flowchart TB
  A[기기 A localStorage] -->|Drive로 내보내기| B[appDataFolder]
  B --> C[board.json]
  B --> D[memo.md]
  B -->|Drive에서 불러오기| E[기기 B localStorage]
~~~

appDataFolder는 Jaycron만 접근할 수 있는 숨김 공간이라 일반 Google Drive 화면에는 나타나지 않는다. 사용자가 파일을 직접
찾을 수 없다는 단점이 있어 Drive 팝업에서 파일명, 수정 시각, 데이터 개수와 버전을 보여 준다.

실시간 양방향 동기화는 삭제 전파, 오프라인 변경과 충돌 병합까지 책임져야 한다. 현재는 로컬 변경 여부와 Drive 버전을 비교해
상태를 알리고, 사용자가 내보내기 또는 불러오기를 선택하게 했다. 삭제 직후 되돌리기 시간이 남아 있을 때는 Drive 동작을
비활성화해, 아직 확정되지 않은 로컬 상태가 다른 기기로 전파되는 것도 막았다.

## 칸반은 상태보다 다음 행동이 먼저 보이게 했다

칸반은 백로그, 진행중, 완료됨, 보류됨의 네 단계로 구성한다. 카드에는 제목, 개인·프로젝트 속성, 우선순위, 상세 내용, 마감일,
생성일과 최근 수정일을 저장하지만 메인 화면에는 판단에 필요한 정보만 남긴다.

| 열 | 기본 정렬 기준 |
|---|---|
| 백로그 | 생성일 최신순 |
| 진행중 | 우선순위 이후 사용자의 수동 순서 |
| 완료됨 | 최근 완료순 |
| 보류됨 | 최근 업데이트순 |

각 열은 네 장까지만 먼저 보여 주고 나머지는 하단의 N개 더 보기로 펼친다. 카드 전체를 드래그 영역으로 만들면 상세 모달을
여는 클릭과 충돌하므로 6-dot 핸들을 별도로 두되, 실제 잡을 수 있는 범위는 아이콘보다 넓혔다.

드래그 미리보기가 원본 카드의 상태와 연결된 채 빈 열로 이동하면서 화면이 사라지는 문제가 있었다. 이동 중 표시할 데이터와
실제 저장 상태를 분리하고, 드롭이 끝난 뒤 한 번만 상태를 확정하도록 바꿨다. 시각적인 버벅임을 줄이는 작업도 결국 상태 변경의
횟수와 책임을 줄이는 문제였다.

마감일은 24시간제로 표시하고, 미완료 카드가 3일 이내면 주황색, 1일 이내이거나 지났으면 빨간색으로 경고한다. 완료된 카드는
긴급도 대신 기록으로 읽히도록 회색을 유지한다.

## 월간 달력과 칸반 사이에 주간 초점을 추가했다

월간 달력은 전체 흐름을 보기 좋고 칸반은 상태별 작업을 보기 좋지만, 이번 주에 마감되는 카드만 빠르게 찾기는 어려웠다.
그래서 칸반 위에 접이식 주간 보기를 추가했다.

- 일요일부터 토요일까지 현재 주를 표시한다.
- 마감일이 있는 칸반 카드만 해당 날짜에 배치한다.
- 하루 최대 세 장을 보여 주고 나머지는 +N으로 요약한다.
- 카드를 누르면 같은 상세 모달을 연다.
- 칸반보기와 모두보기에서는 펼치고, 달력보기와 메모보기에서는 함께 접는다.

새로운 데이터 사본을 만들지 않고 기존 카드에서 마감일만 파생했기 때문에 월간 일정과 섞이지 않으면서도 이번 주의 작업을
빠르게 확인할 수 있다.

## 메모는 문서 편집기보다 여러 장의 포스트잇으로 만들었다

처음에는 하나의 큰 메모 영역과 편집 버튼을 두었다. 하지만 대시보드에서 필요한 것은 긴 문서보다 서로 다른 맥락의 짧은
기록이었다. 메모를 여러 장의 포스트잇으로 바꾸고, 각 메모가 색상·접힘·삭제 상태를 따로 갖게 했다.

기본색은 노란 sand이며 sage, sky, rose, peach, lilac, mint와 slate까지 여덟 가지를 제공한다. 메모 본문을 누르면 같은 크기를
유지한 채 textarea로 전환되고, 하단 도구 모음에서 제목, 굵게, 기울임, 취소선, 목록, 링크와 체크박스를 삽입한다.

Markdown 전체 편집기를 넣는 대신 react-markdown과 GitHub Flavored Markdown으로 필요한 문법만 렌더링한다. 렌더링된 체크박스는
직접 누를 수 있고, 체크된 항목은 원문을 갱신하면서 해당 줄 전체를 취소선 처리한다. 작성과 미리보기를 완전히 분리하지 않아
작은 포스트잇 안에서도 체크리스트를 바로 사용할 수 있게 했다.

## 접기 상태와 화면 모드를 사용자 환경으로 저장했다

데스크톱에서는 모든 영역을 한 번에 보는 것이 편하지만 모바일에서는 세로 길이가 빠르게 늘어난다. 칸반·메모·최근 활동과
주간 보기를 각각 접을 수 있게 하고, 상태를 localStorage에 저장해 앱을 다시 열어도 유지한다.

설정에는 개별 토글을 반복해서 누르지 않도록 네 가지 화면 모드를 추가했다.

| 화면 모드 | 펼쳐 두는 핵심 영역 |
|---|---|
| 달력보기 | 확대 달력 |
| 칸반보기 | 주간 보기와 칸반 |
| 메모보기 | 포스트잇 메모 |
| 모두보기 | 달력 기본 크기와 모든 작업 영역 |

프리셋을 적용한 뒤에도 각 영역은 다시 접거나 펼칠 수 있다. 화면 모드는 고정 레이아웃이 아니라 자주 사용하는 접힘 조합의
단축키다.

## 삭제는 로컬과 원격의 성격을 나눠 처리했다

칸반 카드, 메모와 루틴을 자주 정리하는 화면에서 매번 확인 창을 띄우면 흐름이 끊긴다. 로컬 데이터의 개별 삭제는 즉시 반영한
뒤 5초 동안 되돌리기 toast를 제공하고, 전체 데이터 비우기만 10초 동안 복구할 수 있게 했다.

반면 Google Calendar 일정 삭제와 Drive 백업으로 로컬 데이터를 교체하는 동작은 외부 상태를 바꾸거나 대량 데이터를 덮어쓴다.
이 동작에는 실행 전 확인을 유지했다. 모든 삭제를 같은 UX로 통일하는 것보다 복구 가능성과 영향 범위에 따라 마찰을 다르게
두는 편이 안전했다.

## 작고 차분한 대시보드를 만들기 위해 밀도를 반복 조정했다

초기 화면은 큰 radius, 넓은 padding과 강조색 때문에 카드가 실제 정보보다 더 많은 공간을 차지했다. 이후 디자인 기준을
다음처럼 정리했다.

- Pretendard 100~900 로컬 폰트를 사용하고 제목과 굵은 Markdown은 700으로 통일한다.
- 카드 padding과 제목줄 높이를 줄이고, 작은 radius와 가는 구분선을 사용한다.
- 연결·경고·마감처럼 의미가 있는 상태에만 색을 쓴다.
- 칸반·메모·최근 활동의 제목 크기, 굵기와 hover 범위를 맞춘다.
- 모바일에서는 헤더를 먼저 보여 주고 달력과 작업공간을 세로로 쌓는다.

폰트 파일을 넣는 것만으로 숫자와 굵기가 모두 같은 인상으로 보이지 않았고, 컴포넌트별 font-weight와 기본 브라우저 스타일을
확인해야 했다. select, date/time picker와 drag handle처럼 운영체제 기본 UI가 강하게 드러나는 요소도 전체 밀도에 맞춰 별도로
조정했다.

## 구현보다 연결 상태를 설명하는 일이 더 어려웠다

Google 연동 과정에서는 OAuth origin_mismatch, 승인된 JavaScript 원본, 토큰 만료와 계정 선택 팝업 같은 문제가 반복됐다.
특히 “연결됨”과 “방금 동기화됨”, “로컬 변경 있음”은 서로 다른 상태인데 하나의 체크 아이콘으로 표현하면 사용자가 무엇이
성공했는지 알기 어려웠다.

최종적으로 Calendar와 Drive 버튼은 기능 진입점으로 유지하고, 빨강·주황·초록은 연결 전·만료 임박·연결됨을 나타내도록 했다.
Drive의 로컬 변경과 충돌은 연결 색을 바꾸지 않고 팝업의 파일 정보와 동작으로 설명한다. 인증, 연결과 데이터 동기화를 하나의
boolean으로 축약하지 않은 것이 가장 중요한 상태 모델링 개선이었다.

## 검증과 문서를 기능의 일부로 남겼다

도메인 정렬과 날짜 처리, 저장소, Google 응답 변환과 주요 컴포넌트 상호작용은 Vitest와 Testing Library로 확인한다. TypeScript
검사와 Vite 프로덕션 빌드를 함께 실행하고, 달력 밀도와 모바일 레이아웃처럼 테스트가 대신 판단하기 어려운 부분은 실제 화면에서
직접 확인했다.

README 외에도 디자인 기준, Google Cloud 설정, 브라우저에서 Google API로 이어지는 구조, 공개 배포와 제3자 이용 방식을 별도
문서로 분리했다. OAuth Client ID, 권한 범위와 appDataFolder의 성격은 기능을 구현하는 것만큼 사용자가 알아야 할 운영 계약이기
때문이다.

## 현재 한계와 다음 단계

- Google Access Token이 만료되면 사용자가 직접 다시 연결해야 한다.
- Drive는 실시간 자동 동기화가 아니라 명시적인 내보내기·불러오기 방식이다.
- 두 기기에서 동시에 수정했을 때 자동 필드 병합을 제공하지 않는다.
- Calendar 권한은 공개 배포 전에 더 작은 범위로 줄일 수 있는지 검토해야 한다.
- 모바일 PWA의 OAuth 팝업, drag-and-drop과 장기간 동기화 흐름은 실제 기기 검증을 더 이어가야 한다.
- 카드와 일정이 많아지면 달력 셀 렌더링과 번들 분리를 다시 측정해야 한다.

공식 웹앱을 배포하면 이용자는 각자 OAuth Client ID를 만들지 않고 운영자가 등록한 Client ID로 자신의 Google 계정을 연결할 수
있다. 다만 공개 OAuth 앱은 동의 화면, 개인정보 처리방침, 승인 도메인과 범위 검증까지 운영자가 책임져야 한다. 셀프호스팅 사용자는
자신의 Google Cloud 프로젝트와 배포 도메인을 등록한다.

Jaycron은 모든 생산성 데이터를 하나의 새로운 서비스로 옮기는 대신, **로컬 데이터는 빠르고 독립적으로 유지하고 이미 잘
동작하는 일정 인프라는 선택적으로 연결하는 것**을 목표로 했다. 한 화면에 더 많은 기능을 넣는 과정에서도 데이터의 소유권,
동기화 시점과 복구 가능성을 사용자가 예측할 수 있어야 한다는 기준은 바꾸지 않았다.
