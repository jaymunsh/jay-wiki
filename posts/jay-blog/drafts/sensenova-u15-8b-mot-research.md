> 이 글은 2026년 8월 24일에 확인한 [모델 카드](https://huggingface.co/sensenova/SenseNova-U1.5-8B-MoT), [GitHub 저장소](https://github.com/OpenSenseNova/SenseNova-U1), [arXiv 논문(2605.12500)](https://arxiv.org/abs/2605.12500)을 기준으로 썼다. 벤치마크 수치는 전부 벤더가 공개한 것이고 내가 잰 것이 아니다. 릴리스가 2026년 8월 20일이라 나온 지 며칠 되지 않아 독립적인 검증 자료는 아직 없다.

이미지를 이해하는 모델과 이미지를 그리는 모델은 보통 따로다. 이해 쪽은 비전 인코더를 붙인 언어 모델이고, 생성 쪽은 확산 모델 계열이라서, "사진을 보고 설명한 뒤 고쳐 그려달라"는 작업을 하려면 두 모델을 파이프라인으로 잇는 것이 일반적이다.

[SenseNova-U1.5-8B-MoT](https://huggingface.co/sensenova/SenseNova-U1.5-8B-MoT)는 이 둘을 한 모델에 넣었다고 주장하는 저장소다. 상용 서비스가 아니라 Apache 2.0 가중치로 공개됐고, 개발자는 센스타임(SenseTime) 계열의 SenseNova 팀이다. 다만 이름부터가 관문이다. "8B"라 적혀 있는데 Hugging Face에는 18B로 표시되고, "MoT"가 무엇의 약자인지는 카드에 바로 안 나온다.

이 글에서는 이름 풀이부터 시작해, 같은 컬렉션에 있는 네 저장소의 차이, 벤치마크를 읽을 때 조심할 것들, 공개된 한계까지 순서대로 본다.

## 이름 풀이 - 8B와 18B가 다른 이유

먼저 구조부터. 이 모델은 [NEO-unify](https://huggingface.co/blog/sensenova/neo-unify)라는 아키텍처 위에 서 있다. 핵심 주장은 단순하다. **비전 인코더(VE)도, VAE도 없애고** 픽셀과 텍스트를 직접 처리한다는 것이다.

![SenseNova-U 시리즈 아키텍처. 왼쪽이 이해, 오른쪽이 생성이고 중앙 모델이 픽셀과 텍스트를 함께 입력받는다](/assets/projects/sensenova-u15-8b-mot-research/teaser.png)

이름은 이렇게 읽는다.

| 이름 조각 | 의미 | 근거 |
|---|---|---|
| U1.5 | 시리즈 버전. 2026년 4월의 U1 다음 | [GitHub 릴리스 노트](https://github.com/OpenSenseNova/SenseNova-U1) |
| 8B | **이해 쪽 파라미터 약 8B** | 논문 표: 이해 8.2B / 생성 8.2B |
| MoT | **Mixture of Transformers**. 이해용 전문가와 생성용 전문가를 나눠 둔 구조 | [논문 3장](https://arxiv.org/pdf/2605.12500) |

즉 "8B"는 이해 스트림 기준의 표기고, 생성 스트림용 파라미터 8.2B가 더 얹히므로 Hugging Face의 모델 크기 표기는 **18B**가 된다. 두 숫자가 다르다고 오류가 아니다. 재는 위치가 다를 뿐이다.

MoT는 MoE(Mixture of Experts)와 비슷해 보이지만 다르다. MoE가 토큰마다 필요한 전문가를 고른다면, MoT는 **이해 작업과 생성 작업에 각자의 FFN을 배정**하고 셀프 어텐션만 공유한다. 목적이 다른 두 학습 신호(텍스트 다음 토큰 예측, 이미지 픽셀 flow matching)가 서로를 방해하지 않게 하자는 설계다. 논문 표기로는 이해 전문가 1개 + 생성 전문가 1개의 dense 구성이고, U1 세대에 함께 공개된 A3B 변형(30B-A3B)이 MoE 구성이다.

텍스트는 자기회귀 cross-entropy로, 이미지는 픽셀 공간 flow matching으로 학습한다. 이미지를 잠재 공간으로 압축하는 VAE가 없으므로 32×32 패치로 직접 압축하는데, 논문은 이 인터페이스를 "near-lossless"라고 부른다. 다만 이것도 벤더의 표현이지 독립 검증된 것은 아니다.

## 컬렉션의 네 저장소는 무엇이 다른가

[U1.5 컬렉션](https://huggingface.co/collections/sensenova/sensenova-u15)에는 네 항목이 있다. 이름이 비슷해서 하나로 보이지만 역할이 다르다.

| 저장소 | 정체 | 누구용인가 |
|---|---|---|
| [8B-MoT](https://huggingface.co/sensenova/SenseNova-U1.5-8B-MoT) | **최종 릴리스. SFT 이후 RL까지 거친 체크포인트** | 그냥 쓰려는 사람. 기본 선택지 |
| [8B-MoT-SFT](https://huggingface.co/sensenova/SenseNova-U1.5-8B-MoT-SFT) | 지도 학습(SFT) 단계까지의 체크포인트. RL 적용 전 | 파인튜닝·연구 출발점. RL 이후 가중치에서 시작하고 싶지 않을 때 |
| [8B-MoT-LoRAs](https://huggingface.co/sensenova/SenseNova-U1.5-8B-MoT-LoRAs) | LoRA 어댑터 모음. **LoRA-8step은 8스텝 고속 추론용** | 생성 속도가 우선인 사람. 품질을 조금 내고 시간을 크게 줄인다 |
| [8B-MoT-Preview](https://huggingface.co/sensenova/SenseNova-U1.5-8B-MoT-Preview) | 정식 릴리스 약 3주 전의 미리보기 버전 | 이제 볼 이유가 적다. 비교 연구용 |

정리하면 **일반 사용은 MoT, 파인튜닝 출발점은 MoT-SFT, 빠른 추론은 LoRA-8step**이고 Preview는 역할이 끝났다. 참고로 U1 세대에는 이해 백본을 MoE로 키운 A3B 변형(30B-A3B)도 있었는데, U1.5 컬렉션에는 8B dense만 올라와 있다. A3B급 U1.5가 나올지는 지금으로선 발표된 것이 없다.

## U1.5에서 달라졌다고 주장하는 여섯 가지

모델 카드가 내세우는 개선점은 이렇다.

1. 이미지 생성 품질(구도·색 조화·재질·조명)
2. 한·영 텍스트 렌더링과 인포그래픽(텍스트가 많은 디자인)
3. 네이티브 4K 생성(전역 구조와 색 일관성 유지)
4. 이미지 편집 신뢰성(대상 정체성과 미편집 영역 보존)
5. 복합 지시 이행(개수·공간 관계·다중 제약)
6. 정밀 시각 제어(바운딩 박스·시각 마커·참조 이미지)

공식 쇼케이스가 이 여섯을 어떻게 보여주는지 먼저 보자. 생성 쪽 예시다. 텍스트가 밀집된 포스터와 인포그래픽이 중심에 있다.

![U1.5 생성 쇼케이스. 센스타임 포스터, 여행 인포그래픽, 텍스트 밀집 디자인과 사진 예시](/assets/projects/sensenova-u15-8b-mot-research/showcases-gen.webp)

편집과 다중 입력 쪽이다. 인포그래픽의 요소만 갈아끼우거나, 여러 참조 이미지를 합쳐 한 장을 만드는 예시가 포함돼 있다.

![U1.5 편집·다중 입력 쇼케이스. 인포그래픽 요소 교체, 포스터 부분 수정, 다중 참조 합성](/assets/projects/sensenova-u15-8b-mot-research/showcases-edit.webp)

다만 이 이미지들을 읽을 때 한 가지 조건이 붙는다. **쇼케이스는 벤더가 잘 되는 사례를 골라 편집한 것**이다. 여섯 개선점이 실제 프롬프트에서 일관되게 나오는지와는 별개의 문제다.

여섯 중에서 이 모델의 정체성을 가장 잘 보여주는 것은 2번과 4번이라고 본다. **텍스트가 많은 이미지를 만들고, 이미지를 "고치는" 작업**은 이해와 생성이 한 모델 안에 있을 때 이론적으로 유리한 영역이기 때문이다. 확산 모델만으로는 이미지 속 글자를 읽고 고치는 작업이 구조적으로 어렵다. 위 편집 예시에서 인포그래픽의 레이아웃과 나머지 텍스트를 유지한 채 주제 요소만 바꾼 장면이 바로 그 이점을 노리는 작업이다. 통합 구조가 실제로 이점을 보이는지가 이 모델의 존재 이유를 가늠하는 지점이다.

## 벤치마크는 어디까지 믿을 수 있나

모델 카드가 싣는 비교 차트는 이렇다.

![U1.5 벤치마크 레이더 차트. 좌부터 일반 생성·텍스트 렌더링·인포그래픽, 시각 추론·편집, 순수 텍스트·시각 이해](/assets/projects/sensenova-u15-8b-mot-research/benchmark-radial.webp)

차트를 읽기 전에 조심할 것이 세 가지 있다.

**첫째, 전부 벤더 자체 평가다.** 비교 대상은 GPT-Image-2, Gemini 3 Pro Image, Nano Banana 2.0, Qwen-Image-2512, Seedream 5.0 같은 상위 상용 모델인데, 수치 출처는 전부 SenseNova가 공개한 자료다. 릴리스가 일주일도 안 돼서 독립적인 재현이나 커뮤니티 측정은 아직 확인되지 않는다.

**둘째, 생성 벤치마크의 채점 방식을 봐야 한다.** 공개된 [평가 스크립트](https://github.com/OpenSenseNova/SenseNova-U1/blob/main/evaluation/docs/image_generation.md)에 따르면 이미지를 생성한 뒤 **OpenAI 호환 VLM 판정 모델(기본값 Gemini 3 Pro)이 점수를 매기는** 구조다. 판정자가 누구냐에 따라 점수가 달라지는 방식이라, 같은 차트 안의 숫자라도 절대값으로 읽기보다 상대 순위의 참고로 읽는 편이 안전하다.

**셋째, 차트 각주에 조건 차이가 적혀 있다.** Qwen-Image 비교에는 프롬프트 증강(Prompt Enhance) 사용 여부 각주(미사용 시 52.62)가, RISEBench에는 thinking 모드 사용 여부 각주가 붙어 있다. 조건이 섞인 비교라는 뜻이다.

상세 수치 표도 카드에 함께 있다.

![항목별 상세 벤치마크 표](/assets/projects/sensenova-u15-8b-mot-research/benchmark-combined.webp)

정리하면 벤치마크에서 말할 수 있는 것은 "**벤더 공개 수치 기준으로 이해·생성 여러 항목에서 동급 오픈소스 중 상위권을 주장한다**"까지고, "GPT-Image-2를 이겼다"를 독립 검증된 사실로 말할 수 있는 시점은 아직 아니다.

## 공개된 한계 - 벤더 스스로 적어둔 것

모델 카드의 Ongoing Improvements 절은 이 모델이 아직 못 하는 것을 꽤 구체적으로 적고 있다. 이 부분이 이 글에서 가장 실용적인 절일 수 있다.

| 한계 | 내용 | 완화 방법(카드 명시) |
|---|---|---|
| 색·디테일 과잉 | 과포화 색, 과도한 고주파 디테일이 나올 수 있다 | `cfg_scale` 낮추기 |
| 조밀한 텍스트 오류 | 길고 작고, 한·영 섞인 텍스트에서 오류 | 프롬프트 증강 레시피 사용 |
| 제약 많은 레이아웃 | 정확한 개수·정렬·위계가 흐트러질 수 있다 | 명시적으로 없음 |
| 인체 디테일 불안정 | 작은 얼굴, 손, 사지가 흔들린다 | 명시적으로 없음 |
| 복잡한 편집 드리프트 | 다중 참조·광역 편집에서 보존해야 할 영역이 같이 변한다 | 명시적으로 없음 |

여기에 U1 세대 카드부터 이어지는 제약 하나가 더 있다. **컨텍스트 길이가 32K 토큰**이라는 것. 이해 모델로서 긴 문서나 많은 이미지를 한 번에 넣는 용도에는 제한이 있다. 이 모델의 자리는 "긴 컨텍스트 이해기"가 아니라 "이미지를 보고 그리는 모델"임을 다시 확인해주는 수치다.

## 실행하려면

| 항목 | 확인된 내용 |
|---|---|
| 라이선스 | Apache 2.0 (상업적 사용 가능) |
| 파라미터 | 18B (이해 8.2B + 생성 8.2B) |
| 환경 | Python 3.11, PyTorch 2.8, CUDA 12.8 기준 |
| 추론 코드 | [GitHub 저장소](https://github.com/OpenSenseNova/SenseNova-U1/tree/refs/heads/feat/u1.5)의 예제 스크립트 |
| 설치 없이 써보기 | [SenseNova-Studio 웹 데모](https://unify.light-ai.top/) |
| 양자화 | llama.cpp·LM Studio·Ollama 경로 양자화 2종 존재 |
| Hugging Face 추론 제공자 | 미배포. API로 바로 쓸 수는 없다 |
| 다운로드 | 최근 한 달 약 1.4k (릴리스 일주일 기준) |

주의할 점은 이 모델이 **일반적인 텍스트 생성 모델 파이프라인과 다르다**는 것이다. `AutoModel.from_pretrained`에 `trust_remote_code=True`가 필요하고, 텍스트-이미지 생성과 편집이 서로 다른 예제 스크립트로 분리되어 있다. Ollama 같은 도구에 익숙한 사람이 "8B니까 로컬에서 돌리겠다"고 접근하면 환경 준비(CUDA GPU)부터 장벽이 있다. 가장 빠른 확인 경로는 웹 데모다.

## 정리 - 이 모델의 자리

| 사용 상황 | 판단 | 근거 |
|---|---|---|
| 텍스트 많은 이미지·인포그래픽 생성 | **시험해볼 가치가 있다** | 벤더 수치상 강조점이고, 통합 구조의 이론적 이점 영역 |
| 이미지 편집(부분 수정, 참조 기반) | 시험해볼 만하다 | 다만 복잡한 편집에서 드리프트를 벤더 스스로 인정 |
| 긴 문서·대규모 멀티모달 이해 | **맞지 않다** | 컨텍스트 32K 제한 |
| 검증된 품질이 중요한 운영 서비스 | **아직 이르다** | 릴리스 일주일, 독립 검증 부재, 자체 평가 의존 |

이 모델을 지켜볼 때의 기준도 정리해둔다. 앞으로 확인할 것은 새로운 벤더 발표가 아니라 이 셋이다. 첫째, 커뮤니티나 서드파티의 재현 측정이 나오는가. 둘째, 논문에서 예고된 기술 보고서와 학습 코드가 실제로 공개되는가. 셋째, A3B급 상위 변형이 U1.5에도 나오는가.

통합 멀티모달이라는 접근 자체는 이해와 생성의 경계가 필요 없어지는 방향을 가리키고 있고, Apache 2.0으로 이 구조를 직접 돌려볼 수 있다는 것 자체가 이 저장소의 값이다. 다만 그 값이 실제 품질로 이어지는지는 지금 공개된 자료만으로는 판정할 수 없다. 웹 데모에서 텍스트 렌더링과 편집 작업 몇 개를 직접 돌려본 뒤, 결과가 따라온다면 다음 글에서 기록을 덧붙일 생각이다.
