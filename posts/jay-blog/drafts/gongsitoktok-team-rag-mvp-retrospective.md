공시톡톡은 DART 정기공시를 검색하고 근거와 함께 답변하는 기업 공시 RAG 챗봇이다. KT그룹의 **AX전략 기획 및
멀티 에이전트 서비스 개발** 과정에서 세 개 RFP 중 하나를 선택해 2026년 6월 15일부터 26일까지 4명이 로컬 MVP를 만들었다.

완성 화면과 해피패스 시연은 동작했다. 하지만 자유 질문과 복합 질문까지 안정적으로 처리하는 챗봇 품질에는 아쉬움이 남았다.
이 글은 기능을 많이 구현했다는 설명보다, 짧은 기간에 팀의 결과물을 통합하면서 무엇을 선택했고 무엇을 충분히 검증하지
못했는지를 구분해 기록한다.

![삼성전자 영업이익을 묻고 이어서 매출을 질문하는 공시톡톡 멀티턴 화면](/assets/projects/gongsitoktok/chat-multiturn.webp)

## 로컬 MVP에서 확인한 범위만 다룬다

사용자는 기업을 선택하고 공시 내용을 질문한다. 시스템은 DART 원문, 정형 재무 데이터와 검색 근거를 조합해 답변하고,
출처와 신뢰도 정보를 함께 반환한다. 첫 질문 뒤에는 같은 채팅방에서 후속 질문을 이어갈 수 있다.

| 구분 | MVP 범위 |
|---|---|
| 사용자 화면 | 기업 선택, 로그인, 채팅, 멀티턴, 마이페이지 |
| Spring | 인증, 채팅방 수명주기, 대화 이력, FastAPI 연동 |
| AI 서비스 | 공시 인제스트, 검색, 라우팅, 답변 작성과 검증 |
| 데이터 | PostgreSQL, Chroma, FastAPI 보조 SQLite |
| 실행 환경 | 세 애플리케이션을 로컬에서 실행하고 시나리오로 시연 |

운영 배포와 부하 검증까지 완료한 서비스는 아니다. 보고서의 운영·보안 항목 일부는 다음 단계 제안이며, 이 글에서는 실제 로컬
MVP에서 구현하고 확인한 범위만 다룬다.

## 역할 분담은 계획대로만 가지 않았다

초기 역할은 다음과 같이 나눴다.

| 구분 | 초기 담당 |
|---|---|
| 나 | Spring 백엔드 |
| 팀원 A | React 프론트엔드 |
| 팀원 B | CrewAI 기반 FastAPI·AI |
| 팀원 C | 문서와 발표 |

각 영역을 병렬로 개발한 뒤 통합하는 방식으로 시작했다. 나는 Spring을 단독으로 구성했고, React 초기 화면을 제외한 주요 화면과
API 연동을 마무리했다. 통합 과정에서 기존 CrewAI 기반 AI 서비스의 요약 품질과 구조를 다시 검토하면서 PydanticAI 전환,
하이브리드 검색과 평가셋 재구성까지 맡게 됐다. 발표 자료와 발표 자체는 팀원의 역할로 남겼다.

따라서 최종 코드 기여 범위가 초기 계획보다 커졌지만 프로젝트 전체를 혼자 만든 것은 아니다. 문제 정의, 초기 화면, 기존 AI
파이프라인과 발표는 팀의 선행 작업 위에 있었고, 나는 이를 연결하고 다시 구성하는 역할에 집중했다.

## 세 애플리케이션의 책임을 분리했다

~~~mermaid
flowchart TB
  U[사용자] --> R[React]
  R --> S[Spring Boot]
  S --> P[(PostgreSQL)]
  S --> F[FastAPI PydanticAI]
  F --> C[(Chroma)]
  F --> D[DART·재무·거시 데이터]
~~~

- React는 사용자 흐름과 HTTP 요청을 담당한다.
- Spring은 인증, 채팅방, 만료, 대화 이력과 외부 AI 호출의 경계를 담당한다.
- FastAPI는 공시 검색과 추론에 집중하고 통합 환경에서는 stateless 응답 서비스로 동작한다.
- 각 서비스는 다른 서비스의 저장소를 직접 수정하지 않는다.

Spring과 FastAPI의 요청·응답은 AI 측 초기 응답안을 바탕으로 필요한 필드를 함께 정리했다. 답변, 인용, 신뢰도, 의도와 trace
정보를 명시적인 계약으로 전달하고, 정상 응답만 Spring의 대화 이력에 저장하도록 했다.

이 경계 덕분에 AI 내부 구현을 바꿔도 사용자 계정과 채팅방 수명주기는 Spring에 남았다. 반대로 짧은 일정 탓에 계약을 먼저
고정하고 각자 독립적으로 검증한 뒤 합치는 수준까지는 가지 못했고, 실제 통합 과정에서 필요한 필드와 분기를 계속 보완해야 했다.

## 사용자가 질문하고 답을 받기까지

화면에서 보이는 것은 채팅 한 번이지만 내부에서는 인증, 채팅방 상태, AI 검색과 이력 저장이 순서대로 연결된다.

~~~mermaid
sequenceDiagram
  participant U as User
  participant R as React
  participant S as Spring
  participant A as FastAPI
  participant V as Chroma
  participant P as PostgreSQL
  U->>R: 기업 선택 후 질문
  R->>S: ask 또는 continue
  S->>S: 사용자·채팅방·만료 검증
  S->>A: 질문·회사·history·traceId
  A->>A: intent와 검색 조건 구성
  A->>V: vector와 BM25 검색
  V-->>A: 공시 근거 후보
  A->>A: 재무·거시 근거 결합 후 답변·검증
  A-->>S: answer·citations·confidence
  S->>P: 정상 응답과 대화 이력 저장
  S-->>R: 채팅 응답
~~~

첫 질문은 새 채팅방을 만들고, 이어하기는 기존 방의 소유권과 활성 상태를 확인한 뒤 직전 대화 이력을 AI에 전달한다. AI가
실패하거나 timeout이면 실패 응답을 대화 이력에 정상 답변처럼 저장하지 않는다. 이 구분으로 사용자가 보는 대화 기록과 실제
성공한 AI 응답을 일치시키려 했다.

## Spring에서 인증과 채팅방 수명주기를 만들었다

Spring Boot 3.5와 Java 21을 사용해 사용자 계정, 토큰, 채팅방과 대화 이력을 관리했다. AI 응답이 수 초에서 길게는 수십 초까지
걸릴 수 있어 요청 코드는 이해하기 쉬운 동기 흐름으로 유지하면서 Java 21 virtual thread 위에서 WebClient 응답을 기다리게 했다.

이는 비동기 코드를 없애면 모든 성능 문제가 해결된다는 뜻이 아니다. AI 서비스의 timeout과 동시 요청 상한은 별도로 필요하며,
CPU 작업이 carrier thread를 오래 점유하지 않게 해야 한다. BCrypt 같은 의도적으로 무거운 연산은 고정 플랫폼 thread pool로
분리하고, 동시성 제어에는 synchronized보다 ReentrantLock을 사용해 pinning 가능성을 줄였다.

### 인증 복원과 토큰 경계를 Spring 소유로 뒀다

- Access Token은 프론트 메모리에만 두고 Refresh Token은 httpOnly cookie로 전달했다.
- 새로고침 시 refresh를 사용해 사용자 세션을 복원한다.
- 로그아웃과 토큰 회전 상태는 Spring이 소유한다.
- JWT 검증 결과와 blacklist 조회에는 Caffeine cache를 사용했다.
- 인증 복원이 끝나기 전 보호 화면이 로그인 실패로 판단하지 않도록 완료 상태를 별도로 표시했다.

### 채팅방을 30분 활성 세션으로 모델링했다

채팅방은 단순 CRUD가 아니라 활성 세션으로 모델링했다. 마지막 질문 시간을 기준으로 30분 동안 활성이고, 만료되면 isActive를
false로 바꾸고 closedAt을 기록한다. 만료 확인은 한 경로에만 의존하지 않았다.

| 확인 시점 | 처리 |
|---|---|
| 이어하기 요청 | 즉시 만료를 검사하고 410 CHAT_ROOM_EXPIRED 반환 |
| 채팅방 목록 조회 | 이미 만료된 방을 lazy close |
| 1분 주기 scheduler | 사용자가 화면을 떠난 방도 일괄 close |

프론트는 410을 받으면 오래된 방에 계속 요청하지 않고 안내 뒤 새 채팅으로 복구한다. 한 브라우저의 다른 탭에서 방이 바뀐 경우는
React Query의 focus refetch와 410 복구로 맞췄다. BroadcastChannel을 쓰지 않아 두 창이 항상 동시에 보이는 환경에서는 즉시
동기화되지 않는 한계도 남겼다.

### FastAPI 오류를 사용자 응답으로 번역했다

WebClient에는 연결·응답 timeout을 두고 FastAPI의 오류 code를 Spring ErrorCode로 변환했다. timeout, 잘못된 요청, AI 내부 오류와
검색 근거 부족을 같은 500으로 뭉개지 않고 Spring의 GlobalExceptionHandler가 4xx·502·504로 응답하도록 했다.

모든 요청에는 X-Trace-Id를 전달했다. Spring MDC의 식별자를 FastAPI 요청 header로 보내고, AI 측에서는 같은 값을 Logfire root
span에 연결해 router, 검색, writer와 verifier 단계를 한 요청으로 따라갈 수 있게 했다. 운영 관측 플랫폼까지 구축한 것은 아니지만
서로 다른 런타임을 같은 요청 ID로 묶는 계약을 만든 것이다.

## React에서는 서버 상태와 화면 상태를 나눴다

초기 화면 이후의 주요 화면 구성과 API 연동을 맡았다. React 19, TypeScript와 Vite를 사용하고 상태의 성격에 따라 zustand와
React Query의 책임을 나눴다.

| 상태 | 도구 | 이유 |
|---|---|---|
| 인증 사용자·Access Token·복원 완료 | zustand | 현재 브라우저 세션의 클라이언트 상태 |
| 채팅방·대화 이력·기업 정보 | React Query | 서버 응답 cache와 invalidate·refetch가 필요 |
| 질문 입력·패널·timer | component와 custom hook | 화면 수명 안에서만 필요한 상태 |

새로고침에서는 zustand 메모리가 먼저 비고 Refresh cookie만 남는다. 초기에는 ProtectedRoute가 인증 복원보다 먼저 실행돼 로그인
화면으로 튕기거나, React StrictMode의 effect 이중 실행과 interceptor refresh가 겹치는 race가 있었다.

복원 Promise를 재사용하고, effect 중복 실행을 막고, isAuthChecked가 true가 되기 전에는 보호 화면과 채팅 query를 시작하지 않는
세 경계를 함께 적용했다. 여기서 중요한 것은 로그인 여부와 **로그인 확인이 끝났는가**를 다른 상태로 둔 점이었다.

채팅 패널은 첫 질문과 이어하기를 구분하고, lastActiveAt 기준 남은 시간을 표시한다. 만료, 새 채팅, AI 응답 대기, 출처와 confidence를
같은 화면에서 처리하며, 사용자가 질문 중 페이지를 이동해 요청 상태를 잃지 않도록 API client와 mutation 수명을 조정했다.

## CrewAI를 PydanticAI로 다시 구성했다

현업 피드백에서 공시 요약의 품질과 근거 활용이 기대에 미치지 못한다는 점이 드러났다. 기존 CrewAI 구현은 역할과 Task를
정의했지만, 현재 프로젝트의 흐름은 에이전트들이 자율적으로 협상하는 구조보다 **라우팅 → 검색 → 작성 → 검증**이라는 비교적
고정된 파이프라인에 가까웠다.

CrewAI 자체가 나쁘다기보다 이 프로젝트에서 프레임워크의 역할극 추상화를 충분히 활용하지 못하고 있었다. 반면 이미 단계 사이의
데이터를 Pydantic 모델로 전달하고 있었으므로, 구조화 출력과 검증을 중심에 둔 PydanticAI가 더 직접적인 선택이었다.

| 변경 | 의도 |
|---|---|
| Pydantic output type | LLM 결과를 문자열 추측이 아니라 검증된 객체로 전달 |
| 모듈 단위 agent 재사용 | 요청마다 역할 객체를 다시 조립하지 않음 |
| 일반 Python 흐름 제어 | 고정된 파이프라인에 상태 그래프를 과도하게 도입하지 않음 |
| 공통 persona | 에이전트마다 달라지던 문체와 답변 규칙을 한곳에서 관리 |
| 역할별 모델 | 라우팅, 작성, 검증의 비용과 품질 요구를 분리 |

프레임워크 교체만으로 답변 품질이 자동으로 좋아진 것은 아니다. 실제 품질 변화는 공시 표 파싱, 청크 문맥, 검색 후보 결합,
사업연도 필터와 평가 질문을 함께 손본 결과였다. PydanticAI는 그 흐름의 타입과 실패 경계를 단순하게 만드는 기반이었다.

## AI 한 턴을 다섯 역할과 세 검색 트랙으로 나눴다

PydanticAI 서비스는 프레임워크가 전체 workflow를 자율적으로 결정하게 두지 않았다. 단계의 순서는 Python application code가
소유하고, LLM이 필요한 지점만 typed agent로 분리했다.

| 역할 | 입력과 출력 | 책임 |
|---|---|---|
| router | 질문·회사·history → RouterResult | intent, 검색어, 기간, 재무·거시 사용 여부와 scope 판단 |
| writer | 질문·근거 → QAResult | 근거 안에서 답변 작성 |
| summary writer | 질문·요약 근거 → SummaryResult | 기업·사업 개요를 일관된 문체로 정리 |
| verifier | 질문·답변·근거 → VerificationResult | 근거 충실도와 답변 가능 여부 검사 |
| section summary | 공시 섹션 묶음 → 요약 chunk | 인제스트 시점에 재사용할 요약 생성 |

각 agent의 output type은 Pydantic model이다. 필드 누락이나 잘못된 형태는 ValidationError로 확인하고 프레임워크의 structured output
재시도 범위 안에서 보정한다. 다만 schema가 맞는다고 내용이 사실인 것은 아니므로 citation은 agent가 새로 쓰게 하지 않고 코드가
검색한 실제 근거를 최종 응답에 고정했다.

런타임 검색은 질문 성격에 따라 세 근거를 병렬로 모았다.

1. corpus track은 공시 원문 청크를 vector와 BM25로 찾는다.
2. financial track은 DART 정형 재무 계정을 정확 수치 근거로 가져온다.
3. macro track은 필요한 질문에서 ECOS 거시 지표를 결합한다.

요약 질문은 별도의 summary collection을 먼저 사용한다. 인제스트 단계에서 사업 내용, 위험과 경영진단처럼 분석 가치가 높은
섹션을 묶어 1,188개 요약을 만들었고, 준비되지 않은 기업만 원문 corpus 검색과 실시간 요약으로 fallback한다. 정확 수치 질문과
서술 요약을 같은 검색 결과에 맡기지 않고 역할을 분리하려는 선택이었다.

## 공시 검색은 의미와 정확한 표현을 함께 봤다

공시 질문에는 사업 설명처럼 의미 검색이 중요한 문장도 있고, 계정명·회사명·정확한 숫자처럼 문자 일치가 중요한 표현도 있다.
벡터 검색만으로 두 요구를 모두 충족하기 어려워 Chroma의 임베딩 검색과 전체 청크의 BM25 결과를 합치고 RRF로 순위를 결합했다.

고립된 청크에는 회사, 보고서, 섹션과 사업연도 문맥을 덧붙였다. 답변에는 원문 인용을 유지하고, 정형 재무 수치는 일반 corpus
인용보다 먼저 배치해 제한된 인용 개수 안에서 핵심 근거가 잘리지 않게 했다.

원문 corpus는 67,023개 청크까지 구성했다. 다만 청크 수 자체는 품질 성과가 아니다. 데이터가 많아져도 파싱이 잘못되거나 질문과
맞지 않는 메타데이터를 사용하면 검색 결과는 나빠질 수 있다.

### 표와 고아 청크를 그대로 임베딩하지 않았다

DART 문서는 표가 많다. 표를 단순 plaintext로 펴면 행과 열의 관계가 무너져 계정명과 숫자가 다른 문맥으로 검색될 수 있다.
인제스트에서는 표를 구조가 남는 Markdown 형태로 바꾸고 section path를 추적했다.

또한 매출 3% 증가처럼 청크만 떼어 놓으면 회사·보고서·기간을 알 수 없는 문장 앞에 결정적인 context line을 붙였다. 이 문맥은
청크마다 LLM을 호출해 만들지 않고 회사, 보고서명, 사업연도와 section metadata로 생성해 인제스트 비용을 통제했다.

검색에서는 vector 후보와 전체 BM25 후보의 합집합을 만든 뒤 RRF로 결합했다. 초기 가중치가 vector 쪽으로 기울면서 BM25 1위가
top 5 밖으로 밀리는 사례가 있어 동등 가중에 가깝게 조정했다. 이름만 hybrid인 것이 아니라 한 검색 방식에서 빠진 후보가 다른
방식으로 실제 생존하는지를 평가 질문으로 확인했다.

## 접수일과 사업연도는 같은 시간이 아니었다

보고서의 트러블슈팅에서 가장 도메인적인 사례는 기간 질문이었다. 사용자가 2024년 사업보고서를 요청하면 일반적으로 FY2024
실적을 기대한다. 하지만 해당 보고서는 다음 해에 접수될 수 있어 DART 접수일의 연도와 사업연도가 다르다.

초기에는 기간을 문자열 접수일에 범위 필터로 적용했고, Chroma가 숫자 범위 연산을 거부한 예외가 병렬 처리에서 빈 결과로
바뀌기도 했다. 예외를 고친 뒤에도 접수연도를 기준으로 찾으면 사용자가 기대한 사업연도와 한 해가 어긋날 수 있었다.

이를 다음과 같이 보완했다.

1. 보고서명에서 사업연도를 정수 메타데이터로 분리했다.
2. corpus, 재무와 요약 트랙이 같은 사업연도 필터를 사용하게 했다.
3. 병렬 검색의 부분 실패는 빈 배열로만 바꾸지 않고 원인을 로그로 남겼다.
4. 기간 질문을 검색·행동·회귀 평가에 추가했다.

당시에는 이 문제를 하나의 도메인 시간축 설계로 충분히 설명하지 못했다. 지금 돌아보면 단순 타입 오류보다 중요한 교훈은
**사용자 언어의 연도와 외부 시스템의 접수일을 같은 개념으로 취급하지 않는 것**이었다.

## 통합 과정에서 해결한 대표 문제

두 종합 보고서에는 완성 기능뿐 아니라 통합 중 발견한 문제가 기록돼 있다. 그중 시스템 경계를 설명하는 사례를 추렸다.

| 증상 | 원인 | 조치와 교훈 |
|---|---|---|
| 새로고침하면 로그인 화면으로 이동 | 인증 복원 전에 ProtectedRoute가 초기 false를 확정값으로 사용 | isAuthChecked 완료 신호와 query gate 추가 |
| AI 실패가 자료 없음처럼 보임 | gather의 Exception을 빈 검색 결과로 치환 | 사용자 graceful fallback과 원인 log를 분리 |
| 현대차 수치 근거가 citation에서 빠짐 | 정형 재무 근거가 corpus 뒤에 붙어 상위 5개에서 잘림 | 권위 있는 1급 근거를 먼저 배치 |
| 다른 회사 또는 null이 답변에 표시 | LLM의 detected company 문자열과 현재 방 회사를 신뢰 | 식별자는 코드에서 정규화하고 방 회사명을 권위값으로 주입 |
| 제56기 질문이 다른 사업연도로 매핑 | 기수 환산 산수를 LLM에 맡김 | DART의 기수 기준점을 가져와 코드로 결정적 계산 |
| 사업 요약이 엉뚱한 section으로 시작 | summary 검색이 의미 유사도에만 의존 | summary collection에도 BM25와 RRF 적용 |
| 만료된 방을 다른 탭이 계속 사용 | 화면별 cache 시점이 다름 | focus refetch와 410 복구, 서버 수명주기를 기준으로 통일 |

이 과정에서 반복된 패턴은 명확했다. 회사, 기간, 기수처럼 정답이 하나인 값은 LLM이 추측하지 않게 하고 코드와 권위 데이터가
결정해야 했다. 반대로 문장 요약처럼 정답이 하나가 아닌 영역에는 LLM을 사용하되 실제 검색 근거와 평가 질문으로 범위를 제한했다.

## 시연과 평가를 연결하려 했다

정확 수치, 요약, 거시 결합, 타사 질문 차단, 멀티턴, 기간·기수 질문과 timeout을 시연 시나리오로 구성했다. AI 서비스에는
검색, 행동과 회귀의 세 종류 평가를 두고 일부 시연 질문을 자동 평가와 연결했다.

보고서에는 제한된 must 검색 케이스에서 hit@5 100%, MRR 0.933과 회귀 must 통과 결과가 기록되어 있다. 이 값은 **작성한
평가셋 안에서 기대 근거가 검색됐다는 증거**이지, 임의의 사용자 질문에 대한 전체 챗봇 정확도가 100%라는 뜻은 아니다.

실제 발표 준비 과정에서는 해피패스 질문은 비교적 잘 동작했지만 다음 영역이 충분하지 않았다.

- 여러 의도가 섞인 복합 질문
- 모호한 후속 질문과 긴 멀티턴
- 평가셋에 없는 표현과 기업
- 검색 근거는 맞지만 답변 문장이 기대와 다른 경우
- 외부 API와 모델의 지연·부분 실패
- 답변의 사실성·관련성·인용 충실도를 사람이 평가하는 기준

결과적으로 검색 지표와 시연 성공을 제품 전체 정확도로 확대해 해석할 수 없었다. 최종 피드백에서 정확도와 챗봇 품질이 아쉽다는
평가를 받은 이유도 이 간극과 연결된다.

### 실제 시연에서 보여준 장면

| 장면 | 보여주려던 것 | 당시 검증 수준 |
|---|---|---|
| 영업이익 뒤 매출 후속 질문 | 채팅방 history와 지시어 멀티턴 | 로컬 화면 시연 + 일부 행동 평가 |
| 기업 사업 내용 요약 | 사전요약 collection과 provenance | 골든 질문 + 로컬 시연 |
| 정확 재무 수치 | 정형 재무와 corpus 근거의 역할 분리 | 제한된 must 회귀 케이스 |
| 2024년·제56기 질문 | 사업연도와 기수의 결정적 변환 | 기간·기수 회귀 가드 |
| 다른 기업·투자 조언 질문 | 방 scope와 도메인 이탈 차단 | 행동 평가 |
| 30분 만료와 새 채팅 | Spring 채팅방 수명주기와 410 복구 | 로컬 수동 시연 |
| AI timeout | upstream error mapping과 사용자 안내 | FastAPI 종료·지연 수동 시연 |

시연 장면을 자동 평가와 연결하려 한 방향은 유효했다. 다만 Spring 통합 테스트와 실제 사용자가 만드는 질문 분포가 부족해,
시연 가능한 장면과 서비스 품질 사이에는 여전히 큰 간격이 있었다.

## 생성형 AI로 빠르게 만들었지만 검증 속도는 따라가지 못했다

이 프로젝트는 내가 생성형 AI를 개발에 처음 본격적으로 사용한 경험이었다. Spring 요구사항을 상세한 Markdown으로 작성하고
Claude와 구현을 반복하면서 짧은 기간에 인증, 채팅방, API 연동과 문서를 넓게 구성할 수 있었다.

반면 당시에는 spec, plan과 reusable skill을 체계적으로 사용하는 방법을 몰랐다. 생성되는 코드의 양이 빠르게 늘면서 다음 문제가
생겼다.

- 구현 전에 핵심 사용자 질문과 실패 조건을 충분히 고정하지 못했다.
- 상세 문서는 많았지만 결정 기준과 완료 조건이 여러 문서에 흩어졌다.
- 각자 개발한 코드를 마지막에 합쳐 계약 오류를 늦게 발견했다.
- PR과 동료 코드 리뷰보다 개인별 구현과 통합에 의존했다.
- Spring 핵심 로직의 자동 테스트보다 수동 시연 비중이 높았다.
- AI가 만든 구조를 설명하고 검증하는 시간이 구현 속도를 따라가지 못했다.

따라서 이 프로젝트를 AI로 혼자 완성한 성공 사례라고 표현하지 않는다. AI는 구현 속도를 높였지만, 무엇을 만들고 어떤 질문으로
실패를 확인할지는 팀과 개발자가 책임져야 한다는 점을 배운 사례에 가깝다.

## 다시 한다면 기획과 평가를 먼저 고정한다

Superpowers 같은 spec·plan 중심 작업 방식을 당시 알았다면 다음 순서로 진행했을 것이다.

1. RFP를 사용자 여정, 핵심 질문과 금지해야 할 오답으로 분해한다.
2. React–Spring–FastAPI 계약과 실패 응답을 예시 JSON으로 먼저 합의한다.
3. 팀원별 소유 영역과 통합 시점을 정하고 작은 PR 단위로 리뷰한다.
4. 구현 전에 해피패스·모호한 질문·복합 질문·기간 질문의 평가셋을 만든다.
5. 검색 hit와 최종 답변 품질을 분리하고 사람 평가 기준을 정의한다.
6. AI에게 구현을 맡기더라도 변경마다 테스트, diff 리뷰와 설명 가능한 상태를 완료 조건으로 둔다.
7. 마지막 이틀에 통합하는 대신 매일 세 서비스를 연결한 얇은 수직 흐름을 유지한다.

특히 평가셋은 완성 뒤 점수를 내는 도구가 아니라 제품 요구사항이어야 했다. 어떤 질문을 잘 답해야 하는지 먼저 정했다면,
프레임워크 교체가 필요한지와 검색 개선의 우선순위도 더 일찍 판단할 수 있었을 것이다.

## 남은 과제

- Spring 인증·채팅방 수명주기의 자동 통합 테스트
- 복합·모호한 질문을 포함한 평가셋 확대
- 답변 사실성, 관련성, 인용 충실도의 사람 평가 기준
- 모델·외부 API 지연과 부분 실패 시 사용자 경험
- 실제 부하와 동시 사용자 환경의 성능 측정
- Docker 또는 배포 환경에서의 재현 가능한 실행
- 팀 단위 PR, 리뷰와 API contract test

12일 동안 완성한 로컬 MVP는 모든 질문에 정확히 답하는 서비스는 아니었다. 하지만 프론트, 업무 백엔드와 AI 서비스를 분리하고
한 흐름으로 연결했으며, 잘 보이는 시연 뒤에 어떤 평가 공백이 남는지 직접 확인했다. 가장 큰 결과는 특정 프레임워크의 채택보다
**AI 서비스도 계약, 도메인 모델, 실패 관측과 비해피패스 평가가 먼저다**라는 기준을 얻은 것이다.
