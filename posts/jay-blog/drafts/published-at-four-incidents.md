블로그 글 목록을 열었더니 방금 올린 글이 두 번째에 있었다. 첫 번째는 그 전에 올린 글이었다. 발행 순서와 목록 순서가 어긋난 것이다.

같은 종류의 사고가 처음이 아니었다. 스크립트 주석을 읽어 보니 이미 두 번의 기록이 남아 있었다. 「2026-08-31 에 9편이 그랬다」, 「2026-09-03 에 세 편이 그랬다」. 증상은 매번 달랐다. 어떤 날은 발행일이 통째로 「배포가 돈 시각」으로 찍혔고, 어떤 날은 로컬 화면에서 본 날짜와 운영이 달랐고, 이번에는 순서가 뒤집혔다.

세 번이나 고쳤는데 왜 또 나는가. 그 질문에서 시작해서 하루를 썼고, 결국 네 번째 사고까지 겪은 뒤에야 공통점을 찾았다. **매번 고친 것은 증상이었고, 원인은 「발행일의 정본이 어디인가」에 답이 넷이었다는 것이다.**

## 발행일을 정하는 자리가 넷이었다

발행 스크립트의 날짜 선택 코드는 한 줄이다.

```js
const publishedAt = d.publishedAt ?? local?.publishedAt ?? null;
```

읽으면 이렇다. 초안 머리말에 적힌 값이 있으면 그것을 쓰고, 없으면 로컬 데이터베이스의 값을 쓰고, 그것도 없으면 아무것도 안 보낸다. 안 보내면 서버가 기존 값을 쓰고, 기존 값도 없으면 「지금」을 매긴다.

폴백이 넷인데 **각 단계가 서로 다른 뜻을 갖는다.**

| 단계 | 그 값의 의미 |
|---|---|
| 초안 머리말 | 사람이 「이 날짜로 나가면 좋겠다」고 적은 것 |
| 로컬 DB | 로컬에서 미리보기로 올렸을 때 찍힌 시각 |
| 운영 기존 값 | 이 글이 처음 발행됐던 시각 |
| 서버의 「지금」 | 스크립트가 돈 시각 |

「집필일」과 「처음 발행한 시각」과 「스크립트가 돈 시각」은 다른 것이다. 그런데 코드는 셋 중 아무거나 먼저 잡히는 것을 쓴다. **어느 것이 답인지 코드가 모르니, 사람도 모른다.**

2026-08-31 의 사고가 그 마지막 단계였다. 초안 아홉 편에 발행일을 안 적었고, 로컬 DB 도 안 읽히는 환경(클러스터 안의 러너)에서 배포가 돌았다. 그래서 아홉 편이 전부 「배포가 돈 시각」으로 찍혔다. 실제로 글을 쓴 날과는 무관한 값이다.

## 사람이 적는 값의 정밀도가 날짜뿐이었다

첫 사고를 겪은 뒤 규칙이 하나 생겼다. **「발행일은 저장소가 정본이다」** — 초안 머리말에 적어 두면 그 값이 클러스터까지 따라가니, 적어 두라는 것이다.

그래서 이번에는 적혀 있었다. 두 편 모두.

```
publishedAt: 2026-09-04T00:00:00Z
```

**둘 다 자정이다.** 사람이 날짜를 적을 때 시각까지 신경 쓸 이유가 없으니 당연한 결과다. 그리고 목록은 발행일로 정렬한다. 값이 정확히 같으면 정렬이 순서를 정할 수 없다.

여기까지가 데이터 쪽 문제다. 그런데 그 아래에 코드 문제가 하나 더 있었다.

## 목록 질의에만 2차 정렬 기준이 없었다

값이 같을 때 무엇으로 가르는가. 저장소 인터페이스를 열어 보니 답이 갈려 있었다.

```java
// 목록
List<BlogPost> findByStatusOrderByPublishedAtDesc(String status);

// 이전 글·다음 글
order by p.publishedAt desc, p.id desc
```

**이웃 글을 찾는 질의는 이미 `id` 를 2차 기준으로 쓰고 있었다.** 동점일 때 무엇이 먼저인지 정해 둔 것이다. 그런데 목록 질의 넷만 기준이 하나뿐이었다.

기준이 하나뿐이면 동점의 순서를 데이터베이스가 정한다. 표준은 「정해지지 않음」이고, 실제로는 저장 순서나 실행 계획에 따라 달라진다. 그래서 나중에 올린 글이 아래로 갔다.

증상은 순서였지만 **더 위험한 것은 페이징이었다.** 페이지를 나눌 때 정렬이 흔들리면 같은 글이 두 페이지에 나오거나, 어느 페이지에도 안 나올 수 있다. 눈에 안 띄었을 뿐 이미 그 상태였다.

그리고 기준이 갈려 있었다는 것 자체가 또 다른 버그였다. **목록의 다음 글과 글 하단의 「다음 글」이 서로 다를 수 있었다.** 같은 사이트 안에서 두 화면이 다른 순서를 말하는 상태다.

고친 것은 한 줄이다. 목록도 이웃 글과 같은 기준을 쓰게 했다.

```java
findByStatusOrderByPublishedAtDescIdDesc(String status);
```

되돌리면 실패하는 테스트를 남겼다. 확인해 보니 기존 페이징 테스트는 이 상황을 주석으로 **피하고** 있었다.

```java
// 발행일을 하루씩 벌려 순서를 확정한다. 같은 시각이면 정렬이 id 로 흔들려 경계 검증이 흐려진다.
```

테스트를 쓴 사람은 이미 이 문제를 알고 있었다. 다만 그것을 **고쳐야 할 버그가 아니라 피해야 할 조건**으로 봤다. 그래서 테스트는 통과했고 버그는 남았다.

## 초안을 커밋했더니 배포가 운영을 덮었다

여기까지 고치고 나서 진짜 사고가 났다.

발행 스크립트는 이미지를 다룰 때 순서가 있다. 그림을 오브젝트 스토리지에 올리고, **본문의 그림 주소를 그 저장소 주소로 바꿔 초안 파일에 다시 쓰고**, 원본 파일을 `web/public` 밖으로 옮긴다. `web/public` 은 컨테이너 이미지에 구워지는 폴더라, 그림이 거기 남으면 글 한 편에 배포 한 판이 필요하기 때문이다.

나는 그 발행보다 **먼저** 초안을 커밋했다. 다른 이유였다 — 본문의 내부 링크 하나가 잘못돼 있어서 그것만 고쳐 커밋했다. 그때 커밋된 초안에는 **옛 그림 주소가 그대로** 들어 있었다.

그리고 배포가 돌았다.

```yaml
- name: Publish blog drafts
  if: vars.BLOG_PUBLISH_AUTO == 'true'
```

**배포가 저장소의 초안을 운영에 자동 발행한다.** 커밋된 옛 초안이 운영 본문을 덮었고, 그 안의 그림 주소는 이미 파일이 없는 경로였다. 글 하나의 이미지가 전부 깨졌다.

같은 날 발행한 다른 세 편은 멀쩡했다. **그 셋은 커밋을 안 한 미추적 파일이었기 때문이다.** 저장소에 없으니 클러스터로 갈 것도 없었다.

정리하면 이렇다. **초안을 커밋한 것이 사고의 방아쇠였다.** 커밋하지 않은 초안이 안전하고 커밋한 초안이 덮이는 구조는, 상식과 반대 방향이라 더 위험하다.

여기서 문서 하나가 틀렸다는 것도 드러났다. 저장소 지침에는 이렇게 적혀 있었다.

> 블로그 글은 배포와 무관하다 — 사람이 발행 스크립트를 돌린다.

`BLOG_PUBLISH_AUTO` 가 켜지기 전에는 맞는 말이었다. **자동화를 켜면서 그 문장이 참이 아니게 됐는데, 문장은 그대로 남았다.**

## 동기화 도구가 정본을 반대로 골랐다

깨진 것을 고치려고 동기화 명령을 쳤다. 로컬과 운영을 대조해 편마다 방향을 정해 주는 도구다.

```
↓ 내린다  ornith-gomoku-qwen-code-day2  — 운영이 더 최신이다
```

**반대로 갔다.** 로컬이 맞고 운영이 깨져 있는데, 도구는 운영을 정본으로 골라 깨진 본문을 내려받았다. 그리고 곁들여 내가 고쳐 둔 발행일까지 운영 값(자정)으로 되돌렸다.

판정 규칙은 이렇다.

```js
return served > drafted
  ? { dir: 'pull', reason: '운영이 더 최신이다' }
  : { dir: 'push', reason: '초안이 더 최신이다' };
```

수정 시각이 더 최근인 쪽을 정본으로 본다. 사람이 관리 화면에서 고친 것을 초안이 덮지 않게 하려고 만든 규칙이고, 그 목적에서는 옳다.

**그런데 자동 배포가 그 시각을 갱신한다.** 배포가 발행하면 운영의 수정 시각이 「방금」이 된다. 그러면 로컬에서 무엇을 고쳐 두었든 항상 운영이 더 최신이다. **사람이 고친 내용이 영영 못 올라가는 상태**가 된다.

이 규칙이 만들어질 때의 전제는 「운영이 바뀌었다면 사람이 화면에서 고친 것이다」였다. 자동 발행을 켜는 순간 그 전제가 깨졌는데, 규칙은 그대로 있었다.

우회는 간단하다. 방향 판정을 하지 않고 무조건 올리는 명령이 따로 있다. 「운영이 틀렸고 로컬이 맞다」가 확실할 때는 그쪽을 쓴다.

## 고친 것 — 사람이 시각을 안 적어도 되게

증상을 네 번 고쳤으니 이번에는 원인을 고쳤다. 규칙은 하나다. **발행일의 정밀도를 사람에게 요구하지 않는다.**

```js
function resolvePublishedAt(fromDraft, fromLocal) {
  const base = fromDraft ?? fromLocal ?? null;
  const clock = new Date().toISOString().slice(11);
  if (!base) return `${new Date().toISOString().slice(0, 10)}T${clock}`;
  const day = base.slice(0, 10);
  const hasClock = /T\d{2}:\d{2}/.test(base) && !/T00:00:00(\.0+)?Z?$/.test(base);
  return hasClock ? base : `${day}T${clock}`;
}
```

머리말이 비었거나 자정이면 **그 날짜에 지금 시각을 붙인다.** 날짜는 사람이 적은 대로 지키고 시·분·초만 채운다. 시각까지 직접 적었으면 그 뜻으로 보고 손대지 않는다.

그리고 **확정한 값을 초안 머리말에 되새긴다.** 저장소가 정본이라는 규칙을 코드가 지키는 자리다. 여기 안 남기면 다음 발행에서 다시 자정으로 돌아가 같은 문제가 난다.

이제 같은 날 두 편을 올려도 시각이 다르므로 순서가 정확하다. 그리고 값이 어쩌다 또 겹치더라도 목록 질의가 `id` 로 가르니 나중에 올린 글이 위에 온다. **한 겹으로 막지 않고 두 겹으로 막았다.**

## 곁들여 고친 것 — 시리즈 연결

이어서 쓴 글을 잇는 기능이 있는데, 발행 스크립트가 그 필드를 안 보내고 있었다. 관리 화면에서 손으로 지정해야 했다.

못 보낸 이유가 있다. **연결은 `id` 로 거는데 `id` 는 발행 순간에 정해진다.** 아직 발행 안 된 글의 번호를 초안에 미리 적을 방법이 없다.

그래서 `slug` 로 적게 했다.

```
prevSlug: ornith-gomoku-qwen-code-experiment
```

발행할 때 대상 서버의 글 목록에서 번호를 찾아 보낸다. 서버가 한쪽만 받아도 상대편의 반대 방향까지 함께 맞추므로, **이어 쓴 글에 한 줄만 적으면 양쪽이 연결된다.** 아직 발행 안 된 글을 가리키면 조용히 건너뛰고 그 사실을 알린다 — 그 글을 올린 뒤 이 글을 다시 올리면 그때 걸린다.

## 관통하는 것

네 번의 사고에 공통점이 있다. 전부 **「정본이 어디인가」를 잘못 알아서** 났다.

| 사고 | 정본이라고 믿은 것 | 실제 정본 |
|---|---|---|
| 발행일이 배포 시각으로 찍힘 | 로컬 DB | 저장소 머리말 |
| 로컬과 운영 날짜가 어긋남 | 초안 | 로컬 DB |
| 목록 순서가 뒤집힘 | 발행일 하나 | 발행일 + id |
| 배포가 운영 본문을 덮음 | 로컬 파일 | **커밋된 파일** |
| 동기화가 반대로 감 | 「나중에 고친 쪽」 | 사람이 고친 쪽 |

특히 마지막 둘이 같은 모양이다. **자동화를 하나 켜면서 정본의 위치가 옮겨 갔는데, 그것을 쓰는 도구와 문서는 옛 위치를 가리키고 있었다.** 배포 자동 발행을 켜는 순간 초안의 정본은 「내 파일」에서 「커밋된 파일」로 옮겨 갔고, 운영 수정 시각의 뜻은 「사람이 고친 시각」에서 「기계도 고치는 시각」으로 바뀌었다.

그래서 자동화를 켤 때 붙는 질문이 하나 늘었다. **「이 자동화가 무엇의 정본을 바꾸는가, 그리고 그것을 전제로 쓰는 다른 도구가 있는가.」**

## 방향 판정도 고쳤다 — 파일을 언제 만졌는지 본다

글을 여기까지 쓰고 나서 「남은 한계」로 적어 두려던 것을 다시 봤다. 동기화 도구가 반대로 가는 문제인데, 적어 놓고 보니 **지금 고칠 수 있는 것을 한계라고 부르고 있었다.**

문제는 판정에 쓸 값이 하나뿐이라는 것이었다. 초안의 수정 시각은 머리말의 `updatedAt` 인데, 그 값은 **마지막으로 발행된 시각**이다. 그 뒤에 내가 파일을 고쳤다는 사실을 말해 주지 못한다.

그런데 그 사실을 아는 값이 이미 있다. **파일 시스템의 수정 시각이다.**

```js
const drafted = Math.max(
  draft.updatedAt ? Date.parse(draft.updatedAt) : 0,
  draft.touchedAt ? Date.parse(draft.touchedAt) : 0,
);
```

둘 중 나중 것을 초안의 시각으로 본다. 배포가 운영을 갱신했어도 **그 뒤에 파일을 손댔으면 올리는 쪽**이 되고, 파일을 안 건드렸으면 여전히 운영을 믿는다. 「누가 고쳤는가」를 기록하는 칸을 새로 만들지 않고, **이미 있는 값으로 같은 질문에 답한 것**이다.

이 도구에는 네트워크를 안 타는 자기검사가 붙어 있어서, 규칙 둘을 거기에 고정했다. 「운영이 갱신된 뒤에 초안 파일을 고쳤으면 올린다」와 「파일을 그 뒤에 안 건드렸으면 여전히 운영을 믿는다」다.

## 마크다운이 조용히 새는 것도 검사로 잡았다

이 글을 로컬에 올려 화면으로 보다가 별표 두 개가 글자로 그대로 찍힌 것을 발견했다.

```
방향을 시각이 아니라 **「누가 고쳤는가」**로 정하게 하려면
```

렌더러 버그가 아니다. CommonMark 에서는 닫는 별표 **앞이 구두점이고 뒤에 글자가 바로 붙으면** 굵게가 닫히지 않는다. 한국어로 쓰면 「」 를 자주 쓰니 자주 걸린다. 괄호를 별표 바깥으로 빼면 된다 — 「**굵게**」 로.

**이 함정은 이미 저장소 가이드에 적혀 있었다.** 적어 두고도 또 걸린 것이다. 문서로 막는 데 실패했으면 검사로 막아야 한다.

그래서 초안을 **실제 렌더러로 돌려 보고** 마크다운 기호가 새어 나오는지 확인하는 검사를 붙였다. 규칙을 흉내 내면 오탐이 나므로, 화면이 쓰는 `marked` 를 그대로 부른다. 문단 단위로 돌리고 코드펜스는 건너뛴다 — 코드 안의 별표는 글자로 나오는 게 맞기 때문이다.

돌려 보니 이미 발행된 글에서도 같은 자리가 나왔다. 예를 들어 이런 것이다.

```
**`Qwen3.8-27B-4bit + DFlash2`**다.
```

닫는 별표 앞이 백틱이라 같은 규칙에 걸린다. **화면에서만 보이고 초안에서는 안 보이는 종류**라, 검사가 없으면 계속 쌓인다.

## 관통하는 것

네 번의 사고에 공통점이 있다. 전부 **「정본이 어디인가」를 잘못 알아서** 났다.

| 사고 | 정본이라고 믿은 것 | 실제 정본 |
|---|---|---|
| 발행일이 배포 시각으로 찍힘 | 로컬 DB | 저장소 머리말 |
| 로컬과 운영 날짜가 어긋남 | 초안 | 로컬 DB |
| 목록 순서가 뒤집힘 | 발행일 하나 | 발행일 + id |
| 배포가 운영 본문을 덮음 | 로컬 파일 | **커밋된 파일** |
| 동기화가 반대로 감 | 「나중에 고친 쪽」 | 사람이 고친 쪽 |

특히 마지막 둘이 같은 모양이다. **자동화를 하나 켜면서 정본의 위치가 옮겨 갔는데, 그것을 쓰는 도구와 문서는 옛 위치를 가리키고 있었다.** 배포 자동 발행을 켜는 순간 초안의 정본은 「내 파일」에서 「커밋된 파일」로 옮겨 갔고, 운영 수정 시각의 뜻은 「사람이 고친 시각」에서 「기계도 고치는 시각」으로 바뀌었다.

그래서 자동화를 켤 때 붙는 질문이 하나 늘었다. **「이 자동화가 무엇의 정본을 바꾸는가, 그리고 그것을 전제로 쓰는 다른 도구가 있는가.」**

저장소 지침에서 그 질문에 걸리는 문장 셋을 찾아 고쳤다. 「블로그 글은 배포와 무관하다」가 두 곳, 「사람이 발행 스크립트를 돌린다」가 한 곳이었다. 대신 **커밋된 초안이 곧 운영 본문**이라는 것과, 발행 뒤 바뀐 초안을 안 커밋하면 다음 배포가 되돌린다는 것을 적어 넣었다.

## 남은 것

**초안을 커밋하는 순간 그것이 운영 본문이 된다는 구조 자체는 그대로다.** 이번에는 문서로 적어 두는 데서 그쳤다. 발행 뒤에 초안이 바뀌었는데 커밋 안 된 상태를 **검사로 잡는 것**이 다음 자리인데, 「발행 시점 이후에 파일이 바뀌었는가」를 판정할 기준을 정하지 못했다. 파일 수정 시각은 다른 이유로도 바뀐다.

그리고 마크다운 검사는 아직 배포 파이프라인에 안 넣었다. 이미 발행된 글에서 잡히는 자리가 열 곳 남짓 있어서, 그것을 다 고치기 전에 넣으면 배포가 계속 실패한다. **먼저 고치고 그다음에 관문으로 세우는 순서**가 맞다.
