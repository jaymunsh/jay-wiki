지난 글에서는 공개 벤치마크 점수만으로는 내 컴퓨터와 작업에 맞는 로컬 LLM을 고르기 어렵다는 문제에서 출발해, `LocalLLM`이라는 측정 도구를 만들었다.

도구를 만든 배경과 측정 설계는 [지난 글: 공개 벤치마크만으로 고르기 어려워 만든 나만의 로컬 LLM 실험실](/21/local-llm-fit-tester)에서 먼저 정리했다.

이번에는 그 도구를 실제로 돌린 결과를 정리한다. 모델 이름만 비교한 것이 아니라 **M1 Max 64GB에서 특정 양자화 빌드와 서버 설정을 조합해 실제 작업을 수행한 결과**다.

먼저 전체 결과는 아래 리포트에서 확인할 수 있다. 리포트 안에는 모델이 생성한 단일 HTML 결과물도 연결해 두었다.

**[LocalLLM 실험 결과 리포트 열어보기](/assets/projects/local-llm-fit-tester-report/report.html)**

원본 프로젝트 전체를 올리지는 않았다. `runs.jsonl`에는 개인 fixture와 실행 원문이 포함될 수 있어 제외했고, 정적 리포트와 리포트에서 확인할 수 있는 생성 HTML 결과만 공개용 파일로 묶었다.

다만 이 테스트를 절대적인 모델 평가나 범용 리더보드로 보기는 어렵다. 과제와 실행 환경이 M1 Max 64GB, 그리고 현재 프로젝트에서 실제로 사용할 법한 작업에 맞춰져 있기 때문이다. 이번 측정은 모든 모델의 우열을 확정하려는 목적보다, **현재 프로젝트를 가볍게 점검하고 어떤 조합을 먼저 써 볼지 판단하기 위한 실험**에 가깝다.

## 이번 실험의 범위

지난 글에서 설명한 측정 도구는 모델 서버를 직접 띄우지 않고 OpenAI 호환 endpoint에 연결한다. 이번 결과는 Apple Silicon M1 Max 64GB에서 oMLX와 llama.cpp 계열 환경을 사용해 수집했다.

리포트의 현재 스냅샷에는 **26개 조합과 254회 실행**이 기록되어 있다. 짧은 출력 속도만 재지 않고 다음 작업을 함께 넣었다.

| 영역 | 확인한 작업 |
| --- | --- |
| 한국어·장문 | 한국어 요약, HTML 노이즈가 섞인 문서 요약 |
| 코드 | Java 버그 찾기와 리팩터링 |
| 형식 준수 | JSON only, 3줄 제한, 번역, 짧은 대화 |
| 에이전트 | 첫 툴콜, 3턴 편집 루프, 툴 결과 충실도, 검색 결과 요약 |
| 생성물 | 단일 파일 테트리스, 모래 물리 샌드박스, 제품 소개 페이지 |
| 긴 컨텍스트 | 16K·96K 입력에서 prefill, warm/cold TTFT, 메모리 |

자동 검사는 형식·누락·실행 가능성 같은 부분을 확인하고, 사람이 읽어야 하는 품질은 별도로 1~5점으로 채점했다. 따라서 표에 있는 평균 점수 하나만으로 모델을 줄 세우기보다, **실제 파이프라인을 깨는 바닥값이 있는지**를 더 중요하게 봤다.

## 균형을 보면 Qwen3.6, 개인적인 선호는 Ornith였다

이번에 측정한 네 조합의 위치는 다음과 같았다.

| 조합 | 판정 | 관찰된 수치 | 의미 |
| --- | --- | --- | --- |
| Qwen3.6-35B-A3B OptiQ 4bit | AI 종합 판단상 균형 후보 | 생성 78.2 tok/s · 96K warm 2.5초 · peak 28.3GB · 사람 채점 4.27 | 속도·품질·메모리 어느 한 축에서도 크게 무너지지 않았다. |
| Ornith-1.5-35B-A3B MLX 6bit | 개인적으로 더 끌린 후보 | 사람 채점 4.36 · 96K warm 2.0초 · 생성 29.3 tok/s · peak 33.8GB | 품질은 1위지만 긴 답변을 생성할 때 속도와 메모리를 지불해야 한다. |
| Qwen3.8-27B dense nvfp4 | 긴 컨텍스트 부적합 | 96K cold 27.7분 · 생성 5.5 tok/s · peak 31.5GB · 스왑 0 | 메모리 부족이 아니라 dense 가중치를 토큰마다 읽는 비용이 병목이었다. |
| gemma-4-26B-A4B 4bit | 탈락 | 검색 요약 1.0 · JSON only 2.0 · 96K warm 18.7초 | 스텁 검색 결과를 무시하거나 JSON을 코드 펜스로 감싸 파이프라인을 깨뜨렸다. |

이 표에서 Qwen3.6이 모든 항목에서 1등이라는 뜻은 아니다. Ornith는 사람 채점 평균이 더 높았고, 96K warm TTFT도 더 짧았다. 수치와 실행 조건을 AI 관점에서 종합하면 **여러 축의 균형은 Qwen3.6 4bit가 낫다고 판단할 수 있다.** 다만 실제 결과물을 읽고 품질 차이를 체감한 개인적인 선호는 Ornith 쪽에 조금 더 기운다.

Ornith의 29.3 tok/s는 품질을 얻는 대신 길게 답할 때 체감되는 비용이다. 그래도 품질 우선 작업이라면 이 비용을 감수할 만하다고 개인적으로 느꼈다. 여기에 이번 비교는 Qwen3.6 OptiQ 4bit와 Ornith MLX 6bit를 비교한 것이므로, 모델 자체의 절대적인 우열이라고 말할 수 없다. Ornith 4bit를 다시 측정하면 결론이 달라질 가능성도 리포트에 남겨 두었다.

## 평균보다 실패하는 한 칸이 더 중요했다

사람이 채점한 11개 항목의 평균은 Ornith 4.36, Qwen3.6 4.27, Qwen3.8 3.97, Gemma 3.73이었다. 숫자만 보면 모두 어느 정도 쓸 수 있는 것처럼 보인다.

하지만 실제 선택을 가른 것은 평균 차이가 아니라 특정 작업에서의 실패였다.

| 테스트 | Qwen3.6 | Ornith | Qwen3.8 | Gemma | 실제로 갈린 부분 |
| --- | ---: | ---: | ---: | ---: | --- |
| `harness-websearch` | 5.0 | 4.5 | 5.0 | **1.0** | Gemma가 스텁 검색 결과를 읽지 않고 날짜·수치를 만들어 냈다. |
| `html-noise-4k` | 2.5 | 5.0 | **1.7** | 4.0 | Qwen3.8은 본문보다 CSS·폰트·테마를 요약했다. |
| `format-json` | 5.0 | 5.0 | 5.0 | **2.0** | Gemma만 JSON만 출력하라는 지시에 코드 펜스를 붙였다. |
| `ctx-96k` | 4.0 | 5.0 | 4.0 | 4.0 | Ornith만 잘린 문서 사본을 알아차렸다. |

이런 실패는 평균 점수로 상쇄하면 안 된다. 검색 결과를 읽지 않는 모델이나 JSON 계약을 지키지 않는 모델은 한 번의 답변이 조금 더 빠르더라도 에이전트 파이프라인에 넣기 어렵다.

다만 사람 채점도 완전히 객관적인 정답은 아니다. 현재 리포트의 사람 점수 일부는 LLM이 원문을 읽고 근거와 함께 매긴 값이다. 그래서 점수 자체를 확정된 사실처럼 보기보다, 리포트 안의 출력 원문과 함께 다시 확인할 수 있는 검토용 신호로 취급했다. 생성형 HTML 41건은 숫자 점수 대신 결과물을 직접 열어 보도록 했다.

## Qwen3.6과 Ornith는 모델보다 빌드 차이까지 봐야 한다

이번 비교에서 가장 조심해야 하는 부분은 Qwen3.6과 Ornith가 같은 조건의 모델 카드 대결이 아니라는 점이다.

| 빌드 | 짧은 입력 생성 | 96K 생성 | 96K warm | 96K cold | peak |
| --- | ---: | ---: | ---: | ---: | ---: |
| Qwen3.6-35B-A3B OptiQ 4bit | 103.4 tok/s | 79.1 tok/s | 2.5초 | 391.3초 | 28.3GB |
| Ornith-1.5-35B-A3B MLX 6bit | 52.4 tok/s | 29.6 tok/s | 2.0초 | 384.6초 | 33.8GB |

두 모델 모두 총 35B에 토큰당 약 3B가 활성화되는 MoE 계열이라 긴 입력을 읽는 prefill과 warm TTFT는 비슷했다. 크게 벌어진 곳은 생성 속도였다. 6bit 빌드는 4bit보다 토큰당 읽어야 할 데이터가 많아, 긴 출력을 만들수록 차이가 커졌다.

따라서 “Ornith는 느리다”라고 단정하기보다는 **이번에 잰 Ornith 6bit 빌드가 Qwen3.6 4bit보다 느렸다**고 쓰는 것이 정확하다. 같은 Ornith의 4bit 빌드를 다시 재는 것이 다음 실험에서 가장 값어치 있는 확인 항목이다.

## cold와 warm을 나누지 않으면 체감 속도를 잘못 읽는다

긴 프롬프트를 처음 읽는 속도와 같은 prefix를 캐시한 뒤 다음 질문을 받는 속도는 완전히 달랐다.

동일한 nonce를 사용한 약 13.5K 토큰 입력에서 Qwen 계열의 prefill은 cold 약 189.9초에서 warm 약 18.0초로 줄었다. prefix를 바꾸면 다시 약 184.1초가 걸렸다. 이 측정에서는 warm이 cold의 약 9% 수준, 즉 약 10배 이상 빨랐다.

이 결과는 “96K를 지원한다”라는 문구만으로는 부족하다는 뜻이다. 긴 문서를 매번 새로 넣는 작업인지, 같은 시스템 프롬프트와 문서 prefix 위에서 여러 번 대화하는 작업인지에 따라 체감 시간이 크게 달라진다. 그래서 리포트는 TTFT를 cold와 warm으로 분리하고, 생성 속도와 함께 기록한다.

## Apple Silicon에서는 RSS만 보면 안 됐다

메모리 측정에서도 한 번 교훈을 얻었다. 프로세스 RSS는 약 1.86GB로 보였지만, Apple Silicon에서 실제 메모리 압박을 더 잘 보여 주는 `phys_footprint`는 약 21.0GB였고 조합별 peak는 최대 33.8GB였다.

이 차이를 무시하면 “모델이 2GB만 쓴다”처럼 잘못 해석할 수 있다. 이번 리포트에서는 peak memory와 swap 여부를 별도 축으로 남겼다. Qwen3.8 dense는 peak 31.5GB, 스왑 0인 상태에서도 96K cold가 27.7분이었다. 즉 이 경우에는 RAM을 더 꽂으면 해결되는 문제가 아니라, dense 27B 가중치를 토큰마다 읽는 실행 비용이 핵심 병목이었다.

43K 입력에서도 Qwen3.6·Ornith MoE는 prefill이 약 77초 수준이었지만, Qwen3.8 dense는 약 418초가 걸렸다. 짧은 프롬프트에서는 잘 보이지 않던 구조 차이가 긴 컨텍스트에서 “쓸 수 있다”와 “기다리기 어렵다”로 벌어진 셈이다.

## thinking과 토큰 수는 같은 기준으로 세야 한다

Qwen 계열은 thinking을 켰을 때 내부 추론 텍스트가 응답에 섞여 보일 수 있다. 한 번은 약 6,000자의 영어 reasoning이 출력 길이에 포함되는 것을 확인했다. 이 값을 그대로 일반 답변 토큰으로 세면 모델의 생성 속도를 부풀리거나, 반대로 유효한 답변이 느리다고 오해하게 된다.

그래서 리포트에서는 `reasoning_content`와 최종 `content`를 분리하고, token count는 로컬 tokenizer로 확인하거나 근사치임을 표시한다. Qwen3.8의 `reasoning_effort` 비교에서도 기본 설정은 reasoning 664자·content 319자·33.2초, low는 373자·259자·20.3초, high는 664자·319자·34.8초로 기록됐다.

여기서도 “high가 더 똑똑하니 항상 좋다”거나 “low가 빠르니 항상 좋다”라고 결론 내릴 수 없다. 작업별로 reasoning 비용을 감당할 가치가 있는지, 최종 답변 품질이 실제로 좋아졌는지를 함께 봐야 한다.

## 이번 결과를 최종 리더보드로 고정하지 않은 이유

이 실험은 범용 모델 순위를 만드는 프로젝트가 아니다. 모델 빌드, 양자화, 서버, thinking 설정이 바뀌면 다시 측정해야 하고, 작업 목록도 내가 실제로 하는 일에 맞춰져 있다.

현재 결과에서 말할 수 있는 것은 다음 정도다.

1. **수치와 실행 조건을 AI 관점에서 종합하면 Qwen3.6 4bit가 균형이 좋은 후보다.** 속도·품질·메모리 어느 한 축에서 크게 무너지지 않았다.
2. **개인적인 선호는 품질 1위인 Ornith 6bit 쪽에 조금 더 기운다.** 다만 생성 속도와 메모리 비용은 분명하다.
3. **Qwen3.8 dense는 긴 컨텍스트에서 실행 구조의 비용이 크다.** 이 결과를 RAM 용량 문제로만 해석하면 안 된다.
4. **Gemma는 평균 점수보다 계약 위반이 문제였다.** 검색 결과와 JSON 형식을 다루는 에이전트 파이프라인에는 현재 조합을 넣기 어렵다.
5. **Ornith 4bit와 Qwen3.8 MTP는 아직 측정하지 않았다.** 따라서 다음 리포트에서 결론이 바뀔 여지는 남아 있다.

결국 이 프로젝트에서 얻은 가장 큰 결과는 특정 모델의 순위보다, 모델을 고르는 질문이 구체적으로 바뀐 것이다. “누가 벤치마크 1등인가?”에서 “내가 긴 답변을 기다릴 수 있는가, 검색 결과를 실제로 읽는가, JSON 계약을 지키는가, 같은 prefix를 재사용할 때 빨라지는가?”로 질문이 바뀌었다.

당장은 이 결과를 최종 모델 선정표로 고정하기보다, 현재 프로젝트를 점검할 때 필요한 프롬프트를 가볍게 돌려 보는 용도로 활용해볼 예정이다. 다음 실험에서는 같은 모델의 다른 양자화 빌드와 MTP, reasoning 설정을 추가해 이 판단이 얼마나 오래 유지되는지 확인해 보려고 한다.
