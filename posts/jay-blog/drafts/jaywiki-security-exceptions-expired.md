원래 하려던 일은 보안 점검이 아니었다. jay-wiki 의 배포 구조를 손보는 중이었다. 지금은 앱 배포가 위키 글 동기화와 블로그 발행까지 함께 떠안고 있어서, 코드를 올리는 일과 글을 올리는 일이 한 파이프라인에 엉켜 있다. 이것을 "글은 글대로 대조해서 올리고, 배포는 코드만 바꾼다"로 나누는 것이 목표다.

그 첫 단계로 로컬 작업 폴더를 정리했다. 공개 저장소와 비공개 운영 저장소가 옛 폴더 안에 섞여 있어서, 세션이 엉뚱한 쪽에서 시작해 커밋이 보관본에 들어간 일이 있었다. 둘을 저장소 이름대로 다시 배치하고, 경로 문서와 함께 한 PR로 모았다.

코드는 거의 건드리지 않은 PR이었다. 그런데 검사 21개 중 8개가 실패했다. 모두 보안 검사였다. 배포 구조를 고치려면 먼저 이 PR을 develop 에 모아야 했으므로, 개편은 잠시 멈추고 이것부터 보기로 했다.

## 먼저: 이 저장소의 보안 검사는 무엇을 막나

이 글을 읽으려면 검사가 어떻게 동작하는지부터 알아야 한다.

**규칙은 단순하다.** PR이 올라오면 CI가 앱이 쓰는 라이브러리 목록을 공개된 취약점 목록과 대조한다. High 이상의 취약점이 하나라도 있으면 PR을 막는다. 코드를 고치지 않은 PR도 막힌다. 라이브러리는 그대로여도 취약점 목록 쪽이 매일 늘어나기 때문이다.

**고칠 버전이 없을 때는 예외를 쓴다.** 취약점이 있어도 고친 버전이 아직 없으면 올릴 방법이 없다. 그렇다고 그대로 두면 모든 PR이 계속 막힌다. 그래서 "이 취약점은 이 앱에 해당하지 않는다"는 판단을 예외로 적어 두고 통과시킨다. 판단의 근거는 둘 중 하나다. 그 라이브러리가 개발 도구에만 쓰여 운영에 들어가지 않거나, 앱이 취약한 기능을 쓰지 않는 경우다.

**예외에는 유효기간이 있다.** 예외는 문제를 고친 것이 아니라 "지금 기준으로 괜찮다"는 판단이다. 앱 코드가 바뀌면 판단이 틀려질 수 있고, 고친 버전이 나오면 예외 없이 해결할 수 있게 된다. 그래서 판단에 유효기간을 붙여 가끔 다시 보게 한다. 기간이 끝나면 예외가 사라지고, 위의 규칙대로 PR이 다시 막힌다. 다시 확인해서 판단이 그대로면 기간을 늘리고, 상황이 바뀌었으면 버전을 올려 예외를 지운다.

이 글에서 자주 나오는 VEX가 바로 이 예외를 적는 형식이다. **VEX(Vulnerability Exploitability eXchange)는 "이 라이브러리에 취약점이 있는 것은 맞지만, 우리 앱에서는 그 코드에 닿지 않는다"는 판단을 기계가 읽을 수 있게 적은 문서다.** 스캐너는 이 문서를 읽고 해당 경고를 통과시킨다. OpenVEX 는 그 형식 중 하나다.

<summary>이 글에 나오는 다른 용어</summary>

| 용어 | 뜻 |
|---|---|
| CVE, GHSA, PYSEC | 공개된 취약점에 붙는 번호다. 같은 취약점이 출처에 따라 다른 번호로 불리기도 한다 |
| Trivy | 컨테이너 이미지와 JAR 안의 라이브러리 버전을 읽어 알려진 취약점과 대조하는 스캐너 |
| npm audit, pip-audit | Node 와 Python 의존성 목록을 같은 방식으로 대조하는 명령 |
| High, CRITICAL | 스캐너가 매긴 심각도. 이 저장소는 High 이상이면 CI 를 막는다 |
| `braces` | 파일 경로 패턴(`src/{a,b}.js`)을 펼쳐 주는 작은 Node 라이브러리. 이 저장소는 직접 쓰지 않고, 코드 검사 도구 ESLint 가 여러 단계를 거쳐 끌어온다 |
| SSE | Server-Sent Events. 서버가 연결을 열어 둔 채 브라우저로 데이터를 계속 흘려보내는 방식 |
| view fragment | 서버가 HTML 조각을 만들어 보내는 기능. SSE 와 함께 쓰면 화면 일부를 실시간으로 바꿀 수 있다 |
| `RouterFunction` | Spring 에서 annotation 대신 코드로 URL 과 처리 함수를 연결하는 방식(함수형 엔드포인트) |
| Enterprise Support | Spring 의 유료 지원. 이번 공지들의 6.2.x 수정판은 여기로만 나왔다 |
| 정기 스캔 | 코드가 바뀌지 않아도 매주 한 번 같은 검사를 다시 돌리는 워크플로. 새로 공개된 취약점을 잡으려고 둔다 |

</details>

## 실패 원인은 성격이 다른 두 가지였다

로그를 열어 보니 실패 원인 중 어느 것도 이 PR의 변경과 관계가 없었다. 그리고 원인은 두 종류로 나뉘었다.

| 종류 | 무엇이 | 의미 |
|---|---|---|
| **새 취약점** | `certifi`(Python), `lz4-java`(Spring), Spring CVE 두 건 | 그사이 새로 공개된 취약점이다. 검사가 제 역할을 했다 |
| **예외 만료** | `braces`(Node, 개발 전용), Spring XSLT 취약점 | 10월 초부터 알고 있던 것이다. 바뀐 것은 없고, 유효기간만 지났다 |

처음 로그에서는 두 번째 것만 눈에 띄었다. 로그의 마지막 줄이 이랬기 때문이다.

```text
ValueError: Reassess current MVC reachability before accepting VEX
```

유효기간이 지난 VEX를 거부하면서 다시 확인하라고 요구하는 메시지다. 그래서 처음에는 "만료일 때문에 막혔다"로만 읽었다. 새 취약점이 함께 섞여 있다는 것은 하나씩 고치면서 알게 됐다. 아래에서는 둘을 나눠서 정리한다.

## 새 취약점 1: 고칠 버전이 있는 것은 올렸다

| 패키지 | 변경 | 이유 |
|---|---|---|
| `certifi` | 2026.10.19 | 인증서 묶음에 든 emSign 중간 CA의 키가 유출됐다는 CRITICAL 공지가 10월 20일에 나왔다. 그 CA를 뺀 판으로 올렸다. 결제·배송 API 둘 다 운영에 실제로 들어가는 의존성이다 |
| `lz4-java` | 1.11.1 → 1.11.4 | CVE-2026-106451. Kafka 클라이언트가 끌어오는 의존성이라 Gradle constraint로 버전을 올렸다 |
| `sanitize-html` | 2.17.7 → 2.18.1 | XSS 공지 두 건. Moderate라서 CI를 막지는 않았지만, 블로그와 위키 본문의 HTML을 거르는 자리라 같이 올렸다 |

`certifi`는 이번에 잡힌 것 중 가장 실질적인 문제였다. 운영 서버가 외부와 HTTPS로 통신할 때 이 인증서 묶음을 믿는다.

## 새 취약점 2: Spring 두 건은 Boot 4 대신 테스트로 막았다

| 공지 | 등급 | 발동 조건 | 공개 수정판 |
|---|---|---|---|
| [CVE-2026-47890](https://spring.io/security/cve-2026-47890) | CRITICAL | Server-Sent Events로 view fragment를 보내고, 공격자가 다른 사용자에게 가는 스트림 데이터를 제어할 수 있을 때 | 7.0.9 |
| [CVE-2026-47892](https://spring.io/security/cve-2026-47892) | CRITICAL | 함수형 엔드포인트(`RouterFunction`)의 헤더 predicate를 쓸 때 | 7.0.9 |

두 건 모두 6.2.x 수정판(6.2.20)은 유료 지원으로만 나온다. 공개 버전으로 고치려면 Spring Framework 7, 다시 말해 Spring Boot 4로 메이저 이전을 해야 한다.

Boot 4 이전은 이 PR에서 할 일이 아니라고 판단했다. 대신 예외를 쓰되, 그 근거를 테스트로 고정했다. 공지의 발동 조건이 이 앱에 없다는 것을 확인하고, 그 조건이 생기면 CI가 막히게 하는 방식이다.

이 앱의 Spring 백엔드는 annotated controller가 응답 본문을 쓰는 REST 서버다. WebFlux 의존성은 파트너 API 리허설에서 바깥으로 요청을 보내는 `WebClient` 때문에만 들어 있다. 서버 쪽으로 SSE 엔드포인트나 `RouterFunction`을 쓰는 코드는 없다.

`MvcSseRouterReachabilityTest`는 실제 애플리케이션 컨텍스트를 띄우고 두 가지를 확인한다.

```java
// 앱의 어떤 핸들러도 스트림이나 view fragment를 돌려주지 않는다
assertThat(ResponseBodyEmitter.class.isAssignableFrom(returnType)
        || Publisher.class.isAssignableFrom(returnType)
        || FragmentsRendering.class.isAssignableFrom(returnType)).isFalse();
assertThat(producibleMediaTypes).noneMatch(MediaType.TEXT_EVENT_STREAM::includes);

// 함수형 엔드포인트가 하나도 등록되어 있지 않다
assertThat(context.getBeansOfType(RouterFunction.class)).isEmpty();
assertThat(mapping.getRouterFunction()).isNull();
```

나중에 누군가 SSE 엔드포인트나 `RouterFunction`을 추가하면 이 테스트가 먼저 실패한다. 그 시점에 예외 판단도 다시 해야 한다는 뜻이다. 날짜가 아니라 코드 변경이 재검토를 부르는 구조라서, 유효기간보다 이쪽이 더 확실한 장치다.

VEX 문서를 검사하는 스크립트도 넓혔다. 원래는 "예외가 정확히 한 건"이어야 통과했다. 이제는 검토한 세 건만 정확히 허용하고, 각 건은 자기 제품 범위와 근거 테스트를 가져야 한다.

| 바꿔서 시도한 것 | 결과 |
|---|---|
| 47892의 범위에 `spring-webmvc`를 끼워 넣는다 | 실패 |
| 47890의 근거를 XSLT 테스트 이름으로 바꾼다 | 실패 |
| 세 건 중 하나를 지운다 | 실패 |
| 검토하지 않은 CVE를 추가한다 | 실패 |

마지막으로 로컬에서 CI와 같은 Trivy 명령으로 JAR를 스캔했다. VEX 없이 돌리면 CRITICAL 4건이 나오고, VEX를 적용하면 0건이다. 앞의 결과가 있어야 뒤의 0건이 "스캔이 아무것도 안 읽었다"가 아니라는 것을 증명한다.

## 만료된 예외: 다시 확인하고 기간을 늘렸다

두 예외는 10월 초 [Next.js 보안 공지를 대입해 본 글](/118/nextjs-september-2026-security-patch-review)에서 만들었고, 그때 유효기간을 2주로 잡았다.

- **`braces`**: 고친 버전이 없는 High 경고 하나가 개발 도구 다섯 단계를 타고 올라와 다섯 건으로 보였다. 운영에는 들어가지 않는다.
- **Spring XSLT(CVE-2026-47884)**: 공개 수정판이 7.0.9뿐이었다. 이 앱에는 XSLT 뷰가 없다.

유효기간이 끝났을 때 할 일은 앞에서 말한 대로다. 처음 근거가 지금도 맞는지 다시 확인한다.

| 처음 근거 | 10월 22일에 다시 확인한 것 |
|---|---|
| `braces`에 고친 버전이 없다 | 최신이 여전히 3.0.3이다. 공지의 영향 범위도 `<= 3.0.3`이다 |
| 경로가 개발 도구뿐이다 | 같은 경로다. Next 16의 ESLint 플러그인도 여전히 `fast-glob` 3.3.1에 묶여 있다 |
| 운영 의존성은 깨끗하다 | `npm audit --omit=dev --audit-level=high`가 여전히 0건이다 |
| Spring 6.2.x 공개 수정판이 없다 | Maven Central 최신이 여전히 6.2.19, Boot는 3.5.16이다 |
| 이 앱에는 XSLT 뷰가 없다 | 처음 평가한 뒤로 `spring/src/main`과 `build.gradle`이 한 줄도 바뀌지 않았다. 확인 테스트도 통과한다 |

근거가 모두 그대로였으므로 유효기간을 2주 더 늘렸다. 다시 확인한 날짜와 근거는 보안 문서와 커밋에 함께 남겼다. 이렇게 해서 PR의 검사 21개가 모두 통과했다.

## 정기 스캔은 열흘 전부터 새 취약점을 알고 있었다

글을 쓰려고 기록을 다시 보다가 하나를 더 알게 됐다. 이 저장소에는 PR과 별개로 매주 한 번 `main`을 스캔하는 정기 스캔이 있다.

| 정기 실행 | 결과 | 잡은 것 |
|---|---|---|
| 10월 12일 | 실패 | lz4-java, CVE-2026-47890, CVE-2026-47892 |
| 10월 19일 | 실패 | 같은 세 건 |

새 취약점 세 건은 PR보다 열흘 먼저 정기 스캔에 잡혀 있었다. 다만 그 실패는 GitHub Actions 탭에만 남고, 내가 보는 곳까지 알림으로 오지 않았다. PR에서도 이 세 건은 처음에 보이지 않았다. PR의 검사 순서상 이미지 스캔이 VEX 확인 바로 뒤에 있어서, VEX 만료로 먼저 멈추면 스캔까지 가지 않았기 때문이다.

## 돌아보며: 기한 설계는 손볼 곳이 있다

새 취약점을 잡은 것은 검사가 제 역할을 한 것이다. 그런데 예외 만료로 막힌 쪽은 돌아보면 불필요한 막힘에 가까웠다.

- **2주는 짧았다.** 다시 확인할 거리는 "고친 버전이 나왔나"와 "앱 코드가 바뀌었나"다. 앞의 것은 Spring 유료 지원 정책이나 2024년 이후 멈춘 `braces`를 보면 2주 안에 바뀔 가능성이 낮다. 뒤의 것은 이제 테스트가 코드 변경 즉시 잡는다.
- **만료되면 모든 PR을 막는 것은 과했다.** 날짜가 지났다고 위험이 생기지는 않는다. 그런데 이번에는 상관없는 문서 PR이 그 비용을 치렀다. 만료되면 막지 않고 경고만 띄워도, 다시 보게 하려는 목적은 지킬 수 있다.

둘 다 급한 일은 아니어서 이번 PR에서는 바꾸지 않았다. 지금 위험이 있는 것도 아니다. Spring 세 건은 테스트가 지키고 있고, `braces`는 운영 이미지에 들어가지 않는다.

## 남은 한계

- **테스트가 보는 범위는 좁다.** 핸들러의 반환 타입, `produces`, `RouterFunction` 빈만 확인한다. 필터나 서블릿에서 응답 스트림에 직접 SSE 형식을 쓰는 코드는 잡지 못한다.
- **등급은 Trivy의 판단이다.** 두 건을 CRITICAL로 분류한 것은 스캐너다. Spring 공지에 적힌 CVSS 벡터는 둘 다 공격 복잡도가 High다. 이 글에서는 등급보다 발동 조건을 근거로 판단했다.
- **정기 스캔의 실패를 알려 주는 경로가 아직 없다.** 알림을 붙이면 이번 같은 일을 열흘 먼저 알 수 있다.
- **예외가 늘면 Boot 4를 다시 따져 본다.** VEX는 라이브러리를 고친 것이 아니라 판단을 적은 것이다. Spring 공지가 나올 때마다 같은 확인을 반복해야 하고, 그 비용이 메이저 이전 비용을 넘으면 그때 옮긴다. 세 건인 지금은 그 시점이 아니라고 봤다.

보안 검사를 통과시키고 두 PR을 develop 에 모았다. 이제 멈춰 두었던 배포 구조 개편으로 돌아간다.
