> 이 글은 2026년 8월 24일 기준으로 썼다. GitHub를 기준으로 설명하지만 원칙 자체는 GitLab, Bitbucket 등 어느 호스팅 서비스에도 그대로 적용된다. 표기한 줄 수 기준이나 SLA 수치는 우리 팀에서 통했던 값이지 업계 정답이 아니다.

월요일 아침이다. 리뷰 요청 목록을 열면 800줄짜리 PR 하나가 6일째 대기 중이다. 작성자는 "리뷰 좀 봐달라"고 다그치고, 리뷰어였던 나는 지난주에 스크롤을 몇 번 내리다 만 뒤 창을 닫았다. 결국 목요일에 동료가 "LGTM(Looks Good To Me, 문제 없다는 리뷰 승인 표현)" 한 줄로 승인했다. 아무도 그 코드를 읽지 않았다.

이 글은 이 장면에서 출발한다. 먼저 PR이 정확히 무엇인지 짧게 짚고, 왜 리뷰가 항상 밀리는지 구조를 본 다음, **작성자 편 원칙과 리뷰어 편 원칙**을 정리한다. 이 원칙들이 결국 "사람끼리의 약속"이라는 한계에 도달하면, 약속을 기계가 대신 집행하게 만드는 저장소 설정을 살펴본다. 마지막으로 에이전트가 PR을 만들기 시작하면 뭐가 달라지는지까지 본다.

## PR이 뭐였더라 - 3분 요약

Pull Request(PR)는 **"내 브랜치의 변경 사항을 main에 합쳐달라"는 요청**이다. 정확히 말하면 Git 자체 기능이 아니라 GitHub, GitLab 같은 호스팅 서비스의 협업 기능이다. Git은 브랜치를 만들고 커밋하고 머지하는 것까지만 알 뿐, "검토 후 합치자"라는 절차 자체는 모른다. 그 절차를 올려준 것이 PR이다.

하지만 단순한 머지 요청이라면 PR이 이렇게 중심이 되지 않았을 것이다. PR의 진짜 역할은 **합치기 전에 벌어지는 모든 검토 활동을 한 화면에 묶는 문**이라는 데 있다.

| PR이 묶어주는 것 | 하는 주체 |
|---|---|
| diff(변경 내역) 열람과 코멘트 | 사람 |
| 승인(Approve) 또는 수정 요청(Request Changes) | 사람 |
| 빌드·테스트·린트 자동 실행 | CI (GitHub Actions 등) |
| 머지 가능 여부 판정 | 위 결과를 종합한 규칙 |

여기서 CI(Continuous Integration, 지속 통합)가 등장한다. PR이 열릴 때마다 기계가 자동으로 빌드와 테스트를 돌려 "이 변경이 깨진 코드가 아니다"를 미리 증명해준다. **PR은 사람이 판단하는 문이고, CI는 기계가 미리 검증해주는 검문소**다. 초록불(CI 통과)이 안 뜨면 머지 버튼이 비활성화되는 흐름이 전형적이다.

개념은 이게 전부다. 그런데 여기서 한 가지 의문이 생긴다.

### 잠깐, 혼자 개발하면 PR 없이 그냥 머지하면 되지 않나?

기술적으로는 맞다. Git은 로컬에서 브랜치를 머지하고 푸시하는 것까지 전혀 막지 않고, 1인 프로젝트에서 실제로 PR을 건너뛰고 바로 머지·배포하는 개발자도 많다. 문제없이 굴러간다.

그럼에도 PR이 거의 모든 팀의 기본값이 된 이유, 그리고 혼자일 때도 쓰는 이유는 이렇다.

| 상황 | PR이 주는 것 |
|---|---|
| 여럿이 함께 개발할 때 | 내 변경을 다른 사람이 **먼저 검토한 뒤** main에 반영한다. 실수와 충돌이 main에 도달하기 전에 걸린다 |
| 배포 장애가 났을 때 | PR 단위로 기록이 남아 "어느 변경이 원인인가"를 좁히기 쉽다 |
| 혼자 개발할 때 | 리뷰어는 없지만 CI 게이트(테스트 통과 강제)와 변경 기록은 그대로 쓸 수 있다 |
| 나중에 돌아봤을 때 | 커밋은 조각이고 PR은 완결된 변경이다. "왜 이걸 고쳤나"의 설명이 PR 설명에 남는다 |

정리하면 PR의 본질은 **main으로 가는 모든 변경에 관문 하나를 두는 것**이다. 팀에서는 그 관문에 사람(리뷰어)이 서고, 혼자라면 기계(CI)만 서더라도 관문 자체는 유지하는 편이 안전하다. 다만 사람이 몇 명 늘어나는 순간 이 관문은 "검토"라는 비용을 만들어내고, 이 글의 본론인 문제가 시작된다.

## 왜 리뷰는 항상 밀리는가

앞선 800줄 PR의 사망 과정을 분해하면 원인이 두 겹으로 겹쳐 있다.

첫째 겹은 **작성자 쪽**이다. PR 하나에 신규 기능, 리팩토링, 포맷팅 변경이 섞여 있으면 diff를 읽는 사람은 매 줄마다 "이건 꼭 필요한 변경인가?"를 스스로에게 물어야 한다. 인지 부하는 줄 수에 정비례하지 않고 가속한다. 실제로 리뷰 품질 저하를 피하기 위한 권장 상한으로 400줄 전후가 자주 언급되는데, 800줄짜리 PR은 시작부터 그 한계를 두 배나 넘긴 것이다.

둘째 겹은 **리뷰어 쪽**이다. 리뷰는 어디까지나 남의 작업을 방해받지 않고 해야 하는 일이라 우선순위 경쟁에서 늘 진다. 게다가 너무 큰 PR에는 정당한 전략이 하나 생긴다. 전부 못 읽겠으니 "LGTM"로 도망치는 것이다. 이건 게으름이 아니라 **읽을 수 없는 입력에 대한 합리적 반응**이다.

즉 이 문제는 "리뷰어가 성실해야 한다"는 교훈으로는 못 고친다. 큰 PR이 리뷰 불가능을 만들고, 리뷰 불가능이 LGTM을 낳고, LGTM이 리뷰의 의미를 갉아먹는 **악순환 구조**이기 때문이다. 깨는 지점은 두 곳 모두에서, 동시에 잡아야 한다.

## 작성자 편 - 리뷰어가 읽을 수 있는 PR 만들기

원칙은 하나로 수렴한다. **PR은 기능 단위가 아니라 리뷰 단위로 쪼갠다.**

| 나쁜 패턴 | 대안 |
|---|---|
| 기능 완성 후 PR 하나로 몰아서 올린다 | 기능을 여러 머지 가능한 조각으로 쪼개 순차적으로 올린다 |
| 리팩토링과 신규 로직이 같은 diff에 섞인다 | "리팩토링만" PR을 먼저 머지하고, 그 위에 신규 로직 PR |
| 포맷팅/임포트 정리가 섞여 diff가 부풀어 오른다 | 포맷팅은 별도 PR. 섞는 순간 실질 변경이 안 보인다 |
| 설명이 "~~ 구현함" 한 줄 | 무엇을/왜/어떻게 확인했는지를 템플릿으로 강제 |

설명 템플릿은 거창할 필요가 없다. 세 칸이면 충분하다.

```markdown
## 무엇을
결제 실패 시 사용자에게 에러 메시지를 노출

## 왜
고객사 문의(#1234). 현재는 실패 시 무반응이라 원인 파악이 불가능

## 어떻게 확인했나
- 재현 테스트 추가 (`payment.spec.ts` 참고)
- 로컬에서 실패 케이스 수동 확인 완료
```

여기에 하나만 더하면 리뷰 속도가 눈에 띄게 달라진다. **리뷰 포인트 지정**이다. "전부 다 봐주세요"보다 "특히 `PaymentService.retry()`의 재시도 로직이 맞는지 집중해서 봐주세요"가 리뷰어의 유한한 시간을 가장 중요한 곳에 쓰게 만든다. 나머지는 CI와 테스트가 맡으면 된다.

## 리뷰어 편 - 리뷰를 계속 가능하게 만들기

리뷰어 쪽 원칙의 핵심도 한 문장이다. **완벽한 리뷰보다 시의적절한 리뷰다.**

| 나쁜 패턴 | 대안 |
|---|---|
| "시간 나면 봐야지" 하다가 며칠 방치 | 리뷰 SLA를 정한다. 예: 영업일 1일 내 첫 응답 |
| 사소한 취향(naming 등)도 막고 진행 | 차단 코멘트와 취향 코멘트를 구분해 표기한다 |
| "LGTM"로 도망친다 | 못 읽겠으면 못 읽겠다고 말한다. "이 크기면 리뷰 불가, 쪼개달라"는 정당한 리뷰다 |
| 코멘트를 두괄식으로 쏟아낸다 | 결론 먼저, 근거는 그 다음. 질문형("이 경우 X면 어떻게 되나요?")으로 |

코멘트 톤도 실무에서 의외로 큰 변수다. "이름이 이상한데요"보다 "`getUserData`가 조회만 하는 것 같은데 `fetchUserData`가 더 정확하지 않을까요?"가 받아들여질 확률이 높다. 리뷰의 목표는 코드를 통과시키는 게 아니라 **코드와 작성자 모두 다음 단계로 나아가게 하는 것**이다.

SLA는 거창한 제도처럼 들리지만 실제로는 첫 응답만 보면 된다. "오늘 못 읽지만 내일 오전까지는 봅니다"라는 응답 한 줄만으로도 작성자의 불안과 재촉이 사라진다. 리뷰 지연의 실질 비용은 지연 자체보다 **"언제 될지 모른다"는 불확실성**에서 나온다.

## 약속을 기계가 대신 지키게 한다 - 저장소 설정

지금까지 나온 원칙(PR을 작게, 첫 응답 SLA, 차단/취향 구분)은 전부 **사람끼리의 약속**이다. 약속의 약점은 이미 알려져 있듯 바쁜 날 깨진다는 것이다. 그래서 실무에서는 이 약속들을 저장소 설정에 심어서, 기계가 매 PR마다 대신 집행하게 만든다. GitHub 기준으로 흔히 거는 설정은 이렇다.

| 설정 | 역할 | 막아주는 것 |
|---|---|---|
| 필수 리뷰 1~2명 (Required reviewers) | 승인 없이 머지 불가 | 아무도 안 읽고 머지되는 일 |
| 상태 검사 필수 (Required status checks) | CI 통과 없이 머지 불가 | 깨진 테스트를 아는 채로 머지하는 일 |
| 최신 브랜치 요구 (Require branches up to date) | main 최신화 없이 머지 불가 | 오래된 베이스로 인한 예상 못한 충돌 |
| 머지 방식 통일 (squash 등) | 커밋 히스토리 규격화 | 디버깅 시 추적 불가능한 히스토리 |

핵심 발상은 이것이다. **"리뷰를 해주세요"라는 문화적 요청을 "리뷰 없이는 버튼이 눌리지 않는다"는 구조적 제약으로 바꾼다.** 문화는 변덕스럽지만 설정은 매 PR마다 똑같이 작동한다.

다만 함정이 하나 있다. 설정을 걸어놓기만 하면 LGTM은 사라지지 않고 형태만 바뀐다. 승인 버튼을 누르기 위해 형식적으로 approve하는 LGTM이 될 뿐이다. 설정은 리뷰의 하한을 보장할 뿐 품질을 만들지 않는다. 품질은 앞의 작성자·리뷰어 원칙이 채우는 몫이다.

## 에이전트가 PR을 만들기 시작하면

여기까지의 이야기는 사람이 PR을 쓴다는 전제였다. 그런데 앞선 worktree 글에서 봤듯, 에이전트 도구들은 작업 하나당 worktree 하나를 만들고 그 결과를 브랜치와 PR로 남긴다. 즉 에이전트에게 일을 맡기기 시작하면 **PR의 작성자 자리에 사람이 아닌 프로그램이 앉게 된다.**

재미있는 점은, 지금까지 정리한 원칙들이 사라지지 않고 오히려 더 중요해진다는 것이다.

| 원칙 | 사람 작성자일 때 | 에이전트 작성자일 때 |
|---|---|---|
| PR은 리뷰 단위로 쪼갠다 | 습관과 규율의 문제 | 프롬프트와 도구 설정으로 강제할 수 있다. 오히려 지키기 쉬워진다 |
| 무엇/왜/확인방법 설명 | 작성자가 채운다 | 에이전트가 템플릿대로 생성한다. 다만 사실인지는 검증 필요 |
| 리뷰 포인트 지정 | 사람이 판단해서 지정 | 에이전트가 "불확실한 부분"을 지정하게 할 수 있다 |
| 첫 응답 SLA | 사람 일정에 좌우된다 | 문제 없음. 에이전트는 밤낮없이 기다린다 |
| 형식적 approve의 위험 | 가끔 발생 | 양이 늘어나면서 **구조적으로 심해진다** |

마지막 줄이 핵심이다. 에이전트가 열심히 일할수록 PR 개수는 늘어난다. 그런데 읽는 사람은 여전히 사람 하나다. 지금까지의 시스템이 "800줄짜리 PR 한 개"를 처리하지 못했다면, "200줄짜리 PR 하루 10개"는 더 못 처리한다. LGTM은 사라지는 게 아니라 **자동화되어버릴 위험**이 커진다.

그래서 에이전트 시대의 리뷰 관문은 비중이 옮겨간다. 사람이 모든 diff를 정독하던 방식 대신:

- **CI와 자동 검증이 1차 관문**: 테스트, 린트, 타입 검사는 기계가 전부 통과시킨 뒤 사람에게 넘긴다
- **사람의 리뷰는 2차 관문이되 질적으로 달라진다**: "코드가 동작하는가"보다 "에이전트가 올바른 문제를 풀었는가", "설명한 변경과 실제 diff가 일치하는가"를 보게 된다
- **합치는 최종 판단은 여전히 사람**: worktree 글의 결론과 같다. 격리 덕분에 에이전트의 산물은 언제나 폴더째 버릴 수 있는 상태로 도착한다

결국 PR이라는 장치 자체는 그대로다. 바뀌는 것은 그 관문 앞에 서는 작성자가 누구냐이고, 리뷰어인 사람의 역할은 코드 읽기에서 **방향과 결과의 검증**으로 이동한다.

## 정리 - 당장 내려놓을 수 있는 체크리스트

세 관점을 각각 한 줄씩 압축하면 이렇다.

- **작성자**: PR은 리뷰 단위로 쪼개고, 설명은 무엇/왜/확인방법 세 칸, 리뷰 포인트를 지정한다
- **리뷰어**: 첫 응답 SLA를 지키고, 차단/취향 코멘트를 구분하며, 못 읽겠으면 쪼개달라고 말한다
- **설정**: 필수 리뷰와 CI 게이트로 약속을 기계가 집행하게 만들되, 설정이 품질을 대신하지 않는다고 기억한다
- **에이전트 시대**: diff 정독에서 "올바른 문제를 풀었는가, 설명과 결과가 일치하는가"의 검증으로 리뷰 초점을 옮긴다

마지막에 경계를 하나 명시한다. 이 글의 수치(400줄, 영업일 1일 등)는 많은 팀에서 통용되는 경험값이지 연구로 확립된 임계값이 아니다. 우리 팀의 맥락에 맞게 조정하고, 조정한 값을 기록해두는 편이 맞다.
