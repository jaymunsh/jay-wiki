Day 3가 끝난 뒤의 저장소에는 브라우저 테스트가 16개 통과했다는 기록이 있었다. 그런데 화면을 직접 열어 보니 게임 컨테이너는 넓은데 오목판은 작은 상태로 위쪽에 붙어 있었다. 홈·대기방·대기실도 연결되어 있었지만, 실제 온라인 게임으로 오해하기 쉬운 부분과 아직 로컬 mock에 머문 부분이 섞여 있었다.

Day 4에는 온라인 서버까지 한 번에 만들겠다는 목표를 잠시 내려놓았다. 먼저 보드가 차지해야 할 공간을 되찾고, 홈에서 봇 대국과 로컬 mock 대기방으로 들어가는 흐름을 다시 확인한 뒤, 밤사이 바뀐 코드가 이전 기능을 망가뜨리지 않았는지 회귀 테스트로 묶는 쪽을 택했다. 최종 목표인 온라인 오목은 그대로지만, 이번 단계의 결과는 **온라인 구현 완료가 아니라 다음 연결을 시작할 수 있는 UI·테스트 기준선**이다.

이번 실험의 역할 분담도 다시 적어 둔다. 지금까지의 IMPLEMENTATION_PLAN 문서는 GPT luna-xhigh의 도움으로 작성했고, 실제 구현과 검증은 Ornith 1.5 35B를 연결한 Qwen Code에서 진행했다. Day 4 세션의 직접 작업은 이미 작업 트리에 존재하던 Phase 1·2 앱 변경을 확인하고, 회귀 시나리오 4개를 새 테스트로 이관해 검증하는 일이었다. 계획을 만든 모델과 코드를 실행한 로컬 모델을 같은 주체처럼 기록하지 않기 위해 이 구분을 계속 유지한다.

## 이번에는 한 문장으로 계획서 전체를 맡겼다

Day 3에서는 Git 보존, 반복 오류 처리, 구현 범위와 제외 항목을 긴 Goal 프롬프트에 직접 적었다. Day 4에서는 그 조건을 IMPLEMENTATION_PLAN_DAY4.md로 옮긴 뒤, Qwen Code에는 계획서 전체를 수행하라는 짧은 요청만 보냈다. 오전 6시 44분 39초에 실제로 입력한 원문은 다음 한 문장이다.

~~~text
/goal

IMPLEMENTATION_PLAN_DAY4.md를 처음부터 끝까지 읽고 모든 범위와 완료 조건을 진행해줘.
~~~

문장은 짧지만 실제 작업 범위까지 작았던 것은 아니다. 계획서는 240×240으로 고정된 canvas의 측정부터 홈·대기방 UI, R1~R10 회귀 시나리오, 전후 캡처와 보고서 작성까지 요구했다. 반면 실제 WebSocket 서버, 두 사용자 네트워크 대국, 인증·랭킹·외부 배포는 제외했다.

| 계획서가 이번에 요구한 것 | 다음 단계로 미룬 것 |
| --- | --- |
| canvas 크기·DPR·클릭 좌표 복구 | 실제 WebSocket 또는 Socket.IO 서버 |
| 홈·게임·대기방·대기실 UI 정리 | 두 사용자 사이의 네트워크 대국 |
| 로컬 mock임을 드러내는 문구 | 인증·랭킹·관전자 |
| 기존 봇 대국과 화면 이동 회귀 검사 | 프레임워크 교체와 전면 재작성 |
| 실제 뷰포트 측정·캡처·최종 보고 | 외부 네트워크와 배포 |

계획에는 “2~3시간은 선택 가능한 실행 예산이지 완성 예상 시간이 아니다”라는 문장도 있었다. 결과적으로 Goal 활성 시간은 4시간 26분까지 늘어났다. 짧은 요청으로 상세 계획을 실행시키는 방식은 입력을 단순하게 만들었지만, “계획서 전체”라는 하나의 Goal 안에 UI 수정·브라우저 자동화·시각 증거·보고서까지 묶었다. 이 범위가 뒤에서 확인할 evidence catalog 한도와도 연결됐다.

## 4시간 26분의 작업은 기록에서 다시 복원했다

DAY4_REPORT에는 API 처리 시간과 Goal 활성 시간을 측정하지 않았다고 적혀 있다. 보고서만 보면 여기서 더 나아갈 수 없다. 하지만 Qwen Code의 세션 JSONL과 runtime 기록, oMLX 서버 로그는 남아 있었다. 글을 쓰면서 세 자료의 시각과 토큰 수를 다시 맞춰 보니 Day 4의 수행 시간을 사후 복원할 수 있었다.

Qwen Code 프로세스는 오전 6시 44분 14초에 시작했고, 6시 44분 39초에 IMPLEMENTATION_PLAN_DAY4 전체 수행을 목표로 하는 Goal이 생성됐다. Goal은 오전 11시 10분 46초에 usage_limited 상태가 됐다. Goal 자체가 기록한 활성 시간은 15,966,330ms, 즉 4시간 26분 6.330초다. 이후 정리 응답이 조금 더 이어져 세션의 마지막 기록은 오전 11시 14분 20초에 남았다. 프로세스 시작부터 마지막 기록까지는 4시간 30분 5.165초다.

Goal은 22개 turn을 마친 시점에 30,000,000 토큰 예산 중 16,062,746을 사용했다고 기록했다. 약 53.5%다. 따라서 이번 종료는 토큰 예산 소진 때문이 아니었다. 상태에 남은 이유는 “bounded evidence catalog 초과”였다. 긴 세션에서 근거 항목이 내부 한도를 넘었고 자동 재시도로는 회복할 수 없다는 의미다. 화면과 테스트가 부분 완료된 상태에서 작업이 멈춘 이유를 단순한 시간 초과나 3천만 토큰 소진으로 설명하면 실제 기록과 맞지 않는다.

## 생성은 37.2 tok/s였지만 요청 전체는 16.8 tok/s였다

Qwen 세션에는 assistant 응답이 305개 남아 있다. 각 응답의 시각과 출력 토큰 수를 oMLX의 Chat completion 로그와 대조했고, 305개를 모두 105ms 이내에서 일치시켰다. 이 범위를 기준으로 출력은 156,297토큰이었다. usage metadata에는 이 가운데 생각 토큰이 83,627개로 따로 표시되지만, 출력 합계에 다시 더하지 않았다.

oMLX가 각 요청에 기록한 순수 생성 속도는 29.2~50.6 tok/s에 분포했다. 요청별 중앙값은 38.5 tok/s였고, 출력 토큰 수로 가중한 값은 37.2 tok/s다. MTP가 활성화된 실제 Day 4 세션의 decode 속도로는 이 수치가 가장 가깝다.

그렇다고 사용자가 체감한 에이전트 속도가 37.2 tok/s였다는 뜻은 아니다. 305개 요청의 처리시간을 모두 더하면 9,313.640초, 2시간 35분 13.640초다. 출력 156,297개를 이 시간으로 나누면 요청 전체 기준 처리량은 16.8 tok/s로 내려간다. oMLX의 37.2 tok/s는 토큰을 생성하는 구간을 보고, 16.8 tok/s는 긴 문맥의 prefill, 첫 토큰 대기, 캐시 처리와 요청 종료까지 포함한다.

| 지표 | 값 | 포함 범위 |
| --- | --- | --- |
| oMLX 가중 생성 속도 | 37.2 tok/s | decode 구간 |
| 요청별 생성 속도 중앙값 | 38.5 tok/s | 305개 요청의 중앙값 |
| 요청별 생성 속도 범위 | 29.2~50.6 tok/s | Day 4에서 일치한 요청 |
| 요청 전체 출력 처리량 | 16.8 tok/s | 출력 토큰 ÷ API 요청시간 합계 |
| API 요청시간 합계 | 2시간 35분 13.640초 | 305개 요청 |
| Goal 활성 시간 | 4시간 26분 6.330초 | 모델 호출, 도구 실행, 테스트와 정리 포함 |

누적 프롬프트는 15,948,409토큰이었고 이 중 14,327,808토큰이 캐시됐다. 캐시 비율은 89.84%다. 실제로 새로 처리한 프롬프트는 1,620,601토큰이지만, 세션이 길어지면서 매 요청이 큰 문맥을 다시 참조했다. 높은 캐시 적중률이 있어도 API 처리시간 합계가 Goal 활성 시간의 약 58.3%를 차지한 이유다. 나머지 약 1시간 50분 53초에는 셸 명령, 파일 읽기와 수정, Playwright 실행, 결과 해석, 에이전트 전환 시간이 함께 들어 있으며 세부 항목별 시간은 따로 측정되지 않았다.

## 240px처럼 보이던 보드의 원인을 먼저 측정했다

Day 3 화면에서 가장 먼저 눈에 들어온 문제는 보드 크기였다. 좌측 카드의 내부 공간은 충분한데 canvas가 그 크기를 따라가지 못해 작은 판으로 남아 있었다. 감으로 CSS 값을 조금씩 바꾸는 대신, Day 4에는 실제 뷰포트에서 wrapper의 content box와 canvas의 CSS 크기를 함께 기록했다.

수정의 핵심은 canvas 자신이 아니라 보드 wrapper가 실제로 사용할 수 있는 content box를 기준으로 크기를 계산하는 것이었다. 화면이 아직 숨겨져 있어 측정값이 0이면 그 값을 최종 크기로 저장하지 않고, 화면 전환 뒤 다시 측정한다. device pixel ratio는 backing store를 CSS 크기의 배수로 만들 때만 적용하고, 클릭 좌표에 다시 곱하지 않았다. 표시 크기, 38px padding, 교점 간격을 같은 좌표계로 사용해야 돌을 놓은 위치와 화면에 그린 위치가 어긋나지 않기 때문이다.

![복구 후 보드가 좌측 카드의 사용 가능한 영역을 채우는 게임 화면](/api/wiki-assets/6600eee5-59d2-4b05-9004-534bac1a49e2)

그 결과 1440×900과 1200×800 데스크톱 뷰포트에서는 canvas가 736×736 CSS 픽셀로 측정됐다. wrapper의 테두리까지 포함한 크기는 760이고, 안쪽 content가 736이다. 15×15 오목판의 14개 간격은 47.143px, 좌표 여백은 38px로 기록됐다. 390×844 모바일 뷰포트에서는 canvas가 326×326, 교점 간격은 17.857px로 줄어들면서도 같은 38px 좌표 여백을 유지했다. 세 뷰포트 모두 canvas가 wrapper를 채웠고, CSS 크기와 backing store 크기가 일치했으며, 콘솔 오류가 없었다.

보드 측정 스크립트에도 작은 함정이 있었다. Playwright의 newContext에 width와 height를 직접 넘기면 실제 viewport가 바뀌지 않고 기본값으로 남을 수 있었다. 이를 viewport 객체로 넘기도록 고친 뒤에야 390×844 결과가 정말 모바일 측정값인지 확인할 수 있었다. 자동화 코드의 한 줄이 틀리면 숫자와 캡처가 모두 그럴듯하게 잘못될 수 있다는 사례다.

## 옵션을 저장할 때 이전 봇의 예약 응답이 섞이지 않게 했다

게임 화면에는 규칙, 제한 시간, 봇 난이도, 흑·백 이름을 바꾸는 옵션 모달이 있다. Day 4에는 옵션을 저장하면 botGeneration을 증가시키고 게임을 초기화하도록 연결했다. 이전 판에서 예약된 봇 응답이 새 설정으로 만든 판에 뒤늦게 나타나는 문제를 막기 위해서다.

![규칙과 제한 시간, 봇 난이도, 선수 이름을 바꾸는 옵션 모달](/api/wiki-assets/aaf5250d-c4a3-4980-9202-07a0f1b2fd41)

이 흐름은 R2-1과 R2-2로 확인했다. 사람의 첫 수 직후 재시작했을 때 새 판에 예전 봇 착수가 남지 않아야 하고, 같은 상황에서 옵션을 저장했을 때도 새 판에 이전 예약이 들어오지 않아야 한다. 처음 R2-2가 실패했을 때 앱이 잘못된 것이 아니었다. 테스트가 저장 버튼이 아니라 취소 버튼인 modalCancel을 눌렀고, 그 결과 봇 예약 상호작용을 기대한 흐름과 달라졌다. 선택자를 modalSave로 고친 뒤 앱 코드는 추가 변경 없이 통과했다. 테스트 실패를 곧바로 제품 버그로 분류하지 않고, 입력·기대·구현 중 어느 층이 어긋났는지 나눠 본 기록이다.

수순과 채팅 패널도 무한히 늘어나지 않게 했다. 수순은 최근 3개, 채팅은 최근 5개만 표시하고 각각 고정 높이 내부 스크롤을 사용한다. 화면에 전부 쌓이는지보다 사용자가 지금 확인해야 할 정보가 남는지를 기준으로 정리했다.

## 홈과 대기방에는 지금 가능한 것과 아직 아닌 것을 함께 표시했다

홈에는 공통 브랜드 제목을 한 번만 두고, 본문에는 대국 시작과 온라인 대기방 진입이라는 행동을 배치했다. 아직 다른 브라우저와 연결하는 기능은 없으므로 대기방 버튼과 대기실에 로컬 mock이라는 안내를 넣었다. 한 명뿐인 대기실에서 가짜 상대를 채워 시작 버튼을 활성화하는 방식도 사용하지 않았다.

![공통 헤더와 봇 대국·온라인 대기방 진입 버튼이 있는 홈 화면](/api/wiki-assets/c2ff1292-1d8a-4b5e-9f2c-02c1ce502ce2)

대기방 목록은 방 이름을 입력해 방을 만들고, 새로고침하거나 홈으로 돌아가는 최소 흐름을 제공한다. 빈 목록일 때는 새로운 방을 만들라는 안내가 보인다.

![로컬 mock 안내와 빈 목록이 보이는 온라인 대기방 화면](/api/wiki-assets/f3fddb5b-43e9-4074-8598-23e887c47cf6)

방에 들어가면 흑 Player 슬롯과 비어 있는 백 슬롯, 준비·시작 컨트롤이 보인다. 여기서 “상대를 기다리는 중”이라는 문구와 실제 다른 플레이어 연결 미지원 안내가 함께 있어야 현재 구현 범위를 오해하지 않는다. 이 화면은 서버 방 상태가 아니라 브라우저 안의 RoomManager를 보여주는 로컬 경계다.

![상대 슬롯이 비어 있는 로컬 mock 대기실 화면](/api/wiki-assets/0935f17c-da80-468e-b127-70e66a5b550e)

## 24개 브라우저 테스트가 확인한 것과 확인하지 못한 것

단위 테스트는 규칙 판정, 게임 상태, 봇, RoomManager를 합쳐 90개가 모두 통과했다. 브라우저 테스트는 실제 정적 서버와 시스템 Chrome을 띄워 24개를 순차 실행했다. 보드 클릭도 단순히 함수를 호출하지 않고, padding과 cellSize로 교점 좌표를 계산해 canvas에 실제 click 이벤트를 보냈다. 이관한 수순 테스트는 사람과 봇 턴이 번갈아 오므로 클릭마다 80ms를 기다렸다.

기존 legacy 테스트를 지워 통과율을 올리지는 않았다. 오래된 선택자와 경로를 쓰는 suite는 현재 활성 목록에서 제외하되, 회귀 가치가 높은 네 시나리오만 현재 DOM과 경로에 맞춰 playwright-day4-regression.test.mjs로 옮겼다.

| 이관한 시나리오 | 확인한 조건 |
| --- | --- |
| R2-1 | 첫 수 직후 재시작하면 이전 봇 착수가 새 판에 나타나지 않음 |
| R2-2 | 첫 수 직후 옵션 저장해도 이전 봇 예약이 새 판에 섞이지 않음 |
| 이관-1 | 최근 3수만 보이고 수순 영역에 내부 스크롤이 생김 |
| 이관-2 | 채팅이 최근 5개만 표시됨 |

반대로 제한 시간 옵션을 바꾼 뒤 실제 시간패가 나는 R5는 아직 활성 E2E가 없다. R9도 모달을 열고 저장하는 경로는 확인했지만, 바꾼 규칙·난이도·이름·시간이 다음 봇 대국의 실제 판정과 표시값에 모두 반영되는지는 직접 검증하지 않았다. 모바일은 1열 레이아웃까지 확인했지만 키보드 포커스는 별도 테스트가 필요하다.

## 그래서 Day 4는 부분 완료로 기록했다

보고서의 상태는 “부분 완료”다. R2·R3·R7·R8 네 묶음은 완전히 통과했고, 다섯 묶음은 부분 검증, R5 한 묶음은 미커버다. 당시 보고서에는 운영 수치를 측정하지 않았다고 적었지만, 이번 글에서는 보존된 Qwen 세션과 oMLX 로그를 일대일로 대조해 사후 복원한 값만 사용했다. 실시간으로 따로 계측한 값과 나중에 로그에서 계산한 값을 구분하기 위해 계산 방식도 함께 남겼다.

보고서 작성 시점에는 사람이 보드·홈·대기실을 직접 확인하는 시각 검수도 남아 있었다. 이 글에 붙인 다섯 장의 캡처는 그 화면이 어떤 상태인지 보여주는 증거이지, 자동 테스트가 보장하지 않는 상호작용까지 통과했다는 뜻은 아니다. 테스트가 초록색이어도 사용자가 보는 화면과 실제 지원 범위를 함께 확인해야 완료라고 부를 수 있다.

Goal이 usage_limited로 바뀐 직후 내가 보낸 마지막 입력은 “끝난거 아니야? 그럼 종료해”였다. 에이전트가 완료 조건을 모두 충족해 스스로 complete를 선언한 것이 아니라, 보고서를 만든 뒤에도 자동 continuation이 이어지자 사람이 종료를 요청한 것이다. Day 4의 결말에서 이 사실을 빼면 24/24 통과가 자연스러운 완료로 이어진 것처럼 보이지만, 실제 기록은 그렇지 않았다.

## Day 4가 남긴 결론은 UI 복구만이 아니었다

화면만 보면 Day 4의 변화는 분명하다. 240×240에 머물던 보드는 데스크톱에서 736×736으로 커졌고, 홈·게임·옵션·대기방·대기실은 같은 시각 언어로 정리됐다. 브라우저 테스트도 Day 3의 16개에서 24개로 늘었다. 오래된 테스트를 없애 숫자를 맞추지 않고, 가치가 남은 네 시나리오를 현재 경로로 이관했다.

하지만 실험 운영에서는 다른 문제가 드러났다. 계획서가 요구한 R1~R10 가운데 완전 통과는 4개뿐이고, 5개는 부분 검증, 1개는 미커버다. Goal은 예산의 53.5%를 사용한 상태에서 evidence catalog 한도에 걸렸고, 사용자가 직접 종료해야 했다. 무엇보다 계획서가 요구한 시간·토큰 기록을 최종 보고서가 누락해, 글을 쓰는 단계에서 원본 로그를 다시 분석해야 했다.

따라서 Day 4의 답은 두 문장으로 정리할 수 있다. **Ornith 1.5 35B는 깨진 canvas 좌표계를 추적하고 UI를 복구하며 회귀 테스트를 확장할 수 있었다. 동시에 UI 수정부터 증거 수집과 최종 판정까지 하나의 Goal에 넣으면, 토큰 예산이 남아 있어도 긴 근거 목록과 자동 continuation 때문에 스스로 작업을 닫지 못했다.**

다음 실행에서 바꿔야 할 것은 모델보다 작업 단위다.

| Day 4에서 아쉬웠던 점 | 다음 실행에서 바꿀 방식 |
| --- | --- |
| 계획서 전체를 하나의 Goal로 실행 | 보드 복구, 회귀 부채, 서버 연결을 별도 Goal로 분리 |
| 완료 뒤에도 continuation 반복 | 각 Goal에 최대 turn과 종료 조건을 명시 |
| 보고서에 성능 수치 누락 | 세션 JSONL과 oMLX 로그 집계를 종료 명령에 포함 |
| 자동 테스트 통과 뒤 시각 검수 대기 | 지정 캡처 5장을 완료 게이트에 포함 |
| R5·R9가 부분 검증으로 남음 | 다음 기능 추가 전에 독립 회귀 Goal로 먼저 닫기 |

## Day 5는 두 브라우저가 같은 방을 보는 데까지만 간다

온라인 오목을 완성하려면 로컬 mock을 실제 이벤트 경계로 바꿔야 한다. 순서는 다음처럼 잡는 것이 현실적이다.

~~~mermaid
flowchart TB
  A[R5 시간패와 R9 설정 적용을 별도 Goal로 종료] --> B[브라우저 A가 서버에 방 생성]
  B --> C[브라우저 B가 같은 방에 입장]
  C --> D[두 화면에서 선수·준비 상태 일치]
  D --> E[호스트 시작 뒤 같은 gameId와 흑백 배정 확인]
  E --> F[여기서 Day 5 종료]
~~~

먼저 Day 4의 부채인 R5 시간패와 R9 설정 적용을 기능 추가와 분리해 닫는다. 그다음 Day 5의 온라인 범위는 서버 방 생성·입장·준비·시작까지로 제한한다. 브라우저 A가 방을 만들고 B가 들어왔을 때 두 화면에 같은 방 ID, 선수 두 명, 준비 상태, 흑백 배정과 gameId가 보여야 한다. 한 브라우저의 내부 배열에 상대를 직접 넣는 테스트는 이 조건을 통과한 것으로 세지 않는다.

착수 동기화, 서버 승패 판정, 재대결, 재접속과 외부 네트워크는 그다음 Goal로 넘긴다. Day 4처럼 다음 단계 전체를 한 번에 넣지 않는다. 최종 목표는 온라인 오목 완성이지만, 다음 기록에서 답할 질문은 하나면 충분하다. **로컬 LLM이 로컬 mock을 걷어 내고 두 개의 실제 브라우저에 동일한 대기실 상태를 만들 수 있는가.**
