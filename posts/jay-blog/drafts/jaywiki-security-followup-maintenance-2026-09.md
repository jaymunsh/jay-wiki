> **9월 10일 완료 기록:** 운영 저장소·권한 전환, 백업 복원, 공개 로그인과 DB SSH 연결 검증에 이어 최종 자동 배포와 외부 브라우저 검사까지 통과했다. 이번 전환 작업은 마무리했고, 반복해서 확인할 백업·인증서 관리 항목은 맨 아래에 따로 구분했다.

보안 점검을 끝내고도 기록에 미완료 줄이 남아 있었다. 접근 정책과 호스트 설정은 고쳤지만, 캐시가 인증 기록을 밀어내도 되는지와 백업으로 서비스를 되살릴 수 있는지는 다른 질문이었다. 테스트가 통과한다는 말도 편집 화면에서 저장 버튼이 눌린다는 뜻은 아니었다.

[앞선 보안 점검](/65/jaywiki-security-audit-2026-09)은 외부 접근과 실행 권한을 실제 서버에서 확인한 기록이다. 이번에는 그 뒤에 남은 일을 이어서 했다. 9월 8~10일의 보안 후속 개선과 유지보수를 다루며, **로컬 구현에서 운영 전환과 복구 검증까지 이어진 과정을 날짜별로 구분한다.**

## 후속 점검에서는 글을 잃는 경로와 개발 도구도 봤다

다시 보니 보안은 외부 접속만의 문제가 아니었다. 오래된 초안으로 운영 글을 덮는 일도 데이터의 무결성을 깨뜨린다. 개발 서버의 관리 버튼도 실제 발행 스크립트를 실행한다면 보호할 대상이다.

내부 발행에는 **마지막으로 맞췄던 콘텐츠의 해시**를 기준으로 삼았다. 초안이 기억하는 기준과 서버의 현재 내용이 다르면 409로 멈춘다. 파일을 복사하거나 체크아웃해도 바뀌는 수정 시각만으로 어느 쪽이 최신인지 결정하지 않도록 했다. 다만 관리자 편집 화면 전체에 충돌 해결 기능을 넣은 것은 아니다.

개발 관리 API에는 로컬 주소 바인딩, 필수 출처 검사, 입력 크기·실행 시간·동시 실행 제한을 넣었다. 자산을 읽는 프록시에도 응답 크기와 대기 시간의 상한을 추가했다. 복원 도구는 비밀번호를 명령 인자로 꺼내는 대신 클러스터 내부의 Secret 참조를 사용하도록 바꿨다.

9월 8일 로컬 검증에서는 Spring 282개와 웹 145개 테스트가 통과했고, 타입 검사와 문서 일관성 검사도 통과했다. 린트 경고는 기존 7개를 유지했다. **복원 도구를 고친 것과 실제 복원을 한 것은 다르다.** 당시에는 운영 복원, 새 이미지 검사 CI 실행, 후속 코드 배포가 남아 있었다. 아래 9월 10일 기록에서 그 결과를 이어 쓴다. 운영 SSH 재접속도 당시에는 재인증 때문에 완료하지 못했다. 그 시점의 로컬 검사만으로 운영 호스트까지 다시 검증했다고 판단하지 않았다.

## 9월 9일에는 보안 상태를 지키는 코드를 만들고 실제 백업을 복원했다

앞의 기록을 읽고 남은 일을 이어서 했다. 여기서부터는 **로컬 구현과 검증 결과**다. 운영에 이미 적용한 첫 점검과 섞이지 않도록 날짜와 범위를 나눈다.

### 캐시는 없어져도 되지만 인증 기록은 먼저 사라지면 안 된다

인증 시도 제한과 일회용 코드 사용 이력이 일반 캐시와 같은 Redis에 있었다. [Redis의 퇴출 정책](https://redis.io/docs/latest/develop/reference/eviction/) 중 `allkeys-lru`는 메모리가 부족하면 덜 쓰인 키를 지운다. 캐시는 다시 계산하면 되지만, 아직 유효한 OTP 사용 이력이 먼저 사라지면 재사용을 막는 판단 근거가 없어진다. 실제 공격 성공을 재현한 것은 아니지만 보안 상태를 캐시와 같은 조건으로 버려도 되는지는 따로 다뤄야 했다.

OTP·요청 제한·JWT 폐기 기록에 전용 Redis 연결을 배정하고, 인증과 `noeviction`, 디스크 기록, 접근 정책을 갖춘 배포 구성을 만들었다. **`noeviction`은 장애를 없애지 않는다.** 메모리가 부족하면 새 쓰기를 거절하므로, 인증을 느슨하게 통과시키는 대신 실패시키는 쪽을 선택한 것이다.

테스트에서는 캐시와 보안 키가 다른 인스턴스에 저장되는지, 메모리를 채워도 기존 보안 키가 남는지 확인했다. Redis를 재시작한 뒤 폐기 기록이 유지되는지와 응답을 중단했을 때 인증이 503으로 실패하는지도 확인했다. 9월 9일에는 운영 전환 전이었다. 기존 키의 남은 유효 시간을 보존하며 옮기는 절차 없이 빈 Redis로 바꾸면 바로 그 기록을 잃는다.

### 로그아웃한 토큰을 다시 보내 보고 판단했다

쿠키를 지우는 것만으로는 이미 복사한 JWT가 사라지지 않는다. 그래서 로그아웃한 토큰의 해시를 만료 시각까지 기록하고, 인증 때 폐기 여부를 확인하도록 바꿨다. 원문 토큰은 폐기 목록에 저장하지 않는다. 같은 초에 로그인해도 토큰이 구별되도록 발급 식별자도 넣었다.

검증은 쿠키가 사라지는 화면에서 끝내지 않았다. 로그아웃한 토큰을 다시 보내 인증이 거절되는지, 별도로 발급한 다른 토큰은 유지되는지 확인했다. 모든 기기의 토큰을 계정 단위로 한 번에 폐기하는 기능까지 만든 것은 아니다.

변경 요청의 출처 검사도 넓혔다. 쿠키는 브라우저가 자동 전송하므로 로그인 여부만으로 사용자가 의도한 요청인지 판단할 수 없다. [Spring의 CSRF 설명](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html)에서 다루는 문제다. 브라우저의 Origin과 요청 메타데이터를 확인하고, 쿠키를 사용하는 BFF 변경 요청에는 Origin을 요구했다.

여기서 정상 요청도 한 번 막았다. Spring이 프록시 헤더를 먼저 처리한 뒤에는 원래 헤더만 읽어 호스트를 비교하면 안 됐다. 실제 BFF를 거쳐 로그아웃해 보고 403이 나오는 것을 확인한 뒤, Spring이 해석한 서버명과 포트를 사용하도록 고쳤다. 단위 테스트 통과가 호출 경로 전체의 통과는 아니었다.

### 발행할 파일을 고르는 일과 서버의 글을 비교하는 일을 나눴다

초안을 저장소에 보존한 행동이 곧 공개 발행의 뜻이 되지 않도록, 자동 발행은 명시적인 파일 목록만 읽게 바꿨다. 기본 목록은 비어 있다. 초안 묶음은 ConfigMap 대신 Kubernetes 실행 채널로 임시 볼륨에 보내고 체크섬을 확인한 뒤 실행한다. 객체 저장소용 자격 증명은 추가하지 않았다.

기준 해시 초기화에는 글을 쓰지 않는 비교 경로를 만들었다. 운영과 같은 내용일 때만 기준을 받을 수 있고, 다르거나 글이 없으면 초기화를 중단한다. 최신 해시를 무조건 받아서 덮어쓰기에 쓰는 우회는 만들지 않았다. 이 비교 도구의 로컬 검증 뒤, 9월 10일 운영 비교 API로 같은 본문의 기준 해시를 초기화했다. 다른 작업에서 수정 중인 초안은 대상에서 제외했다.

### 장비 밖 사본으로 세 데이터베이스를 되살렸다

백업 파일이 있다는 사실만으로는 복원할 수 있다고 말할 수 없다. 9월 7일 장비 밖으로 받아 둔 사본을 임시 PostgreSQL에 복원했다. 운영 원본에는 쓰지 않았고, 백업 디렉터리도 읽기 전용으로 연결했다.

| 대상 | 확인한 결과 | 복원 명령 소요 |
|---|---|---|
| 글·계정 DB | 위키 89행, 블로그 64행 등 주요 테이블 조회 | 2.7초 |
| 결제 DB | 결제 31행, 아웃박스 59행 조회 | 0.1초 |
| 배송 DB | 배송 2행, 아웃박스 2행 조회 | 0.1초 |

세 덤프의 체크섬이 일치했고 복원 명령은 오류 없이 끝났다. 이 수치는 **해당 사본을 로컬 DB로 복원한 시간**이다. 컨테이너 준비와 이미지·설정 복구까지 포함한 서비스 RTO가 아니다. 이미지 저장소와 기동 설정까지 되살려 본 것은 아니므로 전체 재해 복구 완료로 적지 않는다.

## 유지보수도 같은 실수가 다시 생기지 않는 쪽으로 정리했다

보안 코드를 고치고 나니 검증과 원고 관리에도 같은 문제가 남아 있었다. 각각은 긴급 취약점이 아니지만, 다음 변경에서 문제를 만들거나 놓치기 쉬운 자리였다.

### 브라우저에서 저장 버튼을 누르는 검사까지 이어 붙였다

기존 브라우저 검사는 공개 페이지가 열리고 정적 자산이 로드되는지를 중심으로 봤다. 여기에 로그인, 초안 저장, 공개 발행, 본문 편집, 시리즈 연결, 로그아웃 뒤 토큰 재사용 거절을 한 흐름으로 추가했다. 실제 Spring과 임시 DB를 사용하는 이 흐름은 데스크톱과 모바일에서 모두 통과했다.

백엔드 응답을 성공으로 꾸며 놓으면 저장용 호출이 실제 보안 필터를 통과하는지 알 수 없다. 그래서 [Playwright의 서버 기동 기능](https://playwright.dev/docs/test-webserver)으로 실제 Spring과 Next를 띄우고, PostgreSQL과 Redis는 테스트용 컨테이너를 사용하게 했다. 쓰기 테스트의 대상 주소는 로컬로 고정해 운영을 향하지 않게 했다.

호출부를 대조하다 블로그 저장용 서버 액션에 새 보안 표식 전달이 빠진 곳을 찾았다. 실제 검사에서는 Node가 서버 요청에 자동으로 붙이는 메타데이터 때문에 정상 저장이 거절되는 문제도 드러났다. 브라우저 로그인 요청과 일반 BFF만 확인했다면 놓칠 수 있는 경로였다.

모바일에서는 관리자 메뉴가 고정된 채 따라와 저장 버튼을 가렸다. 테스트에 강제 클릭을 넣지 않고 좁은 화면에서 메뉴가 함께 스크롤되도록 고쳤다. 편집 화면에서 실제로 저장하는 흐름을 검증해야 하는 이유가 두 군데에서 나왔다.

### 테스트 개수를 여러 곳에 옮겨 적지 않게 했다

문서와 소개 화면에 테스트 수를 각각 적다 보니 숫자가 어긋나 CI가 실패했다. 이제 전체 Spring 테스트와 웹 단위 테스트를 실행한 결과에서 JSON과 문서를 함께 만든다. 화면도 그 JSON을 읽는다. 부분 테스트 결과로 전체 수치를 갱신하지 않도록, 갱신 명령 자체가 전체 실행을 수행하게 했다.

9월 9일 전체 결과는 Spring 291개와 웹 147개, 합계 438개였다. 9월 10일 TLS 검증을 추가한 전체 기록은 Spring 294개와 웹 147개, 합계 441개다. Python 서비스와 브라우저 E2E는 이 합계에서 제외한다. Python 서비스는 별도 실행에서 결제 17개, 배송 14개, 파트너 4개가 통과했다. **범위를 바꿔 합계가 작아지는 것은 테스트가 줄었다는 뜻이 아니다.** 무엇을 센 숫자인지 밝히는 편이 여러 종류를 한데 더한 큰 숫자보다 낫다고 봤다. CI는 실제 보고서와 기록의 수가 다르면 갱신을 요구한다.

### 위키 본문을 JavaScript 문자열 밖으로 꺼냈다

위키 89편이 시드 스크립트의 문자열에 들어 있었다. 글에서 쓴 백틱이 실행 코드의 문법을 깨뜨릴 수 있어 Markdown 작성에도 제약이 있었다. 본문은 글별 Markdown 파일로, 제목·태그·탭·순서는 별도 메타데이터로 옮겼다.

시드와 export, 일관성 검사가 같은 로더를 사용하게 했다. 코드를 정규식으로 읽어 원고를 추측하던 경로도 함께 없앴다. 배포할 때는 검증한 원고를 실행 코드와 단일 파일로 묶으므로 기존 전달 경로에서 파일이 빠지지 않는다.

분리 전후에 89편의 본문과 메타데이터를 전부 비교했다. **내용은 완전히 같았고 export 차이도 없었다.** 로컬 시드를 다시 실행했을 때 변경할 글은 0편이었다. 구조를 바꾼 일이 운영 원고를 다시 쓰는 일로 번지지 않는 것을 확인했다.

## 9월 10일에는 준비한 설정을 실제 운영 연결로 바꿨다

전용 Redis가 떠 있다는 사실만으로 전환을 끝냈다고 쓸 수는 없었다. 앱은 여전히 옛 주소를 사용하고 있었기 때문이다. 앱 쓰기를 멈추고 기존 Pod가 모두 종료된 것을 확인한 뒤, 보안 키와 일반 캐시를 각각 새 저장소로 옮겼다. 실제 전환 시점의 보안 키는 0개였다. 그래서 TTL 보존은 운영에서 키를 잃지 않았다는 확인과, 실제 Redis를 사용하는 별도의 이전 테스트 8개로 나누어 검증했다.

중간에 안전 검사가 한 번 전환을 막았다. 앞선 전송용 Pod가 종료 중인데 다음 이전을 시작했기 때문이다. 검사 조건을 느슨하게 만들지 않고 임시 Pod의 종료까지 기다리도록 고쳤다. 실패한 시도에서는 원본 앱을 다시 켰고, 성공한 시도에서만 연결 설정을 바꿨다.

캐시 Redis에도 인증을 붙였다. 보안 Redis는 `noeviction`과 매 쓰기의 AOF 동기화, 캐시는 `allkeys-lru`와 주기적인 AOF 동기화를 사용한다. 둘의 데이터 손실 허용 범위가 다르기 때문이다. 새 연결로 앱 2개가 기동한 뒤 관리자 OTP 로그인과 관리 API 접근이 성공했고, 다른 출처의 변경 요청은 거절됐다. 로그아웃한 쿠키를 다시 보내도 인증과 관리 API 접근이 거절되는 것까지 확인했다.

### 검색 서버는 암호를 넣는 것과 암호를 안전하게 보내는 것을 함께 바꿨다

네트워크 정책은 연결할 수 있는 Pod를 줄이지만, 허용된 Pod가 침해되었을 때 요청자의 권한까지 구분하지는 않는다. 반대로 HTTP에 비밀번호만 붙이면 전송 구간을 보호하지 못한다. 그래서 검색 서버의 인증과 TLS, 앱의 CA 신뢰·호스트 이름 검증을 함께 구성했다. 인증서 검증을 끄는 우회는 쓰지 않았다.

앱 계정은 게시판과 위키의 두 인덱스만 다룬다. 비활성 검색 서버에 게시판 100,007건과 위키 89건을 복사하고 건수를 대조했다. 최종 전환 전에는 양쪽 인덱스의 변경 이력을 확인해, 복사가 끝난 뒤 변경되지 않은 경우에만 결과를 재사용했다.

무인증 요청은 401, 다른 인덱스와 보안 관리 API는 403이었다. 필요한 문서 쓰기·검색·갱신은 성공했고 시험 문서는 지웠다. 새 앱의 공개 검색도 정상 응답했다. 이전 무인증 Redis와 검색 서버는 연결 확인 후 내려 두고, 원본 저장 공간은 복구용으로 보존했다.

## 백업은 파일 목록에서 앱의 이미지 응답까지 확인했다

기존 MinIO 내부 파일 사본을 같은 버전의 서버에 넣었을 때 버킷과 파일 목록은 보였지만 일부 이미지는 읽히지 않았다. 이 결과만으로 원인을 확정하지는 않았다. 다만 목록 조회만으로 복원 성공이라고 판단할 수 없다는 점은 분명했다.

객체 API로 파일을 내려받는 백업으로 바꾼 뒤, 격리된 MinIO에 **42개 객체, 9,232,476바이트를 복원하고 모든 SHA-256을 대조했다.** 이어 사용자·권한과 버킷 설정도 암호화해서 백업했다. [MinIO의 IAM 내보내기](https://min.io/docs/minio/linux/reference/minio-mc-admin/mc-admin-cluster-iam-export.html)와 [버킷 설정 내보내기](https://min.io/docs/minio/linux/reference/minio-mc-admin/mc-admin-cluster-bucket-export.html)는 객체 바이트와 별개인 복구 대상이다.

그 사본을 다시 가져와 앱 계정으로 이미지를 읽었다. 같은 계정이 백업 버킷에는 접근하지 못하는 것도 확인했다. 마지막에는 복원한 PostgreSQL과 MinIO에 실제 Spring 앱을 붙였다. 운영망과 연결하지 않고 호스트 포트도 열지 않은 환경에서 **이미지 API 17개의 응답이 복원 DB의 체크섬과 모두 일치했다.**

이 복원 실험 전체는 준비된 이미지가 있는 환경에서 약 32.1초였다. 새 장비를 구하고 운영 DNS와 프런트엔드까지 복구하는 시간은 아니다. 버킷은 버전 관리가 중지된 상태였고, 추가 버전 목록 검사에서 비어 있지 않은 과거 version ID는 없었다. 삭제 마커와 버전 목록도 기록했지만, 현재 객체 사본으로 삭제된 옛 파일까지 되살릴 수 있다는 뜻은 아니다.

매일 04:30 맥북에 DB 세 개·객체·권한·클러스터 설정의 암호화 사본을 만드는 일정도 등록하고 첫 실행을 확인했다. 실패하면 로컬 알림과 실패 상태를 남긴다. 맥이 깨어 있고 SSH 인증이 유효해야 하므로 **24시간은 목표 RPO**다. 마지막 성공 시각을 보지 않고 매일 백업된다고 가정하지 않는다. 장비 전체 복구의 RTO는 실제 장애 훈련으로 계속 측정할 운영 지표다.

## Secret은 저장할 때 암호화하고 키가 있는 사본으로 복구했다

Kubernetes Secret의 base64 표현은 암호화가 아니다. API 접근을 막아도 데이터 저장소 사본을 읽을 수 있으면 값이 드러날 수 있다. 따라서 Secret 저장 암호화를 켜되, 복구에 필요한 키를 함께 확보해야 했다. 키 없이 암호문만 남기면 정상 사용자도 복원하지 못한다.

[k3s의 기존 클러스터 활성화 절차](https://docs.k3s.io/cli/secrets-encrypt#enable-secrets-encryption-on-an-existing-cluster)에 따라 설정과 재시작, 키 회전·재암호화, 최종 재시작을 진행했다. 직후 현재 Secret 레코드 101개가 모두 암호문으로 저장되었고, 상태는 `Enabled`, `reencrypt_finished`, 서버 키 해시 일치였다. 이전 SQLite 페이지의 흔적까지 지워졌다는 주장은 하지 않는다.

데이터 저장소의 일관된 사본과 서버 토큰·암호화 키·TLS 설정을 함께 암호화해 장비 밖에 보관했다. 같은 k3s 버전을 외부망 없는 환경에서 기동해 복원한 Secret 값을 운영과 비교했다. 암호화 이후 실험에서는 99개가 모두 일치했다. 차이 2개는 실험에서 Traefik을 끄면서 정리된 차트 설정 Secret이었고, 나머지 값이 달라진 것은 없었다.

## 배포 러너가 개인 계정의 관리자 권한을 가져가지 않게 했다

원래 러너는 관리자 kubeconfig가 있는 개인 계정으로 실행 중이었다. 그 계정에 제한된 kubeconfig를 하나 더 만들어 주어도 옛 관리자 파일을 읽을 수 있으면 경계가 되지 않는다. CI 작업 하나가 침해되었을 때 클러스터 전체로 이어질 수 있다고 판단한 이유다.

러너를 별도 OS 사용자로 옮기고 관리자 홈과 Docker 소켓 접근을 막았다. 앱 배포용 Kubernetes 권한도 관리하는 네임스페이스 안으로 줄였다. 실제 새 계정으로 앱 매니페스트 검증은 통과했고, 시스템 네임스페이스의 Secret과 클러스터 권한·노드·RBAC 조작은 거절됐다.

배포가 Job을 만들 수 있다는 것은 해당 네임스페이스의 Secret을 작업에서 사용할 수도 있다는 뜻이다. 그래서 이것을 완전한 비밀 격리로 설명하지 않는다. 대신 PodSecurity 정책으로 특권 Pod와 호스트 경로 사용을 막고, 시스템 영역으로 권한이 넘어가는 범위를 줄였다.

Helm·Secret·RBAC 초기 설정은 관리자 작업으로 분리했다. 관리자가 인프라를 적용하고 검증한 지문과 저장소의 지문이 다르면 일상 배포는 멈춘다. 일반 러너가 승인 기록을 직접 고칠 수는 없다.

이 과정에서도 두 가지 실행 환경 차이를 잡았다. 첫 배포는 러너에 Node가 없어 위키 동기화 전에 실패했고 자동 롤백됐다. Node 설치를 배포 단계에 명시했다. 러너를 옮길 때는 실행 파일 링크가 옛 홈을 가리켜 시작하지 못했다. 관리자 홈의 접근 제한을 풀지 않고 새 경로로 링크를 옮겼다.

또 한 번은 배포 권한에 백업 작업 이름을 잘못 적은 오류가 드러났다. 앱과 검색 서버 갱신까지 통과했지만, 콘텐츠 쓰기 전 백업 조회가 거절되어 자동 롤백됐다. 실제 작업 이름을 바로잡고 **앱을 변경하기 전에 백업 권한도 검사하도록** 옮겼다. 권한 거절이 작동한 사실과, 필요한 권한을 잘못 구성해 배포를 실패시킨 설정 오류는 따로 기록한다.

### 서버 안의 로그인 성공과 공개 로그인 성공은 달랐다

쓰기 요청을 추가로 확인하면서 롤백된 구형 프런트엔드가 새 백엔드의 요청 표식을 보내지 못하는 조합도 발견했다. 호환되는 프런트엔드 이미지로 맞춘 뒤 일반 쓰기는 돌아왔지만, 브라우저처럼 Origin을 보낸 요청은 여전히 403이었다.

방문자는 HTTPS로 접속했는데 Tunnel과 프록시 뒤에서는 HTTP 연결로 전달되었다. 그 내부 프로토콜을 외부 주소의 기준으로 쓰면서 정상 출처까지 거절한 것이다. Origin 검사를 끄면 다른 출처를 막으려던 목적도 잃으므로, 공개 두 도메인의 프록시 설정에서 외부 HTTPS를 정확히 전달하도록 고쳤다.

[Cloudflare의 방문자 프로토콜 헤더](https://developers.cloudflare.com/fundamentals/reference/http-headers/)로 HTTP 요청을 먼저 HTTPS로 전환하고, 정상 공개 경로에는 [Traefik의 요청 헤더 설정](https://doc.traefik.io/traefik/middlewares/http/headers/)을 적용했다. 공개 접근이 Cloudflare Tunnel을 거치고 원본 직접 접근은 막혀 있는 현재 구조를 전제로 한다. 임의의 요청 헤더를 어느 환경에서나 신뢰해도 된다는 뜻은 아니다.

수정 뒤 두 사이트의 HTTP는301, HTTPS는200이었다. 방문자 헤더를 위조한 HTTP 요청도301로 전환되었다. 정상 Origin의 쓰기는200, 다른 Origin은403이었다. 마지막에는 **공개 주소의 BFF를 거쳐 OTP 로그인·관리 API·로그아웃·폐기 쿠키 재사용 거절까지 9개 검사를 통과했다.** 이후 배포 검사에도 Origin을 포함한 실제 쓰기를 넣었다. 조회 페이지와 서버 내부 로그인만 확인하면 이 실패를 놓칠 수 있었다.

9월 10일 추가 검사에서는 파트너 시뮬레이터의 httpx2/httpcore2 문제가 검출됐다. 서비스 세 개의 최소 버전과 잠금 파일을 2.12.0으로 갱신하고 Python 테스트 35개를 다시 실행했다. 이후 런타임 이미지 다섯 종류와 Java·Node·Python 의존성, 비밀정보 검사가 모두 통과했다. [실행 기록](https://github.com/jaymunsh/jay-wiki/actions/runs/34446289898)으로 어떤 소스와 검사 기준의 결과인지 남겼다.

첫 글의 수치는 당시 검사 결과다. 수정본이 나오거나 잠금 파일이 바뀌면 다시 확인해야 하므로, 예전의 “수정본 없음”을 계속 손댈 수 없다는 뜻으로 사용하지 않는다.

## DB를 보는 SSH 터널은 살리고 직접 포트 접근을 막았다

Tailscale의 실제 수신 정책은 모든 포트를 허용하고 있었다. 여기서 무작정 막으면 맥북의 운영 DB 접속도 끊을 수 있었다. Beekeeper에 저장된 설정을 보니, DB 포트로 직접 붙는 방식이 아니라 **Tailscale의 SSH 터널을 거쳐 클러스터 내부 DB에 붙는 방식**이었다.

미니 PC에 소유 기기의 SSH만 허용하는 별도 호스트 규칙을 적용했다. Tailscale 중앙 ACL 자체를 바꿨다고 적지는 않는다. 맥북에서 SSH 연결과 동일한 방식의 PostgreSQL 터널 응답을 확인했고, DB·Redis·Kubernetes API·MinIO·검색 포트의 직접 연결은 차단되었다. 새 기기를 등록하면 이 허용 목록도 검토해야 한다.

SSH의 비밀번호·root 로그인 차단과 호스트 방화벽의 기본 수신 차단도 실제 설정으로 확인했다. 이어 집 밖의 GitHub 실행 환경에서 운영 서버의 포트 7개를 검사했으며 모두 연결 응답이 없었다. 타임아웃만으로 어느 방화벽이 막았는지까지는 확정할 수 없으므로, **외부 실행 지점에서 직접 도달하지 못했다는 결과**로 기록한다. 공개 HTTP 경로의 무인증 차단 검사도 별도로 통과했다.

| Tailscale·외부 경계 | DB 관리 연결을 보존하며 직접 접근을 줄인다 | DB SSH 터널 정상, 직접 서비스 포트 차단, 외부 포트 검사 |
| 운영 콘텐츠 기준 해시 | 관리 화면에서 고친 글을 낡은 초안이 덮지 않게 한다 | 동일 본문만 비교 API에서 기준을 받고 다른 초안은 보존 |

최종 [자동 배포 실행](https://github.com/jaymunsh/jay-wiki/actions/runs/34451516190)은 전체 테스트, 이미지 빌드, 제한된 러너의 배포, 외부 브라우저 검사까지 모두 성공했다. 앱 다섯 개가 최종 이미지로 정상 실행되고, 인증 저장소 세 개는 Ready이며 옛 무인증 저장소 두 개는 내려가 있다. 위키 89편은 원고와 이미 같아 변경하지 않았다.

마지막에는 실제 Chromium 로그인 폼에서도 로그인·세션 유지·로그아웃을 확인했다. 인증 쿠키는 Secure·HttpOnly·SameSite=Lax였고, 관리 화면 API가 새 보안 검색 서버를 가리키는 것도 확인했다. 이 글은 로컬 블로그에 반영했으며 운영 글을 자동 공개하는 목록은 비워 두었다.

## 완료 목록보다 어떤 실패를 확인했는지가 남았다

후속 작업도 Astra와 함께 진행했다. 특히 인상적이었던 것은 코드 수정에서 운영 전환, 백업 복원, 실제 브라우저 검증까지 이어지는 작업을 함께 풀어 갈 수 있었다는 점이다. 중간에 실패와 재작업도 있었지만, 원인을 좁혀 수정하고 다시 확인하는 데 큰 도움을 받았다. 이번 작업에서 체감한 강점은 여러 계층에 걸친 문제를 실제 동작 확인까지 이어 가는 능력이었다.

실제 편집에서는 정상 저장이 403으로 막혔고, 모바일에서는 메뉴가 저장 버튼을 가렸다. 복구에서는 목록이 보이는 객체를 읽지 못했고, 배포에서는 Node가 없어서 멈췄다. 결과를 끝까지 확인하니 코드와 설정 파일만 봤을 때 놓친 문제가 드러났다.

이번 작업을 안전하다는 영구 판정으로 남기지는 않는다. 매일 백업의 마지막 성공 시각, 인증서와 자격증명의 만료·회전, 의존성 수정본, 기기 허용 목록은 계속 확인해야 한다. 한 번 수행해야 할 전환과 반복해서 유지해야 할 운영 작업을 나누어 기록하는 것이 이번 정리의 마지막 기준이다.
