게시글 목록에 페이징은 언젠가 반드시 필요하다. 글이 계속 쌓이는데 매번 전부 내려보내는 구조는 어느 지점에서 반드시 무너진다. 이 전제는 이 글에서도 유지한다. **뒤에서 계산하겠지만 이 블로그도 약 180편에서 지금 방식의 수명이 끝난다.**

다만 "페이징이 필요하다"는 문장은 실제로 두 가지 결정을 뭉쳐 놓은 것이다.

1. 목록을 페이지로 나눠 보여 줄 것인가
2. 나누는 일을 **어디서** 할 것인가

첫 번째는 논쟁의 여지가 없다. 문제는 두 번째다. 그리고 이 두 번째를 정하려면 지금 무엇이 병목인지 알아야 하는데, 그것을 재 보지 않은 채로 "정석이 DB니까 DB로"라고 정하면 이득 없는 변경에 값을 치르게 된다. 이 글은 그 값을 재 본 기록이다.

2026년 8월 29일 기준이고, 운영에 35편, 로컬에 38편이 있는 상태에서 측정했다.

## 자르는 자리가 둘이라 선택지도 둘이다

이 블로그의 목록은 한 페이지 30편으로 나뉘어 있고, 전체·카테고리·태그·검색 네 화면이 모두 페이저를 그린다. 2페이지도 실제로 존재한다. 즉 **페이징은 이미 적용된 상태**다.

없는 것은 페이징이 아니라 DB에서 자르는 질의다. 지금은 서버가 전체 목록을 주고 화면이 30편만 그린다.

| | 화면에서 자르기 (현재) | DB에서 자르기 |
|---|---|---|
| 질의 | 전체 조회 | `LIMIT` / `OFFSET` |
| 응답 | 전체 목록 | 한 페이지 분량 |
| 응답 크기 | 편수에 비례해 늘어남 | 편수와 무관하게 일정 |
| 서버 메모리 | 전체를 담았다가 직렬화 | 페이지 분량만 |
| 엔드포인트 수 | 하나 | 전체용과 페이지용 둘 |
| 전체 목록이 필요한 소비자 | 그대로 쓴다 | **따로 챙겨야 한다** |
| 총 편수 표시 | 배열 길이 | `count` 질의가 따로 필요 |

마지막 세 줄이 이 글에서 다룰 내용이다. DB 페이징은 응답을 가볍게 만드는 대신 **전체 목록을 전제로 돌아가던 것들을 떼어 놓는다.**

## 지금 목록이 느린 이유부터 확인했다

먼저 운영 API를 스무 번 불렀다. 명령줄에서 잰 값이다.

| 항목 | 값 |
|---|---:|
| 응답 크기 | 19,857 B (35편) |
| 중앙값 | 0.893 s |
| 최소 / 최대 | 0.634 s / 4.392 s |
| 표준편차 | 1.048 s |

35편에 19,857바이트니 **편당 약 570바이트**다. 응답에 본문은 없고 제목·요약·카테고리·표지 주소·날짜만 들어 있다.

두 가지가 걸린다. 1초에 가까운 시간에 비해 데이터가 지나치게 가볍다는 것, 그리고 **표준편차가 중앙값과 맞먹는다**는 것이다. 같은 요청이 어떤 때는 0.6초, 어떤 때는 4.4초에 온다면 원인이 데이터 처리 쪽에 있을 리 없다.

## 같은 질의가 로컬에서는 17밀리초였다

같은 Spring 애플리케이션을 로컬에서 직접 불렀다. 이쪽은 글이 38편이라 응답이 더 크다.

| 구분 | 편수 | 응답 크기 | 소요 시간 |
|---|---:|---:|---:|
| 로컬 Spring 직접 | 38 | 21,603 B | 0.016 ~ 0.027 s |
| 운영 Spring (Cloudflare 경유) | 35 | 19,857 B | 0.893 s (중앙값) |

**같은 질의가 로컬에서 17밀리초다.** 데이터는 오히려 로컬이 더 많다. 이 17밀리초 안에 DB 조회와 JPA 매핑, DTO 변환, JSON 직렬화가 전부 들어 있다.

그러면 나머지는 어디서 생기는가.

## 브라우저에서 재니 337밀리초였고, 그중 19밀리초만 내려받기였다

명령줄 측정에는 함정이 있었다. `curl`은 요청마다 새 연결을 맺어 TLS 핸드셰이크를 처음부터 다시 한다. 브라우저는 한 번 맺은 연결을 계속 쓰므로 그 비용을 내지 않는다.

실제 방문자 쪽에서 개발자 도구로 잰 값은 이렇다.

| 구간 | 시간 | 무엇인가 |
|---|---:|---|
| Queueing · Stalled · Request sent | 0.62 ms | 연결이 이미 있어 거의 0이다 |
| **Waiting for server response** | **317.71 ms** | 요청이 오리진까지 갔다 오는 시간 |
| Content Download | **18.95 ms** | 본문을 받는 시간 |
| 합계 | 337.28 ms | |

**전체의 94%가 서버 응답 대기이고, 본문을 받는 데 쓰인 시간은 19밀리초다.** 응답 크기가 관여하는 구간은 마지막 줄 하나뿐이다.

앞의 명령줄 측정에서 연결을 재사용해 다시 재 봤을 때 327밀리초가 나왔는데, 브라우저 실측 337밀리초와 거의 같다. **명령줄의 0.9초는 측정 방식이 만든 값이고, 방문자가 겪는 값은 0.34초다.**

## 요청이 태평양을 두 번 건너고 있었다

317밀리초가 어디로 가는지는 응답 헤더에 적혀 있었다.

```text
Cf-Ray: a329bb443f6cd8c2-SJC
```

끝의 `SJC`는 요청이 도달한 Cloudflare 엣지다. **한국에서 접속해도 미국 서부 엣지로 붙는다.** 오리진인 miniPC는 한국에 있으므로 경로는 이렇게 된다.

~~~mermaid
flowchart TB
    A[방문자 · 한국] --> B[Cloudflare 엣지 · 미국 서부]
    B --> C[오리진 miniPC · 한국]
    C --> B2[엣지 · 미국 서부]
    B2 --> D[방문자 · 한국]
~~~

한 번의 요청에 태평양을 두 번 건넌다. 317밀리초의 정체가 이것이고, 응답을 아무리 가볍게 만들어도 이 구간은 그대로다.

## 그래서 DB 페이징으로 줄어드는 몫을 계산했다

DB 페이징을 넣으면 응답에서 5편이 빠진다. 35편 중 30편만 내려오기 때문이다.

| 항목 | 현재 | DB 페이징 적용 시 |
|---|---:|---:|
| 응답 크기 | 19,857 B | 약 17,000 B (-14%) |
| 내려받기 구간 | 18.95 ms | 약 16 ms |
| 서버 응답 대기 | 317.71 ms | 317.71 ms (그대로) |
| **총 소요 시간** | 337.28 ms | **약 334 ms (-1%)** |

절약되는 것은 3밀리초 남짓, 전체의 1% 정도다. 응답을 아예 0바이트로 만들어도 337밀리초 중 19밀리초만 사라진다. **지금 이 목록의 지연은 데이터 양과 거의 무관하다.**

## 전체 목록을 전제로 도는 곳이 셋 있다

이득이 없다는 것만으로 결론은 나오지만, 옮길 때 무엇을 함께 해야 하는지는 미리 알아 둘 값어치가 있다. 코드에서 전체 목록을 받아 쓰는 곳을 찾으니 셋이었다.

먼저 짚어 둘 것이 있다. **셋 다 오류를 내지 않는다.** 응답이 30편으로 잘려도 예외가 나거나 화면이 멎지 않고 조용히 빠진다. 그래서 옮기는 작업 자체보다 이 증상들을 미리 아는 쪽이 중요하다.

그리고 셋 모두 해결책이 있다. 어렵지도 않다.

### 사이트맵은 전체 목록 API를 그대로 쓰면 된다

`sitemap.ts`는 받아 온 목록을 그대로 URL 항목으로 펼친다.

```ts
...posts.map((post) => ({
  url: blogAbsoluteUrl(blogPostHref(post.id, post.slug)),
  lastModified: post.publishedAt ? new Date(post.publishedAt) : undefined,
}))
```

30편만 오면 사이트맵에 30개 URL만 실리고, 나머지 글은 검색 엔진에게 존재하지 않는 글이 된다. 사이트맵은 사람이 볼 일이 없어서 이 누락은 색인이 줄어든 뒤에야 드러난다.

여기서 판단이 한 번 갈렸다. **처음 이 목록을 뽑을 때는 사이트맵을 DB 페이징의 가장 큰 걸림돌로 지목했다.** 색인이 조용히 줄어드는 증상이라 위험도가 높다고 봤기 때문이다.

다시 보니 그렇지 않았다. **DB 페이징을 넣는다고 기존 전체 목록 API를 없앨 이유가 없다.** 페이지용 엔드포인트를 하나 더 두고, 사이트맵은 지금 쓰는 전체 목록을 계속 쓰면 그만이다. 사이트맵은 크롤러가 하루에 몇 번 부르는 것이라 20KB를 통째로 줘도 부담이 아니고, 사람이 기다리는 화면도 아니다.

"페이징을 넣으면 모든 소비자가 페이지를 받아야 한다"고 전제한 것이 착각이었다. 걸림돌로 보였던 것이 사실은 **아무것도 안 해도 되는 자리**였다. 더 줄이고 싶다면 id·slug·발행일만 담는 경량 응답을 두는 선택지가 남아 있지만, 그것도 지금 필요한 일은 아니다.

### 공유 카드는 조회수를 안 올리는 단건 조회를 만들면 된다

이쪽이 가장 알아채기 어려운 자리다. `opengraph-image.tsx`는 단건 조회 API를 쓰지 않고 목록에서 글을 찾는다.

```tsx
// 단건 조회 API 는 조회수를 올린다. 크롤러가 카드를 받을 때마다 오르면 통계가 망가지므로 목록에서 찾는다.
const post = (await getBlogPosts()).find((p) => String(p.id) === id);
const src = blogAbsoluteUrl(post?.coverImageUrl ?? '/og-image-1200x630.png');
```

목록에 없는 id를 찾으면 `find`가 `undefined`를 주고, 옵셔널 체이닝이 그것을 받아 기본 이미지로 넘어간다. 오류도 로그도 없다. 31번째 이후 글을 공유하면 표지 대신 사이트 기본 카드가 나가는데, 이것을 알아차리려면 그 글을 실제로 어딘가에 공유해 봐야 한다.

**단건 조회로 바꾸면 되는 것 아니냐**는 것이 자연스러운 질문이고, 답은 그렇다는 쪽이다. 걸림돌이던 조회수 문제도 실제 코드를 보면 생각보다 작다.

```java
@GetMapping("/posts/{id}")
public BlogPostDto post(@PathVariable Long id, HttpServletRequest request) {
    BlogPostDto found = postService.get(id);
    stats.recordView(id, ClientIpResolver.resolve(request), request.getHeader("referer"),
            request.getHeader("user-agent"));
    return found;
}
```

**조회수를 올리는 것은 서비스가 아니라 컨트롤러다.** `postService.get(id)`은 글만 읽어 오고, 통계는 그 다음 줄에서 따로 기록한다. 그러니 `recordView`를 부르지 않는 매핑을 하나 더 두면 그만이다. 서비스도 DTO도 그대로 재사용한다.

카드에 필요한 것이 표지 주소 하나뿐이므로, 본문까지 실어 보내지 않는 가벼운 응답으로 두면 지금보다 오히려 가벼워진다. 목록 전체를 받아 배열을 훑던 일이 id 하나로 바로 찾는 일이 되기 때문이다.

### 관련 글은 전용 질의를 두는 편이 지금보다 낫다

글 하단의 관련 글은 같은 카테고리 목록을 통째로 받아 다섯 편을 고른다.

```tsx
post.categorySlug ? getBlogPostsByCategory(post.categorySlug) : Promise.resolve([])
...
const others = sameCategory.filter((p) => p.id !== post.id).slice(0, 5);
```

카테고리 API도 페이지 형태가 되면 한 카테고리에 30편이 넘을 때부터 뒤쪽 글이 후보에서 빠진다. 지금은 가장 큰 카테고리가 열 편 남짓이라 여유가 있다.

**해결은 `/posts/{id}/related?limit=5` 같은 전용 경로를 두는 것이다.** DB에서 같은 카테고리 다섯 편만 뽑아 오면 되므로, 전체를 받아 자바스크립트에서 자르는 지금보다 구조가 낫다. 카테고리에 글이 몇 편이든 응답이 다섯 편으로 고정된다.

### 정리

| 소비자 | 잘리면 생기는 일 | 해결 | 드는 값 |
|---|---|---|---|
| 사이트맵 | 31번째 이후 URL 누락 | 전체 목록 API를 계속 쓴다 | **없음** |
| 공유 카드 | 기본 이미지로 대체 | 조회수를 안 올리는 단건 조회 추가 | 컨트롤러 매핑 하나 |
| 관련 글 | 후보가 줄어듦 | 관련 글 전용 질의 추가 | 질의 하나 |

셋 중 어느 것도 테스트가 잡아 주지 않는다는 점만은 그대로다. 그래서 옮길 때는 이 셋을 목록으로 들고 하나씩 확인해야 한다.

## 그런데도 지금 옮기기로 했다

여기까지 재고 나면 "지금은 그냥 두자"가 자연스러운 결론이다. 실제로 처음에는 그렇게 정리했다. 옮길 기준을 숫자로 적어 두고, 그 선에 닿으면 그때 옮기자는 쪽이었다.

| 신호 | 기준 | 현재 값 |
|---|---|---|
| 목록 응답 크기 | 100 KB 초과 | 19.9 KB |
| 편수 환산 | 약 180편 | 35편 |
| 서버 처리 시간 | 100 ms 초과 | 약 17 ms |

그런데 이 표를 적고 나서 질문이 하나 남았다. **어차피 180편에서 반드시 해야 하는 일이라면, 35편인 지금 하는 것과 180편일 때 하는 것 중 어느 쪽이 싼가.**

| | 지금 옮기기 | 180편에서 옮기기 |
|---|---|---|
| 손봐야 할 소비자 | 셋 | 셋 + 그 사이 늘어난 것 |
| 잘못 옮겼을 때 | 35편 중 5편이 안 보인다 | 180편 중 150편이 안 보인다 |
| 작업 시점의 압박 | 없다 | 이미 느려진 뒤라 급하다 |
| 성능 비교 기준선 | **오늘 잰 값이 있다** | 옮기기 전 값을 새로 재야 한다 |

넷 다 지금이 유리하다. 특히 마지막 줄이 결정적이었다. **오늘 잰 19,857바이트와 950밀리초가 이미 기준선 노릇을 한다.** 지금 옮기면 같은 조건에서 전후를 비교할 수 있고, 180편까지 기다리면 그 사이 하드웨어도 네트워크도 바뀌어 비교가 어려워진다.

정리하면 이 판단은 "지금 빨라지니까 하자"가 아니다. 측정이 말한 대로 지금 당장 빨라지는 것은 없다. **피할 수 없는 작업을 값이 가장 쌀 때 치르자는 쪽에 가깝다.** 그리고 그 작업이 만들어 낼 구조가 지금 구조보다 낫다는 판단이 함께 있다.

## 목록 조회 API 하나를 네 화면이 함께 쓰게 만든다

지금은 목록을 주는 경로가 넷으로 갈라져 있고, 자르는 일은 화면이 각자 한다.

| 화면 | 지금 부르는 것 | 자르는 곳 |
|---|---|---|
| 전체 | `/posts` | 화면 |
| 카테고리 | `/categories/{slug}/posts` | 화면 |
| 태그 | `/tags/{name}/posts` | 화면 |
| 검색 | `/search?q=` | 화면 |

넷 다 "조건에 맞는 글을 페이지 단위로 달라"는 같은 요청이다. 그래서 조건만 다른 하나의 질의로 묶는다.

```text
GET /api/blog/posts?page=1&size=30
GET /api/blog/posts?category=tech-lab&page=1&size=30
GET /api/blog/posts?tag=mlx&page=1&size=30
GET /api/blog/search?q=페이징&page=1&size=30
```

검색만 경로를 따로 두는 이유가 있다. 검색 결과에는 본문에서 뽑은 스니펫이 붙어 응답 항목의 모양이 다르기 때문이다. **조건과 페이지 규칙은 공유하고, 항목의 타입만 갈린다.**

## 페이지 크기를 나중에 고르게 하려면 지금 구조를 정해야 한다

지금은 한 페이지 30편이 상수로 박혀 있다. 나중에 10편·30편·50편 보기를 고르게 하려면 그 값이 요청을 타고 들어와야 하는데, 여기서 그냥 숫자를 받으면 곤란해진다.

`?size=100000` 한 번이면 페이징이 통째로 무력화되기 때문이다. 페이징을 넣은 이유가 전체를 한 번에 안 주려는 것인데, 크기를 자유롭게 열어 두면 그 문을 다시 여는 셈이다.

그래서 **크기를 자유로운 정수가 아니라 정해진 선택지로 다룬다.**

| 다루는 방식 | 문제 |
|---|---|
| `int size` 를 그대로 받는다 | 임의의 큰 값으로 전체를 긁을 수 있다 |
| 받되 상한을 건다 | 상한 검사가 호출부마다 흩어진다 |
| **허용값을 열거형으로 둔다** | 값이 스스로를 검증한다. 화면의 선택지와 서버의 허용값이 같은 자리에서 온다 |

세 번째를 고른다. 열거형에 10·30·50을 두고, 목록에 없는 값이 오면 기본값으로 떨어뜨린다. 나중에 "20편 보기"를 추가할 때 고칠 자리도 그 열거형 하나다.

조건도 같은 식으로 묶는다. 카테고리·태그·검색어·페이지·크기를 인자로 늘어놓으면 호출부마다 순서를 맞춰야 하고, 조건이 하나 늘 때마다 서명이 바뀐다. 이것들을 요청 객체 하나로 묶으면 새 조건이 생겨도 객체 안쪽만 는다.

응답도 마찬가지다. 항목 배열만 주면 화면이 총 편수와 마지막 페이지를 알 수 없으므로, 항목과 페이지 정보를 함께 담는 껍데기를 하나 두고 목록과 검색이 같이 쓴다. 안에 담기는 타입만 다르고 껍데기는 하나다.

정리하면 새로 만드는 것은 셋이다.

| 무엇 | 하는 일 | 왜 따로 두나 |
|---|---|---|
| 조회 조건 객체 | 카테고리·태그·검색어·페이지·크기를 묶는다 | 조건이 늘어도 서명이 안 바뀐다 |
| 페이지 크기 열거형 | 10·30·50만 허용한다 | 크기를 열어 두면 페이징이 무력해진다 |
| 페이지 응답 껍데기 | 항목과 총 편수·현재 페이지·마지막 페이지를 함께 준다 | 목록과 검색이 같은 모양으로 받는다 |

화면 쪽에서 지금 쓰는 페이저 컴포넌트와 주소 만드는 함수는 그대로 쓴다. 바뀌는 것은 **자르는 일을 화면이 하느냐 서버가 하느냐**뿐이고, 페이저가 그려지는 방식은 같다.

## 옮기고 나서 다시 쟀다

설계한 대로 만들고 같은 조건에서 다시 쟀다. 로컬 서버 기준이고, 이 시점의 글은 39편이다.

| 대상 | 응답 크기 | 소요 시간 |
|---|---:|---:|
| 전체 목록 API (39편) | 22,194 B | 0.018 ~ 0.028 s |
| 페이지 API (size=30) | **17,566 B** | 0.018 ~ 0.028 s |
| 페이지 API (size=10) | **6,005 B** | 0.012 ~ 0.017 s |

**응답은 21% 작아졌고 시간은 그대로다.** 앞에서 계산한 그대로다. size를 10으로 줄이면 시간이 12밀리초로 내려가는데, 이것은 직렬화할 항목이 4분의 1이 되어서지 페이징 자체의 효과라고 보기는 어렵다.

이 결과를 실패로 읽으면 안 된다. 애초에 판정 기준을 이렇게 잡아 두었다.

| 볼 것 | 기대 | 결과 |
|---|---|---|
| 응답 크기 | 편수가 늘어도 고정되는가 | 30편 몫으로 고정됐다 |
| 서버 처리 시간 | 편수와 무관해지는가 | 페이지 크기에만 반응한다 |
| 총 소요 시간 | **거의 그대로일 것이다** | 그대로다 |
| 사이트맵 | 전체 편수를 유지하는가 | 39편 모두 들어 있다 |
| 공유 카드 | 목록 뒤쪽 글도 표지가 나오는가 | 정상으로 그려진다 |

셋째 줄이 예상대로 나온 것이 이번 작업의 결론이다. 여기서 시간이 크게 줄었다면 앞의 측정이 틀렸다는 뜻이므로 오히려 다시 봐야 했다.

바뀐 것은 속도가 아니라 **기울기**다. 지금까지는 글이 한 편 늘 때마다 응답이 570바이트씩 커졌다. 이제 그 증가가 전체 목록 API 쪽에만 남고, 사람이 보는 화면은 몇 편이 쌓이든 30편 몫만 받는다. 180편이 되면 전체 목록은 100KB로 가지만 화면은 여전히 17KB다.

### 사이트맵과 공유 카드는 정말 그대로였다

옮기기 전에 가장 걱정한 자리였는데, 기존 API를 하나도 건드리지 않아 확인할 것이 없었다. 사이트맵은 여전히 전체 목록을 받고, 공유 카드도 같은 목록에서 글을 찾는다. **"아무것도 안 해도 된다"는 판단이 실제로 아무 일도 일어나지 않는 것으로 확인됐다.**

관련 글도 마찬가지다. 카테고리별 전체 목록 API가 살아 있어 그대로 돈다. 전용 질의로 바꾸는 것은 그 API가 페이지가 될 때 할 일이고, 지금은 할 이유가 없다.

### 실제로 시간을 쓴 곳은 따로 있었다

구현 자체보다 오래 걸린 것은 엉뚱한 데였다. 새 엔드포인트가 계속 500을 냈는데, 테스트는 열두 개가 전부 통과하고 컴파일된 클래스에도 매핑이 들어 있었다.

원인은 **낮에 띄워 둔 옛 서버가 8080 포트를 계속 잡고 있었던 것**이다. 새로 띄운 서버는 포트를 못 잡았고, 요청은 전부 낡은 서버로 갔다. 그쪽에는 `/posts/page` 매핑이 없으니 `/posts/{id}`에 잡혀 "page"를 숫자로 바꾸려다 터졌다.

단서는 있었다. `/posts/abc`도 똑같이 500이었다. 매핑이 없는 경로가 아니라 **id 자리에 글자가 들어간 것과 같은 증상**이었으니, 서버가 새 매핑을 모른다는 뜻이었다. 코드를 의심하기 전에 무엇이 그 포트를 잡고 있는지 확인했으면 훨씬 빨랐다.

## 페이징과 별개로, 진짜 병목은 그대로 남는다

317밀리초는 페이징을 옮겨도 1밀리초도 줄지 않는다. 이쪽을 손대는 방법은 하나뿐이다.

응답 헤더가 지금 상태를 그대로 보여 준다.

```text
Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate
Cf-Cache-Status: DYNAMIC
```

**Next 가 캐시 금지를 명시해서 보내므로 Cloudflare 가 손댈 수 없다.** 그래서 모든 요청이 오리진까지 간다.

목록 응답을 엣지에서 캐시하면 태평양 왕복이 두 번에서 한 번으로 준다. 엣지가 가진 것을 바로 주면 되기 때문이다. 317밀리초 중 오리진까지 다녀오는 몫이 사라지므로, 페이징으로 얻은 3밀리초와는 자릿수가 다르다.

문제는 캐시가 낡는 것인데, 이 블로그는 발행 시점을 스크립트가 정확히 알고 있다.

| 방법 | 오리진 왕복이 사라지나 | 낡은 목록이 보이나 | 드는 값 |
|---|---|---|---|
| 시간 기반 만료 | 만료 주기 동안만 | 만료 주기만큼 | 설정 한 줄 |
| 발행 시 캐시 삭제 | 그렇다 | 아니다 | 발행 경로에 호출 하나 |
| Next 경로 재검증 | 아니다 (DB 조회만 준다) | 아니다 | 발행 경로에 호출 하나 |

두 번째가 이 구조에 맞는다. 다만 페이징과는 별개의 작업이라 이번에는 재기만 하고 미룬다. **오늘 잰 337밀리초 중 317밀리초가 여기 걸려 있다는 것을 숫자로 남겨 둔다.**

한 가지는 이미 해결되어 있었다. 처음에는 연결 수립에 309밀리초가 든다고 봤는데, 그것은 `curl` 이 요청마다 새 연결을 맺어서 생긴 값이었다. 브라우저 실측에서 연결 관련 구간은 전부 합쳐 0.62밀리초였고, 응답 헤더에 `alt-svc: h3=":443"` 도 이미 광고되고 있다. **이 축은 손댈 것이 없다.**

## 남은 한계

측정 자체의 한계는 이번에 두 가지를 없앴다. 명령줄 다섯 번으로 잡았던 표본은 스무 번으로 늘렸고, "측정한 자리가 방문자의 자리와 다르다"고 적었던 것은 실제 브라우저 값을 받아 확인하면서 지웠다. **방문자도 같은 미국 서부 엣지를 탄다.** 오히려 명령줄 측정이 연결을 매번 새로 맺어 부풀어 있었고, 그쪽을 실측으로 바로잡았다.

남는 것은 셋이다.

**하루 중 한 시간대에서만 쟀다.** 명령줄 스무 번에서 0.634초부터 4.392초까지 흔들렸는데, 그 폭이 네트워크 상태인지 miniPC 부하인지 터널 쪽인지는 가르지 않았다.

**옮긴 뒤의 운영 값이 없다.** 페이징 후 측정은 전부 로컬 서버에서 한 것이고, 배포 뒤에 같은 자리에서 다시 재야 한다. 다만 응답 크기가 관여하는 구간이 19밀리초뿐이라는 것이 확인됐으므로, 총 시간은 거의 그대로일 것이다.

**곡선이 갈리는 지점을 확인하지 않았다.** 응답 크기가 고정된다는 것은 확인했지만, 180편 근처에서 두 방식이 실제로 갈리는지는 데이터를 채워 재 봐야 안다. 지금은 39편이라 그 지점이 멀다.

페이지 크기를 고르는 화면도 아직 없다. 서버는 10·30·50을 받을 준비가 됐지만 화면에는 선택지를 두지 않았다. 필요해지면 그때 붙인다.
