노치가 있는 MacBook에서 메뉴바는 좁다. Orca, oMLX, Docker Desktop, Tailscale 같은 앱이 상태 아이콘을 올리기 시작하면 우측부터 차례대로 가려진다. 원래 있던 아이콘이 노치 뒤로 숨어 클릭할 수 없게 되는 일이 잦아졌다.

원했던 것은 단순했다 — 가려지는 아이콘들을 메뉴바의 **폴더 하나**에 모아 두고, 필요할 때 펼쳐서 쓰는 것. 다만 처음부터 기대한 경험은 "아이콘 그림만 나열"이 아니라, **폴더 안에서 각 앱의 원래 메뉴를 그대로 여는 것**이었다. 그 기대와 실제로 만들어진 것 사이에는 꽤 차이가 있다. [GitHub 저장소](https://github.com/jaymunsh/fold-menu)

**실기 동작은 macOS 26에서만 확인했다.** 구체적인 환경은 macOS 26.6.2 (25G83), Apple silicon이다. macOS 27이나 다른 OS 버전의 호환성을 보장하는 글은 아니다. 2026-10-01 개선 배포 내용은 아래의 별도 업데이트 섹션에 정리했다.

## 원했던 경험과 실제 구현은 다르다

| 항목 | 초기 기대 | 현재 구현 |
| --- | --- | --- |
| 숨김 | 선택한 아이콘이 메뉴바에서 사라짐 | 사용자가 폴더 왼쪽에 직접 배치한 항목을, 길게 늘어난 Fold Menu 상태 항목의 화면 밖 영역에 둠 |
| 폴더 내용 | 원본 아이콘이 폴더 안에 있는 듯 표시 | 마지막으로 읽은 상태 아이콘 또는 앱 아이콘의 **스냅샷**. 실시간 복제가 아님 |
| 항목 사용 | 폴더 안에서 원본 메뉴를 즉시 사용 | 선택한 항목 하나를 잠시 폴더 옆으로 꺼내 → 원본 메뉴 열기 → 닫히면 다시 숨김 |
| 모니터 | 어느 화면에서나 같은 경험 | 화면마다 폴더 버튼·패널은 표시되지만, 보조 화면에서 연 원본 메뉴가 그 화면에서 뜨는 것은 미해결 |

현재 구현은 다른 앱의 상태 항목을 자체 패널의 자식 뷰로 옮기는 구조가 아니다. 스냅샷 선택 → 실제 항목 임시 이동 → 원본 메뉴 열기라는 우회를 사용한다. 이것을 "폴더 안에서 바로 원본 메뉴를 쓴다"고 설명하거나, 다른 앱의 구현 방식까지 불가능하다고 단정하지 않는다.

## 첫 시도는 체크박스였고, 사고가 났다

초기 프로토타입은 접근성(Accessibility) API로 다른 앱의 메뉴바 항목을 검색하고, 설정 목록에서 체크한 항목을 폴더에 넣는 방식이었다. 이 방식에서 "목록에 체크됨", "패널에 아이콘이 보임", "원본 항목이 실제로 숨겨짐"은 서로 다른 상태였다. 체크했는데 위에 그대로 보이거나, 다른 항목까지 움직이거나, 간헐적으로 깜빡였다.

결정적인 사고가 있었다. 메뉴바 항목을 **아래 방향으로 드래그하면 macOS가 그 항목을 메뉴바에서 제거**할 수 있는데, 실험 중 HoldImg의 아이콘이 화면에서 사라졌다. 어떤 입력이 최종 제거를 일으켰는지 완전한 이벤트 기록이 없어 정확한 원인을 단정할 수는 없지만, 위험한 자동 재배치와 불명확한 안내가 문제를 키운 것은 분명했다. 이후 확인에서는 원본 HoldImg 앱의 상태 항목이 실행 중이며 화면 밖에 접혀 있음을 확인했다 — 앱 파일이 삭제된 사고는 아니었다.

이 사고로 방향을 바꿨다. **편집과 일상 사용을 분리**하고, 재배치는 사용자가 직접 하게 했다.

## 접기는 내가 하고, 배치는 사용자가 한다

1. 설정에서 `항목 편집 시작`을 누르면 폴더를 펼쳐 실제 메뉴바 배치를 보여 준다.
2. 사용자가 `⌘`를 누른 채 아이콘을 **메뉴바 행 안에서 수평으로** 옮긴다. 폴더 왼쪽이 접힐 항목, 오른쪽이 계속 보일 항목이다.
3. `편집 완료하고 접기`를 누르면 현재 배치를 다시 읽어 선택 ID를 저장한다.

체크박스가 다른 앱의 아이콘을 움직이지 않는다. `⌘`-드래그의 목적지는 반드시 메뉴바 행 안이고, 아래로 끄는 "폴더에 넣는" 제스처는 앱 기능이 아니다 — 그게 OS의 제거 동작과 충돌했던 길이다.

접는 방식 자체도 단순하다. Fold Menu의 자체 `NSStatusItem` 하나를 **길이 10,000pt의 예약 영역**으로 만들면, 그 왼쪽에 놓인 다른 앱 아이콘은 화면 밖 좌표에 위치한다. 작은 폴더 그림은 확인된 실제 예약 영역 끝에 오버레이로 얹는다. 다른 앱의 아이콘을 복제해 가리는 구조가 아니다.

## 패널의 아이콘은 스냅샷이고, 꺼낼 때는 실제 항목이 움직인다

폴더를 누르면 버튼 아래에 패널이 붙는다.

![Fold Menu 패널 — 접힌 앱의 아이콘 스냅샷 6개가 나열된다. Xcode, Docker, 카카오톡 등](/api/wiki-assets/126d9b3d-c861-4189-9b43-56884a4491e8)

여기 보이는 그림은 실시간 미러링이 아니다. 상태 아이콘의 CPU 수치나 배지가 계속 바뀌어도 패널의 그림은 이전 캡처일 수 있다. 실제 아이콘 이미지를 캡처하려면 화면 기록 권한이 필요하고, 캡처가 실패하면 이전 이미지나 앱 아이콘, 기본 기호 순으로 대체한다.

하나를 선택하면 그제야 진짜 일이 벌어진다. 화면 밖에 있던 **실제 상태 항목 하나**를 폴더 옆 메뉴바로 잠시 옮기고, `AXPress`가 가능하면 그걸로, 안 되면 좌표 클릭으로 원본 메뉴를 연다. 메뉴가 닫히면 원래 접힌 위치로 되돌린다. 복귀 기준은 일시적인 WindowServer 창 번호가 아니라 **이웃 항목 ID**로 저장해서 재실행 후에도 다시 찾는다.

이 과정에서 포인터 보호도 한다. 화면 밖 항목에 보내는 OS 입력이 커서 위치와 연결되므로, 짧은 자동 입력 동안 포인터를 보호하고 사용자의 물리적 이동량을 복원한다. 커서가 튀는 느낌을 줄이기 위한 것이다.

## 1pt 차이가 항목을 한 칸 밀었다

가장 기억에 남는 버그는 꺼낸 아이콘이 폴더 "옆에 옆"으로 나오던 것이다. 접근성 API가 보고하는 글리프의 x 좌표와 실제 WindowServer 상태창 호스트의 x 좌표가 **1pt 어긋나**, 바로 옆 항목이 후보에서 제외되고 그 다음 슬롯이 선택됐던 것이다. `AX x=1249`와 실제 호스트 `x=1250`, 잘못 고른 슬롯 `x=1304`처럼 좌표를 놓고 비교해서 잡았다.

이런 종류의 문제 때문에 AppKit이 보고하는 프레임이나 창 번호만 믿지 않는다. macOS 26에서는 메뉴바 창이 Control Center에 호스팅되기도 해서, 실제 WindowServer 상태창의 ID·PID·좌표를 따로 확인한다. 추적하던 경계 창이 재생성되면 유일하게 일치하는 후보만 채택하고, 후보가 없거나 모호하면 다른 항목을 덮지 않기 위해 오버레이를 감춘다. 경계를 2초 넘게 잃으면 안전하게 펼친다.

## 잠금에서 돌아올 때가 가장 위험하다

기기 잠금·화면 깨움·세션 재활성화 뒤에는 WindowServer 창이 재생성된다. 이때 상태창 호스트를 잠시 못 찾으면 평상시의 "경계 상실 → 안전 펼침"이 발동해 접힌 항목 전부가 밖으로 나와 버렸다. 지금은 깨움 뒤 창의 ID·좌표·크기가 안정될 때까지 기다리고, 안전 펼침을 **12초 유예**한다. 실제로 선택 항목이 다시 노출됐다고 확인할 때만 다시 접는다. 반복 실물 잠금/절전 검증은 아직 완료하지 않았다.

## 두 모니터는 네이티브 아이콘이 아니라 오버레이로 해결했다

화면마다 `NSStatusItem`을 추가로 만들지 않는다. 네이티브 항목은 하나고, 접힌 상태의 **각 디스플레이에 클릭용 오버레이**를 두고, 공용 폴더 패널 하나를 눌린 화면의 폴더 아래로 옮긴다. 화면별 실제 메뉴바 높이가 다르다는 것도 실측으로 알았다 — 내장 화면 39pt와 외부 화면 30pt를 따로 쓴다. 하나의 높이를 재사용했을 때 내장 화면의 폴더 오버레이가 y=9로 내려갔던 게 단서였다. 활성 화면의 폴더는 진하게, 비활성은 옅게 표시한다.

## 검색은 계속 돌리지 않는다

화면별 폴더 위치 확인은 250ms마다 유지한다 — 다른 아이콘을 덮지 않기 위한 추적이라 뺄 수 없었다. 대신 다른 앱 항목을 찾는 전체 접근성 검색은 매번 돌지 않는다. 5초마다 상태창 ID·위치·크기의 지문을 비교해 변화가 있을 때만 검색하고, 변화가 없어도 대략 10~15초 간격으로 한 번은 다시 본다.

2026-09-24 정책 변경 전 관찰은 평상시 CPU 0~3%, 메모리 약 29MB, 전체 AX 검색 한 번에 약 1.6초였다. 당시 배터리 절감량은 측정하지 않았다. 아래 업데이트의 측정은 선택 항목 수와 조건을 따로 맞춘 비교이며, 이 과거 관찰과 직접 비교하지 않는다.

## 2026-10-01 업데이트 — 최적화·수정 사항을 배포했다

2026년 10월 1일, 기존 사용 흐름을 유지하면서 설정창 간소화, 창 조회·항목 검색 최적화와 로컬 실패 진단을 반영했다. 수정본은 현재 Mac에 적용했고, 소스와 검증 기록은 [GitHub 커밋 `0cd429f`](https://github.com/jaymunsh/fold-menu/commit/0cd429f4546bcd26f1b5f6c819a969b2efbd872e)으로 공개했다. 설치용 앱 ZIP이나 공증된 정식 릴리스가 아니라, 개발자가 저장소에서 직접 빌드하는 형태의 배포다.

이번 배포의 실기 확인 환경도 **macOS 26.6.2 (25G83), Apple silicon**에 한정한다. macOS 27 호환성이나 남은 간헐 실패까지 해결한 버전이라는 의미는 아니다.

### 창 조회·검색 비용을 줄이고 설정창을 간소화했다

이번에는 기존 기능을 유지하는 범위로 최적화를 제한했다. 250ms 위치 추적, 5초 검색 판단과 10~15초 강제 검색, 이동 안정화 대기·커서 보호·복귀·잠금 복구 정책은 그대로다.

- `MenuWindowSnapshot`이 한 확인 회차의 전체 창 목록을 한 번 읽고 원본·경계를 함께 찾는다. 다음 회차는 새로 읽는다. 조회가 줄면서 서로 다른 시점의 배치를 섞을 가능성도 줄었다.
- `MenuIconIndex`가 검색 시작 때 기존 이미지의 ID 인덱스를 만든다. 같은 ID의 첫 이미지 재사용 규칙은 유지하고, 검색이 끝나면 인덱스를 해제한다. AX 요소나 좌표를 장기간 캐시하는 변경은 하지 않았다.
- 화면 목록은 한 앱을 동기식으로 검색하는 동안만 공유한다. 다음 앱으로 실행을 양보한 뒤에는 다시 읽는다.
- UI에서 사용하지 않는 검색 진행 상태의 변경 발행을 제거하고, 권한 값은 실제로 바뀔 때만 발행한다. 목록의 AX 요소는 계속 새로 갱신한다.

설정창도 줄였다. 중복 제목과 큰 편집 박스를 없애고 편집 버튼·항목 수를 한 줄에 배치했다. 실제 정상 창 크기는 **380×205pt에서 360×151pt**로 줄었고, 창 상단은 폴더 아래 y=46pt를 유지했다. 편집 중에는 수평 이동 안내와 제거 경고를 남겨 360×229pt로 커졌다. 종료·완료·메뉴바 설정, 권한 요청·오류·취소·다시 접기 경로도 유지했다.

### 전후 성능을 같은 조건에서 측정했다

같은 설치 경로와 개발 서명으로 버전을 한 번에 하나씩 실행했다. 내장 화면 하나에서 패널·설정을 닫고 15초 기다린 뒤, 1초 간격의 `top` 표본 31개 중 첫 표본을 제외한 30개를 비교했다. 측정 중에는 빌드나 반복 AX 검사를 실행하지 않았다.

| 비교 | 선택 항목 | CPU 평균 전 → 후 | `top MEM` 전 → 후 |
| --- | ---: | ---: | --- |
| 창 조회 공유·설정 간소화 | 8개 | 1.677% → 1.623% | 20–21M → 20–21M |
| 그 뒤 검색 내부 최적화·실패 진단 | 9개 | 1.717% → 1.483% | 20–21M → 21M |

두 번째 비교에는 PortManager가 추가됐다. 따라서 두 행은 각각의 전후 비교이고, 8개였던 첫 결과와 9개였던 두 번째 결과를 이어서 전체 개선률을 계산하지 않는다. CPU는 코어 하나가 100%인 프로세스 표시이며, 메모리는 반올림된 footprint 표시다.

첫 비교에서는 의미 있는 유휴 절감을 확인하지 못했다. 두 번째는 평균 약 0.23%p가 낮게 관찰됐지만, 다른 앱이 실행 중인 짧은 순차 측정이므로 확정적인 절감률이라고 하지 않는다. 메모리 감소도 확인되지 않았다. 배터리, 클릭 지연, 이동 중 CPU와 장시간 메모리 증가는 별도로 측정하지 않았다.

조건과 원본 표본은 [설정·성능 측정](https://github.com/jaymunsh/fold-menu/blob/main/docs/evidence/settings-and-performance-2026-10-01.md)과 [검색 최적화·실패 진단](https://github.com/jaymunsh/fold-menu/blob/main/docs/evidence/scan-optimization-and-diagnostics-2026-10-01.md)에 남겼다.

### 실패 원인을 추적할 로컬 진단을 추가했다

같은 날 메뉴 이동 결과를 검증하지 못한 실패도 있었다. 당시 상세 추적이 없어 원인은 확정하지 못했고, 뒤의 반복 성공으로 실패 기록을 지우지 않았다. 그래서 항목 선택 후 이벤트 전달·꺼내기 검증·메뉴 열림·닫힘·복귀를 최대 32개 단계와 경과 시간으로 기록하게 했다.

정상 동작은 메모리에만 남기고, 실패 때만 로컬 캐시의 `last-menu-failure.json` 하나를 원자적으로 덮어쓴다. 저장이 실패해도 원래 복귀·오류 안내는 유지한다. 스크린샷·창 제목·입력 내용·오류 문구는 저장하지 않고 외부로 전송하지 않는다. 실행 경로 기반 ID도 가린다. 성공한 클릭은 이전 실패 파일을 지우지 않으므로, 진단할 때 기록 시각과 현재 상태를 함께 봐야 한다.

```sh
swift scripts/diagnose-fold-state.swift
```

이 도구는 현재 선택·원본 좌표와 마지막 실패의 최근 12단계를 읽기 전용으로 보여 준다. 폴더가 열리기 전 문제나 검사 도구가 버튼을 찾지 못한 INCOMPLETE는 기록 대상이 아니다. 진단 추가는 원인 추적 준비이지, 기존 간헐 실패를 해결했다는 뜻이 아니다.

### 배포 전 확인한 결과와 남은 한계를 구분했다

최종 버전의 단위 검사 16개 그룹, 릴리스 빌드와 로컬 개발 서명 검증은 통과했다. 실기에서는 편집→접기 3회, 폴더→설정 재열기 3회와 60초 동안의 111회 AX 확인에서 선택 9개가 접힌 상태를 유지했다.

첫 donts3p 메뉴 검사는 버튼을 누르지 못해 INCOMPLETE로 끝났다. 이후 일반 실행 모드의 3회는 실제 메뉴 열림, 폴더와 원본 항목의 간격 0pt, Escape 뒤 미복귀 기록 없음으로 통과했다. 메뉴 내부 명령은 실행하지 않았다. 최종 조회에서 선택 9개는 모두 화면 밖, 임시 복귀 기록은 비어 있고 네이티브 상태 항목과 폴더 오버레이는 각각 하나였다.

이 결과는 **macOS 26.6.2의 내장 화면 하나에서 해당 실행을 확인한 것**이다. 앞의 실패·INCOMPLETE나 다른 앱의 동작까지 모두 해결됐다는 뜻은 아니다. 자세한 실행별 결과는 [검증 기록](https://github.com/jaymunsh/fold-menu/blob/main/docs/verification.md)에 보존했다.

## 메뉴바에 보이는 아이콘과 앱 아이콘은 다른 자산이다

메뉴바의 그림은 `FolderIndicator`가 그리는 숫자가 들어간 닫힌 폴더 템플릿이고, Finder·저장소에 쓰는 대표 아이콘은 별도 벡터 원본에서 만든다. 처음엔 민트 계열 배경이었는데, 흰 배경으로 바꾼 뒤에도 윤곽에 녹색 기운이 남아 최종적으로 `#FFFFFF` 배경에 `#242424` 윤곽, `#666666` 점의 무채색으로 정리했다. 대표 이미지의 점 세 개는 브랜드 표현일 뿐 접힌 항목 수가 아니다. 녹색 재유입을 막기 위해 16px 간격으로 불투명 픽셀을 표본 검사하는 테스트까지 있다.

## 아직 안 되는 것

- **보조 모니터에서 원본 메뉴의 위치·포커스.** 보조 화면의 폴더와 패널 표시는 확인했지만, 원본 메뉴가 클릭한 화면에 뜨고 그 화면으로 포커스가 바뀌는 문제는 미해결이다. 단순 명도 변경으로 해결됐다고 보지 않으며 이번 최적화에서도 해당 실기 검증을 반복하지 않았다.
- **간헐 메뉴 클릭과 잠금·절전 복귀.** 반복 실사용 검증과 실패 원인 확인이 남았다. 진단 파일 추가나 후속 성공을 해결 완료로 간주하지 않는다.
- **macOS 27.** 핵심 재배치가 WindowServer 상태창과 비공개 이벤트 필드에 기대므로, 업데이트마다 실제 열림·복귀·잠금 복귀를 다시 확인해야 한다. `CGWindowListCreateImage`는 macOS 14부터 deprecated라 ScreenCaptureKit 전환도 과제다.
- **앱별 차이.** AX 메뉴바 자식을 노출하지 않는 앱은 목록에 안 나타날 수 있고, 팝업 대신 자체 창을 여는 앱도 있다. 모든 앱에 같은 클릭·복귀를 보장하지 않는다.
- **배포.** Developer ID 공증·자동 업데이트·설치용 ZIP은 없다. 공개 저장소에서 직접 빌드하는 방식만 제공한다.

원했던 "폴더 안에서 바로 쓰는" 경험에는 못 미치지만, 접기와 일부 앱의 원본 메뉴 열기·복귀는 실기에서 확인했다. 지금은 기능을 더 늘리기보다 이 사용 흐름을 유지하며 남은 실패를 추적하는 단계다. 모든 문제가 해결된 정식 배포본은 아니며, OS 버전이 바뀌면 같은 검증을 다시 해야 한다.
