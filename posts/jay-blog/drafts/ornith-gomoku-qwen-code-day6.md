Day 5에서는 본 구현과 후속 LAN 확인 Goal의 활성 시간만 약 13시간 58분이 들었다. 다음 날에는 범위를 줄이기로 했다. 방을 하나 만들면 정확히 하나만 생기고, 두 사람이 구분 가능한 대기실에 들어갔다 나가면 방이 정리되는 것. 이번에는 그 결과를 하루 한 번의 요청으로 맡겼다.

그런데 다시 멈췄다. 터미널에는 코드베이스를 이해했고 서버와 테스트를 확인하겠다는 문단이 반복됐다. 끝에는 출력 토큰 제한과 `potential loop` 안내가 나왔다. 이번 기록은 Day 6 완료 후기가 아니라, 9월 12일 중단 상태에서 원인을 확인하기 시작한 초안이다.

## 하루에 요청 하나를 보내도록 범위를 줄였다

계획과 UI 시안은 외부 AI의 도움으로 준비했고, 실제 앱 구현은 Ornith를 연결한 Qwen Code에 맡겼다. 채팅·무르기·재대결·재접속은 후속 설계로 남겼다. 이번 범위는 방 중복 생성과 목록 오류, 최대 세 방 제한, 빈 방 정리, 로비·대기실 표시 개선이다.

실제로 전달한 요청은 다음과 같다.

~~~text
/goal IMPLEMENTATION_PLAN_DAY6.md를 읽고 문서의 범위와 완료 조건에 따라
구현·검증·보고서 작성·git commit까지 진행해줘. push는 하지 마.
완료한 검사를 이유 없이 반복하지 말고,
실제 두 기기 확인이 필요하면 접속 절차와 미검증 항목을 남기고 끝내줘.
~~~

구현 단계마다 사람이 다음 Goal을 입력하게 하는 대신, 순서를 계획서 안에 두었다. 통과 검사는 이유 없이 반복하지 않고 실제 기기 응답도 자동 실행 안에서 기다리지 않게 했다. 그러나 이 지침은 모델의 한 응답 안에서 일어나는 반복까지 막지는 못했다.

## 마지막 요청 하나가 약 15분간 생성됐다

![같은 문단을 반복한 뒤 출력 토큰 제한과 potential loop 경고로 중단된 Day 6 터미널](/api/wiki-assets/338dca0d-5756-42c6-a3dd-7e567b2fc654 "width=900 align=center")

원본 세션 `7b1429bf…`의 마지막 API 응답 `chatcmpl-223d9043`에도 반복 문장이 들어 있다. 화면만 중복 렌더링됐다고 볼 수 없는 근거다. 저장된 응답 텍스트에서 해당 문단의 시작 문구는 13회 발견됐다. 이는 로그에 저장된 텍스트의 횟수이며 전체 생성 토큰에서 같은 문단이 몇 번 나왔는지까지 뜻하지 않는다.

| 마지막 API 응답 | 기록 |
| --- | --- |
| Qwen Code 버전 | 0.23.3 |
| 모델 식별자 | Ornith-1.5-35B-A3B-oQ6-gs128-mtp-vision |
| 응답 기록 시각 | 2026-09-12 02:08:48 KST |
| 요청 소요 시간 | 898,097ms · 14분 58.097초 |
| 입력 토큰 | 55,742 |
| 출력 토큰 | 32,361 |
| thoughts_token_count | 32,361 |
| 출력 ÷ 요청 시간 | 약 36.0 tok/s |

36.0 tok/s는 이 요청의 출력 토큰을 전체 요청 시간으로 나눈 처리량이다. oMLX가 별도로 측정하는 decode 속도가 아니므로 Day 5의 가중 생성 속도 33.9 tok/s와 직접 비교하지 않는다. 출력과 생각 토큰도 별개로 더하지 않는다. 이번 로그에서는 두 필드에 같은 값이 기록됐다.

이 수치는 개발 진척을 보여주지 않는다. 마지막 요청은 토큰을 계속 생성했지만 같은 확인 의도를 반복했고, 그 응답에서 다음 파일 읽기로 나아가지 못했다.

## 화면의 1시간 46분은 전체 세션 시간이 아니었다

마지막 저장 Goal 상태는 `paused`, 활성 시간은 6,394,276ms, 즉 1시간 46분 34.276초였다. 이 상태는 9월 12일 01:29:46 KST에 기록됐다. 사유는 turn이 중단됐다는 것이었다.

그 이후에도 세션에는 압축과 파일 조회, 02:08:48에 끝난 반복 응답이 남아 있다. 따라서 화면의 `paused (1h 46m)`을 마지막 응답까지 포함한 전체 시간이라고 쓰면 안 된다. 이번 loop 감지가 최초 pause의 원인이었다고 말할 수도 없다. pause 기록이 먼저다.

검토한 로그 범위에는 API 응답 이벤트 97개와 압축 기록 10개가 있었다. 이는 해당 세션 파일에서 집계한 이벤트 수이며, 다른 세션이나 별도 모델 호출까지 포함한 Day 6 전체 집계는 아니다. 정확한 종합 시간과 사용량은 인계와 후속 실행을 마친 뒤 다시 정리해야 한다.

## 압축 이후 요약 대신 파일 읽기 요청이 남았다

마지막 두 압축 기록을 비교하면 문맥 전달이 흔들린 정황이 보인다.

| 시각(KST) | 압축 전 → 후 토큰 추정 | 요약 위치의 내용 |
| --- | --- | --- |
| 01:33:19 | 67,225 → 51,071 | 목표와 진행 상태를 담은 state_snapshot |
| 01:50:06 | 66,450 → 35,874 | 파일을 읽겠다는 문장과 tool_call 문자열 |

마지막 기록도 `compressionStatus: 1`로 남았다. 하지만 압축 이력의 첫 사용자 메시지는 약 755자였고, 상태 요약 대신 `main.js`, `home.mjs`, `UI_SPEC.md`를 읽겠다는 요청 모양의 문자열이 들어 있었다. 뒤에는 최근 파일 내용도 붙어 있으므로 압축 후 전체 문맥이 755자였다는 뜻은 아니다.

그 직후 모델은 존재하지 않는 `src/game/gomoku-core.mjs`, `src/ui/game.mjs` 등을 읽으려 했다. 도구는 파일이 없다고 응답했다. 이후 실제 구현이 `state.js`, `rules.js`, `main.js`에 있다는 점을 확인했지만, 그 차이를 설명하는 문단을 계속 반복했다.

앞선 답변에서는 모델이 말한 “요약의 파일명이 틀렸다”는 설명을 원인처럼 받아들이기 쉬웠다. 하지만 확인한 마지막 요약 첫 메시지에는 `gomoku-core.mjs`가 없다. 모델의 자기 설명만으로 잘못된 파일명이 요약에서 왔다고 확정하지 않는다. 확인된 사실은 압축 산출물이 상태 요약으로 부적절했고, 그 뒤 잘못된 경로 조회와 반복 생성이 이어졌다는 순서다.

## 원인 후보와 확인된 사실을 나눠 본다

| 판단 | 현재 근거 |
| --- | --- |
| 한 응답 내부의 반복 생성 | API 응답 텍스트에 같은 문단 반복 확인 |
| 문맥 복구 실패 가능성 | 비정상적인 압축 산출물 뒤 잘못된 경로 조회 |
| 출력 제한과 loop 경고 발생 | 사용자 터미널 캡처 |
| 모델·샘플링·서빙 계층 중 근본 원인 | 비교 실험과 요청 설정 대조가 없어 미확정 |
| evidence_catalog 재발 | 이번 확인 기록에서는 근거 없음 |

Qwen 공식 설정 문서는 스트리밍 loop 감지와 샘플링·출력 한도 설정을 제공한다. 다만 현재 문서의 옵션을 확인했다고 해서 이번 설치 버전의 실제 설정이나 검출 경로를 모두 확인한 것은 아니다. 경고가 떴다는 이유만으로 감지를 끄는 것은 반복 비용을 더 키울 수 있다. [Qwen 공식 설정 문서](https://github.com/QwenLM/qwen-code/blob/main/docs/users/configuration/settings.md)

Day 5 후속 세션은 사람의 응답을 기다리며 자동 turn을 이어간 문제였다. 이번에는 하나의 응답 안에서 생각이 반복됐다. 두 현상 모두 시간을 쓰지만, 전자는 작업의 대기 조건을 바꾸는 것이 중요하고 후자는 문맥·생성·검출 경로를 함께 확인해야 한다.

## 현재 변경을 보존하고 실제 파일에서 이어간다

초안 작성 시점의 Git HEAD는 계획 정리 커밋 `fe3b299`였다. working tree에는 `server/protocol.mjs` 한 파일의 변경이 있었고, 내용은 `MAX_ROOMS`를 5에서 3으로 바꾸고 주석을 추가한 것이었다. Day 6 진행·최종·인계 보고서는 아직 없었다.

이것만으로 세 방 제한이 완성됐다고 볼 수 없다. 동시 생성과 빈 방 정리, 두 브라우저 목록, UI와 회귀 검증이 남아 있다. 터미널의 `2 tasks done`도 전체 완료를 뜻하지 않는다. 현재 diff는 남아 있는 변경량이며 세션 중 수행한 모든 행동의 양을 뜻하지도 않는다.

복구는 실제 Git 상태와 파일을 기준으로 짧은 인계 기록을 만드는 것부터 진행하려 한다. 검증된 변경만 커밋하고 미검증 변경은 보존한다. 현재 세션에서 인계 요청도 반복된다면 중단하고, 새 세션에서 실제 파일을 읽어 인계 내용을 재구성한다. 새 세션은 반복 문맥을 덜어내기 위한 선택이며 문제를 해결했다는 증거는 아니다.

## 다음에는 한 번에 하나의 조건을 바꿔 확인한다

우선 깨끗한 문맥과 짧은 인계로 같은 미완료 작업을 이어간다. 다시 반복되면 실제 요청의 출력 한도와 샘플링 설정, oMLX의 종료 사유, Qwen loop 감지 설정을 대조한다. 모델이나 추론 옵션까지 모두 동시에 바꾸면 무엇이 영향을 줬는지 알 수 없으므로 한 번에 하나씩 비교한다.

출력 한도를 낮추는 실험은 반복 한 번의 비용을 줄일 수 있지만 정상적인 긴 응답도 끊을 수 있다. 아직 이 실험을 실행하거나 적절한 값을 확정하지 않았다. 완료한 작업·다음 파일·최근 검증을 디스크에 남겨 compact 이후 전체 탐색으로 돌아가지 않게 하는 것도 함께 확인할 부분이다.

현재 결론은 Day 6 구현 완료가 아니다. 범위를 줄인 요청에서도 응답 내부 반복이 발생했고, 그 마지막 요청 하나에 약 15분이 들었다. 다음 실행에서는 생성 속도뿐 아니라 실제 변경, 검증 결과와 반복 없이 다음 행동으로 넘어갔는지를 함께 기록하려 한다.
