2026년 8월 24일 기준 Git 공식 문서와 Orca CLI 가이드를 바탕으로 정리했다. 도구별 명령어는 버전에 따라 달라질 수 있지만, worktree를 격리 단위로 쓰는 발상 자체는 크게 바뀌지 않는다.

기능을 개발하다가 급한 버그 수정 요청이 들어오면 작업을 멈추고 브랜치를 전환해야 한다. 아직 커밋하기 애매한 변경이 있다면 stash를 만들거나 임시 커밋을 남긴 뒤, 다시 원래 상태로 돌아와야 한다. 저장소를 폴더째 하나 더 클론하는 방법도 있지만 관리할 것이 늘어난다.

Git Worktree는 이 문제를 이미 해결하고 있었다. 하나의 Git 저장소를 공유하면서 여러 디렉터리에 서로 다른 브랜치를 동시에 체크아웃하는 기능이다. 그런데 오랫동안 조용하던 이 기능이 최근 다시 주목받는 이유는 사람보다 코딩 에이전트에 있다. Claude Code와 Codex 같은 에이전트, Orca 같은 ADE(Agent Development Environment)가 worktree를 작업 실행의 기본 단위로 채택하고 있기 때문이다.

이 글에서는 사람이 worktree를 어떻게 쓰는지부터 살펴보고, 에이전트에게 왜 worktree가 편의 기능을 넘어 격리 장치가 되는지 정리한다. 마지막에는 같은 핫픽스 상황을 사람과 에이전트가 처리하는 흐름을 나란히 비교한다.

## Worktree는 브랜치마다 작업 폴더를 하나 더 주는 기능이다

브랜치를 전환한다는 것은 한 벌의 작업 디렉터리를 통째로 갈아끼우는 일이다. 반면 worktree는 작업 디렉터리를 여러 벌 두고 각각에 브랜치를 배정한다. 커밋 히스토리와 오브젝트를 담은 Git 저장소는 공유하므로 전체 저장소를 다시 클론하는 것보다 가볍다.

~~~bash
# 로그인 기능 작업 중 긴급 핫픽스 공간을 만든다
git worktree add ../myapp-hotfix -b hotfix/login main
cd ../myapp-hotfix

# 작업이 끝난 뒤 정리한다
cd ../myapp
git worktree remove ../myapp-hotfix
~~~

핵심 명령은 세 가지다.

| 명령 | 역할 |
|---|---|
| worktree add | 새 작업 폴더와 브랜치 생성 |
| worktree list | 현재 worktree 목록 확인 |
| worktree remove | 작업 폴더 제거 |

원래 작업은 그대로 남는다. 리팩토링 중인 폴더를 건드리지 않고 핫픽스 폴더에서 수정할 수 있으며, 두 작업을 각각 실행하고 테스트할 수 있다.

## 사람은 작업 맥락을 분리하기 위해 worktree를 쓴다

사람이 worktree를 쓰는 상황은 대체로 네 가지다.

| 상황 | worktree 없이 하면 | worktree로 하면 |
|---|---|---|
| 기능 개발 중 긴급 핫픽스 | stash → 브랜치 전환 → 수정 → 복귀 | 새 폴더에서 수정 후 원래 작업으로 복귀 |
| 동료 PR 리뷰와 내 개발 병행 | 리뷰하는 동안 내 작업 흐름이 끊긴다 | 리뷰용 폴더에서 실행하며 확인한다 |
| 여러 버전 동시 유지보수 | 버전마다 저장소를 따로 클론한다 | 버전별 폴더를 두고 필요한 커밋만 옮긴다 |
| 실험적 리팩토링 | 현재 브랜치가 불안해진다 | 실험 전용 폴더에서 시도하고 실패하면 제거한다 |

핵심은 **작업 맥락이 폴더 단위로 분리된다**는 점이다. IDE 창, 실행 중인 서버, 빌드 산출물과 브랜치가 한 작업 공간에 묶인다.

worktree는 영구 보관소가 아니다. 독립적으로 테스트를 통과한 변경은 커밋하고, main에 머지하거나 PR을 만든 뒤, worktree와 브랜치를 정리해야 한다.

~~~bash
cd ../myapp-hotfix
git add .
git commit -m "fix: 로그인 검증 우회 수정"

cd ../myapp
git merge hotfix/login
git worktree remove ../myapp-hotfix
git branch -d hotfix/login
~~~

핫픽스를 main에 합쳤다면 진행 중이던 기능 브랜치에도 main의 변경을 반영해야 한다. 여러 worktree가 서로 의존한다면 부모 작업부터 순서대로 합쳐야 한다. 같은 브랜치를 두 worktree에서 동시에 체크아웃할 수 없고, node_modules 같은 의존성은 각 폴더에 따로 설치해야 하며, 여러 개발 서버의 포트도 직접 관리해야 한다.

## 에이전트에게 worktree는 편의가 아니라 안전 경계다

사람에게 worktree는 작업 전환을 편하게 만드는 기능이다. 에이전트에게는 정확성과 안전성의 문제에 가깝다.

코딩 에이전트는 파일을 읽고, 여러 파일을 수정하고, 테스트를 실행하고, 결과를 확인한 뒤 다시 수정한다. 이때 같은 디렉터리에서 에이전트 세션을 두 개 실행하면 다음 문제가 생길 수 있다.

- 세션 A의 변경을 세션 B가 덮어쓴다.
- 두 세션의 테스트 결과가 섞인다.
- 어느 변경이 어느 프롬프트에서 나왔는지 추적하기 어렵다.
- 한 에이전트가 남긴 미완성 상태를 다른 에이전트가 완성된 코드로 오해한다.

세션마다 worktree를 하나씩 주면 이 문제가 구조적으로 줄어든다. 브랜치, diff, 커밋, 테스트 결과가 작업별로 분리된다.

| 특성 | 사람 | 에이전트 |
|---|---|---|
| 현실적인 동시 작업 수 | 1~2개 | 여러 작업을 병렬로 시도 |
| 실수 비용 | 눈에 보이면 바로 수정 | 조용히 다른 파일을 건드릴 수 있음 |
| 작업 단위 | 며칠에서 몇 주 | 하나의 task와 하나의 변경 |
| 필요한 것 | 편리한 전환 | 완전한 격리 |

따라서 worktree는 에이전트에게 동시에 여러 일을 하게 하는 기능이라기보다 **작업 하나와 변경 이력 하나를 대응시키는 장치**다.

## Orca는 worktree 위에 작업 공간과 상태를 얹는다

Git이 제공하는 것은 폴더와 브랜치의 관계다. Orca 같은 ADE는 그 위에 에이전트 실행과 상태 관리를 묶는다.

~~~mermaid
flowchart TB
    A["저장소"] --> B["worktree"]
    B --> C["브랜치"]
    B --> D["에이전트 터미널"]
    B --> E["브라우저·실행 환경"]
    B --> F["상태·코멘트·작업 계보"]
~~~

### 생성과 실행을 하나의 작업으로 묶는다

~~~bash
orca worktree create --name fix-login --no-parent \
  --agent codex --prompt "로그인 버그 수정" --json
~~~

사람이 직접 하던 다음 과정이 하나의 작업 생성 흐름으로 묶인다.

1. 기본 브랜치 기준으로 새 worktree와 브랜치를 만든다.
2. 저장소 설정에 따라 의존성 설치 같은 setup을 실행한다.
3. 지정한 에이전트 CLI를 worktree의 첫 터미널에서 실행한다.
4. 프롬프트를 전달한다.

즉 사람이 입력하던 worktree 생성, 환경 준비, 에이전트 실행을 도구가 한 작업 단위로 관리한다.

### 작업 사이의 계보를 기록한다

Orca는 현재 작업 위에 쌓는 stacked 작업과 독립적인 작업을 구분한다. Git만으로도 브랜치 관계는 표현할 수 있지만, 여러 에이전트가 만든 작업의 부모·자식 관계를 작업 카드에서 보여주면 사람이 전체 흐름을 파악하기 쉬워진다.

### worktree가 상태판이 된다

~~~bash
orca worktree set --worktree active \
  --comment "수정 완료; 통합 테스트 실행 중"

orca worktree set --worktree active \
  --workspace-status in-review
~~~

에이전트가 재현, 원인 파악, 수정, 검증, 막힘 같은 상태를 worktree에 남기면 worktree 카드는 상태 화이트보드가 된다. 사람이 각 터미널을 돌아다니며 물어보지 않아도 작업 목록에서 현재 상태를 확인할 수 있다.

### 예약 작업은 깨끗한 worktree를 반복해서 사용한다

~~~bash
orca automations create --name "매일 코드 점검" \
  --trigger daily --time 09:00 \
  --prompt "열린 PR 검토" --provider codex --repo id:<repoId>
~~~

예약 작업을 worktree와 연결하면 매 실행마다 깨끗한 작업 공간을 만들 수 있다. 사람에게는 매번 폴더를 새로 만드는 일이 번거롭지만, 에이전트에게는 이전 실행의 잔여 상태가 없는 환경이 오히려 안전하다.

## 같은 핫픽스를 사람과 에이전트에게 맡겨 보자

오후 4시, 결제 모듈 리팩토링 중에 고객사로부터 다음 요청이 들어왔다고 하자.

> 결제 실패할 때 에러 메시지가 화면에 안 나옵니다. 내일 배포인데 확인 부탁드립니다.

현재 폴더에는 아직 커밋하지 않은 리팩토링 변경이 남아 있다. 리팩토링을 버릴 수도 없고, 핫픽스를 기다리게 할 수도 없다.

### 사람은 핫픽스 폴더를 직접 만든다

~~~bash
git worktree add ../myapp-hotfix -b hotfix/payment-error main
cd ../myapp-hotfix
npm install
npm test

# 재현 테스트와 수정이 끝난 뒤 커밋한다
git add .
git commit -m "fix: 결제 실패 시 사용자에게 에러 메시지 노출"

cd ../myapp
git merge hotfix/payment-error
git worktree remove ../myapp-hotfix
git branch -d hotfix/payment-error

# 진행 중이던 리팩토링 브랜치에도 main을 반영한다
git rebase main
~~~

사람의 몫은 작업 우선순위를 판단하고, 격리 공간을 만들고, 테스트가 끝난 시점을 알아보고, 머지한 뒤 기존 브랜치에 main을 반영하는 것이다. 명령 입력보다 상태와 순서를 기억하는 일이 더 중요하다.

### 에이전트는 작업 생성부터 상태 보고까지 이어 간다

이번에는 Orca를 통해 Codex에게 같은 작업을 전달한다.

~~~bash
orca worktree create --name payment-error-fix --no-parent \
  --agent codex \
  --prompt "결제 실패 시 에러 메시지가 노출되지 않는 버그 수정.
먼저 재현 테스트를 작성하고, 수정 후 전체 테스트를 통과시켜라." --json
~~~

작업은 다음처럼 흘러간다.

| 시각 | 주체 | 일어나는 일 |
|---|---|---|
| 16:05 | Orca | main 기준 worktree와 hotfix 브랜치 생성 |
| 16:06 | Orca | 저장소 설정에 따라 setup 실행 |
| 16:07 | Orca | 첫 터미널에서 Codex 실행, 프롬프트 전달 |
| 16:07~18:30 | 에이전트 | 코드 탐색 → 원인 특정 → 재현 테스트 → 수정 → 테스트 |
| 중간중간 | 에이전트 | 작업 상태와 코멘트 갱신 |
| 19:00 | 사람 | 카드에서 in-review와 테스트 결과 확인 |
| 19:10 | 사람 | diff 검토 후 PR 승인 |
| 머지 직후 | Orca | worktree 정리 |

사람의 진행 상황은 머릿속에 남기 쉽다. 에이전트 환경에서는 worktree 카드가 작업 상태판이 된다. 사람은 각 세션의 상세 대화를 모두 읽지 않고도 어느 작업이 막혔고 어느 작업이 리뷰 대기인지 확인할 수 있다.

### 두 방식의 차이는 작업 경계에서 드러난다

| 단계 | 사람 방식 | 에이전트 방식 |
|---|---|---|
| 격리 공간 확보 | git worktree add 직접 입력 | worktree 생성과 에이전트 실행을 함께 처리 |
| 원인 분석·수정 | 사람이 디버깅 | 에이전트가 프롬프트대로 수행 |
| 검증 | 사람이 테스트를 실행하고 확인 | 에이전트가 테스트 통과까지 반복 |
| 진행 상황 공유 | 사람의 기억이나 별도 메시지 | worktree 코멘트와 상태 |
| 합치는 타이밍 | 사람이 판단해서 머지 | 사람이 diff를 리뷰한 뒤 판단 |
| 작업 계보 | 브랜치와 커밋을 사람이 추적 | worktree 관계와 카드에서 확인 |

## 머지는 여전히 사람의 책임이다

worktree와 에이전트가 작업 공간을 격리해도 최종 머지는 자동으로 맡기지 않는 편이 안전하다.

에이전트가 테스트를 통과했다는 것과 변경을 main에 합쳐도 된다는 것은 같은 말이 아니다. 사람은 diff를 확인하고, 재현 테스트가 실제 문제를 잡는지 보고, 운영 환경의 위험을 판단해야 한다.

worktree가 이 경계를 자연스럽게 만든다. 에이전트의 변경은 자기 브랜치에 머물러 있고, 사람은 부담 없이 열어본 뒤 합치거나 버릴 수 있다.

## 사람의 역할은 작업보다 작업 공간 관리에 가까워진다

에이전트 도구들이 worktree를 기본값으로 삼는다는 것은 worktree의 역할이 바뀌고 있다는 신호다.

| 관점 | 사람 중심 | 에이전트 포함 |
|---|---|---|
| 용도 | 브랜치 전환의 고통 완화 | 에이전트 작업의 격리 단위 |
| 수명 | 며칠~몇 주 | 작업 하나가 끝날 때까지 |
| 개수 | 2~3개 | 작업 수만큼 |
| 관리 주체 | 사람이 기억해서 관리 | 도구가 생성·추적·상태 표시 |
| 남는 산물 | 머지된 브랜치 | 머지된 브랜치와 작업별 diff |

사람은 어떤 작업을 시킬지와 언제 합칠지를 결정하고, worktree 생성·환경 구성·에이전트 실행·상태 보고는 도구에 맡기게 된다.

## 시작은 Git 명령어 세 개면 충분하다

에이전트 없이 감을 잡으려면 다음만 해보면 된다.

1. 진행 중인 프로젝트에서 git worktree add ../프로젝트-test -b test/something으로 실험용 폴더를 만든다.
2. 그 폴더에서 자유롭게 수정하고 커밋한다.
3. git worktree list로 목록을 확인하고 remove로 정리한다.

익숙해지면 에이전트 쪽은 자연스럽게 연결된다. Orca라면 worktree 생성, 에이전트 선택, 프롬프트 전달을 하나의 작업으로 묶을 수 있다.

Git Worktree는 새로운 기능이 아니다. 사람에게는 작업을 병렬로 유지하는 편의 기능이었고, 에이전트에게는 작업 간 오염을 막는 실행 경계가 됐다. Orca 같은 ADE는 여기에 터미널, 브라우저, 상태와 계보를 묶어 **에이전트 작업 하나가 독립된 개발 공간 하나가 되도록** 만든다.
