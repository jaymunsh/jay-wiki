Quantinue는 실물 미국 주식 시장 데이터와 AI 판단을 사용하되, 주문은 MockBroker 안에서만 체결하는 모의 자동매매 시스템이다.
시세·뉴스·공시·거시 지표를 모으고, 성향이 다른 두 전략가와 비평가가 판단한 뒤, 규칙 기반 배분과 손절·익절을 거쳐 결과를
PostgreSQL 원장에 남긴다.

5명이 약 3주 동안 개발했고, 완성 뒤 6거래일을 실제 시간표로 운영했다. 이 글은 짧은 운영 결과를 투자 성과로 포장하지 않는다.
대신 선형 데모를 독립 JOB 기반 운영 시스템으로 다시 설계한 이유, 내 담당 범위, 실제 실행에서 발견한 결함과 아직 켜지 않은
기능을 함께 기록한다.

## 어떤 문제를 풀려고 했나

자동매매 데모는 종목 하나를 골라 LLM에게 사고팔지를 물은 뒤 결과를 화면에 보여주는 것만으로도 만들 수 있다. 그러나 그런
구조로는 다음 질문에 답하기 어렵다.

- 같은 날 작업이 다시 실행되면 판단과 주문이 중복되지 않는가?
- 수집이나 AI 한 단계가 실패하면 다음 날 전체 파이프라인이 멈추지 않는가?
- AI가 왜 그 종목을 선택했고 어떤 원본을 봤는지 다시 추적할 수 있는가?
- 장중 가격이 급변할 때 LLM을 계속 호출하지 않고도 보유 자산을 방어할 수 있는가?
- 노트북이 잠들거나 네트워크가 끊겼을 때 운영자가 알아챌 수 있는가?
- 실제 주문, LLM 비용과 관리자 쓰기 기능을 실수로 켜지 않게 막을 수 있는가?

Quantinue의 목표는 수익률을 예측하는 모델보다 이 질문에 답할 수 있는 **작은 운영 시스템**을 만드는 것이었다.

## 1차 선형 러너를 2차 독립 JOB 구조로 바꿨다

MVP-1은 종목 하나가 수집부터 회고까지 역할 01~11을 순서대로 통과하는 선형 runner였다. 한 사이클이 끝까지 동작한다는 것은
확인할 수 있었지만, 중간 단계 하나가 실패하면 전체 흐름이 함께 멈췄고 재실행 지점을 정하기 어려웠다. 하나의 공격형 계좌만 있어
전략 차이를 비교하기도 어려웠다.

MVP-2에서는 선형 runner를 14개의 등록 JOB으로 나눠 옮겼다. 한 번에 걷어내지 않고 같은 원장을 함께 쓰며 점진 교체했다. JOB은 다른 JOB을 직접 호출하지 않고 PostgreSQL의 원장과
스냅샷만 읽고 쓴다.

| 변경 | 운영상 얻은 것 |
|---|---|
| 선형 runner를 JOB으로 분리 | 한 단계 실패가 전체 프로세스를 즉시 중단시키지 않음 |
| JOB별 실행 원장 | 어떤 슬롯이 성공·실패·실행 중인지 다시 확인 가능 |
| 날짜·JOB 복합 키 | 같은 일자의 중복 기동을 DB에서 차단 |
| 두 persona와 계좌 | 공격형과 안정형 판단을 같은 입력에서 분리해 관찰 |
| 원본과 전달 snapshot 분리 | LLM에 전달한 값과 외부 원본을 각각 추적 |
| MockBroker 고정 | 시장 데이터는 실제이지만 주문은 외부로 전송하지 않음 |

이 구조는 이벤트 브로커를 흉내 낸 것이 아니다. 단일 PostgreSQL 안에서 DB를 통신 계약과 실행 원장으로 사용해, 작은 팀이
재시작·재시도·중복 차단을 설명할 수 있는 범위로 제한한 선택이다.

## 하루의 판단은 수집부터 체결까지 한 경로를 지난다

뉴욕 세션 기준 일정은 매일 KST 13시에 시작한다. 2026-07-21 슬롯에서는 13:00:22부터 13:10:24까지 12개 일일 JOB이 모두
성공했고 전체 시간은 10분 2초였다. 이 가운데 LLM 분석이 9분 34초를 차지했고 나머지 단계는 30초 안에 끝났다.

1. Alpaca, SEC EDGAR, RSS와 FRED에서 시장·공시·뉴스·거시 데이터를 수집한다.
2. 시가총액 상위 universe와 기존 보유 종목에서 screening 후보를 만든다.
3. 공격형과 안정형 전략가가 서로 독립적으로 매수·보유·매도를 판단한다.
4. critic이 근거, 데이터 신선도와 정책 위반을 검토해 통과·반려·보류한다.
5. 규칙 기반 allocator가 예산, 중복 보유와 포지션 상한을 적용한다.
6. 살아남은 주문만 MockBroker가 체결하고 주문·체결 원장에 남긴다.
7. 결과와 비용, 실패를 관리자 화면과 Telegram에서 확인한다.

해당 일자에는 일봉 1,940건을 읽고 22개 종목을 선별했다. 공격형 25건, 안정형 22건을 분석했으며, allocator는 7건을 실행하고
38건을 건너뛰었다. 이 숫자는 시스템이 실제 데이터로 한 사이클을 통과했다는 증거이지 전략 수익성을 의미하지 않는다.

## 판단은 AI에게 맡기고 경계는 코드가 지켰다

Quantinue는 모든 결정을 AI에 맡기지 않았다. AI는 정성적 근거가 필요한 판단에 사용하고, 재현성과 즉시성이 필요한 정책은
코드와 DB 제약으로 고정했다.

| AI가 담당 | 코드·DB가 담당 |
|---|---|
| 뉴스·공시·거시 맥락 요약 | universe와 screening 범위 |
| 공격형·안정형 매수·보유·매도 의견 | 계좌별 예산과 포지션 상한 |
| 판단 근거와 confidence | 중복 실행·중복 주문 방지 |
| critic의 근거 반박 | 손절·익절 가격과 청산 순서 |
| 사건 발생 시 재판단 후보 | 일일 LLM 비용 상한과 mode switch |

critic은 323건을 검토해 57건을 반려하고 44건을 보류했다. 반려율 18%는 critic이 무조건 통과시키지 않았다는 운영 신호다.
다만 critic 역시 LLM이므로 정확성을 보장하는 최종 심판으로 표현하지 않는다. 실제 안전 경계는 MockBroker, 비용 상한, DB 제약과
결정적인 exit rule이 함께 만든다.

## 장중에는 LLM보다 기계적 방어를 먼저 둔다

일일 판단만으로는 장중 급변을 다루기 어렵다. MVP-2에서 1분 단위 watch runner와 사건 기반 재판단 경로를 추가했다.

- 1분 감시는 현재가가 손절·익절선을 넘었는지 확인하며 LLM을 호출하지 않는다.
- SEC는 30분, 뉴스는 15분, wire는 10분 간격으로 증분 수집한다.
- 가격 급변이나 새로운 사건은 관련 종목만 재판단 후보로 만든다.
- 같은 종목의 반복 사건은 cooldown과 sweep 원장으로 중복 dispatch를 막는다.
- 변경된 판단도 critic과 allocator, MockBroker 경계를 다시 통과한다.

기능 구현과 강제 발동 E2E는 마쳤지만 운영 기본값은 watch=true, rejudge=false, stream=false였다. 즉 장중 기계적 방어는 켰지만
유료 LLM 재판단과 streaming 수집은 켜지 않았다. 기능이 존재한다는 것과 무인 운영에서 활성화했다는 것을 구분한 결정이다.

## PostgreSQL을 결과 저장소가 아니라 판단 원장으로 사용했다

39개 테이블에는 외부 원본, 전달 snapshot, 전략가 판단, critic verdict, 주문·체결, JOB 실행과 비용이 분리돼 있다. 중요한 것은
테이블 수가 아니라 **왜 샀는지와 무엇을 보고 판단했는지 되짚을 수 있는가**였다.

- 공시와 뉴스는 원본 1건을 1행으로 저장하고, LLM 전달용 집계는 별도 signal에 남긴다.
- 전략 판단에는 persona, model, prompt version, input hash와 원천 시각을 기록한다.
- JOB은 job_name과 slot_date의 키로 같은 날짜의 중복 성공을 막는다.
- 주문은 계좌와 signal을 조합한 고유 키로 중복 체결을 막는다.
- 장중 sweep과 종목별 dispatch도 별도 원장으로 재시작 시 경계를 유지한다.

운영 결과를 다시 조사했을 때 판단 342건 모두 screening pick과 연결됐지만, 뉴스 source 계보는 0건이었다. 기록 컬럼이 있다고
계보가 완성되는 것은 아니다. 이 실측 덕분에 prompt·모델 기록과 원천 데이터 연결을 서로 다른 완성도로 보게 됐다.

## 나는 회고 원장과 장중 방어 경로를 맡았다

초기 역할 분담에서 나는 역할 11의 회고와 기록을 맡았다. 전략 판단 이후 T+1부터 T+5까지 가격 snapshot을 쌓고, 판단과 실제
가격 변화를 다시 읽을 수 있도록 review 원장을 설계하는 범위였다.

다만 최종 발표 시점의 2차 tb_review는 0건이었다. 첫 T+5 대상이 프로젝트 후반에야 도래했고 회고 실행도 일일 JOB이 아닌
수동 trigger로 남았기 때문이다. 회고 schema와 가격 snapshot 경로를 만들었다는 사실과, 충분한 회고 데이터로 전략을 개선했다는
주장은 구분해야 한다. 소표본이 쌓여도 전략 반영 가중치는 당분간 0에 가깝게 두는 것이 기획 기준이었다.

MVP-2에서는 장중 감시와 사건 재판단을 중심으로 구현 범위가 넓어졌다.

- 1분 bracket 감시와 보유 포지션 exit 흐름
- SEC·뉴스·wire의 증분 수집 상태와 사건 후보 연결
- 가격 이동과 정기 sweep 기반 재판단 대상 선정
- cooldown, attempts와 dispatch 원장을 통한 중복 호출 차단
- 재판단 결과를 critic·allocator·MockBroker 경로로 다시 연결
- 운영 근거, 트러블슈팅과 최종 설계 문서 정리

전체 시스템은 팀의 수집·전략·critic 설계와 구현 위에서 완성됐다. 내가 프로젝트 전체를 단독 설계했다고 표현하지 않는다.
내 기여는 맡은 회고 영역을 운영 가능한 원장으로 구체화하고, 2차에서 장중 방어와 재판단 경로를 통합하며, 실제 실행 결과와
한계를 다시 읽을 수 있는 문서로 묶은 데 있다.

## 테스트보다 실제 실행에서 더 위험한 결함을 발견했다

프로젝트 기록에는 10일 동안 281개 commit과 실행 중 발견한 결함 27건이 남아 있다. 최종 테스트는 unit·web 804개와 integration
190개로 총 994개였지만, 위험한 문제 상당수는 실제 데이터와 재시작을 겪은 뒤 드러났다.

| 실행에서 드러난 문제 | 수정하며 얻은 기준 |
|---|---|
| 실패한 JOB 슬롯이 재시도를 계속 막음 | 성공과 시도 중 상태를 구분하고 retry 가능한 원장으로 변경 |
| BRK/B 같은 symbol 하나가 batch 전체를 중단 | 외부 source별 symbol 정규화와 개별 실패 격리 |
| 여러 보유 position 중 하나만 exit | 단건 테스트가 아니라 복수 position fixture 추가 |
| persona가 다른 계좌로 기록 | 문자열 기본값 대신 계좌·persona 계약을 한곳에서 결정 |
| 하루 데이터를 통째로 지우다 FK 실패 | 재실행을 delete가 아닌 idempotent upsert로 설계 |
| critic 반려 값이 enum과 불일치 | LLM 구조화 출력과 내부 ontology 경계 고정 |
| screening 점수 때문에 매도가 수학적으로 불가능 | 분기별 도달 가능성을 실제 분포로 검증 |
| 테스트가 개발자 환경 파일을 읽음 | test 설정과 실제 secret 경계를 분리 |

반복된 교훈은 세 가지였다. 데이터가 없다는 것은 0이 아니고, 외부 데이터 정책은 provider마다 달라야 하며, 정적 검색으로 코드를
찾았다고 실제 호출 경로까지 확인한 것은 아니다.

## 관리자 관제실은 원장을 읽는 운영 화면이다

![14개 JOB과 판단·승인·비용·장중 감시 상태를 한 화면에서 읽는 Quantinue 관리자 관제실](/assets/projects/quantinue/control-room.webp)

관리자 관제실은 단순한 통계 dashboard가 아니다. 오늘 어떤 JOB이 성공·실패·실행 중인지, 전략가 판단이 critic을 얼마나
통과했는지, 신규 주문과 방어선이 몇 건인지, LLM 비용이 일 상한 안에 있는지를 같은 슬롯 기준으로 읽는 운영 화면이다.

| 관리자 화면 | 운영 질문 |
|---|---|
| 관제실 | 오늘 14개 JOB이 모두 끝났고 어디서 오래 걸렸는가 |
| 일일 review | 판단·승인·주문·방어선과 비용이 원장 수치와 맞는가 |
| 장중 감시 | 보유 종목, 최근 판단과 방어선 실행이 살아 있는가 |
| 판단과 반박 | 공격형·안정형 판단과 critic의 반려 근거는 무엇인가 |
| 계좌 곡선·총람 | 계좌별 성향과 평가 금액은 어떻게 달라졌는가 |
| 작동 로그·운영 기준 | 실패 원인과 현재 switch·schedule은 무엇인가 |

화면 자체도 검증 대상이었다. 과거 슬롯을 열 때 cycle 기준이 빠져 다른 날의 실험 행이 섞였고, 일부 JOB만 실행된 날을 전체 체인
완주처럼 표시했으며, retry의 시작 시각이 갱신되지 않아 14.5초 작업을 9.8시간으로 보여준 적도 있었다. 이를 원장과 대조해
slot filter, 실행 분모와 attempts 시각을 바로잡았다. 그래서 관제실 숫자는 화면에 보인다는 이유로 믿지 않고 tb_job_run과
일치할 때만 운영 증거로 사용했다.

관리자 쓰기 기능은 계좌 관리와 실패 슬롯 잠금 해제처럼 복구에 필요한 범위로 제한했다. 일반 사용자 화면과 관리자 관제 화면을
분리하고, 로그인 후 역할에 따라 진입 경로를 나눈 것도 조회 편의보다 잘못된 운영 조작을 줄이기 위한 경계였다.

## 6거래일 운영 결과를 어떻게 읽었나

![2,000개 universe가 후보·AI 판단·critic 검토를 거쳐 62건의 체결이 된 운영 퍼널](/assets/projects/quantinue/operation-funnel.webp)

| 지표 | 2026-07-20~27 누적 |
|---|---:|
| 전체 universe | 2,000종목 |
| screening 후보 | 222건 |
| AI 판단 | 342건: 매수 266, 보류 49, 매도 27 |
| critic 검토 | 323건: 통과 222, 반려 57, 보류 44 |
| 주문·체결 | 62건·62건 |
| AI 비용 | 가격 계측 후 4일간 0.53달러, 일 상한 3달러 |
| 자동 테스트 | 994개 |

공격형 세 계좌는 약 -0.55%~-0.65%, 안정형 두 계좌는 +0.02%~+0.19%, 합산은 -0.34%였다. SPY 참고선은 같은 6거래일 기준 -0.44%였다.
기간은 같지만 우위의 근거로는 쓸 수 없다. 6거래일은 전략 우위를 말하기에 너무 짧고, MockBroker는 지정가가 그대로 체결되며 slippage와 실제 유동성을 재현하지 않는다.
따라서 이 비교는 persona별 동작 차이를 관찰한 스냅샷이지 초과 수익의 증거가 아니다.

### 모의 운용 손익은 관리자 페이지에서 확인했다

![관리자 페이지의 운용 계좌 합산 평가액과 SPY 참고선](/assets/projects/quantinue/account-performance.webp)

관리자 페이지는 tb_account_equity_daily에 매일 저장된 현금과 보유 종목 평가액을 합쳐 계좌 곡선을 그린다. 따라서 아래 수치는
발표를 위해 따로 계산한 예상 수익이 아니라 **모의 계좌 원장에 실제로 기록된 평가손익**이다. 다만 실제 자금을 거래한 실현
손익은 아니며, 열린 position의 평가액까지 포함한다.

| 구분 | 시작 기준 | 최종 기록 | 해석 |
|---|---:|---:|---|
| 공격형 3계좌 | 각 계좌 초기 자본 | -0.55%~-0.65% | 같은 입력에서도 높은 매수 성향이 하락 구간에 더 크게 노출됨 |
| 안정형 2계좌 | 각 계좌 초기 자본 | +0.02%~+0.19% | critic과 보수적 allocation을 더 많이 통과한 결과 |
| 운용 5계좌 합산 | 360,000달러 | -0.34% | 반올림 수익률 기준 약 -1,224달러의 평가손익 |
| SPY 참고선 | 07-20을 100으로 지수화 | -0.44% | 같은 6거래일이지만 표본이 짧아 우위의 근거는 아님 |

여기서 수익과 손실은 매일 같은 방식으로 평가한 **시뮬레이션 결과**라는 의미에서 숨기지 않고 공개한다. 그러나 수수료, spread,
slippage, 부분 체결과 시장 충격이 빠진 MockBroker 결과이므로 실제 매매 손익보다 유리하게 측정될 수 있다. 관리자 화면에서도
퍼센트만 보여주지 않고 평가액 곡선, 보유 position과 체결 timeline을 함께 연결한 이유다.

공격형과 안정형의 방향이 갈린 점은 persona 설정이 실제 주문 결과까지 영향을 줬다는 증거다. 반면 어느 persona가 더 좋은
전략인지는 알 수 없다. 최소 수개월의 동일 기간 표본, 동일한 benchmark와 체결 비용을 포함한 뒤에야 성향별 성과를 비교할 수 있다.

### 이 프로젝트에서 성과라고 부를 수 있는 것

| 성과의 층 | 확인한 결과 | 주장하지 않는 것 |
|---|---|---|
| 제품 | 실물 데이터에서 모의 체결까지 매일 한 흐름으로 연결 | 실제 자금 운용이나 투자 서비스 출시 |
| 엔지니어링 | 14개 독립 JOB, 멱등 원장, 비용·중복 주문·실행 owner 경계 | 모든 장애에 대한 완전 무인 복구 |
| AI 통제 | 두 persona의 독립 판단과 critic 18% 반려를 기록 | critic이 사실성이나 수익을 보장한다는 주장 |
| 운영 | 6거래일 원장, 외부 heartbeat와 down·up 사건 확인 | 99.38%를 장기 SLA로 해석하는 것 |
| 품질 | 994개 자동 test와 실제 runtime 결함 27건 수정 | test 수만으로 운영 안전성이 증명됐다는 주장 |
| 학습 | 판단·근거·비용·결과를 다음 실험에 재사용할 구조 | 6거래일 수익률로 전략 우위를 결론 내리는 것 |

수익률 대신 가장 명확한 성과는 시스템을 다시 실험할 수 있게 만든 것이다. 입력 hash, prompt·policy version, 판단과 결과가 원장에
남아 있어 손절선을 바꾸거나 critic 문턱을 조정했을 때 같은 구간을 replay해 비교할 기반이 생겼다. 아직 장기 표본을 모으지
못했으므로 이는 완료된 성과 개선 loop가 아니라 **검증 가능한 다음 실험의 조건**이다.

## 운영 중 노트북 sleep도 하나의 사건이었다

관리자 화면은 JOB, 계좌, 주문과 비용을 보여주고, Telegram은 일일 요약·실패·방어선 발동을 알린다. Healthchecks.io에는 5분마다
heartbeat를 보내 프로세스 자체가 멈춘 상태를 외부에서 감지하게 했다.

실제 운영 중 노트북 sleep 또는 네트워크 단절로 09:03 이후 heartbeat가 끊겼고, 09:13 down 알림이 발생한 뒤 09:36에 복구됐다.
7월 가동률은 99.38%였다. 높은 수치보다 중요한 점은 애플리케이션 안의 로그만으로는 프로세스가 죽은 상황을 알릴 수 없다는 것을
직접 확인한 것이다.

## 안전을 위해 일부러 켜지 않은 것이 있다

- 실제 주문 switch는 OFF다. Alpaca paper adapter는 남아 있지만 live endpoint는 거부하고, submit에는 broker mode와 trading enabled의 이중 잠금이 필요하다.
- 일일 LLM 예산은 3달러이며 가격을 모르는 model이면 시작을 막는다.
- rejudge와 stream은 구현·시험 범위와 운영 활성화 범위를 분리해 기본 OFF로 뒀다.
- laptop 기반이라 재부팅·sleep·네트워크 복구에 사람 손이 필요하다.
- 타인의 자금 운용과 투자 권유는 프로젝트 범위가 아니다.

이 제한은 미완성 기능을 숨기기 위한 문구가 아니다. 금융과 AI가 만나는 시스템에서는 무엇을 할 수 있는지보다 무엇을 아직
보장하지 않는지를 먼저 드러내야 한다고 판단했다.

## 회고: 계속할 것, 아쉬웠던 것, 다시 한다면

### 계속할 것

- AI가 잘하는 해석과 코드가 지켜야 하는 예산·중복·exit 규칙을 분리한다.
- 성공 결과뿐 아니라 반려·보류·실패와 비용도 같은 원장에 남긴다.
- 내부 Telegram과 외부 Healthchecks처럼 장애를 감지하는 주체를 나눈다.
- 화면 지표는 원장과 대조하고, 구현·시험·운영 활성화 상태를 별도로 표시한다.

### 아쉬웠던 것

- 만드는 데 약 3주를 사용해 실제 운영은 6거래일에 그쳤다. 성과 검증은 시작 단계였다.
- T+5 회고는 결과가 닷새 뒤 생기는데 후반에 연결해 최종 시점 tb_review가 0건이었다.
- laptop 한 대에서 실행해 sleep·network·재기동에 사람 손이 필요했다.
- 투자 방법론과 persona는 조사했지만 실제 판단 source는 뉴스·공시·거시 지표 중심에 머물렀다.
- 팀별 담당을 합치는 과정에서 원본·snapshot·시간 컬럼 계약을 더 일찍 고정하지 못했다.

### 다시 한다면

1. 개발 3주 뒤 남은 6거래일만 운영하지 않고, 개발과 검증 기간을 처음부터 분리한다.
2. T+5 회고처럼 결과가 늦게 생기는 기능을 첫 주부터 켜 충분한 표본을 확보한다.
3. 뉴스·공시 source의 계보 완성률을 schema 존재가 아닌 실제 row coverage로 gate한다.
4. 단일 노트북을 벗어나 재시작과 무인 복구가 가능한 실행 환경을 먼저 만든다.
5. MockBroker에 spread, slippage와 부분 체결을 추가해 체결 가정을 더 보수적으로 만든다.
6. rejudge는 비용, 중복 dispatch와 다음 거래일 안정성 기준을 통과한 뒤 단계적으로 활성화한다.
7. 수익률보다 데이터 누락, 판단 재현, 복구 시간과 정책 위반 건수를 핵심 운영 지표로 둔다.

개인적으로는 회고를 마지막 보고서 작성으로 생각하지 않게 됐다. 결과가 늦게 나오는 기능일수록 첫날부터 가동해야 하고,
dashboard 숫자도 근거 테이블과 대조돼야 하며, 기능이 구현됐다는 사실과 운영에서 충분히 검증됐다는 사실은 다르다. Quantinue의
회고는 잘한 일을 정리하는 문서보다 다음 프로젝트의 일정과 완료 조건을 바꾸는 입력에 가깝다.

Quantinue에서 가장 의미 있었던 결과는 AI가 종목을 맞혔다는 주장이 아니다. 실물 데이터가 들어와 판단되고, 반박되고, 규칙으로
줄어들어 모의 체결과 원장으로 남는 전체 경로를 운영해 본 것이다. 그 과정에서 **AI의 역할을 제한하고 모든 판단을 기록하며,
짧은 관측 결과를 긴 성과로 과장하지 않는 기준**을 얻었다.
