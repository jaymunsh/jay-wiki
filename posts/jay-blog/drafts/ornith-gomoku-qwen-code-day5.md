Day 4가 끝났을 때 온라인 대기방과 대기실은 화면만 존재했다. 방을 만들고 준비 버튼을 누를 수는 있었지만, 상대 선수는 같은 브라우저 메모리 안에서 흉내 낸 값이었다. 다른 브라우저를 열어도 서로의 방을 볼 수 없었고, 오목판의 상태를 전달할 서버도 없었다.

Day 5에는 이 경계를 실제 네트워크로 옮겼다. 한 브라우저가 방을 만들고 다른 브라우저가 들어온 뒤, 각자 흑과 백으로 한 수씩 놓는다. 서버가 색과 턴, 착수 가능 여부를 판단하고 두 화면에 같은 상태를 보낸다. 외부 인터넷에 공개하거나 계정과 랭킹을 붙이는 단계는 아니지만, 처음으로 화면 속 `로컬 mock`이 실제 WebSocket 연결로 바뀌었다.

결과만 보면 목표는 통과했다. 서버 테스트 17개, 두 브라우저 온라인 E2E 1개, 기존 단위 테스트 90개와 브라우저 회귀 25개가 모두 성공했다. 하지만 3~4시간 정도로 예상했던 본 구현 Goal의 실제 활성 시간은 **11시간 16분 35.769초**였다. 이후 실제 기기 접속을 확인하려고 연 후속 LAN 검증 Goal도 **2시간 41분 27초** 실행됐다. 두 Goal의 측정 가능한 활성 시간을 합치면 **13시간 58분 2.769초**다. 59번의 자동 compact를 거친 본 구현에는 커밋과 테스트 통과 기록이 남았지만, 마지막 완료 제안은 확정되지 않았고 Goal은 evidence catalog 한도에 걸린 상태다.

이번 기록은 “온라인 연결에 성공했다”는 결과보다 그 한 단계와 후속 확인에 왜 측정 가능한 Goal 활성 시간만 약 14시간이 필요했는지를 함께 살펴본다. 두 Goal 뒤에 `/goal` 없는 일반 요청으로 진행한 서버 상태 확인은 이 합계에 포함되지 않는다.

# 오목 웹앱 Day 5 구현 계획 — 두 브라우저 온라인 대국 수직 흐름

상태: **실행 준비 완료 / 구현 미시작**. 이 문서는 3~4시간짜리 단일 `/goal`의 범위를 정한다. 체크박스는 실제 코드와 검증 증거가 있을 때만 갱신한다.

## 1. Day 5의 한 문장 목표

같은 서버에 접속한 독립 브라우저 두 개가 방 생성·입장·준비·시작을 거쳐 흑과 백으로 번갈아 착수하고, 서버가 판정한 동일한 보드 상태를 보게 만든다.

Day 5는 온라인 기능의 첫 수직 조각이다. 대기방 UI를 더 꾸미거나 모든 운영 기능을 넣는 날이 아니다. 이 조각이 통과하면 같은 Mac의 두 브라우저 대국은 자동 검증되고, 같은 내부망의 다른 기기에서도 서버 주소로 접속해 한 판을 진행할 수 있는 구조가 생긴다. 실제 두 기기 검증을 하지 못했다면 “LAN 가능”으로 추정하지 않고 수동 검증 대기로 기록한다.

## 2. 실험 조건과 책임 구분

- Day 1~3의 `IMPLEMENTATION_PLAN`은 사용자 설명에 따라 GPT luna-xhigh가 작성했고, 앱 개발은 로컬 LLM이 수행했다.
- Day 4 계획·디렉터리 정리와 이 Day 5 계획은 외부 AI 보조로 작성했다. 계획 작성 시간을 로컬 LLM의 구현 실적으로 합산하지 않는다.
- Day 5의 코드 수정, 테스트 작성, 오류 복구와 보고서는 Ornith + Qwen Code 로컬 환경에서 수행하는 것을 기본으로 한다.
- 사람은 `/goal` 시작·중단, 네트워크 환경 제공, 두 번째 실제 기기 접속, 결과 검수를 맡는다. 직접 수정하거나 구체적인 해결책을 제공했다면 보고서에 기록한다.
- 시작 시 모델명, 추론 설정, context 조건을 기록하고 실행 도중 바꾸지 않는다. 모델을 바꿨다면 구간을 분리한다.
- 목표 실행은 **3시간을 기본 예산, 4시간을 절대 상한**으로 둔다. 3시간 시점부터 새 기능을 시작하지 않고 검증·문서·정리에 집중한다.
- 자동 연장이나 “완료될 때까지 계속”을 사용하지 않는다. 4시간에 도달하면 통과한 마지막 게이트에서 멈추고 미완료를 그대로 보고한다.

## 4. 필수 범위와 보류 범위

### 이번 `/goal`에서 반드시 완성할 것

1. 정적 파일과 WebSocket을 함께 제공하는 로컬 Node 서버.
2. 서버가 관리하는 방 목록, 2인 입장, 퇴장, 준비, 시작 상태.
3. 브라우저별 고유 선수 ID와 서버가 정한 흑·백 배정.
4. 서버 권위의 게임 상태와 착수 검증.
5. 두 독립 브라우저에서 방 생성→입장→준비→시작→흑 1수→백 1수 동기화.
6. 잘못된 턴, 점유 칸, 보드 밖 착수를 서버가 거절하고 상태를 바꾸지 않음.
7. 서버를 `0.0.0.0`에 바인딩하고 클라이언트가 현재 페이지의 host로 WebSocket 주소를 구성.
8. 자동화된 두 브라우저 E2E와 실행·성능 기록.

### 필수 게이트가 일찍 끝났을 때만 확장할 것

- 여러 수를 이어 승리까지 도달하는 자동 E2E.
- 서버가 이미 계산한 종료 상태와 승리선을 두 브라우저에 함께 표시하는 결과 UX.
- 상대가 게임 중 나갔을 때 대기실 복귀 또는 명시적인 종료 메시지.

### Day 5에서 다루지 않을 것

- 인터넷 공개 배포, TLS, 포트 포워딩, NAT 통과.
- 로그인, 계정, DB 저장, 랭킹, 관전자, 자동 매칭.
- 재접속 복원, 장시간 연결 안정화, 서버 재시작 복구.
- 채팅 네트워크 동기화, 타이머 동기화, 재대결, 기권·무르기 프로토콜.
- 봇 알고리즘 개선, 대규모 UI 재설계, 프레임워크 전환.
- Day 4의 R5·R9를 이번 필수 게이트에 끼워 넣는 작업.

## 5. 권장 구조

새 서버는 Node ESM으로 만들고 WebSocket 구현은 검증된 `ws` 패키지를 런타임 의존성으로 사용한다. 브라우저는 표준 `WebSocket` API를 사용한다. 정적 서버와 WebSocket 서버를 한 프로세스·한 포트에 두면 내부 IP 접속 주소와 테스트 기동이 단순해진다.

```text
server/
  index.mjs                 # HTTP 정적 파일 + WebSocket upgrade + 종료 처리
  room-service.mjs          # 서버 권위 방·선수·게임 상태
  protocol.mjs              # 메시지 타입, payload 검사, 오류 코드
src/multiplayer/
  room-manager.mjs          # 기존 로컬 mock, 단위 테스트 기준으로 보존
  websocket-room-client.mjs # UI가 쓰는 서버 transport
tests/
  server/*.test.mjs         # 방·착수 정책의 순수/통합 검사
  browser/day5-online.test.mjs
```

파일명은 구현 중 기존 구조에 맞게 조정할 수 있다. 핵심은 UI, 전송 계층, 서버 상태를 분리하고 서버가 유일한 판정 주체가 되는 것이다. 클라이언트가 보드에 먼저 돌을 확정한 뒤 서버 결과를 맞추는 방식은 이번 범위에서 사용하지 않는다.

`package.json`에는 최소한 다음 역할의 명령을 둔다.

```text
npm start              기존 4173 정적 서버가 필요하면 호환용으로 유지
npm run start:online   HTTP + WebSocket 서버 기동
npm run test:server    서버 단위·통합 검사
npm run test:online    두 브라우저 온라인 E2E
```

기존 `npm test`, `npm run test:browser`, `npm run test:all`의 의미를 갑자기 바꾸지 않는다. 전체 검증 명령을 추가한다면 README에 정확히 기록한다.

## 6. 최소 프로토콜

모든 메시지는 JSON 객체이며 `type`, 요청을 구분할 `requestId`, 필요한 payload를 가진다. 서버 응답에는 성공 이벤트 또는 구조화된 오류가 있어야 한다. 내부 예외 문자열과 stack을 브라우저에 그대로 보내지 않는다.

클라이언트→서버 최소 명령:

- `room:list`
- `room:create` — 선수 이름, 방 이름, 규칙
- `room:join` — roomId, 선수 이름
- `room:leave`
- `ready:set` — boolean
- `game:start`
- `game:move` — `{ x, y }`

서버→클라이언트 최소 이벤트:

- `session:welcome` — 안정적인 connection/player ID
- `room:list`
- `room:state` — 선수, host, ready, status
- `game:state` — players/color, board, turn, history, status
- `error` — code, message, requestId

서버는 연결별 player ID와 현재 room을 알고 있어야 한다. 클라이언트가 보낸 player ID, 색, 턴, moveNo, 전체 board는 신뢰하지 않는다. 이름은 공백 제거 후 길이 제한을 둔다. 알 수 없는 type, 잘못된 JSON, 범위를 벗어난 좌표에도 프로세스가 죽지 않아야 한다.

## 7. 구현 순서와 시간 상자

- [ ] HEAD, 변경 파일, Node/npm 버전, 모델·추론 설정, 시작 시각을 `docs/reports/DAY5_PROGRESS.md`에 기록.
- [ ] Day 4의 90/90, 24/24 기준선을 직접 재실행.
- [ ] 목표 산출물 경로 `artifacts/day5/<run-id>/`와 로그 파일을 정함.
- [ ] 4시간 종료 시각을 기록하고 3시간 경고 지점을 둠.

기준선 환경 문제를 20분 안에 고치지 못하면 앱 버그와 구분해 기록한다. 무한 설치·서버 재기동 루프에 들어가지 않는다.

### Phase 1 — 서버와 방 수명 주기, 최대 55분

- [ ] HTTP 정적 제공과 WebSocket 연결을 한 포트에서 기동.
- [ ] `GET /health` 또는 동등한 health check가 서버 상태를 반환.
- [ ] 방 목록, 생성, 입장, 준비, 시작, 퇴장 구현.
- [ ] 2명 제한, host만 시작, 두 명 모두 준비 조건을 서버에서 검증.
- [ ] 연결 종료 시 방 선수 상태를 정리하고 관련 사용자에게 방송.
- [ ] 순수 서비스 또는 실제 WebSocket 통합 테스트로 정책 확인.

로컬 `RoomManager` 코드를 서버에서 억지로 인스턴스 하나 공유하지 않는다. 기존 테스트에서 유용한 정책은 가져오되 서버는 연결별 사용자를 구분하는 독립 상태를 가진다.

### Phase 2 — 서버 권위 게임 상태와 착수, 최대 55분

- [ ] 게임 시작 시 서버가 흑·백을 한 번 배정하고 `createGameState`로 상태 생성.
- [ ] `game:move` 송신자의 색과 현재 턴이 같은지 확인.
- [ ] `applyMove`를 서버에서 호출해 규칙·점유·범위·승리 판정 재사용.
- [ ] 성공한 착수 뒤 전체 `game:state` 또는 재구성 가능한 상태를 두 선수에게 방송.
- [ ] 실패한 착수는 요청자에게 오류를 보내고 authoritative state를 변경하지 않음.
- [ ] 직렬화 결과에 서버 전용 객체, WebSocket, 비밀값이 섞이지 않는지 확인.

기존 게임 모듈이 브라우저 전용 API에 의존하지 않는다는 가정을 테스트로 증명한다. 공유가 깨지면 규칙을 복제하지 말고 작은 순수 경계를 만든다.

### Phase 3 — UI transport 교체와 두 브라우저 흐름, 최대 60분

- [ ] 온라인 대기방 진입 시 `WebSocketRoomClient` 연결.
- [ ] 현재 페이지가 `http:`면 `ws:`, `https:`면 `wss:`를 쓰고 `location.host`에서 주소 구성.
- [ ] 연결 중, 연결됨, 연결 실패, 상대 퇴장 상태를 화면에 표시.
- [ ] 방 목록·생성·입장·준비·시작 UI를 서버 이벤트에 연결.
- [ ] 게임 시작 이벤트로 기존 보드 화면에 진입하고 봇 예약을 만들지 않음.
- [ ] 내 색이 아닌 턴에는 보드 입력을 막고, 서버 응답 뒤 보드·수순·턴을 렌더링.
- [ ] 홈 이동이나 방 나가기에서 listener와 socket을 중복 등록하지 않음.

기존 로컬 mock 버튼을 실제 온라인처럼 보이게 유지하지 않는다. 서버가 없으면 연결 실패를 읽을 수 있어야 하고, 봇 대국은 계속 독립적으로 동작해야 한다.

### Phase 4 — 자동 E2E·LAN 준비·보고, 남은 시간 최소 50분 확보

- [ ] 테스트가 임의의 빈 포트에서 자신이 소유한 서버를 시작하고 `finally`/teardown에서 종료.
- [ ] 독립 browser context A와 B를 사용. 같은 page 두 개만 쓰거나 storage를 공유하지 않음.
- [ ] A 방 생성→B 목록 확인·입장→둘 준비→A 시작.
- [ ] A/B의 player ID와 색이 다르고 두 화면의 room/game ID가 같은지 확인.
- [ ] 흑이 중앙에 착수한 뒤 양쪽 board/history/turn 동일 확인.
- [ ] 백이 다른 합법 위치에 착수한 뒤 다시 동일 확인.
- [ ] 잘못된 턴 또는 점유 칸 요청이 거절되고 양쪽 수순 수가 그대로인지 확인.
- [ ] 페이지 오류, WebSocket 오류, 서버 stderr와 종료 code 수집.
- [ ] 기존 90개 단위, 24개 Day 4 브라우저 회귀를 다시 통과.

두 번째 실제 기기가 준비돼 있다면 같은 Wi-Fi에서 홈→방 입장→서로 한 수 이상까지 수동 확인한다. 방화벽 승인, 게스트 Wi-Fi 격리, VPN은 앱 구현과 별도 환경 변수로 기록한다. 기기가 없다면 자동화된 두 context 통과와 bind 확인까지만 적고 실제 LAN 검증은 **대기**로 남긴다.

## 외부 패키지 대신 WebSocket 프레임부터 직접 만들었다

계획서의 권장안은 검증된 `ws` 패키지를 사용하는 것이었다. Qwen Code는 다른 선택을 했다. 프로젝트가 외부 CDN과 런타임 의존성을 쓰지 않는다는 기존 방향을 이어 가겠다며 Node의 `http`와 `crypto`만으로 최소 WebSocket 서버를 구현했다.

서버는 하나의 포트에서 정적 HTML과 WebSocket upgrade를 함께 처리한다. handshake에서는 `Sec-WebSocket-Key`에 RFC 6455 GUID를 붙여 SHA-1 digest를 만들고, 연결 뒤에는 클라이언트의 masked frame을 해제한다. text, binary, ping, pong, close opcode도 최소 범위에서 처리한다. 그 위에 방과 게임 규칙을 아는 `RoomService`를 분리했다.

~~~mermaid
flowchart TB
  A[브라우저 A] -->|WebSocket JSON| G[WebSocketGateway]
  B[브라우저 B] -->|WebSocket JSON| G
  G --> R[RoomService]
  R --> S[game/state.js]
  S --> R
  R -->|권위 상태 broadcast| G
  G --> A
  G --> B
~~~

이 구조에서 브라우저는 자신의 색이나 다음 턴을 확정하지 않는다. `RoomService`가 연결 ID와 방, 선수 색을 관리하고 기존 `game/state.js`의 `applyMove`를 호출한다. 성공한 착수 뒤에는 서버 상태가 두 연결에 방송되고, 잘못된 턴이나 점유된 칸은 오류로 돌아온다.

클라이언트에는 기존 로컬 `RoomManager`와 비슷한 이벤트 인터페이스를 가진 `WebSocketRoomClient`를 추가했다. URL도 `localhost`로 고정하지 않고 현재 페이지가 HTTP면 `ws://`, HTTPS면 `wss://`를 골라 `location.host`에 연결한다. 덕분에 같은 서버에서 HTML을 연 기기는 접속한 host와 port를 그대로 WebSocket에도 사용한다.

직접 만든 전송 계층은 실험 범위에는 맞지만 범용 WebSocket 서버는 아니다. 코드에도 continuation frame은 지원하지 않는다고 적혀 있다. 압축, 메시지 크기 제한, 느린 클라이언트 대응과 더 세밀한 close 처리가 필요한 운영 환경이라면 검증된 라이브러리나 프록시 계층을 다시 검토해야 한다.

## 첫 서버 테스트 13개는 모두 첫 메시지에서 멈췄다

서버와 테스트를 처음 연결했을 때 방 수명 주기 7개와 착수 정책 6개, 모두 13개가 같은 오류로 실패했다.

~~~text
Error: 메시지 대기 타임아웃
at tests/server/helpers.mjs
~~~

테스트는 WebSocket 연결이 열리기 전에 메시지를 보내고 있었다. Node 24의 WebSocket client가 open 전에 보낸 데이터를 알아서 보관할 것이라는 가정이 맞지 않았다. 테스트 helper에 연결 준비 Promise를 두고, `send()`가 open 이후 실제 전송하도록 바꾸면서 첫 단계가 풀렸다.

그다음에는 서버가 보내는 메시지 크기가 126바이트를 넘을 때 frame header가 깨지는 문제가 나타났다. 짧은 frame만 생각하고 2바이트 header를 잡았는데, 126바이트 이상은 확장 길이 필드가 필요했다. header를 최대 14바이트로 확보하고 실제 길이에 맞는 구간만 잘라 payload와 합치도록 고쳤다.

이 과정에서 정확한 문자열을 찾지 못해 edit가 연속으로 실패하기도 했고, 임시 debug 파일을 만들어 실제 turn과 message 순서를 출력했다. 최종 커밋에서는 `tests/server/_dbg.test.mjs`와 `server/dbg-debug.mjs`를 제거했다. 결과 코드만 보면 곧바로 17개 테스트가 통과한 것처럼 보이지만, 실제 시간의 상당 부분은 전송 전에 메시지가 사라지는 문제와 frame 길이 문제를 분리하는 데 쓰였다.

## 두 브라우저는 같은 메모리를 공유하지 않았다

온라인 E2E는 같은 페이지 객체에 선수 두 명을 주입하는 방식으로 만들지 않았다. Playwright에서 독립 browser context A와 B를 열고, 테스트가 임의의 빈 포트에 서버를 직접 기동했다. 두 context의 WebSocket 연결이 모두 열린 것을 `/health`로 확인한 다음 다음 순서로 움직였다.

1. A가 대기방으로 들어가 방을 만든다.
2. B의 방 목록에 입장 버튼이 나타나면 같은 방에 들어간다.
3. B와 A가 차례로 준비한다.
4. 호스트 A가 게임을 시작한다.
5. A가 흑으로 H8에 둔다.
6. B가 백으로 H9에 둔다.
7. A가 이미 점유된 H8을 다시 눌러 서버 거절을 확인한다.

매 착수 뒤에는 두 화면에서 `board`, `turn`, `moveHistory`, `gameStatus`를 읽어 완전히 같은지 비교했다. 불법 착수 뒤에는 돌과 수순 수가 늘지 않아야 하고, A 화면에는 오류 배너가 보여야 한다. 서버와 브라우저는 테스트의 `finally`에서 종료한다.

![호스트 브라우저에서 흑 H8과 백 H9가 동기화되고 불법 착수 오류가 표시된 화면](/api/wiki-assets/3ec6a7d9-2bea-4840-84a6-3b0fd03b50dd)

![참가자 브라우저에서도 같은 두 수와 다음 턴이 표시된 화면](/api/wiki-assets/67fcc968-6370-46a1-af5e-cb01c531e06f)

두 캡처에는 모두 H8의 흑돌과 H9의 백돌, 다음 차례가 흑이라는 상태가 보인다. A 화면에는 점유된 H8을 다시 누른 뒤 받은 `불법 착수: (7,7)` 오류가 남아 있고 B에는 없다. 오류는 요청자에게만 전달하되 서버의 보드 상태는 양쪽에서 같다는 의미다.

다만 캡처 산출물에는 문제가 있다. 보고서에는 대기실의 `a-room.png`, `b-room.png`와 두 수 뒤의 파일 두 장을 별도로 만들었다고 적혀 있지만, SHA-256을 비교하면 A의 두 파일이 같고 B의 두 파일도 같다. 테스트가 네 번의 screenshot 호출을 모두 흐름 마지막에 실행했기 때문이다. 이번 글에서는 네 장을 서로 다른 단계의 증거처럼 사용하지 않고, 실제로 서로 다른 최종 A/B 화면 두 장만 실었다.

## 네 개 게이트는 통과했지만 G4에는 괄호가 붙는다

최종 검증은 네 suite로 나뉜다.

| 검증 | 결과 | 수행시간 |
| --- | --- | --- |
| 기존 규칙·상태·봇·로컬 RoomManager 단위 테스트 | 90/90 | 85.9ms |
| 서버 방·착수·WebSocket frame 테스트 | 17/17 | 410.0ms |
| 두 브라우저 온라인 E2E | 1/1 | 5.029초 |
| 기존 브라우저 회귀와 Day 5 E2E | 25/25 | 35.811초 |

Day 4의 브라우저 테스트는 24개였다. Day 5 온라인 E2E가 같은 브라우저 glob에 들어가면서 회귀 suite는 25개가 됐다. 따라서 표의 온라인 1개와 브라우저 25개를 더해 서로 다른 테스트 26개라고 말하면 중복 계산이다.

G1~G3는 요구한 동작을 자동화로 확인했다. G4도 서버가 `0.0.0.0`에 bind하고, production code에 `localhost`가 고정되지 않았으며, HTML과 WebSocket이 같은 host와 port를 사용하는 데까지 통과했다.

하지만 실제 다른 기기에서 접속하지는 않았다. 기록에는 당시 사설 IPv4 주소로 접속 URL까지 만들었지만, 두 번째 노트북이나 휴대전화에서 방에 들어가 착수한 증거는 없다. OS 방화벽과 Wi-Fi의 기기 간 격리 여부도 확인하지 않았다. 지금 단계의 정확한 표현은 **내부망 대국 완료가 아니라 내부망 접속 준비 완료**다.

## 오래 걸려 여러 번 끊었고, 재개할 때마다 코드를 다시 읽었다

이번 작업을 사흘 동안 한 번에 계속 실행한 것은 아니다. 생각보다 오래 걸려 내가 여러 번 끊었다가 다시 요청했다. 원본 Goal 상태에는 pause 5회와 resume 5회가 남아 있다. 9월 8일 02:47부터 9월 11일 02:34까지의 달력상 경과와, 하네스가 기록한 활성 시간 11시간 16분은 구분해야 한다. 중간에 쉬었던 시간을 모두 모델의 개발 시간으로 셀 수는 없다.

오래 걸린 이유를 검증 하나로 단정하기도 어렵다. 직접 구현한 WebSocket의 오류를 고치는 작업이 있었고, 그와 별개로 같은 파일을 다시 읽고 통과한 상태를 확인하는 호출도 많이 쌓였다. 세션 JSONL에서 assistant가 요청한 도구 호출을 집계하면 다음과 같다.

| 호출 또는 대상 | 요청 횟수 |
| --- | --- |
| 파일 읽기 도구 | 400회 |
| 셸 명령 도구 | 190회 |
| `src/main.js` 읽기 | 33회 |
| 서버 테스트 helper 읽기 | 25회 |
| `server/protocol.mjs` 읽기 | 24회 |
| `server/room-service.mjs` 읽기 | 23회 |
| `IMPLEMENTATION_PLAN_DAY5.md` 읽기 | 21회 |
| `test:browser`가 들어간 셸 호출 | 15회 |
| `test:server`가 들어간 셸 호출 | 10회 |
| `test:online`이 들어간 셸 호출 | 9회 |
| `git status`가 들어간 셸 호출 | 23회 |
| `git log`가 들어간 셸 호출 | 20회 |

이 숫자는 성공적으로 실행된 테스트 횟수나 서로 다른 테스트 수가 아니다. 명령 문자열에 해당 표현이 들어간 호출을 센 값이고, 직접 `node --test`로 실행한 검사는 별도로 더 있을 수 있다. 한 명령에 여러 검사가 있으면 각 행에도 함께 잡힌다. 그렇더라도 파일 재독과 상태 확인이 작업의 큰 부분이었다는 점은 드러난다.

오류를 수정한 직후 관련 테스트를 다시 실행하는 것은 필요하다. 문제는 이미 통과한 검사를 코드 변경 없이 다시 실행하는 구간이다. 마지막 화면에서도 에이전트는 압축된 요약에 모든 작업이 끝났다고 적혀 있음을 읽은 뒤, Git 상태와 커밋을 확인하고 단위·서버·온라인 검사를 다시 돌렸다. 당시 마지막 명령에는 기존 브라우저 회귀 전체가 포함되지 않았는데도 응답은 모든 게이트가 통과했다고 표현했다. 최종 응답의 확신과 그 직전 실제 검증 범위도 구분해야 한다.

59번의 compact와 여러 차례 재개가 있을 때마다 현재 상태를 재확인할 필요는 생긴다. 그러나 기록에서 확인 가능한 파일·커밋·검증 결과를 짧게 이어받지 못하면 읽기와 테스트를 반복하게 된다. 이 반복에 긴 입력 처리와 요약 생성 시간이 다시 붙는다. 이를 모두 불필요한 검증이라고 할 수는 없지만, 전체 실행이 길어진 원인 중 하나로 볼 근거는 있다. 검증만으로 몇 시간을 썼는지는 현재 집계로 분리하지 못했다.

다음에는 각 단계에 통과한 커밋, 실행 명령, 결과, 남은 실패를 함께 남기는 편이 낫다. 재개 시에는 그 이후 코드가 달라졌거나 해결되지 않은 실패가 있을 때 해당 검사를 다시 실행하고, 전체 회귀는 기능 통합 뒤 한 번 수행한다. 완료 판정을 얻기 위해 동일 suite를 계속 반복하는 일은 별도 문제로 다뤄야 한다.

## potential loop 경고는 반복을 멈추라는 신호로 봤다

작업 중에는 `potential loop` 경고도 다시 나타났다. 이 문구는 Qwen 세션 JSONL에 별도 이벤트로 남아 있지 않아 발생 시각과 횟수를 원본 로그에서 확정할 수 없다. 경고를 직접 본 것은 사용자의 관찰이고, 세션에서 확인할 수 있는 것은 경고가 판단했을 법한 반복 패턴이다.

완전히 같은 셸 명령만 세어도 `npm test`가 6회, `npm run test:browser`가 같은 형태로 5회와 3회, `npm run check`가 4회 실행됐다. 서버 전체 테스트와 온라인 테스트, debug script도 동일한 명령이 각각 2~3회 반복됐다. 한편 문자열이 맞지 않아 같은 파일 편집이 연속으로 실패한 기록도 있다. loop detector가 정확히 어느 호출을 보고 경고했는지는 알 수 없지만, 에이전트가 같은 관찰과 행동을 반복하며 상태 변화가 작을 때 경고가 나타났다는 해석은 기록과 어긋나지 않는다.

이 경고를 완전히 피할 수 있다고 보기는 어렵다. 실패를 재현하고 수정 뒤 같은 테스트를 다시 돌리는 과정은 개발에 필요하며, 겉으로는 반복처럼 보여도 두 실행의 코드 상태가 다를 수 있다. 경고 자체를 끄는 것보다 반복할 이유와 중단 조건을 프롬프트와 계획서에 남기는 편이 안전하다.

| 반복 상황 | 다음 Goal에 넣을 중단 조건 |
| --- | --- |
| 같은 편집이 정확한 문자열을 찾지 못함 | 두 번째 실패 뒤 파일의 해당 구간을 다시 읽고 patch 방식을 바꿈 |
| 같은 테스트가 동일 오류로 실패 | 두 번 실패하면 원인 후보와 마지막 로그를 보고서에 남기고 별도 진단으로 전환 |
| 코드 변경 없이 전체 회귀 재실행 | 마지막 통과 커밋 이후 변경 파일이 있을 때만 다시 실행 |
| compact 또는 resume 뒤 처음부터 재검증 | 진행 문서에서 마지막 통과 커밋과 미완료 게이트만 읽고 이어감 |
| 완료 조건을 충족한 뒤 상태 확인 반복 | Git clean·필수 커밋·최종 검증 1회를 확인한 뒤 완료 제안은 한 번만 수행 |

`potential loop`가 뜬 직후 같은 요청을 그대로 다시 보내는 것은 좋은 복구가 아니다. 마지막으로 달라진 코드나 새로 얻은 증거가 없다면 같은 행동을 반복할 가능성이 높다. 그때는 현재 Goal을 계속 밀기보다 “실패한 서버 테스트 한 개의 최초 원인을 찾고, 재현 로그를 남긴다”처럼 목표를 줄이거나 사람이 다음 행동을 지정하는 편이 낫다.

Day 5 계획에도 같은 도구 오류가 두 번 반복되면 호출 방식을 바꾸는 규칙은 있었다. 하지만 전체 Goal은 서버 구현, 테스트, E2E, 보고서와 최종 완료 판정까지 넓었다. 개별 오류의 재시도를 제한해도 단계가 바뀔 때마다 전체 상태 확인이 다시 시작될 수 있었다. 다음에는 오류 재시도 제한과 함께 **단계별 종료점**을 별도 Goal이나 세션으로 분리할 필요가 있다.

## 59번 compact 뒤에도 구현은 이어졌지만 Goal은 스스로 닫히지 못했다

이번 세션은 9월 8일 새벽에 시작해 9월 11일 새벽까지 이어졌다. 작업을 쉬는 동안 Goal은 pause됐지만, 재개할 때마다 같은 목표와 파일 상태를 이어받았다. 대화 context가 커질 때는 59번의 chat compression이 발생했다. 각 압축은 당시 목표, 수정 파일, 통과한 테스트와 다음 작업을 요약해 다음 문맥으로 넘겼다.

자동 compact 덕분에 세션을 새로 열지 않고 구현을 이어갈 수는 있었다. 다만 압축이 Goal의 모든 누적 상태를 비우는 것은 아니었다. 마지막에는 코드·보고서·네 개 커밋이 모두 존재하고 최종 테스트도 다시 통과한 상태에서 `update_goal`이 완료를 제안했지만, Goal은 다음 이유로 `usage_limited`가 됐다.

~~~text
The current Goal revision exceeded the bounded evidence catalog.
Automatic retries cannot recover.
Edit or replace the Goal before resuming it.
~~~

이때 Goal 내부 토큰 사용량은 3천만 예산 중 약 646만으로 21.5%였다. 종료 원인은 토큰 예산 소진이 아니었다. 당시 세션 기록만으로는 증거 목록의 정확한 한도를 알 수 없어 추정으로 설명했다. 이후 공식 소스와 설치된 코드를 확인해 보니 대화 compact와 별개인 Goal 증거 checkpoint가 있었고, 목록 크기에도 명시적인 제한이 있었다. 그 구조와 재개 동작은 아래에 따로 정리했다. 59회의 대화 압축이 직접 원인이었다고 단정할 수는 없다.

화면의 `UpdateGoal` 결과도 완료가 확정됐다는 응답은 아니다. 완료 제안이 독립 검증을 위해 대기열에 들어갔으며, 최종 상태 전이는 아직 반영하지 않았다고 적혀 있다. 이후 상태는 `complete`가 아닌 `usage_limited`다. 따라서 이 글을 쓰는 시점의 결말은 **구현 커밋과 지정 테스트의 통과 기록은 있지만 Goal 종료는 미확정이며, 실제 두 기기 대국도 미검증**인 상태다.

## 이전 세션 기록에도 같은 종료 사유가 남아 있었다

11시간 넘게 실행한 끝에 제한이 나타나니 이번 요청에만 문제가 생긴 것처럼 느껴졌다. 이전 세션의 `goal_state`를 다시 확인하니 같은 프로젝트에서 동일한 종료 사유가 세 번 남아 있었다. 아래 시간은 각 Goal의 `activeTimeMs`이며, 토큰은 Goal 상태에 기록된 `tokensUsed`다. 앞서 집계한 API usage 합계와는 계측 기준이 다르다.

| 발생일 (KST) | 요청 | Goal 활성 시간 | Goal 사용 토큰 | 종료 사유 |
| --- | --- | --- | --- | --- |
| 9월 3일 | 초기 구현 계획 실행 | 2시간 58분 35초 | 7,411,338 | `evidence_catalog` |
| 9월 7일 | Day 4 계획 실행 | 4시간 26분 6초 | 16,062,746 | `evidence_catalog` |
| 9월 11일 | Day 5 계획 실행 | 11시간 16분 36초 | 6,460,641 | `evidence_catalog` |

세 Goal의 토큰 예산은 모두 3천만이었다. Day 5는 Day 4보다 오래 실행됐지만 Goal에 집계된 토큰은 더 적었다. 종료 당시 turn 수도 초기 구현과 Day 5는 각각 3회, Day 4는 22회였다. 오래 실행했다거나 turn이 많다는 이유만으로 제한을 설명하기 어렵다. 세 기록에서 공통으로 확인되는 직접 원인은 **현재 Goal revision의 evidence catalog 한도 초과**다.

Day 5 JSONL에는 약 13.6MB에 걸쳐 이벤트 2,998개가 남았다. 그중 `tool_result`는 800개, `assistant`는 602개였다. 이는 세션 파일의 이벤트 분류별 개수다. Goal 검증기가 실제로 수집한 증거 항목 수와 같다는 뜻은 아니다. 앞서 센 파일 읽기 400회와 셸 명령 190회 역시 도구 요청 기준의 별도 집계다.

이번에는 서버 구현부터 테스트 작성, 브라우저 연결, 회귀 검사, 아티팩트와 보고서 생성, 커밋과 완료 제안까지 하나의 Goal에 묶였다. 다섯 번 멈췄다가 재개하는 동안에도 같은 Goal ID와 revision 1이 유지됐다. 재개와 compact 뒤 파일과 통과 결과를 다시 확인하는 행동이 누적 기록을 늘렸을 가능성은 있다. 다만 어떤 결과가 catalog에 들어갔는지 확인하지 못했으므로, 반복 검증만이 한도 초과의 원인이라고 단정할 수는 없다.

세션 파일 전체의 크기나 도구 결과 개수를 catalog 상한과 동일시하면 안 된다. “도구 결과 800개가 상한이다”, “59번 compact하면 막힌다”는 결론은 낼 수 없다. `potential loop` 경고와도 구분해야 한다. 반복 행동에 대한 경고를 봤다는 관찰과, Goal 상태에 명시된 종료 사유는 서로 다른 증거다.

다음 실행에서는 서버·방 상태와 서버 테스트, 브라우저 연결과 E2E, 최종 회귀와 보고서, 실제 LAN 검증처럼 결과를 확인할 수 있는 단계에서 Goal을 나누려 한다. 앞 단계의 커밋과 통과 기록을 다음 단계의 기준선으로 넘기면 재검증 범위를 줄일 수 있다. 이것이 제한을 반드시 방지한다는 보장은 없지만, 반복 작업과 한 번에 다뤄야 할 범위를 줄이는 방법은 된다.

## evidence_catalog는 완료 판정에 쓸 증거 목록이다

Qwen Code의 Goal은 모델이 “끝났다”고 말하는 것만으로 완료되지 않는다. 별도 검증기가 대화에 남은 응답과 도구 결과를 보고 완료·차단 제안을 판단한다. 테스트가 통과했다는 설명과 실제 테스트 출력은 증명하는 내용이 다르며, 사용자의 확인이 필요한 조건에는 실제 사용자 메시지가 있어야 한다. 이 판정에 참조할 기록을 제한된 크기로 모아 둔 목록이 evidence catalog다. [Qwen 공식 Goals 문서](https://qwenlm.github.io/qwen-code-docs/en/users/features/goals/#how-a-goal-is-judged)

공식 저장소의 v0.23.0 태그와 현재 설치된 Qwen 번들에서 다음 상수를 확인했다. 아래 숫자는 전체 세션의 최대 길이가 아니라, 검증에 사용할 증거 목록을 구성하는 제한이다. checkpoint로 이전 증거를 요약하므로 “100번 호출하면 무조건 끝난다”는 뜻도 아니다. [v0.23.0 증거 목록 구현](https://github.com/QwenLM/qwen-code/blob/98a9c964158697dd5631d15a62174684ff7bbb53/packages/core/src/goals/goal-evidence.ts#L21)

| 항목 | 코드에서 확인한 값 |
| --- | --- |
| catalog 항목 상한 | 100개 |
| 직렬화된 catalog 항목의 합산 크기 상한 | 24,000바이트 |
| checkpoint 시작 기준 | 항목 80개 또는 19,200바이트, 혹은 이미 잘린 목록 |
| catalog에 담는 각 미리보기의 바이트 상한 | 240바이트 |

대화 compact는 다음 모델 호출에 전달할 문맥을 줄인다. Goal checkpoint는 검증에 쓸 증거를 주장과 참조로 요약하는 별도 과정이다. 공식 문서도 긴 Goal이 증거를 주기적으로 checkpoint로 압축한다고 설명한다. 따라서 “compact가 됐으니 catalog도 비었을 것”이라고 기대하거나, 반대로 “증거에는 압축 기능이 없다”고 설명하면 둘 다 정확하지 않다. [공식 문서의 checkpoint 설명](https://qwenlm.github.io/qwen-code-docs/en/users/features/goals/#commands)

목록을 구성할 때 제한 때문에 필요한 기록이 빠지면 `truncated` 상태가 된다. 완료·차단 제안의 증거를 검사하는 코드에서 이를 `catalog_truncated` 오류로 처리하고, 런타임이 `usage_limited`와 `limitKind: evidence_catalog`로 바꾼다. 최근 세 turn의 증거로 충분한 반복 차단 제안에는 예외가 있지만 모든 제안에 적용되지는 않는다. 후속 LAN 세션의 마지막 제안은 `external` 차단이었으며, 직전 `get_goal` 결과에는 `truncated: true`가 남아 있었다. [증거 검사](https://github.com/QwenLM/qwen-code/blob/98a9c964158697dd5631d15a62174684ff7bbb53/packages/core/src/goals/goal-evidence.ts#L606), [런타임의 제한 상태 전환](https://github.com/QwenLM/qwen-code/blob/98a9c964158697dd5631d15a62174684ff7bbb53/packages/core/src/goals/goal-runtime.ts#L920)

여기까지는 제한이 어떻게 발생하는지에 대한 설명이다. 각 실행에서 checkpoint가 충분한 공간을 확보하지 못한 이유까지 모두 확인한 것은 아니다. 반복 응답이 catalog에 들어간 사실은 관찰할 수 있지만, 특정 모델의 요약 실패나 특정 언어의 바이트 크기를 이번 장애의 단일 원인으로 지목할 근거는 부족하다.

## resume할 수 없다는 앞선 설명도 바로잡는다

처음에는 오류 문구를 읽고 같은 Goal을 resume하면 증거가 그대로 쌓일 것으로 판단했다. 하지만 공식 v0.23.0 소스와 현재 설치된 번들은 증거 제한으로 멈춘 Goal을 resume할 때 **증거 cursor를 재개 시점으로 옮기고, 기존 checkpoint와 정체 횟수를 초기화**한다. 목표와 revision은 유지하지만 이전 증거는 새 완료 제안에서 그대로 인용할 수 없게 된다. 따라서 새 세션이 반드시 필요하다는 앞선 조언은 부정확했다. [재개 시 증거 범위를 초기화하는 코드](https://github.com/QwenLM/qwen-code/blob/98a9c964158697dd5631d15a62174684ff7bbb53/packages/core/src/goals/goal-reducer.ts#L174)

대응은 멈춘 원인에 따라 달라진다. 아래는 공식 명령 동작과 이번 실행에서 얻은 판단을 구분한 것이다.

| 상황 | 대응 |
| --- | --- |
| 사람의 확인을 기다리며 자동 응답이 반복됨 | `/goal pause`로 실행을 멈추고 실제 결과를 먼저 확보한다. 일반 메시지를 입력하는 것만으로는 활성 Goal이 멈추지 않는다. |
| 증거 제한 이후 실제로 진행할 재료가 생김 | 확인한 구현에서는 `/goal resume`으로 새 증거 범위를 시작할 수 있다. 이전 통과 기록을 그대로 인용할 수 없으므로 필요한 증거를 새로 확보해야 한다. |
| 완료 조건 자체에 미래의 사용자 응답이 포함됨 | `/goal edit` 또는 `/goal set`으로 자동 수행 가능한 범위로 고치거나, Goal을 멈춘 뒤 일반 요청으로 분리한다. |
| 단순히 토큰 예산을 늘리려 함 | catalog의 항목·바이트 제한과는 별개이므로 이번 제한의 직접 해결책이 되지 않는다. |

명령의 의미는 [공식 Goals 문서](https://qwenlm.github.io/qwen-code-docs/en/users/features/goals/#commands)에, 활성 Goal 중 일반 입력이 실행을 멈추지 않는다는 설명은 [중단 안내](https://qwenlm.github.io/qwen-code-docs/en/users/features/goals/#interrupting-a-goal)에 있다. 이번 LAN 요청에서는 접속 결과가 여전히 없으므로 resume 기능이 있어도 할 일이 생기지는 않는다. 사람의 확인을 자동 실행 밖으로 빼자는 수정은 이 이유에서 유지한다.

## 새 세션에서 범위를 줄였지만 다시 제한에 걸렸다

당시에는 오류의 `Automatic retries cannot recover` 문구와 Goal을 수정하거나 교체하라는 안내를 보고 새 세션을 택했다. 앞 절의 소스 확인과 resume 동작 정정은 이 후속 실행까지 겪은 뒤에 한 일이다.

이때 외부 AI와 상의해 새 세션에서 남은 LAN 검증만 진행하기로 했다. 구현은 네 개 커밋에 있고 진행·결과 보고서와 Qwen JSONL도 디스크에 남아 있으니, 그 기준을 이어받으면 될 것이라 생각했다. 한도에 걸린 Goal을 그대로 재개하는 대신 새 Goal의 범위를 줄여보자는 판단이었다.

그렇게 정한 요청은 다음과 같다. 전체 계획을 다시 실행하지 말고, 서버를 띄운 뒤 실제 기기 접속을 확인하고 보고서를 남기도록 했다. 이 프롬프트를 새 Qwen 세션에 그대로 입력해 진행했다.

~~~text
/goal Day 5 구현을 다시 만들지 말고,
현재 커밋과 보고서에서 이어서 실제 내부망 검증만 진행해줘.

먼저 다음 자료를 읽어 현재 기준선을 확인해.
- git status
- 최근 Day 5 커밋 4개
- docs/reports/DAY5_REPORT.md

기존 전체 테스트는 코드가 바뀌지 않았다면 반복하지 마.

서버를 0.0.0.0:4173으로 실행하고,
같은 Wi-Fi의 두 번째 기기가 접속할 URL과 확인 절차를 안내한 뒤
사용자의 실제 접속 결과를 기다려.

접속되면 다음 흐름을 확인해.
1. 방 생성
2. 입장
3. 준비
4. 흑 1수
5. 백 1수

결과는 docs/reports/DAY5_LAN_REPORT.md에 기록해.
필요한 문서 변경만 커밋하고 push는 하지 마.
~~~

하지만 이 요청도 예상대로 끝나지 않았다. 새 세션 `9c0932b5…`는 9월 11일 03:24 KST에 시작해 06:05경 다시 제한에 걸려 멈췄다. 마지막 Goal 상태에는 활성 시간 2시간 41분 27초, 155 turn, 사용 토큰 12,879,614가 기록돼 있다. 이 토큰은 반복 입력을 포함하는 Goal 집계이며 출력 토큰 수가 아니다. 앞서 Day 5 본 구현에 적은 11시간 16분과 675회 요청에는 이 후속 세션을 합산하지 않았다.

| 구분 | Day 5 본 구현 | 후속 LAN 검증 요청 | 측정 가능한 합계 |
| --- | --- | --- | --- |
| Goal 활성 시간 | 11시간 16분 35.769초 | 2시간 41분 27초 | **13시간 58분 2.769초** |
| Goal turn | 3회 | 155회 | 158회 |
| Goal 사용 토큰 | 6,460,641 | 12,879,614 | 19,340,255 |
| 기록에서 보인 작업 | 구현·오류 수정·테스트·보고서와 재검증 | 서버 확인과 실제 접속 결과 대기 안내 반복 | 구현과 자동 대기 Goal 합산 |
| 최종 종료 사유 | `evidence_catalog` | `evidence_catalog` | 두 Goal 모두 같은 제한 |

이 합계는 Qwen Goal 상태의 `activeTimeMs`를 더한 값이다. 이후 일반 요청으로 서버 health와 내부 IP를 한 번 확인한 시간은 Goal 계측 밖이라 포함하지 않았다. 달력상 경과 시간과 API 요청시간 합계도 기준이 달라 여기에 더하지 않는다.

서버는 올라갔지만 사용자의 실제 기기 접속 결과가 없는 상태였다. Qwen은 서버가 살아 있고 방과 연결이 0개라고 안내했다. 문제는 그 응답 뒤에도 Goal이 활성 상태로 남았다는 점이다. 런타임은 실제 사용자 메시지가 없는 자동 계속 실행 요청을 보냈고, 모델은 다시 접속 결과가 필요하다고 답했다. 일부 turn에서는 서버 상태도 다시 조회했다. **사람을 기다리는 시간이 모델 호출을 멈추는 시간으로 처리되지 않았다.**

마지막에는 Qwen도 반복을 인식해 외부 입력 부재를 이유로 `blocked`를 제안했다. 하지만 반환값은 상태 변경 확정이 아닌 독립 검증 대기였고, 직후 저장된 최종 상태는 다시 `usage_limited`, 종료 사유는 `evidence_catalog`였다. 정상적인 대기 상태로 전환하기 전에 증거 목록 제한에 걸린 것이다.

이전의 긴 실행과 닮은 점은 있다. 두 경우 모두 새 진전이 적은 확인과 응답이 쌓였고 같은 제한으로 끝났다. 다만 본 구현에는 실제 코드 작성과 오류 수정도 포함됐으므로 11시간 전체를 대기 반복으로 설명할 수는 없다. 후속 세션에서는 사용자 입력을 요구하는 작업과 자동 계속 실행 사이의 충돌이 훨씬 선명하게 드러났다. 공식 문서도 확인할 수 없는 완료 조건이 남으면 제한에 도달할 때까지 실행이 이어질 수 있다고 설명한다. [공식 완료 판정 설명](https://qwenlm.github.io/qwen-code-docs/en/users/features/goals/#how-a-goal-is-judged)

외부 AI와 함께 만든 복구 요청도 적절하지 않았다. 범위를 줄이고 새 세션을 여는 데 집중하면서, 사람이 돌아올 때까지의 대기를 자동 Goal 안에 넣었다. “기다려”라는 문장이 실제 실행의 일시 정지를 보장하지 않는다는 점을 놓쳤다. `potential loop` 경고가 이 후속 세션에서도 표시됐는지는 확인하지 못했지만, 반복 응답 자체는 로그에 남아 있다. 경고의 발생 여부와 무관하게 요청 방식을 고쳐야 했다.

## 사람의 확인을 기다리는 단계는 일반 요청으로 분리한다

이제 서버 준비와 접속 절차 안내는 `/goal` 없이 일반 대화로 요청하려 한다. 아래 첫 문장은 설명이며 Goal 명령이 아니다. 서버를 유지한 채 응답을 끝내고, 실제 기기 확인 결과를 내가 다음 메시지로 보내는 방식이다.

~~~text
일반 요청으로 처리해줘. 새 Goal은 시작하지 마.

현재 LAN 서버 상태를 한 번 확인하고,
접속 주소와 두 기기 테스트 절차를 안내한 뒤 응답을 끝내줘.
서버가 실행 중이면 유지하고 중복 실행하지 마.
반복 상태 확인이나 전체 테스트는 실행하지 마.

실제 접속 결과는 내가 다음 메시지로 전달할게.
~~~

한도에 걸린 기존 Goal을 그대로 resume하지 않는다. 실제 접속 결과를 확보한 뒤 보고서 작성과 문서 커밋을 별도 요청한다. 실패가 있다면 관찰한 오류와 재현 절차를 전달하고 그 문제만 진단하게 한다. 자동으로 끝낼 수 있는 작업의 완료 조건에 사람의 미래 응답을 넣지 않는 것이 이번 수정의 핵심이다.

9월 11일 저장소를 다시 확인했을 때 Day 5의 네 커밋은 그대로 있었고 작업 트리는 깨끗했다. `DAY5_REPORT.md`에는 단위 90개, 서버 17개, 온라인 E2E 1개, 브라우저 회귀 25개의 통과 기록이 남아 있었다. 이번 확인에서 테스트를 다시 실행한 것은 아니다. 실제 기기 검증 결과를 남길 `DAY5_LAN_REPORT.md`는 아직 없었다.

따라서 새 요청이 이어받을 상태는 **Day 5 필수 구현과 자동 검증 기록은 확보했고, 실제 두 기기 연결과 그 결과 기록은 남아 있다**는 것이다. 위 프롬프트는 방 생성부터 흑·백 한 수까지 확인한다. 승리까지 한 판, 기권, 재접속까지 검증하는 요청은 아니다. Goal의 완료 상태와 제품의 검증 범위를 따로 기록해야, 종료 문구 하나를 얻으려고 이미 끝낸 개발을 반복하지 않을 수 있다.

## 온라인 모드로 접속하자 다른 PC에서도 방이 보였다

그 뒤 같은 세션에 위 일반 요청을 입력했다. 이번에는 서버 health와 내부 IP를 확인하는 셸 호출 한 번 뒤 접속 주소와 두 기기 절차를 안내하고 입력창으로 돌아왔다. 화면 하단에는 이전 Goal의 `usage limited` 상태가 남아 있었지만, 일반 요청 자체는 응답을 끝냈다. 적어도 이 요청에서는 앞서처럼 대기 안내를 자동으로 반복하지 않았다.

![일반 요청으로 서버 상태를 한 번 확인하고 접속 절차를 안내한 뒤 입력창으로 돌아온 Qwen 화면](/api/wiki-assets/b37d89e0-8f6a-4c92-9c82-60dbc31f2219)

처음 실제 접속을 시도했을 때는 한쪽에서 방 생성과 준비 완료가 표시됐지만 다른 PC에서는 방이 보이지 않았다. 그래서 방 목록 동기화 문제를 의심하고 진단 요청을 정리했다. 하지만 온라인 모드로 다시 접속하자 다른 PC에서도 방이 보였다. 이번 증상은 온라인 진입 경로를 맞추면서 해소됐으며, 이 과정에서 서버 동기화 코드를 수정한 것은 아니다.

![방 생성과 준비 완료는 표시되지만 상대 슬롯이 비어 있고 로컬 mock 안내가 남아 있는 대기실](/api/wiki-assets/efc4472d-7b1a-4f6b-8ff6-fe691a28a478 "width=900 align=center")

이 화면에는 `로컬 mock · 실제 다른 브라우저 연결 미지원`이라는 문구가 남아 있다. 코드도 함께 확인했다. `src/main.js`는 URL의 `online` 값이 `1`일 때만 `WebSocketRoomClient`를 선택하고, 그 외에는 로컬 `RoomManager`를 사용한다. 따라서 두 PC 모두 같은 서버의 `/?online=1` 주소로 들어갔는지가 첫 확인 항목이다.

하지만 문구만 보고 mock 모드였다고 단정할 수는 없다. `src/ui/room.mjs`와 `src/ui/lobby.mjs`에는 해당 안내가 고정 문자열로 들어 있다. 실제 연결 방식과 화면 문구가 따로 움직일 수 있다는 뜻이다. 서버 health의 `status: ok` 역시 서버가 응답한다는 증거일 뿐, 두 브라우저가 WebSocket에 연결돼 같은 방 목록을 받았다는 증거는 아니다.

이번에 실제로 확인한 범위는 내부 IP로 다른 PC에서 접속하고 온라인 방 목록을 보는 데까지다. 자동 E2E에서 확인한 흑·백 두 수 동기화와는 별도의 수동 확인이다. 실제 두 PC에서 착수가 동기화되거나 승리까지 한 판을 마쳤다는 결과는 아직 기록하지 않는다. 앞서 의심했던 늦은 참가자의 목록 수신 문제도 이번 증상의 확정 원인으로 남기지 않는다.

방이 보이고 나니 다음 불편이 드러났다. 목록의 순서가 규칙적으로 느껴지지 않았고 이름만으로 방을 구분하기 어려웠다. 정렬 코드의 결함을 확인했다는 뜻은 아니다. 사용자가 원하는 방을 알아보고 다시 찾기 어렵다는 사용성 문제다. 이 개선은 Day 6으로 넘기기로 했다.

## 실제로 눌러보니 연결 이후의 문제가 드러났다

추가 확인에서는 온라인 게임 화면까지 들어갔다. 하지만 연결 성공만으로 대국이 정상이라고 말할 수는 없었다. 아래는 실제 조작 중 관찰한 증상이다. 코드에서 원인을 재현해 확정한 결함 목록과는 구분한다.

| 관찰한 증상 | 다음에 확인할 내용 |
| --- | --- |
| 대기실에는 나가기가 있지만 게임 화면에는 없음 | 대국 중 퇴장 처리와 상대 화면의 상태 전환 |
| `알 수 없는 메시지 타입: room:list`가 사용자에게 표시됨 | 요청·응답 메시지 계약과 오류를 발생시킨 경로 |
| 방 만들기 한 번에 여러 방이 생긴 것처럼 보임 | 중복 이벤트·요청·서버 생성·화면 중복 렌더링을 구분 |
| 이전 방이 남고 같은 이름이라 최신 방을 찾기 어려움 | 퇴장·연결 종료 시 방 정리, 방 ID와 생성 시각 기준 |
| 다른 사람이 연결됐는데 백 플레이어에 봇 표시 | 실제 참가자 종류와 화면 라벨 연결 |
| 무르기·기권·재시작이 누른 쪽에만 적용됨 | 로컬 상태 변경 경로와 서버가 결정하는 대국 상태의 일치 |

![사용자 화면에 노출된 알 수 없는 메시지 타입 room:list 오류](/api/wiki-assets/41e25923-36a3-4ea9-9702-607c466f9fe5 "width=600 align=center")

이 오류는 단순히 문구를 친절하게 바꾸는 것으로 끝낼 일이 아니다. 먼저 어느 쪽이 어떤 메시지를 거부했는지 확인해야 한다. 원인을 고친 뒤 사용자에게는 “방 목록을 불러오지 못했습니다”처럼 다음 행동을 알 수 있는 안내를 보여주고, 프로토콜 이름은 진단 로그에 남기는 편이 맞다.

![같은 게임 방 이름이 반복되고 대기 중과 진행 중 상태가 섞인 방 목록](/api/wiki-assets/65a2fa6e-f062-4309-870e-617d79efb726 "width=750 align=center")

화면에 방이 세 개 보인다는 사실만으로 서버가 한 요청에 방을 세 개 만들었다고 단정할 수는 없다. 이전 방이 남았거나 클라이언트가 중복으로 그렸을 가능성도 있다. 버튼 클릭 한 번에서 요청 수, 서버의 방 ID 수, 렌더링된 카드 수를 차례로 확인해야 한다. 정렬 기준이 없어 보이는 문제와 방이 실제로 중복 생성되는 문제도 나눠서 진단한다.

![온라인 게임 화면. 두 참가자가 모두 Player로 표시되고 백에는 봇 라벨이 남아 있으며 대국 중 나가기 버튼은 보이지 않는다](/api/wiki-assets/2bc4d8e0-1fe1-4e97-8d9e-71c5c71a6cfd "width=900 align=center")

가장 우선할 문제는 무르기·기권·재시작 뒤 두 화면이 어긋난다는 관찰이다. 착수만 서버를 거치고 다른 버튼은 싱글플레이의 로컬 상태를 바꾼다면 온라인 대국은 곧바로 깨질 수 있다. 실제 경로는 Day 6에서 확인해야 하지만, 서버 처리가 없는 조작을 온라인 화면에서 실행하게 두어서는 안 된다. 미지원 조작은 숨기거나 이유를 붙여 비활성화하고, 지원할 조작은 서버의 판정과 양쪽 상태 전달까지 구현해야 한다.

## Day 5의 성과와 비용은 함께 봐야 한다

Day 5에서 달라진 경계는 분명하다. 전날까지 브라우저 안에서만 존재하던 방과 선수 상태가 서버로 이동했다. 서로 독립된 두 브라우저가 같은 방에 들어가고, 서버가 흑과 백을 정해 두 수를 검증한 뒤 같은 판을 방송한다. 잘못된 착수도 클라이언트가 조용히 무시하는 데서 끝나지 않고 서버가 거절한다.

Git 기록도 구현, 서버 테스트, 온라인 E2E, 보고서의 네 커밋으로 나뉘었다.

| 커밋 | 내용 |
| --- | --- |
| `2a463c9` | HTTP·WebSocket 서버, RoomService, 클라이언트 transport |
| `9263b0e` | 방 동기화·착수 정책·frame 서버 테스트 |
| `8aa6c20` | 독립 browser context 두 개의 온라인 E2E |
| `aefff45` | Day 5 진행 기록과 결과 보고서 |

반면 비용은 예상보다 컸다. 본 구현 Goal은 11시간 16분, 후속 LAN 검증 Goal은 2시간 41분으로 측정 가능한 합계가 13시간 58분이었다. 본 구현 출력만 약 97만 토큰이었고, 85.76%의 입력이 캐시됐어도 긴 문맥을 반복해 다뤄야 했다. WebSocket을 직접 구현하면서 open 이전 전송과 확장 frame 길이라는 낮은 층의 오류까지 해결해야 했다. 계획의 권장안대로 `ws`를 사용했다면 이 구간은 줄었을 가능성이 있지만, 같은 조건으로 비교하지 않았으므로 절약 시간을 숫자로 주장할 수는 없다.

최종 보고서도 그대로 믿기보다 원본 기록과 대조할 필요가 있었다. “24분”은 전체 Goal 시간이 아니었고, 네 장의 캡처는 실제로 두 상태가 아니라 최종 A/B 두 상태였다. 자동화가 로그와 파일을 남긴 덕분에 이런 차이를 나중에 확인할 수 있었지만, 보고서 생성 자체가 정확성을 보장하지는 않았다.

## Day 6에는 방의 수명과 두 화면의 일치부터 고친다

Day 5의 자동 테스트는 온라인 경계가 연결됐다는 것을 증명했다. 아직 온라인 오목 게임이 완성된 것은 아니다. 두 수 뒤의 동기화는 확인했지만 승리까지 한 판을 진행하지 않았고, 결과 모달·기권·재대결·상대 퇴장·재접속·채팅도 서버 프로토콜에 온전히 연결되지 않았다.

실제 화면을 눌러본 뒤 Day 6의 목표를 다시 잡았다. 단순히 UI를 더 예쁘게 만드는 작업으로는 부족하다. 화면에 있는 행동이 두 사람의 같은 상태를 만들고, 누가 들어오고 나갔는지 서버와 화면이 같은 답을 내야 한다.

Day 6는 **방 관리 안정화와 로비·대기실 개선을 하루 한 번의 `/goal` 요청으로 수행**한다. 방 생성부터 입장·준비·퇴장까지 사용자가 알아볼 수 있고, 서버와 두 화면의 목록이 일치하는 것이 이날의 결과다.

| 계획서 내부 단계 | 확인할 결과 |
| --- | --- |
| 방 관리 수정 | 생성 중복 방지, 최대 세 방, `room:list` 오류 수정, 빈 방 삭제 |
| 로비·대기실 반영 | 방 이름·번호·인원·정렬, 실제 참가자와 연결·준비 상태 표시 |
| 검증과 기록 | 두 브라우저의 목록·입장·퇴장 확인, 관련 회귀, 보고서와 커밋 |

처음에는 Goal A~D를 각각 요청하려 했지만, 그러면 매 단계마다 사람이 다음 요청을 넣어야 했다. 구현 순서는 계획서 안에 두고 Qwen이 이어서 수행하도록 바꾼다. 대신 채팅·무르기·재대결·재접속까지 하루 범위에 넣었던 계획을 줄였다. 한 번의 요청이 하루 안의 완료를 보장한다는 뜻은 아니며, 실행 시간을 강제로 제한하지도 않는다.

Goal을 나누는 것 자체가 반복 제한의 해결책은 아니다. 변경한 경로의 관련 테스트부터 실행하고 최종 회귀 결과를 기록한다. 코드·설정·환경이 그대로라면 통과한 검사를 되풀이하지 않는다. 같은 실패를 두 번 보면 새 사실과 원인 후보를 기록하고 접근을 바꾼다. 실제 두 기기 검증은 접속 절차와 미검증 항목을 남긴 뒤 사람이 확인한다. 그 응답을 기다리며 자동 실행을 이어가지 않는다.

Day 5가 오래 걸린 이유를 “테스트가 많아서”로만 정리하면 다음에도 같은 문제가 남는다. 직접 만든 WebSocket의 open 이전 전송과 frame 길이 오류 수정, compact 뒤 상태 재확인, 파일 재독, 완료 판정을 위한 반복 검사와 사람의 LAN 응답을 기다리는 요청이 두 Goal에 겹쳤다. 각 활동별 시간은 따로 계측하지 못했으므로 13시간 58분 가운데 낭비가 몇 시간이라고 단정할 수는 없다. 다만 반복 검사에 비해 실제 사용자가 누르는 퇴장·기권·재시작의 두 화면 검증이 늦게 남은 것은 분명하다.

## 재접속 정책은 후속 작업을 위해 보관한다

재입장은 Day 6 이후로 넘긴다. 제대로 만들려면 브라우저 연결과 플레이어 좌석을 분리해야 하기 때문이다. 그래도 공개 게임에서 새로고침 한 번이 즉시 패배가 되면 불편이 커서 최소 복구 정책까지 설계하기로 했다.

- 대기실의 `방 나가기`는 즉시 자리를 비우고, 마지막 사람이면 방을 지운다.
- 진행 중 `대국 나가기`는 확인 뒤 기권으로 처리한다.
- 새로고침, 브라우저 종료, Wi-Fi 단절은 좌석과 대국 상태를 60초간 보존한다.
- 그동안 양쪽 착수를 멈추고 상대에게 재접속 남은 시간을 보여준다.
- 같은 브라우저는 추측하기 어려운 `resumeToken`으로 playerId, 색, 방, 보드, 차례와 수순을 복원한다.
- 60초가 지나면 연결이 끊긴 쪽의 패배를 서버가 한 번만 확정한다.

닉네임이나 방 번호만으로 자리를 되찾게 하면 다른 사람이 좌석을 가져갈 수 있다. 같은 토큰의 연결이 이미 살아 있을 때 새 탭이 접속하면 새 연결을 거절한다. 다른 기기로 좌석을 넘기는 기능과 서버 재시작 뒤 대국 복구는 첫 공개 버전에서 제외한다.

재접속은 방과 대국 상태가 안정된 뒤 별도 Goal로 진행한다. 복구할 상태 자체가 흔들리는 동안 재접속부터 붙이면 같은 결함을 두 경로에서 고치게 될 가능성이 크다.

## 시안 중 로비와 대기실부터 적용한다

말로 “UI를 개선해 달라”고 요청했을 때 변화가 작았던 경험이 있어 이번에는 구현 전에 기준 화면을 만들었다. Day 5의 어두운 배경, 목재색 15×15 보드, 금색 강조와 데스크톱 2:1 구성을 유지했다. 보드의 좌표·화점·돌·최근 수 표시도 그대로 살리는 방향이다.

Day 6에는 위 시안 중 로비와 대기실을 적용한다. 게임 패널과 채팅·무르기·재대결은 후속 구현의 기준으로 남긴다. 기존 보드는 유지하고, 온라인의 잘못된 mock·봇 표시는 바로잡는다.

HTML 시안은 제품 코드가 아니다. Qwen에는 이미지 한 장만 주지 않고 `UI_SPEC.md`, `preview.html`, 세 장의 비교 캡처를 함께 읽게 한다. 시안의 가짜 방과 수순을 복사하지 않고 현재 서버 상태와 기존 canvas 보드에 연결하는 것이 완료 조건이다.

## 방 세 개짜리 공개 버전까지 남은 일정을 다시 잡는다

공개 목표는 Spellcrown처럼 주소를 공유해 간단히 접속하고 플레이할 수 있는 형태다. 첫 버전은 **동시에 최대 세 방, 방마다 두 명이 대국하는 작은 온라인 오목**으로 잡는다. 이는 이번 프로젝트의 범위 제안이며 Spellcrown의 기능이나 운영 구조를 그대로 따른다는 뜻은 아니다.

세 방은 영구 고정 방이 아니다. 사용자가 생성하되 서버의 활성 방 수를 세 개로 제한한다. 네 번째 생성은 서버가 거절하고 화면에는 자리가 없다고 안내한다. 마지막 사람이 나가면 방을 지워 다시 만들 수 있어야 한다. 대국 자리는 최대 여섯 개지만 로비 WebSocket 연결은 더 많을 수 있으므로 별도의 연결 수·메시지 크기·빈도 제한도 필요하다.

처음 계산한 20~34시간은 채팅, 무르기 합의와 자동 재접속을 보류한 값이었다. 이 셋과 재대결을 첫 공개 범위에 넣기로 했으므로 추정치를 갱신한다. 아래 값은 실행 제한이 아니라 **남은 작업을 나누기 위한 초기 추정치**다. Day 5의 33.9 tok/s만으로 기능당 시간을 환산할 수 없고, 실제 시간은 진단과 재시도 횟수에 더 크게 좌우된다.

| 순서 | 산출물과 완료 기준 | 예상 작업 시간 |
| --- | --- | --- |
| Day 6부터 · 방과 목록 | 중복 생성과 목록 오류 수정, 세 방 제한, 빈 방 정리, 안정적인 목록 순서 | 4~7시간 |
| 후속 · 대국 동작 | 승리·기권·퇴장, 채팅, 무르기 합의와 재대결의 양쪽 상태 일치 | 6~10시간 |
| 화면별 · UI 통합 | 시안을 실제 상태에 연결하고 데스크톱·모바일에서 비교 | 4~6시간 |
| 후속 · 최소 재접속 | 60초 좌석 보존, 동일 브라우저 복귀, 만료와 중복 연결 처리 | 4~7시간 |
| 다음 단계 · 외부 배포 | HTTPS/WSS, 프록시 upgrade, 프로세스 재시작·로그, 외부 두 기기와 세 방 확인 | 4~7시간 |
| 예비 시간 | 공개 환경에서 발견되는 연결·상태 오류 수정 | 4~8시간 |

합계는 **약 26~45시간**이다. 하루 4시간 정도라면 약 7~12일의 작업량이다. 이 표는 작업 종류별 추정이며 UI 시간에는 Day 6의 로비·대기실과 후속 게임 패널 작업이 함께 포함된다. 하루에는 범위를 정한 요청 하나를 수행하고, 실제 완료 결과를 보고 다음 날 범위를 정한다. 사람의 검수와 배포 계정·도메인 준비를 기다리는 시간도 별도다. Day 6가 끝나면 실제 소요 시간과 재시도 횟수로 나머지 추정을 다시 고친다.

공개 시점은 달력보다 결과로 정한다. 외부 두 기기가 한 판을 같은 결과로 끝내고, 기권·퇴장·재접속 뒤에도 상대 화면과 방 목록이 맞으며, 세 방이 찬 상태와 빈자리가 생긴 상태를 서버와 UI가 동일하게 처리해야 한다.
