# 올인원 배포 — 사람 손 셋을 없애는 설계

배포는 `develop` 을 `main` 에 머지하는 행동 하나다. 2026-08-15 배포로 관측 스택 Helm 이
파이프라인에 들어왔고, 사람이 손으로 하는 일이 셋 남았다. 이 문서는 그 셋을 없애는 설계다.

경계를 어떤 기준으로 그었는지는 위키 `deploy-automation-boundary` 에 있다. 요약하면
**되돌릴 수 있으면 파이프라인이 하고, 없으면 사람이 한다.** 여기 남은 셋은 전부 후자라,
설계의 본체가 기능이 아니라 **안전장치**다.

## 지금 남은 셋

| 남은 일 | 지금 어떻게 하나 | 왜 자동이 아니었나 |
|---|---|---|
| 블로그 발행 | `./scripts/publish-blog-drafts.sh --write` | 관리자 로그인에 TOTP 가 필요하다 |
| 빈 탭 삭제 | 관리자 쿠키로 `DELETE /api/bff/tabs/{id}` | 내부 경로에 `DELETE` 가 없다 |
| 데이터 계층 Helm | miniPC 에서 사람이 `helm upgrade` | 설치 후 한 번도 upgrade 한 적이 없다 |

## 1. 블로그 자동 발행

### 결정 — 위키가 쓰는 길을 그대로 쓴다. TOTP 는 건드리지 않는다

위키는 관리자 로그인을 하지 않는다. 배포 잡이 `sync-wiki-content-k8s.sh` 로 클러스터 안에
Job 을 하나 띄우고, 그 Job 이 시드 스크립트를 돌려 `/internal/content-sync/*` 에 쓴다.
인증은 `X-Content-Sync-Token` 헤더 하나이고, 값은 `APP_CONTENT_SYNC_TOKEN` 환경변수와
상수 시간 비교한다(`ContentSyncAuthorizer`). 토큰이 틀리면 401 이 아니라 **404** 를 준다 —
경로의 존재 자체를 숨긴다.

블로그만 이 길을 안 쓰고 사람이 TOTP 를 쳤다. 같은 컨트롤러에 경로를 붙이면 끝난다.

TOTP 씨앗을 GitHub Secrets 에 넣는 안은 기각했다. 다섯 줄로 되지만, 비밀번호 옆에 2차 인증
씨앗을 두면 2FA 가 1FA 가 된다. 더 나은 길이 이미 있는데 보안을 깎을 이유가 없다.

### 구성

- `ContentSyncController` 에 `POST /internal/content-sync/blog-posts` 를 더한다.
  본문은 발행 스크립트가 이미 만드는 것과 같은 모양(title/slug/category/tags/summary/toc/content)이고,
  기존 블로그 저장 서비스에 그대로 위임한다. 새 저장 로직을 쓰지 않는다.
- `scripts/publish-blog-drafts-k8s.sh` 를 `sync-wiki-content-k8s.sh` 와 같은 꼴로 만든다.
  초안 18편 342KB 를 ConfigMap 으로 넣는다. 시드 스크립트가 이미 578KB 를 같은 방식으로
  넣고 있으므로 1MB 한도 안이다.
- 배포 잡에서 **위키 콘텐츠 싱크 바로 다음**에 부른다. 그 앞 단계가 콘텐츠 반영 직전 백업이라
  같은 백업이 블로그도 덮는다.

### 안전장치 — 여기가 설계의 본체다

**바뀐 것만 올린다.** 매 배포마다 18편을 다시 쓰면 안 바뀐 글의 `updatedAt` 이 계속 튄다.
`check-content-sync.mjs` 가 쓰는 것과 같은 정규화 해시(CRLF·끝 공백만 고른다)로 운영 본문과
비교해, 다른 편만 보낸다.

**되돌리는 절차를 먼저 만든다.** 기계가 운영 글을 덮게 되므로, 잘못 덮였을 때 되돌리는 길이
있어야 한다. 콘텐츠 반영 직전 백업은 파이프라인에 이미 있지만 **그 백업으로 블로그를 되돌리는
리허설을 한 적이 없다.** 이 항목은 리허설을 마치기 전에는 켜지 않는다.

### 발행 대상은 초안 디렉터리 전체다 — 거르는 장치를 두지 않는다

`posts/jay-blog/drafts/` 에 있는 것은 전부 나간다. 지금 18편이고 운영에는 17편이 있는데,
남은 `jay-blog-writing-harness.md` 도 로컬에는 이미 발행돼 있다. 안 내보낼 글이 아니라
아직 안 내보낸 글이었다.

머리말 표시나 별도 디렉터리로 거르는 안을 검토했다가 뺐다. 걸러야 할 글이 지금 없고,
장치를 먼저 만들면 그 장치를 관리하는 일이 새로 생긴다. 정말 붙들어 둘 초안이 생기면
그때 만든다 — **초안 디렉터리에 넣지 않는 것으로도 대부분 해결된다.**

## 2. 빈 탭 자동 삭제

### 결정 — 삭제 경로를 내부에 두고, 글이 0편인 탭만 지운다

`ContentSyncController` 에는 `POST /tabs` 와 `POST /articles` 만 있다. 그래서 지금까지
탭 삭제는 관리자 쿠키로만 됐다. `DELETE /internal/content-sync/tabs/{tabId}` 를 더한다.

시드는 upsert 라 지우지 않는다. 그래서 시드가 정본에 없는 탭을 만나면 지금은
`[extra] tab ...` 으로 보고만 한다. 그 자리에서 삭제를 부르게 한다.

### 안전장치

**글이 든 탭은 지우지 않는다.** 이 가드가 전부다. 서버 쪽에서 검사한다 — 클라이언트가
세어서 보내면 그 사이에 글이 들어와도 모른다. 탭에 글이 하나라도 있으면 409 를 주고,
스크립트는 그것을 실패가 아니라 경고로 남긴다(사람이 글을 옮겨야 하는 상황이지
배포를 멈출 일은 아니다).

**한 번에 지우는 개수를 제한한다.** 시드 형식이 깨져 정본 탭 집합이 통째로 비면, 가드가
있어도 빈 탭이 여럿 한꺼번에 지워질 수 있다. 한 번에 둘까지만 지우고 그 이상이면 멈춘다.
`check-wiki-consistency.mjs` 에 이미 있는 건전성 검사와 같은 성질이다.

## 3. 데이터 계층 Helm

### 결정 — 조건부로 넣는다. values 가 바뀐 배포에서만 돈다

| 릴리스 | 지금 못 도는 이유 | 어떻게 |
|---|---|---|
| `redis` | 없다. `auth.enabled: false` | 그대로 넣는다 |
| `pg` | 비밀번호를 `--set auth.password` 로 준다 | GitHub Secrets 에서 넘긴다 |
| `minio` | 같다(`rootPassword`) | 같다 |

셋 다 REVISION 1 이다. 설치한 뒤 한 번도 올린 적이 없다. 그래서 두 가지를 건다.

**values 가 그 커밋에서 바뀐 경우에만 돈다.** 안 바뀐 배포에서 데이터베이스를 건드릴
이유가 없다. 감지는 이미 들어간 `Detect changes the pipeline does not apply` 단계를
그대로 쓴다(`git diff --name-only HEAD^ HEAD`).

**첫 판은 무인으로 뽑지 않는다.** `workflow_dispatch` 로 사람이 지켜보며 한 번 돌린다.
그 한 번이 성공한 뒤에야 자동 경로를 켠다. bitnami 차트는 비밀번호가 빠지면 조용히
깨지지 않고 큰 소리로 실패하며, `--atomic` 이 되감는다 — 그래도 스테이트풀이다.

## 순서

이 문서의 셋은 **3차**에 들어간다. 1차(2026-08-15, 91커밋)는 이미 나갔고, 그 사이에 1차에서
어긋난 것만 고치는 작은 2차가 끼었다 — 대표 문서 재시도(V24), 롤아웃 상한 600초,
빈 탭 삭제 도구. 고칠 것을 이 문서의 셋과 같이 태우지 않는 이유는, 그러면 무엇이 고쳐졌고
무엇이 새로 깨졌는지 다시 가릴 수 없게 되기 때문이다.

1. 빈 탭 삭제. 셋 중 가장 작고, 지우는 대상이 이미 비어 있어 잃을 것이 없다.
   손으로 쓰는 `scripts/delete-empty-tabs.sh` 가 2차에 들어가므로, 가드가 붙은 로직을
   그대로 파이프라인으로 옮기면 된다
2. 데이터 계층 Helm. `workflow_dispatch` 로 첫 판을 돌린 뒤 자동 경로를 켠다
3. 블로그 자동 발행. **백업 복구 리허설을 마친 뒤에** 켠다

## 검증

- 탭 삭제: 로컬에서 글이 든 탭에 삭제를 걸어 409 가 나는지, 빈 탭에 걸어 지워지는지 본다.
  배포 뒤 `check-wiki-consistency.mjs` 가 「유령 탭 0」이면 끝이다
- 데이터 Helm: `HELM_DRY_RUN=1` 로 렌더를 먼저 본다. 관측 스택에서 쓴 것과 같은 길이다
- 블로그: 배포 뒤 `check-content-sync.mjs` 가 0 이어야 한다. 지금은 위키 13곳, 블로그 17편이
  어긋난 것으로 잡힌다 — 그 숫자가 0 이 되는 것이 이 설계 전체의 완료 조건이다

## 되돌리는 법

- 탭 삭제·블로그 발행: 워크플로에서 그 단계를 빼면 다음 배포부터 안 돈다. 이미 지워진 탭과
  덮인 글은 백업에서 되돌린다
- 데이터 Helm: `helm history` 로 리비전을 보고 `helm rollback`
- 내부 엔드포인트 자체를 물리려면 컨트롤러에서 경로를 지운다. 토큰은 그대로 두면 된다

## 남은 위험

- 블로그 백업 복구 리허설이 아직 없다. 이것이 1번의 선행 조건이다
- 데이터 계층 첫 upgrade 는 언제 뽑아도 처음이다. 조건부 실행은 빈도를 줄일 뿐 위험을
  없애지 않는다
- 내부 경로가 넷으로 는다. 토큰 하나가 새면 위키와 블로그가 같이 열린다.
  지금은 토큰을 배포 잡이 심고 클러스터 안에서만 부른다는 전제에 기대고 있다
