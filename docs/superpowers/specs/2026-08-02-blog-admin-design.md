# 블로그 관리자 화면 설계

작성일: 2026-08-02
상태: 설계 확정, 구현 전
선행: [블로그 설계](./2026-08-02-blog-leneu-cloud-design.md) · [프론트 계획(완료)](../plans/2026-08-02-blog-frontend.md)
참고: 티스토리 관리자 화면 (2026-08-02 computer-use 로 직접 확인)

## 1. 왜 필요한가

읽기 화면은 끝났지만 **글을 새로 쓸 경로가 없다.** LAB 8편은 일회성 SQL 로 옮겼고,
그 스크립트는 한 번 돌리고 버리는 것이다. 지금 블로그는 읽기 전용이다.

블로그 설계 10절 5항의 "최소 쓰기 API" 는 만들지 않았다. 그것이 필요했던 이유가 이관인데
같은 DB 안의 SQL 로 하면 거칠 이유가 없었기 때문이다. 그래서 쓰기 경로는 이 라운드에서
**UI 와 함께** 만든다 — API 를 두 번 그리지 않는다.

## 2. 범위 — 티스토리 24개 메뉴 중 5개

티스토리 좌측 메뉴를 전부 훑고, 혼자 쓰는 블로그에 실제로 필요한 것만 골랐다.

### 이번 범위

| 화면 | 왜 |
|---|---|
| 글 목록 | 수정·삭제 진입점, draft/published 구분 |
| 글 쓰기·수정 | **없으면 블로그가 안 돌아간다.** 유일한 필수 |
| 카테고리 관리 | `sort_order` 가 있는데 바꿀 수단이 없다. 2단 트리 + 드래그 |
| 댓글 관리 | 스팸이 오면 지울 수단이 필요하다. `deleted_at` 이 이미 휴지통 구조다 |
| 통계 대시보드 | **데이터가 이미 쌓이는데 볼 곳이 없다** |

### 이번 범위 밖 — 만들지 않는다

공지, 서식(템플릿), 방명록, 수익, 스킨·사이드바·메뉴 편집, 플러그인, 팀블로그.
전부 여러 사람이 쓰는 서비스라서 있는 기능이다.

**페이지 관리도 만들지 않는다.** 우리 "페이지" 는 `/privacy` 하나뿐이고 지금 코드로 관리된다.
DB 로 옮기면 관리 화면이 하나 늘고 얻는 것이 없다.

## 3. 배치와 인증 — 기존 경계를 그대로 쓴다

관리 화면은 **`portfolio.leneu.cloud/admin/blog/*`** 에 둔다. `blog.leneu.cloud` 에 두지 않는다.

블로그 설계 3절이 "관리자 편집은 계속 `portfolio.leneu.cloud/admin` 에서 한다.
따라서 `jw_token` 쿠키의 Domain 을 넓힐 필요가 없고 현재 보안 경계가 그대로 유지된다" 고
못 박아 두었다. 블로그 host 로 옮기면 쿠키 경계를 다시 설계해야 하는데 얻는 것이 없다.

- 화면: `web/src/app/admin/blog/**` — 기존 `middleware.ts` 의 `/admin` 가드가 그대로 걸린다
- API: `/api/admin/blog/**` — 기존 SecurityConfig 의 관리자 규칙을 그대로 탄다
- **블로그 host 에서는 `/admin` 이 rewrite 되지 않는다.** `blogHost.ts` 의 통과 목록에 이미 있다

### 사이드바를 두 묶음으로 나눈다

지금 `admin-nav` 는 평평하다(`글 목록 / 새 글 작성 / 탭 관리 / 서비스 / 편집 가이드`).
여기에 블로그 항목을 그냥 더하면 "글 목록" 이 둘이 되어 무엇이 위키고 무엇이 블로그인지
구분되지 않는다. 소제목으로 묶는다.

```
위키     글 목록 · 새 글 · 탭 관리
블로그   글 목록 · 새 글 · 카테고리 · 댓글 · 통계
공통     서비스 · 편집 가이드 · 사이트로
```

## 4. 무엇을 그대로 쓰고 무엇을 새로 만드나

코드를 실제로 읽고 정리했다(`ArticleEditor` 382줄, `admin.css` 69개 규칙 기준).

### 그대로 쓴다

- 폼 골격 — `editor-head` / `editor-meta` / `Field` / 오류 배너 / 저장 버튼
- 본문 마크다운 textarea + 실시간 미리보기 + 이미지 드래그·붙여넣기 업로드 + 커서 삽입
- `uploadWikiAssetAction` / `deleteWikiAssetAction` — **자산 테이블을 공유**하므로 그대로 동작한다
- `.editor-*` `.al-*` `.admin-*` CSS 전부
- 글 목록 화면 구조 — 상태 배지 + 제목 + 요약 + 삭제 버튼
- `renderMarkdownPreview`

### 필드는 대부분 같다

| ArticleEditor | 블로그 |
|---|---|
| `title`, `slug`, `status`, 요약(`desc`) | 그대로 |
| `parentId`(1차 탭 셀렉트) | → 카테고리 2단 셀렉트로 교체 |
| `kind`, `sortOrder`, `lastReview` | 제거 |
| — | **태그 입력 추가** (위키 편집기에는 없다) |
| — | **대표 이미지, 발행일 추가** |

### 새로 만든다

- 블로그 서버 액션 — `saveArticleAction` 이 위키 전용이다
- 카테고리 2단 셀렉트, 태그 입력, 대표 이미지 선택
- **드래그 정렬 UI** — 아직 없다. `admin/tabs/page.tsx` 는 `sortOrder` 숫자 입력이고
  주석에 "드래그 UI 는 추후 @dnd-kit" 라고 적혀 있다

### 이미지 업로드 로직을 두 벌로 만들지 않는다

`ArticleEditor` 를 통째로 복사하면 업로드·미리보기·커서 삽입이 두 벌이 된다.
그 부분만 **`MarkdownBodyEditor`** 로 떼어내고 위키 폼과 블로그 폼이 각각 감싼다.
위키 편집기의 동작은 바뀌지 않아야 한다(회귀 테스트 대상).

### 드래그는 새 의존성 없이 한다

`@dnd-kit` 을 넣지 않는다. 카테고리는 2단에 열 개 안팎이라 HTML5 drag and drop 으로 충분하다.
의존성 하나가 번들과 유지보수에 들어오는 값보다 얻는 것이 적다.
접근성을 위해 **드래그 외에 위/아래 버튼도 함께 둔다** — 키보드만으로도 순서를 바꿀 수 있어야 한다.

## 5. 선행 수정 — 이걸 먼저 해야 한다

**`attachReferenced()` 를 블로그 저장 경로에 넣어야 한다.**

지금 `WikiAssetService.attachReferenced(markdown)` 는 `ArticleService` 에서만 두 번 불린다.
블로그는 저장 경로 자체가 없어서 아직 문제가 드러나지 않았을 뿐이다.
이 라운드에서 저장을 만드는 순간, 넣지 않으면 **블로그 본문이 참조하는 자산이 `TEMP` 로 남는다.**

지금은 TEMP 를 치우는 스케줄 작업이 없어 무해하지만, 그런 작업을 만들면 블로그 이미지가 쓸려나간다.
**글 저장을 만드는 태스크에서 같이 처리한다.** 나중으로 미루지 않는다.

## 6. 화면

레이아웃은 기존 `admin-shell`(좌측 nav + 우측 content)을 그대로 쓴다. 색·타이포는 `tokens.css`.

### 6.1 글 목록 `/admin/blog/posts`

머리말 `블로그 글 — n편` + 우측 `＋ 새 글`.

한 줄: `상태 배지 · 카테고리 · 날짜` / **제목** / 요약 / 우측 삭제 버튼.
카테고리는 티스토리처럼 **`부모/자식` 경로 표기**를 쓴다. 우리도 2단이라 그대로 맞는다.

- `draft` 는 회색 배지, `published` 는 초록 배지 (위키 목록과 같은 규칙)
- 위키 목록에 있는 revision 링크(🕒)는 **없다** — 블로그에는 revision 이 없다(설계 4절)
- 정렬은 `published_at` 내림차순, `draft` 는 `updated_at` 기준으로 맨 위

### 6.2 글 쓰기·수정 `/admin/blog/posts/new`, `/admin/blog/posts/[id]`

위 4절의 필드 표대로. 위에서 아래로 **제목 → slug → 카테고리 → 상태 → 발행일 → 요약 → 대표 이미지 → 본문 → 태그**.

- **slug 는 제목에서 자동 생성하되 직접 고칠 수 있다.** 위키 편집기가 이미 그렇게 동작한다.
  블로그 slug 는 unique 가 아니므로(설계 5절) 중복 검사를 하지 않는다
- **`published` 로 저장할 때 `published_at` 이 비어 있으면 지금 시각을 넣는다.**
  V13 의 `chk_blog_post_published_at` 이 `published` + `published_at` null 을 막는다.
  화면에서 막지 않으면 DB 제약 위반이 그대로 500 으로 나간다
- 대표 이미지는 **본문에 이미 올린 자산 중에서 고른다.** 별도 업로드 칸을 만들지 않는다 —
  자산이 두 경로로 들어오면 참조 검사와 TEMP 정리가 복잡해진다
- 태그는 쉼표로 입력받아 화면에서 알약으로 보여준다. 저장 시 `tb_blog_tag` 에 upsert 하고
  `tb_blog_post_tag` 를 맞춘다. `BlogTagService.setTags()` 가 이미 그 일을 한다

### 6.3 카테고리 관리 `/admin/blog/categories`

티스토리와 같은 모양: 안내 한 줄 + 트리 박스. 각 행은 `드래그 핸들 · 이름 · (글 수) · 편집 · 삭제`.

- **2단까지만.** 자식 행에는 자식을 만들 수 없다. 규칙은 이미 `BlogCategoryService` 에 있다
- 드래그로 **같은 부모 안에서만** 순서를 바꾼다. 부모 사이 이동(자식을 다른 부모로)은 이번 범위 밖 —
  글이 딸린 카테고리를 옮기는 것은 되돌리기 어렵고, 지금 필요하지 않다
- 삭제는 `on delete restrict` 에 걸린다. **"글 n편이 있어 지울 수 없습니다. 먼저 옮겨 주세요"** 로
  안내한다. DB 오류 메시지를 그대로 내보내지 않는다
- 티스토리의 "주제 연결(IT 인터넷)" 은 우리에게 없는 개념이라 만들지 않는다

### 6.4 댓글 관리 `/admin/blog/comments`

한 줄: `작성자 · IP · 날짜` / 본문 / 원문 글 제목(링크) / 우측 삭제.

- **IP 는 `121.135.*.*` 까지만 보인다.** 우리는 `ip_prefix`(앞 2옥텟)만 저장하기 때문이다.
  티스토리는 `182.230.***.43` 처럼 마지막 옥텟까지 보여주는데, **우리 쪽이 더 보수적이고
  그대로 간다** — 원본을 저장하지 않는 것이 이 설계의 축이다(블로그 설계 8절)
- **휴지통 탭** — `deleted_at` 이 찬 댓글을 따로 본다. 복구(= `deleted_at` 을 비움)와 완전 삭제
- 차단은 이번 범위 밖. `ip_hash` 가 그 용도로 저장되고 있지만 차단 목록 UI 는 아직 필요하지 않다

### 6.5 통계 대시보드 `/admin/blog/stats`

티스토리 방문 통계와 같은 구성. **위에서 아래로 숫자 줄 → 일자별 차트 → 유입·디바이스.**

1. 숫자 줄 — 오늘/어제/누적 조회수, 오늘/어제/누적 방문자. `GET /api/blog/stats` 가 이미 준다
2. 일자별 막대 차트 — 조회수·방문자 2계열, 최근 30일. `일간/주간/월간` 토글
3. 유입 — 검색/SNS/직접/기타, 검색은 구글·네이버 등으로 펼침
4. 디바이스 — PC / 모바일 비율
5. 인기 글 top 5 — `GET /api/blog/posts/popular` 가 이미 있다

차트는 **새 라이브러리를 넣지 않는다.** 30일 막대 차트는 div 높이로 그린다.
값이 tabular-nums 로 읽히고 hover 툴팁만 있으면 충분하다.

## 7. 데이터 모델 변경 — 통계 보강

지금 `tb_blog_daily_stat` 은 `views / visitors / ref_search / ref_sns / ref_other` 다.
티스토리에 있고 우리에게 없던 것들을 **원본을 저장하지 않는 선에서** 채운다.

| 항목 | 어떻게 | 프라이버시 영향 |
|---|---|---|
| 직접 유입 분리 | referer 가 비었는지만 본다 | **없음** |
| 검색 세부(구글·네이버·다음) | referer 의 **호스트만** 보고 분류. 경로·쿼리는 계속 버린다 | 낮음. 호스트는 식별 정보가 아니다 |
| SNS 세부(카카오·페북·X) | 위와 같다 | 낮음 |
| 디바이스 PC/모바일 | User-Agent 에서 **모바일 여부 boolean 만**. UA 원문을 저장하지 않는다 | 낮음 |

**유입 키워드는 만들지 않는다.** 두 가지 이유다. 요즘 구글·네이버는 referrer policy 때문에
검색어를 넘기지 않아 대부분 빈다. 그리고 검색어는 민감할 수 있는 개인정보라
"식별 가능한 형태로 보관하지 않는다" 는 이 설계의 축과 정면으로 부딪힌다.

### 세로 테이블을 쓴다

`tb_blog_daily_stat` 에 컬럼을 계속 늘리지 않는다. 소스가 늘 때마다 마이그레이션이 붙는다.

#### `tb_blog_referrer_daily`

| 컬럼 | 타입 | 비고 |
|---|---|---|
| `stat_date` | date | |
| `source` | text | `google` `naver` `daum` `bing` … `sns:x` `direct` `other` |
| `count` | bigint | |
| | | PK(stat_date, source) |

#### `tb_blog_device_daily`

| 컬럼 | 타입 | 비고 |
|---|---|---|
| `stat_date` | date | |
| `device` | text | `pc` / `mobile` |
| `count` | bigint | |
| | | PK(stat_date, device) |

기존 `ref_search / ref_sns / ref_other` 컬럼은 **그대로 둔다.** 이미 쌓인 값이 있고,
지우면 과거 집계가 사라진다. 새 테이블은 이 시점부터 쌓인다.

### 분류 로직은 이미 거의 다 있다

`BlogReferrerBucket` 이 이미 `google.com`, `naver.com`, `daum.net`, `bing.com`, `x.com`,
`facebook.com` … 도메인 목록을 갖고 있으면서 `SEARCH` / `SNS` 하나로 뭉갠다.
**열거형을 세분화하고 도메인 → 소스 이름 매핑을 돌려주게 바꾸면 된다.**
호스트 매칭 규칙(정확히 일치하거나 서브도메인, 부분 문자열 금지)은 그대로 지킨다.

## 8. API

전부 `/api/admin/blog/**` 이고 기존 관리자 인증을 탄다.

| 메서드 | 경로 | 용도 |
|---|---|---|
| GET | `/posts` | 목록(draft 포함) |
| GET | `/posts/{id}` | 단건(draft 포함, 조회수 올리지 않음) |
| POST | `/posts` | 생성 |
| PUT | `/posts/{id}` | 수정 |
| DELETE | `/posts/{id}` | 삭제 |
| POST | `/categories` | 생성 |
| PUT | `/categories/{id}` | 수정(이름·설명) |
| POST | `/categories/reorder` | 순서 일괄 반영 |
| DELETE | `/categories/{id}` | 삭제(글 있으면 400) |
| GET | `/comments` | 목록(`?deleted=true` 로 휴지통) |
| DELETE | `/comments/{id}` | 관리자 삭제(암호 없이) |
| POST | `/comments/{id}/restore` | 복구 |
| GET | `/stats/daily?days=30` | 일자별 조회수·방문자 |
| GET | `/stats/referrers?days=30` | 유입 소스별 |
| GET | `/stats/devices?days=30` | 디바이스별 |

**공개 API 의 조회수 증가와 섞지 않는다.** 관리자 단건 조회는 `recordView` 를 부르지 않는다.
부르면 내가 글을 열어볼 때마다 조회수가 오른다.

## 9. 테스트

| 대상 | 확인 |
|---|---|
| 인증 경계 | 로그인 없이 `/api/admin/blog/posts` → 401·403 |
| 발행일 자동 | `published` + `published_at` 빈 값으로 저장 → 지금 시각이 들어간다 |
| 카테고리 2단 | 손자 생성 시도 거부 |
| 카테고리 삭제 | 글 있는 카테고리 삭제 → 400 과 안내 문구 |
| 순서 반영 | reorder 뒤 공개 레일의 카테고리 순서가 바뀐다 |
| 자산 부착 | 블로그 글 저장 후 본문이 참조하는 자산이 `TEMP` 가 아니다 (**5절**) |
| 관리자 조회 | 관리자 단건 조회로는 `view_count` 가 오르지 않는다 |
| 댓글 복구 | 휴지통에서 복구하면 공개 목록에 다시 나온다 |
| 위키 회귀 | `MarkdownBodyEditor` 분리 뒤에도 위키 편집·이미지 업로드가 그대로 동작한다 |
| 유입 분류 | `direct` 는 referer 없음, `google` 은 `www.google.com`, `mygoogle.com` 은 `other` |

## 10. 열린 항목

| 항목 | 결정 시점 |
|---|---|
| 카테고리를 다른 부모로 옮기기 | 필요해지면. 이번엔 같은 부모 안 정렬만 |
| 댓글 IP 차단 UI (`ip_hash` 는 이미 있다) | 스팸이 실제로 오면 |
| 예약 발행 (`published_at` 을 미래로) | 목록·공개 쿼리가 미래 글을 걸러야 한다. 이번 범위 밖 |
| 글 검색(관리자) | 글이 수십 편 넘어가면 |
