# jay-wiki 문서 전수 검토·개선 실행 가이드

이 문서는 다른 코딩 에이전트에게 jay-wiki의 글을 **카테고리별로 한 편씩 읽고, 근거를 확인하며, 실제 사이트에서 검증하도록**
작업을 맡길 때 사용하는 실행 지침이다.

목표는 문장을 그럴듯하게 늘리는 것이 아니다. 현재 시드 86편(초기 54편 전수 검토에서 출발한 글)의 글이 개발자 포트폴리오로 공개됐을 때 다음 질문에 답할 수 있게 만드는 것이다.

- 무엇을 왜 만들었는가?
- 본인이 실제로 구현하고 검증한 범위는 어디까지인가?
- 어떤 근거로 기술 선택과 결과를 설명하는가?
- 실패와 한계를 숨기지 않고 다음 판단으로 연결했는가?
- 면접관이 후속 질문을 해도 코드와 운영 기록으로 답할 수 있는가?

## 1. 반드시 먼저 이해할 콘텐츠 경계

| 대상 | 역할 | 편집 여부 |
|---|---|---|
| `scripts/seed-portfolio-wiki.mjs` | 검토된 탭·본문의 기준 콘텐츠 | **본문 수정 위치** |
| 로컬 PostgreSQL | 현재 로컬 사이트가 읽는 실행 본문과 revision의 SoT | 시드 스크립트로 동기화 |
| `posts/jay-wiki/` | 시드 콘텐츠를 읽기 위한 Markdown snapshot | **직접 수정 금지** |
| `docs/current-project-status.md` | 현재 구현·검증·보류 상태의 기준 문서 | 사실 판단 시 우선 확인 |
| `docs/wiki-editorial-plan.md` | 현재 글과 앞으로 작성할 후보의 편집 백로그 | 문서 수·상태 변경 시 갱신 |
| `진행상황.md` | 구현·문서·검증·배포 이력 | 작업 완료 시 기록 |
| `workbook/`, `docs/`, 코드·테스트·manifest | 글의 사실성과 구현 상태를 확인할 근거 | 필요한 범위에서 읽기 |

PostgreSQL이 실행 중 최신 본문의 SoT지만, 에이전트가 검토한 변경은 먼저 `scripts/seed-portfolio-wiki.mjs`에 반영한다. 이후
시드 스크립트로 로컬 DB에 동기화하고 export를 다시 생성한다. 관리자 화면이나 DB만 수정해 Git 기준 콘텐츠와 갈라지게 만들지 않는다.

### 편집 시 주의

시드의 본문은 `String.raw` template literal이다. 본문 안에 backtick을 넣으면 스크립트 문법이 깨질 수 있다.

- inline code는 backtick 대신 일반 텍스트로 쓴다.
- code block은 backtick 세 개가 아니라 물결표 세 개를 사용한다.
- `posts/jay-wiki/` 파일은 생성 결과이므로 직접 편집하지 않는다.
- DB에만 남아 있는 extra 문서는 자동 삭제하지 않는다.
- 운영 서버 쓰기, commit, push와 배포는 사용자가 명시적으로 요청했을 때만 한다.

### 2026-08-02 전수 검토 이후 바뀐 전제

초기 54편 전수 검토 이후 현재 시드가 86편으로 늘었다. 이전 지침을 그대로 따르기 전에 확인한다.

- **탭 안 문서 정렬은 `sortOrder` 오름차순이 1차 기준이다.** 이전에는 `updated_at` 내림차순이라 글을 고칠
  때마다 그 글이 목록 맨 위로 올라갔다. 이제 시드의 `sortOrder`가 화면 순서를 그대로 결정하므로,
  글을 추가하거나 순서를 바꿀 때 같은 탭 안의 `sortOrder` 충돌을 확인한다.
- **`tb_article.created_at`이 생겼다.** 정렬용이 아니라 작성일 표시용이다. 근거 없는 값을 채우지 않는 규칙이
  적용돼 일부 문서는 `null`일 수 있다.
- 두 변경 모두 `docs/current-project-status.md`의 `2026-08-02 문서 정렬 기준 변경과 created_at 도입` 절에
  현재 반영 상태가 있다. 로컬은 V12 적용과 새 정렬 확인을 마쳤고 `d2c2b4d`로 2026-08-21 운영 배포도 완료했다.
- 이미지 자산은 성격에 따라 위치가 다르다. 글과 함께 검토·배포되는 고정 이미지는 저장소의 web public에,
  운영 중 관리자가 올리는 이미지는 MinIO assetId 경로에 둔다. assetId가 환경마다 새로 발급되기 때문이다.
- 공개 포트폴리오이므로 **외부 링크는 실제로 열리는지 확인한다.** 전수 검토에서 비공개 저장소를 가리키는
  404 링크 2건이 나왔다. 하드웨어·화면 사진을 추가할 때는 MAC 주소, 시리얼, 개인정보가 찍혔는지 먼저 본다.

## 2. 전체 작업 원칙

### 한 번에 한 카테고리, 한 편씩

86편 전체를 한 번에 다시 쓰지 않는다. 다음 단위를 지킨다.

1. 카테고리 하나의 전체 글 목록과 중복을 먼저 확인한다.
2. 글 한 편을 끝까지 검토한다.
3. 근거를 찾고 판정을 내린다.
4. 필요한 경우에만 본문을 수정한다.
5. 로컬 DB와 export를 동기화한다.
6. 실제 브라우저에서 해당 글을 확인한다.
7. 결과를 기록한 뒤 다음 글로 이동한다.

한 편을 끝내기 전에 다른 글을 동시에 대규모 수정하지 않는다. 여러 글의 공통 표현이나 상호 모순을 발견하면 현재 글의 검토 기록에
남기고, 카테고리 전체를 다 읽은 뒤 함께 조정한다.

### 문서 분량보다 주장 밀도를 높인다

다음 내용이 이미 충분하면 문장을 추가하지 않는다.

- 문제와 배경
- 선택 기준과 대안
- 구현 경계
- 실행 또는 운영 증거
- 실패와 한계
- 본인 기여
- 다음 단계

기술 이름, 일반론과 같은 결론을 반복하는 문장은 줄인다. 글이 길어져도 새로운 판단이나 증거가 늘지 않으면 개선이 아니다.

### 근거가 없으면 만들지 않는다

- 코드에서 확인하지 못한 기능은 구현 완료라고 쓰지 않는다.
- 운영 기록이 없으면 운영 검증이라고 쓰지 않는다.
- 결정론적 simulator, Mock과 실제 부하·실서비스 결과를 구분한다.
- 팀 프로젝트의 팀 전체 성과와 개인 기여를 구분한다.
- 수치에는 기준일, 표본, 단위와 측정 조건을 붙인다.
- 외부 자료를 사용할 때는 출처와 라이선스를 확인한다.
- 기억이나 추정만 있는 내용은 `사용자 확인 필요`로 남긴다.

## 3. 검토 판정

각 문서에는 다음 중 하나를 부여한다.

| 판정 | 의미 | 조치 |
|---|---|---|
| PASS | 사실·구성·근거·화면이 공개 가능한 수준 | 수정하지 않고 검증 기록만 남김 |
| MINOR | 표현, 순서, 링크나 작은 설명 보완 | 범위를 좁혀 바로 수정 |
| MAJOR | 사실 경계, 근거, 기승전결이나 본인 기여가 불명확 | 근거 조사 후 본문 재구성 |
| HOLD | 사용자만 확정할 수 있는 경험·수치·역할이 필요 | 임의 수정 금지, 질문 목록 작성 |

오래된 글이라는 이유만으로 MAJOR를 주지 않는다. 현재 코드와 충돌하거나 독자가 잘못 이해할 가능성이 있을 때 문제로 판정한다.

## 4. 모든 글에 공통으로 적용할 검토표

### 메타데이터

- 제목만 읽어도 대상과 핵심 판단이 드러나는가?
- summary가 제목을 반복하지 않고 글에서 얻을 내용을 한 줄로 설명하는가?
- slug, parentId, sortOrder, kind와 tags가 현재 카테고리에 맞는가?
- 같은 카테고리의 최신순·읽기 순서가 자연스러운가?
- lastReview가 실제 검토일과 맞는가?

### 기승전결

- 첫 두세 문단에서 문제, 프로젝트 범위와 글의 주장을 알 수 있는가?
- 기술을 선택한 이유와 검토한 대안이 있는가?
- 구현 흐름이 나열이 아니라 입력·처리·결과로 연결되는가?
- 결과가 수치, 실행 화면, test, log, DB 또는 운영 기록으로 뒷받침되는가?
- 실패와 한계가 변명 없이 설명되는가?
- 회고가 일반적인 교훈이 아니라 다음 설계·일정·완료 조건을 바꾸는가?

### 사실성과 증거

- 현재 코드, schema, manifest와 문서 설명이 일치하는가?
- 구현, 로컬 검증, 운영 검증, 계획 상태가 구분되는가?
- 수치의 기준일·표본·단위·환경을 확인할 수 있는가?
- Mock·simulation 결과를 실제 서비스 성능이나 실거래 결과로 오인할 표현이 없는가?
- commit, runbook, 공개 링크와 이미지가 실제 근거로 이어지는가?
- 이미 제거하거나 이름이 바뀐 기능을 현재 기능처럼 설명하지 않는가?

### 포트폴리오와 면접

- 본인이 내린 기술적 판단이 드러나는가?
- 본인 기여와 팀·AI·기존 프로젝트의 기여가 구분되는가?
- trade-off를 설명할 수 있는가?
- 가장 어려웠던 문제와 해결 과정이 구체적인가?
- 면접관이 `왜`, `대안은`, `실패하면`, `어떻게 검증했나`를 물어도 본문 근거로 답할 수 있는가?
- 이 글에서만 확인할 수 있는 고유한 어필 지점이 있는가?

### 문장과 시각

- 같은 결론이나 기술 목록이 반복되지 않는가?
- 긴 문단을 표·목록으로 바꾸는 편이 실제 이해에 도움이 되는가?
- 표가 지나치게 넓거나 mobile에서 내용을 잃지 않는가?
- 이미지에 대체 text와 본문에서의 해석이 있는가?
- Mermaid가 단순 장식이 아니라 실제 흐름을 설명하는가?
- 내부 링크, 외부 링크와 이미지가 HTTP 200인가?
- 한국어 줄바꿈, code block과 heading hierarchy가 자연스러운가?

## 5. 카테고리별 검증 초점과 작업 순서

### 0. DASHBOARD: 전체 지도

대상: `00-start`, 1편

먼저 읽는다. 나머지 문서의 약속과 실제 카테고리 구조가 일치하는지 확인하는 기준이다.

- 프로젝트를 BUILD, OPERATE, IMPROVE, LAB으로 읽는 이유가 명확한가?
- 현재 기술 스택과 오케스트레이션 맵이 실제 코드·manifest와 일치하는가?
- 실행 가능한 시나리오와 문서 링크가 현재 경로로 연결되는가?
- 문서 수처럼 자주 바뀌는 값이 핵심 설명을 방해하지 않는가?
- 처음 방문한 사람이 다음에 무엇을 읽거나 실행할지 판단할 수 있는가?

### 1. BUILD: 설계와 구축

대상: `01-infra`, `02-backend`, `03-data`, `04-frontend`, 총 18편

이 카테고리는 **왜 이 구조를 선택했고 어떻게 만들었는가**를 증명한다.

#### 인프라

- miniPC, k3s, Cloudflare Tunnel과 storage 선택 이유가 제약과 연결되는가?
- host, container, cluster와 외부 edge의 책임이 섞이지 않는가?
- 재부팅 복구, resource와 hardware 설명에 실측 근거가 있는가?
- AWS 비교는 기준일·region·instance 조건을 포함하고 현재 정보와 구분되는가?

#### 백엔드

- Browser → Next.js BFF → Spring → FastAPI 경계가 실제 route와 일치하는가?
- 인증, 오류, timeout, idempotency와 transaction 경계가 설명되는가?
- 코드 예시는 실제 구현과 동일하거나 예시임을 명시하는가?
- 외부 API 실패와 내부 domain failure가 구분되는가?

#### 데이터

- PostgreSQL SoT, revision, restore, OpenSearch, Redis, Kafka와 MinIO의 역할이 겹치지 않는가?
- 데이터 소유권, 정합성, index와 lifecycle을 설명하는가?
- OpenSearch nori 선택을 Elasticsearch와 단순 제품 비교로 과장하지 않는가?
- backup 파일 생성과 실제 restore 검증을 구분하는가?

#### 프론트엔드

- 정보 구조, BFF, server/client component와 responsive 선택이 실제 코드와 맞는가?
- 간헐적 CSS, theme persistence와 CJK 줄바꿈 같은 문제를 원인·수정·회귀 검증으로 설명하는가?
- 디자인 개선이 예쁘다는 평가를 넘어 탐색 비용과 안정성 개선으로 측정되는가?

BUILD 완료 조건은 독자가 저장소를 보지 않아도 주요 경계를 설명할 수 있고, 저장소를 보면 그 설명을 확인할 수 있는 상태다.

### 2. OPERATE: 운영과 검증

대상: `05-observability`, `06-operations`, `07-demo`, `08-security`, `09-verification`, 총 15편

이 카테고리는 **실제로 돌리고, 관측하고, 실패에서 복구할 수 있는가**를 증명한다.

#### 관측

- metric, log와 trace의 역할과 연결 지점이 구분되는가?
- Prometheus, Loki, Tempo, OTel Collector와 Grafana의 데이터 흐름이 맞는가?
- 공개 aggregate와 보호된 raw 운영 정보의 경계가 설명되는가?

#### 운영

- GitHub Actions → GHCR → runner → k3s rollout 흐름이 현재 workflow와 일치하는가?
- backup, MinIO asset과 GitOps content sync의 실패·재시도·rollback 경계가 있는가?
- Secret, 계정과 내부 endpoint를 공개 문서에서 과도하게 노출하지 않는가?

#### 시나리오·시연

- 화면에서 실제로 실행되는 기능과 설명용 정책 model이 구분되는가?
- Saga, Kafka, Redis와 검색 시나리오의 상태 변화가 DB·event·관측 증거로 이어지는가?
- happy path뿐 아니라 retry, DLQ, compensation과 failure injection을 설명하는가?

#### 보안

- 위협 모델, 공격 표면과 보호 자산이 먼저 정의되는가?
- Markdown XSS, OAuth, ADMIN·USER, TOTP와 machine token 경계가 코드와 일치하는가?
- 보안을 `문제없다`고 단정하지 않고 residual risk와 운영 책임을 남기는가?

#### 운영 검증

- `구현했다`가 아니라 언제, 어떤 환경에서, 무엇을 관찰했는지 기록하는가?
- screenshot이나 성공 로그만으로 복구·무결성을 과장하지 않는가?
- 실패한 배포와 rollback도 결과로 남기는가?

OPERATE 완료 조건은 각 글에 최소 하나의 실행 증거와 그 증거가 말하지 못하는 한계가 함께 있는 상태다.

### 3. IMPROVE: 개발 과정과 개선

대상: `10-development-process`, `11-ai-usage`, `12-governance`, `13-retrospective`, `14-roadmap`, 총 12편

이 카테고리는 **실패와 변경을 어떻게 다음 판단으로 바꿨는가**를 증명한다.

#### 개발 프로세스

- 요구사항 → 조사 → 구현 → test → browser QA → 문서 → 배포가 실제 작업 방식과 일치하는가?
- 가설 기반 debugging과 증거 수준이 구체적 사례에 연결되는가?
- AI가 만든 계획 문구가 아니라 실제 저장소의 반복 가능한 절차인가?

#### AI 활용

- AI가 담당한 부분, 사람이 결정·검증한 부분과 실패가 구분되는가?
- agent, plan, skill과 병렬 작업의 효과를 결과 없이 과장하지 않는가?
- TOTP, Keychain과 machine access 설명이 보안 우회처럼 보이지 않는가?

#### 거버넌스

- license, font, image, 개인정보와 공개 asset의 책임이 구분되는가?
- 법률 자문처럼 단정하지 않고 출시 전 확인할 항목을 제시하는가?
- MinIO 공개 경로와 내부 원본, 삭제·보존 정책이 현재 구현과 일치하는가?

#### 회고

- 잘한 점, 부족한 점과 다시 한다면을 분리하는가?
- 회고가 특정 사건·수치·결정에 연결되는가?
- 실패를 미화하거나 결과론적으로 설명하지 않는가?

#### 로드맵

- 구현 완료와 후보·보류 항목이 분리되는가?
- 각 항목의 착수 조건과 완료 증거가 있는가?
- 이미 완료된 항목이 미래 계획에 남아 있지 않는가?

IMPROVE 완료 조건은 글의 교훈이 `더 잘하겠다`가 아니라 다음 프로젝트의 설계, 일정 또는 검증 기준을 실제로 바꾸는 상태다.

### 4. LAB: 프로젝트와 실험

대상: `15-personal-projects`, `16-team-projects`, `17-tech-lab`, `18-tools-workflow`, 총 8편

이 카테고리는 **jay-wiki 밖의 프로젝트·실험·도구 경험을 사실에 맞게 설명하는가**를 증명한다.

#### 개인 프로젝트

- 문제를 직접 겪은 맥락과 사용자가 누구인지 드러나는가?
- 기술 기능보다 제품 판단과 의도적으로 구현하지 않은 범위가 설명되는가?
- screenshot, 저장소, 실행 방법과 현재 한계가 연결되는가?
- 다른 개인 프로젝트 글과 구조·표현이 지나치게 반복되지 않는가?

#### 팀 프로젝트

- 과정명, 기간, 팀 규모와 목표가 명시되는가?
- 초기 역할, 실제 기여와 팀 전체 결과가 구분되는가?
- 협업 방식과 통합 과정의 한계를 숨기지 않는가?
- 성과 수치가 표본·기간·Mock 조건과 함께 제시되는가?
- `혼자 만들었다` 또는 `AI가 만들었다`처럼 실제 협업을 왜곡하지 않는가?

#### 기술 실험

- 비교 대상이 충분히 동등하고 환경·version·hardware가 고정되는가?
- 측정 script, raw 결과와 checksum을 재현할 수 있는가?
- 작은 benchmark를 일반 성능 우위로 확대하지 않는가?
- 체감과 정량 결과가 다른 경우 둘 다 남기는가?

#### 도구·워크플로

- 공식 기능 소개가 아니라 실제 사용 흐름과 판단이 중심인가?
- 장점, 중단 이유와 다시 평가할 조건이 구체적인가?
- 사용하지 못한 기능을 사용 경험처럼 표현하지 않는가?
- 외부 screenshot과 logo의 출처·license가 명시되는가?

LAB 완료 조건은 각 글에서 `무엇을 사용했다`보다 `어떤 상황에서 어떤 판단을 했고 무엇이 남았는가`가 먼저 보이는 상태다.

## 6. 한 편을 검토하는 표준 실행 절차

### 단계 A. 현재 글과 이웃 글 읽기

1. `posts/jay-wiki/<category>/<slug>.md`에서 현재 글을 읽는다.
2. 같은 디렉터리의 제목과 summary를 함께 읽어 중복을 찾는다.
3. `scripts/seed-portfolio-wiki.mjs`의 해당 article metadata와 body를 찾는다.
4. `docs/current-project-status.md`에서 현재 구현 상태를 확인한다.

### 단계 B. 근거 조사

글의 핵심 주장마다 다음 중 최소 하나를 연결한다.

- 실제 source code와 schema
- test 또는 build 결과
- Kubernetes manifest와 workflow
- runbook과 진행 기록
- 공개 페이지와 실행 화면
- 사용자가 제공한 원본 프로젝트 문서
- 운영 metric, log, trace, DB 원장 또는 timestamp가 있는 screenshot

핵심 주장에 근거가 없으면 문장을 강화하지 말고 약화하거나 `HOLD`로 분류한다.

### 단계 C. 개선안 결정

수정 전 아래 형식으로 짧게 판단한다.

```text
문서: <title> (<slug>)
판정: PASS | MINOR | MAJOR | HOLD
핵심 주장: <한 문장>
좋은 점: <유지할 내용>
문제: <사실·구성·근거·시각 문제>
근거: <확인한 코드·문서·실행 결과>
수정 범위: <바꿀 section과 바꾸지 않을 section>
사용자 확인: <필요한 질문, 없으면 없음>
```

PASS면 억지로 수정하지 않는다. HOLD면 사용자 답을 받기 전까지 추정으로 메우지 않는다.

### 단계 D. 본문 수정

- 기존 article object 안에서 metadata와 body만 필요한 만큼 수정한다.
- unrelated article, code와 design은 건드리지 않는다.
- 이미지가 필요하면 프로젝트 소유 자료 또는 출처가 명확한 자료를 사용한다.
- 단순 장식 이미지는 추가하지 않는다.
- 이미지에는 의미 있는 alt text를 작성하고 본문에서 무엇을 봐야 하는지 설명한다.

### 단계 E. 로컬 동기화

먼저 문법과 diff를 확인한다.

```bash
node --check scripts/seed-portfolio-wiki.mjs
node scripts/export-portfolio-wiki.mjs
node scripts/seed-portfolio-wiki.mjs --dry-run
```

dry-run이 검토한 글 외의 변경을 보고하면 원인을 확인한 뒤 멈춘다. 예상한 변경만 있으면 로컬 DB에 반영한다.

```bash
node scripts/seed-portfolio-wiki.mjs
node scripts/seed-portfolio-wiki.mjs --dry-run
```

두 번째 dry-run의 완료 기준은 다음과 같다.

```text
0 tab changes, 0 article changes, 0 extras
```

기존 환경에 extra가 이미 존재한다면 자동 삭제하지 않고 수량과 이유를 보고한다.

### 단계 F. 실제 화면 검증

로컬 페이지를 실제 브라우저에서 연다.

```text
http://localhost:3000/wiki/<slug>
```

최소 다음 조건을 확인한다.

- HTTP 200
- desktop 1440px
- mobile 390px
- 제목·summary·본문의 한글 줄바꿈
- 표의 가로 처리와 code block overflow
- 이미지 로드와 비율
- Mermaid syntax error 부재
- 내부 링크와 외부 링크
- browser console runtime error 부재
- 같은 카테고리 문서 목록의 제목과 timestamp 잘림 부재

긴 문서는 첫 화면만 보지 않는다. 이미지, 넓은 표, 회고와 관련 자료가 있는 마지막 section까지 내려가 확인한다.

### 단계 G. 기록

한 편이 끝날 때 다음을 `진행상황.md`에 기록한다.

- 무엇을 검증했는가
- 어떤 근거를 확인했는가
- 무엇을 바꾸고 무엇을 유지했는가
- 로컬 DB·export 동기화 결과
- desktop·mobile 화면 검증 결과
- 운영 배포 여부

카테고리 전체가 끝나면 중복, 상호 링크, 읽기 순서와 남은 HOLD 항목을 별도로 요약한다.

## 7. 다른 에이전트에게 전달할 시작 프롬프트

아래에서 `<CATEGORY>`와 `<DIRECTORY>`만 바꿔 사용한다.

```text
docs/wiki-article-review-and-improvement-playbook.md를 먼저 끝까지 읽어줘.

jay-wiki의 <CATEGORY> 카테고리를 검토하고 개선해줘.
대상 디렉터리는 posts/jay-wiki/<DIRECTORY>/ 이다.

규칙:
1. 먼저 카테고리 전체 글 목록, 읽기 순서와 중복 가능성을 보고한다.
2. 글을 한 편씩 처리하고, 한 편의 검증·수정·로컬 반영·브라우저 QA를 끝낸 뒤 다음 글로 간다.
3. scripts/seed-portfolio-wiki.mjs를 기준 콘텐츠로 수정한다. posts/jay-wiki는 직접 수정하지 않는다.
4. 현재 코드, test, manifest, docs/current-project-status.md와 진행상황.md를 근거로 사실을 확인한다.
5. 근거 없는 기능·수치·기여를 만들지 않는다. 사용자만 확정할 수 있으면 HOLD와 질문으로 남긴다.
6. 구현, Mock, 로컬 검증, 운영 검증과 계획 상태를 구분한다.
7. PASS 문서는 억지로 고치지 않는다.
8. 각 문서 결과를 제목, slug, 판정, 핵심 문제, 근거, 변경 내용, 화면 검증으로 표에 누적한다.
9. 로컬 DB 동기화까지만 수행한다. commit, push와 운영 배포는 하지 않는다.
10. 모든 변경은 진행상황.md에 기록한다.

완료 조건:
- 대상 카테고리의 모든 글에 PASS, MINOR, MAJOR 또는 HOLD 판정이 있다.
- 수정한 글은 node 문법 검사와 시드 dry-run no-op을 통과한다.
- 수정한 모든 페이지를 desktop 1440px와 mobile 390px에서 실제로 확인한다.
- 카테고리 내부 중복, 모순, 링크와 다음 개선 항목을 마지막에 요약한다.
```

## 10. 최종 전수 검토 완료 조건

다음 조건을 모두 만족해야 전체 문서 검토가 끝난다.

- 현재 운영 11개 탭 86편이 모두 판정됐다.
- 시드, export와 로컬 DB의 tab·slug·문서 수가 일치한다.
- MAJOR가 해결됐거나 HOLD 사유와 사용자 질문이 남아 있다.
- 카테고리 안과 카테고리 사이의 중복·모순을 정리했다.
- 현재 상태와 로드맵의 완료·보류 표현이 일치한다.
- 모든 내부 링크와 정적 asset이 정상 응답한다.
- 수정한 모든 페이지가 desktop과 mobile에서 읽힌다.
- 기술·운영·성과 수치에 조건과 한계가 명시된다.
- 개인·팀·AI 기여 경계가 왜곡되지 않는다.
- `진행상황.md`에 카테고리별 검토 기록이 남아 있다.

최종 결과는 글을 모두 길게 만드는 것이 아니라, **각 글의 주장을 현재 구현과 증거 수준에 맞추고 서로 이어지는 포트폴리오로
정리하는 것**이다.
