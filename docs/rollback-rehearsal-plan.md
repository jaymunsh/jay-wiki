# 롤백 리허설 계획

## 2026-08-16 갱신 — 스텝 실패 경로는 실제 사고에서 검증됐다

「아직 실행하지 않았다」는 더는 사실이 아니다. 배포 run 31944815984 에서 블로그 발행 스텝이
처음 돌면서 실패했고(ConfigMap 키에 `/` 불가), 그 실패에서 워크플로의 `if: failure()` 롤백 스텝이
**실제로 탔다.**

| 시각 (KST) | |
|---|---|
| 20:51:20 | 스텝 실패 |
| 20:51:21 | rollback 시작 |
| 20:51:52 | rollout 완료 |
| 20:51:55 | `rollback verified: https://portfolio.leneu.cloud responds` |

약 32초. 공개 화면은 죽지 않았다. 성격은 아래 후보 1번(스모크 실패)과 가깝다 —
캡처·rollout 이후의 스텝 실패라 워크플로 롤백 스텝 경로를 탔고, Pod 자체는 멀쩡했다.

## 2026-08-19 갱신 — 후보 2번(뜨지 않는 이미지)도 실행했다

없는 태그로 `set image` 해서 ImagePullBackOff 를 만들고, `rollback-deployment.sh` 를 운영에서 처음 태웠다.

| | |
|---|---|
| 깨뜨린 시각 | 11:04:50 UTC |
| ImagePullBackOff 확인 | 11:05:35 (45초 뒤) |
| 롤백 | 11:05:40 → 11:05:49, **9초** |
| 공개 프로브 | 1초 간격 66회, **전부 200, 실패 0** |

옛 파드 둘은 내려가지 않았다 — `maxUnavailable 25%` 가 replicas 2 에서 0 이라, 새 파드가 Ready 가
되기 전에는 아무것도 못 내린다. 기록은 위키 `image-that-never-pulled` 에 있다.

**남은 것은 「떴는데 잘못 도는 이미지」다.** readinessProbe 가 `/actuator/health` 만 보므로
기동은 되고 기능이 깨진 판은 이 경로로 안 잡힌다. 아래 본문의 계획은 그 관점에서 그대로 둔다.

---

위 두 리허설은 완료됐다. 아래 내용은 당시 후보와 측정 항목을 보존한 계획 섹션이며,
현재 남은 후보는 **떴지만 기능이 깨진 이미지** 하나다.

## 무엇을 확인하려는 것인가

"롤백이 있다"는 지금 코드가 있다는 뜻이다. 리허설은 그걸 아래 다섯 개로 바꾼다.

1. `capture-deployment-images.sh` 가 배포 전 이미지 네 줄을 정확히 남기는가
2. 실패가 났을 때 워크플로가 롤백 스텝을 **실제로 타는가** (`if: failure() && steps.capture.outcome == 'success'`)
3. `set image` 가 네 Deployment를 전부 되돌리고 `rollout status` 가 180초 안에 끝나는가
4. 되돌린 뒤 공개 경로가 살아나는가 (스크립트 자신의 `rollback verified`)
5. **장애 시간이 얼마인가.** 지금은 아무도 모른다

## 어디서 도는가

`kubectl` 은 개발 머신에서 클러스터에 안 닿는다. 리허설은 miniPC 위에서 돈다.
경로는 둘 중 하나다.

| 방법 | 어떻게 | 쓸 곳 |
|---|---|---|
| `workflow_dispatch` | `deploy.yml` 에 이미 있다. 실패를 심은 브랜치에서 수동 실행 | 파이프라인 전체 경로를 재는 진짜 리허설 |
| miniPC에서 직접 | LAN `192.168.0.82` 로 ssh → capture → 일부러 깨진 이미지 → rollback | 스크립트만 따로 재는 최소 리허설 |

`cloudflared` 는 건드리지 않는다. 재시작하면 ssh 경로가 끊긴다.

## 어떻게 실패시킬 것인가 — 후보 셋

깨뜨리는 방법에 따라 재는 것이 다르다. **세 개를 다 하지 말고 2번부터 한다.**

### 1. 스모크 URL 하나를 실패시킨다 (가장 가벼움)

`deploy.yml` 의 스모크 curl에 없는 경로를 하나 추가하면 `curl -fsS` 가 비영으로 끝난다.
캡처 이후·rollout 이후 실패라 **워크플로 롤백 스텝** 경로를 탄다.
다만 이때 Pod는 멀쩡하므로, 되돌려도 화면은 원래 정상이다. 3·4번은 못 재고 2번만 재진다.

### 2. 뜨지 않는 이미지를 배포한다 (권장 — 여기부터 한다)

`deploy-ghcr-images.sh` 가 존재하지 않는 태그로 `set image` 하게 만들면 새 Pod가
`ImagePullBackOff` 로 멈추고 `rollout status` 가 180초 뒤 실패한다.
이건 **배포 스크립트 안의 `trap ... ERR`** 경로다 — 진단 덤프(describe·로그·이벤트)까지 함께 확인된다.

Deployment의 `maxUnavailable` 기본값 덕에 옛 Pod가 남아 있어 **공개 화면은 안 죽는 게 정상**이다.
그 "안 죽는다"를 확인하는 것도 이 리허설의 목적이다. 안 죽지 않으면 그게 발견이다.

### 3. 뜨지만 깨진 이미지를 배포한다 (가장 무거움, 나중)

Pod는 Ready인데 공개 경로가 500인 상태. 실제 장애에 가장 가깝고, `rollout status` 가 통과한 뒤
스모크에서 잡히는 유일한 경우다. 옛 Pod가 이미 교체된 뒤라 **진짜 다운타임이 생긴다.**
2번 기록을 남긴 다음에 한다.

## 무엇을 잴 것인가

기록 없이 돌리면 리허설이 아니라 그냥 사고다. 아래를 남긴다.

- 캡처 파일의 실제 네 줄 (namespace / deployment / container / image)
- 실패 감지 시각 → 롤백 시작 → `rollout status` 완료 → `rollback verified` 까지의 각 구간 시간
- 그동안 공개 화면이 실제로 죽었는지 (별도 창에서 홈을 1초 간격으로 curl해 실패 건수를 센다)
- 진단 덤프에 실제로 원인이 보였는지 (2번은 `ImagePullBackOff` 가 이벤트에 찍혀야 한다)
- 롤백 후 네 Deployment의 이미지가 캡처값과 같은지

## 되돌아가는 길

리허설 자체가 실패했을 때의 길도 있어야 한다.

- 캡처 파일은 리허설 전에 손으로 한 번 더 떠서 miniPC 로컬에 둔다. 워크플로의 `RUNNER_TEMP` 는 잡이 끝나면 사라진다
- 최악의 경우 `main` 의 마지막 정상 커밋 SHA 이미지를 직접 `set image` 한다. 그 SHA를 리허설 전에 적어 둔다
- 콘텐츠는 건드리지 않는다. 롤백 스크립트는 이미지만 되돌리고 DB는 손대지 않는다.
  다만 배포는 콘텐츠 시드까지 돌리므로, **시드 단계 전에 실패시키는 편이 안전하다** (2번이 그렇다)
