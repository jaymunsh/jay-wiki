## 발행 변경을 적용할 때

1. 운영 글 사본과 현재 초안을 별도로 보존한다. 충돌을 해결하려고 초안을 먼저 내려받기로 덮지 않는다.
2. `syncHash`는 콘텐츠의 기준 버전이다. 비밀번호나 내부 동기화 토큰이 아니다.
3. 최초 도입 시 운영과 동일한 초안을 내부 발행 경로로 보내면 `unchanged`와 syncHash를 받고 머리말에 기록된다.
   기존 내용과 다른 초안인데 syncHash가 없다면 409가 정상이다. 운영 사본을 별도 파일에 보존·대조한 뒤
   그 기준을 확보하고 편집본에 반영해야 한다. 409를 무시하거나 현재 해시를 무조건 재조회해 재시도하지 않는다.
4. 기준을 얻은 이후 제목·본문·태그·발행일·대표 이미지·시리즈 연결 등이 운영에서 달라지면 오래된 초안은 409다.
   조회수는 해시에 넣지 않는다. 상태 전환도 비교한다. 표시용 updatedAt과 동기화 기준 해시는 분리했다.
5. 발행 스크립트가 돌려받은 syncHash를 초안에 새기므로 성공 후 초안을 커밋한다.
   클러스터 Job의 임시 디렉터리에서만 새겨진 값은 저장소로 돌아오지 않는다. 수동 발행 후 커밋이 우선이다.
6. 이 경계는 내부 콘텐츠 싱크에 적용된다. 관리자 UI의 모든 편집 폼에 낙관적 잠금을 구현한 것은 아니다.
   관리자 로그인으로 직접 PUT하는 미리보기 경로도 기존 동작을 유지한다.
7. `blog-sync`는 본문이 같으면 같은 글로 판단하는 기존 규칙이 남는다. 메타데이터까지 포함한
   양방향 3-way 비교와 관리자 편집 폼의 충돌 UI는 후속이다.

## 배포 전 남은 조건

- 초안 압축 크기 검사. 기존 기록에서 이미 600,000바이트를 넘었다. ConfigMap 운반 방식 교체 전에는 배포를 진행하지 않는다.
- 초기 syncHash 수집과 초안별 신규 발행 여부 검토. 이전 미추적 글을 전부 자동 발행해도 된다고 간주하지 않는다.
- 보안 워크플로의 실제 GitHub 실행 확인. 이번에는 5개 이미지를 로컬에서 모두 재빌드·재스캔하지 않았다.
- Cloudflare Access 재인증 후 운영 이미지·RBAC·NetworkPolicy를 읽기 전용으로 대조한다.
- 개발 서버는 `npm run dev`의 loopback 바인딩을 사용한다. Origin 검사 자체가 임의 클라이언트의 인증 수단은 아니다.
