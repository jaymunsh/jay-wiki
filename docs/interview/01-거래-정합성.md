# 01. 거래 · 정합성

사이트 그룹: **거래·정합성** — "동시 요청과 재실행에서도 주문, 잔액, 쿠폰과 정산 결과를 한 번만 확정한다."

**4편 전부 B군(고정 대본)이다.** 화면에서 실행 버튼을 누르면 단계가 흐르지만, 실제로 동시 요청이 발생하거나 DB 락이 걸리는 게 아니라 **미리 적힌 시나리오가 재생**된다.

그래서 이 파일은 **"설계만 한 것을 어떻게 당당하게 말하는가"의 첫 사례**이기도 하다.
결론부터 말하면 — **감추지 않고 내가 먼저 말하되, 설계의 깊이로 증명한다.**

---

## 시작하기 전에 — 이 그룹을 관통하는 두 개의 축

02(분산·연동)가 "응답이 없다"는 하나의 문제였다면, 이 그룹은 **축이 둘**이다.

```
        ┌──────────────────────────────────────┐
        │  같은 일이 "두 번" 벌어지는 두 가지 방식 │
        └──────────────────────────────────────┘
                    │
        ┌───────────┴───────────┐
        │                       │
   ① 동시에 (concurrency)   ② 다시 (retry / 재실행)
        │                       │
   "둘이 같은 순간에"        "하나가 시간차를 두고 두 번"
        │                       │
   마지막 재고에 주문 2건     결제 callback이 두 번 옴
   쿠폰 100장에 요청 120개    정산 배치를 다시 돌림
        │                       │
        ▼                       ▼
   해법: 원자성(atomicity)   해법: 멱등성(idempotency)
   "읽고 쓰는 사이를 쪼갤 수 없게"  "몇 번 해도 결과가 한 번"
```

**이 둘은 다른 문제고 해법도 다르다.** 헷갈리면 면접에서 바로 티가 난다.

| | ① 동시성 문제 | ② 재실행 문제 |
|---|---|---|
| 언제 생기나 | 두 요청이 **같은 순간** | 한 요청이 **시간차를 두고 두 번** |
| 증상 | 재고가 -1이 된다, 쿠폰이 120장 나간다 | 결제가 두 번 된다, 정산이 중복된다 |
| 해법 | **원자성** — 읽기·판단·쓰기를 쪼갤 수 없게 | **멱등성** — 같은 키는 한 번만 처리 |
| 도구 | 조건부 UPDATE, 락, Redis Lua, unique 제약 | 멱등키, unique 제약, 처리 기록 |

> **공통 도구가 하나 있다: `UNIQUE` 제약.**
> 이건 동시성과 재실행을 **동시에** 막는다. 그래서 최후의 방어선이다. (뒤에서 자세히)

네 편의 배치는 이렇다.

| 편 | 주로 다루는 축 |
|---|---|
| 주문·재고·결제 확정 | ① 동시성(마지막 재고) + ② 재실행(중복 callback) |
| 상품권 사용 정합성 | ② 재실행 중심 (중복 재전송, 응답 유실) |
| 선착순 쿠폰 발급 경합 | ① 동시성 중심 (120 요청 → 100장) |
| 정산 배치 재실행 | ② 재실행 중심 (배치 전체 재시작) |

## 1. 한 줄 정의

**마지막 한 개 남은 상품에 주문 두 건이 동시에 들어와도** 하나만 확정되고, 결제 callback이 두 번 와도 주문은 한 번만 확정된다.

## 2. 원리 — 왜 이 문제가 생기나

### 2-1. ⭐ Lost Update — 재고가 깨지는 정확한 메커니즘

가장 순진한 재고 차감 코드는 이렇다.

```java
int stock = 재고조회(상품);        // ① 읽기
if (stock >= 1) {                  // ② 판단
    재고갱신(상품, stock - 1);      // ③ 쓰기
}
```

혼자 실행하면 완벽하다. 두 명이 **동시에** 실행하면 이렇게 된다. (재고 1개 남음)

```
시각    요청 A                          요청 B                    DB의 재고
──────────────────────────────────────────────────────────────────────
t1     ① 재고 읽기 → 1                                              1
t2                                     ① 재고 읽기 → 1              1
t3     ② 1 >= 1 이니까 살 수 있다!                                   1
t4                                     ② 1 >= 1 이니까 살 수 있다!   1
t5     ③ 재고를 0으로 UPDATE                                        0
t6                                     ③ 재고를 0으로 UPDATE        0
──────────────────────────────────────────────────────────────────────
결과: 주문 2건이 확정됐는데 재고는 1개만 줄었다.  💀
      실제 물건은 1개인데 2명에게 팔았다.
```

**B가 t2에 읽은 값 "1"은 t5 시점에 이미 낡은 값**인데, B는 그걸 모른다. 그리고 t6에서 A가 쓴 결과를 **덮어쓴다.** A의 갱신이 사라졌다고 해서 이걸 **Lost Update(갱신 유실)** 라고 한다.

> ### 핵심
> 문제는 "읽기"도 "쓰기"도 아니다. **읽기와 쓰기 사이에 틈이 있다**는 것이다.
> 그 틈에 남이 끼어든다. 해법은 전부 **"이 틈을 없애는"** 방향이다.

### 2-2. 틈을 없애는 네 가지 방법

#### 방법 ① 비관적 락 (Pessimistic Lock)

**"내가 읽을 때부터 남이 못 건드리게 잠근다."**

```sql
SELECT 재고 FROM 상품 WHERE id = 1 FOR UPDATE;   -- ← 이 행을 잠근다
-- 다른 트랜잭션은 여기서 대기한다
UPDATE 상품 SET 재고 = 재고 - 1 WHERE id = 1;
COMMIT;                                          -- ← 잠금 해제
```

- **장점**: 확실하다. 이해하기 쉽다
- **단점**: 대기가 생긴다. 인기 상품이면 **모든 요청이 한 줄로 선다.** 트랜잭션이 길면 그만큼 다 기다린다
- **비관적인 이유**: "충돌이 날 것이다"라고 **비관적으로 가정**하고 미리 잠근다

#### 방법 ② 낙관적 락 (Optimistic Lock)

**"일단 진행하고, 쓸 때 남이 건드렸는지 확인한다."**

```sql
-- version 컬럼을 하나 둔다
SELECT 재고, version FROM 상품 WHERE id = 1;      -- 재고=1, version=5

UPDATE 상품 SET 재고 = 0, version = 6
WHERE id = 1 AND version = 5;                     -- ← 내가 읽은 version이 그대로일 때만
```

- 갱신된 행 수가 **1이면 성공**, **0이면 그 사이에 남이 바꿨다**는 뜻 → 재시도하거나 실패 처리
- **장점**: 잠그지 않으니 대기가 없다. 충돌이 드문 경우 훨씬 빠르다
- **단점**: 충돌이 잦으면 재시도가 폭증한다
- **낙관적인 이유**: "충돌은 잘 안 날 것이다"라고 낙관하고 진행한다

#### 방법 ③ ⭐ 조건부 UPDATE (이 시나리오의 선택)

**"읽지 않는다. 조건을 붙여서 한 방에 쓴다."**

```sql
UPDATE 재고 SET 수량 = 수량 - 1
WHERE 상품id = 1 AND 수량 >= 1;      -- ← 조건이 SQL 안에 있다
```

이게 왜 안전한가? **DB는 하나의 UPDATE 문을 실행하는 동안 그 행을 자동으로 잠근다.** 읽기(`수량 >= 1` 확인)와 쓰기(`수량 - 1`)가 **DB 안에서 하나의 원자적 연산**으로 일어난다. 사이에 틈이 없다.

```
시각    요청 A                              요청 B                     DB의 재고
─────────────────────────────────────────────────────────────────────────
t1     UPDATE ... WHERE 수량 >= 1
       → 행 잠금 → 1 >= 1 확인 → 0으로                                  0
       → 갱신된 행: 1건 ✅
t2                                         UPDATE ... WHERE 수량 >= 1
                                           → 0 >= 1 ? 아니오
                                           → 갱신된 행: 0건 ❌            0
─────────────────────────────────────────────────────────────────────────
결과: A만 성공. B는 품절.  ✅ 정확하다.
```

**애플리케이션은 "갱신된 행 수"만 보면 된다.** 1이면 내가 확보한 것, 0이면 품절.

```java
int affected = jdbc.update("UPDATE 재고 SET 수량=수량-1 WHERE 상품id=? AND 수량>=1", id);
if (affected == 0) throw new 품절();
```

- **장점**: 별도 락 관리도, 재시도 루프도, version 컬럼도 필요 없다. **가장 단순하고 가장 빠르다**
- **단점**: 복잡한 비즈니스 판단을 SQL 조건으로 표현하기 어려울 때가 있다

#### 방법 ④ UNIQUE 제약 — 최후의 방어선

위 셋은 전부 **애플리케이션이 올바르게 짜였을 때** 동작한다. 코드에 버그가 있거나 새 개발자가 다른 경로로 INSERT 하면 뚫린다.

`UNIQUE` 제약은 **DB 스키마 레벨**이라 어떤 경로로 와도 막힌다.

```sql
ALTER TABLE 주문 ADD CONSTRAINT uq_주문_멱등키 UNIQUE (멱등키);
-- 같은 멱등키로 두 번 INSERT 하면 두 번째는 DB가 거부한다
```

> **원칙**: 정합성의 마지막 방어선은 **애플리케이션이 아니라 DB 제약**에 둔다.
> 애플리케이션 로직은 우회될 수 있지만 DB 제약은 우회할 수 없다.

### 2-3. 왜 재고에 칸이 두 개인가 (`available` / `reserved`)

02의 Saga에서도 나온 개념인데, 여기서 더 자세히 본다.

**칸이 하나라면 이런 문제가 생긴다.**

```
결제 전에 재고를 그냥 뺀다:   수량 100 → 99

그런데 결제가 실패했다.
  → 얼마를 돌려놔야 하지?  "이 주문이 1개를 뺐다"를 어딘가에 따로 기억해야 한다
  → 그 기록이 유실되면 재고가 영원히 어긋난다
  → 그리고 이 99라는 숫자만 봐서는 "팔린 것"인지 "예약 중"인지 알 수 없다
```

**칸이 둘이면 상태 자체가 답을 갖는다.**

| 시점 | `available` | `reserved` | 의미 |
|---|---|---|---|
| 초기 | 100 | 0 | 100개 판매 가능 |
| 예약 후 | 99 | 1 | **99개 판매 가능, 1개는 결제 대기 중** |
| 확정 | 99 | 0 | 1개 판매 완료 (`reserved` 만 줄임) |
| 실패(보상) | 100 | 0 | 예약 취소 (`available` 로 되돌림) |

`reserved` 는 **"아직 확정 안 됐지만 남에게 팔면 안 되는 수량"** 이다.
별도 기억이 필요 없고, 재고 테이블만 봐도 언제든 정확한 상태를 알 수 있다.

### 2-4. 중복 결제 callback — ②번 축(재실행) 문제

결제사는 callback을 **여러 번 보낼 수 있다.** 이건 버그가 아니라 정상 동작이다. 이유가 이렇다.

```
결제사 → 내 서버: "결제 성공했어요" (callback)
결제사: 내 서버의 200 OK 응답을 못 받음 (네트워크 유실)
결제사: "전달 실패했나 보다" → 다시 보냄
결제사 → 내 서버: "결제 성공했어요" (같은 callback, 두 번째)
```

**결제사 입장에서는 옳은 행동이다.** callback이 유실되면 주문이 영원히 미확정으로 남으니까, 확실히 전달될 때까지 재시도하는 게 맞다. 02에서 본 **at-least-once** 가 여기서도 나온다.

그래서 **받는 쪽이 멱등해야 한다.**

```java
// payment_id 로 이미 처리했는지 확인
if (결제기록.존재하는가(payment_id)) {
    return 기존결과;          // 아무것도 바꾸지 않고 200 OK
}
// 처음 보는 payment_id 만 처리
주문확정(); 재고확정(); 결제기록저장(payment_id);
```

**핵심**: 두 번째 callback에도 **200 OK를 돌려줘야 한다.** 400이나 409를 주면 결제사는 "아직 전달 안 됐네" 하고 계속 재시도한다. *"이미 처리했음 = 성공"* 이다.

### 2-5. 예약 만료 — 아무도 실패시켜 주지 않는 실패

`RESERVATION_EXPIRED` 모드가 다루는 상황이다.

```
10:00  주문 생성, 재고 1개 예약  (available -1, reserved +1)
10:00  결제창으로 이동
10:01  사용자가 그냥 브라우저를 닫음
       → 결제 안 함
       → 실패 신호도 없음
       → 재고 1개가 영원히 reserved 에 묶임 💀
```

**02의 채팅 heartbeat와 똑같은 구조의 문제다.** "실패했다"는 신호가 오지 않는 실패. 그리고 해법도 같은 발상이다.

> **신호를 기다리지 말고, 시간을 기준으로 판단한다.**

```
예약 행에 만료 시각을 넣는다:   expires_at = now() + 10분
스케줄러가 주기적으로:          expires_at < now() 인 예약을 찾아 회수
                              → available += 수량, reserved -= 수량
```

이걸 안 하면 인기 상품이 **"재고는 있는데 아무도 못 사는"** 상태가 된다. 실무에서 티켓팅·한정판매에서 자주 나는 사고다.

## 3. 대안 표와 내 선택

**마지막 재고 경합을 막는 방법:**

| 방법 | 원리 | 장점 | 단점 | 이 시나리오 |
|---|---|---|---|---|
| 아무것도 안 함 | 읽고 판단하고 쓴다 | — | **Lost Update.** 초과 판매 | ✗ |
| 비관적 락 (`FOR UPDATE`) | 읽을 때부터 잠근다 | 확실하다 | 인기 상품에서 전부 한 줄로 대기 | △ |
| 낙관적 락 (version) | 쓸 때 변경 여부 확인 | 대기 없음 | 충돌이 잦으면 재시도 폭증 | △ |
| **조건부 UPDATE** | 조건을 SQL에 넣어 한 방에 | **가장 단순하고 빠르다** | 복잡한 조건 표현이 어려울 수 있다 | **✓** |
| UNIQUE 제약 | DB 스키마가 막는다 | 우회 불가 | 단독으로는 수량 제어 불가 | **✓ (병행)** |

**조건부 UPDATE를 고른 이유**: 재고 차감의 조건(`수량 >= 1`)이 SQL로 완벽히 표현되고, 별도 락 관리나 재시도 루프가 필요 없다. 가장 적은 코드로 가장 정확하다. 여기에 주문 멱등키 `UNIQUE` 를 병행해서 애플리케이션 버그까지 막는다.

## 4. 진위 한 줄

**⚠️ 이건 실행 데모가 아니라 설계 정리다.**

화면에서 실행 버튼을 누르면 단계가 흐르지만, **실제로 동시 요청이 발생하지 않는다.** `DomainScenarioEngine.order()` 가 모드별로 미리 적힌 step 배열을 그대로 돌려주고, DB에는 "이 대본을 재생했다"는 실행 기록만 남는다.

```java
case "LAST_STOCK_RACE" -> result("ONE_CONFIRMED", "마지막 재고는 한 주문만 확보", 1, 0, key,
        step("TWO_ORDERS_CREATED", "Order", "WARNING", "마지막 재고에 주문 두 건이 도착했다."),
        step("STOCK_LOCKED", "PostgreSQL", "SUCCESS", "재고 갱신 경계를 직렬화했다."),
        ...
```

**그래서 면접에서는 이렇게 말한다.**

> "이 화면은 실행 데모가 아니라 설계 정리입니다. 실무에서 마지막 재고 경합과 중복 결제 callback을 겪었고, 그때 고려한 축이 다섯 개였습니다. 정상 흐름, 마지막 재고 경합, 중복 callback, 확정 실패 시 보상, 예약 만료. 화면은 그 다섯을 눈으로 비교하려고 만들었습니다."

**이게 오히려 강한 답변인 이유**: 면접관이 실제로 궁금한 건 "화면에서 돌아가느냐"가 아니라 **"마지막 재고 경합을 어떻게 막을 줄 아느냐"** 다. 그건 2번 칸에 전부 있다.

**다만 화면에는 고쳐야 할 게 하나 있다** — `p95Ms` 같은 측정값 형태의 숫자를 대본이 주장하면 안 된다. (`README.md` 의 2단계 작업)

## 5. 30초 구두 답변

> 마지막 재고 한 개에 주문 두 건이 동시에 들어오면, 순진하게 짜면 둘 다 "재고 1개 있음"을 읽고 둘 다 확정합니다. 읽기와 쓰기 사이에 틈이 있어서 그 사이에 남이 끼어드는 건데, Lost Update라고 부릅니다.
>
> 해법은 그 틈을 없애는 방향인데 네 가지가 있습니다. 비관적 락은 확실하지만 인기 상품에서 전부 한 줄로 대기합니다. 낙관적 락은 대기가 없는 대신 충돌이 잦으면 재시도가 폭증하고요. 저는 조건부 UPDATE를 택했습니다. `WHERE 수량 >= 1` 조건을 SQL 안에 넣으면 DB가 그 행을 잠근 채로 확인과 갱신을 한 번에 하니까 틈 자체가 없어집니다. 애플리케이션은 갱신된 행 수가 1인지 0인지만 보면 되고요.
>
> 그리고 결제 callback은 중복으로 옵니다. 결제사가 응답을 못 받으면 재시도하는 게 정상 동작이라서요. 그래서 payment_id로 이미 처리했는지 확인하고, 두 번째부터는 아무것도 바꾸지 않고 200 OK만 돌려줍니다. 400을 주면 결제사가 계속 재시도하거든요.

## 6. 꼬리질문과 답

**Q1. 비관적 락과 낙관적 락 중 뭘 쓰시겠어요?**

**충돌 빈도로 결정합니다.**

일반 상품처럼 동시에 같은 행을 건드릴 일이 드물면 낙관적 락이 낫습니다. 잠금 대기가 없어서 처리량이 훨씬 높고, 어쩌다 충돌하면 한 번 재시도하면 됩니다.

반대로 선착순 한정판처럼 **모두가 같은 행 하나를 노리면** 낙관적 락은 최악입니다. 대부분이 충돌해서 재시도가 폭증하고, 결국 아무도 성공 못 하는 라이브록 비슷한 상황이 됩니다. 이럴 땐 비관적 락으로 줄을 세우거나, 아예 조건부 UPDATE로 한 방에 끝내는 게 낫습니다.

지금 설계는 조건부 UPDATE입니다. **락 대기도 없고 재시도도 없어서** 두 방식의 단점을 다 피합니다.

**Q2. 재고를 Redis에 두면 더 빠르지 않나요?**

빠릅니다. 실제로 대규모 선착순에서는 그렇게 합니다. 다만 **정합성의 최종 원본을 어디에 둘지**를 정해야 합니다.

Redis가 원본이면 Redis가 죽었을 때 재고가 날아갑니다. 그래서 보통은 **Redis에서 수량을 원자적으로 차감해 진입을 통제하고(게이트), 실제 원장은 DB에 기록**합니다. 두 곳이 어긋날 수 있으니 대조(reconciliation) 절차가 필요하고요.

트래픽이 DB로 감당되는 규모면 굳이 두 곳을 관리할 이유가 없다고 봐서, 여기서는 DB 단일 원본으로 설계했습니다.

**Q3. 중복 callback에 왜 409가 아니라 200을 주나요?**

**결제사 입장에서 409는 "전달 실패"로 읽히기 때문입니다.** 그러면 계속 재시도합니다. 무한 재시도로 이어지고요.

의미론적으로도 200이 맞습니다. callback의 목적은 "이 결제 결과를 너에게 알린다"인데, **이미 알고 있으면 그 목적은 달성된 상태**입니다. 실패가 아닙니다. *"이미 처리했음 = 성공"* 으로 취급하는 게 멱등 API의 원칙입니다.

여담으로 이 프로젝트에는 **게시판과 블로그가 같은 상황에 다른 코드를 쓰는 불일치**가 있습니다. 익명 삭제 암호 오류가 게시판은 409, 블로그는 400입니다. 게시판을 고치면 기존 UI가 깨져서 미뤄 둔 상태고요.

**Q4. 예약 만료 스케줄러가 여러 대에서 동시에 돌면요?**

같은 예약을 두 번 회수해서 **재고가 부풀 수 있습니다.** 막는 방법이 셋입니다.

첫째, 회수도 조건부 UPDATE로 합니다. `WHERE status='RESERVED' AND expires_at < now()` 로 갱신하고 **갱신된 행 수가 1일 때만** 재고를 되돌리면, 두 번째 스케줄러는 0건을 받아 아무것도 안 합니다. 가장 깔끔합니다.

둘째, `SELECT ... FOR UPDATE SKIP LOCKED` 로 서로 다른 행을 가져갑니다.

셋째, 스케줄러를 리더 한 대에서만 돌립니다.

**첫 번째가 제일 좋습니다.** 다른 방어 장치 없이 SQL 한 문장으로 끝나거든요.

## 7. 모르면 인정할 선

**여기까지는 자신 있게 답한다**
- Lost Update가 발생하는 정확한 시간순 메커니즘

## 2. 원리 — 왜 이 문제가 생기나

### 2-1. ⭐ 잔액을 어떻게 저장할 것인가 — 이게 첫 번째 설계 결정이다

가장 순진한 방법은 컬럼 하나다.

```sql
CREATE TABLE 상품권 (
    id       varchar PRIMARY KEY,
    잔액      int         -- ← 이 숫자 하나가 진실
);
```

동작은 한다. 그런데 실무에서 이런 질문이 반드시 들어온다.

- "이 상품권이 왜 4만 원이죠? 5만 원짜리였는데요"
- "언제 1만 원이 빠졌나요?"
- "그 거래 취소했다는데 왜 잔액이 그대로죠?"

**컬럼 하나로는 답할 수 없다.** 현재 값만 있고 **과정이 없기** 때문이다.

그래서 금융·정산 도메인은 **원장(ledger)** 방식을 쓴다.

```sql
CREATE TABLE 상품권_원장 (
    id           bigserial,
    상품권id      varchar,
    변동액        int,        -- +50000, -10000, +10000 ...
    사유          varchar,    -- ISSUED, USED, CANCELLED
    멱등키        varchar,    -- ← 중복 방지의 핵심
    생성시각      timestamptz
);
```

| | 잔액 컬럼 방식 | **원장 방식** |
|---|---|---|
| 저장하는 것 | **현재 상태** | **변동 이력** |
| 잔액 조회 | 컬럼 읽기 (빠름) | `SUM(변동액)` 또는 캐시 컬럼 |
| "왜 이 값인가?" | **답할 수 없다** | 이력을 그대로 보여주면 된다 |
| 취소 | 잔액을 되돌린다 (덮어씀) | **+10000 행을 추가**한다 (흔적 보존) |
| 감사·정산 | 불가능 | 가능 |

**02의 Saga에서 본 "롤백 vs 보상"과 정확히 같은 사상이다.** 지우지 않고 반대 기록을 추가한다.

```
[취소를 원장으로 표현하면]
  +50,000  ISSUED      (발행)
  -10,000  USED        (사용)
  +10,000  CANCELLED   (사용 취소)   ← 새 행. -10,000 행은 그대로 남는다
  ──────────────────────────────
   50,000  현재 잔액
```

**현실적인 절충**: 원장을 원본으로 두되, 조회 성능을 위해 **잔액 캐시 컬럼**을 함께 둔다. 둘은 같은 트랜잭션에서 갱신하고, 주기적으로 `SUM(변동액)` 과 대조해서 어긋나면 알람을 띄운다.

### 2-2. 다섯 모드가 각각 다루는 문제

| 모드 | 상황 | 축 | 핵심 방어 |
|---|---|---|---|
| `NORMAL` | 정상 사용 | — | 기준선 |
| `DUPLICATE_RETRY` | 응답 유실로 클라이언트가 같은 요청 재전송 | ② 재실행 | **멱등키** |
| `CONCURRENT_USE` | 잔액 1만 원에 1만 원 사용 요청 2건 동시 | ① 동시성 | **조건부 UPDATE / 직렬화** |
| `TIMEOUT_RETRY` | 서버는 커밋했는데 응답이 유실 | ② 재실행 | **멱등키 + 결과 복구** |
| `CANCEL` | 사용 취소 | — | **보상 원장 추가** |

### 2-3. ⭐ 멱등키가 실제로 어떻게 동작하나

02에서 "엘리베이터 버튼"으로 설명했는데, 여기서는 **DB 레벨에서 어떻게 구현되는지**를 본다.

```sql
-- 원장 테이블에 UNIQUE 제약을 건다
ALTER TABLE 상품권_원장 ADD CONSTRAINT uq_멱등키 UNIQUE (멱등키);
```

이제 흐름은 이렇다.

```java
try {
    원장.insert(상품권id, -10000, "USED", 멱등키);   // ① 시도
    잔액갱신(상품권id, -10000);
    return 성공;
} catch (DuplicateKeyException e) {                  // ② DB가 막았다
    return 원장.조회(멱등키).결과;                    // ③ 기존 결과를 그대로 반환
}
```

**"먼저 조회해서 있으면 건너뛰기"가 아니라 "일단 넣고 걸리면 기존 것 반환"인 이유가 중요하다.**

```
[먼저 조회하는 방식 — 위험하다]
  t1  A: 멱등키 조회 → 없음
  t2  B: 멱등키 조회 → 없음        ← 둘 다 "없다"고 봤다
  t3  A: INSERT
  t4  B: INSERT                    ← 중복! 💀
  = 2-1의 Lost Update와 똑같은 check-then-act 문제

[일단 넣는 방식 — 안전하다]
  t1  A: INSERT → 성공
  t2  B: INSERT → DB가 UNIQUE 위반으로 거부 ✅
  = 확인과 삽입이 DB 안에서 원자적으로 일어난다
```

> ### 이 패턴의 이름
> **"Insert-or-Get"** 또는 **"낙관적 삽입"**.
> **확인을 애플리케이션이 하지 말고 DB 제약이 하게 한다.**
> 조건부 UPDATE가 갱신에서 틈을 없앤 것처럼, UNIQUE 제약은 삽입에서 틈을 없앤다.

### 2-4. `TIMEOUT_RETRY` — 02와 이어지는 지점

```
클라이언트 → 서버: "1만 원 사용" (멱등키: gc-abc-001)
서버: 원장 기록, 커밋 완료 ✅
서버 → 클라이언트: 응답 전송
⚡ 응답 유실
클라이언트: 타임아웃. "실패했나?" → 같은 멱등키로 재전송
서버: UNIQUE 위반 → 기존 원장 조회 → "이미 완료됨, 잔액 4만 원" 반환 ✅
```

**02의 제휴 API 편에서 "타임아웃은 재시도하면 안 된다"고 했는데, 여기서는 재시도가 안전하다.** 차이가 뭘까?

> **내가 멱등키를 지원하는 서버이기 때문이다.**
> 02에서 재시도가 위험했던 건 **외부 제휴사가 멱등을 보장한다는 확신이 없어서**였다.
> 내 서버라면 내가 보장할 수 있다. **그래서 멱등성은 "재시도를 허락하는 권한"** 이다.

이 대비를 면접에서 말할 수 있으면 좋다. 같은 "타임아웃 재시도"인데 한쪽은 금지, 한쪽은 권장인 이유를 설명하는 것이니까.

### 2-5. `CONCURRENT_USE` — 잔액 경합

잔액 1만 원에 1만 원 사용 요청 두 건이 동시에 들어온 상황. **주문 재고와 완전히 같은 구조**다.

```sql
UPDATE 상품권 SET 잔액 = 잔액 - 10000
WHERE id = ? AND 잔액 >= 10000;      -- 조건부 UPDATE

-- 갱신 1건 → 사용 성공
-- 갱신 0건 → 잔액 부족으로 거절
```

**"잔액이 음수가 되면 안 된다"는 규칙을 SQL 조건으로 표현한 것**이다. 애플리케이션에서 `if (잔액 >= 금액)` 으로 검사하면 틈이 생긴다.

여기에 **DB 제약을 하나 더 두면 완벽해진다.**

```sql
ALTER TABLE 상품권 ADD CONSTRAINT chk_잔액 CHECK (잔액 >= 0);
```

어떤 코드 경로로 와도 잔액이 음수가 되는 순간 DB가 거부한다. **애플리케이션 로직이 뚫려도 데이터는 안 깨진다.**

## 3. 대안 표와 내 선택

| 접근 | 대가 | 채택 |
|---|---|---|
| 잔액 컬럼만 | "왜 이 값인가"에 답할 수 없다. 감사·정산 불가 | ✗ |
| **원장 + 잔액 캐시 컬럼** | 두 곳을 관리해야 하고 대조 절차가 필요 | **✓** |
| 원장만 (매번 `SUM`) | 이력이 쌓이면 조회가 느려진다 | △ |

| 중복 방지 | 대가 | 채택 |
|---|---|---|
| 먼저 조회 후 없으면 삽입 | **check-then-act race.** 동시 요청에서 뚫린다 | ✗ |
| **UNIQUE 제약 + Insert-or-Get** | 예외 처리 코드가 필요 | **✓** |
| 분산 락 | 락 관리 부담, 실패 모드 증가 | ✗ |

## 4. 진위 한 줄

**⚠️ 이건 실행 데모가 아니라 설계 정리다.**

`DomainScenarioEngine.giftCard()` 가 모드별 고정 step 배열을 반환한다. 실제 원장 테이블도, 동시 요청도 없다. `beforeAmount` / `afterAmount` (50,000 → 40,000 같은 값)도 코드에 적힌 상수다.

**면접에서는 이렇게 말한다.**

> "실무에서 상품권 중복 사용 이슈를 겪었고, 해결할 때 고려한 축이 다섯 개였습니다. 정상 사용, 중복 재전송, 잔액 경합, 응답 유실 후 복구, 사용 취소. 화면은 그 다섯 축을 눈으로 비교하려고 만든 설계 정리입니다. 실제 원장 테이블을 만들어 돌리진 않았습니다."

## 5. 30초 구두 답변

> 상품권 잔액을 컬럼 하나로 들면 "왜 4만 원이죠?"라는 질문에 답할 수 없습니다. 현재 값만 있고 과정이 없어서요. 그래서 원장 방식으로 설계했습니다. 변동액을 행으로 쌓고, 취소도 기존 행을 지우는 게 아니라 반대 부호 행을 추가합니다. 그러면 감사랑 CS 대응이 가능해집니다.
>
> 중복 방지는 멱등키에 UNIQUE 제약을 걸고, "먼저 조회해서 없으면 삽입"이 아니라 "일단 삽입하고 걸리면 기존 결과 반환" 방식으로 갑니다. 먼저 조회하면 두 요청이 동시에 "없다"를 보는 순간이 생겨서 뚫립니다. DB 제약이 확인을 대신하게 하는 거죠.
>
> 잔액 경합은 `WHERE 잔액 >= 금액` 조건부 UPDATE로 막고, 추가로 `CHECK (잔액 >= 0)` 제약을 둬서 어떤 코드 경로로 와도 음수가 안 되게 합니다.

## 6. 꼬리질문과 답

**Q1. 원장이 쌓이면 잔액 조회가 느려지지 않나요?**

느려집니다. 그래서 **잔액 캐시 컬럼을 함께 둡니다.** 원장 삽입과 캐시 갱신을 같은 트랜잭션에서 하고, 조회는 캐시만 읽습니다.

문제는 둘이 어긋날 수 있다는 건데, **주기적으로 `SUM(변동액)` 과 캐시를 대조해서 불일치를 알람으로 띄웁니다.** 정산 시스템에서 흔히 쓰는 방식입니다. 그리고 어긋났을 때 **원장이 원본**이라는 걸 명확히 해둡니다. 캐시를 원장에 맞추지, 그 반대로 하면 안 됩니다.

**Q2. 02에서는 타임아웃에 재시도하면 안 된다고 하셨는데, 여기선 재시도하네요?**

**멱등을 누가 보장하느냐가 다릅니다.**

02는 **외부 제휴사**를 부르는 상황이었습니다. 제 통제 밖이라 그쪽이 멱등키를 제대로 처리한다는 확신이 없었고, 그래서 재시도 대신 callback으로 확정하는 쪽을 택했습니다.

여기는 **제 서버**입니다. 제가 멱등키에 UNIQUE 제약을 걸어서 보장할 수 있으니 재시도가 안전합니다.

**멱등성은 재시도를 허락하는 권한**이라고 생각합니다. 보장이 있으면 재시도해도 되고, 없으면 하면 안 됩니다.

**Q3. 멱등키는 누가 만드나요?**

**클라이언트가 만들어야 합니다.** 서버가 만들면 의미가 없습니다. 재전송할 때 서버가 또 새 키를 만들어 버리면 다른 요청으로 취급되니까요.

보통 클라이언트가 UUID를 생성해서 첫 요청과 모든 재시도에 같은 값을 씁니다. 화면 진입 시점에 만들어 두면 "결제 버튼 두 번 클릭"도 같은 키가 돼서 자동으로 막힙니다.

키의 유효 기간도 정해야 합니다. 영원히 보관하면 테이블이 무한히 커지고, 너무 짧으면 늦은 재시도를 못 막습니다. 보통 24시간~7일 정도로 잡고 그 뒤엔 정리합니다.

**Q4. 취소를 두 번 하면요?**

**취소에도 멱등키가 필요합니다.** 안 그러면 +10,000이 두 번 들어가서 잔액이 부풀어 오릅니다.

그리고 상태 검증도 필요합니다. 이미 `CANCELLED` 인 사용 건은 다시 취소할 수 없게 막아야 합니다. 조건부 UPDATE로 `WHERE 상태 = 'USED'` 를 붙이고 갱신 행 수가 1일 때만 보상 원장을 넣으면 두 가지가 한 번에 해결됩니다.

## 7. 모르면 인정할 선

**여기까지는 자신 있게 답한다**
- 원장 방식과 잔액 컬럼 방식의 차이, 왜 금융 도메인이 원장을 쓰는지
- 취소를 보상 행으로 표현하는 이유 (02의 Saga와 같은 사상)
- **Insert-or-Get 패턴과 "먼저 조회"가 왜 위험한지**
- 멱등성이 "재시도를 허락하는 권한"이라는 관점 (02와의 대비)
- `CHECK` 제약을 마지막 방어선으로 두는 이유

**여기부터는 "안 해봤습니다"라고 말한다**
- 원장 테이블이 수억 행일 때의 파티셔닝과 아카이빙
- 잔액 캐시와 원장 대조 배치의 실제 운영
- 멱등키 만료 정책의 정량적 근거
- 다중 통화·환율이 섞인 원장 설계

> ### 자가 점검
> **"왜 잔액 컬럼이 아니라 원장인가"** 를 CS 문의 상황으로 설명할 수 있는가.
> **"먼저 조회하면 왜 뚫리는가"** 를 시간표로 그릴 수 있는가.
> **"02에서는 재시도 금지, 여기선 권장"** 의 차이를 답할 수 있는가.

# 3. 선착순 쿠폰 발급 경합

**시나리오 id**: `coupon-race-condition`
**화면**: `/scenarios/coupon-race-condition`
**모드**: `BASELINE` / `CONDITIONAL_UPDATE` / `REDIS_LUA` / `DUPLICATE_REQUEST`

## 1. 한 줄 정의

**쿠폰 100장에 요청 120개가 동시에 도착해도** 정확히 100장만 발급된다.

## 2. 원리 — 왜 이 문제가 생기나

### 2-1. 이건 재고 경합의 극단 버전이다

1편의 마지막 재고 문제와 **구조는 같지만 규모가 다르다.**

| | 마지막 재고 | **선착순 쿠폰** |
|---|---|---|
| 경합하는 요청 수 | 2~3개 | **수백~수만 개** |
| 대상 행 | 상품마다 분산 | **단 하나의 행에 전부 몰린다** |
| 낙관적 락 | 쓸 만하다 | **거의 전부 충돌.** 재시도 폭증 |
| 비관적 락 | 견딜 만하다 | **전부 한 줄로 대기.** 응답 지연 폭발 |

**"모두가 같은 행 하나를 노린다"** — 이게 선착순의 본질이고, 그래서 일반적인 락 전략이 잘 안 통한다.

`BASELINE` 모드가 보여주는 게 이 실패다.

```
step("STOCK_READ",     "동시 요청이 모두 잔여 수량 100을 읽었다.")      ← 전부 100을 봤다
step("ISSUE_INSERTED", "각 요청이 독립적으로 발급을 기록했다.")
step("LIMIT_EXCEEDED", "한정 수량보다 20건 많이 발급됐다.")            ← 120장 발급됨
```

**120개 요청이 전부 "아직 100장 남았네"를 읽었다.** 1편의 Lost Update가 120배로 벌어진 것이다.

### 2-2. 해법 ① 조건부 UPDATE — 가장 단순한 정답

```sql
UPDATE 쿠폰재고 SET 잔여 = 잔여 - 1
WHERE 캠페인id = ? AND 잔여 > 0;
```

- 갱신 1건 → 발급 성공
- 갱신 0건 → 품절

**정확히 100번만 1건이 갱신되고, 나머지 20번은 0건이 된다.** DB가 행을 잠근 채 확인과 갱신을 한 번에 하니까 초과가 원천적으로 불가능하다.

**대가**: 120개 요청이 전부 **같은 행에 UPDATE를 시도**한다. DB 내부에서 행 잠금 대기가 생긴다. 100개면 괜찮지만 10만 개면 DB가 버거워진다.

### 2-3. ⭐ 해법 ② Redis Lua — 규모가 커지면

**왜 Redis인가?** DB보다 훨씬 빠르고, 무엇보다 **DB를 보호**할 수 있다. 10만 요청이 DB를 때리는 대신 Redis가 먼저 걸러서 **100개만 DB로 보낸다.**

그런데 여기서 02의 채팅 편과 똑같은 함정이 있다.

```java
// ❌ 이렇게 하면 안 된다
Long 잔여 = redis.get("coupon:remaining");   // ① 읽기
if (잔여 > 0) {                               // ② 판단
    redis.decr("coupon:remaining");           // ③ 쓰기
}
```

**Redis 명령 하나하나는 원자적이지만, 세 명령을 묶은 건 원자적이지 않다.** ①과 ③ 사이에 다른 클라이언트가 끼어든다. 02 채팅의 `synchronized` 문제와 정확히 같은 구조다.

**해법은 셋을 하나의 Lua 스크립트로 묶는 것이다.**

```lua
local remaining = tonumber(redis.call('GET', KEYS[1]))
if remaining and remaining > 0 then
    redis.call('DECR', KEYS[1])
    return 1        -- 발급 성공
else
    return 0        -- 품절
end
```

**왜 이게 원자적인가?**

> **Redis는 명령을 단일 스레드로 처리하고, Lua 스크립트는 그 전체가 하나의 명령처럼 실행된다.**
> 스크립트가 도는 동안 다른 클라이언트의 명령은 **대기**한다.
> 그래서 읽기·판단·쓰기 사이에 틈이 없다.

**더 단순한 방법도 있다.** `DECR` 자체가 원자적이고 결과를 돌려준다는 점을 이용한다.

```
new = DECR coupon:remaining
if new >= 0  → 발급 성공
if new <  0  → 품절 (INCR로 되돌린다)
```

100장에서 120번 `DECR` 하면 결과가 99, 98, ..., 0, -1, ..., -20이 된다. **0 이상인 100개만 성공**시키면 정확하다. Lua 없이도 되지만, 음수가 된 값을 되돌리는 보정이 필요해서 로직이 지저분해진다.

### 2-4. `DUPLICATE_REQUEST` — 동시성이 아니라 공정성 문제

지금까지는 "100장을 정확히 100장만"이었다. 그런데 이런 상황이 있다.

```
120개 요청 중 28개가 사실 같은 사용자의 중복 클릭이었다
→ 수량은 정확히 100장 나갔는데
→ 어떤 사용자는 3장 받고, 다른 사람은 못 받았다
```

**수량은 맞는데 불공정하다.** 선착순 이벤트에서 이건 심각한 문제다.

해법은 **사용자별 멱등**이다.

```
발급 전에 확인:  이 campaign + 이 user 조합이 이미 있나?
  → 있으면: 새로 발급하지 않고 기존 쿠폰을 반환
  → 없으면: 발급
```

구현은 2편의 Insert-or-Get과 똑같다.

```sql
ALTER TABLE 쿠폰발급 ADD CONSTRAINT uq_캠페인_사용자
    UNIQUE (캠페인id, 사용자id);
```

**"먼저 조회"가 아니라 "UNIQUE 제약"이어야 하는 이유도 똑같다.** 같은 사용자의 두 요청이 동시에 오면 둘 다 "없다"를 보기 때문이다.

> ### 정리하면 이 시나리오에는 **두 종류의 정확성**이 있다
> 1. **총량 정확성** — 100장을 넘지 않는다 → 조건부 UPDATE / Redis 원자 연산
> 2. **1인 1매 정확성** — 한 사람이 여러 장 받지 않는다 → UNIQUE (캠페인, 사용자)
>
> **둘은 다른 방어다.** 하나만 하면 반드시 구멍이 생긴다.

## 3. 대안 표와 내 선택

| 접근 | 총량 정확성 | 처리량 | DB 부담 | 복잡도 |
|---|---|---|---|---|
| 읽고 판단하고 쓰기 | ❌ **초과 발급** | 높음 | 낮음 | 낮음 |
| 비관적 락 | ✅ | **낮음** (전부 대기) | 높음 | 중간 |
| 낙관적 락 | ✅ | **매우 낮음** (재시도 폭증) | 높음 | 중간 |
| **조건부 UPDATE** | ✅ | 중간 | 중간 | **낮음** |
| **Redis Lua** | ✅ | **매우 높음** | **낮음** (게이트가 막아줌) | 중간 |

**선택 기준은 규모다.**

- **수백~수천 요청**: 조건부 UPDATE. 인프라가 하나 줄고 원본이 하나다
- **수만 이상**: Redis Lua로 게이트를 세우고 통과한 것만 DB에 기록

**두 번째를 택하면 새 문제가 생긴다** — Redis와 DB가 어긋날 수 있다. 그래서 발급 후 **대조(reconciliation)** 절차가 필요하다. 사이트 화면의 `DB_RECONCILED` 스텝이 그걸 가리킨다.

## 4. 진위 한 줄

**⚠️ 이건 실행 데모가 아니라 설계 정리다.**

`OperationalTroubleshootingEngine.coupon()` 이 모드별 고정 step 배열을 반환한다. **실제로 120개 동시 요청을 쏘지 않는다.** 화면의 `p95Ms` 값(780ms, 210ms, 95ms)도 전부 코드에 적힌 상수다.

**다만 이 편은 실제 구현으로 승격할 후보 3편 중 하나다.** (`README.md` 3단계) 이유는:

- 스레드풀로 동시 요청 120개를 쏘면 **진짜 숫자가 나온다** — "100장에 120요청 → 정확히 100"이 실측이 된다
- 면접 빈출 주제라 실측값의 가치가 크다

## 5. 30초 구두 답변

> 선착순은 마지막 재고 경합의 극단 버전입니다. 차이는 모두가 같은 행 하나를 노린다는 거고요. 그래서 일반적인 락 전략이 잘 안 통합니다. 낙관적 락은 거의 전부 충돌해서 재시도가 폭증하고, 비관적 락은 전부 한 줄로 대기해서 응답이 무너집니다.
>
> 수백 건 규모면 조건부 UPDATE가 답입니다. `WHERE 잔여 > 0` 을 걸고 갱신된 행 수가 1일 때만 발급하면 초과가 원천적으로 불가능합니다. 수만 건이 넘어가면 Redis Lua로 게이트를 세웁니다. 읽고 판단하고 쓰는 걸 하나의 Lua 스크립트로 묶으면 Redis가 단일 스레드로 원자 실행하니까 틈이 없고, DB에는 통과한 100건만 갑니다.
>
> 그리고 총량만 맞추면 부족합니다. 한 사람이 중복 클릭으로 여러 장 받으면 수량은 맞는데 불공정하거든요. 그래서 캠페인과 사용자 조합에 UNIQUE 제약을 걸어서 1인 1매를 따로 보장합니다. 총량 정확성과 1인 1매 정확성은 다른 방어입니다.

## 6. 꼬리질문과 답

**Q1. Redis Lua가 원자적인 이유가 뭔가요?**

**Redis가 명령을 단일 스레드로 처리하기 때문입니다.** Lua 스크립트는 그 전체가 하나의 명령처럼 취급돼서, 스크립트가 도는 동안 다른 클라이언트의 명령은 큐에서 대기합니다. 그래서 읽기·판단·쓰기 사이에 다른 요청이 끼어들 수 없습니다.

주의할 점은 **스크립트를 짧게 유지해야 한다**는 겁니다. 단일 스레드라 스크립트가 느리면 Redis 전체가 그동안 멈춥니다.

**Q2. Redis가 죽으면 발급 수량이 깨지지 않나요?**

깨질 수 있습니다. 그래서 **Redis를 게이트로만 쓰고 원본은 DB에 둡니다.**

Redis가 죽으면 두 가지 선택이 있습니다. **이벤트를 중단**하거나(안전), **DB 조건부 UPDATE로 폴백**하거나(가용성). 어느 쪽이든 사전에 정해 둬야 하고, 저는 선착순 이벤트라면 중단이 낫다고 봅니다. 초과 발급은 되돌리기가 훨씬 어렵거든요.

그리고 발급이 끝나면 **Redis 카운터와 DB 발급 건수를 대조**해야 합니다. 어긋나면 알람을 띄우고요.

**Q3. `DECR` 만 써도 되지 않나요? Lua까지 필요한가요?**

`DECR` 만으로도 됩니다. `DECR` 자체가 원자적이고 결과를 돌려주니까, 결과가 0 이상인 요청만 성공시키면 정확히 100건입니다.

다만 **음수가 된 만큼 `INCR` 로 되돌리는 보정**이 필요하고, 그 보정 사이에 또 다른 요청이 끼어들면 값이 잠시 이상해 보입니다. 최종 결과는 맞지만 모니터링 값이 튀죠.

Lua는 **"수량이 0보다 클 때만 감소"** 라는 의도를 그대로 표현할 수 있어서 보정이 필요 없습니다. 그리고 나중에 조건이 복잡해질 때(사용자별 한도, 시간대 제한 등) 확장하기가 쉽습니다.

**Q4. 대기열 방식은 어떤가요?**

트래픽이 훨씬 클 때 쓰는 방법입니다. 요청을 Kafka나 Redis 큐에 넣고 **순서대로 천천히 처리**합니다.

**장점**: DB와 Redis가 순간 부하를 안 받습니다. 요청은 전부 접수되고 결과는 나중에 알려줍니다.
**단점**: 사용자가 즉시 결과를 못 받습니다. "발급 중입니다" 화면과 결과 조회·푸시가 필요해서 UX가 복잡해집니다.

**선착순은 즉시성이 경험의 핵심**이라 저는 게이트 방식이 맞다고 봤습니다. 대기열은 티켓팅처럼 애초에 대기가 자연스러운 도메인에 어울립니다.

## 7. 모르면 인정할 선

**여기까지는 자신 있게 답한다**
- 선착순이 왜 일반 재고 경합과 다른지 (같은 행에 전부 몰린다)
- 낙관적/비관적 락이 왜 여기서 안 통하는지
- 조건부 UPDATE와 Redis Lua의 원리, 규모에 따른 선택 기준
- **Lua가 원자적인 이유 (Redis 단일 스레드)**
- **총량 정확성과 1인 1매 정확성이 다른 방어라는 것**
- Redis를 게이트로 쓸 때 원본을 DB에 두는 이유

**여기부터는 "안 해봤습니다"라고 말한다**
- 실제 부하 테스트로 측정한 처리량 (현재 화면 숫자는 상수다)
- Redis Cluster에서 Lua 스크립트의 키 슬롯 제약
- 대기열 방식의 실제 구현과 UX 설계
- Redis-DB 대조 배치의 운영

> ### 자가 점검
> **"선착순이 왜 낙관적 락에 최악인가"** 를 답할 수 있는가.
> **"Lua가 왜 원자적인가"** 를 Redis 단일 스레드로 설명할 수 있는가.
> **"총량은 맞는데 불공정한 상황"** 을 예로 들 수 있는가.

# 4. 정산 배치 재실행과 부분 복구

**시나리오 id**: `settlement-batch-retry`
**화면**: `/scenarios/settlement-batch-retry`
**모드**: `BASELINE_DUPLICATE` / `CHECKPOINT_RESUME` / `IDEMPOTENT_UPSERT` / `PARTIAL_RETRY`

## 1. 한 줄 정의

정산 배치가 **중간에 죽었을 때, 처음부터 다시 돌려도 중복 정산이 나지 않게** 한다.

## 2. 원리 — 왜 이 문제가 생기나

### 2-1. 배치가 온라인 처리와 다른 점

| | 온라인 요청 | **배치** |
|---|---|---|
| 처리 단위 | 1건 | **수만~수백만 건** |
| 실행 시간 | 밀리초 | **분~시간** |
| 실패하면 | 그 요청만 실패 | **중간까지 처리된 상태로 멈춘다** |
| 재시도 | 그냥 다시 요청 | **"어디서부터?"가 문제** |

**배치의 핵심 난점은 "부분 성공"이다.** 온라인 요청은 성공 아니면 실패지만, 배치는 **"1만 건 중 7,500건까지 성공하고 죽은 상태"** 가 존재한다.

`BASELINE_DUPLICATE` 모드가 정확히 이걸 보여준다.

```
step("BATCH_STARTED",   "정산일 전체 대상을 처음부터 조회했다.")
step("PROCESS_CRASHED", "7,500건 처리 뒤 process가 종료됐다.")     ← 부분 성공
step("FULL_RESTARTED",  "동일 날짜 배치를 전체 재실행했다.")        ← 처음부터 다시
step("DUPLICATES_FOUND","250건이 중복 정산됐다.")                  ← 💀
```

**"전체를 트랜잭션으로 묶으면 되지 않나?"**

안 된다. 이유가 셋이다.

1. **1만 건을 한 트랜잭션에 담으면** 락이 오래 유지되고 다른 작업이 전부 막힌다
2. **트랜잭션 로그(WAL)가 폭증**한다. 롤백 비용도 그만큼 크다
3. **한 건 실패로 1만 건을 전부 롤백**하는 건 낭비다. 9,999건은 멀쩡한데

그래서 배치는 **작은 단위(청크)로 나눠서 커밋**한다. 그 순간 "부분 성공"이 필연이 된다.

### 2-2. 해법 ① 체크포인트 — "어디까지 했는지" 기억한다

```
배치 진행 중 주기적으로 저장:
  마지막_성공_커서 = 7500

재시작하면:
  1. 체크포인트를 읽는다 → 7500
  2. 7501번부터 처리한다
  3. 2,500건만 하면 끝
```

`CHECKPOINT_RESUME` 모드가 이걸 보여준다 — 처리 시간이 절반 이하로 줄어든다(대본 기준 3,800ms → 1,900ms).

**장점**: 빠르다. 이미 한 일을 반복하지 않는다.
**단점**: **체크포인트 자체가 정확하지 않을 수 있다.**

```
t1  7,500번까지 처리하고 커밋 ✅
t2  체크포인트를 7500으로 갱신하려는 순간 ⚡ 다운
    → 체크포인트는 아직 7000

재시작: 7001번부터 → 7001~7500이 중복 처리된다 💀
```

**02의 Outbox와 똑같은 구조다.** "일을 하고 나서 그 사실을 기록하는" 두 단계 사이에서 죽으면 중복이 난다.

> **체크포인트는 성능 최적화지 정확성 보장이 아니다.**
> 정확성은 다음 방법이 책임진다.

### 2-3. ⭐ 해법 ② 멱등 upsert — 진짜 방어선

체크포인트가 틀려도, 배치를 몇 번 돌려도 결과가 같게 만든다.

```sql
-- 거래 + 정산일 조합에 UNIQUE 제약
ALTER TABLE 정산 ADD CONSTRAINT uq_거래_정산일
    UNIQUE (거래id, 정산일);

-- 중복이면 무시하고 넘어간다
INSERT INTO 정산 (거래id, 정산일, 금액, ...)
VALUES (?, ?, ?, ...)
ON CONFLICT (거래id, 정산일) DO NOTHING;
```

**이제 배치를 처음부터 몇 번을 돌려도 결과가 같다.** 이미 정산된 건은 DB가 조용히 건너뛴다.

`IDEMPOTENT_UPSERT` 모드가 이걸 보여준다 — 전체 재실행인데 250건을 건너뛰고 최종 결과가 10,000건 그대로다.

**여기서 중요한 설계 판단이 하나 있다: "무엇이 같은 것인가"를 정하는 일이다.**

```
UNIQUE (거래id)              → 같은 거래는 영원히 한 번만 정산.
                               재정산이 필요하면 못 한다

UNIQUE (거래id, 정산일)       → 거래별·정산일별로 한 번.
                               정산일이 다르면 다시 정산 가능 ✅

UNIQUE (거래id, 정산일, 버전) → 같은 날 재정산도 버전을 올려서 가능
```

**멱등키를 어떻게 잡느냐가 곧 "재실행 가능 범위"를 정한다.** 너무 좁으면 정당한 재정산도 막히고, 너무 넓으면 중복이 새어 나온다. 2편의 상품권 멱등키와 같은 고민이다.

### 2-4. 해법 ③ 부분 재처리 — 실패한 구간만

`PARTIAL_RETRY` 모드다. 앞의 둘과 발상이 다르다.

```
[체크포인트 방식]  실패 지점 이후 전부 다시  →  순차적
[부분 재처리]      데이터를 구간으로 나누고, 실패한 구간만  →  병렬 가능
```

```
정산 대상 1만 건을 10개 구간으로 나눈다
  구간 1 (1~1000)     ✅ 성공
  구간 2 (1001~2000)  ✅ 성공
  ...
  구간 7 (6001~7000)  ❌ 실패 ← 이 구간만 다시
  ...

→ 구간 7만 별도 worker로 재처리
→ 나머지는 건드리지 않는다
```

**장점**
- 구간별로 **병렬 처리** 가능 (대본 기준 `replicas: 2`)
- 실패 영향 범위가 명확하다 — "구간 7이 실패했다"고 정확히 보고할 수 있다
- 재처리 비용이 최소다

**단점**
- 구간 나누기(파티셔닝) 설계가 필요하다
- 구간 간 의존성이 있으면 못 쓴다 (예: 누적 합계를 순서대로 계산해야 하는 경우)

**02의 Kafka 파티션과 같은 발상이다.** 독립적으로 처리 가능한 단위로 쪼개면 병렬화와 실패 격리가 동시에 된다.

### 2-5. 마지막 단계 — 대조(reconciliation)

`PARTIAL_RETRY` 의 마지막 스텝이 이거다.

```
step("TOTAL_RECONCILED", "합계와 건수를 원본 거래와 대조했다.")
```

**정산 배치는 "돌았다"로 끝나면 안 된다.** 반드시 확인해야 한다.

```
원본 거래 테이블:  건수 10,000건,  합계 1,234,567,890원
정산 결과 테이블:  건수 10,000건,  합계 1,234,567,890원
                  ─────────────────────────────────
                  일치 ✅ → 정산 확정
                  불일치 ❌ → 알람, 확정 보류, 사람 확인
```

**이게 마지막 안전망이다.** 체크포인트가 틀려도, 멱등키가 잘못 잡혔어도, 부분 재처리에서 구간을 빠뜨렸어도 — **합계가 안 맞으면 잡힌다.**

> **정산에서 "돌았다"와 "맞다"는 다르다.**
> 배치가 예외 없이 끝났다는 건 아무것도 증명하지 않는다. **대조가 증명한다.**

## 3. 대안 표와 내 선택

| 접근 | 중복 방지 | 재실행 비용 | 병렬 | 복잡도 |
|---|---|---|---|---|
| 전체 재실행만 | ❌ **중복 정산** | 최대 | ✗ | 최소 |
| 체크포인트 | △ (경계에서 중복 가능) | 낮음 | ✗ | 낮음 |
| **멱등 upsert** | ✅ **확실** | 중간(전체 스캔) | ✗ | 낮음 |
| **부분 재처리** | △ (upsert와 병행 필요) | **최소** | ✅ | 중간 |
| **셋 다 + 대조** | ✅✅ | 최소 | ✅ | 높음 |

**내 선택: 멱등 upsert를 기반으로 깔고, 체크포인트로 속도를 얻고, 대조로 확인한다.**

세 가지의 역할이 다르다.

| 장치 | 역할 |
|---|---|
| **멱등 upsert** | **정확성 보장.** 이게 없으면 나머지는 의미가 없다 |
| 체크포인트 / 부분 재처리 | **성능 최적화.** 있으면 빠르고 없어도 정확하다 |
| 대조 | **검증.** 앞의 것들이 틀렸을 때 잡아낸다 |

**순서가 중요하다.** 정확성을 먼저 확보하고 그 위에 최적화를 얹는다. 반대로 하면 빠르지만 틀린 정산이 나온다.

## 4. 진위 한 줄

**⚠️ 이건 실행 데모가 아니라 설계 정리다.**

`OperationalTroubleshootingEngine.settlement()` 가 모드별 고정 step 배열을 반환한다. 실제 정산 테이블도, 1만 건 데이터도, 배치도 없다. 처리 시간(3,800ms / 1,900ms)과 건수(10,000 / 250)는 전부 코드에 적힌 상수다.

**면접에서는 이렇게 말한다.**

> "정산 배치는 중간에 죽으면 부분 성공 상태가 남는 게 본질적인 문제입니다. 실무에서 그걸 다룰 때 고려한 축이 넷이었고, 화면은 그 넷을 비교하려고 만든 설계 정리입니다. 실제 배치를 만들어 돌린 건 아닙니다."

## 5. 30초 구두 답변

> 배치는 온라인 요청과 달리 "부분 성공"이 존재합니다. 1만 건 중 7,500건까지 처리하고 죽은 상태요. 전체를 한 트랜잭션으로 묶으면 락이 너무 오래 걸리고 롤백 비용도 커서, 청크 단위로 커밋할 수밖에 없고 그러면 부분 성공은 필연입니다.
>
> 여기서 그냥 처음부터 다시 돌리면 7,500건이 중복 정산됩니다. 그래서 세 겹으로 막았습니다. 먼저 거래ID와 정산일 조합에 UNIQUE 제약을 걸고 `ON CONFLICT DO NOTHING` 으로 upsert합니다. 이게 정확성의 기반이라 몇 번을 돌려도 결과가 같습니다. 그 위에 체크포인트로 이미 한 구간을 건너뛰어 속도를 얻고, 실패한 구간만 골라서 병렬로 재처리합니다.
>
> 마지막으로 원본 거래의 건수·합계와 정산 결과를 대조합니다. 배치가 예외 없이 끝났다는 게 정산이 맞다는 걸 증명하진 않으니까요. 체크포인트는 성능 최적화고 정확성은 멱등 upsert와 대조가 책임진다는 구분이 중요하다고 봅니다.

## 6. 꼬리질문과 답

**Q1. 체크포인트만으로는 왜 부족한가요?**

**체크포인트를 갱신하는 것 자체가 또 하나의 쓰기라서 그렇습니다.**

7,500건을 처리하고 커밋한 다음, 체크포인트를 7500으로 갱신하려는 순간 죽으면 체크포인트는 이전 값(예: 7000)입니다. 재시작하면 7001번부터 시작해서 7001~7500이 중복 처리됩니다.

**Outbox 릴레이가 발행 후 status 갱신 전에 죽는 것과 완전히 같은 구조**입니다. 두 시스템(또는 두 쓰기)을 원자적으로 묶을 수 없다는 같은 뿌리고요. 그래서 체크포인트는 성능 최적화로만 쓰고, 정확성은 멱등 upsert에 맡깁니다.

**Q2. 멱등키를 뭘로 잡아야 하나요?**

**"무엇을 같은 것으로 볼 것인가"라는 비즈니스 질문입니다.** 기술 질문이 아닙니다.

`거래ID` 만 잡으면 같은 거래는 영원히 한 번만 정산됩니다. 정산 로직에 버그가 있어서 재정산해야 할 때 못 합니다.

`거래ID + 정산일` 로 잡으면 정산일이 다르면 다시 정산할 수 있습니다. 저는 이걸 택했습니다.

같은 날 재정산까지 허용해야 하면 `거래ID + 정산일 + 버전` 으로 잡고 버전을 올립니다.

**너무 좁으면 정당한 재정산이 막히고, 너무 넓으면 중복이 샙니다.** 도메인 담당자와 합의해야 하는 부분입니다.

**Q3. 대조에서 불일치가 나면 어떻게 하나요?**

**자동으로 고치지 않습니다.** 이게 원칙입니다.

정산은 돈이라, 자동 보정이 틀리면 피해가 훨씬 큽니다. 그래서 **정산을 확정하지 않고 보류 상태로 두고, 알람을 띄우고, 불일치 내역을 조회할 수 있게** 합니다. 사람이 원인을 확인하고 판단합니다.

이것도 02의 DLQ와 같은 발상입니다. **자동 복구가 불가능한 건 시스템이 삼키지 말고 사람에게 올려야 합니다.** 조용히 넘어가는 게 최악이고요.

**Q4. 배치가 여러 대에서 동시에 돌면요?**

**같은 대상을 중복 처리합니다.** 멱등 upsert가 있으면 결과는 안 깨지지만, 같은 일을 두 번 해서 자원이 낭비되고 처리 시간이 오히려 늘어납니다.

막는 방법은 셋입니다. **배치 실행 자체에 락**을 겁니다 — DB에 실행 행을 만들고 UNIQUE 제약으로 두 번째 실행을 막는 방식이 간단합니다. 아니면 **리더 선출**로 한 대만 돌게 하거나, 애초에 **구간을 미리 배분**해서 각 인스턴스가 다른 구간을 맡게 합니다.

세 번째가 가장 좋습니다. 중복을 막으면서 병렬 처리까지 얻으니까요. 2-4의 부분 재처리 설계가 그대로 쓰입니다.

## 7. 모르면 인정할 선

**여기까지는 자신 있게 답한다**
- 배치의 "부분 성공"이 왜 필연인지 (전체 트랜잭션이 안 되는 세 가지 이유)
- 체크포인트가 왜 정확성 보장이 아닌지 (**갱신 자체가 또 하나의 쓰기**)
- 멱등 upsert와 `ON CONFLICT DO NOTHING`
- **멱등키 범위 설계가 곧 재실행 가능 범위라는 것**
- 부분 재처리와 병렬화, Kafka 파티션과의 유사성
- **"돌았다"와 "맞다"의 차이**, 대조가 마지막 안전망인 이유
- 정확성 → 성능 → 검증의 순서

**여기부터는 "안 해봤습니다"라고 말한다**
- Spring Batch의 실제 사용 (Job/Step/Chunk, `JobRepository` 재시작 메커니즘)
- 수백만 건 규모에서의 청크 크기·커밋 간격 튜닝
- 배치 실행 락 / 리더 선출의 실제 구현
- 정산 불일치 조사 운영 도구

> ### 자가 점검
> **"체크포인트만으로 왜 부족한가"** 를 Outbox와 같은 구조로 설명할 수 있는가.
> **"멱등키를 거래ID만으로 잡으면 뭐가 문제인가"** 를 답할 수 있는가.
> **"돌았다와 맞다의 차이"** 를 설명할 수 있는가.

# 마무리 — 이 그룹을 하나로 묶는 답변

면접에서 **"동시성이나 정합성 문제를 다뤄 본 경험이 있나요"** 가 나오면 이렇게 묶는다.

> 정합성이 깨지는 경로는 크게 두 가지라고 봅니다. **같은 순간에 둘이 하는 것**과, **한 요청이 시간차를 두고 두 번 오는 것**입니다. 증상은 비슷한데 원인과 해법이 완전히 다릅니다.
>
> **동시성 쪽**은 읽기와 쓰기 사이의 틈이 문제입니다. 재고를 읽고, 판단하고, 쓰는 사이에 남이 끼어들면 Lost Update가 납니다. 해법은 전부 그 틈을 없애는 방향이고요. 저는 조건부 UPDATE를 기본으로 씁니다. `WHERE 수량 >= 1` 을 SQL 안에 넣으면 DB가 행을 잠근 채 확인과 갱신을 한 번에 하니까 틈 자체가 사라집니다. 락 관리도 재시도 루프도 필요 없고요. 선착순처럼 한 행에 수만 개가 몰리면 Redis Lua로 게이트를 세웁니다.
>
> **재실행 쪽**은 멱등성입니다. 결제 callback은 중복으로 오는 게 정상이고, 정산 배치도 중간에 죽으면 다시 돌려야 합니다. 여기서 중요한 건 확인을 애플리케이션이 하지 않는 겁니다. "먼저 조회해서 없으면 삽입"은 두 요청이 동시에 "없다"를 보는 순간이 있어서 뚫립니다. UNIQUE 제약을 걸고 일단 삽입한 뒤 걸리면 기존 결과를 반환하는 방식이 안전합니다.
>
> 공통점은 **정합성의 마지막 방어선을 애플리케이션이 아니라 DB 제약에 둔다**는 겁니다. 애플리케이션 로직은 새 코드 경로가 생기면 우회되지만, UNIQUE나 CHECK 제약은 어떤 경로로 와도 막습니다.
>
> 다만 이 네 화면은 실행 데모가 아니라 설계 정리입니다. 고정 입력으로 대안을 비교한 것이고, 실제로 동시 요청을 쏘는 코드는 아닙니다.

## 왜 이 답변이 강한가

1. **두 축으로 나눈 분류가 정확하다.** 동시성과 재실행을 섞어 말하는 사람이 많다
2. "조건부 UPDATE" 하나로 여러 시나리오를 관통한다 — 재고·잔액·쿠폰·예약 회수가 전부 같은 도구다
3. **"확인을 DB가 하게 한다"** 는 원칙이 Insert-or-Get, UNIQUE, CHECK를 하나로 꿴다
4. **마지막에 진위를 스스로 밝힌다.** 이게 나머지 전부의 신뢰를 지킨다
