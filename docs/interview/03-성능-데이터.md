# 03. 성능 · 데이터

사이트 그룹: **성능·데이터** — "트래픽, DB 자원과 조회 비용을 측정해 병목의 위치와 완화 전략을 비교한다."

5편 중 **1편만 실제로 돌아간다** (검색 비교). 나머지 4편은 고정 대본이다.

| 편 | 진위 |
|---|---|
| 이벤트 트래픽 폭주 제어 | ⚠️ 고정 대본 |
| DB Connection Pool 고갈 | ⚠️ 고정 대본 (**승격 후보**) |
| 주문 목록 JPA N+1 | ⚠️ 고정 대본 (**승격 후보**) |
| **LIKE·tsvector·nori 검색 비교** | ✅ **실제 실행** — 10만 건에 진짜 쿼리 3개를 던지고 시간을 잰다 |
| 이미지 업로드 최적화 | ⚠️ 고정 대본 (사이트가 이미 "정책 모델"이라고 밝힘) |

---

## 시작하기 전에 — 성능 문제를 보는 세 가지 질문

성능 이야기는 막연해지기 쉽다. **"느리다"는 증상이지 원인이 아니기 때문**이다. 이 그룹의 5편은 사실 아래 세 질문의 변주다.

```
①  무엇이 유한한가?
     DB 커넥션 20개, 스레드 200개, 메모리 2GB, 초당 처리 220건...
     → 무한한 자원은 없다. 병목은 항상 "가장 먼저 바닥나는 것"이다

②  누가 얼마나 오래 쥐고 있는가?
     성능 문제의 대부분은 "일을 많이 해서"가 아니라
     "자원을 오래 쥐고 있어서" 생긴다
     → 특히 "일하지 않으면서 쥐고 있는" 경우가 최악이다 (외부 호출 대기)

③  넘칠 때 무엇을 포기할 것인가?
     입력이 용량을 넘으면 셋 중 하나다.
       버린다(거절)  /  미룬다(대기열)  /  다 같이 느려진다(최악)
     → 아무것도 정하지 않으면 자동으로 세 번째가 된다
```

**5편의 배치는 이렇다.**

| 편 | 유한한 자원 | 핵심 질문 |
|---|---|---|
| 트래픽 폭주 | 초당 처리량 | ③ 넘칠 때 무엇을 포기하나 |
| Connection Pool | DB 커넥션 20개 | ② **일 안 하면서 쥐고 있는** 시간 |
| JPA N+1 | 쿼리 횟수·왕복 시간 | ① 비용이 데이터 건수에 비례하는가 |
| 검색 비교 | 조회 시간 | ① **미리 일해 두면**(인덱스) 나중이 싸다 |
| 이미지 | 저장·전송 용량 | ① 원본을 그대로 두면 비용이 계속 나간다 |

> ### 그리고 하나 더 — **측정하지 않으면 아무것도 모른다**
> 이 그룹에서 유일하게 실제로 도는 편이 **검색 비교**인데, 하필 그게 **실제 숫자를 재는 편**이다.
> 나머지 4편의 숫자는 전부 코드에 적힌 상수다. 이 대비 자체가 면접에서 할 말이 된다.

# 1. 이벤트 트래픽 폭주 제어

**시나리오 id**: `traffic-burst-control`
**모드**: `BASELINE` / `RATE_LIMIT` / `QUEUE_BUFFER` / `SLOW_CONSUMER` / `DUPLICATE_BURST` / `RECOVERY`

## 1. 한 줄 정의

**초당 600건이 몰리는데 서버는 220건밖에 처리 못 할 때**, 무엇을 버리고 무엇을 미룰 것인가.

## 2. 원리 — 왜 이 문제가 생기나

### 2-1. 입력이 처리 능력을 넘으면 반드시 뭔가가 무너진다

이건 물리 법칙에 가깝다.

```
들어오는 양:  600 건/초
처리하는 양:  220 건/초
──────────────────────────
매초 380건이 어딘가에 쌓인다
```

**380건은 사라지지 않는다.** 어딘가로 가야 한다. 선택지는 셋뿐이다.

```
① 버린다 (rate limit)
     → 380건에게 "지금 안 됩니다" 라고 즉시 답한다
     → 220건은 정상 속도로 처리된다
     → 사용자 일부가 실패를 본다. 하지만 빠르게 안다

② 미룬다 (queue / buffer)
     → 380건을 대기열에 넣는다
     → 순서대로 처리한다. 아무도 안 버려진다
     → 대기 시간이 점점 길어진다

③ 아무것도 안 한다  ← 기본값
     → 380건이 전부 서버 안으로 들어온다
     → 스레드·커넥션·메모리를 나눠 갖는다
     → 220건도 느려진다  💀
     → 전부 타임아웃 → 재시도 → 더 몰림 → 붕괴
```

> ### ③이 최악인 이유
> **일부가 실패하는 게 아니라 전부가 실패한다.**
> 아무것도 정하지 않으면 시스템은 자동으로 ③을 택한다. **의도적으로 ①이나 ②를 골라야 한다.**

`BASELINE` 모드가 ③을 보여준다.

```
step("BURST_STARTED",    "600 RPS 고정 입력을 시작했다.")
step("DB_DIRECT_WRITE",  "모든 요청이 동기 DB 처리 경로로 진입했다.")   ← 아무도 안 막았다
step("POOL_SATURATED",   "connection 대기와 p95가 함께 증가했다.")      ← 다 같이 느려짐
step("BACKLOG_REMAINED", "입력 종료 뒤 95초 동안 backlog가 남았다.")    ← 입력이 끝나도 안 끝남
```

**마지막 줄이 중요하다.** 트래픽이 멈춰도 시스템은 한참 동안 회복하지 못한다. 이미 쌓인 걸 다 소화해야 하기 때문이다.

### 2-2. ⭐ 버리기 (Rate Limit) — 빠른 실패가 친절하다

**직관에 반하는 사실 하나**: 사용자에게는 **30초 기다리다 실패하는 것보다 0.1초 만에 실패를 아는 게 낫다.**

- 30초 기다린 사용자: 그동안 서버 자원을 쓴다. 실패하고 나서 화가 난다. 그리고 **재시도한다** (부하 증가)
- 0.1초에 거절당한 사용자: 자원을 거의 안 쓴다. "지금 사람이 많구나" 하고 이해한다

**Rate Limit의 원리 — Token Bucket**

```
양동이에 토큰이 있다. 용량 20개.
매초 일정 속도로 토큰이 채워진다.

요청이 오면:
  토큰이 있나?  →  있으면 하나 꺼내고 통과 ✅
                →  없으면 즉시 429 거절 ❌

핵심: 양동이 용량(burst 허용치)과 채우는 속도(평균 처리율)를 따로 정할 수 있다
      → 순간적인 몰림은 받아주고, 지속적인 과부하는 막는다
```

**이 프로젝트에 실제로 있는 것**: 게시판에 `BoardRateLimitInterceptor` 가 있고 운영에서 capacity 20으로 켜져 있다. 이건 대본이 아니라 실제 코드다. (블로그 작업 중에 **이 인터셉터가 `/api/board/**` 에만 등록돼 있어서 블로그 공개 댓글에는 rate limit이 전혀 없었다**는 걸 최종 리뷰에서 발견해 고쳤다. 좋은 이야깃거리다.)

**어디서 거절할 것인가가 중요하다.**

```
❌ 나쁨:  요청이 서버 깊숙이 들어와서 DB 커넥션까지 잡은 뒤에 거절
          → 이미 자원을 다 썼다. 거절의 의미가 없다

✅ 좋음:  최대한 앞단(게이트웨이, 인터셉터)에서 거절
          → 자원을 거의 안 쓰고 끝난다
```

### 2-3. 미루기 (Queue) — 대가는 지연이다

```
사용자 요청 → Kafka에 "접수했습니다" 기록 → 즉시 200 응답
                                          ↓
                              Consumer가 자기 속도로 천천히 처리
```

**장점**: 아무도 안 버려진다. 순간 폭주를 흡수한다. 사용자는 빠른 응답을 받는다.
**단점**: **"접수됨"과 "처리됨"이 분리된다.** UX가 달라진다.

```
[동기]  주문하기 → (2초 대기) → "주문 완료! 주문번호 12345"
[비동기] 주문하기 → (0.1초) → "주문 접수됨. 결과는 알림으로 보내드립니다"
```

**이건 기술 결정이 아니라 제품 결정이다.** 티켓팅은 후자가 자연스럽고, 일반 쇼핑몰 결제는 전자를 기대한다.

### 2-4. ⭐ 대기열의 함정 — lag은 저절로 안 줄어든다

`SLOW_CONSUMER` 모드가 보여주는 게 이거다. 대기열을 뒀는데도 문제가 남는 경우.

```
입력:  600 건/초
처리:  120 건/초  (외부 의존성이 느려져서 처리 속도가 떨어짐)
─────────────────────────────
매초 480건씩 lag이 쌓인다

입력이 멈춰도:  쌓인 걸 120건/초로 소화 → 240초(4분) 걸림
```

> **대기열은 "순간 폭주"를 흡수하는 장치지 "지속적인 처리량 부족"을 해결하지 못한다.**
> 평균 입력 > 평균 처리량이면 lag은 **무한히 증가**한다. 큐를 아무리 키워도 마찬가지다.

**그래서 대기열에는 반드시 두 가지가 따라와야 한다.**

1. **lag 모니터링과 알람** — 안 보면 조용히 쌓인다
2. **처리량을 늘리는 수단** — `RECOVERY` 모드가 보여주는 게 이것 (consumer replica 1→2)

### 2-5. `DUPLICATE_BURST` — 폭주의 상당수는 중복이다

실무에서 자주 있는 일이다.

```
600건이 몰렸다.  그런데 그중 420건이 같은 사용자의 중복 클릭이었다.
                (버튼이 반응 없으니 계속 누른다 → 부하가 더 커진다 → 더 안 반응한다)
```

**악순환이다.** 그리고 해법은 성능 튜닝이 아니라 **01에서 배운 멱등성**이다.

```
요청 key(사용자+상품+요청ID)를 Redis에서 확인
  → 이미 있으면: 처리하지 않고 첫 결과를 반환  (부하 0에 가까움)
  → 없으면: 처리
```

**"성능 문제인 줄 알았는데 정합성 설계로 풀리는" 경우**다. 이런 연결을 면접에서 말할 수 있으면 좋다.

## 3. 대안 표와 내 선택

| 접근 | 버려지나 | 지연 | 복잡도 | 언제 |
|---|---|---|---|---|
| 아무것도 안 함 | **전부 느려지고 결국 다 실패** | 최악 | 없음 | ✗ 절대 |
| **Rate limit** | 일부 거절 (빠르게) | 낮음 | 낮음 | 즉시 응답이 중요할 때 |
| **Queue buffer** | 없음 | 높아질 수 있음 | 중간 | 접수·처리 분리가 자연스러울 때 |
| 멱등 중복 제거 | — | — | 낮음 | **거의 항상 같이** |
| Consumer 확장 | 없음 | 낮아짐 | 높음 | 지속적 부하 증가 |

**내 판단**: 이건 하나를 고르는 문제가 아니라 **계층으로 쌓는** 문제다.

```
1단계  앞단에서 중복 제거      → 실제 필요한 부하만 남긴다
2단계  rate limit             → 감당 가능한 양만 통과
3단계  통과한 것은 queue       → 순간 몰림을 흡수
4단계  lag 모니터링 + 확장     → 지속적 증가에 대응
```

## 4. 진위 한 줄

**⚠️ 고정 대본이다. 그리고 이 편이 21편 중 가장 위험하다.**

`DomainScenarioEngine.trafficBurst()` 가 모드별로 고정 step과 **고정 숫자**를 반환한다.

```java
case "BASELINE" -> trafficResult("SATURATED", "직접 처리 경로가 포화", 600, 220, key,
        1_450, 0, 380, 1, 95,   // ← p95Ms=1450, queueLag=380, recoverySeconds=95
```

600 RPS, p95 1,450ms, backlog 95초 — **전부 측정값 형태인데 코드에 적힌 상수다.**

> **`README.md` 의 기준을 다시 보자.**
> "재고 갱신 경계를 직렬화했다" 같은 **설계 주장**은 대본이어도 괜찮다.
> "p95 1,450ms" 같은 **측정값**은 대본이면 안 된다. "어떻게 측정하셨어요?" 한 마디에 무너진다.

**2단계 수정 대상 1순위다.** 숫자를 빼고 관계만 남기는 게 맞다 — *"직접 처리 경로에서는 풀이 포화되면 p95가 함께 오른다"* 는 참이지만, *"1,450ms"* 는 근거가 없다.

**면접에서 이 편이 나오면**: 숫자를 먼저 부인한다.
> "화면 숫자는 고정 입력 모델이라 실측이 아닙니다. 여기서 보여드리고 싶었던 건 값이 아니라 **선택지의 구조**입니다 — 넘칠 때 버릴 것인가 미룰 것인가, 그리고 그 대가가 각각 무엇인가요."

## 5. 30초 구두 답변

> 입력이 처리 능력을 넘으면 초과분은 사라지지 않고 어딘가에 쌓입니다. 선택지가 셋인데, 버리거나 미루거나 아니면 아무것도 안 하는 겁니다. 문제는 아무것도 안 하면 자동으로 세 번째가 되고, 그게 최악이라는 거예요. 초과분이 전부 서버 안으로 들어와서 자원을 나눠 갖고, 결국 감당 가능했던 요청까지 다 같이 느려져서 전부 실패합니다.
>
> 그래서 의도적으로 골라야 합니다. rate limit은 일부를 빠르게 거절하는 대신 나머지를 정상 속도로 지킵니다. 사용자한테도 30초 기다리다 실패하는 것보다 0.1초에 아는 게 낫고요. 대기열은 아무도 안 버리는 대신 접수와 처리가 분리돼서 UX가 달라집니다.
>
> 중요한 건 대기열이 순간 폭주는 흡수해도 지속적인 처리량 부족은 해결 못 한다는 겁니다. 평균 입력이 평균 처리량보다 크면 lag은 무한히 쌓여요. 그래서 대기열에는 반드시 lag 모니터링이랑 처리량을 늘릴 수단이 같이 따라와야 합니다.
>
> 다만 이 화면 숫자는 고정 입력 모델이고 실측이 아닙니다.

## 6. 꼬리질문과 답

**Q1. Rate limit을 어디에 걸어야 하나요?**

**최대한 앞단**입니다. 요청이 서버 깊숙이 들어와서 DB 커넥션까지 잡은 다음 거절하면, 이미 자원을 다 쓴 뒤라 거절의 의미가 없습니다.

이상적으로는 API 게이트웨이나 리버스 프록시 레벨이고, 애플리케이션 안이라면 인터셉터/필터 같은 최상단입니다.

**실제로 이 프로젝트에서 관련된 사고가 있었습니다.** 게시판 rate limit 인터셉터가 `/api/board/**` 에만 등록돼 있었는데, 블로그 댓글 기능을 추가하면서 서비스 코드의 조건은 넓혔지만 **인터셉터 등록 경로를 안 고쳐서 블로그 공개 댓글에는 rate limit이 전혀 안 걸렸습니다.** 코드상으로는 분기가 존재하는데 **호출되지 않는 죽은 코드**였던 거죠. 태스크 단위 리뷰로는 안 잡히고 전체 리뷰에서 발견했습니다.

**Q2. Rate limit 카운터를 어디에 두나요?**

**Redis입니다.** 애플리케이션 메모리에 두면 인스턴스가 여러 대일 때 각자 세서 실제 한도가 인스턴스 수만큼 곱해집니다. 02의 채팅 정원 문제와 완전히 같은 구조예요.

그리고 Redis 연산도 원자적이어야 합니다. `INCR` 은 원자적이니 괜찮은데, "읽고 판단하고 증가"로 짜면 또 뚫립니다.

**Q3. 429를 받은 클라이언트가 바로 재시도하면 의미가 없지 않나요?**

맞습니다. 그래서 **`Retry-After` 헤더를 함께 줍니다.** 02의 제휴 API 편에서 봤던 것의 반대편이죠 — 거기서는 제가 받는 쪽이었고 여기서는 주는 쪽입니다.

그리고 클라이언트가 그걸 안 지킬 수도 있으니, **거절 자체가 아주 싸야 합니다.** 앞단에서 토큰 확인만 하고 끝나면 재시도가 몰려도 감당됩니다.

**thundering herd**도 조심해야 합니다. 전부 "3초 뒤"를 정확히 지키면 3초 뒤에 또 몰립니다. 그래서 클라이언트 쪽에 지터를 넣거나, 서버가 `Retry-After` 값을 요청마다 조금씩 다르게 줍니다.

**Q4. 큐를 쓰면 응답이 빨라지는 거 아닌가요?**

**응답은 빨라지고 완료는 느려집니다.** 이 구분이 중요합니다.

"접수했습니다"를 0.1초에 주니까 응답 시간 지표는 좋아집니다. 하지만 실제 처리가 끝나는 시점은 오히려 늦어질 수 있어요. 지표만 보면 개선된 것처럼 보이는데 사용자 경험은 나빠질 수 있습니다.

그래서 큐를 쓰면 **"end-to-end 완료 시간"** 을 따로 측정해야 합니다. API 응답 시간만 보면 lag이 4분 쌓여 있어도 알아채지 못합니다.

## 7. 모르면 인정할 선

**여기까지는 자신 있게 답한다**
- 입력 > 처리량일 때 선택지가 셋뿐이고, **아무것도 안 하면 최악이 자동 선택된다**는 것
- Token Bucket 원리와 burst 허용치/평균 처리율을 분리하는 이유
- rate limit을 앞단에 둬야 하는 이유
- **큐가 순간 폭주는 흡수해도 지속적 부족은 해결 못 한다**는 것
- 응답 시간과 완료 시간의 구분
- 폭주의 상당수가 중복이고 그건 멱등성으로 푼다는 연결

**여기부터는 "안 해봤습니다"라고 말한다**
- **실제 부하 테스트** (k6, Gatling 등)와 그 결과 해석 — **화면 숫자는 전부 상수다**
- Token Bucket / Sliding Window / Leaky Bucket의 실측 비교
- consumer lag 기반 오토스케일링(KEDA 등) 구성
- 백프레셔(backpressure)를 프로토콜 레벨에서 전파하는 방식

> ### 자가 점검
> **"아무것도 안 하면 왜 최악인가"** 를 설명할 수 있는가.
> **"큐를 뒀는데도 왜 lag이 쌓이나"** 에 평균 처리량 이야기로 답할 수 있는가.
> **숫자가 실측이 아니라는 걸 먼저 말할 수 있는가.**

# 2. DB Connection Pool 고갈

**시나리오 id**: `connection-pool-exhaustion`
**모드**: `TX_EXTERNAL_CALL` / `BOUNDARY_SPLIT` / `TIMEOUT` / `BULKHEAD`

## 1. 한 줄 정의

**외부 API를 트랜잭션 안에서 기다리면** DB 커넥션을 쥔 채 놀게 되고, 결국 DB와 무관한 요청까지 막힌다.

## 2. 원리 — 왜 이 문제가 생기나

### 2-1. 커넥션 풀이 뭐고 왜 유한한가

DB 연결은 **비싸다.** TCP 연결, 인증, 세션 설정에 수십 밀리초가 든다. 요청마다 새로 만들면 그 비용이 매번 든다.

그래서 **미리 만들어 두고 재사용**한다. 이게 커넥션 풀이다.

```
[HikariCP 풀 — 기본 10~20개]
  ┌────┬────┬────┬────┬────┐
  │ #1 │ #2 │ #3 │ ...│#20 │
  └────┴────┴────┴────┴────┘

요청이 오면:  풀에서 하나 빌린다 → 쿼리 → 반납
풀이 비었으면: 대기한다 → 정해진 시간 안에 못 빌리면 예외
```

**왜 20개뿐인가? 더 늘리면 안 되나?**

DB 쪽 한계 때문이다. PostgreSQL은 커넥션마다 **프로세스를 하나씩** 띄운다. 수백 개가 되면 메모리와 컨텍스트 스위칭 비용이 폭증하고, **오히려 전체가 느려진다.** 그래서 애플리케이션 쪽 풀을 작게 유지하는 게 정석이다.

> **커넥션은 늘릴 수 없는 자원이다. 그러니 "빨리 돌려주는" 것 말고는 방법이 없다.**

### 2-2. ⭐ 사고의 메커니즘 — 놀면서 쥐고 있다

```java
@Transactional                        // ← 여기서 커넥션을 빌린다
public void 주문처리() {
    주문저장();                        // DB 작업 (50ms)
    결제API호출();                     // 🌐 외부 호출 (3,000ms) ← 이 동안 커넥션은?
    결제결과저장();                     // DB 작업 (50ms)
}                                      // ← 여기서 커넥션을 반납한다
```

**결제 API를 기다리는 3초 동안 이 커넥션은 아무 일도 안 한다. 그런데 반납되지도 않는다.**

```
커넥션 점유 시간:  50ms + 3,000ms + 50ms = 3,100ms
실제 DB 작업 시간:  50ms + 50ms          =   100ms
────────────────────────────────────────────────────
낭비:  3,000ms  (전체의 97%를 놀면서 쥐고 있다)
```

이제 동시 요청이 늘면 이렇게 된다.

```
동시 요청 20개 → 커넥션 20개 전부 점유 → 풀이 빈다
동시 요청 21번째 → 대기
동시 요청 36번째 → 대기        ← 화면의 "active 20, pending 16"
...
그리고 이때, 결제와 아무 상관 없는 "게시판 목록 조회" 요청이 들어오면?
→ 커넥션이 없어서 대기한다 → 타임아웃 → 500 💀
```

> ### 핵심
> **결제사 한 곳이 느려졌을 뿐인데 게시판이 죽는다.**
> 이게 02에서 본 **장애 전파(cascading failure)** 의 DB 버전이다.
> 원인은 "느린 외부 호출"이 아니라 **"느린 외부 호출을 트랜잭션 안에 넣은 것"** 이다.

### 2-3. ⭐⭐ 이 프로젝트가 실제로 이 안티패턴을 저질렀고, 고쳤다

**고치기 전** `OrderSagaService.run()` 이 이랬다.

```java
@Transactional                                 // ← 커넥션 획득
public OrderSagaView run(OrderSagaRequest request) {
    ...
    payment = authorizePayment(order, request);  // 🌐 FastAPI 결제 서비스 HTTP 호출
    ...
}                                               // ← 커넥션 반납
```

**이 화면이 경고하는 패턴을 저 화면이 그대로 하고 있었다.** 자기 포트폴리오가 자기 자신을 반박하는 상태였다.

**2026-08-03에 고쳤다.** DB 단계를 `OrderSagaSteps` 라는 별도 빈으로 빼고 단계마다 짧은 트랜잭션을 걸었다. 오케스트레이터는 트랜잭션을 아예 열지 않고, 결제 호출은 단계 사이에서 일어난다. (Spring 프록시가 자기 호출에는 트랜잭션을 못 걸어서 **별도 빈이어야** 했다.)

**면접에서 이건 아주 좋은 소재다.**

> "이 시나리오를 정리하다가 저희 Saga 코드가 정확히 이 안티패턴을 저지르고 있다는 걸 발견했습니다. `@Transactional` 안에서 FastAPI 결제 서비스를 호출하고 있었거든요. 데모를 요청 한 번으로 끝내려다 그렇게 된 건데, 커넥션 점유 문제뿐 아니라 **예외가 나면 통째로 롤백돼서 보상 로직이 실행될 일이 없다**는 더 근본적인 문제가 있었습니다. Saga를 쓰는데 정작 Saga가 필요 없는 구조였던 거죠.
>
> 단계별 트랜잭션으로 나눠서 고쳤고, 대신 원자성을 잃었습니다. **경계 분리는 원자성을 보상으로 바꾸는 거래**라는 걸 실제로 겪었습니다."

**스스로 찾아내고 고친 자기 코드의 결함**만큼 신뢰를 주는 답변은 드물다.

### 2-4. 해법 ① 경계 분리 — 가장 정석

```java
// ❌ 이전
@Transactional
void 주문처리() {
    주문저장();
    결제API호출();      // 트랜잭션 안
    결제결과저장();
}

// ✅ 이후
void 주문처리() {
    주문저장_트랜잭션();          // 짧은 트랜잭션 ①  (50ms 점유)
    var 결과 = 결제API호출();     // 트랜잭션 밖 🌐   (커넥션 점유 0)
    결제결과저장_트랜잭션(결과);   // 짧은 트랜잭션 ②  (50ms 점유)
}
```

**커넥션 점유 시간이 3,100ms → 100ms로 줄었다.** 같은 커넥션 20개로 31배 많은 요청을 처리할 수 있다.

**대가**: 원자성이 사라진다. 트랜잭션 ①과 ② 사이에서 죽으면 "주문은 있는데 결제 결과가 없는" 상태가 남는다.

> **이걸 어디서 본 적 있다.** 02의 Saga가 정확히 이 문제를 다룬다.
> **경계를 나누면 원자성을 잃고, 그래서 보상이 필요해진다.** 두 시나리오가 이렇게 이어진다.

### 2-5. 해법 ② 타임아웃 — 점유 시간에 상한을 건다

경계를 못 나누는 상황이라도, **최소한 얼마나 오래 쥘지에 상한**은 걸어야 한다.

```
connect timeout:  연결 자체를 맺는 데 걸리는 시간 (예: 1초)
read timeout:     연결 후 응답을 기다리는 시간 (예: 3초)
```

**둘을 나누는 이유**: 성격이 다르다. 연결이 안 되는 건 대개 상대가 죽었거나 방화벽 문제라 오래 기다릴 이유가 없다. 응답이 느린 건 상대가 처리 중일 수 있으니 조금 더 준다.

**타임아웃이 없으면 어떻게 되나?** OS 기본값까지 기다린다. 수십 초에서 수 분이다. 그동안 커넥션은 묶여 있다.

> **"타임아웃 없는 외부 호출"은 실무에서 가장 흔한 장애 원인 중 하나다.**
> 그리고 평소에는 아무 문제가 없다가 상대가 느려지는 날 한 번에 터진다.

### 2-6. 해법 ③ Bulkhead — 격벽

배의 격벽에서 온 이름이다. 배가 한 칸 물에 잠겨도 다른 칸이 막혀 있으면 안 가라앉는다.

```
[격벽이 없으면]
  전체 스레드 200개 중 몇 개를 결제가 쓸까?  → 제한 없음 → 전부 쓸 수 있다
  → 결제사가 느려지면 200개가 전부 결제 대기에 묶인다
  → 게시판 조회도 못 한다

[격벽이 있으면]
  결제 호출 동시성 = 최대 8개로 제한
  → 결제사가 느려져도 8개만 묶인다
  → 9번째 결제 요청은 즉시 거절 (fail-fast)
  → 나머지 192개는 게시판·검색 등을 계속 처리한다 ✅
```

**핵심**: 결제는 여전히 실패한다. **하지만 결제만 실패한다.** 이게 격리의 목적이다.

> 02의 서킷 브레이커와 짝이다.
> **서킷 브레이커**는 "죽은 상대를 계속 부르지 마라" (시간축 방어)
> **Bulkhead**는 "한 상대에 쓸 자원을 제한해라" (자원축 방어)
> 둘 다 목적은 같다 — **남의 장애가 내 전체를 삼키지 못하게.**

## 3. 대안 표와 내 선택

| 접근 | 점유 시간 | 원자성 | 복잡도 | 효과 |
|---|---|---|---|---|
| 아무것도 안 함 | **3,100ms** | 유지 | 없음 | ✗ 풀 고갈 |
| 풀 크기 늘리기 | 3,100ms | 유지 | 낮음 | ✗ **DB가 먼저 죽는다** |
| **경계 분리** | **100ms** | **잃는다 → 보상 필요** | 높음 | **✓ 근본 해결** |
| 타임아웃 | 상한선까지 | 유지 | 낮음 | ✓ 최소한의 방어 |
| Bulkhead | 3,100ms(단 8개만) | 유지 | 중간 | ✓ 격리 |

**내 판단: 경계 분리가 근본 해법이고, 나머지는 그걸 못 할 때의 완화책이다.**

다만 **타임아웃은 경계를 분리해도 반드시 함께 건다.** 트랜잭션 밖이라도 스레드는 여전히 묶이니까.

**"풀 크기를 늘리면 되지 않나"가 왜 함정인지**: 애플리케이션 풀을 100개로 늘리면 DB에 프로세스 100개가 뜬다. 인스턴스가 3대면 300개다. PostgreSQL이 먼저 무너진다. **병목을 옮겼을 뿐 없애지 못했고, 더 나쁜 곳으로 옮겼다.**

## 4. 진위 한 줄

**⚠️ 고정 대본이다.** `OperationalTroubleshootingEngine.connectionPool()` 이 고정 step과 숫자(active 20, pending 16, p95 4,800ms)를 반환한다.

**하지만 승격 후보 3편 중 하나다.** 이유:
- 필요한 게 **HikariCP 설정 변경(풀 크기를 3~5로 줄임)과 엔드포인트 하나**뿐이다
- 트랜잭션 안에서 3초 `sleep` 하는 엔드포인트를 만들고 동시 요청을 쏘면 **진짜 `SQLTransientConnectionException` 이 뜬다**
- 경계 분리 전/후 대비가 극적이라 보여주기 좋다
- 그리고 무엇보다 **이미 Saga에 실제 사례가 있다**

## 5. 30초 구두 답변

> DB 커넥션은 비싸서 미리 만들어 두고 재사용하는데, 풀 크기를 무한정 늘릴 수가 없습니다. PostgreSQL은 커넥션마다 프로세스를 띄워서 수백 개가 되면 DB가 먼저 무너지거든요. 그래서 커넥션은 늘릴 수 없는 자원이고, 빨리 돌려주는 것 말고 방법이 없습니다.
>
> 그런데 트랜잭션 안에서 외부 API를 호출하면 응답 기다리는 3초 동안 커넥션을 쥔 채로 아무 일도 안 합니다. 실제 DB 작업은 100ms인데 점유는 3.1초예요. 97%를 놀면서 쥐고 있는 거죠. 동시 요청이 20개만 돼도 풀이 비고, 그러면 결제랑 아무 상관 없는 게시판 조회까지 커넥션을 못 받아서 죽습니다. 결제사 한 곳이 느려졌을 뿐인데 전체가 무너지는 겁니다.
>
> 근본 해법은 경계 분리입니다. 외부 호출을 트랜잭션 밖으로 빼고 상태 반영만 짧은 트랜잭션으로 하면 점유가 100ms로 줄어듭니다. 대신 원자성을 잃어서 보상 로직이 필요해지고요. 경계를 못 나누는 상황이면 최소한 타임아웃으로 상한을 걸고, bulkhead로 외부 연동에 쓸 동시성을 제한해서 나머지 요청을 지킵니다.
>
> 사실 저희 Saga 데모가 정확히 이 안티패턴을 저지르고 있습니다. `@Transactional` 안에서 결제 서비스를 호출하거든요. 알고 있고 고쳐야 할 부분입니다.

## 6. 꼬리질문과 답

**Q1. 풀 크기를 늘리면 안 되나요?**

**병목을 더 나쁜 곳으로 옮길 뿐입니다.** PostgreSQL은 커넥션마다 프로세스를 하나씩 띄웁니다. 애플리케이션 풀을 100개로 늘리고 인스턴스가 3대면 DB에 300개 프로세스가 생기고, 메모리와 컨텍스트 스위칭 비용이 폭증해서 **전체 쿼리가 다 느려집니다.**

일반적인 권장은 **오히려 작게** 유지하는 겁니다. HikariCP 문서도 그렇게 말하고요. 커넥션 수를 늘려서 얻는 병렬성보다 DB가 감당할 수 있는 동시 실행 수가 먼저 한계에 닿습니다.

**Q2. 그럼 트랜잭션 없이 하면 되지 않나요?**

**원자성을 포기하는 대가가 있습니다.** 주문 저장과 결제 결과 저장이 별도 트랜잭션이 되면, 그 사이에서 죽었을 때 불일치 상태가 남습니다.

그래서 경계를 나누면 **보상 로직이나 상태 복구 절차가 반드시 따라와야 합니다.** 02의 Saga가 정확히 그 이야기고요. **경계 분리는 공짜가 아니라 "원자성을 보상으로 바꾸는 거래"** 입니다.

**Q3. 타임아웃 값은 어떻게 정하나요?**

**측정해서 정합니다.** 상대 API의 응답 시간 분포를 보고 p99보다 조금 여유 있게 잡는 게 시작점입니다. 감으로 "3초" 하면 정상 요청도 잘리거나 너무 오래 기다리게 됩니다.

그리고 **전체 예산에서 역산**하는 접근도 중요합니다. 사용자 요청 전체가 2초 안에 끝나야 하는데 내부에 외부 호출이 셋이면, 각각에 5초를 줄 수 없습니다. **상위 타임아웃이 하위 타임아웃의 합보다 커야** 앞단이 먼저 끊기는 이상한 상황을 피할 수 있고요.

솔직히 저는 이 값을 실측으로 정해 본 경험은 없습니다. 원칙만 압니다.

**Q4. Bulkhead와 서킷 브레이커는 뭐가 다른가요?**

**막는 축이 다릅니다.**

**서킷 브레이커는 시간축**입니다. "이 상대가 계속 실패하니 당분간 부르지 마라." 실패율을 집계해서 임계치를 넘으면 호출 자체를 차단합니다.

**Bulkhead는 자원축**입니다. "이 상대에게 쓸 수 있는 동시성은 최대 8개." 상대가 정상이어도 8개를 넘으면 거절합니다.

**둘은 같이 씁니다.** 서킷 브레이커만 있으면 "아직 임계치는 안 넘었는데 느린" 구간에서 자원이 다 묶이고, Bulkhead만 있으면 죽은 상대를 8개 슬롯으로 계속 두드립니다.

## 7. 모르면 인정할 선

**여기까지는 자신 있게 답한다**
- 커넥션 풀이 왜 있고 왜 작아야 하는지 (PostgreSQL 프로세스 모델)
- **"놀면서 쥐고 있는" 시간이 문제의 본질**이라는 것
- 장애 전파가 일어나는 정확한 경로
- 경계 분리의 효과와 **원자성을 보상으로 바꾸는 거래**라는 성격
- connect/read timeout을 나누는 이유
- Bulkhead와 서킷 브레이커의 축 차이
- **내 Saga 코드가 이 안티패턴을 저지르고 있다는 자기 진단**

**여기부터는 "안 해봤습니다"라고 말한다**
- 실제 풀 고갈 재현과 튜닝 (**화면 숫자는 상수다**)
- 타임아웃 값의 실측 기반 산정
- Resilience4j Bulkhead 실제 적용
- HikariCP 지표(`hikaricp_connections_pending` 등) 기반 알람 구성

> ### 자가 점검
> **"3초 대기 동안 커넥션은 어떻게 되나"** 를 점유/작업 시간으로 나눠 설명할 수 있는가.
> **"풀을 늘리면 왜 안 되나"** 를 PostgreSQL 프로세스 모델로 답할 수 있는가.
> **내 Saga 코드의 문제를 먼저 꺼낼 수 있는가.**

# 3. 주문 목록 JPA N+1

**시나리오 id**: `jpa-n-plus-one`
**모드**: `N_PLUS_ONE` / `FETCH_JOIN` / `PROJECTION` / `BATCH_FETCH`

## 1. 한 줄 정의

주문 100건을 조회했는데 **SQL이 301번 실행되는** 상황과, 그걸 2번 또는 1번으로 줄이는 방법들.

## 2. 원리 — 왜 이 문제가 생기나

### 2-1. 지연 로딩(Lazy Loading)이 무엇이고 왜 있나

JPA에서 연관 관계는 기본적으로 **지연 로딩**이다.

```java
@Entity
class 주문 {
    @Id Long id;
    String 주문번호;

    @OneToMany(fetch = LAZY)     // ← 기본값
    List<주문상품> 상품들;

    @ManyToOne(fetch = LAZY)
    결제 결제;
}
```

**지연 로딩은 좋은 기본값이다.** 주문 하나를 조회할 때마다 상품·결제·배송·회원·쿠폰까지 전부 따라오면, 필요 없는 데이터를 매번 읽게 되니까.

그래서 JPA는 **실제로 그 필드를 건드릴 때까지 조회를 미룬다.**

```java
주문 o = repo.findById(1);        // SELECT * FROM 주문 WHERE id=1   ← 여기까지만
System.out.println(o.주문번호);    // 추가 쿼리 없음 (이미 있다)
System.out.println(o.상품들);      // ← 이 순간 SELECT * FROM 주문상품 WHERE 주문id=1
```

**어떻게 이게 가능한가?** JPA가 `상품들` 자리에 **프록시(대리인 객체)** 를 넣어 둔다. 겉보기엔 리스트인데, 실제로 접근하는 순간 "아직 안 읽었네" 하고 DB를 다녀온다.

### 2-2. ⭐ 그런데 목록에서는 이게 재앙이 된다

```java
List<주문> 주문목록 = repo.findAll();   // SQL 1번 → 100건

for (주문 o : 주문목록) {
    화면에표시(o.상품들);              // ← 각각 SQL 1번씩!
}
```

```
SQL 1번   : SELECT * FROM 주문                        (100건)
SQL 100번 : SELECT * FROM 주문상품 WHERE 주문id = 1
            SELECT * FROM 주문상품 WHERE 주문id = 2
            ...
            SELECT * FROM 주문상품 WHERE 주문id = 100
─────────────────────────────────────────────────────
합계 101번
```

**"1 + N"이라 N+1 문제**라고 부른다. 여기에 결제와 배송까지 lazy면:

```
1 (주문)  +  100 (상품)  +  100 (결제)  +  100 (배송)  =  301번
```

화면의 `N_PLUS_ONE` 모드가 정확히 이 301이다.

### 2-3. 왜 301번이 100번보다 3배 느린 게 아니라 훨씬 느린가

**쿼리 자체는 빠르다.** `WHERE 주문id = 1` 은 인덱스가 있으면 1ms도 안 걸린다. 문제는 다른 데 있다.

```
쿼리 1회의 실제 비용:
  ① 애플리케이션 → DB 네트워크 왕복      (0.5ms)
  ② DB가 쿼리 파싱·계획 수립             (0.1ms)
  ③ 실제 데이터 읽기                     (0.1ms)  ← 진짜 일은 이것뿐
  ④ 결과 전송 + JPA가 객체로 매핑         (0.3ms)
  ─────────────────────────────────────────────
  약 1ms  (그중 실제 데이터 읽기는 10%)
```

**301번이면 왕복만 301번이다.** 그리고 이게 **데이터 건수에 비례해서 늘어난다.**

```
주문 10건   →  31번    (체감 없음)
주문 100건  →  301번   (느껴짐)
주문 1000건 →  3001번  (타임아웃)
```

> ### N+1이 위험한 진짜 이유
> **개발 환경에서는 절대 안 보인다.** 테스트 데이터가 10건이니까.
> **운영에서 데이터가 쌓이면 어느 날 갑자기 터진다.**
> 그리고 코드는 아무것도 안 바뀌었으니 원인을 찾기 어렵다.

### 2-4. 해법 ① Fetch Join — 한 번에 다 가져온다

```java
@Query("SELECT o FROM 주문 o JOIN FETCH o.결제 JOIN FETCH o.배송")
List<주문> findAllWithDetails();
```

```sql
SELECT o.*, p.*, s.*
FROM 주문 o
JOIN 결제 p ON ...
JOIN 배송 s ON ...
```

**SQL 1번으로 끝난다.** 그런데 **컬렉션(`@OneToMany`)에는 함정이 있다.**

```
주문 1건에 상품 3건을 JOIN 하면?

주문id | 주문번호 | 상품명
──────┼────────┼───────
  1   | A-001  | 티셔츠     ← 주문 행이
  1   | A-001  | 바지       ← 3번
  1   | A-001  | 양말       ← 중복된다
```

**주문 100건 × 상품 평균 3건 = 300행**이 돌아온다. 이걸 **카테시안 곱 폭발**이라고 한다. 컬렉션을 둘 이상 fetch join하면 곱셈이 돼서 더 심해진다 (상품 3 × 옵션 4 = 12행).

게다가 **페이징이 깨진다.** `LIMIT 10` 을 걸면 "주문 10건"이 아니라 "조인된 행 10개"가 잘려서 주문 3~4건만 나온다. JPA는 이 경우 **전체를 메모리로 읽어서 자르는데**(`firstResult/maxResults specified with collection fetch; applying in memory` 경고), 데이터가 많으면 그대로 OOM이다.

**그래서 실무 정석은 이렇다.**

```
to-one 관계(@ManyToOne, @OneToOne)  →  fetch join    ✅ 행이 안 늘어난다
to-many 관계(@OneToMany)            →  batch fetch   ✅ 아래 참고
```

화면의 `FETCH_JOIN` 모드가 SQL 2번인 이유가 이거다. **to-one은 조인으로 1번, 컬렉션은 별도 batch로 1번.**

### 2-5. 해법 ② Batch Fetch — 묶어서 IN 절로

```yaml
spring.jpa.properties.hibernate.default_batch_fetch_size: 100
```

이 설정 하나가 동작을 바꾼다.

```
[설정 전]  SELECT * FROM 주문상품 WHERE 주문id = 1
           SELECT * FROM 주문상품 WHERE 주문id = 2
           ... 100번

[설정 후]  SELECT * FROM 주문상품 WHERE 주문id IN (1,2,3,...,100)
           → 1번
```

**N번이 `ceil(N / batch_size)` 번으로 줄어든다.** 화면의 `BATCH_FETCH` 모드가 SQL 8번인 건 배치 크기가 작게 잡혔을 때의 예다.

| | Fetch Join | Batch Fetch |
|---|---|---|
| SQL 횟수 | 1번 | **몇 번** (건수/배치크기) |
| 행 중복 | **있다** (카테시안 곱) | 없다 |
| 페이징 | **컬렉션에서 깨진다** | **정상 동작** ✅ |
| 적용 | 쿼리마다 명시 | **설정 한 줄로 전역** ✅ |

> **실무에서 가장 가성비 좋은 조치는 `default_batch_fetch_size` 설정이다.**
> 코드를 한 줄도 안 고치고 대부분의 N+1이 완화된다.

### 2-6. ⭐ 해법 ③ Projection — 애초에 엔티티를 안 쓴다

이게 가장 근본적이고, 목록 화면에서는 가장 좋은 답이다.

**질문을 바꿔 보자. "목록 화면에 엔티티 전체가 필요한가?"**

```
목록 화면에 실제로 표시하는 것:
  주문번호, 주문일시, 대표상품명, 총액, 상태     ← 5개 컬럼

엔티티로 조회하면 가져오는 것:
  주문 전체 컬럼 + 상품 전체 + 결제 전체 + 배송 전체 + 회원 전체 ...
  그리고 이걸 전부 객체로 만들고 영속성 컨텍스트에 넣는다
```

**필요 없는 걸 잔뜩 읽고 있다.**

```java
// 화면에 필요한 것만 담는 DTO
record 주문목록DTO(Long id, String 주문번호, String 대표상품, int 총액, String 상태) {}

@Query("""
    SELECT new 주문목록DTO(o.id, o.주문번호, ..., o.총액, o.상태)
    FROM 주문 o JOIN o.결제 p
    """)
List<주문목록DTO> 목록조회();
```

**SQL 1번, 필요한 컬럼만, 영속성 컨텍스트 부담 없음.** 화면의 `PROJECTION` 모드가 SQL 1번에 가장 빠른 이유다.

**대가**: 엔티티의 편의(더티 체킹, 연관 탐색)를 못 쓴다. 그래서 **읽기 전용 목록에만** 적합하다.

> ### 정리하면 — 목적에 따라 도구가 다르다
> **수정이 필요한 단건 조회** → 엔티티 + fetch join
> **읽기 전용 목록 화면** → **Projection** ✅
> **어디에나 깔아 두는 안전망** → batch fetch size 설정

### 2-7. 어떻게 발견하나 — 이게 실무에서 제일 중요하다

**N+1은 기능 테스트로 안 잡힌다.** 결과는 정확하니까. 느릴 뿐이다.

```
1. SQL 로그를 켠다
   spring.jpa.show-sql: true
   logging.level.org.hibernate.SQL: DEBUG

2. 더 좋은 방법: 쿼리 횟수를 테스트로 고정한다
   Hibernate Statistics 로 실행된 쿼리 수를 세고,
   "주문 100건 조회에 SQL 3번 이하" 를 단언한다
   → 누가 나중에 lazy 필드를 하나 더 건드리면 테스트가 깨진다 ✅
```

화면의 `BATCH_FETCH` 모드 마지막 스텝이 이걸 가리킨다 — *"SQL 횟수가 데이터 건수에 비례하지 않음을 확인했다."*

> **"성능은 테스트로 고정할 수 없다"는 흔한 오해다.**
> 시간은 환경마다 달라서 고정하기 어렵지만, **쿼리 횟수는 결정적이라 고정할 수 있다.**
> 그리고 N+1은 시간이 아니라 횟수의 문제다.

## 3. 대안 표와 내 선택

| 방법 | SQL 횟수 | 페이징 | 행 중복 | 적용 범위 | 언제 |
|---|---|---|---|---|---|
| 지연 로딩 그대로 | **N+1** | ✅ | 없음 | — | ✗ 목록에서 |
| Fetch Join (to-one) | 1 | ✅ | 없음 | 쿼리별 | ✅ 항상 |
| Fetch Join (컬렉션) | 1 | **❌ 깨진다** | **있다** | 쿼리별 | △ 페이징 없을 때만 |
| **Batch Fetch** | 건수/배치 | ✅ | 없음 | **전역 설정** | ✅ 기본으로 깔기 |
| **Projection** | **1** | ✅ | 없음 | 쿼리별 | ✅ **읽기 전용 목록** |

**내 선택은 조합이다.**

```
기본으로  →  default_batch_fetch_size 를 전역 설정  (안전망)
목록 화면  →  Projection                          (가장 빠름)
단건 상세  →  to-one fetch join + 컬렉션은 batch    (엔티티 필요하니까)
그리고    →  쿼리 횟수를 테스트로 고정              (재발 방지)
```

## 4. 진위 한 줄

**⚠️ 고정 대본이다.** `OperationalTroubleshootingEngine.nPlusOne()` 이 고정 숫자를 반환한다. 301회 / 2회 / 1회 / 8회, 그리고 1,280ms / 145ms / 82ms / 190ms 전부 코드에 적힌 상수다.

**하지만 승격 후보 3편 중 최우선이다.** 이유:
- **면접 빈출 1위 주제**다. 실측이 있으면 무게가 완전히 달라진다
- 구현이 가장 싸다. 이미 있는 PostgreSQL과 엔티티 몇 개면 된다
- Hibernate Statistics로 **실제 SQL 실행 횟수**를 세면 "301회 → 2회"가 진짜 숫자가 된다
- 그리고 **쿼리 횟수는 환경에 안 흔들리는 결정적 값**이라, 실측하기도 재현하기도 쉽다

## 5. 30초 구두 답변

> JPA 연관 관계는 기본이 지연 로딩입니다. 좋은 기본값이에요. 주문 하나 볼 때마다 상품·결제·배송이 다 따라오면 낭비니까요. 그런데 목록에서는 이게 재앙이 됩니다.
>
> 주문 100건을 조회하면 SQL 1번이고, 반복문에서 상품을 건드리는 순간 100번이 더 나갑니다. 결제랑 배송까지 lazy면 301번이고요. 문제는 쿼리 자체는 빠른데 네트워크 왕복이 301번이라는 겁니다. 그리고 이게 데이터 건수에 비례해서 늘어나요. 개발 환경에서는 데이터가 10건이라 안 보이다가 운영에서 어느 날 터집니다.
>
> 해법은 셋인데 목적이 다릅니다. to-one 연관은 fetch join으로 한 번에 가져오고, 컬렉션은 fetch join하면 카테시안 곱으로 행이 중복되고 페이징이 깨지니까 batch fetch로 IN 절에 묶습니다. 목록 화면처럼 읽기 전용이면 아예 엔티티를 안 쓰고 필요한 컬럼만 DTO로 뽑는 projection이 제일 낫고요.
>
> 그리고 제일 중요한 건 발견하는 방법이라고 생각합니다. N+1은 결과가 정확해서 기능 테스트로 안 잡힙니다. 그래서 Hibernate Statistics로 쿼리 횟수를 세서 "100건 조회에 SQL 3번 이하"를 테스트로 고정합니다. 시간은 환경마다 다르지만 쿼리 횟수는 결정적이라 고정할 수 있거든요.

## 6. 꼬리질문과 답

**Q1. 그냥 전부 EAGER로 바꾸면 안 되나요?**

**더 나빠집니다.** EAGER는 N+1을 없애지 않고 **숨깁니다.**

엔티티를 조회할 때마다 연관을 전부 따라가니까, 필요 없는 화면에서도 다 읽습니다. 그리고 연관이 연관을 물면 **한 번의 조회가 테이블 10개를 훑는** 상황이 생깁니다.

게다가 **어디서 쿼리가 나가는지 예측하기 어려워집니다.** LAZY는 "내가 그 필드를 건드렸으니 여기서 쿼리가 나가겠구나"가 보이는데, EAGER는 조회 시점에 전부 나가서 통제가 안 됩니다.

**LAZY를 기본으로 두고 필요할 때 fetch join으로 명시하는 게 정석**입니다. "기본은 최소, 필요하면 명시"요.

**Q2. Fetch join으로 컬렉션을 가져오면서 페이징하면 왜 안 되나요?**

**JOIN 결과의 행 수와 엔티티 수가 다르기 때문**입니다.

주문 1건에 상품 3건이면 JOIN 결과가 3행입니다. 여기에 `LIMIT 10` 을 걸면 DB는 "10행"을 자르는데, 그게 주문 3~4건밖에 안 됩니다. 사용자는 10건을 기대했는데요.

그래서 Hibernate는 이 경우 **`LIMIT` 을 SQL에 안 걸고 전체를 읽어서 메모리에서 자릅니다.** `firstResult/maxResults specified with collection fetch; applying in memory` 라는 경고를 남기고요. 데이터가 많으면 그대로 OOM입니다.

**컬렉션은 fetch join 대신 batch fetch를 쓰면 이 문제가 없습니다.** 주문만 페이징해서 읽고, 그 ID들로 상품을 IN 절로 가져오니까 행 수가 안 꼬입니다.

**Q3. N+1을 어떻게 미리 발견하나요?**

**쿼리 횟수를 테스트로 고정합니다.** 이게 제일 확실합니다.

Hibernate `Statistics` 에서 `getPrepareStatementCount()` 를 읽어서, 테스트 시작 전후 차이를 재고 "주문 100건 조회에 SQL 3회 이하"를 단언합니다. 나중에 누가 lazy 필드를 하나 더 건드리면 **테스트가 바로 깨집니다.**

시간을 단언하면 환경 따라 흔들려서 못 쓰는데, **쿼리 횟수는 결정적이라 안정적인 테스트가 됩니다.**

보조로는 SQL 로그를 켜서 개발 중에 눈으로 보는 것, 그리고 `p6spy` 나 `datasource-proxy` 로 쿼리를 집계하는 방법도 있습니다.

**Q4. Projection을 쓰면 항상 좋은 거 아닌가요?**

**읽기 전용일 때만 좋습니다.**

DTO로 뽑으면 영속성 컨텍스트에 안 들어가서 더티 체킹이 안 됩니다. 값을 바꿔도 DB에 반영이 안 되고요. 연관을 따라 탐색할 수도 없습니다.

그리고 **화면마다 DTO가 늘어납니다.** 목록용, 상세용, 관리자용... 관리 부담이 생깁니다.

그래서 **수정이 필요한 로직에는 엔티티를, 목록 같은 읽기 전용 화면에는 projection을** 쓰는 게 맞습니다. 조회와 수정의 모델을 나누는 건데, 크게 보면 CQRS와 같은 발상입니다.

## 7. 모르면 인정할 선

**여기까지는 자신 있게 답한다**
- 지연 로딩이 왜 좋은 기본값이고 목록에서 왜 재앙이 되는지
- **301 = 1 + 100 + 200** 의 구성
- 쿼리 비용의 대부분이 왕복이라는 것, 그리고 **건수에 비례**한다는 것
- **개발에서 안 보이고 운영에서 터지는 이유**
- fetch join의 카테시안 곱과 **페이징이 깨지는 정확한 이유**
- to-one은 fetch join / to-many는 batch fetch라는 실무 정석
- Projection의 장단과 적용 범위
- **쿼리 횟수를 테스트로 고정하는 방법**과 왜 시간이 아니라 횟수인지

**여기부터는 "안 해봤습니다"라고 말한다**
- 실제 측정 (**화면 숫자는 상수다**) — 승격하면 채울 부분
- `@EntityGraph` 와 fetch join의 실전 비교
- 배치 크기의 최적값 산정 (IN 절이 너무 길면 그것도 느리다)
- 2차 캐시 적용 여부 판단

> ### 자가 점검
> **"301이 어떻게 나오는가"** 를 1 + 100 + 200으로 분해할 수 있는가.
> **"컬렉션 fetch join에 페이징이 왜 깨지나"** 를 행 수와 엔티티 수로 설명할 수 있는가.
> **"N+1을 어떻게 미리 잡나"** 에 쿼리 횟수 테스트로 답할 수 있는가.

# 4. LIKE · tsvector · nori 검색 비교

**시나리오 id**: `search-compare`
**화면**: `/board` 검색 비교
**코드**: `BoardService.compare()`, `CommunityPostRepository`, `BoardOpenSearchService`

## 1. 한 줄 정의

**게시판 10만 건에 같은 검색어를 세 방식으로 던지고**, 결과와 걸린 시간을 같은 화면에서 비교한다.

## 2. 원리 — 왜 이 문제가 생기나

### 2-1. `LIKE '%검색어%'` 는 왜 느린가

가장 먼저 떠올리는 방법이다.

```sql
SELECT * FROM tb_post WHERE title ILIKE '%스프링%' OR content ILIKE '%스프링%';
```

**동작은 한다. 그런데 인덱스를 쓸 수 없다.**

**왜 못 쓰나?** B-tree 인덱스는 **사전(dictionary)** 처럼 동작한다.

```
사전에서 "스프링"을 찾는 건 빠르다 — ㅅ 페이지로 바로 간다
그런데 "중간에 '프링'이 들어가는 모든 단어"를 찾으라면?
→ 사전을 처음부터 끝까지 다 읽어야 한다
```

`'스프링%'` (앞이 고정)이면 인덱스를 쓸 수 있다. `'%스프링%'` (앞이 와일드카드)이면 **못 쓴다.**

```
결과: 10만 행을 전부 읽어서 각각 문자열 포함 여부를 검사한다
     = Sequential Scan (순차 스캔)
     → 데이터가 늘면 선형으로 느려진다
```

**그리고 느린 것보다 더 큰 문제가 있다 — 정확도다.**

```
검색어: "스프링"
매칭됨: "스프링부트 강의"      ✅ 원하는 결과
       "오프스프링 앨범"       ❌ 단어 중간에 우연히 포함
       "마우스프링클러"        ❌ 완전히 무관

검색어: "검색을"  (조사가 붙음)
매칭 안 됨: "검색 최적화"      ❌ 원하는 건데 못 찾음
```

**문자열이 포함되는지만 볼 뿐 "단어"라는 개념이 없다.**

### 2-2. ⭐ tsvector — 미리 단어로 쪼개 둔다

PostgreSQL의 전문 검색(Full Text Search)이다. 핵심 발상은 이것이다.

> **검색할 때 문서를 훑지 말고, 미리 단어로 쪼개서 색인을 만들어 둔다.**

```
[원문]      "스프링 부트로 검색을 최적화했다"
                ↓ 저장 시점에 미리 쪼갠다 (to_tsvector)
[tsvector]  '스프링':1 '부트로':2 '검색을':3 '최적화했다':4
                ↓ GIN 인덱스로 색인
[검색]      '검색을' 이라는 단어를 가진 문서 목록 → 즉시 조회
```

**이게 역색인(inverted index)이다.** 보통 색인은 "문서 → 단어"인데, 뒤집어서 **"단어 → 문서 목록"** 으로 만든다. 책 뒤의 "찾아보기"와 같다.

```
[일반 색인]  문서1 → [스프링, 부트, 검색]
[역색인]     스프링 → [문서1, 문서5, 문서9]     ← 단어로 문서를 즉시 찾는다
            검색   → [문서1, 문서3]
```

**이 프로젝트의 실제 쿼리:**

```sql
WHERE tsv @@ plainto_tsquery('simple', :q)
```

- `tsv` : 미리 만들어 둔 tsvector 컬럼 (GIN 인덱스가 걸려 있다)
- `@@` : "이 tsvector가 이 조건과 매칭되나" 연산자
- `plainto_tsquery` : 사용자 입력을 안전하게 검색 조건으로 변환 (특수문자 등을 처리해서 **SQL 인젝션 걱정 없이** 쓸 수 있다)

**속도는 극적으로 빨라진다.** 순차 스캔이 사라지고 색인 조회가 된다.

### 2-3. ⭐⭐ 그런데 한국어에서 tsvector의 한계가 드러난다

**이 프로젝트가 쓰는 설정이 `'simple'` 이다.** 이게 결정적이다.

```sql
plainto_tsquery('simple', '검색')
```

`'simple'` 은 **공백으로 자르고 소문자로 바꾸는 것 말고는 아무것도 안 한다.** 형태소 분석도, 어간 추출도 없다.

**영어라면 `'english'` 설정이 있어서 어느 정도 된다.**

```
'english' 설정:
  "running" → "run"      (어간 추출)
  "searched" → "search"
  → 활용형이 달라도 매칭된다
```

**한국어는 PostgreSQL 기본 설치에 사전이 없다.** 그래서 `'simple'` 을 쓸 수밖에 없고, 이런 일이 생긴다.

```
문서: "검색을 최적화했다"
tsvector('simple'): '검색을':1 '최적화했다':2      ← 조사가 붙은 채로 저장된다

검색어: "검색"
→ '검색' ≠ '검색을'  →  못 찾는다  ❌
```

> ### 한국어의 구조적 문제
> 한국어는 **교착어**라서 단어 뒤에 조사·어미가 계속 붙는다.
> **검색**, 검색**이**, 검색**을**, 검색**은**, 검색**에서**, 검색**했다** ...
> 공백으로만 자르면 이게 **전부 다른 단어**가 된다.
> 영어(`search`, `searches`, `searched` — 어간이 명확)와는 난이도가 다르다.

### 2-4. nori — 형태소 분석기

OpenSearch(Elasticsearch)의 한국어 형태소 분석 플러그인이다. **단어를 문법적으로 분해한다.**

```
"검색을 최적화했다"
     ↓ nori_tokenizer
"검색" (명사) + "을" (조사) + "최적화" (명사) + "하" (동사) + "었" (어미) + "다" (어미)
     ↓ nori_part_of_speech 필터 — 조사·어미를 버린다
"검색", "최적화"                                  ← 의미 있는 것만 남는다
```

**이제 "검색"으로 검색하면 "검색을 최적화했다"가 찾아진다.** ✅

**이 프로젝트의 실제 설정** (`BoardOpenSearchService`):

```json
"analyzer": {
  "korean_nori": {
    "tokenizer": "nori_tokenizer",
    "filter": ["lowercase", "nori_part_of_speech"]
  }
},
"mappings": {
  "title":   { "type": "text", "analyzer": "korean_nori" },
  "content": { "type": "text", "analyzer": "korean_nori" }
}
```

**같은 분석기가 색인할 때와 검색할 때 양쪽에 적용된다.** 이게 중요하다 — 저장할 때 "검색/최적화"로 쪼갰으면 검색어도 같은 방식으로 쪼개야 매칭된다.

### 2-5. 세 방식 정리

| | **LIKE** | **tsvector (GIN)** | **OpenSearch + nori** |
|---|---|---|---|
| 원리 | 전체를 훑으며 문자열 포함 검사 | 미리 쪼갠 단어의 역색인 | 형태소 분석 후 역색인 |
| 인덱스 | ❌ 못 씀 (`%앞%`) | ✅ GIN | ✅ 역색인 |
| 속도 | **데이터 비례로 느려짐** | 빠름 | 빠름 |
| "검색" ↔ "검색을" | ❌ | ❌ (`simple` 설정) | ✅ **찾는다** |
| 부분 문자열 | ✅ ("프링"으로 "스프링" 찾음) | ❌ | ❌ |
| 오탐 | **많음** ("오프스프링") | 적음 | 적음 |
| 관련도 순위 | ❌ 없음 | △ `ts_rank` | ✅ **BM25 기본 제공** |
| 오타 보정 | ❌ | ❌ | ✅ fuzzy |
| 인프라 | 없음 | 없음 (PG 내장) | **별도 클러스터 필요** |

> ### 그래서 뭘 써야 하나 — 이게 면접의 핵심 질문이다
> **"OpenSearch가 제일 좋으니 항상 쓰자"가 정답이 아니다.**
> 별도 클러스터를 띄우고, 색인을 동기화하고, 장애에 대응해야 한다. **운영 비용이 붙는다.**
>
> - **데이터 수천 건 + 단순 검색** → `LIKE` 로 충분하다. 인프라 0
> - **수만~수십만 건 + 영어 위주 / 정확한 단어 매칭** → **tsvector.** PostgreSQL 안에서 끝난다
> - **한국어 자연어 검색 + 관련도 순위 + 오타 보정** → **OpenSearch + nori**
>
> **"이 화면이 그 판단 근거를 눈으로 보여준다"** 가 이 시나리오의 진짜 가치다.

### 2-6. 색인 동기화 — OpenSearch를 쓰면 따라오는 숙제

**원본은 PostgreSQL이고 OpenSearch는 사본이다.** 둘이 어긋나면 검색 결과가 거짓말을 한다.

**이 프로젝트에서 실제로 이 문제를 겪었다.** 위키 글을 SQL로 직접 지우면:

```
PostgreSQL:  행 삭제됨 ✅
OpenSearch:  문서 그대로 남음 ❌  ← 애플리케이션 이벤트가 안 돌았으니까

결과: 검색하면 지운 글이 계속 나온다 (유령 문서)
```

그리고 `reindex` 엔드포인트는 **upsert만 해서 이걸 못 고친다.** 없는 걸 지우진 않으니까. 그래서 **삭제는 양쪽을 명시적으로 지워야 한다.**

> **02의 이중 쓰기 문제가 여기서 또 나온다.** DB와 검색 엔진은 서로 다른 두 시스템이고,
> 원자적으로 쓸 수 없다. 정석은 **Outbox로 색인 이벤트를 내보내는 것**이다.

## 3. 대안 표와 내 선택

| 접근 | 인프라 | 한국어 | 언제 |
|---|---|---|---|
| LIKE | 없음 | ❌ | 수천 건 이하, 단순 필터 |
| **tsvector** | 없음 (PG 내장) | △ (`simple` 한계) | 수만~수십만, 정확 매칭 |
| **OpenSearch + nori** | **별도 클러스터** | ✅ | 한국어 자연어, 순위, 오타 |

**이 프로젝트의 선택: 셋 다 두고 비교한다.**

포트폴리오 목적이라 그렇지만, 실무라면 **하나를 고르는 게 맞다.** 그리고 그 판단 기준을 말할 수 있는 게 실력이다.

**추가로 이 프로젝트는 폴백을 둔다** — OpenSearch가 죽으면 tsvector로 내려간다. 검색이 아예 안 되는 것보다 낫고, **인프라 의존을 하나 늘렸을 때 그 실패를 어떻게 다룰지 정해 둔 것**이다.

## 4. 진위 한 줄

**✅ 실제로 돌아간다. 이 그룹에서 유일하다.**

- 게시판에 **실제로 10만 건**이 들어 있다
- `BoardService.compare()` 가 **같은 검색어로 세 쿼리를 진짜로 던지고** `timed()` 로 각각 시간을 잰다
- LIKE는 `ILIKE '%q%'`, tsvector는 `plainto_tsquery('simple', :q)`, OpenSearch는 nori 분석기로 실제 조회한다
- 화면의 시간과 건수는 **매번 다르다. 실측이기 때문이다**

> **이게 이 편의 가장 큰 가치다.** 다른 20편과 달리 **숫자를 주장해도 되는 유일한 편**이다.
> 면접에서 이 화면을 켜 놓고 검색어를 바꿔 가며 보여줄 수 있다.

## 5. 30초 구두 답변

> 게시판 10만 건에 같은 검색어를 세 방식으로 던지고 시간을 재는 화면입니다. 이건 실제로 도는 코드고 숫자도 실측입니다.
>
> LIKE는 `%검색어%` 라서 인덱스를 못 씁니다. B-tree는 앞에서부터 비교하는 구조인데 앞이 와일드카드면 사전을 처음부터 끝까지 읽는 것과 같거든요. 그래서 10만 행을 전부 훑습니다. 게다가 단어 개념이 없어서 "스프링"으로 검색하면 "오프스프링"도 걸립니다.
>
> tsvector는 저장할 때 미리 단어로 쪼개서 역색인을 만들어 둡니다. 단어에서 문서를 바로 찾으니까 훨씬 빠릅니다. 다만 저희는 `simple` 설정을 쓰는데, PostgreSQL에 한국어 사전이 없어서 그렇습니다. 공백으로만 잘라서 "검색"과 "검색을"이 다른 단어가 됩니다. 한국어는 교착어라 조사가 계속 붙는데 그걸 못 떼는 거죠.
>
> nori는 형태소 분석기라 "검색을"을 "검색"이라는 명사와 "을"이라는 조사로 분해하고 조사를 버립니다. 그래서 "검색"으로 검색해도 찾힙니다. 여기에 BM25 관련도 순위랑 오타 보정까지 붙고요.
>
> 다만 OpenSearch는 별도 클러스터를 띄우고 색인 동기화를 관리해야 해서, 수천 건 규모면 LIKE로 충분하고 수만 건에 영어 위주면 tsvector가 낫다고 봅니다. 한국어 자연어 검색이 핵심이면 그때 nori를 씁니다.

## 6. 꼬리질문과 답

**Q1. `LIKE '검색어%'` 는 인덱스를 쓸 수 있나요?**

**쓸 수 있습니다.** 앞이 고정되어 있으면 B-tree가 범위 스캔을 할 수 있거든요. 그래서 **자동완성 같은 접두어 검색에는 LIKE도 충분히 빠릅니다.**

이 프로젝트에도 그렇게 쓰는 곳이 있습니다. `suggestTitlePrefix` 가 `title ilike (:q || '%')` 로 되어 있어서 제목 자동완성에 쓰입니다. **문제가 되는 건 `%` 가 앞에 붙는 경우뿐**입니다.

**Q2. PostgreSQL로 한국어 형태소 분석은 못 하나요?**

**확장을 붙이면 됩니다.** `pg_bigm` 이나 mecab 기반 확장 같은 게 있습니다.

다만 **설치와 유지보수 부담**이 생기고, 관리형 DB 서비스에서는 확장을 못 붙이는 경우도 많습니다. 그리고 그 정도까지 갈 거면 검색 전용 엔진을 쓰는 게 기능(관련도 순위, 오타 보정, 하이라이팅)까지 얻어서 낫다고 봅니다.

**중간 대안으로 n-gram**이 있습니다. "검색을"을 "검", "검색", "색을"처럼 글자 단위로 쪼개서 색인하는 방식인데, 형태소 분석 없이도 부분 매칭이 됩니다. 대신 색인이 커지고 오탐이 늘어납니다.

**Q3. OpenSearch와 DB 데이터가 어긋나면요?**

**실제로 겪은 문제입니다.** 위키 글을 SQL로 직접 지웠더니 PostgreSQL에서는 사라졌는데 OpenSearch 색인에는 그대로 남았습니다. 애플리케이션을 거치지 않아서 색인 갱신 이벤트가 안 돈 거죠. 검색하면 지운 글이 계속 나오는 **유령 문서** 상태가 됩니다.

그리고 `reindex` 엔드포인트는 upsert만 해서 이걸 못 고칩니다. 없는 문서를 지우진 않으니까요. 그래서 **삭제는 PostgreSQL과 OpenSearch 양쪽을 명시적으로 지워야** 합니다.

근본적으로는 **02에서 본 이중 쓰기 문제**입니다. DB와 검색 엔진은 서로 다른 시스템이라 원자적으로 못 씁니다. 정석은 Outbox 패턴으로 색인 이벤트를 내보내는 거고요.

**Q4. 관련도 순위는 어떻게 매겨지나요?**

**BM25라는 알고리즘**이 기본입니다. 직관적으로는 세 가지를 봅니다.

첫째, **그 단어가 문서에 몇 번 나오나** (많이 나오면 더 관련 있다). 둘째, **그 단어가 전체 문서 중 몇 개에 나오나** (희귀한 단어일수록 가치가 높다 — "그리고"가 매칭되는 건 의미 없고 "OpenSearch"가 매칭되면 강한 신호다). 셋째, **문서 길이** (긴 문서에 한 번 나오는 것보다 짧은 문서에 한 번 나오는 게 더 관련 있다).

tsvector에도 `ts_rank` 가 있긴 한데 훨씬 단순하고, 제목에 가중치를 주는 식의 세밀한 조정은 OpenSearch가 훨씬 편합니다.

## 7. 모르면 인정할 선

**여기까지는 자신 있게 답한다**
- `%앞%` 이 왜 인덱스를 못 쓰는지 (**사전 비유로**)
- 역색인이 뭐고 왜 빠른지
- **`'simple'` 설정의 한계와 한국어가 교착어라는 구조적 이유**
- nori 형태소 분석이 조사를 떼는 방식
- **셋 중 뭘 고를지의 판단 기준** (데이터 규모 × 언어 × 필요 기능 × 운영 비용)
- 색인 동기화가 이중 쓰기 문제이고, 유령 문서를 실제로 겪었다는 것
- BM25가 보는 세 가지

**여기부터는 "안 해봤습니다"라고 말한다**
- nori 사용자 사전 튜닝 (고유명사·신조어 등록)
- 색인 설계 최적화 (샤드 수, 매핑 세부, 리프레시 주기)
- BM25 파라미터 조정
- Outbox 기반 색인 동기화 실제 구현 (지금은 애플리케이션 이벤트 방식)

> ### 자가 점검
> **"`%검색어%` 가 왜 인덱스를 못 쓰나"** 를 사전 비유로 설명할 수 있는가.
> **"한국어에서 tsvector가 왜 약한가"** 를 교착어와 `simple` 설정으로 답할 수 있는가.
> **"그래서 뭘 써야 하나"** 에 규모와 운영 비용을 넣어 답할 수 있는가.

# 5. 이미지 업로드 최적화

**시나리오 id**: `image-upload-optimization`
**모드**: `UNRESTRICTED` / `REJECT_OVERSIZE` / `SYNC_OPTIMIZE` / `ASYNC_OPTIMIZE` / `ASYNC_COMPLETE`

## 1. 한 줄 정의

**12MB 원본 사진을 그대로 저장하고 그대로 내려보내면** 저장 비용과 전송 비용이 계속 나간다. 어디서 어떻게 줄일 것인가.

## 2. 원리 — 왜 이 문제가 생기나

### 2-1. 비용이 한 번이 아니라 계속 나간다

```
사용자가 아이폰 사진 1장을 올린다:  12MB, 6000×4000 픽셀

[저장 비용]  12MB × 사용자 수 × 사진 수  →  한 번 쌓이면 계속 나간다
[전송 비용]  목록 화면을 볼 때마다 12MB를 내려보낸다  ←  ⭐ 이게 진짜 문제
```

**`UNRESTRICTED` 모드의 마지막 스텝이 이거다.**

```
step("PAGE_DELIVERED", "Browser", "REJECTED", "목록 화면에서도 12MB 원본을 내려받았다.")
```

**목록에 20개 상품이 있으면 240MB를 내려받는다.** 화면에서는 200×200 픽셀로 줄여서 보여주면서. 모바일 데이터로는 재앙이고, CDN 비용은 전송량 기준이라 돈이 그대로 나간다.

> **핵심**: 저장은 한 번이지만 **전송은 조회할 때마다**다. 그래서 **전송 최적화가 저장 최적화보다 훨씬 중요하다.**

### 2-2. ⭐ 검증은 저장 "전에" 해야 한다

`REJECT_OVERSIZE` 모드의 마지막 스텝을 보자.

```
step("UPLOAD_REJECTED", "MinIO write 전에 413 정책 오류를 반환했다.")
```

**"MinIO write 전에"가 핵심이다.** 저장한 뒤에 검사해서 지우면 이미 비용을 다 쓴 것이다.

**그리고 무엇을 검사할 것인가가 중요하다.**

```
❌ 확장자 검사        "photo.jpg" → jpg니까 이미지겠지
                      → 공격자가 파일 이름만 바꾸면 통과한다

❌ Content-Type 헤더  "image/jpeg" 라고 하네
                      → 요청 헤더는 클라이언트가 마음대로 쓴다

✅ Magic Bytes 검사   파일의 첫 몇 바이트를 실제로 읽는다
                      JPEG: FF D8 FF
                      PNG:  89 50 4E 47
                      → 내용 자체를 보므로 속일 수 없다

✅ 실제 decode 시도   진짜로 이미지로 열어 본다
                      → 열리지 않으면 이미지가 아니다
```

> **원칙**: **클라이언트가 보낸 메타데이터는 전부 거짓일 수 있다.**
> 파일 이름, 확장자, `Content-Type`, `Content-Length` 전부.
> 서버는 **실제 바이트**를 봐야 한다.

**`Content-Length` 도 마찬가지다.** 화면 스텝이 *"Content-Length와 실제 stream byte 상한을 함께 확인했다"* 라고 되어 있는 이유가 이거다. 헤더에 1MB라고 써 놓고 실제로 100MB를 흘려보낼 수 있으니, **읽으면서도 상한을 세야 한다.**

### 2-3. 픽셀 수를 따로 검사하는 이유 — Decompression Bomb

용량만 검사하면 뚫리는 공격이 있다.

```
파일 크기: 1MB          ← 용량 제한 통과 ✅
이미지 크기: 30000 × 30000 픽셀

이걸 메모리에 decode하면?
  30000 × 30000 × 4 bytes(RGBA) = 3.6GB      💀 OOM
```

**압축된 상태로는 작지만 펼치면 거대해진다.** 이걸 **압축 폭탄(decompression bomb)** 이라고 한다. 단색 이미지는 압축률이 극도로 높아서 이게 가능하다.

그래서 **decode 전에 헤더만 읽어서 가로×세로를 먼저 확인**하고, 상한을 넘으면 아예 decode를 시도하지 않는다.

### 2-4. EXIF 제거 — 성능이 아니라 개인정보 문제

```
아이폰 사진의 EXIF 메타데이터:
  - GPS 좌표      ← 📍 촬영 장소가 그대로 들어 있다
  - 촬영 일시
  - 기기 모델, 일련번호
  - 소프트웨어 버전
```

**사용자가 집에서 찍은 중고거래 사진을 올리면 집 주소가 노출된다.** 실제로 사고가 여러 번 났던 문제다.

> **이건 최적화 항목이 아니라 개인정보 보호 항목이다.** 용량이 줄어드는 건 부수 효과고.
> 변환 과정에서 자연스럽게 제거되므로 **"변환한다"는 결정 자체가 개인정보 보호가 된다.**

### 2-5. Variant — 용도별로 다른 크기를 만든다

```
원본:      6000×4000, 12MB     → 비공개 보관 (또는 정책에 따라 삭제)
display:   최대 1920px, WebP    → 상세 화면용   약 1.8MB
thumbnail: 480px, WebP          → 목록 화면용   약 50KB
```

**목록에서는 thumbnail만 내려받는다.** 20개 상품이면 240MB → 1MB. **240배 차이**다.

**WebP를 쓰는 이유**: 같은 화질에서 JPEG보다 25~35% 작다. 브라우저 지원도 이제 충분하다.

**`immutable key` 로 저장하는 이유**: 파일 이름에 내용 해시를 넣으면 (`abc123.webp`) 내용이 바뀌면 이름도 바뀐다. 그러면 **캐시를 영구(`Cache-Control: immutable`)로 걸 수 있다.** 같은 이름의 파일이 바뀌는 일이 없으니까. CDN 캐시 무효화 고민이 사라진다.

### 2-6. ⭐ 동기 변환 vs 비동기 변환

이게 이 시나리오의 마지막 설계 결정이다.

```
[동기 — SYNC_OPTIMIZE]
  업로드 요청 → 검증 → 변환(2초) → 저장 → "완료!" 응답
  ✅ 응답이 오면 이미 쓸 수 있는 상태
  ❌ 사용자가 2초 기다린다
  ❌ 변환이 요청 스레드를 2초간 점유한다  ← 트래픽이 몰리면 스레드 고갈

[비동기 — ASYNC_OPTIMIZE → ASYNC_COMPLETE]
  업로드 요청 → 검증 → 원본을 임시 격리 저장 → 변환 job 발행 → "접수됨" 즉시 응답
                                                    ↓
                                        Worker가 변환 → READY 로 상태 갱신
  ✅ 응답이 빠르다. 스레드를 안 묶는다
  ❌ 변환 완료 전 상태(PROCESSING)를 화면이 다뤄야 한다  ← placeholder 필요
```

**1편(트래픽 폭주)의 "버리기 vs 미루기"와 정확히 같은 구조다.** 그리고 여기서도 **기술 결정이 아니라 제품 결정**이다.

- 프로필 사진 1장 → 동기가 낫다. 2초 기다리고 바로 보는 게 자연스럽다
- 상품 사진 20장 일괄 업로드 → 비동기가 맞다. 40초를 기다릴 수는 없다

**비동기를 택하면 따라오는 것들:**

| 필요한 것 | 왜 |
|---|---|
| 상태 필드 (`PROCESSING` / `READY` / `FAILED`) | 화면이 "아직 변환 중"을 표현해야 한다 |
| placeholder 이미지 | 변환 전에 보여줄 것 |
| **job 멱등성** (checksum 확인) | 큐는 at-least-once다. **02에서 배운 그것** |
| 원본 lifecycle 정책 | 임시 원본을 언제 지울 것인가 |
| 실패 처리 | 변환 실패한 자산을 어떻게 할 것인가 |

`ASYNC_COMPLETE` 모드의 첫 스텝이 *"checksum 기준으로 중복 job을 확인했다"* 인 게 이 때문이다. **Kafka DLQ 편의 consumer 멱등성이 여기서 그대로 재등장한다.**

## 3. 대안 표와 내 선택

| 접근 | 저장 | 전송 | 응답 시간 | 복잡도 |
|---|---|---|---|---|
| 무제한 원본 | **최대** | **최대** | 빠름 | 최소 |
| 크기 제한만 | 중간 | 중간 | 빠름 | 낮음 |
| **동기 변환** | 낮음 | **낮음** | **느림** | 중간 |
| **비동기 변환** | 낮음 | **낮음** | **빠름** | **높음** |

**내 판단: 검증은 무조건, 변환 방식은 업로드 패턴에 따라.**

```
반드시 (예외 없음)
  → magic bytes + 픽셀 상한 + 실제 크기 검사, 전부 저장 전에
  → EXIF 제거 (개인정보)
  → variant 생성 (전송 비용이 반복 비용이니까)

선택
  → 단건 업로드      : 동기
  → 대량/큰 파일     : 비동기 + 상태 관리
```

## 4. 진위 한 줄

**⚠️ 고정 대본이다. 그리고 사이트가 이미 이걸 밝히고 있다.**

이 편은 21편 중 **사이트가 스스로 "정책 비교 모델"이라고 배지를 단** 편이고, 회고 문구에도 이렇게 적혀 있다.

> "현재 수치는 고정 입력 정책 모델이며 실제 이미지 decoder나 MinIO에 파일을 쓰지 않는다."

**정직하게 표시된 편이다.** 12MB → 1.8MB 같은 숫자는 코드에 적힌 상수다.

**다만 이 프로젝트에 실제 이미지 자산 시스템은 있다.** 위키/블로그 관리자 화면의 이미지 업로드가 MinIO를 실제로 쓰고, `tb_article_asset` 에 `TEMP` / `ATTACHED` 상태를 관리한다. 그래서 이렇게 말할 수 있다.

> "이 화면은 정책 비교 모델이고 실제 decoder는 안 붙였습니다. 다만 위키 이미지 자산은 실제로 MinIO에 저장하고 TEMP/ATTACHED 상태를 관리하고 있어서, 자산 lifecycle 부분은 실제 구현 경험이 있습니다."

## 5. 30초 구두 답변

> 이미지에서 진짜 비용은 저장이 아니라 전송입니다. 저장은 한 번이지만 전송은 조회할 때마다 나가거든요. 12MB 원본을 목록 화면에서도 그대로 내려보내면 상품 20개에 240MB입니다. 화면에서는 200픽셀로 줄여서 보여주면서요.
>
> 그래서 용도별 variant를 만듭니다. 목록용 480px 썸네일이 50KB 정도니까 240MB가 1MB가 됩니다.
>
> 검증은 저장 전에 해야 하고, 무엇을 검증하느냐가 중요합니다. 확장자나 Content-Type 헤더는 클라이언트가 마음대로 쓸 수 있어서 못 믿습니다. magic bytes를 실제로 읽어서 확인해야 하고요. 그리고 용량만 보면 압축 폭탄에 뚫립니다. 1MB짜리 파일이 3만×3만 픽셀이면 decode할 때 3.6GB를 먹어서 OOM이 나거든요. 그래서 헤더에서 픽셀 수를 먼저 확인합니다.
>
> EXIF 제거는 성능이 아니라 개인정보 항목입니다. 아이폰 사진에는 GPS 좌표가 들어 있어서 집에서 찍은 중고거래 사진을 올리면 집 주소가 노출됩니다.
>
> 변환을 동기로 할지 비동기로 할지는 업로드 패턴에 따라 다릅니다. 단건이면 2초 기다리는 게 자연스럽고, 20장 일괄이면 비동기로 가야 하는데 그러면 PROCESSING 상태 관리랑 job 멱등성이 따라옵니다.

## 6. 꼬리질문과 답

**Q1. 확장자 검사로는 왜 부족한가요?**

**파일 이름은 클라이언트가 정하는 값이라 아무 의미가 없습니다.** 악성 스크립트 파일을 `photo.jpg` 로 바꿔서 올리면 확장자 검사는 통과합니다.

`Content-Type` 헤더도 마찬가지로 요청에 클라이언트가 직접 쓰는 값입니다.

**믿을 수 있는 건 파일 내용 자체뿐**입니다. 그래서 첫 몇 바이트(magic bytes)를 읽어서 실제 포맷을 확인하고, 더 확실하게는 실제로 decode를 시도해 봅니다. 안 열리면 이미지가 아닌 거죠.

**Q2. 원본은 지워야 하나요, 보관해야 하나요?**

**도메인에 따라 다릅니다.**

상품 이미지처럼 나중에 다른 크기가 필요할 수 있으면 원본을 보관합니다. 대신 **비공개 경로**에 두고 공개 URL로는 접근 못 하게 합니다.

증빙 서류처럼 원본 자체가 법적 의미를 가지면 반드시 보관하고 보존 기간도 지켜야 합니다.

프로필 사진처럼 재생성할 일이 없으면 **variant만 남기고 원본을 지우는 게** 저장 비용상 낫습니다.

중요한 건 **정책을 명시적으로 정해 두는 것**입니다. 안 정하면 기본값이 "다 보관"이 되고, 몇 년 뒤 저장 비용이 문제가 됩니다.

**Q3. 비동기로 하면 사용자가 뭘 보나요?**

**placeholder를 보여주고 상태가 바뀌면 교체합니다.**

업로드 응답에 asset ID와 placeholder를 주고, 화면은 그 ID로 상태를 폴링하거나 서버 푸시로 완료를 받습니다. 완료되면 실제 이미지 URL로 바꿔치기하고요.

여기서 놓치기 쉬운 게 **실패 처리**입니다. 변환이 실패하면 그 자산은 영원히 PROCESSING으로 남습니다. 그래서 **타임아웃과 FAILED 상태**가 필요하고, 실패한 자산을 정리하거나 재시도하는 절차도 있어야 합니다. 02의 DLQ와 같은 이야기입니다.

**Q4. 변환 job이 두 번 실행되면요?**

**02에서 배운 그대로입니다.** 큐는 at-least-once라 같은 job이 두 번 올 수 있습니다.

그래서 **원본 checksum으로 멱등성을 확보**합니다. 이미 그 checksum으로 variant가 만들어져 있으면 다시 안 만들고 기존 걸 씁니다. 화면 스텝에 *"checksum 기준으로 중복 job을 확인했다"* 라고 되어 있는 게 이겁니다.

**변환 자체는 결정적**이라 두 번 해도 결과가 같긴 합니다. 다만 CPU를 두 배로 쓰고, 상태를 두 번 갱신하면서 경합이 생길 수 있어서 막는 게 맞습니다.

## 7. 모르면 인정할 선

**여기까지는 자신 있게 답한다**
- **전송 비용이 반복 비용**이라 저장보다 중요하다는 것
- 검증을 저장 전에 해야 하는 이유
- **클라이언트 메타데이터를 믿으면 안 되는 이유**와 magic bytes
- **압축 폭탄**과 픽셀 수를 따로 검사하는 이유
- EXIF가 개인정보 문제라는 것
- variant와 immutable key로 캐시를 영구화하는 원리
- 동기/비동기 선택 기준과 비동기에 따라오는 것들 (상태, placeholder, job 멱등성)

**여기부터는 "안 해봤습니다"라고 말한다**
- 실제 이미지 처리 라이브러리 사용 (**이 화면은 decoder를 안 붙였다**)
- decode를 별도 프로세스/샌드박스에서 돌리는 격리
- worker의 CPU·메모리 limit 설정과 변환 큐 튜닝
- orphan 자산(참조 없는 파일) 정리 배치
- CDN 캐시 정책 실제 구성

> ### 자가 점검
> **"확장자 검사로 왜 부족한가"** 를 답할 수 있는가.
> **"압축 폭탄"** 이 뭔지 숫자로 설명할 수 있는가.
> **"EXIF를 왜 지우나"** 에 개인정보로 답할 수 있는가.

# 마무리 — 이 그룹을 하나로 묶는 답변

면접에서 **"성능 개선 경험이 있나요"** 가 나오면 이렇게 묶는다.

> 성능 문제를 볼 때 저는 세 가지를 먼저 묻습니다. **무엇이 유한한가, 누가 얼마나 오래 쥐고 있는가, 넘칠 때 무엇을 포기할 것인가.**
>
> **무엇이 유한한가** — 무한한 자원은 없고, 병목은 항상 가장 먼저 바닥나는 것입니다. DB 커넥션 20개일 수도, 초당 처리량 220건일 수도 있습니다. 여기서 흔한 실수가 커넥션 풀을 늘리는 건데, PostgreSQL은 커넥션마다 프로세스를 띄워서 병목을 더 나쁜 곳으로 옮길 뿐입니다.
>
> **누가 얼마나 오래 쥐는가** — 성능 문제의 대부분은 일을 많이 해서가 아니라 자원을 오래 쥐고 있어서 생깁니다. 특히 **일하지 않으면서 쥐고 있는 경우**가 최악이고요. 트랜잭션 안에서 외부 API를 3초 기다리면 실제 DB 작업은 100ms인데 커넥션 점유는 3.1초입니다. 97%를 놀면서 쥐고 있는 거죠. 그래서 경계를 분리해서 외부 호출을 트랜잭션 밖으로 뺍니다. 대신 원자성을 잃으니까 보상이 필요해지고요.
>
> **넘칠 때 무엇을 포기하는가** — 입력이 처리 능력을 넘으면 버리거나 미루거나, 아니면 아무것도 안 해서 다 같이 죽거나입니다. 아무것도 정하지 않으면 세 번째가 기본값이 돼서, 감당 가능했던 요청까지 다 실패합니다.
>
> 그리고 **비용이 데이터에 비례하는지**를 봅니다. N+1은 쿼리 횟수가 건수에 비례해서 개발 환경에서는 안 보이다가 운영에서 터집니다. 그래서 시간이 아니라 **쿼리 횟수를 테스트로 고정**합니다. 시간은 환경마다 다르지만 횟수는 결정적이거든요.
>
> 실제로 측정해서 비교한 건 검색 부분입니다. 게시판 10만 건에 LIKE, tsvector, OpenSearch nori를 같은 검색어로 던지고 시간을 재는데, 이건 실측입니다. 나머지 화면 숫자들은 고정 입력 모델이고요.

## 왜 이 답변이 강한가

1. **세 질문이라는 틀**이 있어서 어떤 성능 문제가 나와도 대입할 수 있다
2. **"놀면서 쥐고 있다"** 는 표현이 커넥션 풀 문제의 본질을 한 방에 전달한다

4. **"시간이 아니라 횟수"** 는 성능을 테스트로 다뤄 본 사람의 언어다
5. 마지막에 **뭐가 실측이고 뭐가 모델인지 스스로 구분**한다
