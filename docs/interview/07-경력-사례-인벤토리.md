# 운영의 그림자 노동: 경력 사례 인벤토리

## 목적

이 문서는 운영 중 반복해서 수행했지만 이력서의 기능 목록에서는 빠지기 쉬운 업무를 면접 사례로 복원하기 위한 기준 자료다.
실제로 수행한 회사 경험은 숨기지 않고 적극적으로 공개 사례의 출발점으로 사용한다. 다만 회사의 코드·데이터·식별정보를
복제하지 않고, 당시 경험과 jay-wiki에서 다시 만든 리허설의 경계를 함께 밝힌다.

## 세 가지 보관 위치

| 위치 | 넣는 내용 | 공개 기준 |
|---|---|---|
| 실무 사례 허브 | 익명화된 경력 사례와 실행 가능한 운영 리허설 | 당시 문제·담당·한계 또는 현재 실행 증거를 구분해 표시 |
| 공개 위키 | 문제, 판단, 절차와 회고를 익명화한 기술 사례 | 회사·고객·금액·계정·SQL 등 민감정보 제거 후 |
| 이 문서 | 실제 경력의 사실·담당 범위와 아직 확인되지 않은 후보 | 확인된 항목은 익명화해 위키·시나리오로 승격 |

사례 수를 늘리는 것 자체가 목적은 아니다. 실행기가 없어도 실제 문제·대응·회고가 분명하면 narrative 사례로 공개하고,
재현 가치가 큰 항목만 이후 실행 모드와 영속 증거를 추가한다.

## 기존 프로젝트와의 중복 조사

표의 `현재 겹침`은 **jay-wiki 저장소에서 확인되는 재구현 근거**다. 실제 회사 경험은 별도로 확인하되, 확인된 경험은
`실무에서 겪은 문제 → 당시 대응 → 현재 재구성 → 지금 보완할 점` 순서로 공개한다.

| 후보 경험 | 현재 겹침 | 판단 | 권장 처리 |
|---|---|---|---|
| 운영 데이터 직접 정정 | 위키 revision·rollback과 관리자 변경 이력 | 사례 공개 | `조회 → snapshot → 승인 → 조건부 수정 → 검증 → 감사` narrative를 추가했다. 실제 격리 DB 실행기는 후속이다. |
| 엑셀 다운로드·업로드 | 구현 근거 없음 | 사례 공개 | streaming export, staging validation과 partial failure 절차를 공개했다. 건수·memory benchmark는 후속이다. |
| 반복 통계·지표 추출 | Prometheus 운영 지표와 검색 비교 화면 | 사례 공개 | `일회성 SQL → 지표 정의 → 화면·export → 대조`를 업무 통계 사례로 추가했다. |
| 알림톡·SMS·이메일 | Kafka notification consumer의 retry·DLQ, Alertmanager Telegram | 사례 공개 | provider 실패·중복 발송 방지·재처리 사례를 추가하고 Kafka 리허설로 연결했다. 실제 SMS 연동이라고 표현하지 않는다. |
| 이벤트·프로모션 | 쿠폰 경합 정책 모델 | 부분 중복 | 기간, 대상자, 예산, 중복 지급, 종료 시각이 확인되는 실제 사례는 공개 위키로 분리한다. 단순 쿠폰 동시성은 기존 시나리오에 유지한다. |
| 점검 페이지·공지 | 구현 근거 없음 | 사례 공개 | `degraded mode → 공지 → 복구 smoke → 정상화`와 cache·권한 경계를 narrative로 추가했다. |
| 개인정보 마스킹·휴면·파기 | 법적 출시 점검, 보존기간·파기 backlog | 사례 공개 | 역할별 masking, 탈퇴, 보존 예외, 로그·backup 파기를 하나의 수명주기 사례로 연결했다. |
| WebView·앱 브릿지·딥링크 | 구현 근거 없음 | 경력 확인 필요 | jay-wiki에 억지로 넣지 않는다. RN 앱에서 메시지 계약, 버전 호환, 뒤로가기, 로그인 복귀를 다룬 사실이 확인되면 익명 경력 사례로 관리한다. |
| 크로스브라우징·구형 브라우저 | 390·768·1440px 반응형 QA | 다른 문제 | 반응형 검증을 IE 대응 경험으로 바꾸어 말하지 않는다. 실제 브라우저·polyfill·장애 사례가 있을 때만 별도 기록한다. |
| 외부 서비스 장애 대응 | 실제 Spring WebClient → FastAPI 장애 리허설 | 강한 중복 | 기존 `외부 제휴 API 장애 대응`을 대표 면접 장면으로 사용한다. 회사 경험은 실제 provider와 장애 영향만 익명화해 연결한다. |
| PG 정산·대사 파일 | 정산 배치 재실행 정책 모델 | 부분 중복 | 새 카드보다 기존 정산 시나리오에 `파일 수신 → 포맷 검증 → 대사 → 차이 격리 → 재처리` 모드를 추가하는 편이 낫다. |
| 버전 업그레이드·마이그레이션 | Flyway migration, 라이브러리·인프라 변경 기록 | 기술적 인접 | 회사의 Java·Spring·DB upgrade와 동일시하지 않는다. 호환성 표, 단계 배포와 rollback을 실제로 수행한 사례만 공개한다. |
| 온보딩·인수인계 문서 | 프로젝트 상태·운영 runbook·면접 가이드 | 개인 문서화 근거 | 문서화 역량의 보조 증거로 사용한다. 신규 입사자 지원 경험은 대상, 문서, 피드백과 효과를 별도로 확인한다. |
| QA와 테스트 시나리오 협의 | 자동 테스트와 브라우저 QA | 조직 협업 근거 없음 | 혼자 수행한 QA를 협업 경험으로 표현하지 않는다. 합의한 acceptance criteria와 결함 조정 사례가 확인될 때만 STAR로 작성한다. |
| 기획 변경에 기술 대안 제시 | ADR과 기술 선택 기록 | 판단 역량은 확인 | 포트폴리오의 trade-off 설명에는 사용 가능하다. 회사 협업 사례는 원안, 제약, 대안, 최종 결정 주체를 확인한다. |
| 디자이너와 컴포넌트·에셋 협의 | 디자인 시스템과 MinIO 자산 관리 | 조직 협업 근거 없음 | 실제 handoff, 상태 정의, 해상도·용량·접근성 조정 경험이 확인될 때만 경력 사례로 쓴다. |
| 릴리스 노트·배포 공지 | `진행상황.md`, GitHub Actions, 운영 검증 글 | 부분 중복 | 프로젝트에서는 릴리스 증거로 사용한다. 회사 경험은 대상 독자, 위험·영향·rollback·공지 시점을 확인한 뒤 작성한다. |

## 추천 우선순위

### P0: 기존 시나리오를 더 실무적으로 확장

1. **정산 배치 재실행에 PG 대사 파일 흐름 추가**
   기존 카드의 문제 범위를 유지하면서 파일 검증, 합계 대조, 불일치 격리와 부분 재처리를 보여준다.
2. **Kafka DLQ에 고객 알림 전달 경계 추가**
   전송 요청 ID, provider message ID, retry 가능 오류, 영구 실패, 중복 발송 방지를 구분한다.
3. **외부 제휴 API 장애 사례를 대표 면접 답변으로 연결**
   현재 실제 HTTP 리허설과 회사에서 겪은 장애 경험은 구분하되, timeout·429·5xx·callback 신뢰 경계를 같은 설명 축으로 사용한다.

### P1: 공개 사례를 실행 장면으로 확장

1. **운영 데이터 정정 runbook**
   원본 row를 직접 수정하는 위험을 보여주고 dry-run, 대상 snapshot, 2인 승인 가정, 조건부 UPDATE,
   수정 후 불변조건 검사와 audit log를 남긴다. 공개 화면은 실제 운영 DB가 아닌 격리된 사례 데이터만 사용한다.
2. **점검·성능 저하 모드 전환**
   전체 장애가 아닌 degraded mode, 사용자 공지, 쓰기 차단, 복구 확인과 cache 무효화를 다룬다.

### P2: 현재 사례에 실행 증거 추가

- 대용량 Excel/CSV export·import
- 반복 지표 요청의 백오피스 화면화
- 개인정보 파기 rehearsal

세 항목의 문제·절차·한계는 실무 사례 허브에 먼저 공개했다. 다음 단계에서는 처리 건수, memory, 소요 시간,
실패 row와 재실행 결과를 추가해 narrative와 실행 증거의 차이를 줄인다.

## 실제 경력을 복원하는 질문

각 후보마다 아래 질문에 답이 없는 항목은 이력서 문장으로 만들지 않는다.

1. **상황**: 어느 업무 흐름에서 누가 무엇을 요청했는가?
2. **규모**: row, 파일 크기, 요청량, 사용자 수, 처리 시간 중 기억나는 범위는 무엇인가?
3. **실패 위험**: 중복 반영, 누락, 개인정보 노출, 장시간 lock 중 무엇이 가장 위험했는가?
4. **내 행동**: 내가 직접 작성·결정·검증한 부분과 다른 사람이 담당한 부분은 어디까지인가?
5. **안전장치**: SELECT 선행, backup, transaction, idempotency, 승인, masking, reconciliation 중 실제 사용한 것은 무엇인가?
6. **결과**: 처리 시간, 오류, CS 재발, 수작업 횟수 또는 운영자 경험이 어떻게 달라졌는가?
7. **증거**: ticket, query, 문서, release note, 장애 보고서 중 공개하지 않고도 기억을 검증할 자료가 있는가?
8. **공개 경계**: 회사명, 고객정보, 금액, 내부 schema를 제거해도 기술적 판단이 남는가?

## 실무 경험과 포트폴리오를 연결하는 공개 구조

1. **실무에서 겪은 상황**: 업종과 문제 구조는 밝히고 회사·고객·거래 식별정보는 제거한다.
2. **당시 담당 범위**: 직접 결정·구현·검증한 경계를 명확히 한다.
3. **당시 안전장치와 한계**: 적용한 절차와 당시에는 하지 못했던 부분을 함께 말한다.
4. **jay-wiki 재구성**: 같은 위험을 어떤 simulator·정책 모델·운영 리허설로 다시 만들었는지 연결한다.
5. **현재 보완한 설계**: audit, idempotency, 관측, rollback처럼 경력 이후 보강한 판단을 보여준다.

시나리오 화면은 출처를 다음처럼 표시한다.

- `실무 경험 재구성`: 확인된 이커머스·상품권·외부 API 경험을 익명화해 재현
- `포트폴리오 운영 검증`: jay-wiki에서 직접 실행하고 상태·지표·복구 결과를 확인
- `정책 비교 모델`: 고정 입력으로 대응 방식을 비교하며 운영 실측으로 주장하지 않음

## STAR보다 기술 면접에 적합한 답변 구조

면접에서는 다음 6문장 구조로 압축한다.

1. 어떤 운영 요청이 반복되거나 위험했는지 말한다.
2. 기존 절차가 왜 실수·지연·장애에 취약했는지 설명한다.
3. 내가 담당한 경계와 선택한 안전장치를 밝힌다.
4. 실패하거나 되돌려야 할 때의 절차를 말한다.
5. 결과를 수치 또는 확인 가능한 변화로 설명한다.
6. 지금 다시 한다면 추가할 검증·자동화·권한 통제를 말한다.

## 다음 인터뷰에서 먼저 확인할 다섯 항목

사용자의 경력 배경과 현재 포트폴리오 연결성을 고려하면 아래 순서가 효율적이다.

1. 외부 PG·문자·제휴 API 장애를 실제로 어떻게 처리했는가?
2. 상품권 또는 결제 정산에서 원장·PG 파일을 대사한 경험이 있는가?
3. 포인트·상태값을 운영에서 정정할 때 어떤 승인·백업·검증 절차를 사용했는가?
4. RN WebView와 웹 사이에서 어떤 메시지·딥링크 장애를 해결했는가?
5. Excel export/import의 최대 규모와 memory·timeout 문제를 겪었는가?

이 답을 받으면 확인된 회사 경험은 적극적으로 공개 위키와 시나리오에 연결한다. 확인되지 않은 세부 수치와 담당 범위만
확정형 표현에서 제외한다.
