# 개발자 면접 관점 프로젝트 개선 평가

기준일: 2026-07-12

## 1. 총평

jay-wiki의 가장 큰 강점은 기능 개수가 아니라 직접 운영한 흔적이다. miniPC, k3s, 배포, 관측, 실패 주입,
복구, 백업과 문서화까지 연결되어 있어 일반적인 CRUD 포트폴리오보다 설명할 수 있는 운영 장면이 많다.

반대로 가장 큰 위험은 넓은 기술 범위다. PostgreSQL, Redis, Kafka, OpenSearch, MinIO, FastAPI와 관측 스택이
모두 들어 있어, 각 기술의 도입 이유와 대안을 명확히 설명하지 못하면 기술 전시장처럼 보일 수 있다.

현재는 새로운 기술을 추가하기보다 다음 질문에 답할 증거를 보강할 단계다.

- 실제로 실패시켜 봤는가?
- 실제로 복원하고 롤백했는가?
- 수치로 개선 전후를 비교했는가?
- 브라우저 사용자 흐름까지 자동 검증하는가?
- 보안 경계와 감수한 한계를 설명할 수 있는가?

## 2. 현재 강점

| 영역 | 강점 | 면접에서 강조할 내용 |
|---|---|---|
| 운영 | miniPC 단일 노드에 직접 배포·운영 | 관리형 서비스가 숨겨주는 배포, 저장소, 네트워크 문제를 직접 경험했다 |
| 아키텍처 | Next.js BFF 뒤에 Spring과 내부 서비스를 배치 | 외부 공개 경계와 내부 Service DNS 책임을 분리했다 |
| 데이터 | PostgreSQL SoT, Redis 상태, Kafka 이벤트, OpenSearch 검색 분리 | 저장소마다 해결하는 문제와 데이터 수명을 구분했다 |
| 장애 시연 | Saga 실패 주입, Kafka retry·DLQ, Redis 대기열 | 정상 흐름보다 실패와 복구 흐름을 시연할 수 있다 |
| 관측 | Prometheus, Loki, Tempo, Grafana 연결 | metric, log, trace를 동일 요청 흐름으로 추적했다 |
| 배포 | GitHub Actions, GHCR SHA 이미지, self-hosted runner | 빌드와 miniPC 내부 배포 책임을 분리했다 |
| 기록 | 상태 문서, workbook, 회고, 위키 문서 | 구현 사실과 계획·보류 항목을 구분한다 |

## 3. 기존 P0 항목의 현재 판정

초기 평가에서 P0로 잡았던 네 항목 중 롤백 두 경로와 공개 화면 Playwright 회귀는 완료했고,
외부 백업은 개발 머신 사본으로 대체했다. Google OAuth는 개인정보 처리 부담을 줄이기 위해 제거했다.
따라서 아래 내용은 새 작업 목록이 아니라 당시 문제와 현재 결론을 함께 보존한 기록이다.

### 3.1 실제 배포 롤백 리허설

워크플로 스텝 실패와 ImagePullBackOff에서 배포 전 이미지 캡처·자동 롤백·공개 화면 무중단을 운영에서
검증했다. 남은 범위는 readiness probe는 통과하지만 실제 기능이 깨진 이미지다.

면접 예상 질문:

> 롤백 코드가 있다는 것과 실제로 롤백 가능한 것은 다른데 직접 실행했는가?

운영에서 검증한 절차:

1. 의도적으로 잘못된 이미지를 배포한다.
2. rollout 또는 public smoke 실패를 감지한다.
3. 배포 전 캡처한 SHA 이미지로 복구한다.
4. home과 핵심 BFF smoke가 다시 통과한다.
5. 감지 시간, 복구 시간, 사용자 영향과 데이터 처리 방식을 기록한다.

### 3.2 외부 백업과 독립 복원 — 대체 완료, 재해 한계 유지

PostgreSQL dump를 반영 시점마다 개발 머신으로 내보내고 그 사본만으로 임시 PostgreSQL 복원을 검증했다.
miniPC 단일 디스크 장애에는 대응하지만 두 장비가 같은 장소에 있어 화재·도난 같은 동시 손실에는 대응하지 못한다.
Cloudflare R2는 결제 수단 등록을 피하기 위해 보류했고, 목적지만 교체할 수 있게 스크립트 경계를 뒀다.

초기 완료 기준 가운데 현재 채택한 범위:

```text
miniPC PostgreSQL backup
  -> Cloudflare R2 복제
  -> 외부에서 dump 다운로드
  -> 임시 PostgreSQL 복원
  -> 주요 테이블 row count 확인
  -> 애플리케이션 핵심 조회 확인
```

기록할 내용:

- 백업 크기와 복제 시간
- RPO와 RTO
- 암호화와 보존 기간
- 복원에 사용한 PostgreSQL 버전
- 다운로드부터 서비스 확인까지 걸린 시간

### 3.3 핵심 브라우저 E2E — 공개 화면 기준 완료

production build 기준 위키 딥링크·본문·CSS/JavaScript 자산·새로고침·desktop/mobile overflow를
Playwright로 검증하고 PR CI와 배포 후 workflow에 연결했다. 인증 변경과 실제 Saga 실행처럼 상태를 바꾸는
시나리오는 테스트 데이터 격리와 운영 안전장치가 생길 때 별도 확장한다.

현재 smoke 이후 확장 후보:

1. 문서 선택 후 URL, 새로고침, 브라우저 history가 같은 문서를 유지한다.
2. 로그인 상태와 역할에 따라 메뉴와 관리자 기능 노출이 달라진다.
3. 관리자 문서 편집 후 version과 revision이 생성된다.
4. Saga 배송 실패 실행 후 결제 취소와 재고 해제 타임라인이 나타난다.
5. favicon, MinIO 로고, CSS와 Mermaid가 배포 환경에서 정상 로드된다.
6. 다크·라이트 테마가 새로고침 후 유지된다.

### 3.4 Google OAuth 실제 사용자 흐름 — 제거

redirect URL과 callback 경로는 과거에 검증했지만, 개인정보처리방침·수집 고지·파기 절차를 지속할 만큼
포트폴리오 가치가 크지 않다고 판단해 소셜 로그인을 제거했다. 현재 인증 범위는 관리자 비밀번호와 TOTP다.

제거 결정으로 폐기한 초기 완료 기준:

1. 실제 Google 계정으로 동의 화면을 통과한다.
2. `jw_token`이 Secure, HttpOnly, SameSite 조건으로 발급된다.
3. `tb_user`에 Google provider와 subject가 저장된다.
4. 게시판 작성자가 USER 계정과 연결된다.
5. 로그아웃 뒤 인증 상태가 복구되지 않는다.

## 4. 기술적 개선점

### 4.1 프론트엔드 서버 상태 관리

현재 여러 컴포넌트가 `useEffect`와 직접 `fetch`를 각각 관리한다. lint warning 7개가 허용 상한으로
남아 있으며, stale 요청과 중복 사용자 조회가 발생하기 쉬운 구조다.

개선 방향:

- 공통 HTTP 오류 계약과 fetch 계층을 만든다.
- 서버 상태는 TanStack Query 도입 여부를 비교한 뒤 통합한다.
- 문서 선택 상태는 URL을 단일 기준으로 유지한다.
- 로그인 사용자 정보의 중복 요청을 제거한다.
- 폴링의 주기, 취소, 백오프 정책을 명시한다.
- 테마 초기화 스크립트와 React 상태가 같은 저장 키와 파서를 사용하게 한다.

### 4.2 DB 조회 성능

현재 게시판은 offset 페이징과 매 요청 `count(*)`를 사용한다. Saga 최근 목록은 관련 엔티티 조회 과정에서 N+1
가능성이 기록되어 있다.

개선 방향:

- 게시판 최신순 목록을 cursor 기반 페이징으로 비교한다.
- 전체 건수가 필요하지 않은 화면에서는 `Slice` 형태를 사용한다.
- Saga 최근 목록은 projection 또는 fetch join으로 한 번에 조회한다.
- `EXPLAIN ANALYZE`, 쿼리 수, p50·p95 응답시간을 개선 전후로 기록한다.
- 검색 비교는 warm/cold 조건, 반복 횟수와 인덱스 크기를 함께 공개한다.

### 4.3 보안 경계

Markdown XSS와 관리자 Server Action 재검증은 강점이다. 하지만 쿠키 기반 JWT를 사용하면서 Spring CSRF는
비활성화되어 있어 SameSite 쿠키 외의 방어 기준을 설명할 필요가 있다.

검토 항목:

- mutation 요청의 Origin 또는 CSRF token 검증
- 로그인·회원가입 brute-force rate limit
- 관리자 변경 작업 감사 로그
- OAuth session fixation과 state 검증
- JWT와 관리자 비밀번호 Secret 회전 절차
- 익명 게시판 비밀번호 정책과 삭제 요청 제한

산출물은 짧은 threat model 문서와 회귀 테스트가 적합하다.

### 4.4 Kubernetes 보안과 복원력

resource request·limit과 readiness·liveness probe는 구성돼 있다. 다음 항목은 추가 검토 가치가 있다.

- `runAsNonRoot`
- read-only root filesystem
- Linux capability drop
- 서비스 간 NetworkPolicy
- Secret 회전 runbook
- PVC와 노드 장애 시 복구 절차

단일 노드에서는 PDB나 replica 증가가 노드 장애 고가용성을 제공하지 않는다. 의미 없는 설정을 추가하기보다
적용하지 않은 이유와 단일 노드에서 검증 가능한 범위를 설명하는 편이 낫다.

## 5. 설명할 때 주의할 부분

### 5.1 기술 전시장처럼 보이지 않게 하기

각 기술마다 다음 세 문장으로 설명을 준비한다.

1. 어떤 실제 문제가 있었는가?
2. 더 단순한 대안은 무엇이었는가?
3. 왜 현재 기술을 선택했고 어떤 운영 비용을 감수했는가?

특히 FastAPI payment-api, Kafka, OpenSearch와 MinIO는 이 질문을 받을 가능성이 높다.

### 5.2 단일 노드 k3s의 의미 제한

HPA가 Pod를 1개에서 2개로 늘려도 같은 miniPC에서 실행된다. 따라서 노드 장애 고가용성 증거가 아니라 다음을
검증한 시연이라고 표현해야 한다.

- stateless workload 복제
- 공유 상태를 외부 저장소로 분리
- readiness 기반 rollout
- Kubernetes Service와 DNS 경계
- resource request에 따른 스케줄링

권장 답변:

> 노드 장애 내성은 없지만, stateless workload 복제와 공유 상태 분리, readiness 기반 rollout을 직접 검증하기
> 위해 단일 노드 k3s를 사용했습니다. 고가용성 클러스터라고 표현하지 않습니다.

### 5.3 Saga와 Kafka의 시연 범위

면접관은 현재 구현이 실제 분산 시스템인지 교육용 시뮬레이터인지 물을 수 있다.

명확히 구분할 내용:

- Spring은 orchestration과 최종 상태를 담당한다.
- FastAPI는 결제 참여자라는 좁은 경계만 담당한다.
- 실패 주입은 보상 흐름을 재현하기 위한 시연 장치다.
- Kafka 데모는 Outbox, fan-out, retry와 DLQ의 책임 차이를 보여주는 목적이다.
- 실제 결제, 다중 리전, exactly-once를 구현했다고 주장하지 않는다.

## 6. 문서 정합성 문제

운영·시드·export는 위키 86편·11개 탭으로 맞췄다. 과거 시점의 설계 기록은 당시 숫자를 보존하되,
현재 기준 문서와 실행 안내서가 그 숫자를 현재 상태처럼 다시 주장하지 않도록 관리한다.

개선 방향:

- 기준일과 운영 배포 SHA를 문서 상단에 둔다.
- 탭·문서 수를 API에서 읽어 검증하는 스크립트를 만든다.
- 완료, 운영 중, NEXT, 보류 상태의 모순을 검사한다.
- 깨진 내부 링크와 존재하지 않는 commit SHA를 CI에서 확인한다.
- 오래된 상태 설명은 현재 문서가 아니라 archive로 이동한다.

## 7. 성능 증거 보강

현재 반응형과 기능 동작은 확인했지만 Web Vitals와 운영 API 지연 수치가 부족하다.

측정 후보:

| 대상 | 측정값 |
|---|---|
| 홈·문서 | LCP, CLS, INP |
| 문서 전환 | API 응답시간, 렌더 완료 시간, stale 요청 발생 여부 |
| 게시판 | 페이지 조회 p50·p95, 실행 쿼리 수 |
| 검색 비교 | 방식별 p50·p95, warm/cold, 결과 품질 |
| Saga | 성공·실패 시나리오별 전체 소요 시간 |
| 배포 | build, image pull, rollout, smoke, rollback 소요 시간 |
| 복원 | dump 다운로드부터 서비스 확인까지의 RTO |

수치는 동일 환경에서 여러 번 측정하고 조건을 함께 기록해야 한다.

## 8. 추천 우선순위

면접 효과와 운영 위험 감소를 함께 고려한 순서다.

| 순위 | 개선 | 완료 결과 |
|---:|---|---|
| 1 | CSRF·Origin 보안 경계 | threat model, 구현과 cross-origin 회귀 테스트 |
| 2 | cursor 페이징과 Saga N+1 | 실행계획, 쿼리 수와 p95 개선 결과 |
| 3 | Web Vitals와 API 운영 지표 | 성능을 감상이 아닌 수치로 설명 |
| 4 | Ready-but-broken rollback rehearsal | readiness 한계를 포함한 복구 실행 기록 |
| 완료 | 공개 화면 Playwright smoke | PR CI와 배포 후 딥링크·자산·overflow 검사 |
| 대체 | 외부 백업 | 개발 머신 사본 복원 완료, 같은 장소 동시 손실은 감수 |
| 제거 | Google OAuth | 개인정보 처리 범위를 줄이고 관리자 TOTP만 유지 |

## 9. 면접용 핵심 결론

이 프로젝트는 이미 “무엇을 만들었는가”는 충분하다. 앞으로는 기술을 더 추가하기보다 다음 세 문장을 증명하는
방향이 좋다.

> 실패를 의도적으로 만들고 관측했습니다.

> 복구와 롤백을 실제 운영 환경에서 실행했습니다.

> 개선 전후를 테스트와 수치로 비교했습니다.

이 세 가지가 완성되면 넓은 기술 스택이 단순 나열이 아니라 운영 판단과 문제 해결 경험으로 읽힌다.
