# 면접 준비 — /scenarios 23편

작성 시작: 2026-08-03
목적: `portfolio.leneu.cloud/scenarios` 의 23편을 **내 입으로 설명할 수 있게** 만든다.
최근 갱신: 2026-09-02 (21편 → 23편)
암기용이 아니다. 원리를 이해하는 것이 목표고, 대본은 이해의 부산물이다.

## 이 문서를 쓰는 법

각 편은 7개 칸으로 되어 있고 순서에 이유가 있다.

| 칸 | 내용 | 왜 필요한가 |
|---|---|---|
| 1. 한 줄 정의 | 이 시나리오가 다루는 문제 | 남한테 한 문장으로 설명 못 하면 이해한 게 아니다 |
| 2. **원리 — 왜 이 문제가 생기나** | 메커니즘을 밑바닥부터 | **여기가 전부다.** 나머지 6칸은 이 칸의 응용 |
| 3. 대안 표와 내 선택 | 가능한 해법과 각각의 대가 | 면접은 정답이 아니라 **트레이드오프를 아는지**를 본다 |
| 4. 진위 한 줄 | 실제 실행인가 설계 정리인가 | **내가 먼저 말하면 강점, 들키면 치명타** |
| 5. 30초 구두 답변 | 실제로 입으로 낼 문장 | 아는 것과 말하는 것은 다르다 |
| 6. 꼬리질문 3개와 답 | 면접관이 파고들 지점 | 여기서 막히면 2번 칸으로 돌아가라는 신호 |
| 7. 모르면 인정할 선 | 어디까지 답하고 어디부터 "안 해봤습니다"인가 | 경계를 미리 정해야 즉석에서 지어내지 않는다 |

각 편 끝의 **자가 점검** 문장을 보지 않고 설명할 수 있으면 그 편은 끝난 것이다.

### 서술 기준 — 23편 전부 이 수준으로 쓴다

02가 기준선이다. 아래를 지킨다.

- **용어를 건너뛰지 않는다.** 멱등성·2PC·poison pill·at-least-once 같은 말은 처음 나올 때 반드시 풀어쓴다.
  "멱등성(idempotency)" 하고 지나가지 말고 엘리베이터 버튼 비유까지 붙인다
- **"왜"를 3단계까지 판다.** "재시도하면 안 된다" → "중복 처리되니까" → "상대가 이미 처리했을 수 있고
  그걸 구별할 방법이 없으니까" 까지 가야 이해다
- **사고를 시간순으로 그린다.** `10:00:00 / 10:00:01 / ⚡ 다운` 형태로 어느 순간에 뭐가 깨지는지 보인다.
  "이럴 수 있다"는 서술로는 이해가 안 된다
- **비교는 표로.** LIST vs ZSET, 롤백 vs 보상, at-most-once vs at-least-once
- **코드는 핵심 몇 줄만.** 인용이 길어지면 원리가 묻힌다
- **내 코드의 약점은 감추지 않고 굵게 쓴다.** 면접에서 내가 먼저 말할 문장을 여기서 만들어 둔다

### 지도 — 아직 만드는 중이다

시각 언어는 **청사진** 으로 정했고, 바탕을 칠판 초록으로 바꿨다.

| 파일 | 무엇 |
|---|---|
| **[chalk-map.html](./chalk-map.html)** | **지금 판.** 칠판 초록 위에 분필로 그린 도면. 요청이 지나는 경로가 줄기이고 그 길에 글이 매달린다. 확대할수록 더 적힌다 |
| [design-samples.html](./design-samples.html) | 톤을 고른 자리. 아키텍처 한 조각·마인드맵 한 가지·시퀀스 한 장면을 네 가지 시각 언어(청사진 · 손으로 그린 노트 · 기판 · 편집 지면)로 각각 그렸다. 데이터를 안 붙인 톤 비교다 |

`archive/` 의 넷은 **선이 무엇을 뜻하는지 정하기 전에** 만든 것이라 서로 다른 물건이다.
`flow-map.html` 이 마지막 것이고 구조는 그쪽이 가장 가깝다 — 요청이 지나는 경로를 줄기로 삼고
줌 단계마다 적히는 양이 달라진다. 시각 언어를 고르면 그 구조 위에 입힌다.

`archive/` 는 생성물이다. 글이 바뀌면 다시 뽑는다.

```bash
node scripts/build-knowledge-map.mjs
```

**이으는 선은 손으로 적지 않았다.** 글 본문의 `/wiki/<slug>` 를 센 것이라 글이 낡으면 선도 같이
낡는다 — 위키가 오답이 아니라 노화로 틀리는 물건이라, 손으로 그린 지도는 반년 뒤에 거짓말을 한다.
지금 기준으로 위키끼리 128개, 이 폴더에서 위키로 81개이고 **어디에도 안 이어진 위키 글은 0편**이다.

### 읽는 순서 — 02부터 시작하기를 권한다

실제로 돌아가는 9편 중 5편이 02에 몰려 있다. 원리를 읽고 곧장 화면에서 확인할 수 있어
이해가 붙는 속도가 가장 빠르다. 그다음은 어느 순서든 좋다.

```
02 (분산·연동)      전부 실제 동작. "응답이 없다"는 하나의 문제를 네 각도로
  ↓
01 (거래·정합성)     동시성 vs 재실행. 조건부 UPDATE 하나가 네 편을 관통한다
  ↓
03 (성능·데이터)     유한한 자원 · 점유 시간 · 넘칠 때의 선택
  ↓
04 (인프라·복구)     선언과 증명의 차이. 02·03의 약점이 여기서 드러난다
  ↓
05 (운영·거버넌스)   사람이 개입하는 순간. 앞의 모든 원칙이 절차로 재등장한다
```

### 편들이 서로 이어지는 지점 — 이걸 잡으면 23편이 하나가 된다

| 개념 | 처음 나오는 곳 | 다시 나오는 곳 |
|---|---|---|
| **멱등성** | 02 제휴 API | 01 상품권·쿠폰·정산 / 03 트래픽 중복 / 05 알림 재처리 |
| **조건부 UPDATE** | 01 주문 재고 | 01 상품권·쿠폰 / 05 데이터 정정 / 04 HPA 락 |
| **이중 쓰기 문제** | 02 Kafka Outbox | 01 정산 체크포인트 / 03 검색 색인 / 05 알림 |
| **at-least-once → 멱등 소비** | 02 Kafka | 03 이미지 job / 05 알림 재처리 |
| **DLQ · 사람에게 올리기** | 02 Kafka | 01 정산 대조 / 02 Saga 보상 실패 / 05 알림 |
| **"돌았다 ≠ 맞다"** | 01 정산 대조 | 04 복원 리허설 / 05 불변조건·지표 결과 비교 |
| **경계 분리 ↔ 원자성 상실** | 03 커넥션 풀 | 02 Saga 보상 |
| **`synchronized` 는 JVM 안에서만** | 02 채팅 | 04 HPA가 이걸 깨뜨린다 |
| **신호를 기다리지 말고 시간으로 판단** | 02 채팅 heartbeat | 01 예약 만료 / 04 HPA / 05 알림 상태 추적 |

**면접에서 가장 강한 답변은 이 연결을 말하는 것이다.** "Kafka 써봤습니다"가 아니라
"이중 쓰기 문제는 Kafka에도 검색 색인에도 정산 체크포인트에도 똑같이 나타납니다" 쪽이다.

## 진위 지도 — 이걸 먼저 외운다

23편은 **실제로 인프라가 도는 9편**과 **결과가 미리 적힌 14편**으로 갈린다.
`DomainScenarioController` 는 `partner-api` 하나만 실제 서비스로 보내고 나머지는
`DomainScenarioEngine` 으로 보내는데, 이 엔진은 `(시나리오, 모드)` 를 받아
**하드코딩된 step 배열을 그대로 돌려준다.**

### 대본이어도 되는 것과 안 되는 것

기준은 하나다 — **숫자를 주장하는가.**

- "재고 갱신 경계를 한 transaction으로 직렬화했다" → 설계 주장. 대본이어도 괜찮다.
- "600 RPS 입력, p95 380ms, backlog 95초" → **측정값 형태인데 상수다.** "어떻게 측정하셨어요?" 한 마디에 무너진다.

**대본인데 실행처럼 보이는 상태가 셋 중 최악이다.** 들키면 진짜 7편까지 의심받는다.
그래서 B군은 면접에서 내가 먼저 "이건 설계 정리입니다"라고 말한다. 그게 오히려 강한 답변이다.

## 2단계 — 사이트 반영 결과 (2026-08-03)

### A. 진위 표시 ✅

**문제**: "실무 경험 재구성" 배지 9편 중 8편이 고정 대본인데, 배지만으로는 알 수 없었다.
화면에 실행 버튼이 있고 단계가 흐르므로 실제 실행으로 읽힌다.

**원인**: 출처와 실행 성격이 **서로 다른 축인데 한 축으로 표현**하고 있었다.
"실무에서 가져온 문제인데 실행은 아니다"를 표현할 방법이 없었다.

**고친 방법**: 축을 둘로 분리했다.

| 축 | 값 | 뜻 |
|---|---|---|
| 출처 (`ScenarioProvenance`) | 실무 경험 재구성 / 포트폴리오 운영 검증 / 정책 비교 모델 | 이 문제를 **어디서 가져왔나** |
| **실행 (`ScenarioExecution`, 신규)** | **실제 실행(7편) / 정의된 흐름(14편)** | 화면의 단계와 숫자가 **실측인가** |

- `scenarios.ts` 에 `SCENARIO_EXECUTION` 맵 추가, `ScenarioProvenance` 컴포넌트가 두 칩을 함께 렌더
- 실제 실행은 초록, 정의된 흐름은 회색

### B. 측정값 주장 제거 ✅

**고친 방법**: 숫자를 지우는 대신 **성격을 명시**했다. 숫자를 없애면 모드 간 비교라는
이 화면의 목적 자체가 사라지기 때문이다.

- 도메인 랩 지표 아래 캡션 추가 — `partner-api` 는 *"이번 실행에서 측정한 값입니다"*,
  나머지는 *"비교를 위한 고정 입력값입니다. 측정값이 아닙니다."*
- hero 문구를 *"아래 단계와 숫자는 실행 결과가 아니라 미리 정의한 흐름과 고정 입력입니다.
  … 실제 처리량이나 지연을 주장하지 않습니다"* 로 교체

### C. 코드 결함 ✅ 4건 수정 / ⚠️ 3건 남음

| 결함 | 위치 | 결과 |

**정정**: 처음에 *"화면에 `CIRCUIT_OPENED` 라고 표시되는데 사실과 다르다"* 고 적었는데 **틀렸다.**

`PartnerApiRehearsalService` 로 보내기 때문에 **한 번도 호출되지 않는 죽은 코드**였다.
실제 경로는 처음부터 `RETRY_EXHAUSTED` 였다. 죽은 코드를 지우고, 엔진이 `partner-api` 를 받으면
예외를 던지도록 바꿔 테스트로 고정했다.
