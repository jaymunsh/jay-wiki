# jay-wiki 면접 설명 가이드

최근 갱신: 2026-09-02

## 이 문서의 목적

이 문서는 기능 목록이 아니라, jay-wiki를 왜 시작했고 어떤 순서로 설계·구축·운영했는지 스스로 설명하기 위한 기준 문서다.
면접에서는 외운 기술 이름보다 문제, 선택, 트레이드오프, 실패, 검증을 연결해서 말한다.

## 30초 소개

jay-wiki는 miniPC 한 대의 k3s에서 직접 운영하는 풀스택 위키이자 실행형 포트폴리오다.
한 앱이 host를 보고 위키와 블로그 두 사이트로 갈리며, 배포도 이미지도 하나다.
Next.js BFF 뒤에 Spring Boot와 FastAPI를 두고 PostgreSQL, Redis, Kafka, OpenSearch, MinIO를 실제 시나리오로 연결했다.
Saga 보상, Kafka retry와 DLQ, Redis 대기열, 검색 방식 비교를 화면에서 실행할 수 있고, 그 결과를 Prometheus, Loki, Tempo,
Grafana로 관측한다. GitHub Actions와 self-hosted runner로 배포하며 PostgreSQL 복원 리허설까지 기록하는 것이 핵심이다.

## 2분 설명 순서

1. 기술을 나열하는 포트폴리오가 아니라 실패를 재현하고 증거를 남기는 환경을 만들고 싶었다.
2. 비용과 운영 경험을 함께 얻기 위해 클라우드 매니지드 서비스 대신 miniPC 단일 노드 k3s를 선택했다.
3. 외부에는 Next.js만 공개하고 Spring과 데이터 서비스는 클러스터 내부 DNS로 격리했다.
4. 위키 본문은 컨테이너 파일이 아니라 PostgreSQL을 Source of Truth로 두고 revision을 남겼다.
5. Saga, Kafka, Redis, 검색은 일반론이 아니라 사용자가 직접 실패와 상태 변화를 확인하는 시나리오로 만들었다.
6. 배포, 백업, 알림, trace, 재부팅 복구를 실제로 실행해 운영 가능성을 검증했다.
7. 반복 절차는 파이프라인으로 밀어 넣되 되돌릴 수 없는 것은 사람에게 남겼고, 그 경계를 문서로 고정했다.
8. 현재는 새 기술 추가보다 운영 증거를 반복 가능하게 만들고, 글 반영과 배포를 서로 떼어 두는 단계다.

## 구축 과정

| 단계 | 해결하려던 문제 | 선택 | 검증 |
|---|---|---|---|
| 1. 위키 기반 | 구축 내용을 계속 남길 공간이 필요했다 | Next.js + Spring Boot + PostgreSQL | 문서 CRUD와 revision |
| 2. 검색 | 단순 CRUD보다 데이터 규모와 검색 전략을 보여주고 싶었다 | LIKE, tsvector+GIN, OpenSearch+nori 3-way 비교 | 동일 10만 건과 같은 검색어 비교 |
| 3. 사용자 기능 | 인증과 상태 저장의 경계를 보여줄 필요가 있었다 | local ADMIN, 게시판, Redis 조회수 (Google USER 는 뒤에 제거) | role별 UI와 API 권한 |
| 4. 실시간 상태 | Redis를 캐시 외 용도로 검증하고 싶었다 | SET, ZSET, STREAM 기반 랜덤채팅 | 정원 3명, 4번째 대기, 자동 승격 |
| 5. 분산 흐름 | 실패와 보상을 눈으로 확인할 시나리오가 필요했다 | Spring Saga orchestrator + FastAPI payment participant | 배송 실패 시 결제 취소와 재고 해제 |
| 6. 비동기 처리 | fan-out, retry, DLQ를 독립적으로 보여주고 싶었다 | Kafka KRaft + Outbox | 정상, 일시 실패, 영구 실패 비교 |
| 7. 운영 배포 | 로컬 데모를 실제 서비스로 바꿀 필요가 있었다 | miniPC k3s, Cloudflare Tunnel, Traefik | 공개 HTTP와 내부 Service DNS 확인 |
| 8. 관측 | 성공 여부만으로는 분산 실패를 설명할 수 없었다 | OTel, Prometheus, Loki, Tempo, Grafana | 하나의 요청을 metric, log, trace로 연결 |
| 9. 전달과 복구 | 배포와 데이터 복구가 사람 기억에 의존했다 | Actions, GHCR, self-hosted runner, backup CronJob | rollout, public smoke, 임시 DB restore |
| 10. 포트폴리오 UX | 기능이 많아도 방문자가 전체 구조를 이해하기 어려웠다 | 시나리오 허브와 k3s 오케스트레이션 지도 | 390, 768, 1280px 탐색 QA |
| 11. 콘텐츠 경계 | DB Markdown과 관리자 변경을 같은 신뢰 수준으로 둘 수 없었다 | HTML 이중 sanitize, strict Mermaid, Server Action ADMIN 재검증 | XSS·권한 회귀 테스트와 브라우저 QA |
| 12. 두 번째 사이트 | 위키와 성격이 다른 글을 같은 곳에 두기 어려웠다 | 한 앱에서 `middleware.ts` 가 host로 가르는 블로그 | 배포·이미지 하나로 두 도메인 서빙 |
| 13. 배포 자동화 경계 | 배포 뒤 사람이 기억해야 할 절차가 넷 있었고 실제로 잊어 사고가 났다 | 되돌릴 수 있는 것만 파이프라인에, 삭제는 사람에게 | 복구 리허설 뒤 하나씩 켬. 알림 35일 침묵 사고가 계기 |
| 14. 글 반영과 배포 분리 | 그림 한 장 때문에 글 한 편에 배포 한 판이 필요했다 | 그림을 MinIO로 보내고 내부 문을 ssh 터널로 사람도 쓴다 | TOTP·GitHub Actions 없이 몇 초. 삭제 경로까지 실제로 밟아 확인 |

## 아키텍처를 설명하는 기준

```text
Browser
  -> Cloudflare Tunnel / Traefik
  -> Next.js web + BFF
  -> Spring Boot jaywiki
  -> PostgreSQL / Redis / Kafka / OpenSearch / MinIO

Spring Boot <-> FastAPI payment-api        (Saga 결제 참여자)
            <-> FastAPI shipping-api       (자기 DB를 든 배송 참여자)
            <-> partner-simulator          (외부 HTTP 장애 재현)
  -> OTel Collector -> Prometheus / Loki / Tempo -> Grafana

git push -> GitHub Actions -> GHCR -> miniPC self-hosted runner
  -> 기존 이미지 캡처 -> kubectl rollout -> public smoke -> 실패 시 캡처 이미지 복구
```

- Next.js는 공개 화면과 BFF를 책임진다. 브라우저는 내부 Spring 주소를 알지 않는다.
- Spring Boot는 위키, 게시판, 인증, 검색 조정, Saga, Kafka 시나리오를 책임진다.
- FastAPI는 Saga의 결제·배송 참여자로 좁게 유지해 서비스 간 계약과 trace 전파를 보여준다. 배송은 자기 DB를 들어 경계가 데이터까지 갈린다.
- PostgreSQL은 영속 원본, Redis는 짧은 수명의 상태, OpenSearch는 재생성 가능한 검색 색인이다.
- k3s는 단순 배포 도구가 아니라 재시작, Service DNS, Secret, PVC, HPA의 운영 경계다.

## 핵심 설계 결정과 트레이드오프

### 관리자 TOTP와 제한된 Kubernetes Autoscaling 리허설

- 관리자는 비밀번호와 TOTP를 모두 통과하며, OTP 재사용과 반복 실패를 Redis로 제한했다.
- Kubernetes Horizontal Pod Autoscaler(HPA) 시연은 관리자만 고정된 Job을 실행하고, 관측된 평시 p95보다 높은 CPU 80% 기준에서 replica가 `1→2→1`로 autoscaling되는 과정을 보여준다. 방문자는 익명화된 Pod·CPU·replica를 읽기 전용으로 본다.
- Job이 끝났다는 사실과 확장을 관측했다는 사실을 분리해, 2 Pod를 보지 못한 실행은 `NO_SCALE`로 남긴다.
- 트레이드오프는 단일 miniPC 노드 안의 수평 확장으로, 노드 장애 고가용성을 증명하지는 않는다.

### miniPC 단일 노드 k3s

- 선택 이유: 비용 절감만이 아니라 네트워크, 스토리지, 재부팅, 리소스 압박을 직접 경험하기 위해서다.
- 얻은 것: 실제 배포·복구·관측 경험과 명확한 운영 증거다.
- 감수한 것: 노드 장애가 곧 전체 장애이고, 같은 장비의 백업은 재해 복구가 아니다.
- 현재 보완: 운영 백업을 개발 머신으로 내보내 복원까지 검증했다. 다만 두 기계가 같은 장소에 있어 화재·도난 같은 동시 손실은 막지 못하며, 외부 오브젝트 스토리지는 비용·계정 경계를 받아들일 때 다시 검토한다.

### Next.js BFF

- 선택 이유: 브라우저가 내부 API 주소와 인증 경계를 직접 다루지 않게 하기 위해서다.
- 얻은 것: 외부 공개 지점 하나, same-origin 쿠키, Spring 내부 Service 유지다.
- 감수한 것: 프록시에서 쿠키, forwarded origin, 오류 응답을 정확히 전달해야 한다.
- 실제 교훈: OAuth public origin과 관리자 Server Action 쿠키 전달이 별도 경계임을 장애로 확인했다.

### PostgreSQL 위키 Source of Truth

- 선택 이유: 컨테이너 이미지에 들어간 Markdown은 운영 중 편집과 revision에 적합하지 않았다.
- 얻은 것: 배포와 콘텐츠 수명 분리, 관리자 편집, version과 rollback이다.
- 감수한 것: 코드의 시드 원본과 운영 DB 사이에 동기화 정책이 필요하다.
- 현재 기준: 시드는 DB와 비교해 달라진 문서만 저장하며 `--dry-run`은 변경과 추가 잔존 문서를 보고한다.
- 운영 원칙: PostgreSQL이 실행 중 콘텐츠의 SoT이고 시드는 자동 reconcile이 아닌 검토된 bootstrap 입력이다.

### Saga와 Kafka를 분리한 이유

- Saga는 동기 참여자 사이의 실패와 보상을 설명한다.
- Kafka는 Outbox 이후 fan-out, 재시도, DLQ를 설명한다.
- 두 패턴을 하나의 거대한 주문 흐름으로 섞지 않아 각각의 실패 모델과 관측 신호를 분명히 했다.

### 되돌릴 수 있는 것만 파이프라인에 넣었다

- 배포 뒤 사람이 기억해야 하는 절차가 넷 있었고, 실제로 잊어서 알림이 35일 죽은 사고가 났다.
- 그렇다고 전부 자동화하지는 않았다. **기준은 「되돌릴 수 있는가」다.** 관측 스택 Helm과 블로그 발행은
  켰고, 빈 탭 삭제는 서버가 가드를 쥐고 한 번에 둘까지만 지우도록 좁힌 뒤에 켰다.
- 켜기 전에 복구 리허설을 먼저 했다. 운영 글 하나를 일부러 26자로 망가뜨려 화면이 깨진 것을 확인하고
  백업에서 되돌렸다 — 9305자 복구, 2.4초. **그 리허설에서 복구 스크립트의 버그가 실제로 나왔다.**
  되돌리는 길이 있다는 문서와 되돌려 봤다는 사실의 차이가 버그 하나만큼 실재했다.

### 글을 올리는 일에서 배포를 떼어냈다

- 글 한 편에 그림 한 장이 들어가면 배포 한 판(과금 13분, 대기 20분)이 필요했다.
  `web/public` 이 컨테이너 이미지에 구워지기 때문이다.
- 그림을 MinIO로 보내고 원본은 저장소의 `web/public` 밖에 두었다. **git 이력은 지키면서 배포만 떼어낸다.**
- 인증은 배포가 쓰던 내부 토큰 경로를 사람도 쓰게 했다. 관리자 API를 타면 TOTP를 매번 넣어야 해서,
  결국 사람이 다시 폴더를 고르는 일로 돌아간다. 토큰은 ssh로 그 자리에서 읽고 노트북에 남기지 않는다.
- **트레이드오프**: 그만큼 이 경로는 노트북의 ssh 접근에 의존한다. 그리고 되돌릴 지점이 파이프라인의
  DB 백업보다 약해서, 덮이는 글의 운영 사본만 미리 받아 둔다.

### 운영 문서의 탐색과 콘텐츠 보안

- 선택 이유: 글이 늘어난 뒤에는 링크 공유, 빠른 연속 선택, 모바일 다이어그램 읽기가 기능만큼 중요해졌다.
- 얻은 것: URL을 문서 선택의 계약으로 고정하고, 늦게 끝난 요청이 최신 선택을 덮지 못하게 했다. 넓은 탭·표·Mermaid는 페이지가 아닌 각 컴포넌트 안에서만 스크롤한다.
- 보안 경계: raw HTML escape와 allowlist sanitize를 함께 적용하고, 관리자 변경 Server Action은 ADMIN을 다시 확인한 뒤 jw_token만 Spring 변경 API로 전달한다.
- 검증 범위: 390, 768, 1280px 브라우저 QA와 Markdown·권한 Vitest를 통과했다. Web Vitals 수치는 아직 측정하지 않았으므로 성능 수치로 과장하지 않는다.
- 상세 기록: [frontend-security-improvement-log.md](../frontend-security-improvement-log.md).

## 대표 실패와 배운 점

| 사건 | 원인 | 수정 | 재발 방지 기준 |
|---|---|---|---|
| 결제 요청 무한 대기 | HTTP client timeout 부재 | connect 2초, read 5초 | 외부 의존 호출은 시간 경계를 계약에 포함 |
| 결제 장애가 409 | 범용 예외 매핑 | 503 problem+json 분리 | 비즈니스 충돌과 인프라 장애를 구분 |
| 시드 스크립트 실행 실패 | String.raw 본문의 백틱 | 본문 규칙 검사 | 문법 검사와 실제 실행 검증을 함께 수행 |
| PostgreSQL 백업 실패 | 서버 18, pg_dump 16 | postgres:18 이미지 사용 | 서버와 client major version을 운영 계약으로 기록 |
| OAuth callback이 http | 내부 forwarded origin 사용 | 명시적 public origin | reverse proxy의 내부 origin과 공개 origin을 구분 |
| 관리자 편집 403 | Server Action이 JWT 쿠키를 Spring에 전달하지 않음 | ADMIN 확인 후 동일 쿠키 전달 | 서버 간 호출도 브라우저 인증이 자동 전달되지 않음을 테스트 |
| Mermaid 오류 문구 노출 | 렌더 실패 SVG와 React 재렌더 충돌 | parse 실패 격리와 렌더 수명 고정 | 문법 검사와 실제 브라우저 SVG 검증을 함께 수행 |
| Markdown XSS 경로 | DB 본문을 HTML로 렌더링하며 raw HTML·위험한 URL을 신뢰 | raw HTML escape와 allowlist sanitize | XSS payload 회귀 테스트와 strict Mermaid renderer |
| 빠른 문서 전환 | 이전 fetch 응답이 최신 선택보다 늦게 도착 가능 | URL 동기화와 stale response 차단 | 연속 선택, 딥링크, 반응형 브라우저 QA |
| 알림이 35일 침묵 | Helm 을 사람이 올리며 텔레그램 values 를 빠뜨렸다 | 관측 스택을 배포 잡이 올린다 | 사람이 기억해야 하는 절차는 언젠가 반드시 빠진다 |
| 운영 이미지 업로드가 한 번도 안 됐다 | 서비스 계정 정책에 `s3:GetBucketLocation` 이 없었다. minio-java 가 putObject 앞에서 버킷 위치를 묻는다 | 정책에 추가하고 부트스트랩 스크립트도 고쳤다 | **넓은 열쇠로 시험하고 좁은 열쇠로 운영하면 좁힌 만큼이 사각지대다.** 로컬은 root 계정이라 정책을 안 탔다 |
| 로컬은 통과, CI 는 실패 | 멱등 테스트가 진짜 MinIO 를 썼다. Testcontainers 에는 PostgreSQL·Redis 뿐이다 | 창고를 `@MockitoBean` 으로 뒀다 | 로컬에만 있는 것이 테스트를 통과시킨다. 끄고 한 번 돌려 본다 |
| 자산 검사기가 거짓말 | 존재 확인에 HEAD 를 썼는데 `SecurityConfig` 가 GET 만 공개로 열어 둬 403 이었다 | GET 으로 확인한다 | 놓치는 검사기보다 거짓말하는 검사기가 나쁘다 |
| 발행일만 고친 글이 운영에 안 닿음 | 변경 감지 `same()` 이 발행일을 비교 대상에서 빼고 있었다 | 견주게 고치되 안 보낸 값은 안 견준다 | 비교 필드를 더할 때는 그 필드를 안 싣는 경로를 같이 본다 |

## 면접에서 보여줄 세 가지 시나리오

### Saga 배송 실패

1. `/saga/order`에서 배송 실패를 선택한다.
2. 주문과 재고 예약, 결제 승인 뒤 배송 요청을 실패시킨다.
3. 결제 취소와 재고 해제가 역순으로 기록되는지 확인한다.
4. 같은 요청을 Loki와 Tempo에서 trace ID로 연결한다.

### Kafka DLQ

1. `/kafka/order`에서 알림 영구 실패를 선택한다.
2. Outbox relay와 consumer별 fan-out을 확인한다.
3. retry 횟수 이후 DLQ로 격리되는 상태를 확인한다.
4. metric과 alert가 같은 사건을 가리키는지 설명한다.

### 검색 3-way 비교

1. `/board/search`에서 같은 검색어를 실행한다.
2. LIKE, PostgreSQL tsvector, OpenSearch nori의 결과와 시간을 비교한다.
3. 한국어 형태소 차이, highlight, 장애 시 fallback 기준을 설명한다.

### 실무 도메인 상태 전이

`/scenarios`의 상품권, 외부 API, 주문 확정 카드에서 각각 전용 리허설 화면으로 이동한다.

1. 상품권에서는 중복 key, 동시 사용, 응답 유실과 취소를 실행하고 잔액·원장 원칙을 설명한다.
2. 외부 API에서는 Spring이 FastAPI simulator를 실제 호출한다. 정상 200, 429 후 재시도, 반복 500 종료,
   read timeout 뒤 HMAC callback 복구와 위조 callback 차단을 실행하고 WebClient·callback 코드를 함께 설명한다.
3. 주문 확정에서는 마지막 재고, 중복 결제 callback과 확정 실패의 보상 순서를 설명한다.
4. 모든 실행은 PostgreSQL에 run과 step으로 남으므로 새로고침 뒤에도 최근 결과를 다시 열 수 있다.

상품권과 주문 화면은 실제 발행사, PG 또는 재고 시스템을 호출하지 않는 영속 상태 전이 리허설이다. 외부 API 화면만
제어 가능한 FastAPI simulator와 실제 HTTP로 통신한다. 따라서 `외부 업체 장애를 재현했다`가 아니라
`외부 HTTP 경계의 실패 정책을 제어된 simulator로 반복 검증했다`고 설명한다. callback registry는 현재 단일 process 메모리이므로
다중 replica 운영에서는 PostgreSQL 또는 Redis inbox, 중복 수신과 재시작 복구가 추가로 필요하다.

### 운영 실무 사례를 실행으로 설명하기

`/scenarios`의 `운영 도구·거버넌스` 여섯 사례는 익명화한 실무 문제를 결정론적 정책 리허설로 다시 만든 화면이다.

1. 데이터 정정은 직접 UPDATE와 dry run·조건부 UPDATE·rollback의 affected row와 감사 단계를 비교한다.
2. 개인정보는 원문 조회에서 역할별 masking, 탈퇴와 보존기간 만료까지 원문 노출 필드가 줄어드는 과정을 비교한다.
3. Excel은 전체 메모리 적재와 streaming 정책을 비교하고, 검색에 쓰는 실제 게시글 10만 건을 Apache POI
   `SXSSFWorkbook`으로 다운로드한다. DB fetch 2,000행, workbook window 500행이며 본문·password hash는 제외한다.
4. 업무 통계는 일회성 SQL의 정의 차이와 versioned 지표, 화면·export 합계 및 index 전후를 비교한다.
5. 알림은 timeout, 429, 영구 실패와 운영자 replay를 request key·provider 상태·DLQ 관점으로 비교한다.
6. 점검 모드는 정상·degraded·maintenance·recovery에서 허용 기능, write gate와 smoke 순서를 비교한다.

각 실행은 PostgreSQL의 동일한 run·step 구조에 저장되므로 새로고침 뒤 최근 실행을 다시 열 수 있다. 화면의 수치는 실제 회사 데이터나
실측 benchmark가 아니라 정책 차이를 설명하기 위한 고정 입력이다. 면접에서는 `회사에서 이런 문제 구조를 겪었다 → 회사 정보 없이
재구성했다 → 현재 포트폴리오에서 정책과 실행 증거를 반복 검증한다` 순서로 설명한다.

Excel 다운로드 자체는 실제 구현 증거다. 2026-07-16 로컬 실행에서 10만 데이터 행과 header 1행, 약 3.7MB 파일을 생성했고
Spring 직접 경로 약 3.8초, Next streaming proxy 경로 약 2.2초가 측정됐다. 이는 로컬 1회 결과이며 운영 miniPC benchmark로
일반화하지 않는다. peak memory 값은 아직 실측하지 않았으므로 화면의 memory 비교는 `MODELLED`로 구분한다.

## 현재 상태를 솔직하게 말하는 법

- 운영·시드·export는 11개 DB 탭과 위키 88편으로 맞췄다. 블로그는 별도 사이트로 53편이다.
- 글 반영은 backup, dry-run diff, 내부 sync, public smoke 순서를 지키며 배포와 분리할 수 있다.
  **블로그는 그림까지 배포 없이 나간다**(2026-09-02부터). 위키 글은 여전히 배포가 시드를 실행해야 화면이 바뀐다.
- 워크플로 스텝 실패와 ImagePullBackOff 롤백은 운영에서 검증했다. Ready지만 기능이 깨진 이미지의 롤백은 아직 검증하지 않았다.
- 외부 백업은 개발 머신 사본과 복원 리허설로 대체했다. 같은 장소의 두 장비가 함께 손실되는 재해에는 대응하지 못한다.
- Google OAuth는 개인정보 처리 부담에 비해 포트폴리오 가치가 낮다고 판단해 제거했다. 현재 인증 범위는 관리자 비밀번호와 TOTP다.
- Spring Cloud Gateway와 Spring Batch는 도입한 기술이 아니라 필요 조건을 검토 중인 항목이다.

## 자주 받을 질문

### 왜 EKS나 GKE를 사용하지 않았나

이 프로젝트의 목적은 관리형 Kubernetes 사용 경험보다 노드, 스토리지, 네트워크, 재부팅과 복구를 직접 운영하는 것이었다.
대신 단일 노드라는 약점을 숨기지 않고 외부 백업과 restore drill을 다음 완료 조건으로 두었다.

### 마이크로서비스인가

전체를 억지로 분리한 구조는 아니다. 핵심 위키와 데모 조정은 Spring 모놀리스에 두고, Saga의 결제 참여자와
외부 제휴사 장애 simulator처럼 실패를 독립적으로 제어할 이유가 있는 FastAPI 경계만 분리했다. 서비스 수보다 실패 경계가 분리 기준이다.

### Kubernetes가 꼭 필요했나

기능 구현만 보면 Docker Compose로 충분하다. 그러나 이 프로젝트는 rollout, Service DNS, Secret, PVC, HPA, 재부팅 복구와
self-hosted 배포를 직접 검증하는 것이 목표였기 때문에 k3s가 학습 장치이자 운영 경계로 필요했다.

### CI 비용은 어떻게 관리했나

무료 한도 2,000분을 다 쓰고서야 배포 한 판의 값을 알았다. 한 판이 과금 13분, 대기 20분이다.
줄이는 방법을 찾기 전에 **배포를 부르는 일 자체를 줄였다** — 글만 고쳤으면 배포가 필요 없도록
경로를 따로 냈고, 그림까지 배포 없이 나가게 만든 것이 마지막 조각이었다.
self-hosted runner 를 쓰면서도 과금이 붙는다는 점, 경로 필터로 안 걸리는 커밋을 가르는 점을 함께 설명한다.

### 가장 개선하고 싶은 부분은 무엇인가

첫째는 Origin/CSRF 같은 변경 요청의 서버 측 보안 경계, 둘째는 cursor 페이징과 Saga N+1의 측정 기반 개선,
셋째는 Ready지만 기능이 깨진 이미지의 롤백 리허설이다. 기본 공개 화면의 브라우저 회귀 검사는 이미 PR CI와 배포 후 workflow에 연결했다.
새 기술을 추가하는 것보다 이미 주장한 운영 능력을 반복 가능한 증거로 만드는 것이 우선이다.

## 증거를 말할 때의 규칙

각 설명에는 가능하면 다음 중 하나 이상을 연결한다.

- commit SHA 또는 배포 image SHA
- GitHub Actions run
- 실제 실행 날짜와 환경(local, miniPC k3s, production)
- HTTP status와 응답의 핵심 상태
- trace ID, metric 이름, Loki query
- 백업 checksum, restore 소요 시간, row count
- 390, 768, 1280px 화면 검증 결과

“구현했다”와 “운영에서 검증했다”를 같은 말로 사용하지 않는다.

## 갱신 규칙

- 기능, 배포, 장애, drill을 끝낼 때 `구축 과정`, `대표 실패`, `현재 상태` 중 관련 항목을 갱신한다.
- 완료되지 않은 작업은 완료형으로 바꾸지 않는다.
- 숫자와 버전은 추측하지 않고 API, Git, 로그에서 다시 확인한다.
- 상세 명령은 런북(`docs/deploy-runbook.md` 등)에 두고, 이 문서에는 면접에서 설명할 판단과 결과만 남긴다.

## 회사 운영 경험을 연결하는 기준

운영 DB 정정, 엑셀, 정산 대사, 알림 발송, WebView와 협업 사례처럼 실제 회사에서 수행한 경험은 기술 목록 뒤에 숨기지 않는다.
[운영의 그림자 노동: 경력 사례 인벤토리](./07-경력-사례-인벤토리.md)에서 실제 상황, 본인의 담당 범위,
안전장치와 결과를 복원한 뒤 익명화된 사례로 공개한다.

설명 순서는 `회사에서 겪은 문제 → 당시 대응과 한계 → jay-wiki에서 다시 만든 리허설 → 현재 보완한 설계`로 고정한다.
실무 경험과 포트폴리오 구현을 함께 보여주되, 회사의 코드·데이터·고객 식별정보는 포트폴리오에 복제하지 않는다.
