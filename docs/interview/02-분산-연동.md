# 02. 분산 처리 · 외부 연동

사이트 그룹: **분산 처리·외부 연동**
화면: `portfolio.leneu.cloud/scenarios` 의 두 번째 묶음

**5편 전부 실제로 돌아간다.** 23편 중 진짜로 동작하는 9편의 절반 이상이 여기 몰려 있다.

---

## 시작하기 전에 — 이 그룹 전체를 관통하는 것 하나

5편은 겉보기에 다른 기술이다. HTTP 연동, Saga, DB 소유권, Kafka, Redis. 그런데 **하나의 문제를 다섯 각도에서 다루고 있다.** 그 문제를 먼저 이해하면 나머지가 전부 쉬워진다.

앞의 넷은 「경계 너머의 응답을 어떻게 다루나」이고, **소유권 편은 그 경계가 애초에 실재하는가를 묻는다.** 데이터가 한 덩어리면 나머지 넷은 그림 위의 선일 뿐이라, 순서로는 이 편이 앞의 전제에 해당한다.

### 로컬 호출과 원격 호출의 결정적 차이

같은 프로그램 안에서 함수를 부르는 걸 생각해 보자.

```java
int result = calculate(10);   // 여기서 일어날 수 있는 일은 딱 둘
```

1. 값이 돌아온다 (**성공**)
2. 예외가 터진다 (**실패**)

**끝이다. 세 번째는 없다.** 그리고 실패했다면 "계산이 안 됐다"는 게 확실하다.

이제 네트워크 너머의 서버를 부른다고 하자.

```java
Response result = httpClient.post("https://결제사.com/승인", 요청);
```

여기서는 **세 가지**가 가능하다.

1. 응답이 온다 (**성공** — 결제됐다)
2. "실패" 응답이 온다 (**실패** — 결제 안 됐다)
3. **아무 응답도 안 온다** (타임아웃)

3번이 문제다. **아무 응답이 없을 때, 상대가 처리를 했는지 안 했는지 내 쪽에서는 알 방법이 없다.** 두 가지 완전히 다른 상황이 똑같이 보인다.

```
[상황 A] 내 요청이 상대에게 도착도 못 했다     → 결제 안 됨
[상황 B] 상대는 결제를 완료했는데 응답만 유실  → 결제 됨

내가 보는 것: "응답이 없다"  ← A와 B가 구별이 안 된다
```

우편으로 비유하면 이렇다. 등기를 보냈는데 회신이 없다. **편지가 도착 안 한 건지, 도착해서 상대가 처리했는데 회신 편지만 분실된 건지** 알 수 없다. 그래서 "또 보낸다"는 위험하다. 상대가 이미 처리했다면 같은 일을 두 번 시키는 셈이니까.

> ### 이 그룹의 한 문장
> **분산 시스템에서 결과는 성공/실패가 아니라 성공/실패/모름 셋이다. 그리고 "모름"을 어떻게 다루느냐가 설계의 대부분을 결정한다.**

네 편이 각각 이 "모름"의 다른 얼굴을 다룬다.

| 편 | 어떤 "모름"인가 | 해법의 방향 |
|---|---|---|
| 제휴 API | 외부 서버 응답이 안 온다 | 재시도 대신 **확정 절차**(조회·callback) |
| Saga | 여러 단계 중 어디서 멈췄는지 | 롤백 대신 **보상**(반대 작업) |
| Kafka DLQ | DB 저장과 이벤트 발행 사이에서 죽었다 | **Outbox**로 원자성 확보, 중복은 감수 |
| Redis 대기열 | 사용자가 나간 건지 그냥 조용한 건지 | **heartbeat**로 발상을 뒤집기 |

이제 하나씩 본다.

## 1. 한 줄 정의

내 서버가 남의 서버를 부를 때, **네 가지 실패를 절대로 같은 실패로 취급하지 않는다.**

## 2. 원리 — 왜 이 문제가 생기나

### 2-1. 먼저 "재시도"가 왜 위험한지부터

위에서 본 "모름" 상황을 다시 보자. 응답이 안 왔다. 여기서 개발자가 가장 자연스럽게 하는 생각은 이것이다.

> "응답이 없네? 실패했나 보다. 다시 보내자."

**이 한 줄의 판단에 두 개의 비약이 숨어 있다.**

- 비약 1: "응답이 없다" = "실패했다" ← **틀렸다.** 모르는 것이지 실패한 게 아니다
- 비약 2: "실패했으니 다시 보내면 된다" ← 실패한 게 맞다면 옳다. 하지만 1번이 틀렸으므로 위험하다

구체적으로 뭐가 벌어지는지 시간순으로 보자.

```
10:00:00  내 서버 → 결제사: "50,000원 승인해줘"
10:00:01  결제사: 승인 완료. 고객 카드에서 50,000원 빠짐. 응답 전송
10:00:02  ⚡ 응답이 네트워크에서 유실됨
10:00:04  내 서버: 4초 지나도 응답 없음 → 타임아웃
10:00:04  내 서버: "실패했나 보다. 다시 보내자"
10:00:05  내 서버 → 결제사: "50,000원 승인해줘"
10:00:06  결제사: 승인 완료. 고객 카드에서 또 50,000원 빠짐   ← 💀
```

**고객은 10만 원을 냈다.** 그리고 내 DB에는 5만 원짜리 주문 하나만 있다. 이런 사고는 실제로 자주 난다.

### 2-2. 그래서 멱등성이 필요하다

이 문제를 푸는 개념이 **멱등성(idempotency)** 이다. 말은 어렵지만 뜻은 단순하다.

> **같은 요청을 몇 번 보내든 결과가 한 번 보낸 것과 같다.**

엘리베이터 버튼을 생각하면 된다. 다섯 번 눌러도 엘리베이터는 한 번만 온다. 그게 멱등이다.

이걸 API에서 구현하는 방법이 **멱등키(idempotency key)** 다.

```
요청에 고유한 키를 붙인다:  Idempotency-Key: request-001

상대 서버는 이렇게 동작한다:
  1. 이 키를 전에 본 적 있나? → DB 조회
  2. 있으면 → 새로 처리하지 않고 저장해 둔 결과를 그대로 반환
  3. 없으면 → 처리하고, 키와 결과를 함께 저장
```

이제 위 시나리오를 다시 돌려 보자.

```
10:00:05  내 서버 → 결제사: "50,000원 승인해줘" (키: order-12345)
10:00:06  결제사: "어? 이 키 아까 봤는데. 처리 안 하고 저번 결과 줄게"
          → 승인 완료 응답. 카드에서 추가로 빠지지 않음        ← ✅
```

> **중요한 관점 전환**
> 멱등키는 "내가 편하려고" 붙이는 게 아니다. **재시도를 안전하게 만들기 위한 전제 조건**이다.
> 멱등성 보장이 없으면 재시도를 하면 안 된다. 순서가 이렇다.

그런데 여기 현실의 벽이 있다. **외부 제휴사가 멱등키를 지원한다는 보장이 없다.** 내가 통제할 수 없는 시스템이니까. 그래서 이 프로젝트는 타임아웃에서 재시도를 아예 하지 않고 **다른 길**로 간다. (2-4에서 설명)

### 2-3. 네 가지 실패는 왜 다른 실패인가

실패를 구별하는 기준은 하나다. **상대가 나에게 뭘 알려줬는가.**

---

#### ① 타임아웃 — 상대가 아무것도 안 알려줬다

```
내 서버 ──요청──> 상대 서버
내 서버 <──  ?  ── (아무것도 안 옴)
```

**알 수 있는 것**: 없음. 상태는 **모름**.
**하면 안 되는 것**: 재시도 (2-1에서 본 이중 결제)
**해야 하는 것**: 상태를 **확정**하는 절차. 두 가지 방법이 있다.

- **조회(polling)**: "아까 그 요청 어떻게 됐어?"라고 물어본다. 상대가 조회 API를 제공해야 한다
- **callback 대기**: 상대가 나중에 "그거 성공했어"라고 알려주게 한다

이 프로젝트는 **callback 방식**을 쓴다.

---

#### ② HTTP 429 Too Many Requests — 상대가 "언제 오라"고 알려줬다

```
내 서버 ──요청──> 상대 서버
내 서버 <─429 + Retry-After: 3 ── 상대 서버
                  └─ "3초 뒤에 다시 와라"
```

429는 **네 가지 실패 중 유일하게 상대가 재시도 시점을 알려주는 실패**다. 이게 특별한 이유다.

`Retry-After` 헤더를 **무시하고 바로 재시도하면 어떻게 되나?**

상대는 이미 처리량 한계에 있다. 거기에 요청을 더 밀어 넣으면:
- 내 요청은 또 429를 받는다 (나는 실패)
- 상대는 429를 반환하는 데도 자원을 쓴다 (상대는 더 아파진다)
- 상대의 복구가 더 늦어지고, 결국 내 복구도 늦어진다

**서로 손해다.** 그래서 상대가 알려준 시간을 지키는 것이 이기적으로 봐도 옳다.

여기에 실무 디테일이 하나 더 있다. **지터(jitter)** 다.

```
문제: 100개 클라이언트가 전부 "3초 뒤"를 지킨다
      → 3초 뒤에 100개가 동시에 몰린다 → 또 터진다  (thundering herd)

해법: 3초 ± 랜덤값. 예를 들어 2.7초, 3.4초, 2.9초...로 흩어 놓는다
```

---

#### ③ HTTP 5xx Server Error — 상대가 "내가 고장났다"고 알려줬다

```
내 서버 ──요청──> 상대 서버
내 서버 <── 500 ── 상대 서버 (내부 오류)
```

**알 수 있는 것**: 상대 문제다. 일시적일 수도, 장기 장애일 수도.
**위험한 것**: **무한 재시도.**

무한 재시도가 왜 위험한지가 이 시나리오에서 가장 중요한 부분이다.

```
상대 서버가 죽었다. 응답이 안 온다.
  → 내 서버의 스레드 1이 상대를 기다린다 (묶임)
  → 사용자 요청이 계속 들어온다
  → 스레드 2, 3, 4... 전부 상대를 기다리며 묶인다
  → 내 서버의 스레드 풀이 고갈된다
  → 💀 상대와 무관한 요청(게시판 조회 등)도 처리 못 한다
```

**상대의 장애가 내 장애로 번졌다.** 이걸 **장애 전파(cascading failure)** 라고 한다.

이걸 끊는 것이 **제한 재시도 + fail-fast(빠른 포기)** 다. "N번 해보고 안 되면 즉시 포기하고 스레드를 놓아준다." 사용자에게는 "지금 이 기능은 안 됩니다"라고 빨리 답하는 게, 30초 기다리게 하다가 전체 서비스를 죽이는 것보다 낫다.

> 이 사고방식의 완성형이 **서킷 브레이커(circuit breaker)** 다. 두꺼비집과 같은 원리다.
> 실패가 일정 비율을 넘으면 **아예 호출을 시도조차 안 하고 즉시 실패**시킨다.
> 일정 시간 뒤에 딱 한 개만 흘려보내서(half-open) 살아났는지 본다.
> **이 프로젝트에는 없다.** (4번 칸 참고)

---

#### ④ 위조 callback — 상대라고 주장하는 누군가가 왔다

앞의 셋은 **내가 상대를 부르는 방향**이었다. callback은 **방향이 반대**다.

```
①②③   내 서버 ──> 상대 서버
④      내 서버 <── 누군가       ← 이게 진짜 상대가 맞나?
```

callback을 받으려면 내 서버에 공개된 주소가 있어야 한다. **공개돼 있으면 누구나 두드릴 수 있다.**

```
공격자 → 내 서버: POST /partner/callback
                  {"correlationId": "order-12345", "status": "APPROVED"}

검증이 없다면 → 결제 안 했는데 주문이 성공 처리된다 💀
```

막는 방법이 **HMAC 서명 검증**이다. 원리는 이렇다.

```
[사전 준비] 제휴사와 나만 아는 비밀키를 공유한다.  secret = "abc123..."

[제휴사가 callback 보낼 때]
  1. 보낼 내용(body)과 비밀키로 계산한다:  서명 = HMAC-SHA256(secret, body)
  2. body와 서명을 함께 보낸다

[내가 받을 때]
  1. 받은 body와 내 비밀키로 똑같이 계산한다:  내계산 = HMAC-SHA256(secret, body)
  2. 내계산 == 받은서명 ?  → 진짜 제휴사
                          → 아니면 위조
```

**왜 위조가 불가능한가?** 공격자는 비밀키를 모른다. 비밀키 없이는 올바른 서명을 만들 수 없다. body를 조금이라도 바꾸면 서명이 완전히 달라진다(해시 함수의 성질).

이 프로젝트는 `HmacSHA256` 으로 실제 구현돼 있다(`PartnerCallbackController`). 서명이 틀리면 **주문 상태를 바꾸지 않고 감사 기록만 남긴다.** 조용히 무시하지 않는 이유는, 위조 시도 자체가 보안 신호이기 때문이다.

### 2-4. 이 프로젝트가 실제로 하는 일

`PartnerApiClient` 의 재시도 정책이 위 논리를 그대로 반영한다.

| 모드 | 최대 시도 | 왜 그 횟수인가 |
|---|---|---|
| `SERVER_ERROR` (5xx) | **3회** | 일시적 장애일 수 있으니 기회는 준다. 하지만 3회에서 끊어 스레드를 놓는다 |
| `RATE_LIMIT` (429) | **2회** | `Retry-After` 만큼 쉬고 한 번 더. 상대가 알려준 시점이니 성공 확률이 높다 |
| `TIMEOUT_CALLBACK` | **1회** | **재시도하지 않는다.** 이중 결제 위험. callback으로 확정한다 |
| `NORMAL` | 1회 | 성공 |
| `BAD_SIGNATURE` | 1회 | 서명 검증에서 걸러진다 |

- 전체 응답 대기 상한: **4초** (`block(Duration.ofSeconds(4))`)
- callback 대기 상한: **2초** (`callbackRegistry.await(runId, Duration.ofSeconds(2))`)
- 실측값을 DB에 남긴다: `httpStatus`, `attemptCount`, `elapsedMs`

## 3. 대안 표와 내 선택

| 접근 | 하는 일 | 대가 | 채택 |
|---|---|---|---|
| 무한 재시도 | 될 때까지 다시 보낸다 | **장애 전파.** 상대가 죽으면 내 스레드 풀이 고갈된다 | ✗ |
| 재시도 없음 | 한 번 실패하면 끝 | 0.1초짜리 네트워크 흔들림에도 거래가 실패한다 | ✗ |
| **실패 유형별 분기** | timeout/429/5xx/위조를 각각 다르게 | 코드가 복잡해지고 테스트할 경우의 수가 늘어난다 | **✓** |
| 서킷 브레이커 도입 | Resilience4j로 자동 차단·복구 | 의존성 추가. 임계치·창 크기 튜닝이 필요 | 미도입 |

**실패 유형별 분기를 고른 이유**: 네 실패의 올바른 대응이 실제로 서로 다르다. 하나로 뭉뚱그리는 순간 **반드시 어느 하나는 틀린 대응을 하게 된다.** 예를 들어 "모든 실패에 3회 재시도"라고 하면 타임아웃에서 이중 결제가 나고, "모든 실패에 재시도 없음"이라고 하면 429에서 불필요하게 거래를 버린다.

## 4. 진위 한 줄

**✅ 실제로 돌아간다.**

- `services/partner-simulator` 라는 **별도 서비스를 진짜 HTTP로 호출**한다
- read timeout, 429 `Retry-After` 대기, 5xx 재시도가 실제로 발생한다
- callback 서명은 **진짜 HMAC-SHA256으로 검증**한다
- 실측 `elapsedMs` / `attempts` / `httpStatus` 가 DB(`tb_domain_scenario_run`)에 남는다
- 21편 중 `DomainScenarioController` 가 **유일하게 실제 서비스로 보내는** 시나리오다

**⚠️ 단, 서킷 브레이커는 없다.**

코드에 Resilience4j 같은 브레이커 라이브러리가 없다. 5xx에서 일어나는 일은 **재시도 3회 소진 후 fail-fast** 다. 개념적으로는 비슷한 효과(더 이상 시도 안 함)지만, 진짜 브레이커의 핵심인 **실패율 집계 → 일정 시간 차단 → half-open 복구 탐색** 이 없다.

**다만 화면은 이걸 정직하게 표시하고 있다.** 실제로 실행되는 `PartnerApiRehearsalService` 는 `RETRY_EXHAUSTED` 로 기록한다. `DomainScenarioEngine` 에 `CIRCUIT_OPEN` 이라고 적힌 분기가 있었지만 **컨트롤러가 `partner-api` 를 rehearsal 서비스로 보내기 때문에 한 번도 호출되지 않는 죽은 코드**였고, 2026-08-03에 지웠다. 지금은 엔진이 `partner-api` 를 받으면 예외를 던지고, 그 결정을 테스트가 고정한다.

**서킷 브레이커 미구현은 내가 먼저 말해야 한다.** 면접관이 먼저 찾으면 나머지 진짜인 부분까지 의심받는다.

## 5. 30초 구두 답변

> 외부 API 연동에서 제일 어려운 건 타임아웃입니다. 실패가 아니라 '모름'이거든요. 상대가 처리를 안 한 건지, 처리는 했는데 응답만 유실된 건지 구별이 안 됩니다. 여기서 그냥 재시도하면 이중 결제가 납니다.
>
> 그래서 실패를 네 종류로 나눠서 다르게 대응했습니다. 타임아웃은 재시도하지 않고 callback을 기다려서 상태를 확정합니다. 429는 상대가 Retry-After로 재시도 시점을 알려준 유일한 실패라 그 시간을 지켜서 한 번 더 보냅니다. 5xx는 상대 장애가 제 스레드를 묶어서 저까지 죽는 걸 막으려고 3회만 재시도하고 빠르게 포기합니다. callback은 방향이 반대라 누구나 호출할 수 있어서 HMAC-SHA256으로 서명을 검증하고, 틀리면 주문 상태를 안 바꾸고 감사 로그만 남깁니다.
>
> 다만 서킷 브레이커는 구현 안 했습니다. 화면에 그렇게 표시되는 건 재시도 소진 후 fail-fast일 뿐입니다.

## 6. 꼬리질문과 답

**Q1. 타임아웃 뒤에 그냥 재시도하면 뭐가 문제죠?**

상대가 이미 처리했을 수 있어서 중복 처리가 됩니다. 결제라면 고객 카드에서 두 번 빠집니다.

재시도를 안전하게 하려면 상대가 멱등키를 지원해서 같은 키의 요청을 한 번만 처리해 줘야 하는데, **외부 제휴사가 그걸 보장한다는 확신이 없습니다.** 제가 통제할 수 없는 시스템이니까요. 그래서 타임아웃에서는 재시도 대신 callback 대기로 상태를 확정하는 쪽을 택했습니다.

**Q2. 서킷 브레이커는 어떻게 구현하셨나요?**

**구현 안 했습니다.** 5xx에서 하는 건 재시도 3회 소진 후 fail-fast입니다. 화면에도 `RETRY_EXHAUSTED` 로 그대로 표시하고 있고요.

진짜 브레이커라면 세 가지가 더 있어야 합니다. 첫째, 실패율을 시간 창이나 요청 수 창 단위로 집계합니다. 둘째, 임계치를 넘으면 일정 시간 **호출 자체를 시도하지 않고** 즉시 실패시킵니다. 셋째, 그 시간이 지나면 half-open 상태로 요청 하나만 흘려보내서 살아났는지 확인하고, 성공하면 닫고 실패하면 다시 엽니다. Resilience4j를 붙이면 되는데 아직 안 했습니다.

**Q3. HMAC 서명이 있으면 재전송(replay) 공격도 막히나요?**

**안 막힙니다.** 서명이 유효한 요청을 그대로 복사해서 다시 보내면 그대로 통과합니다. 서명은 "위조가 아님"만 증명하지 "처음 보는 요청임"은 증명하지 않으니까요.

막으려면 두 가지 중 하나가 필요합니다. **서명 대상에 timestamp를 포함**시키고 서버에서 허용 시간창(예: 5분)을 검사하거나, **correlation ID를 한 번만 쓰도록 소비 기록**을 남기는 겁니다. 지금은 `PartnerCallbackRegistry` 가 `await` 뒤에 correlation ID를 제거하기 때문에 부분적으로만 막힙니다.

**Q4. callback을 받는 서버가 여러 대면 어떻게 되나요?**

**지금 구조로는 깨집니다.** `PartnerCallbackRegistry` 가 `ConcurrentHashMap` 이라 **JVM 메모리**에 있습니다. 1번 인스턴스가 요청을 보냈는데 callback이 로드밸런서를 통해 2번 인스턴스로 들어오면, 2번에는 그 correlation ID가 등록돼 있지 않아서 대기 중인 1번은 영원히 타임아웃됩니다.

해결하려면 대기 상태를 Redis 같은 공유 저장소에 두거나, callback을 받은 인스턴스가 Pub/Sub으로 전체에 알리거나, 애초에 동기 대기를 버리고 callback을 받으면 DB 상태만 갱신하는 비동기 구조로 가야 합니다. 마지막이 제일 정석입니다.

## 7. 모르면 인정할 선

**여기까지는 자신 있게 답한다**
- 성공/실패/모름 3분법과 그것이 왜 재시도를 위험하게 만드는지

- 장애 전파가 일어나는 메커니즘(스레드 풀 고갈)

- 여러 인스턴스 환경에서의 callback 라우팅 (문제는 정확히 알지만 안 고침)

# 2. Saga 실패 요청 추적

**시나리오 id**: `saga-observability`
**화면**: `/saga/order`
**코드**: `OrderSagaService`, `PaymentClient`, `services/payment-api`(FastAPI)

## 1. 한 줄 정의

여러 서비스에 걸친 거래가 중간에 실패했을 때, **취소가 아니라 반대 작업을 새로 실행해서** 상태를 되돌린다.

## 2. 원리 — 왜 이 문제가 생기나

### 2-1. 하나의 DB 안에서는 이게 공짜다

주문·재고·결제가 전부 같은 DB 테이블이라면 문제 자체가 없다.

```sql
BEGIN;
  INSERT INTO 주문 ...;
  UPDATE 재고 SET 수량 = 수량 - 1 ...;
  INSERT INTO 결제 ...;
COMMIT;
```

중간에 뭐가 실패하면 `ROLLBACK` 이 일어나고 **전부 없던 일이 된다.** DB가 알아서 해준다. 이게 트랜잭션의 **원자성(atomicity)** 이다. 전부 되거나 전부 안 되거나, 중간은 없다.

### 2-2. 그런데 결제사는 내 DB에 없다

현실은 이렇다.

```
주문   → 내 PostgreSQL
재고   → 내 PostgreSQL
결제   → 🌐 결제사 서버 (다른 회사, 다른 DB, 내가 통제 못 함)
배송   → 🌐 물류사 서버
```

**두 시스템에 걸친 `BEGIN` 은 존재하지 않는다.** 내가 `ROLLBACK` 을 외쳐도 결제사가 들을 리 없다.

### 2-3. 2PC라는 이론적 해법과, 그걸 안 쓰는 이유

이 문제에 대한 교과서적 답이 **2PC(Two-Phase Commit, 2단계 커밋)** 다. 결혼식 주례처럼 동작한다.

```
[1단계 - 준비]
  조정자 → 모두에게: "준비됐나?"
  각 참여자: 실제로 작업을 준비하고 자원을 잠근 뒤 "예" 또는 "아니오"

[2단계 - 확정]
  전원 "예" → 조정자: "커밋해!"  → 모두 확정
  하나라도 "아니오" → 조정자: "취소해!" → 모두 취소
```

깔끔해 보인다. 안 쓰는 이유가 셋이다.

**① 조정자가 죽으면 참여자가 멈춘다 (blocking)**

이게 가장 치명적이다. 시간순으로 보자.

```
10:00:00  조정자 → 전원: "준비됐나?"
10:00:01  참여자 A: "예" (자원을 잠근 채 대기 중)
10:00:01  참여자 B: "예" (자원을 잠근 채 대기 중)
10:00:02  ⚡ 조정자 서버 다운

이제 A와 B는?
  - 커밋하라는 말도, 취소하라는 말도 못 들었다
  - 마음대로 커밋할 수 없다 (다른 쪽이 실패했을 수도)
  - 마음대로 취소할 수도 없다 (다른 쪽이 성공했을 수도)
  → 잠금을 쥔 채로 조정자가 살아날 때까지 무한 대기 💀
```

잠긴 자원은 다른 요청도 못 쓴다. 조정자 하나가 죽으면 **전체가 멈춘다.**

**② 외부 회사가 2PC를 지원해 줄 리 없다**

2PC는 모든 참여자가 이 프로토콜을 구현해야 한다. 외부 결제사가 "저희 시스템을 당신 조정자에 맞춰 잠가 드릴게요"라고 할 리가 없다.

**③ 처리량이 무너진다**

잠금 유지 시간이 "네트워크 왕복 × 2단계"만큼 길어진다. 밀리초 단위였던 잠금이 수백 밀리초가 된다. 동시 처리량이 그만큼 떨어진다.

### 2-4. 그래서 Saga — 쪼개고, 되돌린다

Saga의 발상은 이것이다.

> **하나의 큰 트랜잭션을 여러 개의 작은 로컬 트랜잭션으로 쪼갠다.**
> **각 단계는 즉시 커밋한다** (잠금을 오래 안 쥔다).
> **중간에 실패하면, 이미 끝난 단계들을 반대 작업으로 되돌린다.**

여기서 이 시나리오의 가장 중요한 개념이 나온다.

### 2-5. ⭐ 롤백과 보상은 다르다

이걸 이해하면 Saga의 절반은 끝난 것이다.

| | 롤백 (rollback) | 보상 (compensation) |
|---|---|---|
| 무엇을 하나 | **없던 일로** 만든다 | **반대 작업을 새로 실행**한다 |
| 흔적 | 남지 않는다 | **양쪽 다 남는다** |
| 누가 하나 | DB가 자동으로 | 내가 코드로 명시적으로 |
| 가능한 범위 | 하나의 DB 안 | 시스템 경계를 넘어서 |

결제로 예를 들면 이렇게 갈린다.

```
[롤백이라면]
  결제 승인 기록  → 삭제됨. 애초에 없던 일.
  최종 상태: (아무것도 없음)

[보상이라면]
  결제 승인 기록  → 그대로 남음
  결제 취소 기록  → 새로 추가됨
  최종 상태: 승인 + 취소  (합쳐서 0원이지만 둘 다 보인다)
```

**실무에서는 반드시 보상이 맞다.** 이유가 셋이다.

1. **돈이 실제로 움직였다.** 카드사에는 이미 승인 기록이 갔다. 내 DB에서 지운다고 없어지지 않는다
2. **회계와 감사가 흔적을 요구한다.** "이 거래는 왜 취소됐나"를 나중에 설명할 수 있어야 한다
3. **고객 문의 대응**: "결제됐다는 문자 왔는데요?" → 승인과 취소가 둘 다 있어야 설명할 수 있다

> **한 문장**: 롤백은 시간을 되감는 것이고, 보상은 **되돌리는 행위를 역사에 추가**하는 것이다.

### 2-6. Saga의 두 가지 방식

| | **Orchestration (오케스트레이션)** | **Choreography (코레오그래피)** |
|---|---|---|
| 비유 | **오케스트라 지휘자** | **군무 — 각자 음악 듣고 알아서** |
| 구조 | 중앙 조정자가 각 단계를 순서대로 지시 | 각 서비스가 이벤트를 듣고 스스로 반응 |
| 흐름이 보이는 곳 | **조정자 코드 한 곳** | **어디에도 없다** (각 서비스에 흩어짐) |
| 장점 | 흐름 파악·디버깅이 쉽다 | 서비스 간 결합도가 낮다 |
| 단점 | 조정자에 로직이 집중된다 | **장애 났을 때 전체 흐름을 재구성해야 한다** |

**이 프로젝트는 Orchestration이다.** `OrderSagaService` 가 중앙에서 순서대로 지시한다.

포트폴리오·중소 규모에서는 Orchestration이 거의 항상 맞다. 흐름이 코드 한 곳에 보이는 것의 가치가 결합도보다 크기 때문이다. Choreography는 서비스가 수십 개고 팀이 나뉘어 있을 때 의미가 생긴다.

### 2-7. 실제 흐름 — 성공했을 때

```
① ORDER_CREATED        주문 행 생성 (status=CREATED)
② INVENTORY_RESERVED   재고 예약        available -1, reserved +1
③ PAYMENT_AUTHORIZED   🌐 FastAPI 결제 서비스 호출 → 승인
④ SHIPPING_REQUESTED   배송 요청 행 생성
⑤ ORDER_CONFIRMED      주문 확정 (status=CONFIRMED), 재고 확정  reserved -1
```

### 2-8. 실제 흐름 — 배송에서 실패했을 때 (보상이 도는 경우)

```
① ORDER_CREATED        ✅
② INVENTORY_RESERVED   ✅  available -1, reserved +1
③ PAYMENT_AUTHORIZED   ✅  결제 승인됨 (돈이 실제로 움직임)
④ SHIPPING_REQUESTED   ❌  실패!

    ↓ 여기서부터 보상이 역순으로 돈다

⑤ PAYMENT_CANCELLED    🔄 🌐 결제사에 취소 요청 (③을 되돌림)
⑥ INVENTORY_RELEASED   🔄 재고 예약 해제 (②를 되돌림)  available +1, reserved -1
⑦ ORDER_FAILED         주문을 실패로 표시
```

**왜 역순인가?** 나중에 잡은 자원을 먼저 놓는다. 이래야 보상 중에 또 실패했을 때 남는 상태가 단순하다. 접시를 쌓은 역순으로 치우는 것과 같다.

### 2-9. 재고에 왜 칸이 두 개인가 (`available` / `reserved`)

이게 은근히 중요한 설계 포인트다.

**만약 칸이 하나라면?**

```
결제 전에 재고를 그냥 빼버린다:  수량 100 → 99

결제 실패!  → 얼마를 돌려놔야 하지?
             "이 주문이 1개를 뺐다"는 걸 어딘가에 따로 기억해야 한다.
             그 기록이 유실되면 재고가 영원히 어긋난다.
```

**칸이 둘이면 상태 자체가 답을 갖는다.**

```
초기:       available=100  reserved=0
예약 후:    available=99   reserved=1     ← "1개가 예약 중"이라고 상태가 말한다
확정:       available=99   reserved=0     (reserved만 줄임 = 판매 확정)
실패(보상): available=100  reserved=0     (available로 되돌림)
```

`reserved` 는 **"아직 확정 안 됐지만 남에게 팔면 안 되는 수량"** 이다. 별도 기억이 필요 없고, 언제든 재고 테이블만 봐도 상태를 알 수 있다.

### 2-10. 여기도 멱등성이 있다

`run()` 의 첫 줄이 이것이다.

```java
return orderRepo.findByIdempotencyKey(request.idempotencyKey())
        .flatMap(order -> sagaRepo.findByOrderId(order.getId()).map(this::view))
        .orElseGet(() -> runNew(request));
```

**같은 멱등키로 다시 오면 새로 실행하지 않고 기존 결과를 돌려준다.** 사용자가 결제 버튼을 두 번 눌러도 주문은 하나다. 1편의 멱등성이 여기서도 똑같이 쓰인다.

### 2-11. 관측(observability)이 왜 이 시나리오의 절반인가

Saga는 단계가 여러 시스템에 흩어진다. 장애가 나면 운영자가 답해야 할 질문이 이렇다.

- 어느 단계에서 멈췄나?
- 보상은 어디까지 실행됐나?
- 결제는 취소된 게 맞나, 아직 승인 상태인가?

**이걸 한 화면에서 못 보면 운영이 불가능하다.** 그래서 세 겹으로 남긴다.

| 남기는 것 | 어디에 | 무엇을 답하나 |
|---|---|---|
| 단계 기록 | `tb_saga_step` (`compensating` 플래그로 보상 단계 구분) | "어디까지 갔나" |
| 로그 + trace | Loki(로그) + Tempo(trace), 같은 `trace_id` 로 묶임 | "각 서비스에서 무슨 일이" |
| 지표 | `jaywiki.saga.compensations` 카운터 | "보상이 얼마나 자주 도나" |

`trace_id` 로 묶는 게 핵심이다. Spring의 주문 처리와 FastAPI의 결제 처리는 **다른 프로세스, 다른 언어, 다른 로그 파일**인데, 같은 trace_id를 달고 있으면 Grafana에서 하나의 타임라인으로 볼 수 있다.

## 3. 대안 표와 내 선택

| 접근 | 대가 | 채택 |
|---|---|---|
| 단일 DB 트랜잭션 | 결제사가 내 DB에 없다. **애초에 불가능** | ✗ |
| 2PC | 조정자 장애 시 참여자 blocking, 외부 참여자 지원 불가, 처리량 저하 | ✗ |
| **Orchestration Saga** | 조정자에 로직 집중 | **✓** |
| Choreography Saga | 전체 흐름이 코드 어디에도 없어 장애 분석이 어렵다 | ✗ |

## 4. 진위 한 줄

**✅ 실제로 돌아간다.**
- DB 행이 진짜 바뀐다 (재고 `available`/`reserved` 를 화면에서 확인 가능)
- 결제는 **별도 프로세스인 FastAPI `services/payment-api` 를 진짜 HTTP로 호출**한다
- Loki/Tempo에 실제 trace가 남고 Grafana에서 교차 확인된다

**✅ 트랜잭션 경계는 2026-08-03에 고쳤다. 이 이야기 자체가 좋은 답변이 된다.**

**고치기 전**: `run()` 전체가 하나의 `@Transactional` 이었다. 그래서 두 가지 문제가 있었다.

```java
@Transactional                          // ← 여기서 시작해서
public OrderSagaView run(...) {
    ...
    payment = authorizePayment(...);     // 🌐 외부 HTTP 호출이 이 안에 있었다
    ...
}                                        // ← 여기서 한 번에 커밋
```

1. **외부 호출이 트랜잭션 안**이라 결제사가 느려지면 DB 커넥션을 쥔 채 대기했다. **이 포트폴리오의 "DB Connection Pool 고갈" 시나리오가 경고하는 바로 그 안티패턴**이었다
2. 전부 한 트랜잭션이면 예외가 나는 순간 통째로 롤백돼서 **보상 로직이 사실상 죽은 코드**가 된다. Saga는 각 단계가 이미 커밋됐다는 전제 위에 성립한다

**고친 방법**: DB 단계를 `OrderSagaSteps` 라는 별도 빈으로 빼고 각 단계에 짧은 `@Transactional` 을 걸었다. `OrderSagaService` 는 순서만 지시하고 **트랜잭션을 열지 않는다.** 결제 호출은 단계 사이, 즉 트랜잭션 밖에서 일어난다.

> Spring 프록시는 자기 자신의 메서드 호출에 트랜잭션을 걸지 못하므로 **별도 빈이어야** 한다.
> 같은 클래스 안에서 `@Transactional` 메서드를 부르면 프록시를 안 거쳐서 아무 일도 안 일어난다.

**⚠️ 남은 한계 둘은 여전히 내가 먼저 말한다.**

1. **분리된 참여자는 여전히 FastAPI 결제 하나뿐이다.** 주문·재고는 같은 DB다. 다만 이제 단계마다 커밋되므로 보상이 실제로 필요하고 실제로 동작한다
2. **중단된 saga를 복구하는 절차가 없다.** 경계를 나눈 대가로 원자성을 잃었으므로, 결제 호출 도중 프로세스가 죽으면 `STARTED` 상태의 saga가 남는다. 그걸 찾아 이어가거나 보상시키는 프로세스는 아직 없다

## 5. 30초 구두 답변

> 주문·재고·결제·배송이 서로 다른 서비스에 있으면 하나의 DB 트랜잭션으로 묶을 수 없습니다. 2PC라는 방법이 있긴 한데, 조정자가 죽으면 참여자들이 자원을 잠근 채로 무한 대기하고, 외부 결제사가 그 프로토콜을 지원해 줄 리도 없어서 현실적이지 않습니다.
>
> 그래서 Orchestration Saga로 갔습니다. 거래를 로컬 트랜잭션 단위로 쪼개서 각각 즉시 커밋하고, 중앙 조정자가 순서를 지시하다가 배송에서 실패하면 역순으로 결제 취소와 재고 해제를 실행합니다.
>
> 여기서 핵심이 롤백이 아니라 보상이라는 점입니다. 결제 승인 기록을 지우는 게 아니라 취소 기록을 새로 추가하는 겁니다. 돈은 이미 움직였고 카드사에 승인이 갔으니까, 회계랑 감사 관점에서 승인과 취소가 둘 다 남아야 합니다.
>
> 다만 지금 구현은 결제만 실제로 분리돼 있고 나머지는 같은 DB 트랜잭션 안이라, Saga의 형태를 보여주는 수준이라는 건 분명히 말씀드립니다. 외부 호출이 트랜잭션 안에 있는 것도 실제 운영이면 고쳐야 할 부분이고요.

## 6. 꼬리질문과 답

**Q1. 보상 트랜잭션도 실패하면 어떻게 하나요?**

Saga의 가장 아픈 지점입니다. 원칙은 **보상은 실패하면 안 되도록 설계한다**는 겁니다. 구체적으로는 보상 작업을 재시도 가능하고 멱등하게 만듭니다. 재고 해제 같은 건 몇 번 실행해도 결과가 같도록요.

그래도 끝내 실패하면 **자동 복구를 포기하고 사람이 개입할 대상으로 큐에 남기는 게** 정석입니다. 무한 재시도로 시스템을 갉아먹는 것보다, 건수를 격리해서 운영자에게 올리는 게 낫습니다. 1편의 DLQ와 같은 발상입니다. **지금 구현에는 그 큐가 없습니다.**

**Q2. 재고 예약이 실패한 채로 남으면요?**

타임아웃 기반 만료가 필요합니다. 예약 행에 만료 시각을 넣고 스케줄러가 주기적으로 지난 예약을 회수하는 방식입니다.

**지금 코드에는 없습니다.** 사이트의 "주문·재고·결제 확정" 시나리오에 `RESERVATION_EXPIRED` 모드로 **설계만** 그려 놨고, 그건 실행되는 코드가 아니라 고정 대본입니다.

**Q3. 트랜잭션 경계는 어떻게 잡으셨나요?**

처음에는 `run()` 전체를 하나의 `@Transactional` 로 감쌌는데, 그게 두 가지로 잘못됐습니다. 외부 결제 호출이 트랜잭션 안에 있어서 결제사가 느려지면 DB 커넥션을 쥔 채 기다렸고, 더 근본적으로는 **예외가 전파되면 통째로 롤백돼서 보상 로직이 실행될 일이 없었습니다.** Saga를 쓰는데 정작 Saga가 필요 없는 구조였던 거죠.

그래서 DB 단계를 별도 빈으로 빼고 단계마다 짧은 트랜잭션을 걸었습니다. 오케스트레이터는 트랜잭션을 아예 열지 않고 순서만 지시하고, 결제 호출은 단계 사이에서 일어납니다. 여기서 Spring 프록시가 자기 호출에는 트랜잭션을 못 건다는 점 때문에 **반드시 별도 빈이어야** 했고요.

대가로 원자성을 잃습니다. 결제 호출 도중 죽으면 재고는 예약됐는데 결제 결과가 없는 saga가 남습니다. **경계 분리는 원자성을 보상으로 바꾸는 거래**고, 그래서 중단된 saga를 찾아 정리하는 복구 프로세스가 필요한데 그건 아직 없습니다.

**Q4. Saga 인스턴스가 중간에 서버 재시작으로 멈추면요?**

멈춘 채로 남습니다. 제대로 하려면 `tb_saga_instance` 의 상태를 주기적으로 스캔해서 **일정 시간 이상 진행이 없는 saga를 찾아 이어서 실행하거나 보상시키는 복구 프로세스**가 필요합니다. 그 복구 프로세스도 여러 인스턴스에서 동시에 돌면 중복 실행되니까 잠금이 필요하고요. 지금은 없습니다.

## 7. 모르면 인정할 선

**여기까지는 자신 있게 답한다**
- 2PC를 안 쓰는 세 가지 이유, 특히 **blocking이 일어나는 정확한 메커니즘**
- 롤백과 보상의 차이를 **회계·감사 관점**으로 설명
- Orchestration/Choreography 선택 근거
- `available`/`reserved` 두 칸을 두는 이유
- 관측을 왜 Saga에 붙였는지 (`trace_id` 로 다른 프로세스를 잇는 것)
- **내 구현의 트랜잭션 경계가 잘못됐다는 자기 진단**

**여기부터는 "안 해봤습니다"라고 말한다**
- 보상 실패 시 복구 큐 / 사람 개입 워크플로
- 예약 만료 스케줄러
- 멈춘 Saga 복구 프로세스와 그 중복 실행 방지
- 이벤트 소싱(Event Sourcing) / CQRS와의 비교
- Saga 상태를 여러 인스턴스에서 동시에 진행할 때의 잠금 전략

> ### 자가 점검
> **"롤백이 아니라 보상인 이유"** 를 돈과 회계 관점으로 설명할 수 있는가.
> **"2PC에서 조정자가 죽으면 왜 참여자가 멈추나"** 를 시간순으로 설명할 수 있는가.
> **내 구현의 트랜잭션 경계 문제를 내 입으로 먼저** 꺼낼 수 있는가.

# 3. 결제 데이터 소유권 경계

**시나리오 id**: `data-ownership-boundary`
**화면**: `/scenarios` → 데이터 소유권 카드 · 근거 글은 `/wiki/msa-data-ownership-split`
**코드**: `infra/k8s/data/pg-services.yaml`(StatefulSet + NetworkPolicy), `services/payment-api`,
`tb_payment_projection` 컨슈머, 백업 CronJob 허용 목록

## 1. 한 줄 정의

**프로세스를 나눠도 한 데이터를 둘이 쓰면 경계는 그림에만 있다.** 결제 데이터의 소유권을 계정 권한과 NetworkPolicy 두 겹으로 강제하고, **강제됐다는 것을 문장이 아니라 대조군과 함께 잰 결과로** 보인다.

## 2. 원리 — 왜 이 문제가 생기나

### 2-1. 체크리스트는 다 채워져 있었는데 실질은 모놀리스였다

2026-08-17 시점에 이 프로젝트를 MSA 요건 목록에 대 보면 이랬다.

| 요건 | 상태 |
|---|---|
| 프로세스 분리 | `payment-api` 가 별도 컨테이너로 돈다 |
| 독립 배포 | 이미지가 따로 빌드·배포된다 |
| 비동기 통신 | Kafka + 트랜잭셔널 아웃박스가 있다 |
| 분산 트랜잭션 | Saga 오케스트레이션 + 보상 + 실패 주입이 있다 |
| 분산 추적 | 두 프로세스 다 OTel 로 Tempo 에 보낸다 |
| **데이터 소유권** | **없다** |

**마지막 한 칸이 나머지를 전부 무의미하게 만들고 있었다.**

결제의 원본은 모놀리스 DB 의 `tb_saga_payment`(운영 65행)에 있었고, `payment-api` 는 파이썬 `dict` 하나를 든 161줄짜리 프로세스였다. 결제 상태를 읽고 쓰는 코드가 **전부 모놀리스 안에** 있으니, 사가가 아무리 단계를 나눠도 상태는 한 덩어리였다.

> **프로세스는 나뉘었는데 데이터가 한 덩어리면, 경계는 그림에만 있고 어느 쪽 코드든 상대의 상태를 읽고 고칠 수 있다.**

### 2-2. 요건은 「누가 쓰는가」이지 「어디에 있는가」가 아니다

**물리적으로 다른 DB 여야 한다는 말이 아니다.** 한 테이블의 주인이 하나면 스키마로 나누든 같은 인스턴스에 DB 만 나누든 소유권은 선다.

그래서 이 결정은 두 층으로 갈린다. **위층은 「소유권을 나눈다」는 결정이고, 아래층은 「그것을 무엇으로 강제할 것인가」다.** 인스턴스를 나눈 것은 아래층의 선택이지 요건이 아니다.

면접에서 이 구분을 먼저 말하는 것이 중요하다. 안 그러면 「MSA 하려고 DB 를 쪼갰다」는, 흔하고 근거 없는 주장으로 들린다.

### 2-3. 소유권이 없으면 생기는 실제 버그

이 상태가 버그도 하나 품고 있었다. `payment-api` 를 **재시작하면 메모리가 비어서**, 그 전 주문의 보상 취소가 404 로 떨어졌다. 결제 서비스가 한 번이라도 재시작하면 **그 전 주문들의 보상이 깨져 있었다는 뜻**이다.

분리는 비용만 늘린다는 통념에 대한 반례가 여기서 나온다 — **자기 데이터를 자기 DB 에 들게 하는 것만으로 이 버그가 사라진다.**

### 2-4. 가장 아팠던 자리는 조회 한 줄이었다

주문 화면을 그릴 때 모놀리스가 이렇게 읽었다.

```
paymentRepo.findByOrderId(orderId)   ← 같은 트랜잭션, 같은 DB, 항상 최신
```

**이 한 줄이 있는 한 결제 데이터의 주인은 모놀리스다.** 자르면 이 조회가 프로세스 경계를 넘고, 그 순간 **타임아웃·재시도·결과적 일관성이 전부 따라온다.**

> **그 비용을 어디서 낼지가 이 결정의 본론이다.** 「나눌까 말까」가 아니라 「나눈 대가를 읽기에서 낼까 쓰기에서 낼까」다.

고른 답: **쓰기(승인·취소)는 동기 HTTP, 읽기는 이벤트로 채우는 읽기 전용 사본(`tb_payment_projection`).** 쓰기는 즉답이 필요하지만 읽기까지 같은 경로일 이유가 없다.

### 2-5. 강제는 두 겹 — 한 겹이면 증명할 수 없다

| 층 | 수단 | 위반하면 |
|---|---|---|
| 애플리케이션 | DB 계정 권한 | 붙어도 권한이 없다 |
| 네트워크 | NetworkPolicy | **애초에 패킷이 안 닿는다** |

첫 겹의 알맹이는 `revoke` 두 줄이다. **PostgreSQL 은 `PUBLIC` 이 기본으로 아무 DB 에나 `CONNECT` 를 갖기 때문에, 계정을 나눠 만들기만 해서는 분리가 이름뿐이다.**

```
create role payment_svc login password '...';
create database payment owner payment_svc;
revoke connect on database payment from public;   ← 이 줄이 없으면 아무나 붙는다
grant connect on database payment to payment_svc;
```

둘째 겹은 `pg-services` 파드에 건 NetworkPolicy 다. 허용 목록은 `payment-api`, `shipping-api`, **백업 CronJob 파드** 셋이고 나머지는 전부 거부다 — **모놀리스 포함.**

**백업 파드를 넣은 것은 사족이 아니다.** 빠뜨리면 정책이 백업 접속까지 막아서 **결제 데이터가 백업에서 조용히 빠진다.** 데이터가 인스턴스 둘로 갈리는 순간 백업 대상도 같이 늘려야 한다.

### 2-6. 읽기 전용 사본의 규칙 셋

사본은 「이벤트를 받아 쓰면 된다」로 끝나지 않는다. 조용히 틀리는 자리가 셋 있다.

| 규칙 | 안 지키면 |
|---|---|
| 유니크는 `payment_id` 가 아니라 **`order_id`** 에 건다 | 화면 조회가 주문 기준이라, 한 주문에 사본이 둘이면 **어느 쪽을 보여줄지 정할 수 없다** |
| 늦게 온 과거 이벤트는 **`occurred_at` 비교로 걸러** 최신을 안 덮는다 | 재전송된 옛 이벤트가 최신 상태를 되돌린다 |
| `event_type` 으로 거르지 않고 **payload 의 `status` 를 그대로 반영** | 승인만 받고 취소를 빠뜨리면 **화면이 취소된 결제를 `AUTHORIZED` 로 계속 보여준다** |

셋 다 「터지지 않고 조용히 틀리는」 종류다. 그래서 규칙으로 박아 뒀다.

`payment-api` 쪽에서도 승인과 취소 **양쪽이** 아웃박스에 이벤트를 남기고, **결제 저장과 아웃박스 기록은 반드시 한 트랜잭션**이다(이중 쓰기 문제 — 02의 Kafka 편과 같은 원리).

## 3. 대안 표와 내 선택

| 안 | 얻는 것 | 대가 | 판단 |
|---|---|---|---|
| **스키마·DB 만 분리** (같은 인스턴스) | 백업·모니터링·업그레이드가 안 늘어난다. **실무 다수가 이쪽이고 대체로 옳다** | 강제 수단이 **계정 한 겹뿐.** NetworkPolicy 의 `podSelector` 는 파드 라벨을 보는데 같은 파드에 붙으면 구분할 대상이 없다 | 기각 — 보여줄 증거가 "그렇게 안 썼습니다" 뿐이 된다 |
| **인스턴스 둘** (`pg-payment`·`pg-shipping`) | payment ↔ shipping 사이 네트워크 차단 한 칸 | 파드 하나와 **백업 대상 하나가 는다** | 기각 — 그 둘은 서로 조인할 일이 없고, 이 설계의 주제는 인스턴스 하나로도 선다 |
| **조회를 동기 호출로 통일** | 항상 최신 | `payment-api` 가 죽으면 **주문 화면도 같이 죽는다.** 분리 전 조회가 스팬 5 / 서비스 1 / 9.00ms 였는데 여기에 원격 왕복과 실패 가능성을 얹는다 | 기각 — 장애 격리를 죽인다 |
| **인스턴스 하나(`pg-services`) + 계정 + NetworkPolicy** | 두 겹 강제, **증명 가능** | 백업 대상 하나 증가, 결과적 일관성 | **채택** |

**흔히 드는 근거 하나를 일부러 뺐다.** 「인스턴스를 나누면 다른 노드로 옮길 수 있다」는 이 환경에서 성립하지 않는다 — miniPC 는 노드가 하나라 postgres 를 몇 개로 띄워도 같은 커널, 같은 디스크, 같은 전원이다. **그 이점을 근거로 쓰면 거짓말이라, 나눈 이유는 NetworkPolicy 하나만 남는다.**

## 4. 진위 한 줄

> **✅ 실제 실행.** 다만 이 그룹의 다른 편들과 성격이 다르다 — **실행이 아니라 상시 구성이라 확인이 명령이다.**
> 버튼을 누르는 편이 아니라, 같은 명령을 세 곳에서 돌려 결과를 대조하는 편이다.
> 2026-08-17 운영 실측이고, `SCENARIO_EXECUTION` 에도 `LIVE_VERIFIED_BY_COMMAND` 로 따로 표시돼 있다.

| 어디서 → 어디로 | 결과 |
|---|---|
| 모놀리스 → `pg-services:5432` | **거부** |
| 모놀리스 → `pg-postgresql:5432` | 통과 |
| `payment-api` → `pg-services:5432` | 통과 |

**대조군 둘을 같이 잰 것이 이 표의 요점이다.** 거부 한 줄만 보면 「서비스가 죽어서 난 거부」와 구분이 안 된다. 같은 모놀리스가 자기 DB 에는 붙고, 같은 `pg-services` 에 `payment-api` 는 붙는데 모놀리스만 막히므로, **막는 주체가 정책이라는 것이 세 줄로 갈린다.**

데이터도 실제로 갈렸다. 배포 직후 `pg-services` 의 payment DB 에 `tb_payment` 3행과 아웃박스 SENT 5건, `portfolio` 에는 `tb_saga_payment` 가 **없고** `tb_payment_projection` 3행이었다. 보상 경로에서는 **모놀리스가 취소 상태를 한 글자도 쓰지 않는데** `payment-api` 가 낸 이벤트만으로 8~9초 뒤 화면이 `CANCELLED` 로 따라왔다 — **소유권이 실제로 넘어갔다는 증거가 이 한 줄이다.**

조회 경로의 모양은 안 변했다. 분리 후에도 주문 조회 트레이스는 **스팬 5 / 서비스 1** 이다. 동기 호출이 어디선가 새어 들어갔다면 여기서 스팬이 늘거나 서비스가 둘로 보였을 것이다.

## 5. 30초 구두 답변

> MSA 요건을 목록으로 대 보면 프로세스 분리, 독립 배포, Kafka, 사가, 분산 추적까지 다 채워져 있었는데 **데이터 소유권 한 칸이 비어 있었습니다.** 결제 원본이 모놀리스 DB 에 있었고 결제 서비스는 파이썬 dict 하나를 든 161줄짜리였거든요. **프로세스는 나뉘었는데 데이터가 한 덩어리면 경계는 그림에만 있습니다.**
>
> 다만 **물리적으로 다른 DB 여야 한다는 뜻은 아니라고 봅니다.** 요건은 「누가 쓰는가」이지 「어디에 있는가」가 아니어서요. 그래서 소유권을 나눈다는 결정과, 그걸 무엇으로 강제할 것인가를 갈라서 판단했습니다.
>
> 강제는 두 겹으로 했습니다. **DB 계정 권한**과 **NetworkPolicy** 입니다. 한 겹만 있으면 위반이 가능하거나, 가능하지 않다는 걸 증명할 수 없어서요. 계정 쪽에서 놓치기 쉬운 게 **PostgreSQL 은 PUBLIC 이 기본으로 CONNECT 를 갖는다는 점**이라, `revoke connect ... from public` 이 없으면 계정을 나눠도 이름뿐입니다.
>
> 그리고 **막혔다는 걸 대조군 셋으로 쟀습니다.** 모놀리스는 새 DB 에 거부되고, 자기 DB 에는 붙고, 같은 새 DB 에 결제 서비스는 붙습니다. 거부 한 줄만 보이면 서비스가 죽은 건지 정책인지 구분이 안 되니까요. 차단이 타임아웃이 아니라 **Connection refused** 로 나는 것도 실측에서 알았습니다 — k3s 의 kube-router 가 드롭이 아니라 REJECT 를 하더군요.

## 6. 꼬리질문과 답

**Q1. 그냥 스키마만 나눠도 되지 않나? 인스턴스를 늘린 값은 했나?**

**대체로는 스키마 분리가 옳다고 봅니다.** 백업·모니터링·업그레이드가 N배가 되지 않으니까요. 실무 다수가 그렇게 합니다.

여기서 인스턴스를 나눈 이유는 하나뿐입니다. **NetworkPolicy 의 `podSelector` 는 파드 라벨을 보기 때문에, 모놀리스와 서비스가 같은 postgres 파드에 붙으면 네트워크 층에서 구분할 대상 자체가 없습니다.** 그러면 강제가 계정 한 겹으로 줄고, **보여줄 증거가 "그렇게 안 썼습니다" 뿐이 됩니다.**

반대로 **인스턴스를 둘로 더 쪼개는 안은 기각했습니다.** 더 얻는 게 payment ↔ shipping 사이 차단 한 칸뿐인데 그 둘은 서로 조인할 일이 없고, 그 한 칸 값으로 **백업 대상이 하나 늘기** 때문입니다. 백업은 이 설계가 리스크로 꼽은 자리라서요.

그리고 되돌리기 쉬운 쪽을 나중으로 미뤘습니다. **`pg-services` 하나에서 인스턴스 둘로 가는 건 나중에 쉽습니다** — `pg_dump` 하나와 커넥션 문자열 교체면 되고 두 DB 가 조인하지 않으니 엉킬 게 없습니다. 반대 방향은 그때쯤 서비스들이 같은 커넥션으로 조인하고 있어 어렵습니다.

**Q2. 읽기를 사본으로 바꾸면 화면이 옛 데이터를 보여주는데, 그건 괜찮은가?**

**괜찮지 않고, 비용을 지불하기로 한 자리입니다.** 취소 직후 잠깐 화면에 `AUTHORIZED` 가 남습니다. 모놀리스가 즉시 쓰지 않고 이벤트를 기다리기 때문이고, 실측으로 8~9초였습니다.

**버그가 아니라 성질인데, 처음 보는 사람에게는 틀린 화면으로 읽힙니다.** 그래서 화면이 그 지연을 감추지 않고 **기준 시각과 함께 표시**합니다.

동기 호출이면 항상 최신이지만 `payment-api` 가 죽을 때 주문 화면도 같이 죽습니다. **쓰기는 즉답이 필요해서 동기 HTTP 로 두고, 읽기만 사본으로 낸** 이유가 이 비대칭입니다.

사본 쪽에서 조용히 틀리는 자리가 셋 있어서 규칙으로 박아 뒀습니다. 유니크를 `payment_id` 가 아니라 **`order_id`** 에 걸고(화면 조회가 주문 기준이라), 늦게 온 이벤트는 `occurred_at` 으로 거르고, **`event_type` 이 아니라 payload 의 `status` 를 그대로 반영**합니다. 마지막 게 중요한데, 승인만 받고 취소를 빠뜨리면 화면이 취소된 결제를 계속 승인으로 보여주거든요.

**Q3. 분리했다는 걸 어떻게 증명하나? 코드 리뷰로는 안 되나?**

코드 리뷰는 **「지금 코드가 그렇게 안 한다」**는 것만 보여줍니다. 다음 커밋에 누가 한 줄 넣으면 끝입니다.

그래서 **런타임에서 강제되는지를 명령으로 확인**합니다. 같은 `psql` 접속을 세 곳에서 돌려 결과를 대조합니다.

```
모놀리스 → pg-services     Connection refused   ← 정책이 막는다
모놀리스 → pg-postgresql   통과                 ← 모놀리스가 살아 있다는 대조군
payment-api → pg-services  통과                 ← pg-services 가 살아 있다는 대조군
```

**대조군이 없으면 첫 줄은 아무것도 증명하지 않습니다.** 서비스가 죽어도 같은 메시지가 나오니까요.

그리고 **차단이 `Connection refused` 로 난 게 예상 밖이었습니다.** 설계 때는 타임아웃을 예상했는데, k3s 의 kube-router 가 패킷을 드롭하지 않고 REJECT 하기 때문이더군요. **실측이 예상을 고쳐 준 자리**라 그대로 적어 뒀습니다.

## 7. 모르면 인정할 선

**답할 수 있다**

- MSA 요건 목록에서 데이터 소유권이 왜 다른 칸들을 무의미하게 만드는지
- 「누가 쓰는가」와 「어디에 있는가」의 구분, 그리고 인스턴스 분리가 요건이 아니라 수단인 이유
- `revoke connect from public` 이 없으면 계정 분리가 이름뿐인 이유
- 대조군 셋으로 재는 이유와, 차단이 `Connection refused` 인 이유
- 읽기 사본의 규칙 셋과 각각이 안 지켜졌을 때 조용히 틀리는 방식
- 되돌리는 경로와, 되돌리기 쉬운 쪽을 나중으로 미룬 기준

**"안 해봤습니다"**

- **미결 결제를 자동으로 맞추는 절차.** 결제에 못 닿아 취소가 실패하면 그 건은 미결로 남고 경고 로그와 알림이 가리키기만 한다. **자동 정합 절차가 없다**
- **물리적 격리 주장.** 노드가 하나라 두 겹 강제는 논리적 격리다. 커널이 뚫리면 같이 뚫린다
- **서비스끼리의 네트워크 층 증거.** payment ↔ shipping 은 계정 한 겹뿐이고, 네트워크 증거는 모놀리스 쪽에만 있다
- **여러 서비스로 확장했을 때의 스키마 진화·계약 관리.** 서비스가 둘이라 아직 문제가 안 됐다

> ### 자가 점검
> **「프로세스는 나뉘었는데 데이터가 한 덩어리면」** 을 자기 문장으로 말할 수 있는가.
> **인스턴스를 나눈 이유가 NetworkPolicy 하나뿐**이라는 것과, 노드가 하나라 못 쓰는 근거가 무엇인지 말할 수 있는가.
> **대조군 없이 거부 한 줄만 보이면 무엇과 구분이 안 되는지** 답할 수 있는가.
> 읽기 사본의 **세 규칙과 각각이 깨질 때의 증상**을 말할 수 있는가.

# 4. 주문 이벤트 fan-out과 DLQ

**시나리오 id**: `kafka-dlq`
**화면**: `/kafka/order`
**코드**: `KafkaDemoOrderService`, `KafkaDemoOutboxRelay`, `KafkaDemoConsumers`

## 1. 한 줄 정의

주문 저장과 후속 처리를 분리해서, **알림 서비스가 죽어도 주문은 살아 있게** 만든다.

## 2. 원리 — 왜 이 문제가 생기나

### 2-1. ⭐ 이중 쓰기 문제 (dual write)

이 시나리오의 출발점이자 가장 중요한 개념이다.

주문을 저장하고 Kafka에 이벤트를 보낸다고 하자. 가장 자연스럽게 짜면 이렇다.

```java
orderRepository.save(order);              // 1. DB에 저장
kafkaTemplate.send("orders", event);      // 2. Kafka에 발행
```

**1과 2 사이에서 서버가 죽으면 어떻게 되나?**

```
10:00:00  주문 DB 저장 완료 ✅ (커밋됨, 되돌릴 수 없음)
10:00:01  ⚡ 서버 다운
          → Kafka 발행 안 됨

결과: 주문은 DB에 있는데 이벤트가 없다
      → 재고 안 줄어듦
      → 알림 안 감
      → 집계에 안 잡힘
      → 영원히. 아무도 모른다. 💀
```

**"그럼 순서를 바꾸면?"**

```java
kafkaTemplate.send("orders", event);      // 1. 먼저 발행
orderRepository.save(order);              // 2. 그 다음 저장
```

```
10:00:00  Kafka 발행 완료 ✅
10:00:01  ⚡ DB 저장 실패

결과: 존재하지 않는 주문에 대한 알림이 고객에게 발송된다 💀 (더 나쁘다)
```

**"트랜잭션으로 묶으면?"**

```java
@Transactional
void createOrder() {
    orderRepository.save(order);
    kafkaTemplate.send("orders", event);   // ← Kafka는 DB 트랜잭션에 참여하지 않는다
}
```

**안 된다.** `@Transactional` 은 DB에만 적용된다. Kafka는 이미 발행된 메시지를 "롤백"할 수 없다. 롤백돼도 메시지는 나가 있다.

> ### 문제의 뿌리
> **서로 다른 두 시스템에 원자적으로(둘 다 되거나 둘 다 안 되게) 쓸 방법은 없다.**
> 이건 라이브러리로 해결되는 문제가 아니라 구조로 우회해야 하는 문제다.

### 2-2. Outbox 패턴 — 두 시스템을 하나로 만든다

발상이 아주 단순하고 아름답다.

> **Kafka에 바로 보내지 말고, 같은 DB의 테이블에 "보낼 메시지"를 적어 둔다.**
> 그러면 "주문 저장"과 "이벤트 기록"이 **같은 DB, 같은 트랜잭션**이라 원자적이다.
> 별도 프로세스가 나중에 그 테이블을 읽어서 Kafka로 보낸다.

Outbox는 "발신함"이라는 뜻이다. 편지를 우체통에 넣는 것과 같다. 우체부가 언제 가져갈지는 몰라도, **넣었다는 사실은 확실하다.**

```java
// 1단계: 주문과 이벤트를 같은 트랜잭션으로 저장
@Transactional
void createOrder() {
    orderRepository.save(order);           // 같은
    outboxRepository.save(event);          // 트랜잭션
}                                           // → 둘 다 커밋되거나 둘 다 롤백. 중간 없음 ✅

// 2단계: 별도 스케줄러가 폴링해서 발행 (KafkaDemoOutboxRelay)
@Scheduled(fixedDelay = 2초)
void publishPending() {
    // status='NEW' 인 행을 10개씩 읽어서
    // → Kafka로 발행
    // → 성공하면 status='PUBLISHED' 로 갱신
}
```

**이제 유실이 없다.** 서버가 언제 죽든, 주문이 DB에 있으면 outbox 행도 반드시 있고, 릴레이가 살아나면 발행한다.

### 2-3. ⭐ 대신 새로운 성질이 생긴다 — at-least-once

공짜는 없다. Outbox는 유실을 없애는 대신 **중복 가능성**을 만든다. 정확히 어느 지점에서 그런지 보자.

릴레이의 발행 코드는 두 단계다.

```java
kafkaTemplate.send(topic, payload).get(5, SECONDS);   // ① Kafka에 발행
jdbcTemplate.update("update ... set status='PUBLISHED' ...");  // ② 상태 갱신
```

**①과 ② 사이에서 죽으면?**

```
10:00:00  ① Kafka 발행 성공 ✅  (메시지는 이미 Kafka에 있다)
10:00:00  ⚡ 릴레이 프로세스 다운
          ② status 갱신 안 됨 → DB에는 여전히 status='NEW'

10:00:30  릴레이 재시작
          → status='NEW' 인 행을 읽는다 → 아까 그 행이 또 있다
          → ① 같은 메시지를 Kafka에 또 발행 💥 중복!
```

**이건 버그가 아니라 필연이다.** ①과 ②는 서로 다른 시스템이라 원자적으로 묶을 수 없다 — **2-1의 이중 쓰기 문제가 여기서 또 나온다.** 다만 이번에는 유실이 아니라 중복 쪽으로 기울였을 뿐이다.

| 보장 | 뜻 | 대가 |
|---|---|---|
| at-most-once (최대 한 번) | 중복은 없지만 **유실될 수 있다** | 주문이 사라진다 |
| **at-least-once (최소 한 번)** | 유실은 없지만 **중복될 수 있다** | 중복 처리 대비 필요 |
| exactly-once (정확히 한 번) | 이상적 | **DB 상태 변경까지 포함하면 사실상 불가능** |

**Outbox는 at-least-once를 선택한 것이다.** 그리고 이 선택이 강제하는 결론이 하나 있다.

> ### 그래서 consumer는 반드시 멱등해야 한다
> 같은 이벤트를 두 번 받아도 재고가 두 번 줄면 안 된다.
> 구현: 이벤트마다 고유 ID를 두고 처리 기록을 남긴다. 이미 처리한 ID면 건너뛴다.

**왜 유실보다 중복을 택하나?** 중복은 코드로 막을 수 있지만(멱등 처리), 유실은 **아무도 모른다.** 주문이 사라진 걸 알아채는 방법 자체가 없다. 그래서 분산 시스템은 거의 항상 중복 쪽을 택한다.

### 2-4. consumer group — "복사"와 "분담"의 차이

Kafka에서 가장 많이 헷갈리는 부분이다. 이 프로젝트에는 group이 셋 있다.

```
topic: orders  (주문 이벤트가 여기로 발행됨)
  │
  ├─ group: ...-inventory      재고 반영
  ├─ group: ...-notification   알림 발송
  └─ group: ...-analytics      집계
```

**핵심 규칙 하나만 외우면 된다.**

> **group이 다르면 복사(각자 다 받는다). group이 같으면 분담(하나만 받는다).**

```
[group이 다를 때 = fan-out]
  주문 이벤트 1개 발행
    → inventory group 이 받음     ✅
    → notification group 이 받음   ✅  (같은 메시지를 또)
    → analytics group 이 받음      ✅  (또)
  = 각자 독립적으로 전부 처리

[group이 같을 때 = 분산 처리]
  같은 group에 인스턴스 3개
  주문 이벤트 3개 발행
    → 인스턴스 A가 1번
    → 인스턴스 B가 2번
    → 인스턴스 C가 3번
  = 나눠서 처리. 같은 메시지를 둘이 받지 않는다
```

**왜 이렇게 되나?** Kafka는 **오프셋(offset)** — "이 group이 어디까지 읽었는지" — 을 **group마다 따로 관리**하기 때문이다.

```
topic의 메시지:  [1] [2] [3] [4] [5] [6] ...

inventory group 오프셋:     ────────────> 200번째 읽는 중
notification group 오프셋:  ──> 100번째에서 막힘 ❌
analytics group 오프셋:     ──────────────> 205번째 읽는 중
```

### 2-5. ⭐ 이게 이 시나리오의 핵심 가치 — 실패 격리

위 그림이 이 시나리오가 증명하려는 것이다.

> **알림 consumer가 100번째에서 막혀 있어도, 재고 consumer는 200번째를 처리하고 있다.**

동기 호출이었다면 이렇게 됐을 것이다.

```
[동기 방식]
  주문 저장 → 재고 차감 호출 → 알림 발송 호출 → 집계 호출 → 응답
                                    ↑
                            알림 서버가 죽어 있으면?
                            → 여기서 예외 → 주문 전체 실패 💀
                            → 알림이 안 되면 주문도 못 받는다
```

**알림이 안 간다고 주문을 못 받는 건 말이 안 된다.** 중요도가 완전히 다른 두 작업이 하나의 실패 운명을 공유하고 있었다. 이벤트로 분리하면 그 결합이 끊긴다.

### 2-6. ⭐ DLQ — poison pill을 격리한다

이제 마지막 개념이다. 알림 consumer가 100번째에서 막혔다고 했다. **왜 막히나?**

Kafka는 파티션 안에서 **순서를 보장**한다. 그 대가로, 어떤 메시지 하나가 계속 실패해서 오프셋이 안 넘어가면:

```
[1] [2] ... [99] [100] [101] [102] [103] ...
                  ↑
              계속 실패
              오프셋이 안 넘어감
              → 101, 102, 103... 전부 대기 💀
```

**메시지 하나가 그 뒤의 모든 메시지를 막는다.** 이걸 **poison pill(독이 든 알약)** 이라고 부른다. 잘못된 형식의 메시지 하나가 파티션 전체를 세우는 일은 실무에서 정말 자주 난다.

**DLQ(Dead Letter Queue, 실패 격리 대기열)** 가 이걸 끊는다.

```
[100번 메시지가 N번 재시도해도 실패]
  → 100번을 별도 topic(DLQ)으로 옮긴다
  → 오프셋을 101로 넘긴다
  → 101, 102, 103... 다시 흐른다 ✅
  → 100번은 DLQ에 모여 있으니 나중에 원인 보고 재처리
```

> ### DLQ의 본질
> **실패를 없애는 장치가 아니다. 실패를 한곳에 가둬서 나머지를 살리는 장치다.**
> 병원의 격리 병동과 같다. 병을 고치는 게 아니라 번지는 걸 막는다.

### 2-7. 재시도로 될 실패 vs 안 될 실패

DLQ를 제대로 쓰려면 이 구별이 필요하다. 프로젝트의 두 모드가 정확히 이걸 보여준다.

| 모드 | 동작 | 실무에서 이런 경우 | 올바른 대응 |
|---|---|---|---|
| `NOTIFICATION_RETRY` | 1회차만 실패, 2회차 성공 | 네트워크 순간 끊김, 상대 서버 재시작, 일시적 부하 | **재시도** — 곧 될 일이다 |
| `NOTIFICATION_ALWAYS_FAIL` | 계속 실패 | 메시지 형식 오류, 삭제된 사용자, 코드 버그 | **DLQ** — 몇 번을 해도 안 된다 |

**이 구별을 못 하면 두 가지 사고가 난다.**

- 재시도로 될 실패를 바로 DLQ로 보냄 → 멀쩡한 건들이 DLQ에 쌓여 불필요한 수작업이 생긴다
- 영구 실패를 무한 재시도 → **파티션이 멈춘다** (2-6의 poison pill)

## 3. 대안 표와 내 선택

| 접근 | 하는 일 | 대가 | 채택 |
|---|---|---|---|
| 동기 호출 | 주문 저장하며 알림·재고를 직접 호출 | **알림 장애 = 주문 실패.** 응답도 느려진다 | ✗ |
| DB 커밋 후 바로 Kafka 발행 | 트랜잭션 끝나고 발행 | **이중 쓰기 문제.** 사이에서 죽으면 이벤트 유실 | ✗ |
| **Outbox 폴링 릴레이** | 같은 트랜잭션에 기록 후 별도 발행 | 폴링 지연(최대 2초), at-least-once라 consumer 멱등 필요 | **✓** |
| CDC (Debezium) | DB의 WAL(변경 로그)을 읽어 즉시 발행 | 폴링 지연 없음. 하지만 컴포넌트·운영 부담 추가 | 과함 |

**Outbox 폴링을 고른 이유**: 유실을 없애면서 **추가 인프라가 전혀 필요 없다.** 스케줄러 하나면 된다. 2초 지연은 주문 알림 용도에 충분하고, CDC는 이 규모에 과하다. 트래픽이 훨씬 커지고 지연이 문제가 되면 그때 CDC로 옮기면 되며, **Outbox 테이블 구조는 그대로 쓸 수 있다.**

## 4. 진위 한 줄

**✅ 실제로 돌아간다.**
- 진짜 Kafka topic에 발행된다
- consumer group 3개가 실제로 각자 소비한다
- 재시도와 DLQ 이동이 실제로 일어난다
- `tb_outbox_event` 의 `status` / `attempt_count` / `last_error` 가 실제로 갱신된다
- 지표가 실제로 나간다 (`outboxPublished`, `outboxPublishFailed`)

## 5. 30초 구두 답변

> 주문을 저장하고 Kafka에 바로 발행하면 그 사이에서 서버가 죽었을 때 이벤트가 유실됩니다. 서로 다른 두 시스템에 원자적으로 쓸 방법이 없거든요. 트랜잭션으로 묶어도 Kafka는 DB 트랜잭션에 참여하지 않아서 소용없습니다.
>
> 그래서 Outbox 패턴을 썼습니다. 이벤트를 같은 DB의 outbox 테이블에 주문과 같은 트랜잭션으로 저장하고, 별도 릴레이가 2초마다 폴링해서 Kafka로 보냅니다. 이러면 유실이 없어집니다. 대신 발행에는 성공했는데 상태 업데이트 직전에 죽으면 중복 발행되니까 at-least-once가 되고, consumer는 멱등해야 합니다. 유실은 아무도 모르지만 중복은 코드로 막을 수 있어서 이쪽을 택했습니다.
>
> Consumer는 group을 셋으로 나눠서 재고·알림·집계가 오프셋을 각자 관리하게 했습니다. 알림이 막혀도 재고는 계속 진행됩니다. 그리고 알림이 영구 실패하면 오프셋이 안 넘어가서 뒤 메시지가 전부 막히니까, 재시도 후 DLQ로 옮겨서 나머지를 흐르게 합니다.

## 6. 꼬리질문과 답

**Q1. 릴레이를 여러 인스턴스로 띄우면 어떻게 되나요?**

**예전에는 중복 발행됐습니다. 2026-08-03에 고쳤습니다.**

원래 쿼리가 `status='NEW'` 인 행을 `limit 10` 으로 **읽기만 하고 잠그지 않아서**, 두 인스턴스가 같은 행을 둘 다 가져가 둘 다 발행했습니다. replica가 1대라 안 드러났는데 HPA maxReplicas가 2라 언제든 터질 수 있었고요.

고친 방식은 **선점(claim)** 입니다. `update ... set status='CLAIMED' where id in (select ... for update skip locked) returning ...` 한 문장으로 대상을 표시하면서 가져옵니다. 한 문장이라 확인과 표시 사이에 끼어들 수 없고, `skip locked` 는 이미 잠긴 행을 기다리지 않고 건너뛰니까 두 인스턴스가 서로 다른 행을 가져갑니다.

여기서 중요하게 판단한 게 하나 있습니다. **선점 트랜잭션 안에서 Kafka로 발행하면 안 됩니다.** send가 최대 5초를 기다리는데 그동안 행 잠금과 DB 커넥션을 쥐고 있게 되거든요. Saga에서 고친 것과 같은 문제라서, 선점은 짧은 트랜잭션으로 끝내고 발행은 그 밖에서 합니다.

대신 새 문제가 생깁니다. 선점하고 발행 전에 죽으면 그 행이 `CLAIMED` 로 영원히 남습니다. 되돌려 줄 주체가 없으니까요. 그래서 `claimed_at` 컬럼을 추가하고, **60초가 지난 선점은 다음 릴레이가 회수**하도록 했습니다. 발행에 실패하면 `NEW` 로 되돌리고요.

**Q2. exactly-once는 어떻게 하나요?**

Kafka 트랜잭션과 idempotent producer를 쓰면 **브로커까지는** 가능합니다. 하지만 "메시지를 받아서 DB 상태를 바꾸는 것"까지 포함한 진짜 exactly-once는 사실상 불가능합니다. Kafka 오프셋 커밋과 DB 커밋이 또 이중 쓰기 문제거든요.

현실적인 답은 **at-least-once + consumer 멱등**입니다. 이벤트에 고유 ID를 두고 `처리된_이벤트` 테이블에 기록해서, 이미 있는 ID면 건너뜁니다. "정확히 한 번 전달"이 아니라 **"여러 번 받아도 결과는 한 번"** 으로 목표를 바꾸는 겁니다.

**Q3. DLQ에 쌓인 건 어떻게 재처리하나요?**

**지금은 기록만 남깁니다.** `dlq()` consumer가 `recordDlq()` 로 이력을 남기는 게 전부입니다.

실무라면 셋이 필요합니다. 첫째, 원인을 수정한 뒤 **원본 topic으로 재발행**하는 경로. 둘째, DLQ 메시지를 골라서 재처리하거나 폐기하는 **운영 도구**. 셋째, **DLQ 적재량에 알람** — 아무도 안 보면 DLQ는 쓰레기통이 됩니다.

솔직히 **DLQ는 만드는 것보다 쌓인 걸 처리하는 운영 절차가 훨씬 중요한데**, 거기까지는 안 했습니다.

**Q4. 파티션이 여러 개면 순서 보장은요?**

**파티션 안에서만 보장됩니다.** topic 전체의 순서는 보장되지 않습니다.

그래서 **파티션 키 설계**가 중요합니다. 이 프로젝트는 `orderId` 를 키로 발행하는데, 같은 키는 항상 같은 파티션으로 가니까 **한 주문의 이벤트들끼리는 순서가 보장**됩니다. 서로 다른 주문 간 순서는 보장 안 되지만 그건 필요도 없고요. "순서가 필요한 단위"를 파티션 키로 잡는 게 원칙입니다.

## 7. 모르면 인정할 선

**여기까지는 자신 있게 답한다**
- 이중 쓰기 문제와 왜 트랜잭션으로 못 푸는지
- Outbox가 그걸 우회하는 방식
- **at-least-once가 발생하는 정확한 지점** (발행 성공 후 상태 갱신 전)
- 유실보다 중복을 택하는 이유
- consumer group과 오프셋, "복사 vs 분담"
- poison pill과 DLQ의 역할
- 재시도로 될 실패와 안 될 실패의 구별
- 파티션 키와 순서 보장 범위

**여기부터는 "안 해봤습니다"라고 말한다**
- consumer lag 기반 오토스케일링
- DLQ 재처리 운영 도구와 알람
- Kafka 트랜잭션 API 실사용
- 여러 릴레이 인스턴스에서의 중복 방지 (**문제는 정확히 알지만 안 고쳤다**)
- 파티션 재배치(rebalancing) 중의 중복 처리

> ### 자가 점검
> **"Outbox를 쓰면 왜 at-least-once가 되나?"** 를 죽는 시점을 짚어 가며 설명할 수 있는가.
> **"group이 다르면 어떻게 되고 같으면 어떻게 되나?"** 를 즉답할 수 있는가.
> **"DLQ가 없으면 뭐가 문제인가?"** 에 poison pill로 답할 수 있는가.

# 5. 랜덤채팅 정원과 대기열

**시나리오 id**: `redis-chat-queue`
**화면**: `/chat`
**코드**: `ChatRoomService`, `ChatWebSocketHandler`

## 1. 한 줄 정의

방 정원이 차면 **먼저 온 순서대로 대기**시키고, 자리가 나면 자동으로 올린다.

## 2. 원리 — 왜 이 문제가 생기나

### 2-1. 왜 애플리케이션 메모리가 아니라 Redis인가

서버가 **한 대**라면 이걸로 충분하다.

```java
Set<String> members = new HashSet<>();   // 방 참가자
Queue<String> waiting = new LinkedList<>(); // 대기열
```

빠르고 간단하다. 문제는 서버가 **두 대**가 되는 순간이다.

```
        로드밸런서
       ╱          ╲
  서버 A          서버 B
  members:        members:
   {철수,          {지훈,
    영희,           민수,
    민지}           수진}

정원 3인 방에 실제로는 6명이 들어가 있다 💀
서로의 존재를 모른다.
```

**각 서버가 자기 메모리만 보기 때문**이다. A는 "3명이니까 꽉 찼다"고 하고, B도 "3명이니까 꽉 찼다"고 한다. 둘 다 맞는데 합치면 틀렸다.

> ### 원칙
> **여러 인스턴스가 공유해야 하는 상태는 프로세스 밖에 있어야 한다.**
> Redis를 쓰는 진짜 이유는 "빨라서"가 아니라 **"공유되기 때문"** 이다.

### 2-2. 왜 자료구조를 다섯 개나 쓰나

이 시나리오의 핵심이 여기다. **각 용도가 요구하는 성질이 다르기 때문**이고, 그 선택 근거를 말할 수 있는 게 면접에서 실력으로 읽힌다.

| 용도 | 자료구조 | Redis 키 | 왜 이것인가 |
|---|---|---|---|
| 방 참가자 | **SET** | `chat:room:main:members` | 순서 불필요 + **중복 방지가 공짜** + 인원수(`SCARD`)와 포함 여부(`SISMEMBER`)가 **O(1)** |
| 대기열 | **ZSET** | `chat:room:main:queue` | **순서가 필요하다.** score에 입장 시각을 넣으면 자동 정렬 |
| 참가자 정보 | **HASH** | `...:profiles:<userId>` | 닉네임·가상여부·입장시각을 한 키에 필드로. 하나만 골라 읽고 쓸 수 있다 |
| 이벤트 로그 | **STREAM** | `chat:room:main:events` | 시간순 추가 전용 로그. `XTRIM` 으로 최근 200개만 유지 |
| 실시간 전파 | **Pub/Sub** | `chat:room:main:broadcast` | 지금 접속 중인 WebSocket에 **즉시 밀어준다** |
| 생존 확인 | **TTL 키** | `chat:user:<id>:heartbeat` | 아래 2-4에서 자세히 |

#### 왜 대기열이 LIST가 아니라 ZSET인가 (자주 나오는 질문)

LIST도 FIFO(선입선출)를 만들 수 있다. `LPUSH` 로 넣고 `RPOP` 으로 꺼내면 된다. 그런데 이 서비스는 대기 화면에 **"당신은 3번째입니다"** 를 보여줘야 한다.

| 연산 | LIST | ZSET |
|---|---|---|
| 넣기 | `LPUSH` O(1) | `ZADD` O(log N) |
| 맨 앞 꺼내기 | `RPOP` O(1) | `ZRANGE 0 0` + `ZREM` O(log N) |
| **내 순번 알기** | **O(N) — 전체를 훑어야 한다** | **`ZRANK` O(log N)** ✅ |
| **중간 이탈자 제거** | **O(N) — 찾아서 지워야 한다** | **`ZREM` O(log N)** ✅ |

대기열은 **중간 이탈이 흔하다.** 기다리다 지쳐서 창을 닫는 사람이 많으니까. LIST면 그때마다 전체를 훑는다. ZSET은 바로 지운다.

**score에 뭘 넣나?** 입장 시각(밀리초)을 넣는다. ZSET은 score 오름차순으로 정렬되니까 **가장 작은 score = 가장 먼저 온 사람**이 자동으로 맨 앞에 온다. 별도 정렬 로직이 필요 없다.

```
ZADD queue 1754200000123 "user_A"    ← 먼저 온 사람 (score 작음)
ZADD queue 1754200005456 "user_B"
ZADD queue 1754200009789 "user_C"    ← 나중에 온 사람 (score 큼)

ZRANK queue "user_B"  →  1  (0부터 시작하니 화면에는 +1 해서 "2번")
ZRANGE queue 0 0      →  "user_A"  (맨 앞 = 다음 승급 대상)
```

### 2-3. 승급은 언제, 어떻게 일어나나

누가 나가서 `leave()` 가 호출될 때다.

```java
private void promote() {
    while (memberCount() < properties.roomCapacity()) {   // 정원이 찰 때까지 반복
        Set<String> next = redis.opsForZSet().range(QUEUE, 0, 0);  // 맨 앞 1명
        if (next == null || next.isEmpty()) return;                // 대기자 없으면 끝
        String userId = next.iterator().next();
        redis.opsForZSet().remove(QUEUE, userId);   // 대기열에서 빼고
        redis.opsForSet().add(MEMBERS, userId);     // 참가자로 옮긴다
        event("PROMOTED", ...);
    }
}
```

**`if` 가 아니라 `while` 인 이유**: 한 번에 여러 자리가 날 수 있다. 가상 유저 여러 명을 한꺼번에 퇴장시키거나, 스케줄러가 유령 여러 명을 정리할 때가 그렇다. `if` 면 한 명만 올라가고 자리가 비어 있게 된다.

### 2-4. ⭐ heartbeat — 발상을 뒤집는다

이게 이 시나리오에서 가장 실무적인 부분이다.

**문제**: 사용자가 나가는 방법은 여러 가지다.

```
① "나가기" 버튼 클릭       → 서버에 신호 옴 ✅
② 브라우저 탭 닫기          → 신호가 올 수도, 안 올 수도
③ 브라우저 강제 종료        → 신호 안 옴 ❌
④ 노트북 덮기 / 절전       → 신호 안 옴 ❌
⑤ 지하철 진입, 와이파이 끊김 → 신호 안 옴 ❌
```

③④⑤에서는 **"나갔다"는 신호가 서버에 영원히 오지 않는다.** 그 사람은 정원 한 자리를 계속 차지한다.

```
정원 3인 방:
  [유령] [유령] [철수]     ← 실제 대화 가능한 사람은 1명
  대기열: 5명이 하염없이 기다림 💀
```

**해결의 핵심은 관점을 뒤집는 것이다.**

| | 방식 | 문제 |
|---|---|---|
| 순진한 접근 | **"나갔다"는 신호를 기다린다** | ③④⑤에서는 신호가 안 온다. 영원히 못 기다린다 |
| **heartbeat** | **"살아 있다"는 신호가 끊긴 걸 감지한다** | ✅ 어떤 방식으로 끊겨도 감지된다 |

> **없는 신호를 기다리지 말고, 있던 신호가 사라진 것을 신호로 삼는다.**

구현은 Redis의 **TTL(Time To Live, 만료 시간)** 로 아주 간단해진다.

```
[클라이언트] 주기적으로 heartbeat 전송 (예: 10초마다)
      ↓
[서버] chat:user:<id>:heartbeat 키를 TTL과 함께 SET
       → 키가 TTL 뒤에 자동으로 사라진다
       → heartbeat가 계속 오면 계속 갱신되어 안 사라진다
       → heartbeat가 끊기면 TTL이 지나 키가 소멸한다 ✅

[스케줄러] 10초마다 (cleanupStaleUsers)
       → 참가자와 대기자를 순회하며
       → heartbeat 키가 없는 사람을 찾아 leave() 호출
       → leave()가 promote()를 부르므로 대기자가 자동으로 올라간다
```

**TTL이 우아한 이유**: 만료를 직접 관리할 필요가 없다. Redis가 알아서 지운다. 내 코드는 **"키가 있나?"만 물어보면 된다.**

이 발상은 이 프로젝트만의 것이 아니다. **Kubernetes의 liveness probe, Kafka의 consumer 세션 타임아웃, 분산 시스템의 failure detector가 전부 같은 원리다.** 면접에서 이 연결을 짚으면 좋다.

### 2-5. Pub/Sub과 Stream을 왜 둘 다 쓰나

같은 이벤트를 두 곳에 쓰는 게 낭비처럼 보이는데, 역할이 다르다.

| | Pub/Sub | Stream |
|---|---|---|
| 저장 | **안 한다.** 지나가면 끝 | **저장한다.** 나중에 다시 읽을 수 있다 |
| 못 받으면 | **영영 못 받는다** | 오프셋으로 이어받을 수 있다 |
| 용도 | 지금 접속 중인 사람에게 **즉시 전파** | 재접속 시 **최근 이력 복원** |

```
[메시지가 발생하면]
  → Stream에 추가 (XADD)          : 기록. 최근 200개 유지(XTRIM)
  → Pub/Sub으로 발행 (PUBLISH)     : 지금 접속 중인 WebSocket들에 즉시 전달

[사용자가 새로 접속하면]
  → Stream에서 최근 30건을 읽어 화면을 채운다
  → 이후 메시지는 Pub/Sub으로 실시간 수신
```

**Pub/Sub만 쓰면** 새로 들어온 사람의 화면이 텅 비어 있다. **Stream만 쓰면** 실시간성을 위해 계속 폴링해야 한다. 둘 다 쓰는 게 맞다.

## 3. 대안 표와 내 선택

| 접근 | 대가 | 채택 |
|---|---|---|
| 애플리케이션 메모리 | **인스턴스마다 상태가 갈라진다.** 정원 제한이 무의미해진다 | ✗ |
| DB 테이블 | 매 입퇴장이 write, 순번 조회마다 쿼리. 휘발돼도 되는 데이터에 과하다 | ✗ |
| **Redis (SET + ZSET + …)** | 별도 인프라 의존. 영속성이 약하다(이 용도엔 문제없음) | **✓** |
| Redis + Lua 원자 스크립트 | 여러 인스턴스에서도 정원이 정확하다. 스크립트 유지보수 부담 | 미도입 |

## 4. 진위 한 줄

**✅ 실제로 돌아간다.**
- 진짜 Redis에 SET / ZSET / HASH / STREAM / Pub-Sub 키가 만들어진다
- WebSocket으로 실시간 전파된다
- 가상 유저를 붙여 정원 초과 → 대기 → 승급을 실제로 재현할 수 있다
- 인원수와 대기열 길이가 Micrometer Gauge로 실제 지표에 나간다

**✅ 동시성 제어는 2026-08-03에 고쳤다. 고치기 전 이야기가 좋은 답변이 된다.**

**고치기 전**: `join()` · `leave()` · `promote()` 가 전부 Java의 `synchronized` 였다. 이건 **JVM 하나 안에서만 유효한 잠금**이다.

```
상태는 Redis에 공유되는데,  잠금은 각 JVM 안에만 있었다.  ← 어긋나 있었다
```

**정원이 깨지는 시나리오** (정원 3, 현재 2명):

```
시각   서버 A                          서버 B
─────────────────────────────────────────────────────────
t1    SCARD members → 2
t2                                     SCARD members → 2
t3    2 < 3 이니까 입장 가능!
t4                                     2 < 3 이니까 입장 가능!
t5    SADD members "철수"
t6                                     SADD members "영희"
─────────────────────────────────────────────────────────
결과: 4명. 정원 3을 넘겼다 💀
```

**"읽고(read) → 판단하고(check) → 쓰는(write)" 사이가 원자적이지 않기 때문**이다. 이걸 **check-then-act race condition** 이라고 부른다. `synchronized` 는 A 안의 스레드끼리는 막아 주지만 **A와 B 사이는 못 막는다.**

**그리고 이게 이 포트폴리오의 다른 시나리오와 정면으로 충돌했다.** "Pod 자동 확장" 화면이 replica를 1→2로 늘리는데, **그 순간 채팅방 정원이 깨졌다.** 두 화면이 서로를 반박하고 있었다.

**고친 방법 — Lua로 확인과 추가를 원자화했다.**

```lua
redis.call('SREM', KEYS[1], ARGV[1])
redis.call('ZREM', KEYS[2], ARGV[1])
if redis.call('SCARD', KEYS[1]) < tonumber(ARGV[2]) then
  redis.call('SADD', KEYS[1], ARGV[1])      -- 확인과 추가가 한 스크립트 안
  return 'E'
end
redis.call('ZADD', KEYS[2], tonumber(ARGV[3]), ARGV[1])
return 'W:' .. tostring(redis.call('ZRANK', KEYS[2], ARGV[1]) + 1)
```

**Redis는 명령을 단일 스레드로 처리하고 Lua 스크립트를 원자적으로 실행하므로**, 스크립트가 도는 동안 다른 클라이언트의 명령은 대기한다. 이제 t1~t6 사이에 끼어들 틈이 없다.

`leave()` 와 `promote()` 도 같은 방식으로 스크립트화했고, **`synchronized` 는 전부 제거했다.** 잠금이 Redis로 옮겨졌으니 JVM 잠금은 의미가 없다.

**함께 고친 것**: `reset()` 이 쓰던 `KEYS chat:*` 를 `SCAN` 으로 바꿨다. `KEYS` 는 전체 키 공간을 훑는 O(N) 연산이고 Redis가 단일 스레드라 그동안 모든 요청이 멈춘다.

## 5. 30초 구두 답변

> 채팅방 정원과 대기열을 애플리케이션 메모리에 두면 서버가 두 대가 되는 순간 각자 다른 목록을 갖게 돼서 정원 제한이 무의미해집니다. 그래서 상태를 Redis에 뒀습니다. 빨라서가 아니라 공유돼야 해서요.
>
> 자료구조는 용도별로 나눴습니다. 참가자는 순서가 필요 없고 중복 방지와 인원수 조회가 O(1)이라 SET을 썼고, 대기열은 "몇 번째입니다"를 보여줘야 해서 score에 입장 시각을 넣은 ZSET을 썼습니다. LIST도 FIFO는 되지만 순번 조회랑 중간 이탈자 제거가 O(N)이라서요.
>
> 그리고 브라우저를 그냥 닫거나 네트워크가 끊기면 퇴장 신호가 아예 안 옵니다. 그러면 유령이 정원을 차지하죠. 그래서 heartbeat를 TTL 키로 받고 스케줄러가 키 없는 사용자를 정리합니다. 나갔다는 신호를 기다리는 대신, 살아 있다는 신호가 끊긴 걸 감지하는 쪽으로 뒤집은 겁니다. Kubernetes liveness probe랑 같은 발상이고요.
>
> 다만 동시성 제어가 synchronized라 JVM 안에서만 유효합니다. Pod가 두 개가 되면 정원이 깨지는데, 고치려면 인원 확인과 추가를 Lua 스크립트로 묶어야 합니다.

## 6. 꼬리질문과 답

**Q1. 서버가 두 대면 정원이 정확한가요?**

**지금은 정확합니다. 원래는 아니었고 고쳤습니다.**

처음에는 `synchronized` 로 감쌌는데 그건 JVM 안에서만 유효합니다. 상태는 Redis에 공유하면서 잠금은 공유하지 않았던 거죠. 두 인스턴스가 각각 인원수를 읽고 둘 다 "자리 있음"으로 판단하면 정원을 넘깁니다. check-then-act가 원자적이지 않아서요.

**인원수 확인과 추가를 Lua 스크립트 하나로 묶어서** 해결했습니다. Redis는 명령을 단일 스레드로 처리하고 Lua 스크립트를 원자적으로 실행하니까, 스크립트 안에서 `SCARD` 로 세고 조건이 맞을 때만 `SADD` 하면 중간에 다른 요청이 끼어들 수 없습니다.

분산 락(Redlock 등)도 방법이지만 Lua 쪽을 택했습니다. 락은 획득·해제·타임아웃·소유권 확인이 다 필요해서 실패 모드가 훨씬 많거든요. Lua는 그 전부가 필요 없습니다.

**Q2. Redis가 죽으면 어떻게 되나요?**

방 상태가 전부 날아갑니다. 채팅방이라 치명적이진 않고 재입장하면 되는데, **대기 순번이 사라지는 건 사용자 입장에서 불공정합니다.** 30분 기다린 사람이 맨 뒤로 가니까요.

순서가 돈이나 형평성과 직결되는 도메인(티켓팅, 선착순 이벤트)이라면 Redis 영속화(AOF)를 켜거나, 순번을 DB에 이중화하거나, Redis Sentinel/Cluster로 이중화해야 합니다. 이 서비스는 그 정도 가치가 없다고 판단했습니다.

**Q3. Pub/Sub 대신 Stream만 쓰면 안 되나요?**

가능하지만 **실시간성을 위해 계속 폴링해야 합니다.** 반대로 Pub/Sub만 쓰면 새로 접속한 사람 화면이 텅 빕니다. Pub/Sub은 저장을 안 해서 접속 전 메시지를 못 받거든요.

그래서 **둘 다 씁니다.** 실시간 전파는 Pub/Sub, 재접속 시 최근 30건 복원은 Stream입니다. 역할이 다릅니다.

**Q4. `reset()` 에서 `KEYS chat:*` 를 쓰던데 괜찮나요?**

**운영에서는 안 됩니다.** `KEYS` 는 전체 키 공간을 훑는 O(N) 연산이고, Redis가 단일 스레드라 **그동안 다른 모든 요청이 멈춥니다.** 키가 수백만 개면 수 초간 서비스 전체가 정지합니다.

대신 `SCAN` 을 써야 합니다. 커서 기반으로 조금씩 나눠 순회해서 다른 요청을 막지 않습니다. 지금은 데모용 초기화 기능이고 키가 몇십 개 수준이라 문제가 안 드러난 겁니다.

# 마무리 — 이 그룹을 하나로 묶는 답변

면접에서 **"분산 시스템 경험을 말해 보세요"** 가 나오면 5편을 따로 나열하지 말고 이렇게 묶는다.

> 분산 처리에서 제일 어려운 건 **"응답이 없다"는 상태**라고 생각합니다. 로컬 호출은 성공 아니면 예외인데, 네트워크 너머는 성공·실패·**모름** 셋이거든요. 그리고 이 '모름'을 어떻게 다루느냐가 설계의 대부분을 결정합니다.
>
> 저는 네 가지 작업에서 이걸 각각 다르게 다뤘습니다.
>
> 다만 그 전에 **경계가 실재하는지부터 봤습니다.** 프로세스를 나누고 Kafka 와 사가까지 갖췄는데 결제 원본이 모놀리스 DB 에 있었거든요. **데이터가 한 덩어리면 경계는 그림에만 있어서**, 소유권을 계정 권한과 NetworkPolicy 두 겹으로 강제하고 막혔다는 것을 대조군과 함께 쟀습니다.
>
> **외부 API 연동**에서는 모름을 재시도로 덮으면 이중 결제가 나니까, callback으로 **확정**하는 절차를 뒀습니다.
>
> **Saga**에서는 중간 단계가 모름이 됐을 때 롤백이 불가능하니까 **보상**으로 되돌렸습니다. 결제 기록을 지우는 게 아니라 취소 기록을 추가하는 방식으로요.
>
> **Kafka**에서는 DB 커밋과 이벤트 발행 사이의 모름을 없애려고 Outbox로 원자성을 만들고, 대신 중복을 감수하는 at-least-once를 택했습니다. 유실은 아무도 모르지만 중복은 코드로 막을 수 있으니까요.
>
> **채팅**에서는 사용자가 나갔는지 모르는 상태를 heartbeat로 뒤집어서, 없는 신호를 기다리는 대신 있던 신호가 끊긴 걸 감지하게 했습니다.
>
> 공통점은 **모름을 없애려 하지 않고, 모름을 안전하게 다루는 구조를 만든 것**입니다. 분산 환경에서 모름은 제거할 수 없는 성질이라고 봤습니다.
>
> 그리고 그 모름을 다루는 장치들은 **경계가 진짜일 때만 값을 합니다.** 그래서 소유권을 먼저 세웠습니다.

## 왜 이 답변이 강한가

1. **기술 나열이 아니라 하나의 관점**이다. "Kafka 써봤습니다"보다 훨씬 기억에 남는다
2. 네 기술이 **왜 그 선택이었는지**가 관점에서 자동으로 따라 나온다
2-1. 소유권 편이 **나머지 넷의 전제**라는 순서를 말하면, 기술 나열이 아니라 설계 순서로 들린다
3. 면접관이 어디를 파고들어도 **2번 칸(원리)** 으로 내려가면 답이 있다
4. 마지막 문장이 **"제거할 수 없는 성질"** 이라는 인식을 보여준다. 이게 분산 시스템을 실제로 이해한 사람의 언어다

## 내 코드의 약점 — 고친 것과 남은 것

**2026-08-03에 셋을 고쳤다.** 전부 *"단일 인스턴스에서는 정상 동작하지만 수평 확장하는 순간 드러나는"* 종류였다. HPA maxReplicas가 2라 이론이 아니라 실제 위험이었다.

| 약점 | 어디 | 상태 |
|---|---|---|
| 동시성 제어가 `synchronized` → Pod 2개면 정원이 깨짐 | 채팅 | ✅ **Redis Lua로 원자화** |
| Outbox 릴레이가 행을 잠그지 않아 replica 2대면 중복 발행 | Kafka | ✅ **claim + `for update skip locked`** |
| `run()` 전체가 하나의 `@Transactional`, 외부 호출이 그 안 | Saga | ✅ **단계별 트랜잭션으로 분리** |
| `reset()` 이 `KEYS` 사용 (O(N) 블로킹) | 채팅 | ✅ **`SCAN` 으로 교체** |
| 서킷 브레이커가 없다 (재시도 소진일 뿐) | 제휴 API | ⚠️ **남음** (화면 표시는 정직함) |
| `PartnerCallbackRegistry` 가 JVM 메모리 | 제휴 API | ⚠️ **남음** — replica 2면 callback이 엉뚱한 인스턴스로 |
| 중단된 saga를 복구하는 절차가 없다 | Saga | ⚠️ **남음** (경계를 나눈 대가) |

**고친 것에도 답변이 있고, 남은 것에도 답변이 있다.**

> "수평 확장을 켜기 전에 애플리케이션이 무상태인지부터 확인해야 한다는 걸 이 프로젝트에서 직접 겪었습니다. 상태는 Redis에 잘 공유해 놨는데 **잠금은 JVM 안에 있었고**, Outbox 릴레이는 행을 잠그지 않았고, Saga는 트랜잭션 경계가 너무 넓었습니다. 셋 다 replica 1개에서는 멀쩡히 도는데 2개가 되는 순간 깨지는 종류였고요.
>
> 고치면서 배운 게, **경계를 나누면 원자성을 잃는다**는 겁니다. Saga 트랜잭션을 쪼개니까 결제 호출 중에 죽으면 중단된 saga가 남고, Outbox에 선점을 넣으니까 선점하고 죽으면 CLAIMED가 영원히 남습니다. 후자는 `claimed_at` 과 타임아웃 회수로 막았는데, 전자는 아직 복구 프로세스가 없습니다."
