# 05. 운영 도구 · 거버넌스

사이트 그룹: **운영 도구·거버넌스** — "반복되는 운영 작업을 승인·감사·복구가 가능한 도구와 절차로 전환한다."

**6편 전부 고정 대본이다.** 다만 한 편(대량 스프레드시트)은 **export 엔드포인트가 실제로 동작**하고, 한 편(개인정보)은 **이 프로젝트에 실제 구현된 개인정보 설계가 따로 있다.**

| 편 | 진위 |
|---|---|
| 운영 데이터 조회·정정 | ⚠️ 고정 대본 |
| 개인정보 마스킹·파기 | ⚠️ 고정 대본 — **단, 블로그 댓글에 실제 개인정보 설계가 있다** |
| 대량 스프레드시트 작업 | ⚠️ 고정 대본 — **단, 10만 행 xlsx 스트리밍 export는 실제 동작** |
| 비즈니스 지표 백오피스 | ⚠️ 고정 대본 |
| 알림 발송 운영 | ⚠️ 고정 대본 |
| 점검 공지 | ⚠️ 고정 대본 |

---

## 시작하기 전에 — 이 그룹은 왜 다른가

앞의 네 그룹은 **"시스템이 알아서 하는 일"** 이었다. 동시 요청을 막고, 이벤트를 발행하고, Pod를 늘리고.

**이 그룹은 "사람이 개입하는 일"** 이다. 그리고 그게 훨씬 위험하다.

```
[코드로 하는 일]
  코드 리뷰를 거친다
  테스트가 있다
  단계적으로 배포된다
  문제가 있으면 롤백한다

[운영자가 손으로 하는 일]
  ❌ 리뷰 없음
  ❌ 테스트 없음
  ❌ 바로 운영 DB에 닿는다
  ❌ 되돌릴 방법이 미리 준비돼 있지 않다
```

> ### 이 그룹의 한 문장
> **운영 사고의 상당수는 버그가 아니라 "권한 있는 사람이 옳다고 믿고 실행한 작업"에서 난다.**
> 그래서 이 그룹의 답은 전부 **기능이 아니라 절차**다.

**6편을 관통하는 원칙이 셋이다.**

```
① 최소 노출 (Least Exposure)
     필요한 것만 본다. 필요한 만큼만 바꾼다.
     → 개인정보 마스킹, 조건부 UPDATE의 범위 제한

② 되돌릴 수 있음 (Reversibility)
     하기 전에 "어떻게 되돌릴지"가 준비돼 있어야 한다.
     → 수정 전 snapshot, staging 후 반영, DLQ 재처리

③ 같은 정의 (Single Definition)
     같은 질문에는 어디서 물어도 같은 답이 나와야 한다.
     → 지표 계약, 화면과 export의 필터 공유
```

**그리고 전부에 공통으로 깔리는 것: 감사 기록(audit).** 누가, 언제, 왜, 무엇을 했는지가 남아야 한다. 사고가 났을 때 이게 없으면 원인을 찾을 수 없고, 없다는 사실 자체가 사고를 부른다.

# 1. 운영 데이터 조회 · 정정

**시나리오 id**: `operations-data-correction`
**모드**: `DIRECT_UPDATE` / `SELECT_ONLY` / `CONDITIONAL_UPDATE` / `ROLLBACK`

## 1. 한 줄 정의

**CS로 접수된 "포인트가 누락됐어요" 한 건을 고치는데**, 실수로 37건을 바꾸지 않게 하는 절차.

## 2. 원리 — 왜 이 문제가 생기나

### 2-1. ⭐ 운영 UPDATE는 왜 위험한가

`DIRECT_UPDATE` 모드가 보여주는 사고다.

```
step("TICKET_RECEIVED",  "누락 포인트 한 건의 복구 요청을 접수했다.")
step("UPDATE_EXECUTED",  "대상 snapshot과 expected state 없이 UPDATE를 실행했다.")
step("SCOPE_EXCEEDED",   "예상 1건보다 많은 37건이 변경됐다.")     ← 💀
```

**왜 1건인 줄 알았는데 37건이 되나?** 흔한 경로가 셋이다.

```
① WHERE 조건이 생각보다 넓었다
     UPDATE 회원 SET 포인트 = 포인트 + 1000 WHERE 이름 = '김철수';
     → 동명이인이 37명

② 조인 조건을 빠뜨렸다
     UPDATE 주문 SET 상태='완료' WHERE 상품id=5;
     → "그 사람의 주문"이 아니라 "그 상품의 모든 주문"

③ WHERE 절 자체를 빠뜨렸다
     UPDATE 회원 SET 포인트 = 1000;
     → 전체 행 💀💀
```

**그리고 실행 후에는 되돌릴 방법이 없다.**

```
"37건이 바뀌었네. 원래 값이 뭐였지?"
  → 모른다. 덮어썼으니까
  → 백업으로 돌리면? 그 사이 정상 거래도 사라진다 (04에서 본 논리적 손상)
```

> **UPDATE는 "이전 값을 지우는" 명령이다.**
> 그래서 **실행 전에 이전 값을 어딘가에 남기지 않으면 되돌릴 수 없다.**

### 2-2. 안전한 절차 — 네 단계

#### 단계 ① 근거 확인 (`SELECT_ONLY`)

```
step("EVIDENCE_MATCHED", "CS ticket과 거래 원장을 대조했다.")
```

**"고객이 그렇게 말했다"는 근거가 아니다.** 실제 거래 원장을 봐서 "정말 누락이 맞는지"를 확인한다. 이 단계에서 상당수의 요청이 "사실은 정상이었다"로 걸러진다.

#### 단계 ② 대상 확인 — **먼저 SELECT를 돌린다**

```sql
-- 실행할 UPDATE 의 WHERE 절을 그대로 SELECT 로 돌려 본다
SELECT * FROM 회원포인트
WHERE 회원id = 'u-12345' AND 거래id = 't-999' AND 상태 = 'PENDING';
-- → 1건이 나오는가?  37건이 나오면 여기서 멈춘다 ✅
```

> **이것 하나로 대부분의 사고가 막힌다.**
> `UPDATE` 를 쓰기 전에 **같은 `WHERE` 절로 `SELECT` 를 먼저 돌린다.** 비용이 0에 가깝고 효과가 크다.

#### 단계 ③ 수정 전 값 보존 (snapshot)

```
step("SNAPSHOT_SAVED", "수정 전 값과 rollback key를 보존했다.")
```

```sql
-- 감사 테이블에 이전 값을 먼저 넣는다
INSERT INTO 운영작업감사 (작업id, 대상테이블, 대상키, 이전값, 티켓id, 승인자, 시각)
SELECT 'op-2026-0803-01', '회원포인트', id, row_to_json(t), 'CS-9999', 'admin', now()
FROM 회원포인트 t WHERE ...;
```

**`rollback key`(작업 식별자)가 중요하다.** 나중에 "이 작업을 되돌려라"라고 할 때 대상을 정확히 지목할 수 있다.

#### 단계 ④ ⭐ 조건부 UPDATE + 영향 행 수 검증

```sql
UPDATE 회원포인트
SET 포인트 = 포인트 + 1000, 상태 = 'COMPLETED'
WHERE id = 12345
  AND 상태 = 'PENDING';      -- ← expected state
```

**두 가지를 동시에 한다.**

1. **`AND 상태 = 'PENDING'`** — 내가 조회했을 때의 상태와 지금 상태가 같을 때만 바꾼다. 그 사이에 누가 이미 처리했으면 갱신되지 않는다
2. **갱신된 행 수가 정확히 1인지 확인** — 0이면 이미 처리됨, 2 이상이면 조건이 넓다. **둘 다 즉시 롤백**

> **01에서 배운 조건부 UPDATE가 여기서도 그대로 쓰인다.**
> 거기서는 동시성 방어였고, 여기서는 **"내가 본 상태가 아직 유효한가"** 를 확인하는 낙관적 락 역할이다.
> **같은 도구가 다른 목적으로 쓰인다.**

#### 그리고 마지막 — 불변조건 검증

```
step("INVARIANTS_VERIFIED", "잔액과 원장 합계가 일치함을 재조회했다.")
```

**"UPDATE가 1건 됐다"와 "데이터가 올바르다"는 다르다.** 01의 상품권 편에서 본 원장 방식이면, **포인트 잔액과 원장 합계가 여전히 일치하는지**를 확인해야 진짜 끝이다.

> 01의 정산 편, 04의 복원 리허설에서 본 **"돌았다 ≠ 맞다"** 가 세 번째로 나온다.
> 이 프로젝트 전체를 관통하는 사고방식이다.

### 2-3. ROLLBACK 모드 — 되돌리기도 절차다

```
step("AUDIT_LOADED",         "원 작업과 before snapshot을 조회했다.")
step("CURRENT_STATE_CHECKED","후속 변경이 없는지 확인했다.")     ← ⭐ 여기가 핵심
step("ROLLBACK_APPLIED",     "조건부 역변경을 실행했다.")
step("RESTORE_VERIFIED",     "복구 값과 작업 이력을 검증했다.")
```

**두 번째 스텝이 결정적이다.** 무작정 되돌리면 안 되는 이유가 있다.

```
10:00  운영자 A가 포인트를 1000 더함    (snapshot: 이전 값 500)
11:00  고객이 포인트 300을 사용         (현재 값 1200)
12:00  "아까 그 작업 되돌려주세요"

  ❌ snapshot 값 500으로 되돌리면?  →  고객이 쓴 300이 사라진다 💀
  ✅ 후속 변경이 있는지 먼저 확인   →  있으면 자동 롤백을 거부하고 사람이 판단
```

> **롤백은 "시간을 되감는 것"이 아니다.** 그 사이에 세상이 움직였을 수 있다.
> **02의 Saga에서 본 "롤백 vs 보상"과 같은 이야기다.** 되돌리는 것도 결국 **새로운 변경**이고, 그러니 앞의 네 단계를 똑같이 밟아야 한다.

## 3. 대안 표와 내 선택

| 접근 | 사고 위험 | 되돌리기 | 속도 | 채택 |
|---|---|---|---|---|
| DB 콘솔에서 직접 UPDATE | **매우 높음** | ❌ 불가 | 빠름 | ✗ |
| SELECT 먼저 확인 후 UPDATE | 중간 | ❌ 불가 | 빠름 | △ 최소선 |
| **snapshot + 조건부 UPDATE + 검증** | **낮음** | ✅ 가능 | 느림 | **✓** |
| 운영 도구(백오피스)로만 허용 | **가장 낮음** | ✅ | 개발 비용 | ✓ 반복 작업이면 |

**핵심 판단**: **한 번뿐인 작업이면 절차로, 반복되는 작업이면 도구로.**

같은 유형의 정정이 매주 반복된다면 그건 **기능으로 만들어야 한다는 신호**다. 매번 사람이 SQL을 쓰면 언젠가 반드시 실수한다. 백오피스 화면으로 만들면 조건·승인·감사가 코드로 강제된다.

## 5. 30초 구두 답변

> 운영 데이터 정정이 위험한 이유는 코드 리뷰도 테스트도 없이 바로 운영 DB에 닿기 때문입니다. 그리고 UPDATE는 이전 값을 지우는 명령이라, 실행 전에 남겨두지 않으면 되돌릴 수가 없어요. 한 건 고치려다 동명이인 37건이 바뀌는 식의 사고가 이래서 납니다.
>
> 그래서 네 단계로 정리했습니다. 먼저 CS 티켓 말고 실제 거래 원장으로 근거를 확인하고, 실행할 UPDATE의 WHERE 절을 그대로 SELECT로 돌려서 몇 건이 나오는지 봅니다. 이거 하나로 대부분의 사고가 막힙니다. 그다음 수정 전 값을 감사 테이블에 스냅샷으로 남기고, 마지막에 조건부 UPDATE로 실행합니다. `AND 상태 = 'PENDING'` 같은 expected state를 붙여서 그 사이에 누가 이미 처리했으면 안 바뀌게 하고, 영향 행 수가 정확히 1이 아니면 즉시 롤백합니다.
>
> 그리고 끝나고 불변조건을 검증합니다. UPDATE가 1건 됐다는 것과 데이터가 올바르다는 건 다르니까, 포인트 잔액이랑 원장 합계가 여전히 맞는지 재조회합니다.
>
> 롤백도 그냥 스냅샷 값으로 덮으면 안 됩니다. 그 사이에 고객이 포인트를 썼으면 그 사용이 사라지거든요. 그래서 후속 변경이 있는지 먼저 확인하고, 있으면 자동 롤백을 거부합니다.

## 6. 꼬리질문과 답

**Q1. 그냥 트랜잭션으로 감싸고 확인 후 커밋하면 안 되나요?**

**부분적으로 됩니다.** `BEGIN` 하고 UPDATE한 다음 영향 행 수를 보고 이상하면 `ROLLBACK` 하는 건 좋은 습관입니다.

다만 두 가지가 부족합니다. 첫째, **커밋한 뒤에는 못 돌립니다.** 나중에 "역시 잘못됐다"를 알았을 때 이전 값이 필요한데 없습니다. 둘째, **누가 왜 했는지가 안 남습니다.** 사고 조사를 못 합니다.

그래서 트랜잭션은 즉각적인 안전장치고, **snapshot과 감사 기록은 사후 대응을 위한 것**입니다. 둘 다 필요합니다.

**Q2. 감사 기록에 뭘 남겨야 하나요?**

**"나중에 이 작업을 설명할 수 있는 것"** 전부입니다. 구체적으로는 누가(실행자), 언제, 왜(티켓 번호와 사유), 무엇을(대상 테이블·키), 어떻게(이전 값과 이후 값), 그리고 승인자입니다.

**이전 값을 JSON으로 통째로 남기는 게 편합니다.** 어떤 컬럼이 필요할지 미리 모르니까요.

주의할 점은 **감사 기록 자체에 개인정보가 들어간다는 것**입니다. 그래서 접근 권한을 따로 관리해야 하고, 보존 기간도 정해야 합니다. 다음 편과 이어지는 부분입니다.

**Q3. 승인 절차가 꼭 필요한가요?**

**작업의 위험도에 비례해서요.** 전부 승인을 받게 하면 절차가 무거워져서 사람들이 우회합니다. 그게 더 위험합니다.

기준은 **되돌릴 수 있는가와 영향 범위**입니다. 되돌릴 수 있고 1건이면 실행자 기록만으로 충분하고, 되돌리기 어렵거나 다건이면 승인이 필요합니다. 돈이 걸리면 무조건 승인이고요.

**Q4. 반복되는 정정 작업은 어떻게 하나요?**

**기능으로 만들어야 한다는 신호입니다.** 같은 유형이 매주 반복되는데 매번 사람이 SQL을 쓰면 언젠가 반드시 실수합니다.

백오피스 화면으로 만들면 조건·승인·감사가 **코드로 강제**됩니다. 사람의 주의력에 기대지 않게 되는 거죠. 그리고 그 화면 자체는 코드 리뷰와 테스트를 거치고요.

## 7. 모르면 인정할 선

**여기까지는 자신 있게 답한다**
- 운영 작업이 코드보다 위험한 이유 (리뷰·테스트·롤백 없음)
- **UPDATE 전에 같은 WHERE로 SELECT를 돌리는 것**의 가성비
- snapshot과 rollback key가 필요한 이유
- **expected state 조건과 영향 행 수 검증** (01의 조건부 UPDATE 재사용)
- **불변조건 검증** — "돌았다 ≠ 맞다"
- **롤백에도 후속 변경 확인이 필요한 이유**
- 절차와 도구를 가르는 기준 (반복성)

**여기부터는 "안 해봤습니다"라고 말한다**
- 감사 로그의 보존 정책과 접근 통제 실제 구현
- 승인 워크플로 시스템 구축
- 운영 DB 접근 자체를 통제하는 방식 (bastion, 임시 권한 부여)

> ### 자가 점검
> **"1건인 줄 알았는데 37건"** 이 나오는 경로 셋을 댈 수 있는가.
> **"롤백을 그냥 하면 왜 안 되나"** 를 시간순 예로 설명할 수 있는가.

# 2. 개인정보 마스킹 · 파기

**시나리오 id**: `privacy-data-lifecycle`
**모드**: `RAW_ACCESS` / `ROLE_MASKING` / `WITHDRAWAL` / `PURGE_WITH_RETENTION`

## 1. 한 줄 정의

개인정보를 **볼 때(마스킹), 탈퇴할 때(분리), 보존기간이 끝날 때(파기), 그리고 백업본까지** 전 수명주기를 관리한다.

## 2. 원리 — 왜 이 문제가 생기나

### 2-1. 개인정보는 "가지고 있는 것 자체가 위험"이다

일반적인 데이터는 많을수록 좋다. 개인정보는 반대다.

```
[일반 데이터]  많이 모을수록 분석이 정확해진다
[개인정보]     많이 모을수록 유출 시 피해가 커진다
              → 안 가진 정보는 유출될 수 없다  ⭐
```

> **가장 확실한 개인정보 보호는 애초에 수집하지 않는 것이다.**
> 그다음이 최소한만 저장하는 것, 그다음이 최소한만 보여주는 것.

### 2-2. 최소 노출 — 역할별 projection

`RAW_ACCESS` 모드가 보여주는 문제다.

```
step("PROFILE_REQUESTED", "고객 프로필 조회를 요청했다.")
step("RAW_PROJECTED",     "역할 구분 없이 원문 필드를 응답했다.")   ← 6개 필드 전부
step("ACCESS_REJECTED",   "최소 노출 원칙을 위반했다.")
```

**CS 상담원이 고객 문의에 답하는 데 주민번호·전체 주소·전체 전화번호가 다 필요한가?**

```
[필요한 것]   "전화번호 뒤 4자리가 1234 맞으세요?"  →  본인 확인용
[불필요한 것]  전체 번호, 주소, 생년월일 전체
```

`ROLE_MASKING` 모드가 해법이다.

```
step("ROLE_CHECKED",     "CS 역할과 업무 목적을 확인했다.")
step("FIELDS_PROJECTED", "전화번호 끝 4자리 외 필드를 마스킹했다.")   → 6개 → 1개
step("ACCESS_AUDITED",   "조회 사유와 접근자를 기록했다.")
```

**세 가지를 동시에 한다.** 역할 확인 + 필드 마스킹 + **조회 자체를 기록**.

> ### 조회를 기록하는 게 왜 중요한가
> 개인정보 사고의 상당수는 **외부 해킹이 아니라 내부자 조회**다.
> 연예인 정보를 궁금해서 열어 보는 식이다.
>
> **"누가 언제 누구의 정보를 왜 봤는지"가 남으면** 그 자체가 억제력이 된다.
> 그리고 사고가 나면 범위를 특정할 수 있다.

**구현 시 주의점**: 마스킹을 **화면단에서 하면 안 된다.** API 응답에 원문이 실려 나가면 개발자 도구로 볼 수 있다. **서버에서 projection 단계에 잘라야 한다.**

### 2-3. ⭐ 탈퇴 = 즉시 삭제가 아니다

가장 많이 오해하는 부분이다.

```
사용자: "탈퇴할게요"
개발자: DELETE FROM 회원 WHERE id = ?;     ← ❌ 이러면 안 된다
```

**법적으로 보존해야 하는 것들이 있기 때문이다.**

```
전자상거래법:  계약·청약철회 기록 5년, 대금결제 기록 5년,
              소비자 불만·분쟁처리 기록 3년
전자금융거래법: 거래 기록 5년
```

**"탈퇴했으니 결제 기록도 지운다"고 하면 법 위반이다.** 그래서 `WITHDRAWAL` 모드가 이렇게 되어 있다.

```
step("WITHDRAWAL_ACCEPTED",   "탈퇴 요청과 기준 시각을 기록했다.")
step("TOKENS_REVOKED",        "활성 session과 refresh token을 폐기했다.")   ← 즉시
step("IDENTIFIERS_ISOLATED",  "즉시 파기 대상과 보존 예외를 분리했다.")      ← ⭐
```

**핵심은 "분리"다.**

```
[즉시 파기]        이름, 이메일, 전화번호, 주소, 로그인 정보
                  → 서비스 이용에 필요했던 것들. 이제 필요 없다

[보존 (기간 만료까지)]  거래 기록, 결제 기록
                      → 단, 식별자는 분리하거나 대체키로 바꾼다
                      → "누가 샀는지"는 최소화하고 "무엇이 팔렸는지"는 남긴다
```

**토큰 폐기가 왜 즉시인가**: 탈퇴 처리가 진행 중이어도 **기존 세션으로 로그인 상태가 유지되면** 탈퇴한 계정으로 서비스를 계속 쓸 수 있다. 그래서 이건 가장 먼저 한다.

### 2-4. ⭐⭐ `PURGE_WITH_RETENTION` — 파기의 진짜 어려움

이 모드가 이 편에서 가장 중요하다. **개인정보는 한 곳에만 있지 않기 때문이다.**

```
step("POLICY_RESOLVED", "필드별 보유기간과 예외 근거를 확인했다.")
step("EXPIRED_PURGED",  "만료된 원문 식별자를 파기했다.")
step("LOGS_REDACTED",   "로그와 export의 식별값을 검사했다.")      ← ⭐
step("RESTORE_TESTED",  "복원본에 재파기 절차가 적용됨을 확인했다.")  ← ⭐⭐
```

**개인정보가 실제로 흩어져 있는 곳들:**

```
✅ DB 본 테이블        ← 여기만 지우면 된다고 생각한다
❌ 애플리케이션 로그    ← "user=hong@example.com 조회" 같은 게 찍혀 있다
❌ 검색 엔진 색인      ← OpenSearch에 복사본이 있다
❌ 캐시 (Redis)       ← TTL 전까지 남아 있다
❌ 다운로드된 엑셀 파일 ← 담당자 PC에 있다
❌ 백업 파일          ← 💀 여기가 가장 어렵다
```

**백업 문제를 보자.**

```
2026-08-01  백업 뜸 (홍길동 정보 포함)
2026-08-15  홍길동 파기 요청 → 운영 DB에서 삭제 ✅
2026-08-20  장애 발생 → 8/1 백업으로 복원
            → 홍길동 정보가 되살아난다 💀
```

**백업 파일을 직접 수정하는 건 사실상 불가능하다.** 압축된 덤프고, 수정하면 무결성이 깨진다.

**현실적인 해법은 둘이다.**

```
① 보관 기간으로 자연 소멸시킨다
     백업 보관 기간(예: 7일)이 파기 주기보다 짧으면
     → 파기 후 7일 지나면 그 정보가 담긴 백업이 전부 사라진다
     → 04에서 본 "7일 보관"이 여기서 의미를 갖는다

② ⭐ 복원 시 재파기 절차를 밟는다
     복원했다는 것 자체를 트리거로 삼아
     "복원 시점 이전에 파기 요청된 대상"을 다시 파기한다
     → 파기 요청 목록은 별도로 보존해야 한다
     → 화면 스텝의 "복원본에 재파기 절차가 적용됨을 확인했다"가 이것
```

> **"복원했더니 지운 개인정보가 살아났다"는 실무에서 실제로 나는 사고다.**
> 그리고 이건 **복원 절차에 파기를 포함시켜야만** 막을 수 있다.
> 04의 복원 리허설과 여기가 연결되는 지점이다.

**로그도 마찬가지다.** 그래서 애초에 **로그에 개인정보를 안 찍는 게** 정답이다. 나중에 지우려면 훨씬 어렵다.

### 2-5. ⭐⭐⭐ 이 프로젝트에 실제로 구현된 개인정보 설계

**여기가 이 편에서 유일하게 "실제로 만든 것"이고, 면접에서 가장 강한 부분이다.**

블로그 댓글과 방문자 통계 기능을 만들면서 **개인정보 설계를 축으로 삼았다.**

#### ① 원본 IP를 저장하지 않는다

```
댓글에 남기는 것은 둘뿐:

  ip_prefix   앞 2옥텟만 (예: "203.0.*.*")   →  화면 표시용
  ip_hash     salt + SHA-256 해시            →  차단 판단용
```

**왜 둘로 나눴나?** 목적이 다르기 때문이다.

- **표시**: 관리자가 "이 사람 아까 그 사람이네" 정도를 알면 된다 → 앞 2옥텟이면 충분
- **차단**: 같은 사람인지 대조만 하면 되고 원본 값은 필요 없다 → 해시면 충분

**둘 다 원본 IP가 필요 없다.** 그래서 저장하지 않는다.

#### ② ⭐ salt가 이 설계 전체의 축이다

```
ip_hash = SHA-256(salt + IP)

salt 가 없거나 알려지면?
  → IPv4는 43억 개뿐이다
  → 전부 해시해서 대조하면 원본 IP를 역산할 수 있다 (rainbow table)
  → ip_hash 가 사실상 "되돌릴 수 있는 원본 IP" 가 된다 💀
```

**그래서 salt를 코드에 두지 않고 Kubernetes Secret으로 관리하고, 운영에서 값이 없으면 아예 기동이 실패하도록 만들었다.**

```yaml
# application-prod.yml 에 기본값이 없다
# secretKeyRef 로만 주입된다
# → 값이 없으면 백엔드가 CrashLoop
```

**이건 의도적인 설계다.** 기본값을 두면 "설정을 깜빡했는데 잘 돌아가는" 상황이 생기고, 그러면 **공개 저장소에 적힌 `local-dev-salt` 로 해싱된다.** 그건 salt가 없는 것과 같다.

**실제로 이 문제를 최종 리뷰에서 발견했다.** 배포 직전에 Secret이 없다는 걸 확인하고 만들었다. 없이 배포했으면 백엔드가 CrashLoop에 빠졌을 것이다 — **설계대로 안전하게 실패한 것**이다.

#### ③ ⭐ 방문자 중복 제거에 날짜를 섞는다

```
Redis 집합에 넣는 값:  hash(salt + 날짜 + IP)
```

**날짜를 왜 섞나?**

```
[날짜가 없다면]
  8/1의 해시값과 8/2의 해시값이 같다
  → "이 사람이 어제도 왔고 오늘도 왔다" 를 알 수 있다
  → 날짜를 넘나드는 추적이 가능해진다

[날짜를 섞으면]
  8/1: hash(salt + "2026-08-01" + IP) = A
  8/2: hash(salt + "2026-08-02" + IP) = B      ← A와 B는 완전히 다르다
  → 하루 안에서는 중복 제거가 되고
  → 다음 날에는 같은 사람인지 대조할 수 없다  ✅
```

**"하루치 순 방문자 수"라는 목적은 달성하면서 추적은 불가능하게 만든 것이다.** 이게 **목적 제한(purpose limitation)** 의 구체적 구현이다.

#### ④ 유입 경로를 받는 즉시 축소한다

```
referer 원본 URL  →  받는 즉시 세 버킷으로 축소  →  원본은 버린다
                     (search / sns / other)
```

**원본 referer에는 검색어나 개인 정보가 들어 있을 수 있다.** "어느 경로로 들어왔나"만 알면 되므로, **받는 즉시 필요한 형태로 줄이고 원본을 버린다.**

> ### 이 넷을 관통하는 원칙
> **"목적에 필요한 최소 형태로 변환한 뒤 원본을 버린다."**
> 나중에 지우는 것보다 **애초에 안 가지는 게** 훨씬 안전하다. (2-1의 원칙)

## 3. 대안 표와 내 선택

| 접근 | 유출 시 피해 | 기능 | 채택 |
|---|---|---|---|
| 원본 저장 + 화면에서 마스킹 | **최대** (API에 원문이 나감) | 전부 가능 | ✗ |
| 원본 저장 + 서버 projection | 큼 | 전부 가능 | △ |
| **필요 최소 형태로 변환 후 원본 폐기** | **최소** | 목적 범위 내 | **✓** |

**IP를 예로 들면**: 원본을 저장하고 마스킹해서 보여주는 것과, 애초에 `ip_prefix` 와 `ip_hash` 만 저장하는 것은 **유출 시 피해가 완전히 다르다.** 후자는 유출돼도 원본 IP를 복원할 수 없다(salt를 함께 잃지 않는 한).

## 4. 진위 한 줄

**⚠️ 시나리오 화면은 고정 대본이다.** `OperationsPracticeEngine.privacyLifecycle()` 이 고정 step을 반환한다.

**✅ 하지만 이 프로젝트에 실제 개인정보 설계가 따로 있다.** 블로그 댓글과 방문자 통계의 IP 처리(`ip_prefix` / salted `ip_hash` / 날짜 혼합 Redis 집합 / referer 3버킷 축소)는 **실제로 구현되고 배포된 코드**다.

**면접에서는 이렇게 나눠 말한다.**

> "이 화면은 개인정보 수명주기를 정리한 설계 문서입니다. 다만 실제로 구현한 개인정보 설계가 따로 있는데, 블로그 댓글에서 원본 IP를 저장하지 않고 표시용 앞 2옥텟과 차단용 salted 해시만 남기도록 만들었습니다. 그리고 방문자 중복 제거 해시에 날짜를 섞어서 하루 안에서만 대조되고 다음 날에는 같은 사람인지 알 수 없게 했고요."

## 5. 30초 구두 답변

> 개인정보는 일반 데이터와 반대라고 생각합니다. 많이 가질수록 유출 시 피해가 커지니까, 가장 확실한 보호는 애초에 안 가지는 겁니다.
>
> 그래서 블로그 댓글을 만들 때 원본 IP를 저장하지 않았습니다. 표시용으로는 앞 2옥텟만, 차단 판단용으로는 salt를 섞은 SHA-256 해시만 남깁니다. 둘 다 원본이 필요 없는 용도라서요. salt가 이 설계의 축인데, salt가 새면 IPv4가 43억 개뿐이라 전부 해시해서 대조하면 역산이 됩니다. 그래서 Secret으로 관리하고 운영에서 값이 없으면 아예 기동이 실패하게 만들었습니다. 기본값을 두면 설정을 깜빡했는데 잘 돌아가는 상황이 생기고, 그게 제일 위험하거든요.
>
> 방문자 중복 제거는 해시에 날짜를 섞었습니다. 그러면 하루 안에서는 중복 제거가 되는데 다음 날에는 같은 사람인지 대조가 안 됩니다. 순 방문자 수라는 목적은 달성하면서 추적은 불가능하게요.
>
> 그리고 파기에서 제일 어려운 게 백업입니다. 지웠는데 예전 백업으로 복원하면 되살아나거든요. 백업 파일을 직접 수정할 수는 없으니까, 보관 기간을 짧게 해서 자연 소멸시키거나 복원 절차 자체에 재파기를 포함시켜야 합니다.

## 6. 꼬리질문과 답

**Q1. 탈퇴하면 다 지우면 되지 않나요?**

**법적으로 안 됩니다.** 전자상거래법상 계약·결제 기록은 5년, 소비자 불만 처리 기록은 3년 보존 의무가 있습니다. 다 지우면 법 위반입니다.

그래서 **분리**합니다. 이름·이메일·전화번호처럼 서비스 이용에 필요했던 건 즉시 파기하고, 거래 기록은 보존하되 **식별자를 분리하거나 대체키로 바꿉니다.** "무엇이 팔렸는지"는 남기고 "누가 샀는지"는 최소화하는 거죠.

그리고 **세션과 리프레시 토큰은 가장 먼저 폐기합니다.** 탈퇴 처리 중에 기존 세션으로 계속 서비스를 쓸 수 있으면 안 되니까요.

**Q2. 백업에 있는 개인정보는 어떻게 지우나요?**

**백업 파일을 직접 수정하는 건 사실상 불가능합니다.** 압축된 덤프고 수정하면 무결성이 깨집니다.

현실적인 방법이 둘입니다. 하나는 **보관 기간으로 자연 소멸**시키는 겁니다. 백업을 7일만 보관하면 파기 후 7일이 지나면 그 정보가 담긴 백업이 전부 사라집니다. 다른 하나는 **복원 시 재파기**입니다. 복원했다는 것 자체를 트리거로 삼아서, 복원 시점 이전에 파기 요청된 대상을 다시 파기합니다. 그러려면 파기 요청 목록은 따로 보존해야 하고요.

**복원 절차에 파기를 포함시키지 않으면 "복원했더니 지운 정보가 살아나는" 사고가 납니다.** 실무에서 실제로 나는 문제입니다.

**Q3. 로그에 개인정보가 찍히는 건요?**

**애초에 안 찍는 게 정답입니다.** 로그는 여러 시스템에 복제되고 장기 보관되기 때문에 나중에 지우는 게 훨씬 어렵습니다.

방법은 **로깅 시점에 마스킹**하는 겁니다. 로거에 필터를 걸어서 이메일·전화번호 패턴을 자동으로 가리거나, 애초에 식별자 대신 내부 ID만 찍습니다.

그리고 **에러 스택트레이스도 조심해야 합니다.** 예외 메시지에 요청 본문이 통째로 들어가는 경우가 있어서요.

**Q4. `ip_hash` 는 개인정보인가요?**

**salt가 안전하면 아니고, salt가 새면 개인정보입니다.** 이 구분이 중요합니다.

IPv4 주소 공간은 43억 개라서 salt 없이 해싱하면 전부 미리 계산해서 대조하는 게 현실적으로 가능합니다. 그러면 해시가 원본 IP와 사실상 같아집니다.

그래서 **이 설계 전체가 salt 한 문자열의 비밀성에 달려 있습니다.** 그게 제가 salt를 Secret으로 관리하고, 운영에서 값이 없으면 기동이 실패하도록 만든 이유입니다. "돌아가긴 하는데 안전하지 않은" 상태를 아예 불가능하게 만든 거죠.

## 7. 모르면 인정할 선

**여기까지는 자신 있게 답한다**
- **안 가진 정보는 유출될 수 없다**는 기본 원칙
- 역할별 마스킹과 **서버에서 잘라야 하는 이유**
- **조회 기록이 내부자 사고에 대한 억제력**이라는 것
- 탈퇴 ≠ 삭제, 보존 의무와 식별자 분리
- **파기의 진짜 어려움 — 개인정보가 흩어져 있는 곳들**
- **백업 파기 문제와 두 가지 현실적 해법**
- **내 프로젝트의 실제 설계**: `ip_prefix`/`ip_hash` 분리, salt의 역할, 날짜 혼합, referer 축소
- **salt가 없으면 기동이 실패하게 만든 이유**

**여기부터는 "안 해봤습니다"라고 말한다**
- 개인정보 보호법 조항의 정확한 인용 (원칙은 알지만 조문은 확인 필요)
- 파기 요청 워크플로와 처리 기한 관리 시스템
- 로그 마스킹 필터 실제 구현
- 개인정보 영향평가(PIA) 수행
- 암호화 저장과 키 관리(KMS) 실무

> ### 자가 점검
> **"탈퇴하면 다 지우면 되지 않나"** 에 보존 의무와 분리로 답할 수 있는가.
> **"백업에 있는 개인정보"** 문제와 두 해법을 설명할 수 있는가.
> **"방문자 해시에 날짜를 왜 섞나"** 를 답할 수 있는가.

# 3. 대량 스프레드시트 작업

**시나리오 id**: `bulk-spreadsheet-operations`
**모드**: `IN_MEMORY_EXPORT` / `STREAMING_EXPORT` / `INVALID_UPLOAD` / `STAGED_IMPORT`

## 1. 한 줄 정의

**10만 행 엑셀을 내려받고 올리는데**, 서버 메모리가 터지지 않고 잘못된 데이터가 운영에 반영되지 않게 한다.

## 2. 원리 — 왜 이 문제가 생기나

### 2-1. 내려받기 — 메모리가 터지는 이유

가장 순진한 엑셀 생성 코드는 이렇다.

```java
List<Post> posts = repository.findAll();        // ① 10만 행을 전부 메모리에
Workbook workbook = new XSSFWorkbook();         // ② 워크북 생성
for (Post p : posts) {
    Row row = sheet.createRow(...);             // ③ Cell 객체를 전부 만든다
    row.createCell(0).setCellValue(p.getTitle());
}
workbook.write(outputStream);                   // ④ 여기서야 파일로 나간다
```

**①에서 ④까지 모든 게 메모리에 있다.**

```
10만 행 × 10컬럼 = 100만 개의 Cell 객체
각 Cell 객체가 수십~수백 바이트
+ 엔티티 10만 개
─────────────────────────────
수백 MB ~ 1GB   💀
```

**그리고 이게 동시에 여러 명이 누르면 곱해진다.** 담당자 3명이 동시에 다운로드하면 3배다.

`IN_MEMORY_EXPORT` 모드가 이걸 보여준다 — peak memory 820MB.

### 2-2. ⭐ 해법 — 스트리밍

**발상은 단순하다: 전부 모으지 말고, 만들면서 바로 흘려보낸다.**

```
[적재 방식]  전부 읽는다 → 전부 만든다 → 파일로 쓴다
              ↑ 여기서 다 들고 있다

[스트리밍]   조금 읽는다 → 조금 만든다 → 파일로 쓴다 → 버린다 → 반복
                                                    ↑ 메모리에서 놓아준다
```

**두 군데를 동시에 고쳐야 한다.**

#### ① 읽기 — 페이징 (커서)

```
step("PAGES_READ", "2,000행 단위 cursor로 읽었다.")
```

10만 행을 한 번에 안 읽고 2,000행씩 나눠 읽는다. **한 번에 메모리에 있는 엔티티가 2,000개로 제한된다.**

여기서 놓치기 쉬운 게 하나 있다.

```
step("SNAPSHOT_FIXED", "조회 기준 시각과 예상 10만 행을 고정했다.")
```

**페이징 중에 데이터가 바뀌면 결과가 어긋난다.** 1페이지를 읽는 동안 새 글이 하나 추가되면 페이지 경계가 밀려서 **같은 행이 두 번 나오거나 누락된다.** 그래서 **기준 시각을 고정**하고 `created_at <= 기준시각` 조건으로 읽는다.

#### ② 쓰기 — SXSSF (Apache POI의 스트리밍 워크북)

```java
try (SXSSFWorkbook workbook = new SXSSFWorkbook(ROW_WINDOW)) { ... }
```

**`SXSSFWorkbook` 은 최근 N행만 메모리에 두고 나머지는 임시 파일로 밀어낸다.**

```
step("ROWS_FLUSHED", "window 밖 row를 임시 파일로 flush했다.")
```

```
[XSSFWorkbook]   10만 행 전부 메모리
[SXSSFWorkbook]  최근 N행만 메모리, 나머지는 디스크
                 → peak memory 820MB → 96MB
```

**대가**: 이미 flush된 행은 다시 수정할 수 없다. 순차적으로 쓰기만 가능하다. 대량 export에는 아무 문제가 없다.

#### ③ 응답도 스트리밍

```java
StreamingResponseBody body = output -> {
    try (InputStream input = Files.newInputStream(file.path())) {
        input.transferTo(output);          // 파일 → 응답으로 흘려보낸다
    } finally {
        deleteQuietly(file.path());        // ⭐ 다 보내면 임시 파일 삭제
    }
};
```

**임시 파일을 반드시 지워야 한다.** 안 지우면 디스크가 찬다. `finally` 에 둔 이유는 전송이 중간에 끊겨도 지우기 위해서다.

### 2-3. ⭐ 올리기 — Staging이 핵심이다

내려받기가 메모리 문제라면, **올리기는 정합성 문제**다.

```
운영자가 10,000행짜리 상품 정보 수정 파일을 올린다
  → 그중 18행에 오류가 있다 (가격이 음수, 존재하지 않는 상품코드 등)
  → 그냥 처리하면?
```

```
❌ 나쁜 방식: 한 행씩 읽으면서 바로 운영 테이블에 반영
   → 9,982행이 반영된 상태에서 18행이 실패
   → 부분 반영. 어디까지 됐는지 모른다
   → 롤백? 이미 커밋된 9,982행을 어떻게?
```

**01의 정산 배치에서 본 "부분 성공" 문제와 똑같다.**

**해법이 Staging(임시 적재)이다.**

```
1단계  파일 형식 검사      →  version, 필수 컬럼이 맞는가
2단계  전체 행 검증        →  10,000행을 전부 검사. 오류 18행 발견
3단계  ⭐ 판단
         정책 A: 오류가 하나라도 있으면 전부 거부  (INVALID_UPLOAD 모드)
         정책 B: 정상 건만 반영하고 오류는 보고    (STAGED_IMPORT 모드)
4단계  staging 테이블에 정상 9,982행 적재
5단계  조건부 upsert로 운영 테이블에 반영
6단계  오류 18행에 사유를 붙인 보고서 생성
```

> **핵심은 "검증이 전부 끝나기 전에는 운영 테이블을 건드리지 않는다"** 는 것이다.
> `INVALID_UPLOAD` 모드의 마지막 스텝이 정확히 이것이다 —
> *"검증 완료 전 운영 table 반영을 차단했다."*

**정책 A와 B 중 뭘 고르나?** 도메인에 따라 다르다.

```
정책 A (전부 거부)   →  정합성이 중요할 때. 정산, 회계
                        "일부만 반영된 상태"가 더 위험하다

정책 B (부분 반영)   →  운영 효율이 중요할 때. 상품 정보, 재고
                        9,982건을 다시 올리게 하는 게 비효율
```

**어느 쪽이든 오류 보고서는 반드시 필요하다.** "18행이 실패했습니다"만으로는 아무것도 못 고친다. **몇 번째 행이, 어떤 값이, 왜 거부됐는지**가 있어야 한다.

### 2-4. 업로드도 멱등해야 한다

```
step("REQUEST_KEY_CHECKED", "중복 upload request를 확인했다.")
```

**운영자가 "반응이 없네" 하고 업로드 버튼을 두 번 누르면?** 01에서 본 그대로다. 요청 키로 중복을 막는다.

## 3. 대안 표와 내 선택

**내려받기:**

| 접근 | peak memory | 구현 | 채택 |
|---|---|---|---|
| 전체 적재 | **수백 MB~1GB** | 쉬움 | ✗ |
| **페이징 + SXSSF** | **~100MB** | 중간 | **✓** |
| CSV로 대체 | 매우 낮음 | 쉬움 | △ (서식이 필요 없으면 최선) |
| 비동기 생성 + 링크 발송 | 낮음 | 높음 | 초대용량이면 |

**올리기:**

| 접근 | 부분 반영 | 오류 보고 | 채택 |
|---|---|---|---|
| 한 행씩 바로 반영 | **발생** | 어렵다 | ✗ |
| **전체 검증 → staging → 반영** | 없음 | 쉽다 | **✓** |

**CSV 이야기를 덧붙이면**: 서식·수식·여러 시트가 필요 없다면 **CSV가 압도적으로 가볍다.** 스트리밍이 자연스럽고 라이브러리도 필요 없다. "엑셀로 주세요"라는 요청이 실제로는 "표 데이터로 주세요"인 경우가 많으므로, **한 번 물어볼 가치가 있다.**

## 4. 진위 한 줄

**⚠️ 시나리오 화면은 고정 대본이다.** (peak memory 820MB → 96MB 같은 숫자는 상수)

**✅ 하지만 export 엔드포인트는 실제로 동작한다.**

`SpreadsheetExportController` / `SpreadsheetExportService` 가 실제로:
- `SXSSFWorkbook(ROW_WINDOW)` 로 **스트리밍 워크북**을 만들고
- 게시판 데이터를 페이징으로 읽어서
- 임시 파일에 쓰고
- `StreamingResponseBody` 로 응답에 흘려보낸 뒤
- `finally` 에서 임시 파일을 지운다

**면접에서 이렇게 말한다.**
> "시나리오 화면 숫자는 모델이지만, 10만 행 xlsx를 SXSSF 스트리밍으로 내보내는 엔드포인트는 실제로 동작합니다. 눌러서 파일을 받아 보실 수 있고요."

## 5. 30초 구두 답변

> 10만 행 엑셀을 만들 때 순진하게 짜면 엔티티 10만 개랑 Cell 객체 100만 개가 전부 메모리에 올라가서 수백 MB를 씁니다. 담당자 세 명이 동시에 누르면 세 배고요.
>
> 그래서 읽기와 쓰기를 둘 다 스트리밍으로 바꿉니다. 읽기는 2,000행 단위 커서로 나눠 읽고, 쓰기는 Apache POI의 SXSSFWorkbook을 씁니다. 최근 N행만 메모리에 두고 나머지는 임시 파일로 밀어내는 방식이라 peak memory가 100MB 아래로 떨어집니다. 응답도 StreamingResponseBody로 흘려보내고 끝나면 임시 파일을 지우고요.
>
> 여기서 놓치기 쉬운 게 페이징 중에 데이터가 바뀌면 페이지 경계가 밀려서 같은 행이 두 번 나오거나 누락된다는 겁니다. 그래서 조회 기준 시각을 고정합니다.
>
> 올리기는 메모리보다 정합성 문제입니다. 한 행씩 바로 반영하면 9,982행이 들어간 상태에서 18행이 실패하는 부분 반영이 생기거든요. 그래서 전체를 먼저 검증하고, 통과한 것만 staging에 적재한 다음 조건부 upsert로 반영합니다. 검증이 끝나기 전에는 운영 테이블을 아예 안 건드리는 게 핵심이고요.

## 6. 꼬리질문과 답

**Q1. 그냥 CSV로 주면 안 되나요?**

**서식이 필요 없으면 CSV가 훨씬 낫습니다.** 스트리밍이 자연스럽고 라이브러리도 필요 없고 메모리도 거의 안 씁니다.

xlsx가 필요한 건 여러 시트, 셀 서식, 수식, 열 너비 같은 게 있을 때입니다. **"엑셀로 주세요"가 실제로는 "표 데이터로 주세요"인 경우가 많아서**, 저는 한 번 물어보는 게 맞다고 봅니다.

CSV의 함정은 **한글 인코딩**입니다. UTF-8로 저장하면 엑셀에서 깨져 보여서, BOM을 붙이거나 UTF-8 BOM으로 저장해야 합니다.

**Q2. 파일이 너무 커서 다운로드가 타임아웃되면요?**

**비동기 생성으로 바꿉니다.** 요청을 받으면 즉시 "생성 중입니다"를 응답하고, 백그라운드에서 파일을 만들어 오브젝트 스토리지에 올린 다음, 완료되면 다운로드 링크를 알려줍니다.

**03의 이미지 편에서 본 동기/비동기 선택과 같은 구조**입니다. 그리고 따라오는 것들도 같습니다 — 상태 관리, 완료 알림, 실패 처리, 그리고 생성된 파일의 수명주기 정책이요.

**Q3. staging 테이블은 어떻게 관리하나요?**

**업로드 단위로 구분하고 처리 후 정리합니다.** 업로드 ID를 컬럼으로 두고, 반영이 끝나면 지우거나 일정 기간 뒤 자동 삭제합니다.

**바로 안 지우고 며칠 두는 게 유용합니다.** "어제 올린 파일 뭐가 문제였죠?"를 확인할 수 있고, 잘못 반영했을 때 원본 입력을 볼 수 있어서요.

**Q4. 검증을 어디까지 해야 하나요?**

**형식 검증과 업무 규칙 검증을 나눠서 봅니다.**

형식 검증은 컬럼 개수, 데이터 타입, 필수값 같은 겁니다. 이건 빨라서 전부 검사할 수 있습니다.

업무 규칙 검증은 "이 상품코드가 실제로 존재하는가", "이 가격이 정책 범위 안인가" 같은 거라 **DB 조회가 필요합니다.** 10,000행에 각각 쿼리를 날리면 03에서 본 N+1이 됩니다. 그래서 **필요한 참조 데이터를 한 번에 읽어서 메모리에 두고 대조**하는 식으로 처리합니다.

## 7. 모르면 인정할 선

**여기까지는 자신 있게 답한다**
- 엑셀 생성에서 메모리가 터지는 정확한 이유 (엔티티 + Cell 객체)
- 스트리밍이 읽기·쓰기 양쪽에 필요하다는 것
- **SXSSF가 하는 일** (윈도우 밖 행을 디스크로 flush)
- **페이징 중 데이터 변경 문제와 기준 시각 고정**
- 임시 파일 정리를 `finally` 에 두는 이유
- **staging의 핵심 — 검증 완료 전 운영 테이블 미접촉**
- 전부 거부 vs 부분 반영의 판단 기준
- 업무 규칙 검증이 N+1이 되는 것과 그 회피

**여기부터는 "안 해봤습니다"라고 말한다**
- SXSSF 윈도우 크기의 실측 기반 튜닝 (**화면 숫자는 상수다**)
- 비동기 파일 생성과 오브젝트 스토리지 연동
- staging 테이블 파티셔닝과 대량 정리
- 업로드 파일 자체의 보안 검사 (매크로 포함 xlsm 등)

> ### 자가 점검
> **"메모리가 왜 터지나"** 를 객체 개수로 설명할 수 있는가.
> **"페이징 중 데이터가 바뀌면"** 무슨 일이 생기는지 답할 수 있는가.
> **"staging이 왜 필요한가"** 를 부분 반영으로 설명할 수 있는가.

# 4. 비즈니스 지표 백오피스

**시나리오 id**: `business-metrics-backoffice`
**모드**: `ONE_OFF_SQL` / `DEFINED_METRIC` / `EXPORT_RECONCILIATION` / `INDEXED_QUERY`

## 1. 한 줄 정의

**"이번 달 가입자 수 알려주세요"** 라는 같은 질문에, 누가 언제 물어도 같은 답이 나오게 한다.

## 2. 원리 — 왜 이 문제가 생기나

### 2-1. ⭐ "가입자 수"는 정의되지 않은 질문이다

`ONE_OFF_SQL` 모드가 보여주는 문제다.

```
step("REQUEST_INTERPRETED", "가입자 수의 기간과 상태를 개별 해석했다.")
step("QUERY_EXECUTED",      "일회성 SQL로 결과를 추출했다.")
step("TOTALS_DIVERGED",     "기존 보고서와 143건 차이가 발생했다.")     ← 💀
```

**왜 143건이 차이 나나?** "가입자 수"를 세는 데 결정해야 할 게 최소 다섯 가지다.

```
① 기간의 경계는?
     UTC 기준인가 KST 기준인가?
     → 9시간 차이. 월말·월초에 결과가 달라진다

② 탈퇴한 사람은?
     "이번 달 가입했다가 이번 달 탈퇴한 사람"은 가입자인가?

③ 테스트 계정은?
     내부 QA 계정, 데모 계정은 빼야 하나?

④ 이메일 미인증 계정은?
     가입 버튼은 눌렀는데 인증 안 한 사람은?

⑤ 중복 계정은?
     같은 사람이 두 번 가입한 경우?
```

**두 사람이 각자 SQL을 쓰면 이 다섯 가지를 다르게 해석한다.** 그리고 둘 다 "가입자 수"라고 부른다.

> ### 핵심
> **문제는 SQL이 틀린 게 아니다. "가입자 수"라는 말이 정의되지 않은 것이다.**
> 정의가 없으면 매번 다른 답이 나오고, **그러면 아무 숫자도 못 믿게 된다.**
> 숫자를 못 믿으면 그 숫자로 하는 의사결정도 못 한다.

### 2-2. 해법 — 지표를 "계약"으로 만든다

`DEFINED_METRIC` 모드다.

```
step("CONTRACT_LOADED",     "KST cutoff와 탈퇴·테스트 계정 제외 조건을 적용했다.")
step("VERSIONED_QUERY_RUN", "지표 version과 query hash를 기록했다.")
step("TOTAL_RECONCILED",    "정의서의 표본과 합계를 대조했다.")
```

**지표 정의서(metric contract)에 들어가야 하는 것:**

| 항목 | 예 |
|---|---|
| 이름 | `monthly_signups` |
| 한 줄 정의 | "해당 월에 가입 완료된 실사용자 계정 수" |
| 기간 기준 | **KST 기준 월초 00:00 ~ 월말 23:59:59** |
| 포함 조건 | `status = 'ACTIVE'` 또는 `'WITHDRAWN'` (가입은 했으므로) |
| 제외 조건 | `is_test = true`, `email_verified = false` |
| 버전 | v2 (2026-07-01부터. v1은 탈퇴자를 제외했었다) |
| 소유자 | 그로스팀 |

**버전이 왜 필요한가?**

```
"작년 6월 가입자는 1,200명이었는데 지금 조회하니 1,150명이네요?"
  → 그 사이 지표 정의가 바뀌었다 (탈퇴자 제외로)
  → 버전이 없으면 "숫자가 틀렸다"로 보인다
  → 버전이 있으면 "v1 기준 1,200, v2 기준 1,150" 으로 설명된다 ✅
```

> **지표 정의는 바뀐다. 바뀌는 게 문제가 아니라 바뀐 걸 모르는 게 문제다.**

**`query hash` 를 기록하는 이유**도 같다. 실제로 어떤 쿼리가 돌았는지를 남겨야 나중에 재현할 수 있다.

### 2-3. 화면과 export가 다르면 신뢰가 무너진다

`EXPORT_RECONCILIATION` 모드다.

```
화면:      "12,480건"
엑셀 받음:  12,463행                    ← 왜 다르지? 💀
```

**흔한 원인 셋:**

```
① 필터 조건이 다르다
     화면은 "최근 30일", export는 "이번 달"

② 조회 시점이 다르다
     화면을 본 뒤 export를 누르는 사이에 데이터가 늘었다

③ 페이징 처리가 다르다
     화면은 count 쿼리, export는 실제 행 — 조건이 미묘하게 다름
```

**해법:**

```
step("FILTERS_SHARED",   "화면과 export가 같은 filter contract를 사용했다.")
step("EXPORT_GENERATED", "기준 시각을 포함해 파일을 생성했다.")     ← ⭐
step("COUNTS_MATCHED",   "화면 합계와 export row 수가 일치했다.")
```

**① 필터를 코드로 공유한다.** 화면 쿼리와 export 쿼리가 **같은 조건 객체**를 쓰게 만든다. 두 곳에 조건을 따로 쓰면 반드시 어긋난다.

**② 기준 시각을 파일에 박는다.** *"2026-08-03 14:30:00 기준"* 이 파일 안에 있으면, 나중에 숫자가 달라도 **"시점이 다르다"로 설명된다.** 3편의 스냅샷 고정과 같은 이야기다.

**③ 건수를 대조한다.** export 후 화면 합계와 파일 행 수를 비교해서 다르면 경고한다.

> **"숫자가 다르다"는 신뢰의 문제다.** 한 번 어긋나면 그 뒤로 모든 숫자를 의심하게 된다.
> **기준 시각 한 줄이 이 신뢰를 지킨다.**

### 2-4. `INDEXED_QUERY` — 지표 쿼리는 무겁다

```
step("PLAN_CAPTURED",    "EXPLAIN으로 full scan과 정렬 비용을 확인했다.")
step("INDEX_APPLIED",    "기간·상태 조건에 맞는 index를 적용했다.")
step("RESULTS_COMPARED", "변경 전후 결과 집합이 같음을 검증했다.")     ← ⭐
```

**세 번째 스텝이 핵심이다.** 인덱스를 붙이거나 쿼리를 고친 뒤에는 **결과가 같은지 반드시 확인해야 한다.**

```
"2,800ms → 180ms 로 빨라졌습니다!"
  → 그런데 결과 건수가 12,480에서 12,350으로 바뀌었다면?
  → 빨라진 게 아니라 틀린 것이다 💀
```

**성능 개선에서 가장 흔한 사고**다. 쿼리를 고치다가 조건 하나를 놓치면 빨라지면서 틀린다.

> **최적화의 전제는 "결과가 같다"이다.** 이걸 확인하지 않은 최적화는 최적화가 아니다.

**그리고 EXPLAIN을 먼저 보는 이유**: 감으로 인덱스를 붙이면 안 쓰이는 인덱스만 늘어난다. 인덱스는 공짜가 아니라 **쓰기 성능을 깎고 저장 공간을 쓴다.** 실제 실행 계획을 보고 "여기서 full scan이 나니까 이 조건에 인덱스"라고 판단해야 한다.

## 3. 대안 표와 내 선택

| 접근 | 일관성 | 속도 | 유지보수 | 채택 |
|---|---|---|---|---|
| 요청마다 SQL 작성 | **❌ 매번 다름** | 즉시 | 최악 | ✗ |
| **지표 정의서 + 버전 관리** | ✅ | 중간 | 좋음 | **✓** |
| BI 도구 도입 | ✅ | 좋음 | 도구 학습 | 규모가 크면 |
| 사전 집계 테이블 | ✅ | **매우 빠름** | 집계 갱신 관리 | 지표가 고정되면 |

**지표 정의서를 고른 이유**: 정합성 문제의 원인이 **속도가 아니라 정의**이기 때문이다. BI 도구를 도입해도 정의가 없으면 같은 문제가 그대로 난다.

## 5. 30초 구두 답변

> "이번 달 가입자 수"는 사실 정의되지 않은 질문이라고 생각합니다. 기간이 UTC인지 KST인지, 탈퇴한 사람을 포함하는지, 테스트 계정을 빼는지, 이메일 미인증은 어떻게 하는지에 따라 답이 달라지거든요. 두 사람이 각자 SQL을 쓰면 이걸 다르게 해석하고, 둘 다 "가입자 수"라고 부릅니다. 그러면 숫자가 안 맞고, 한 번 안 맞으면 그 뒤로 모든 숫자를 의심하게 됩니다.
>
> 그래서 지표를 계약으로 만듭니다. 이름, 한 줄 정의, 기간 기준, 포함·제외 조건, 버전, 소유자를 문서로 고정하고 쿼리는 거기서 파생시킵니다. 버전이 중요한데, 지표 정의는 바뀌기 마련이고 바뀌는 게 문제가 아니라 바뀐 걸 모르는 게 문제라서요.
>
> 화면과 export가 다른 것도 같은 문제입니다. 필터 조건을 코드로 공유해서 두 곳에 따로 쓰지 않게 하고, 파일에 기준 시각을 박아 넣습니다. 그러면 나중에 숫자가 달라도 "시점이 다르다"로 설명이 됩니다.
>
> 그리고 지표 쿼리를 최적화할 때는 반드시 결과 집합이 같은지 확인합니다. 2,800ms가 180ms가 됐는데 건수가 바뀌었으면 빨라진 게 아니라 틀린 거니까요.

## 6. 꼬리질문과 답

**Q1. 지표 정의를 어디에 두나요?**

**코드와 문서 양쪽입니다.**

문서에는 사람이 읽을 정의를 둡니다. "월간 가입자 = 해당 월 KST 기준 가입 완료된 실사용자 계정 수, 테스트 계정 제외" 같은 식으로요.

코드에는 그 정의를 **한 곳에만** 구현합니다. 화면·API·export·배치가 전부 같은 함수를 부르게요. **두 곳에 조건을 쓰면 반드시 어긋납니다.**

그리고 정의서에 **표본 검증 케이스**를 붙이면 좋습니다. "2026년 7월은 1,234명"처럼 알려진 값을 테스트로 고정해 두면, 나중에 누가 조건을 건드렸을 때 바로 깨집니다.

**Q2. 시간대 문제가 왜 그렇게 자주 생기나요?**

**DB는 UTC로 저장하고 사람은 KST로 생각하기 때문**입니다.

`timestamptz` 로 저장하면 내부적으로 UTC고, 조회할 때 세션 타임존에 따라 변환됩니다. 그런데 **배치는 서버 타임존, 화면은 브라우저 타임존, SQL 콘솔은 또 다른 타임존**을 쓰기 쉽습니다.

특히 **월말·월초에 9시간 차이가 결과를 바꿉니다.** 7월 31일 오후 4시(KST) 가입은 UTC로는 7월 31일 오전 7시라 괜찮은데, 8월 1일 오전 5시(KST) 가입은 UTC로 7월 31일 오후 8시라 **7월 가입자로 잡힙니다.**

그래서 **지표 정의에 타임존을 명시**하고, 쿼리에서 `AT TIME ZONE 'Asia/Seoul'` 로 명시적으로 변환합니다.

**Q3. 실제로 지표 문제를 겪은 적 있나요?**

**있습니다. 블로그 통계 대시보드를 만들었을 때입니다.**

API는 200을 주고 테이블에도 행이 쌓이고 있었는데, 대시보드에 그려 놓고 보니 **유입 경로가 전부 `direct`, 디바이스가 전부 `pc`, 방문자 수가 1로 고정**돼 있었습니다.

원인은 글 조회가 Next.js 서버에서 Spring으로 부르는 **서버-서버 fetch**였다는 겁니다. 그래서 Spring이 본 `referer`·`user-agent`·IP가 **방문자 것이 아니라 Next.js 서버 것**이었습니다. 방문자 정보가 아예 도달하지 않고 있었던 거죠. `getBlogPost` 가 그 세 헤더를 실어 보내도록 고쳤습니다.

**여기서 배운 게 큽니다.** 집계는 **실패가 아니라 "한쪽으로 쏠린 성공"으로 나타납니다.** 응답 코드로는 절대 안 잡히고, **화면에 숫자로 그려 놓고서야** 이상한 걸 알았습니다.

**Q4. 사전 집계 테이블은 언제 쓰나요?**

**지표가 고정되고 조회가 잦을 때**입니다. 매번 원본을 스캔하는 대신 일별 집계를 미리 만들어 두는 거죠.

대가는 **집계와 원본이 어긋날 수 있다**는 겁니다. 그래서 주기적으로 대조해야 하고, 지표 정의가 바뀌면 과거 집계를 다시 만들어야 합니다.

실제로 이 프로젝트에 그 부채가 있습니다. `tb_blog_daily_stat` 의 유입 경로 컬럼과 새로 만든 `tb_blog_referrer_daily` 테이블이 **같은 것을 두 번 세고 있습니다.** 새 테이블이 충분히 쌓이면 옛 컬럼을 지울 계획인데 아직 안 했습니다.

## 7. 모르면 인정할 선

**여기까지는 자신 있게 답한다**
- **"가입자 수"가 정의되지 않은 질문인 이유** (결정해야 할 다섯 가지)
- 지표 정의서에 들어갈 항목과 **버전이 필요한 이유**
- 화면-export 불일치의 원인 셋과 각각의 해법
- **기준 시각을 파일에 박는 것**의 가치
- **최적화의 전제는 "결과가 같다"** 는 것
- 시간대 문제가 월말·월초에 터지는 메커니즘
- **집계 오류는 "쏠린 성공"으로 나타난다** — 실제 겪은 사례

**여기부터는 "안 해봤습니다"라고 말한다**
- BI 도구(Metabase, Superset 등) 실제 운영
- 데이터 웨어하우스 / dbt 같은 지표 관리 체계
- 사전 집계 테이블의 재생성 전략
- 지표 이상 탐지 자동화

> ### 자가 점검
> **"가입자 수를 세는 데 결정해야 할 것"** 을 셋 이상 댈 수 있는가.
> **"2,800ms가 180ms가 됐는데 건수가 달라졌다면"** 뭐라고 답할 것인가.
> **블로그 통계 사고**를 "쏠린 성공"이라는 말로 설명할 수 있는가.

# 5. 알림 발송 운영

**시나리오 id**: `notification-delivery-operations`
**모드**: `NORMAL` / `TIMEOUT_RETRY` / `RATE_LIMIT` / `PERMANENT_FAILURE` / `MANUAL_REPLAY`

## 1. 한 줄 정의

**결제 완료 알림이 안 갔을 때**, 중복 발송 없이 정확히 한 번 전달되게 하고, 안 되면 사람이 처리할 수 있게 남긴다.

## 2. 원리 — 이 편은 02의 종합편이다

**이 시나리오를 보면 02에서 배운 게 전부 다시 나온다.** 그래서 복습에 딱 좋다.

| 모드 | 02의 어느 개념 |
|---|---|
| `NORMAL` | **Outbox 패턴** (Kafka DLQ 편) |
| `TIMEOUT_RETRY` | **타임아웃은 "모름"** (제휴 API 편) |
| `RATE_LIMIT` | **429와 Retry-After** (제휴 API 편) |
| `PERMANENT_FAILURE` | **DLQ와 poison pill** (Kafka DLQ 편) |
| `MANUAL_REPLAY` | **DLQ 재처리 + 멱등성** (02에서 "안 했다"고 한 부분) |

### 2-1. `NORMAL` — Outbox가 여기서도 필요하다

```
step("EVENT_COMMITTED",   "결제 완료와 발송 요청을 함께 기록했다.")   ← ⭐ 같은 트랜잭션
step("MESSAGE_SENT",      "request key와 template으로 발송했다.")
step("DELIVERY_CONFIRMED","provider message ID의 전달 상태를 확정했다.")
```

**왜 여기도 Outbox인가?**

```
❌ 결제 완료 저장 → 커밋 → SMS 발송 호출
   → 커밋과 발송 사이에서 죽으면 알림이 영원히 안 간다
   → 고객: "결제됐는데 문자가 안 왔어요"

✅ 결제 완료 + 발송 요청을 같은 트랜잭션에 기록
   → 릴레이가 발송 요청을 읽어서 처리
   → 서버가 언제 죽든 발송 요청은 남아 있다
```

**02의 이중 쓰기 문제 그대로다.**

**그리고 "발송했다"와 "전달됐다"는 다르다.**

```
발송(sent)     : 내가 통신사 API에 요청을 보냈다
전달(delivered): 실제로 고객 휴대폰에 도착했다     ← callback으로만 알 수 있다
```

번호가 없는 번호이거나 수신 거부 상태면 **발송은 성공하고 전달은 실패**한다. 그래서 provider callback으로 최종 상태를 확정한다.

### 2-2. `TIMEOUT_RETRY` — 02의 핵심이 그대로

```
step("MESSAGE_SENT",     "발송 요청을 전송했다.")
step("RESPONSE_TIMEOUT", "응답 없이 read timeout이 발생했다.")      ← 모름
step("STATUS_QUERIED",   "같은 request key의 처리 상태를 조회했다.")  ← ⭐ 재시도 아님
step("DELIVERY_REUSED",  "새 발송 없이 기존 전달 결과를 반영했다.")
```

**타임아웃에 재시도하지 않고 조회한다.** 02에서 배운 그대로다.

**여기서 재시도하면?** 고객이 같은 결제 문자를 두 번 받는다. 심각한 사고는 아니지만 **신뢰가 깎이고, 마케팅 메시지라면 스팸 신고 대상**이 된다.

### 2-3. `RATE_LIMIT` — 여기선 내가 받는 쪽이다

```
step("RATE_LIMITED",     "HTTP 429와 Retry-After를 받았다.")
step("RETRY_SCHEDULED",  "jitter와 최대 횟수를 포함해 재시도를 예약했다.")   ← ⭐
step("MESSAGE_DELIVERED","두 번째 attempt에서 전달됐다.")
```

**통신사 API는 대부분 초당 발송 한도가 있다.** 그리고 알림은 **대량 발송이 흔해서** 429가 자주 난다.

**`jitter` 가 명시된 이유**: 03에서 본 thundering herd 때문이다. 1만 건이 전부 "3초 뒤"를 지키면 3초 뒤에 또 몰린다.

**그리고 여기서는 "즉시 재시도"가 아니라 "예약"이다.** 큐에 다시 넣어서 나중에 처리한다. 요청 스레드를 붙잡고 기다리지 않는다 — 03의 커넥션 풀 편과 같은 사고방식이다.

### 2-4. ⭐ `PERMANENT_FAILURE` — 재시도하면 안 되는 실패

```
step("RECIPIENT_REJECTED", "유효하지 않은 수신처 오류를 반환했다.")
step("RETRY_SKIPPED",      "영구 실패로 분류해 자동 재시도를 중단했다.")   ← ⭐
step("DLQ_REDACTED",       "민감값을 마스킹해 운영 검토 대상으로 보냈다.")  ← ⭐⭐
```

**"없는 번호"에 100번 재시도해도 100번 실패한다.** 자원만 쓰고 큐만 막는다.

> **02의 두 모드가 여기서 다시 나온다.**
> `NOTIFICATION_RETRY`(일시적) vs `NOTIFICATION_ALWAYS_FAIL`(영구)의 구별.
> **재시도로 될 실패와 안 될 실패를 가르는 것**이 알림 시스템의 핵심 판단이다.

**그리고 여기 새로운 게 하나 있다 — `DLQ_REDACTED`.**

```
DLQ에 보내는 메시지에는 뭐가 들어 있나?
  → 수신자 전화번호, 이름, 결제 금액, 주문 내역...
  → 즉 개인정보다

DLQ는 어디에 있나?
  → Kafka topic. 운영자가 조회한다. 오래 보관된다
  → ⚠️ 개인정보가 별도 시스템에 장기 보관된다
```

**그래서 DLQ에 넣기 전에 민감값을 마스킹한다.** 2편(개인정보)과 이어지는 지점이다.

**운영자가 원인을 파악할 만큼만 남기고 원문은 가린다.** "010-****-1234로 발송 실패, 사유: 없는 번호" 정도면 충분하다.

### 2-5. ⭐⭐ `MANUAL_REPLAY` — 02에서 "안 했다"고 한 그것

02의 Kafka 편 꼬리질문에서 이렇게 답했다.

> "DLQ는 만드는 것보다 쌓인 걸 처리하는 운영 절차가 훨씬 중요한데, 거기까지는 안 했습니다."

**이 모드가 바로 그 절차를 설계한 것이다.**

```
step("DLQ_REVIEWED",      "실패 원인과 수신처 정정 근거를 확인했다.")      ← 1편의 "근거 확인"
step("REPLAY_AUTHORIZED", "권한과 승인 ticket을 기록했다.")               ← 1편의 "승인·감사"
step("KEY_REUSED",        "기존 request key로 중복 생성 여부를 확인했다.")  ← 01의 "멱등성"
step("DELIVERY_CONFIRMED","재처리 attempt의 최종 전달을 확인했다.")        ← "돌았다 ≠ 맞다"
```

**네 스텝이 각각 다른 편의 원칙을 그대로 가져온다.** 이 시나리오가 종합편인 이유다.

**`KEY_REUSED` 가 특히 중요하다.**

```
운영자가 재처리를 눌렀다.
  → 새 request key로 발송하면?
     → 원래 건이 사실은 전달됐었다면 고객이 두 번 받는다 💀
  → 기존 request key를 재사용하면?
     → provider가 "이미 처리한 요청"으로 인식해서 중복을 막는다 ✅
```

> **재처리는 "새 요청"이 아니라 "같은 요청의 재시도"여야 한다.**
> 그래야 멱등성이 유지된다.

## 3. 대안 표와 내 선택

| 실패 유형 | 대응 | 근거 |
|---|---|---|
| 타임아웃 | **재시도 X, 상태 조회** | 중복 발송 위험 |
| 429 | **Retry-After + jitter로 예약** | 상대가 시점을 알려줌 |
| 5xx | 제한 재시도 | 일시적일 수 있음 |
| 유효하지 않은 수신처 | **재시도 X, DLQ** | 100번 해도 실패 |
| 템플릿 오류 | **재시도 X, DLQ** | 코드 수정이 필요 |

**전체 구조:**

```
결제 완료 ─┬─ (같은 트랜잭션) ─→ Outbox
           └─→ 릴레이 → 발송 → provider callback → 전달 확정
                        │
                        ├─ 일시 실패 → 백오프 재시도 (jitter)
                        └─ 영구 실패 → 마스킹 → DLQ → 운영자 검토 → 승인 → 같은 key로 재처리
```

**다만 이 프로젝트에 실제 알림은 있다** — 운영 알람이 **Alertmanager를 통해 텔레그램으로** 나간다(`scripts/test-alertmanager-telegram.sh`, `rehearse-backend-down-alert.sh`). 사용자 알림은 아니고 운영자 알람이지만, **알림 경로를 실제로 구성하고 리허설까지 해본 경험은 있다.**

## 5. 30초 구두 답변

> 알림은 두 가지를 동시에 만족해야 합니다. 반드시 가야 하고, 두 번 가면 안 됩니다.
>
> 반드시 가게 하려면 결제 완료와 발송 요청을 같은 트랜잭션에 기록하는 Outbox가 필요합니다. 커밋하고 나서 발송을 호출하면 그 사이에 죽었을 때 알림이 영원히 안 가거든요. 그리고 "발송했다"와 "전달됐다"는 달라서, provider callback으로 최종 상태를 확정합니다.
>
> 두 번 안 가게 하려면 실패 유형을 구별해야 합니다. 타임아웃은 상태가 '모름'이라 재시도하면 고객이 문자를 두 번 받습니다. 그래서 재시도 대신 같은 request key로 상태를 조회합니다. 429는 통신사가 재시도 시점을 알려준 거니까 그 시간에 jitter를 섞어서 예약하고요. 대량 발송이라 전부 같은 시각에 재시도하면 또 몰립니다.
>
> 없는 번호 같은 영구 실패는 100번 해도 실패라 자동 재시도를 중단하고 DLQ로 보냅니다. 이때 중요한 게 DLQ 메시지에 전화번호랑 이름이 들어 있다는 겁니다. DLQ는 별도 시스템에 오래 보관되니까 개인정보가 거기 쌓이는 거죠. 그래서 마스킹해서 보냅니다.
>
> 그리고 운영자가 재처리할 때는 반드시 기존 request key를 재사용합니다. 새 키로 보내면 원래 건이 사실 전달됐던 경우에 중복이 나니까요.

## 6. 꼬리질문과 답

**Q1. 알림이 안 갔는지 어떻게 아나요?**

**provider callback으로 최종 상태를 받아야 압니다.** API 호출이 200을 줬다는 건 "요청을 접수했다"까지고, 실제 전달은 별개입니다.

그래서 발송 건마다 상태를 관리합니다. `PENDING` → `SENT` → `DELIVERED` 또는 `FAILED` 로요. 그리고 **일정 시간이 지나도 `SENT` 에 머물러 있는 건**을 찾는 배치가 필요합니다. callback이 유실될 수도 있으니까요.

지표로는 **전달률**을 봅니다. 평소 98%인데 갑자기 80%로 떨어지면 뭔가 잘못된 겁니다.

**Q2. DLQ에 개인정보를 넣지 않으려면요?**

**참조만 남기는 방법**이 있습니다. DLQ에는 발송 ID와 실패 사유만 넣고, 실제 수신처는 원본 테이블에서 권한을 확인한 뒤 조회하는 거죠.

그러면 DLQ 자체에는 개인정보가 없고, 조회할 때마다 권한 검사와 감사 기록이 남습니다. 2편에서 본 "조회를 기록한다"와 이어집니다.

다만 **원본이 파기되면 DLQ 건을 재처리할 수 없게 됩니다.** 그건 오히려 맞는 동작이라고 봅니다. 파기된 사람에게 알림을 보내면 안 되니까요.

**Q3. 대량 발송은 어떻게 하나요?**

**속도 제한을 지키면서 큐로 흘려보냅니다.** 10만 건을 한꺼번에 API에 던지면 429만 잔뜩 받습니다.

그래서 발송 요청을 큐에 넣고 **consumer가 통신사 한도에 맞춰 천천히 소비**합니다. 03에서 본 "미루기" 전략이고요.

그리고 **우선순위 분리**가 필요합니다. 결제 완료 알림 같은 거래성 메시지와 마케팅 대량 발송이 같은 큐에 있으면, 마케팅 10만 건 뒤에 결제 알림이 밀립니다. **큐를 나누거나 우선순위를 둬야 합니다.** 02의 consumer group 분리와 같은 발상입니다.

**Q4. 실제로 알림을 구현해 보셨나요?**

**사용자 알림은 아니고 운영 알람은 구성했습니다.** Prometheus Alertmanager에서 텔레그램으로 나가게 만들었고, 백엔드 다운 알람을 실제로 발생시켜 보는 리허설 스크립트도 있습니다.

04에서 말한 것과 같은 이유입니다. **"알람이 설정돼 있다"와 "알람이 실제로 온다"는 다르니까요.** 알람 설정을 해놓고 정작 장애 때 안 오는 경우가 많습니다.

다만 사용자 대상 알림 시스템(SMS, 푸시)은 만들어 본 적이 없습니다. 이 시나리오는 설계 정리입니다.

## 7. 모르면 인정할 선

**여기까지는 자신 있게 답한다**
- 알림에 Outbox가 필요한 이유 (02의 이중 쓰기)
- **"발송"과 "전달"의 구분**과 callback으로 확정하는 이유
- 실패 유형별 대응 (타임아웃/429/영구 실패)
- jitter가 필요한 이유
- **DLQ에 개인정보가 쌓인다는 인식**과 마스킹·참조 방식
- **재처리에 기존 request key를 재사용해야 하는 이유**
- 대량 발송에서 우선순위 큐 분리의 필요성
- 운영 알람을 실제로 구성하고 리허설한 경험

**여기부터는 "안 해봤습니다"라고 말한다**
- 실제 SMS/푸시 provider 연동
- 발송 상태 추적 배치와 전달률 모니터링
- 대량 발송 큐의 처리량 튜닝
- 템플릿 관리와 다국어 처리

> ### 자가 점검
> **"발송과 전달의 차이"** 를 설명할 수 있는가.
> **"DLQ에 왜 마스킹이 필요한가"** 를 답할 수 있는가.
> **"재처리에 왜 기존 key를 쓰나"** 를 중복 관점으로 설명할 수 있는가.

# 6. 점검 공지 (Maintenance Communication)

**시나리오 id**: `maintenance-communication`
**모드**: `NORMAL` / `DEGRADED` / `MAINTENANCE` / `RECOVERY`

## 1. 한 줄 정의

장애나 점검 때 **"전부 죽었습니다"와 "다 됩니다" 사이의 중간 상태**를 정의하고, 그걸 사용자에게 일관되게 알린다.

## 2. 원리 — 왜 이 문제가 생기나

### 2-1. ⭐ 장애는 0과 1이 아니다

가장 흔한 오해다.

```
[흔한 인식]   서비스는 "정상" 아니면 "장애" 둘 중 하나

[실제]        결제사가 죽었다
              → 결제는 안 된다
              → 그런데 상품 조회, 주문 내역 확인, 공지 읽기는 멀쩡하다
              → 이걸 전부 막으면?  ⚠️ 불필요하게 서비스를 다 죽이는 것
```

**`DEGRADED` 모드가 이 중간 상태다.**

```
step("SCOPE_DECIDED",    "결제 의존성 장애 범위를 확인했다.")
step("WRITE_GATES_CLOSED","결제·포인트·주문 확정을 제한했다.")     ← 위험한 쓰기 3개만
step("READS_PRESERVED",  "상품 조회와 공지를 계속 제공했다.")       ← 조회 5개 유지
```

> ### 핵심 원칙
> **읽기는 최대한 지키고, 위험한 쓰기만 막는다.**
>
> **왜 쓰기가 위험한가?** 결제사가 죽은 상태에서 주문을 받으면
> "주문은 생겼는데 결제가 안 된" 불완전한 데이터가 쌓인다.
> 나중에 사람이 하나하나 정리해야 한다. **차라리 안 받는 게 낫다.**

**기능 단위로 게이트를 나눈다**는 게 요점이다. "서비스 전체"가 아니라.

| 상태 | 기능 8개 중 | 의미 |
|---|---|---|
| `NORMAL` | 8개 제공 | 정상 |
| `DEGRADED` | 5개 (읽기 유지, 쓰기 3개 차단) | **부분 장애** |
| `MAINTENANCE` | 2개 | 계획 점검, 전체 쓰기 차단 |
| `RECOVERY` | 8개 복구 | 검증 후 재개 |

### 2-2. `MAINTENANCE` — 계획 점검의 세 가지 요소

```
step("MODE_AUTHORIZED", "승인된 운영자가 mode version을 변경했다.")      ← ① 권한
step("WRITES_BLOCKED",  "모든 변경 요청을 일관된 오류 계약으로 차단했다.")  ← ② 일관성
step("NOTICE_PUBLISHED","웹·앱·API용 공지 version을 배포했다.")           ← ③ 다채널
step("CACHE_VERIFIED",  "구형 공지가 남지 않았는지 확인했다.")             ← ④ 캐시
```

#### ① 권한 — 아무나 점검 모드를 켜면 안 된다

점검 모드는 **서비스 전체를 멈추는 스위치**다. 실수로 켜면 그 자체가 장애다. 그래서 승인된 운영자만, 그리고 **누가 켰는지 기록**이 남아야 한다. (1편의 감사 원칙)

#### ② ⭐ 일관된 오류 계약

**이게 놓치기 쉬운 부분이다.**

```
❌ 나쁜 예: 점검 중인데 화면마다 다른 반응
     주문 화면    → 500 에러 페이지
     결제 화면    → 무한 로딩
     API          → 타임아웃
     앱           → "알 수 없는 오류"

   → 사용자는 "서비스가 고장났다"고 생각한다
   → CS 문의가 폭증한다
```

```
✅ 좋은 예: 모든 변경 요청이 같은 형태로 응답
     HTTP 503 Service Unavailable
     Retry-After: 3600
     {
       "code": "MAINTENANCE",
       "message": "시스템 점검 중입니다",
       "until": "2026-08-03T18:00:00+09:00"
     }

   → 클라이언트가 이걸 인식해서 점검 안내 화면을 띄운다
   → 사용자는 "점검 중이구나" 하고 이해한다
```

**`503` 과 `Retry-After` 를 쓰는 이유**: HTTP 표준이라 클라이언트·프록시·검색엔진이 전부 이해한다. **500을 주면 검색엔진이 "이 페이지는 깨졌다"고 판단**해서 색인에서 뺄 수도 있다. 503은 "일시적"이라는 의미가 명확하다.

#### ③ 다채널 공지

```
웹 화면 · 모바일 앱 · 공개 API · 상태 페이지
```

**앱은 배포 주기가 달라서 특히 문제다.** 그래서 공지 내용을 앱에 하드코딩하지 않고 **서버에서 내려주는 구조**여야 한다. `version` 을 두는 이유도 그것이다 — 앱이 "내가 가진 공지가 최신인가"를 판단할 수 있다.

#### ④ ⭐ 캐시 검증 — 가장 자주 놓친다

```
점검이 끝났다. 서버는 정상이다.
그런데 CDN에 "점검 중입니다" 페이지가 캐시돼 있다면?
  → 사용자는 여전히 점검 화면을 본다 💀
  → "서비스가 안 열려요" 문의가 계속 온다
```

**반대 방향도 있다.** 점검을 시작했는데 CDN에 정상 페이지가 캐시돼 있으면 사용자가 계속 정상 화면을 보고 주문을 시도한다.

> **점검 공지는 "띄우는 것"보다 "내리는 것"이 어렵다.**
> 그래서 공지 페이지는 **캐시하지 않도록(`Cache-Control: no-store`)** 설정하고,
> 모드 전환 후 **실제로 반영됐는지 확인**하는 절차가 필요하다.

### 2-3. ⭐ `RECOVERY` — 복구가 가장 위험한 순간이다

```
step("DEPENDENCY_RECOVERED","장애 의존성의 정상 신호를 확인했다.")
step("SMOKE_PASSED",        "조회·결제·상태 조회 경로를 실행했다.")      ← ⭐
step("BACKLOG_CHECKED",     "queue와 retry backlog가 정상임을 확인했다.")  ← ⭐⭐
step("NORMAL_RESTORED",     "쓰기 gate를 열고 종료 공지를 반영했다.")
```

**성급하게 열면 두 번 장애가 난다.**

#### 왜 스모크 테스트가 필요한가

```
"결제사가 살아났다"는 신호를 받았다
  → 바로 게이트를 연다
  → 사실 결제사는 일부만 복구됐다
  → 주문이 몰려 들어오고 다시 실패한다
  → 2차 장애 💀 (그리고 사용자 신뢰는 훨씬 크게 깎인다)
```

**"의존성이 살아났다"와 "우리 서비스가 정상 동작한다"는 다르다.** 그래서 실제 경로를 한 번 실행해 본다. 04의 복원 리허설, 01의 대조와 같은 사고방식이다 — **"돌았다 ≠ 맞다".**

#### ⭐ 왜 백로그를 먼저 확인해야 하는가

**이게 가장 놓치기 쉽고 가장 위험하다.**

```
점검 중에 쌓인 것들:
  - 재시도 대기 중인 알림 5만 건
  - Kafka에 밀린 이벤트 10만 건
  - 클라이언트들이 재시도하려고 대기 중인 요청

게이트를 여는 순간:
  → 이 전부가 동시에 쏟아진다
  → 03에서 본 thundering herd
  → 방금 복구한 서비스가 다시 죽는다 💀
```

**그래서 순서가 있다.**

```
1. 의존성 정상 확인
2. 스모크 테스트 (소수의 요청만)
3. 백로그 규모 확인 → 크면 천천히 소화시킨다
4. 게이트를 단계적으로 연다 (전체가 아니라 일부부터)
5. 지표를 보면서 나머지를 연다
```

> **복구는 스위치가 아니라 절차다.**

## 3. 대안 표와 내 선택

| 접근 | 사용자 경험 | 데이터 안전 | 채택 |
|---|---|---|---|
| 아무것도 안 함 (그냥 에러) | **최악** — 이유를 모른다 | 위험 (불완전 데이터) | ✗ |
| 전체 차단 | 나쁨 — 멀쩡한 기능도 못 씀 | 안전 | △ 계획 점검이면 |
| **기능 단위 게이트** | **좋음** — 되는 건 된다 | 안전 | **✓** |

**기능 단위 게이트를 고른 이유**: 장애는 대개 **일부 의존성**에서 나고, 그 영향 범위는 **일부 기능**에 그친다. 전체를 막는 건 과잉 대응이고, 아무것도 안 막는 건 데이터를 위험하게 한다.

**대가**: 기능마다 게이트를 정의하고 관리해야 한다. 그리고 **"이 기능은 어떤 의존성에 묶여 있는가"를 미리 정리해 둬야** 장애 때 빠르게 판단할 수 있다. 그 정리 자체가 이 시나리오의 산출물이다.

## 4. 진위 한 줄

**⚠️ 고정 대본이다.** `OperationsPracticeEngine.maintenanceMode()` 가 고정 step을 반환한다. 실제 게이트 시스템은 없다.

**다만 관련된 실제 구현은 있다** — 관리자 화면에 `ServiceControlController` 기반의 서비스 제어 기능이 있고, 데모 서비스들을 켜고 끌 수 있다. 완전한 점검 모드 시스템은 아니지만 **"기능을 런타임에 통제한다"는 발상은 실제로 구현돼 있다.**

## 5. 30초 구두 답변

> 장애를 정상이냐 장애냐 둘로 보면 대응이 과해집니다. 결제사가 죽었을 때 상품 조회랑 주문 내역 확인은 멀쩡한데 그것까지 막을 이유가 없거든요.
>
> 그래서 중간 상태를 정의했습니다. 읽기는 최대한 지키고 위험한 쓰기만 막는 겁니다. 결제사가 죽은 상태에서 주문을 받으면 "주문은 생겼는데 결제가 안 된" 불완전한 데이터가 쌓여서 나중에 사람이 하나하나 정리해야 하니까, 차라리 안 받는 게 낫습니다.
>
> 차단할 때 중요한 게 일관된 오류 계약입니다. 화면마다 500, 무한 로딩, 타임아웃으로 제각각이면 사용자는 서비스가 고장났다고 생각하고 CS가 폭증합니다. 모든 변경 요청이 503에 Retry-After와 점검 종료 시각을 담아서 같은 형태로 응답하면, 클라이언트가 그걸 인식해서 점검 안내를 띄울 수 있고요. 500이 아니라 503인 이유는 검색엔진도 일시적이라고 이해하기 때문입니다.
>
> 그리고 복구가 제일 위험합니다. 의존성이 살아났다고 바로 열면 점검 중에 쌓인 재시도 요청이랑 큐 백로그가 한꺼번에 쏟아져서 방금 복구한 서비스가 다시 죽습니다. 그래서 스모크 테스트로 실제 경로를 먼저 확인하고, 백로그 규모를 본 다음, 게이트를 단계적으로 엽니다. 복구는 스위치가 아니라 절차라고 생각합니다.

## 6. 꼬리질문과 답

**Q1. 왜 500이 아니라 503인가요?**

**의미가 다르고, 그걸 기계들이 읽기 때문입니다.**

500은 "서버에서 예기치 못한 오류가 났다"입니다. 503은 "지금은 서비스할 수 없지만 일시적이다"입니다.

**검색엔진이 500을 받으면 "이 페이지는 깨졌다"고 판단해서 색인에서 뺄 수 있습니다.** 503에 `Retry-After` 를 붙이면 "나중에 다시 오겠다"로 처리합니다. 점검 몇 시간 때문에 검색 노출을 잃으면 손해가 큽니다.

클라이언트 라이브러리들도 503과 `Retry-After` 를 이해해서 자동으로 백오프하는 경우가 많습니다.

**Q2. 점검 공지를 어떻게 내리나요?**

**내리는 게 띄우는 것보다 어렵습니다.** 캐시 때문입니다.

CDN이나 브라우저에 "점검 중" 페이지가 캐시돼 있으면 서버가 정상으로 돌아와도 사용자는 계속 점검 화면을 봅니다. 그래서 **공지 페이지와 모드 상태 API는 `Cache-Control: no-store` 로** 캐시를 아예 막습니다.

그리고 모드를 바꾼 뒤 **실제로 반영됐는지 확인**해야 합니다. 여러 지역의 CDN 엣지에서 실제로 조회해 보는 식으로요. "바꿨으니 됐겠지"가 아니라 확인이 필요합니다.

**Q3. 어떤 기능을 막을지 어떻게 정하나요?**

**기능별 의존성 지도를 미리 그려 둬야 합니다.** 장애가 난 뒤에 파악하려면 늦습니다.

"주문 확정은 결제사와 재고 시스템에 의존한다", "상품 조회는 DB와 캐시만 쓴다" 같은 식으로요. 그러면 결제사 장애 때 **막을 것과 열어 둘 것이 즉시 나옵니다.**

기준은 **"이 기능이 실패했을 때 불완전한 데이터가 남는가"** 입니다. 남으면 막고, 안 남으면 열어 둡니다. 조회는 대부분 후자고요.

**Q4. 복구할 때 왜 단계적으로 여나요?**

**점검 중에 쌓인 백로그가 한꺼번에 쏟아지기 때문입니다.**

재시도 대기 중인 알림 5만 건, Kafka에 밀린 이벤트 10만 건, 클라이언트들이 재시도하려고 대기하는 요청까지요. 게이트를 한 번에 열면 이게 전부 동시에 들어와서 03에서 본 thundering herd가 됩니다. **방금 복구한 서비스가 다시 죽습니다.**

그리고 **2차 장애는 1차보다 신뢰를 훨씬 크게 깎습니다.** "복구했다고 했는데 또 안 되네"가 되니까요.

그래서 백로그 규모를 먼저 확인하고, 크면 천천히 소화시킨 다음, 게이트를 일부부터 열면서 지표를 봅니다.

## 7. 모르면 인정할 선

**여기까지는 자신 있게 답한다**
- **장애가 0과 1이 아니라는 것**과 DEGRADED 상태의 필요성
- **"읽기는 지키고 위험한 쓰기만 막는다"** 는 원칙과 그 근거(불완전 데이터)
- **일관된 오류 계약**의 가치와 503 + `Retry-After` 를 쓰는 이유
- 다채널 공지에서 앱의 배포 주기 문제
- **점검 공지를 내리는 게 더 어렵다** (캐시)
- **복구가 가장 위험한 순간**인 이유 (백로그 폭주, 2차 장애)
- 기능별 의존성 지도를 미리 그려야 하는 이유

**여기부터는 "안 해봤습니다"라고 말한다**
- 기능 게이트 시스템 실제 구현 (feature flag 도구 등)
- 상태 페이지(status page) 운영
- 실제 장애 상황에서의 단계적 복구 경험
- CDN 캐시 무효화의 실무 (지역별 전파 확인)

> ### 자가 점검
> **"왜 500이 아니라 503인가"** 를 검색엔진까지 넣어 답할 수 있는가.
> **"복구가 왜 가장 위험한가"** 를 백로그로 설명할 수 있는가.
> **"어떤 기능을 막을지"** 의 판단 기준을 말할 수 있는가.

# 마무리 — 이 그룹을 하나로 묶는 답변

면접에서 **"운영 경험이 있나요"** 또는 **"백오피스를 만들어 봤나요"** 가 나오면 이렇게 묶는다.

> 운영 도구를 볼 때 저는 **사람이 개입하는 순간이 가장 위험하다**고 봅니다. 코드는 리뷰와 테스트를 거치고 롤백도 되는데, 운영자가 손으로 하는 작업은 그게 전부 없이 바로 운영 DB에 닿거든요. 운영 사고의 상당수가 버그가 아니라 **권한 있는 사람이 옳다고 믿고 실행한 작업**에서 납니다.
>
> 그래서 세 가지 원칙으로 정리했습니다.
>
> **최소 노출** — 필요한 것만 보고 필요한 만큼만 바꿉니다. CS 상담원에게 주민번호 전체가 필요하지 않으니 역할별로 마스킹하고, 조회 자체를 기록합니다. 개인정보 사고의 상당수가 외부 해킹이 아니라 내부자 조회라서요. 데이터 정정도 마찬가지로, UPDATE를 쓰기 전에 같은 WHERE 절로 SELECT를 먼저 돌려서 몇 건이 나오는지 확인합니다. 이거 하나로 대부분의 사고가 막힙니다.
>
> **되돌릴 수 있음** — 하기 전에 어떻게 되돌릴지가 준비돼 있어야 합니다. 수정 전 값을 스냅샷으로 남기고, 엑셀 업로드는 전체 검증이 끝나기 전에 운영 테이블을 아예 안 건드리고, 알림은 실패한 걸 DLQ에 모아서 나중에 같은 request key로 재처리합니다. 롤백도 그냥 하면 안 되는데, 그 사이에 후속 변경이 있었으면 그걸 지우게 되니까 먼저 확인합니다.
>
> **같은 정의** — 같은 질문에 어디서 물어도 같은 답이 나와야 합니다. "이번 달 가입자 수"는 기간 기준이 UTC냐 KST냐, 탈퇴자를 포함하냐에 따라 답이 달라지는 정의되지 않은 질문이라, 지표를 계약으로 만들고 버전을 붙입니다. 화면과 export가 다르면 그 뒤로 모든 숫자를 못 믿게 되니까 필터를 코드로 공유하고 파일에 기준 시각을 박고요.
>
> 실제로 구현한 건 개인정보 쪽입니다. 블로그 댓글에서 원본 IP를 저장하지 않고 표시용 앞 2옥텟과 차단용 salted 해시만 남겼고, salt가 없으면 운영에서 아예 기동이 실패하게 만들었습니다. 나머지 화면들은 설계 정리고요.

## 왜 이 답변이 강한가

1. **"사람이 개입하는 순간이 가장 위험하다"** 는 첫 문장이 운영을 이해한 사람의 관점이다
2. 세 원칙이 6편 전부를 덮으면서 **각 원칙에 구체적 사례**가 붙는다
3. **"UPDATE 전에 SELECT"** 같은 실천 가능한 습관을 말한다 — 추상론이 아니다
4. 개인정보 부분은 **실제 구현**이라 무게가 다르다
5. **마지막에 뭐가 구현이고 뭐가 설계인지 스스로 구분**한다
