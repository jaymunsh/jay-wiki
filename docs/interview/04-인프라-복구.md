# 04. 인프라 · 복구

사이트 그룹: **인프라·복구** — "부하 변화와 장애 이후에도 서비스 용량과 데이터를 운영 가능한 상태로 되돌린다."

**3편 전부 실제로 돌아간다.** 그리고 이 그룹은 다른 그룹과 성격이 다르다. 애플리케이션 코드가 아니라 **운영 체계**에 관한 것이다.

| 편 | 진위 |
|---|---|
| **부하에 반응하는 Pod 자동 확장** | ✅ **실제 실행** — 진짜 부하를 걸고 진짜 Kubernetes HPA가 replica를 바꾼다 |
| **PostgreSQL 백업과 외부 복제** | ✅ **실제 실행** — 진짜 `pg_dump` 를 뜨고 진짜 임시 DB에 복원해 검증한다 |
| **오류 한 건이 휴대폰까지 가는 길** | ✅ **실제 실행** — 진짜 오류를 주입하고 진짜 텔레그램 한 통이 온다. **화면 밖에서 끝나는 유일한 편** |

## 시작하기 전에 — 이 그룹을 관통하는 것

앞의 세 그룹은 **"어떻게 만들 것인가"** 였다. 이 그룹은 **"어떻게 증명할 것인가"** 다.

```
        선언                          증명
─────────────────────────  ────────────────────────────
"부하가 늘면 Pod가 늘어납니다"  →  실제로 부하를 걸어서 1→2가 되는 걸 봤나?
"매일 백업하고 있습니다"        →  그 백업으로 실제로 복원해 봤나?
"장애 나면 알림이 옵니다"       →  그 알림이 실제로 휴대폰까지 온 걸 봤나?
"장애 나면 복구됩니다"          →  복구에 몇 분 걸리는지 재 봤나?
```

**운영에서 가장 위험한 건 "될 거라고 믿는 것"이다.** 그리고 그 믿음은 대개 **필요한 순간에 처음 시험된다.** 그때가 최악의 타이밍이다.

> ### 이 그룹의 한 문장
> **`scripts/rehearse-postgres-restore.sh` 파일 맨 위에 적혀 있는 그대로다.**
> > *"백업은 복원해보기 전까지 백업이 아니다"*
>
> HPA도 똑같다. **부하를 걸어 보기 전까지 오토스케일링은 YAML 파일일 뿐이다.**

두 편이 각각 "리허설(rehearsal)"이라는 이름을 달고 있는 이유가 이것이다. 실제 스크립트 이름도 `rehearse-hpa-scaleout.sh`, `rehearse-postgres-restore.sh` 다.

# 1. 부하에 반응하는 Pod 자동 확장

**시나리오 id**: `hpa-scaleout`
**화면**: `/scenarios` → HPA 리허설 패널
**코드**: `HpaRehearsalController`, `HpaRehearsalService`, `scripts/rehearse-hpa-scaleout.sh`, `infra/k8s/backend/jaywiki-hpa.yaml`

## 1. 한 줄 정의

**고정 부하를 걸어서 CPU를 기준선 위로 올리고**, Kubernetes HPA가 replica를 1→2→1로 조정하는 전 과정을 관측한다.

## 2. 원리 — 왜 이 문제가 생기나

### 2-1. 수동 확장의 문제

트래픽이 늘면 서버를 늘려야 한다. 사람이 하면 이렇게 된다.

```
14:00  트래픽 증가 시작
14:05  응답이 느려짐
14:12  알람 발생
14:15  담당자가 확인
14:20  replica를 2로 늘림
14:22  새 Pod가 준비됨
─────────────────────────
장애 시간: 약 17분
```

그리고 트래픽이 줄어도 **아무도 다시 줄이지 않는다.** 무서우니까. 결국 항상 최대치로 띄워 두고 비용을 낭비한다.

**HPA(Horizontal Pod Autoscaler)** 는 이 판단을 자동화한다.

```
지표를 주기적으로 관측 → 목표치와 비교 → replica 수를 계산 → 조정
```

### 2-2. ⭐ HPA가 replica 수를 계산하는 방법

공식은 아주 단순하다.

```
원하는 replica = ceil( 현재 replica × (현재 지표 / 목표 지표) )
```

**이 프로젝트의 설정** (`jaywiki-hpa.yaml`):

```yaml
minReplicas: 1
maxReplicas: 2
metrics:
  - resource:
      name: cpu
      target:
        averageUtilization: 80     # ← 목표: CPU 80%
```

**대입해 보자.**

```
현재 replica 1개, CPU 사용률 160%

원하는 replica = ceil( 1 × (160 / 80) ) = ceil(2) = 2
→ Pod를 2개로 늘린다

늘린 뒤: 같은 부하를 2개가 나눠 가지므로 각각 약 80%
→ 목표에 도달 → 더 안 늘린다 ✅
```

### 2-3. ⭐⭐ "CPU 80%"의 80%는 무엇에 대한 비율인가

**이게 가장 많이 틀리는 부분이다.** CPU 코어 대비가 아니다.

```
Pod에 설정한 resources.requests.cpu 에 대한 비율이다.
```

```yaml
resources:
  requests:
    cpu: 200m        # 0.2 코어를 요청
```

```
실제 사용량 160m  →  160 / 200 = 80%
실제 사용량 320m  →  320 / 200 = 160%   ← 요청량의 1.6배를 쓰고 있다
```

> ### 여기서 나오는 함정
> **`resources.requests.cpu` 를 설정하지 않으면 HPA는 CPU 기준으로 동작하지 않는다.**
> 분모가 없으니 비율을 계산할 수 없다. HPA가 `<unknown>` 을 표시하고 아무것도 안 한다.
>
> **"HPA를 만들었는데 안 늘어나요"의 1순위 원인이 이것이다.**

그리고 **metrics-server**가 클러스터에 떠 있어야 한다. HPA는 지표를 직접 재지 않고 metrics-server가 수집한 걸 읽는다.

### 2-4. ⭐ 확장은 빠르게, 축소는 천천히 — 비대칭이 핵심이다

이 프로젝트 설정을 보자.

```yaml
behavior:
  scaleUp:
    stabilizationWindowSeconds: 0      # ← 0초. 즉시 판단
    policies:
      - type: Pods
        value: 1
        periodSeconds: 30              # 30초에 1개씩

  scaleDown:
    stabilizationWindowSeconds: 300    # ← 300초(5분). 한참 지켜본다
    policies:
      - type: Pods
        value: 1
        periodSeconds: 60              # 60초에 1개씩
```

**확장 0초 vs 축소 300초. 왜 이렇게 비대칭인가?**

**실패의 대가가 다르기 때문이다.**

```
[확장을 늦게 하면]     사용자가 느린 응답이나 에러를 본다.  →  손해가 크다
[확장을 성급하게 하면]  Pod 하나 더 뜬다. 잠깐 비용이 더 든다. →  손해가 작다

[축소를 늦게 하면]     비용이 조금 더 나간다.               →  손해가 작다
[축소를 성급하게 하면]  트래픽이 다시 오면 또 늘려야 하고,
                      그 사이에 사용자가 느린 응답을 본다.   →  손해가 크다
```

> **불확실할 때는 손해가 작은 쪽으로 기운다.** 이게 비대칭의 이유다.

**stabilization window가 하는 일**은 이렇다.

```
[축소 판단 시 - 5분 창]
  최근 5분간의 "원하는 replica 수" 를 전부 기억한다
  → 그중 가장 큰 값을 택한다
  → 5분 내내 계속 1이어야만 1로 줄인다

  즉: 잠깐이라도 부하가 튀었으면 축소하지 않는다
```

**이걸 안 하면 flapping(진동)이 생긴다.**

```
CPU 85% → 2개로 확장 → 각 42% → "너무 낮네" → 1개로 축소 → 85% → 확장 → ...
무한 반복. Pod가 계속 뜨고 죽는다. 매번 JVM 워밍업 비용이 든다. 💀
```

### 2-5. 리허설이 실제로 하는 일

`scripts/rehearse-hpa-scaleout.sh` 를 보면 진짜다.

```bash
kubectl -n backend run "${name}" \
  --image=curlimages/curl:8.11.1 \
  --command -- /bin/sh -c "
    worker() {
      while [ 시간 남았으면 ]; do
        curl 'http://jaywiki:8080/api/board/search?q=샘플'    # 검색 API를 계속 호출
      done
    }
    # 고른 수만큼 워커를 동시에 띄운다 (기본 8)
  "
```

- **부하 생성 Pod**를 클러스터 안에 띄운다 (`curlimages/curl`)
- **워커(기본 8, 화면에서 2~16 중 선택)**가 `LOAD_SECONDS`(기본 180초) 동안 검색 API를 쉬지 않고 호출한다
- 워커는 요청마다 HTTP 코드와 소요 시간을 남기고, 합계를 10초마다 파드 로그로 찍는다
- 검색을 고른 이유: **10만 건 게시판 검색이라 CPU를 실제로 쓴다.** 단순 조회로는 CPU가 안 오른다
- 끝나면 `trap cleanup EXIT` 로 부하 Pod를 지운다

**애플리케이션 쪽에서도 관측한다** (`HpaRehearsalService`). 화면에 이런 게 실시간으로 나온다.

| 항목 | 무엇 |
|---|---|
| `cpuUtilization` | 현재 CPU 사용률 |
| `targetCpuUtilization` | 목표치 (80) |
| `desiredReplicas` / `readyReplicas` | HPA가 원하는 수 / 실제 준비된 수 |
| `pods[]` | Pod별 이름·상태·재시작 횟수·CPU·메모리 |
| `events[]` | 상태 전이 타임라인 |

**`desiredReplicas` 와 `readyReplicas` 를 나눠 보여주는 게 포인트다.** "HPA가 2개를 원한다"와 "실제로 2개가 준비됐다" 사이에는 **Pod 스케줄링 + 컨테이너 시작 + readiness probe 통과**라는 시간이 있다. 그 지연이 곧 **확장이 늦는 실제 이유**다.

### 2-6. 동시 실행 방지 — Redis 락

```java
if (!Boolean.TRUE.equals(redis.opsForValue().setIfAbsent(LOCK, runId, LOCK_TTL))) {
    throw new IllegalStateException("HPA rehearsal is already running");
}
```

`setIfAbsent` 는 Redis의 `SET key value NX` 다. **키가 없을 때만 설정하고, 그 판단과 설정이 원자적**이다. 01에서 본 조건부 UPDATE, 02에서 본 Lua와 같은 원리다.

**TTL을 15분으로 건 이유**: 리허설 중에 서버가 죽으면 락이 영원히 남는다. TTL이 있으면 저절로 풀린다. **락에는 반드시 만료가 있어야 한다.**

### 2-7. ⭐ HPA가 해결하지 못하는 것 — 이게 면접의 핵심

**Pod를 늘려도 안 되는 경우가 훨씬 많다.** 이걸 아는 게 중요하다.

```
[HPA가 도움이 되는 경우]
  병목이 애플리케이션 CPU에 있다
  → Pod를 늘리면 CPU가 나눠진다 ✅

[HPA가 소용없거나 오히려 나쁜 경우]

① 병목이 DB다
   Pod를 2배로 늘리면?  → DB 커넥션 요구도 2배
                        → DB가 더 빨리 죽는다 💀
   ※ 03의 커넥션 풀 편과 직결된다

② 병목이 외부 API다
   Pod를 늘려도 상대가 안 빨라진다. 오히려 상대를 더 때린다

③ 상태를 공유하는 애플리케이션이다
   → 아래 2-8 참고 ⚠️

④ 시작이 느리다 (JVM 워밍업)
   Pod가 떠도 몇십 초는 느리다. 급증 대응이 안 된다
```

> **HPA는 "CPU가 병목일 때"만 답이다.**
> 병목이 어디인지 모르고 HPA부터 켜면, 아래층(DB, 외부 API)으로 부하만 전가한다.

### 2-8. ⭐⭐ HPA를 켜 보고서야 알게 된 것 — 이 편에서 가장 좋은 이야기

**HPA는 인프라 설정이지만, 그게 동작하려면 애플리케이션이 무상태여야 한다.** 이 프로젝트는 그 전제를 두 군데서 위반하고 있었다.

```
① ChatRoomService 의 join()/leave()/promote() 가 Java synchronized
     → JVM 하나 안에서만 유효한 잠금
     → 상태는 Redis에 공유되는데 잠금은 공유되지 않았다
     → replica가 2가 되면 두 인스턴스가 각자 인원수를 읽고
       둘 다 "자리 있음"으로 판단해 정원 3인 방에 4명이 들어간다

② KafkaDemoOutboxRelay 가 outbox 행을 잠그지 않고 읽기만 함
     → replica가 2가 되면 같은 행을 둘 다 가져가 중복 발행
```

**즉 이 화면(Pod 확장)이 저 화면들을 깨뜨리고 있었다.** `maxReplicas: 2` 라 이론이 아니라 언제든 실제로 벌어질 일이었다.

**2026-08-03에 둘 다 고쳤다.** 채팅은 정원 확인과 입장을 Redis Lua 스크립트로 원자화했고, Outbox는 `update ... where id in (select ... for update skip locked) returning ...` 으로 선점하는 방식으로 바꿨다.

**면접에서 이 이야기가 이 편의 핵심이다.**

> "HPA를 붙이고 나서 저희 애플리케이션이 수평 확장을 견디지 못한다는 걸 알게 됐습니다. maxReplicas가 2인데 실제로 2가 되면 깨지는 곳이 두 군데 있었어요. 채팅방 정원 제어가 `synchronized` 였는데 그건 JVM 안에서만 유효하고, Outbox 릴레이는 행을 잠그지 않아서 중복 발행됐습니다.
>
> 공통점이 **상태는 프로세스 밖으로 잘 뺐는데 잠금은 안 뺐다**는 겁니다. Redis에 데이터를 두면 공유되니까 됐다고 생각하기 쉬운데, 그 데이터를 읽고 판단하고 쓰는 구간의 원자성은 별개더라고요. 각각 Redis Lua와 `for update skip locked` 로 고쳤습니다.
>
> **수평 확장은 인프라 설정이 아니라 애플리케이션 설계 문제**라는 걸 직접 겪었습니다."

**이게 "HPA 써봤습니다"보다 몇 배 강한 답변**이다. 오토스케일링을 설정만 해본 사람과, 그 전제 조건을 알고 자기 코드에서 위반을 찾아 고친 사람의 차이니까.

## 3. 대안 표와 내 선택

| 접근 | 반응 속도 | 비용 | 언제 |
|---|---|---|---|
| 고정 replica (최대치) | 즉시 | **항상 최대** | 트래픽이 일정할 때 |
| 수동 확장 | **10~20분** | 낮음 | ✗ 사실상 못 쓴다 |
| **HPA (CPU 기준)** | 30초~2분 | 사용량 비례 | **✓ CPU가 병목일 때** |
| HPA (커스텀 지표) | 30초~2분 | 사용량 비례 | 큐 lag 등이 병목일 때 |
| VPA (수직 확장) | 재시작 필요 | — | Pod 크기 자체가 안 맞을 때 |

**CPU 기준 HPA를 고른 이유**: 이 서비스의 실제 병목이 검색·렌더링 같은 **CPU 작업**이고, metrics-server만 있으면 추가 구성이 필요 없다.

**커스텀 지표(예: Kafka consumer lag 기반 확장, KEDA)는 안 했다.** 02의 Kafka 편에서 "lag이 쌓이면 consumer를 늘려야 한다"고 했는데, **그 자동화는 없다.** 정직하게 인정할 부분이다.

## 4. 진위 한 줄

**✅ 실제로 돌아간다.**

- **진짜 부하 Pod**가 클러스터에 뜬다 (`curlimages/curl`, 워커 2~16, 180초)
- **진짜 Kubernetes HPA**가 replica를 조정한다 (`kubectl get hpa` 로 확인 가능)
- 화면의 CPU 사용률·Pod 목록·이벤트 타임라인이 **실시간 실측**이다
- Redis 락으로 동시 실행을 막는 것도 실제 코드다

**⚠️ 다만 규모의 한계는 밝혀야 한다.**

```yaml
minReplicas: 1
maxReplicas: 2      # ← 1에서 2로 가는 것뿐이다
```

**miniPC 단일 노드 환경이라 확장 여력이 작다.** "수십 대로 늘어나는" 걸 보여주는 게 아니라 **"오토스케일링이 실제로 동작하는 것을 관측 가능하게 만든" 것**이 이 편의 가치다. 이걸 과장하면 안 된다.

## 5. 30초 구두 답변

> 트래픽이 늘 때 사람이 replica를 늘리면 알람 확인부터 Pod 준비까지 15분 넘게 걸리고, 줄어들어도 무서워서 아무도 다시 안 줄입니다. 그래서 HPA로 자동화했습니다.
>
> HPA는 현재 replica 곱하기 (현재 지표 나누기 목표 지표)로 필요한 개수를 계산합니다. 여기서 중요한 게 "CPU 80%"의 기준이 코어가 아니라 `resources.requests.cpu` 라는 겁니다. requests를 안 잡으면 분모가 없어서 HPA가 아예 동작하지 않는데, "HPA 만들었는데 안 늘어나요"의 1순위 원인이 이겁니다.
>
> 그리고 확장과 축소를 비대칭으로 잡았습니다. 확장은 stabilization window 0초로 즉시 하고, 축소는 300초 동안 지켜봅니다. 실패의 대가가 다르거든요. 확장이 늦으면 사용자가 에러를 보고, 축소가 늦으면 비용이 조금 더 나갈 뿐입니다. 불확실하면 손해가 작은 쪽으로 기웁니다. 그리고 축소를 성급하게 하면 늘렸다 줄였다 반복하는 flapping이 생기고요.
>
> 다만 HPA는 CPU가 병목일 때만 답입니다. 병목이 DB면 Pod를 늘릴수록 커넥션 요구가 늘어서 DB가 더 빨리 죽습니다. 그리고 저희 프로젝트에서는 replica가 2가 되면 채팅방 정원 제어가 깨집니다. `synchronized` 로 잠그는데 그건 JVM 안에서만 유효해서요. **수평 확장은 인프라 설정이 아니라 애플리케이션이 무상태여야 가능하다**는 걸 직접 확인한 셈입니다.

## 6. 꼬리질문과 답

**Q1. HPA를 만들었는데 안 늘어납니다. 뭘 봐야 하나요?**

**순서대로 넷을 봅니다.**

첫째, **`resources.requests.cpu` 가 설정돼 있나.** 없으면 비율의 분모가 없어서 HPA가 `<unknown>` 을 표시하고 아무것도 안 합니다. 가장 흔한 원인입니다.

둘째, **metrics-server가 떠 있나.** HPA는 지표를 직접 재지 않고 metrics-server가 수집한 걸 읽습니다. `kubectl top pod` 가 되면 정상입니다.

셋째, **`kubectl describe hpa` 의 이벤트.** 왜 조정 안 하는지 이유가 적혀 있습니다.

넷째, **CPU가 실제로 안 오르는 건 아닌가.** I/O 대기가 병목이면 CPU는 낮게 유지됩니다. 그러면 HPA는 옳게 동작하고 있는 거고, 지표를 바꿔야 합니다.

**Q2. 왜 확장과 축소의 정책이 다른가요?**

**실패의 대가가 비대칭이기 때문입니다.**

확장이 늦으면 사용자가 느린 응답이나 에러를 봅니다. 확장이 성급하면 Pod 하나 더 뜨고 비용이 잠깐 더 듭니다. **손해 차이가 큽니다.**

축소는 반대입니다. 늦게 줄이면 비용이 조금 더 나가고, 성급하게 줄이면 트래픽이 다시 왔을 때 또 늘려야 하는데 그 사이에 사용자가 느린 응답을 봅니다.

그래서 **양쪽 다 "사용자가 손해 보는 쪽"을 피하는 방향**으로 기울입니다. 그리고 축소에 5분 창을 두면 flapping도 같이 막힙니다.

**Q3. Pod를 늘리면 항상 빨라지나요?**

**아니요. 오히려 나빠지는 경우가 많습니다.**

병목이 DB면 Pod를 2배로 늘릴 때 DB 커넥션 요구도 2배가 됩니다. PostgreSQL은 커넥션마다 프로세스를 띄우니까 **DB가 더 빨리 무너집니다.** 03의 커넥션 풀 편과 같은 이야기고요.

병목이 외부 API여도 마찬가지입니다. 상대가 빨라지지 않고, 오히려 상대를 더 때려서 429나 5xx가 늘어납니다.

**그래서 HPA를 켜기 전에 병목이 어디인지부터 확인해야 합니다.** 모르고 켜면 아래층으로 부하를 전가할 뿐입니다.

**Q4. 상태를 가진 애플리케이션은 어떻게 하나요?**

**상태를 프로세스 밖으로 빼야 합니다.** 세션은 Redis나 JWT로, 파일은 오브젝트 스토리지로, 캐시는 공유 캐시로요.

**그리고 잠금도 프로세스 밖으로 빼야 합니다.** 이게 놓치기 쉬운 부분인데, 저희 프로젝트가 정확히 여기서 걸렸습니다. 채팅방 상태는 Redis에 잘 공유해 놨는데 **동시성 제어는 `synchronized` 로 JVM 안에서** 하고 있었어요. 데이터를 공유 저장소에 두면 됐다고 생각했는데, **그 데이터를 읽고 판단하고 쓰는 구간의 원자성은 별개**더라고요.

인원 확인과 추가를 Redis Lua 스크립트 하나로 묶어서 고쳤습니다. Outbox 릴레이도 같은 종류의 문제라 `update ... for update skip locked ... returning` 으로 선점하는 방식으로 바꿨고요.

## 7. 모르면 인정할 선

**여기까지는 자신 있게 답한다**
- HPA의 replica 계산 공식
- **"CPU 80%"의 기준이 `resources.requests.cpu`** 라는 것과 그게 없으면 안 도는 이유
- 확장/축소 비대칭의 근거 (**실패의 대가가 다르다**)
- stabilization window와 flapping
- `desiredReplicas` 와 `readyReplicas` 의 차이가 곧 확장 지연이라는 것
- **HPA가 해결 못 하는 병목들** (DB, 외부 API, 상태 공유, JVM 워밍업)
- **수평 확장의 전제는 무상태**라는 것과 **내 코드가 그걸 위반한다는 자기 진단**

**여기부터는 "안 해봤습니다"라고 말한다**
- 커스텀 지표 기반 확장 (KEDA, Kafka lag 기반) — **02에서 필요하다고 말했지만 안 했다**
- 노드 오토스케일링 (Cluster Autoscaler) — **단일 노드라 해당 없음**
- maxReplicas를 크게 잡았을 때의 동작 (**여기는 2가 최대다**)
- PodDisruptionBudget, 무중단 배포와 HPA의 상호작용

> ### 자가 점검
> **"CPU 80%의 80%는 무엇에 대한 비율인가"** 를 즉답할 수 있는가.
> **"왜 확장은 0초, 축소는 300초인가"** 를 손해의 크기로 설명할 수 있는가.
> **"내 프로젝트에서 replica가 2가 되면 뭐가 깨지나"** 를 먼저 말할 수 있는가.

# 2. PostgreSQL 백업과 외부 복제

**시나리오 id**: `backup-restore`
**코드**: `infra/k8s/backup/postgres-backup.yaml`, `scripts/rehearse-postgres-restore.sh`

## 1. 한 줄 정의

**miniPC 저장장치가 고장 나서 운영 DB를 읽을 수 없을 때**, 무엇으로 얼마나 되돌릴 수 있는가.

## 2. 원리 — 왜 이 문제가 생기나

### 2-1. ⭐ 백업의 두 가지 숫자 — RPO와 RTO

백업 이야기는 이 두 단어로 시작해야 한다. 나머지는 전부 이 둘을 만족시키기 위한 수단이다.

```
[RPO — Recovery Point Objective]  "얼마나 잃어도 되는가"
   마지막 백업 시점 ~ 장애 시점 사이의 데이터는 사라진다
   → 이 프로젝트: 하루 1회 백업이므로 최대 24시간 ⚠️

[RTO — Recovery Time Objective]  "얼마나 빨리 돌아와야 하는가"
   장애 발생 ~ 서비스 정상화까지 걸리는 시간
   → 이 프로젝트: 복원 리허설로 실측한다
```

```
시간축으로 보면

  03:17 ─────────────── 14:30 ──────────→
  백업 뜸              장애 발생
    │◄──── 이 사이 데이터 = 유실 ────►│
              (RPO = 최대 24시간)

                        14:30 ──── 15:10
                        장애      복구 완료
                          │◄─ RTO ─►│
```

> **RPO를 줄이려면** 백업 주기를 짧게 하거나 WAL 아카이빙으로 시점 복구(PITR)를 한다.
> **RTO를 줄이려면** 복원 절차를 자동화하고 미리 연습한다.
>
> **둘 다 공짜가 아니다.** 그래서 "얼마까지 감당할 수 있는가"를 먼저 정해야 한다.
> 포트폴리오 사이트에 RPO 0을 목표로 하는 건 과투자다.

### 2-2. 이 프로젝트의 백업 정책

`infra/k8s/backup/postgres-backup.yaml` 의 실제 설정이다.

```yaml
schedule: "17 3 * * *"                              # 매일 03:17 (UTC)

pg_dump --format=custom --file="${target}"          # 커스텀 포맷으로 덤프
sha256sum "${target}" > "${target}.sha256"          # 체크섬 생성

find /backups -name 'portfolio-*.dump.sha256' -mtime +7 -delete   # 7일 보관
```

**설계 판단이 넷 들어 있다.**

#### ① 왜 `--format=custom` 인가

```
plain (기본)   →  SQL 텍스트 파일. 사람이 읽을 수 있지만 크고 느리다
custom         →  압축된 바이너리. 그리고 결정적인 장점이 있다:
                  ✅ 테이블 단위 선택 복원 가능 (pg_restore -t)
                  ✅ 병렬 복원 가능 (pg_restore -j)
                  ✅ 자동 압축으로 용량 절약
```

**"테이블 하나만 복원"이 가능한 게 실무에서 크다.** 운영 실수로 테이블 하나를 날렸을 때 전체를 되돌릴 필요가 없다.

#### ② 왜 sha256 체크섬을 만드나

**백업 파일이 손상됐는데 그걸 모르는 게 최악**이다. 디스크 오류나 전송 중 손상은 조용히 일어난다.

```
백업할 때:  sha256 계산해서 옆에 저장
복원할 때:  다시 계산해서 비교
           → 다르면 이 백업은 못 쓴다. 그 이전 것을 찾는다
```

**"복원해 보니 파일이 깨져 있었다"를 장애 상황에서 처음 알면 안 된다.**

#### ③ 왜 7일 보관인가

```
너무 짧으면:  "3일 전 데이터로 돌려주세요" 를 못 한다
              → 데이터 손상을 늦게 발견하는 경우가 많다
              → 어제 백업은 이미 손상된 데이터를 담고 있을 수 있다

너무 길면:    저장 비용이 계속 늘어난다 (PVC 5Gi 한계)
```

**7일은 "주말에 문제가 나도 월요일에 대응할 수 있는" 최소선**이다. 실무에서는 보통 계층화한다 — 일간 7일 + 주간 4주 + 월간 12개월.

#### ④ 테이블 필터가 없다

**전체 DB를 덤프한다.** 그래서 **새 테이블이 자동으로 포함**된다.

이게 실제로 효과를 본 사례가 있다. 블로그 기능을 추가하면서 `tb_blog_post` 등 새 테이블이 여럿 생겼는데, **백업 설정을 아무것도 안 고쳐도 자동으로 백업 대상이 됐다.**

> **필터를 두면 "새 테이블을 백업 목록에 추가하는 것"을 잊는 사고가 반드시 난다.**
> 그리고 그 사실은 **복원할 때 처음 발견된다.**

### 2-3. ⭐⭐ 복원 리허설 — 이 편의 핵심

`scripts/rehearse-postgres-restore.sh` 맨 위에 이렇게 적혀 있다.

> *"백업은 복원해보기 전까지 백업이 아니다"*

**백업 파일이 있다는 사실은 아무것도 보장하지 않는다.** 실무에서 나는 사고가 이렇다.

```
❌ 파일은 있는데 손상돼 있다
❌ 덤프는 됐는데 스키마가 안 맞아서 복원이 실패한다
❌ 복원 명령을 아무도 몰라서 장애 상황에서 처음 찾아본다
❌ 복원은 되는데 3시간이 걸린다 (RTO를 아무도 몰랐다)
❌ 복원했는데 데이터가 비어 있다
```

**전부 "복원해 보면" 미리 알 수 있는 것들이다.**

**스크립트가 하는 일:**

```
1. 백업 비밀번호를 Secret에서 가져온다
2. 임시 Pod를 띄운다 (postgres 클라이언트 + 백업 PVC 마운트)
3. 최신 dump 파일을 고른다
4. ✅ sha256 을 검증한다              ← 무결성 확인
5. ✅ 임시 DB에 pg_restore 한다        ← 실제 복원
6. ✅ 핵심 테이블 row count를 원본과 비교  ← 내용 검증
      TABLES = tb_article tb_revision tb_post
7. ✅ 임시 DB와 Pod를 삭제한다         ← trap cleanup EXIT
```

**두 가지 안전장치가 특히 중요하다.**

#### 안전장치 ① 원본 DB는 절대 건드리지 않는다

```bash
# 원본 DB 는 읽기만 한다. 복원은 항상 별도의 임시 DB 로만 한다.
RESTORE_DB="restore_drill_$(date -u +%Y%m%d%H%M%S)"
```

**리허설이 사고를 내면 안 된다.** 복원 대상은 항상 타임스탬프가 붙은 새 DB고, 원본은 row count를 읽기 위해서만 접근한다.

> **"복구 연습을 하다가 장애를 냈다"는 실화가 많다.**
> 그래서 리허설 자체가 안전해야 연습을 자주 할 수 있다.

#### 안전장치 ② `trap cleanup EXIT`

```bash
trap cleanup EXIT     # 스크립트가 어떻게 끝나든 정리 함수를 실행
```

**중간에 실패해도, Ctrl+C를 눌러도** 임시 DB와 Pod가 정리된다. 이게 없으면 리허설을 돌릴 때마다 찌꺼기가 쌓이고, 결국 PVC가 차서 진짜 백업이 실패한다.

#### row count 비교 대상을 왜 그 셋으로 골랐나

```
TABLES = tb_article  tb_revision  tb_post
         (위키 본문)  (위키 이력)  (게시판)
```

**"이 셋이 살아 있으면 복원이 유효하다"** 는 판단이다. 모든 테이블을 비교하면 느리고, 하나도 안 비교하면 "복원 명령이 에러 없이 끝났다"만 확인하는 셈이다.

> **"명령이 성공했다"와 "데이터가 맞다"는 다르다.**
> 01의 정산 편에서 본 *"돌았다"와 "맞다"의 차이*가 여기서도 나온다.

### 2-4. 3-2-1 규칙과 이 프로젝트의 위치

백업의 고전적 원칙이다.

```
3  복사본 3개 (원본 + 백업 2개)
2  서로 다른 매체 2종
1  ⭐ 최소 1개는 물리적으로 다른 장소에 (off-site)
```

**이 프로젝트의 현재 상태:**

```
원본:  miniPC의 PostgreSQL
백업:  miniPC의 PVC (5Gi)
       └── ⚠️ 같은 물리 장비다
```

**miniPC가 통째로 고장 나면 원본과 백업이 함께 사라진다.** 이건 백업이 있는 게 아니다.

시나리오 화면이 *"다음 단계로 R2 외부 복제 플랜"* 이라고 적은 이유가 이것이다. **Cloudflare R2 같은 외부 오브젝트 스토리지로 복제하는 것이 남은 숙제**고, 아직 안 했다.

**면접에서 이건 정직하게 말해야 한다.**

> "지금 백업은 원본과 같은 장비에 있어서 3-2-1 규칙의 '1'을 만족하지 못합니다. 장비 자체가 고장 나면 둘 다 잃습니다. R2로 외부 복제하는 게 다음 단계인데 아직 안 했고, 그래서 현재는 **디스크 논리 장애나 운영 실수에는 대응되지만 장비 전체 손실에는 대응이 안 되는** 상태입니다."

**"백업 있습니다"보다 이게 훨씬 신뢰를 준다.** 백업의 한계를 정확히 아는 사람이니까.

### 2-5. 백업이 못 막는 것 — 논리적 손상

```
[물리 장애]  디스크 고장, 서버 다운       →  백업으로 복구 ✅

[논리 손상]  WHERE 절 없는 UPDATE로 3만 건을 날림
             →  백업으로 복구 가능은 하지만...
             →  ⚠️ 마지막 백업 이후 정상 거래도 함께 사라진다
             →  ⚠️ 언제 망가졌는지 모르면 어느 백업으로 갈지 모른다
```

**그래서 백업만으로는 부족하다.** 05에서 다룰 "운영 데이터 조회·정정" 시나리오가 이 지점을 다룬다 — **애초에 잘못된 UPDATE가 나가지 않게 하는 절차**가 백업보다 앞선 방어선이다.

> **백업은 마지막 방어선이지 첫 번째 방어선이 아니다.**

## 3. 대안 표와 내 선택

| 접근 | RPO | RTO | 비용 | 이 프로젝트 |
|---|---|---|---|---|
| 백업 없음 | ∞ | ∞ | 0 | ✗ |
| **일간 `pg_dump`** | **최대 24h** | 수십 분 | 낮음 | **✓ 현재** |
| WAL 아카이빙 + PITR | **수 분** | 중간 | 중간 | 미도입 |
| 스트리밍 복제 (standby) | **거의 0** | **수 초** | 높음 (장비 2배) | 과함 |

**일간 `pg_dump` 를 고른 이유**: 포트폴리오 사이트의 데이터 특성상 **24시간 유실이 감당 가능**하다. 위키 글은 시드 파일과 `posts/jay-wiki/` 에도 있고, 게시판 글은 데모 데이터다. 스트리밍 복제는 장비를 하나 더 사야 해서 명백히 과투자다.

**다만 블로그가 생기면서 이 판단이 조금 달라졌다.** 블로그는 **PostgreSQL이 유일한 원본**이다(시드도 revision도 없다). 그래서 블로그 글이 늘어나면 RPO 24시간이 부담이 될 수 있다. 지금은 8편이라 괜찮지만, 이 변화를 인지하고 있다는 게 중요하다.

## 4. 진위 한 줄

**✅ 실제로 돌아간다.**

- **진짜 CronJob**이 매일 03:17에 `pg_dump` 를 뜬다
- **진짜 sha256** 을 만들고 검증한다
- **복원 리허설이 진짜 임시 DB에 `pg_restore` 하고 row count를 비교**한다
- 배포 파이프라인이 **매 배포 전에 수동 백업**을 뜬다 (`jaywiki-postgres-backup-manual-*`)

**⚠️ 한계는 둘이다. 둘 다 내가 먼저 말한다.**

1. **백업이 원본과 같은 장비에 있다.** 3-2-1의 "1"(off-site)이 없다. **장비 전체 손실에는 대응 못 한다**
2. **RPO가 최대 24시간**이다. WAL 아카이빙 기반 시점 복구(PITR)는 없다

## 5. 30초 구두 답변

> 백업 이야기는 RPO와 RTO 두 숫자로 시작한다고 생각합니다. 얼마나 잃어도 되는가, 얼마나 빨리 돌아와야 하는가요. 저희는 하루 한 번 `pg_dump` 라서 RPO가 최대 24시간이고, 포트폴리오 데이터 특성상 감당 가능하다고 판단했습니다. 스트리밍 복제는 장비가 하나 더 필요해서 명백히 과투자고요.
>
> 형식은 custom을 씁니다. 압축도 되지만 무엇보다 테이블 단위 선택 복원이 가능해서요. 운영 실수로 테이블 하나 날렸을 때 전체를 되돌릴 필요가 없습니다. 그리고 sha256 체크섬을 같이 만듭니다. 백업 파일이 조용히 손상됐는데 그걸 장애 상황에서 처음 아는 게 최악이라서요.
>
> 제일 중요하게 생각한 건 복원 리허설입니다. "백업은 복원해보기 전까지 백업이 아니다"라고 스크립트에 적어 놨는데, 실제로 최신 dump를 골라서 체크섬을 검증하고 임시 DB에 복원한 다음 핵심 테이블 row count를 원본과 비교합니다. 원본은 읽기만 하고 복원은 항상 타임스탬프 붙은 새 DB로만 해서, 연습하다가 사고 내는 일이 없게 했습니다.
>
> 다만 한계가 명확합니다. 백업이 원본과 같은 장비에 있어서 3-2-1 규칙의 off-site가 없습니다. miniPC가 통째로 고장 나면 둘 다 잃어요. R2로 외부 복제하는 게 다음 단계인데 아직 안 했습니다.

## 6. 꼬리질문과 답

**Q1. 백업이 잘 되고 있는지 어떻게 확인하나요?**

**세 겹으로 봅니다.**

첫째, **CronJob이 성공했는가.** 실패하면 알람이 와야 합니다. 백업이 조용히 며칠째 안 되고 있는 게 흔한 사고입니다.

둘째, **파일이 실제로 생겼고 크기가 이상하지 않은가.** 0바이트나 갑자기 절반으로 줄어든 파일은 문제 신호입니다.

셋째, 그리고 이게 제일 중요한데 **복원이 되는가.** 앞의 둘은 "파일이 존재한다"만 증명하지 "쓸 수 있다"를 증명하지 않습니다. 그래서 복원 리허설 스크립트를 만들었습니다.

**Q2. 복원에 얼마나 걸리나요?**

**리허설로 재는 값입니다.** 그리고 그게 리허설을 하는 이유 중 하나고요. 장애 상황에서 "얼마나 걸릴까요?"라는 질문에 "해봐야 압니다"라고 답하면 안 되니까요.

RTO를 줄이려면 `pg_restore -j` 로 병렬 복원을 하거나, 전체가 아니라 필요한 테이블만 복원하는 방법이 있습니다. custom 포맷을 고른 이유가 그 둘이 가능해서고요.

**Q3. 논리적 손상은 백업으로 해결되나요?**

**부분적으로만요.** 그리고 이게 백업의 한계입니다.

`WHERE` 절 없는 `UPDATE` 로 3만 건을 날렸다고 하면, 백업으로 돌릴 수는 있습니다. 그런데 **마지막 백업 이후의 정상 거래도 함께 사라집니다.** 그리고 언제 망가졌는지 모르면 어느 백업으로 가야 할지도 모릅니다.

그래서 **백업은 마지막 방어선이지 첫 번째가 아닙니다.** 애초에 잘못된 UPDATE가 나가지 않게 하는 절차가 앞에 있어야 합니다. 대상을 먼저 SELECT로 확인하고, 수정 전 값을 스냅샷으로 남기고, 조건부 UPDATE로 영향 행 수를 검증하는 식으로요. 저희 시나리오 중에 "운영 데이터 조회·정정"이 그걸 다룹니다.

**Q4. 왜 백업을 같은 장비에 두셨나요?**

**아직 외부 복제를 안 했기 때문이고, 이건 한계가 맞습니다.**

현재 상태로는 디스크 논리 장애나 운영 실수에는 대응되지만, **miniPC 자체가 고장 나면 원본과 백업을 함께 잃습니다.** 3-2-1 규칙의 off-site 조건을 못 지키고 있는 거죠.

다음 단계로 Cloudflare R2에 복제하는 걸 계획하고 있습니다. 오브젝트 스토리지에 올리고, 거기에도 수명주기 정책을 걸어서 오래된 건 자동 삭제하는 방식으로요. 다만 그러면 **백업 파일이 외부에 나가니까 암호화가 따로 필요**해집니다. 그 부분까지 정리가 안 돼서 미뤄 둔 상태입니다.

## 7. 모르면 인정할 선

**여기까지는 자신 있게 답한다**
- **RPO와 RTO의 정의**와 이 프로젝트의 실제 값
- `--format=custom` 을 고른 이유 (선택 복원, 병렬 복원, 압축)
- 체크섬이 필요한 이유 (조용한 손상)
- 보관 기간의 트레이드오프
- **테이블 필터를 두지 않는 이유** (새 테이블 누락 사고 방지) — 블로그에서 실제로 효과를 봄
- **"백업은 복원해보기 전까지 백업이 아니다"** 와 리허설이 검증하는 것들
- 리허설이 원본을 안 건드리는 설계와 `trap cleanup`
- **3-2-1 규칙과 내 백업이 그걸 못 지킨다는 자기 진단**
- 백업이 논리적 손상에는 약하다는 것

**여기부터는 "안 해봤습니다"라고 말한다**
- **WAL 아카이빙과 PITR(시점 복구)** 실제 구성
- **외부 복제(R2)** — 계획만 있고 안 함
- 백업 파일 암호화와 키 관리
- 스트리밍 복제 / standby 구성과 failover
- 대용량 DB에서의 복원 시간 최적화 실측

> ### 자가 점검
> **RPO와 RTO를 이 프로젝트의 실제 숫자로** 답할 수 있는가.
> **"백업이 잘 되는지 어떻게 아나"** 에 세 겹으로 답하고 마지막이 복원이라고 말할 수 있는가.
> **3-2-1 중 뭘 못 지키는지** 먼저 말할 수 있는가.

# 3. 오류 한 건이 휴대폰까지 가는 길

**시나리오 id**: `alert-chain-drill`
**화면**: `/scenarios` → 알림 사슬 리허설 · 근거 글은 `/wiki/silent-500-alert-gap`
**코드**: `infra/k8s/observability/prometheus-values.yaml`, `loki-rules.yaml`,
`alertmanager-telegram-values.yaml`, `GlobalExceptionHandler`, `GlobalExceptionHandlerTest`

## 1. 한 줄 정의

**오류를 일부러 내서**, 그것이 지표와 로그 중 어느 쪽에 먼저 걸리고 텔레그램까지 실제로 도착하는지를 끝까지 따라간다. 이 그룹에서 **유일하게 화면 밖(휴대폰)에서 끝나는 편**이다.

## 2. 원리 — 왜 이 문제가 생기나

### 2-1. 비율 알림은 조용한 사이트에서 안 울린다

알림 규칙의 표준형은 이렇다.

```
5xx 비율이 1%를 넘은 상태로 2분 지속되면 울린다
```

큰 서비스에서는 맞는 식이다. 초당 수천 건이 흐르면 1%도 수십 건이고, 진짜 장애는 2분 넘게 간다.

그런데 이 사이트는 트래픽이 **0.5 req/s** 쯤이다. 여기에 500이 **한 건** 나면 이렇게 된다.

```
5분 창의 전체 요청   약 150건
5xx 1건 → 비율      약 0.7%     ← 1% 문턱을 못 넘는다
지속 시간           한 번뿐     ← 2분을 못 버틴다
```

두 조건 다 못 채운다. **규칙 7개가 전부 「지속되는 장애」를 잡게 설계돼 있었고, 관리자가 저장 한 번 못 한 사고는 설계상 안 잡히는 종류였다.**

여기가 이 편의 출발점이다. 2026-08-12 에 운영에서 실제로 그 일이 났다. 블로그 글 수정이 500으로 실패했는데 텔레그램에는 아무것도 오지 않았다. **오류가 난 것보다 아무도 모를 뻔한 것이 사건이다.**

### 2-2. 건수로 세면 되는가 — `increase` 가 새 시계열을 못 본다

그래서 비율 대신 건수로 세는 규칙을 넣었다. 처음 쓴 식이 이것이다.

```promql
increase(http_server_requests_seconds_count{...status=~"5.."}[10m]) > 0
```

**이것도 틀렸다.** 같은 데이터로 재보니 `increase(...[6h])` 가 0을 뱉었다. 원본 카운터는 1인데도.

`increase` 는 시간 창 안의 **첫 샘플을 기준선으로 잡아 마지막 값에서 뺀다.**

```
시계열이 이미 있던 경우          시계열이 그 오류로 처음 생긴 경우
10:00  count = 12               10:00  (시계열 없음)
10:10  count = 13               10:10  count = 1   ← 첫 샘플이자 마지막 샘플
increase = 13 - 12 = 1  ✅      increase = 1 - 1 = 0  ❌
```

즉 **어떤 API에서 처음 나는 5xx는 통째로 못 잡는다.** 게다가 pod가 재시작하면 시계열도 새로 태어나므로 **배포할 때마다 같은 구멍이 다시 생긴다.**

새 기능에서 처음 터지는 오류가 제일 알고 싶은 것인데, 바로 그것이 안 잡히는 규칙이었다.

고친 식은 뺄셈이다. 지금 값에서 10분 전 값을 빼되, **그때 없던 시계열은 0을 기준으로 둔다.** 같은 데이터로 이 식은 1을 뱉는다.

### 2-3. 규칙이 울리는 것과 알림이 가는 것은 다른 층이다

규칙을 고쳐 실제로 `firing` 시키는 데까지 성공했는데도 **텔레그램은 오지 않았다.**

Alertmanager가 받은 알림을 열어 보니 `receivers` 가 `telegram` 이 아니라 `default-receiver` 였다. 그것은 **아무 데도 보내지 않는 빈 receiver** 다.

```
텔레그램 설정 파일        저장소에 35일째 있었다
bot-token, chat-id       Secret 에 35일째 있었다
클러스터에 올라간 적      한 번도 없다
```

**재료는 전부 갖춰져 있었고 배선만 안 꽂혀 있었다.**

원인은 Helm 이다. 두 values 파일이 같은 릴리스인데, `helm upgrade` 에 `prometheus-values.yaml` 하나만 주면 Alertmanager 의 receiver 가 `default-receiver` 로 **되돌아간다.**

그래서 35일 동안 몰랐다. 규칙은 정상적으로 firing 하고, Alertmanager 도 알림을 받는다. **어느 화면에도 이상이 안 보인다.**

> **알림 체계는 「규칙」과 「전달」 두 층이고, 규칙이 울리는 것을 봤다고 전달까지 확인한 것이 아니다.**

### 2-4. 지표와 로그는 중복이 아니라 덮는 범위가 다르다

지표(Prometheus) 경로에는 **숫자만 흐른다.** 예외 본문과 `trace_id` 는 로그에만 있어서, 지표 규칙이 아무리 정확해도 알림에 실을 수 없다. 그래서 Loki ruler 로 **로그 본문을 보는 갈래**를 하나 더 놓았다.

| | 지표 규칙 | 로그 규칙 |
|---|---|---|
| 잡는 범위 | 백엔드의 **모든** 5xx | 그 핸들러를 타고 그 형식으로 찍힌 예외만 |
| 실을 수 있는 것 | 숫자뿐 | `trace_id`, pod 까지 |
| 성해야 하는 것 | Prometheus 스크랩 | promtail · Loki · **로그 형식**까지 |
| 성격 | 넓고 튼튼하다 | **상세하지만 더 좁고 더 잘 깨진다** |

둘 다 남기고, 같은 사고를 둘이 잡으면 **Alertmanager 억제로 상세한 쪽만** 보낸다.

이 판단이 나중에 실전에서 증명됐다. **배포 직후 10분은 지표 규칙의 눈먼 구간**이다(2-2의 이유로 뺄셈이 0 이하가 된다). 09:42 에 그 구간 안에서 일부러 500을 냈더니 **지표는 조용했고 로그 규칙만 잡아 `trace_id` 까지 실어 보냈다.** 로그 규칙은 카운터가 아니라 로그 줄을 세므로 pod 가 새로 떠도 눈멀지 않는다.

### 2-5. 정규식이 어긋났는데도 알림은 떴다

로그 규칙을 Spring 배포보다 **먼저** 올렸더니 옛 형식 로그와 정규식이 안 맞았다. 그런데도 알림은 왔다 — **값이 전부 빈 채로.**

```
텔레그램 수신 내용:  "오류 ·"       ← 그 뒤가 통째로 비었다
```

`LogQL` 의 `regexp` 는 **안 맞아도 줄을 버리지 않고 라벨만 비운 채 통과시키기** 때문이다.

그래서 정규식 **뒤에** `status =~ "5.."` 라는 라벨 필터를 문지기로 세웠다. 5xx 를 고르려는 게 아니라 **정규식이 실제로 맞았는지 보는 장치**다. status 가 비어 있으면 여기서 걸러진다.

### 2-6. 억제가 안 걸렸다 — 같은 요청을 둘이 다른 이름으로 불렀다

억제를 `equal: [method, uri]` 로 걸었는데 두 통이 그대로 왔다.

```
지표: uri = /api/blog/posts/{id}/comments   ← Spring 이 지표에 쓰는 라우트 패턴
로그: uri = /api/blog/posts/24/comments     ← 실제 요청 경로
```

같은 요청인데 문자열이 달라 억제가 통과하지 못했다. 로그에 `path`(실제 경로)와 `route`(패턴)를 **둘 다** 찍게 하고, Loki 규칙이 `route` 를 `uri` 라는 이름으로 뽑아 지표 라벨과 맞췄다. 사람에게 보여줄 때는 **재현에 그대로 쓸 수 있는 `path`** 를 쓴다.

### 2-7. 검증할 수 없는 알림 — 사고를 안전하게 만드는 손잡이

알림 체계는 **오류가 나야 검증되고, 오류를 기다리면 검증이 안 된다.** 게다가 버그를 고치고 나면 그 500을 다시 낼 수 없다.

그래서 인증 없이 진짜 500을 내는 손잡이를 찾았다. `POST /api/blog/posts/{id}/comments` 는 `permitAll` 이고, 본문에 `{"broken` 처럼 깨진 JSON 을 보내면 `HttpMessageNotReadableException` 이 나 같은 경로를 탄다. **데이터는 바뀌지 않는다.**

### 2-8. 그 손잡이가 500이 아니어야 할 것을 드러냈다 — 그리고 이 편을 뒤집었다

읽을 수 없는 본문은 **보낸 쪽 잘못이라 400이 맞다.** 처리기가 없어 500으로 나가고 있었다. 그대로 두면 **봇이 아무 JSON 이나 던져도 5xx 지표가 오르고 운영 알림이 울린다.** 남 잘못에 내 폰이 울리면 알림을 곧 무시하게 되고, 그러면 여기까지 세운 것이 전부 무의미해진다.

400으로 내렸다. 그러자 이런 일이 생겼다.

> 이 편이 다루는 원래 사고 — 관리자 화면이 발행일을 오프셋 없이 보낸 것 — **도 읽을 수 없는 본문이다.**
> 400으로 바로잡은 뒤로는 **그 사고가 5xx가 아니다.**
> **하루 종일 세운 5xx 알림 체계가 정작 이 편의 사고를 못 잡게 됐다.**

그래서 400을 곁가지가 아니라 **본체로** 다뤘다. 400 로그도 500과 같은 꼬리(`status·method·path·route`)를 찍고, Loki 규칙 하나가 둘 다 잡는다. 규칙 이름도 `JaywikiUnhandledException` 에서 `JaywikiApiErrorLogged` 로 바꿨다. 억제의 `equal` 에는 `status` 를 더했다 — **같은 경로에서 400과 500이 함께 나면 서로 다른 사고**이기 때문이다.

401·403·404 와 봇 스캔(`/**`, `UNKNOWN`, `REDIRECTION`)은 뺐다. **남이 문을 두드리는 것에는 울리지 않고, 우리 화면이 잘못 보낸 것에만 울린다.**

## 3. 대안 표와 내 선택

| 안 | 잡는 것 | 대가 | 판단 |
|---|---|---|---|
| 비율 + 지속시간 (원래 규칙) | 지속되는 장애 | **조용한 사이트의 단발 오류를 놓친다** | 지우지 않고 남김 — 큰 장애용 |
| `increase` 로 건수 | 이미 있던 시계열의 증가 | **처음 나는 오류와 배포 직후를 못 본다** | 기각 |
| 지금 값 − 10분 전 값 (없으면 0) | 단발 오류, 새 시계열 포함 | 배포 직후 10분은 여전히 눈먼다 | **채택 (지표 갈래)** |
| Loki ruler 로 로그 본문 | `trace_id`·pod 까지, pod 재시작에 안 눈먼다 | 로그 형식에 의존해 더 잘 깨진다 | **채택 (로그 갈래)** |
| 로그 갈래만 남기기 | — | 로그 파이프라인이 죽으면 통째로 못 본다 | 기각 — 둘의 실패 모드가 다르다 |

**두 갈래를 다 둔 것이 핵심 판단이다.** 중복 비용을 내는 대신, 하나가 눈먼 구간을 다른 하나가 덮는다. 그리고 그것을 09:42 실측으로 증명했다.

## 4. 진위 한 줄

> **✅ 실제 실행.** 다만 이 그룹의 다른 두 편과 성격이 다르다 — **화면에서 끝나지 않고 휴대폰에서 끝난다.**
> 실제 오류를 주입하고(공개 엔드포인트에 깨진 JSON), 실제 Prometheus·Loki 규칙이 평가되고,
> 실제 Alertmanager 억제가 걸리고, 실제 텔레그램 한 통이 온다. 그 스크린샷이 위키 글에 있다.
> 도달 지연도 실측이다 — 스크랩 15초 + evaluation 1분 + `for 0m` + group_wait 10초 = **보통 30~50초, 최악 85초.**

## 5. 30초 구두 답변

> 운영에서 500이 한 건 났는데 텔레그램이 안 울린 적이 있습니다. 규칙을 보니 **5xx 비율 1%가 2분 지속** 조건이었는데, 저희는 트래픽이 초당 0.5건이라 500 한 건이 0.7%밖에 안 되고 한 번뿐이라 2분도 못 버팁니다. **규칙 일곱 개가 전부 지속되는 장애용이었고, 저장 한 번 실패한 사고는 설계상 안 잡히는 종류였습니다.**
>
> 건수로 세는 규칙을 넣었는데 `increase` 를 썼더니 그것도 0이 나왔습니다. **그 오류 때문에 시계열이 처음 생겨서** 첫 샘플과 마지막 샘플이 같았거든요. 지금 값에서 10분 전 값을 빼는 식으로 바꿨습니다.
>
> 그런데 규칙을 firing 시키고도 알림이 안 왔습니다. Alertmanager 의 receiver 가 빈 값이었고, **텔레그램 설정 파일은 저장소에 35일째 있었는데 클러스터에 한 번도 안 올라가 있었습니다.** 여기서 **알림은 규칙과 전달 두 층이고, 규칙이 울리는 걸 봤다고 전달까지 확인한 게 아니라는 걸** 배웠습니다.
>
> 지금은 지표와 로그 두 갈래로 봅니다. 지표는 모든 5xx 를 잡지만 `trace_id` 를 못 싣고, 로그는 `trace_id` 까지 싣지만 로그 형식에 의존해 더 잘 깨집니다. 둘이 같은 사고를 잡으면 억제로 상세한 쪽만 보냅니다.

## 6. 꼬리질문과 답

**Q1. 왜 `increase` 대신 뺄셈인가? `rate` 나 `resets` 는?**

`increase` 와 `rate` 는 **창 안의 첫 샘플을 기준선으로 삼는다.** 시계열이 그 창에서 처음 태어나면 첫 샘플이 곧 마지막 샘플이라 증가량이 0이다. 카운터 초기화를 보정해 주지만, **없던 시계열이 생기는 것**은 초기화가 아니라서 보정 대상이 아니다.

뺄셈 식은 10분 전 값을 명시적으로 조회하고 **없으면 0으로 둔다.** 그래서 새 시계열의 첫 1건이 그대로 1로 잡힌다.

`resets` 는 카운터가 줄어든 횟수를 세는 함수라 이 문제와 다른 것을 본다.

**남는 한계**: 배포로 pod 가 바뀌면 10분 전 값이 옛 pod 것이라 뺄셈이 0 이하가 된다. 그 10분은 지표 갈래가 눈먼다 — **그걸 로그 갈래가 덮는 것을 실측했다.**

**Q2. 알림 두 개가 오면 시끄럽지 않나? 억제는 어떻게 거는가?**

Alertmanager 억제 규칙으로 **로그 알림이 떠 있으면 지표 알림을 누른다.** `equal` 로 `method`, `uri`, `status` 셋이 같을 때만 같은 사고로 본다.

여기서 두 번 틀렸다. 처음엔 `equal: [method, uri]` 였는데, **지표는 라우트 패턴(`/{id}`)을 쓰고 로그는 실제 경로(`/24`)를 써서** 문자열이 안 맞아 억제가 통과하지 못했다. 로그가 `path` 와 `route` 를 둘 다 찍게 하고 규칙이 `route` 를 `uri` 로 뽑게 맞췄다.

그리고 `status` 를 나중에 더했다. **같은 경로에서 400과 500이 함께 나면 서로 다른 사고**라서다.

**Q3. 로그 형식이 바뀌면 규칙이 조용히 깨지는데, 어떻게 막나?**

실제로 겪었다. 규칙을 배포보다 먼저 올렸더니 정규식이 안 맞았는데 **알림은 떴다 — 값이 전부 빈 채로.** `LogQL` 의 `regexp` 는 안 맞아도 줄을 버리지 않고 라벨만 비우기 때문이다.

두 겹으로 막았다.

1. **문지기 라벨 필터.** 정규식 뒤에 `status =~ "5.."` 를 세운다. 5xx 를 고르려는 게 아니라 **정규식이 맞았는지 보는 장치**다. 값이 비면 걸러진다.
2. **테스트로 계약을 고정.** `loki-rules.yaml` 의 정규식을 `GlobalExceptionHandlerTest` 에 그대로 두고, 400·500 두 형식의 로그 한 줄이 그 정규식과 맞는지 검사한다. **형식을 바꾸면 배포 전에 테스트가 먼저 깨진다.**

여러 줄 예외 메시지가 로그 한 줄을 쪼개는 것도 같은 테스트가 막는다(한 줄로 접고 200자로 자른다).

## 7. 모르면 인정할 선

**답할 수 있다**

- 왜 비율 규칙이 조용한 사이트에서 안 울리는지, 숫자로
- `increase` 가 새 시계열에서 0을 뱉는 이유와 대체 식
- 알림의 두 층(규칙·전달)과 35일 침묵의 원인
- 지표와 로그 갈래가 각각 덮는 범위와 깨지는 방식
- 억제 규칙의 `equal` 에 무엇이 들어가고 왜 그것인지
- 알림 문구에 무엇을 싣고 무엇을 뺐는지, 해제 알림을 끈 이유
- 도달 지연 30~50초의 구성 요소

**"안 해봤습니다"**

- **대규모 트래픽에서의 알림 튜닝.** 여기 규칙은 초당 0.5건짜리 사이트에 맞춘 것이라, 건건이 보는 방식이 트래픽이 크면 그대로 알림 폭풍이 된다. 그때는 다시 비율과 급증으로 가야 한다
- **온콜 로테이션·에스컬레이션.** 받는 사람이 나 하나라 정책이 없다
- **SLO 기반 알림(에러 버짓 소진율).** 다중 창 번burn rate 규칙은 읽어만 봤고 세워 본 적 없다
- **브라우저에서만 깨지는 오류.** 서버로 보내는 통로가 아직 없다

> ### 자가 점검
> **500 한 건이 왜 안 잡혔는지**를 트래픽 숫자와 함께 말할 수 있는가.
> **`increase` 가 0을 뱉은 이유**를 첫 샘플·마지막 샘플로 설명할 수 있는가.
> **"규칙이 울리는 것과 알림이 가는 것은 다른 층"** 을 35일 사례로 말할 수 있는가.
> 400으로 내린 결정이 **왜 이 편을 뒤집었는지** 설명할 수 있는가.

면접에서 **"인프라나 운영 경험이 있나요"** 또는 **"장애 대응 경험"** 이 나오면 이렇게 묶는다.

> 운영에서 제일 위험한 건 **"될 거라고 믿는 것"** 이라고 생각합니다. 그리고 그 믿음은 대개 **필요한 순간에 처음 시험됩니다.** 그게 최악의 타이밍이고요.
>
> 그래서 세 가지를 실제로 돌려 보는 형태로 만들었습니다.
>
> **오토스케일링**은 YAML만 써 놓으면 동작하는지 알 수 없어서, 부하 Pod를 띄워서 검색 API를 계속 호출하고 HPA가 replica를 1에서 2로, 다시 1로 조정하는 걸 화면에서 관측하게 만들었습니다. 설정에서 신경 쓴 건 확장과 축소를 비대칭으로 잡은 건데, 확장이 늦으면 사용자가 에러를 보고 축소가 늦으면 비용이 조금 더 나갈 뿐이라 손해가 작은 쪽으로 기울였습니다.
>
> **백업**은 "복원해보기 전까지 백업이 아니다"를 스크립트로 만들었습니다. 최신 dump의 체크섬을 검증하고 임시 DB에 실제로 복원한 다음, 핵심 테이블 row count를 원본과 비교합니다. 원본은 읽기만 하고 복원은 항상 새 임시 DB로만 해서 연습이 사고가 되지 않게 했고요.
>
> **알림**은 500이 한 건 났는데 텔레그램이 안 온 사고에서 시작했습니다. 규칙이 「5xx 비율 1%가 2분 지속」이었는데 트래픽이 초당 0.5건이라 애초에 안 잡히는 종류였고, 규칙을 고쳐 firing 시킨 뒤에도 알림은 안 왔습니다. **Alertmanager 의 receiver 가 비어 있었고, 텔레그램 설정 파일은 저장소에 35일째 있었는데 클러스터에 한 번도 안 올라가 있었습니다.** 알림은 규칙과 전달 두 층인데 규칙만 보고 있었던 겁니다. 지금은 지표와 로그 두 갈래로 보고, 둘이 같은 사고를 잡으면 억제로 상세한 쪽만 보냅니다.
>
> 세 편 다 **한계를 명확히 알고 있습니다.** HPA는 maxReplicas가 2고, 무엇보다 실제로 2가 되면 저희 채팅방 정원 제어가 깨집니다. `synchronized` 로 잠그는데 그건 JVM 안에서만 유효해서요. **수평 확장은 인프라 설정이 아니라 애플리케이션이 무상태여야 가능하다**는 걸 직접 확인한 셈입니다. 백업은 원본과 같은 장비에 있어서 3-2-1의 off-site를 못 지킵니다. 장비 전체가 죽으면 둘 다 잃습니다. 알림은 배포 직후 10분 동안 지표 갈래가 눈머는데, 그 구간을 로그 갈래가 덮는 것까지 실측으로 확인했습니다.
>
> 이 한계들을 아는 게 기능을 하나 더 만드는 것보다 중요하다고 생각합니다.

## 왜 이 답변이 강한가

1. **"선언 vs 증명"** 이라는 관점이 두 편을 하나로 꿴다
2. **"믿음은 필요한 순간에 처음 시험된다"** 는 운영을 해본 사람의 문장이다
3. 확장/축소 비대칭처럼 **설정값 하나에 담긴 판단 근거**를 설명한다
4. **한계 둘을 스스로 정확히 짚는다.** 특히 "HPA가 내 채팅 코드를 깨뜨린다"는 건 시나리오 간 연결을 이해했다는 증거다
5. 마지막 문장이 **엔지니어링 성숙도**를 보여준다

## 이 그룹의 진위 요약

| 편 | 진위 | 한계 (내가 먼저 말한다) |
|---|---|---|
| **HPA 자동 확장** | ✅ 실제 실행 | maxReplicas 2 (단일 노드) / **replica 2면 채팅·Outbox가 깨진다** |
