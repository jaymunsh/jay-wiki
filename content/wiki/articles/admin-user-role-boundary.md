
- 둘로 나눠 설계한 역할 중 USER가 실제로는 아무 경로도 지키지 않고 있었다는 발견이다.
- 지키는 것이 없는 역할을 위해 남의 개인정보를 받을 이유가 없으므로 구글 로그인을 제거하고 email·subject 컬럼을 드롭한 뒤 ADMIN 경계 하나만 남기기로 판단했다.
- 인가 규칙을 처음부터 다시 읽어 규칙이 ADMIN 요구와 전체 공개 둘뿐임을 확인했고, 운영 게시판 최근 100건이 전부 익명임을 확인했다.

처음에는 역할을 둘로 나눠 설계했다. 관리자는 로컬 계정과 OTP로, 일반 사용자는 구글 로그인으로 들어오고,
권한은 서버가 role로 가른다. 표까지 그려 두면 그럴듯해 보였다.

나중에 인가 규칙을 처음부터 다시 읽었다. **USER만 통과하는 경로가 하나도 없었다.**

## 무엇이 실제로 걸려 있었나

규칙은 두 종류뿐이었다. ADMIN을 요구하거나, 전부 공개하거나.

| 경로 | 실제 규칙 |
|---|---|
| 조회(GET) 전체 | 공개 |
| 게시판 작성, 댓글, 본인 삭제 | 공개 |
| 블로그 댓글 작성과 본인 삭제 | 공개 |
| 시나리오 실행 | 공개 |
| 관리 목록, 문서 편집, 탭 관리, 서비스 제어 | ADMIN |

로그인한 USER가 비로그인 방문자보다 더 할 수 있는 일이 없었다. 로그인이 실제로 하는 일은 하나였다.
게시판 작성자 이름이 익명 대신 계정 이름으로 바뀌는 것.

운영 게시판의 최근 100건을 확인했더니 전부 익명이었다. 로그인해서 쓴 글은 없었다.

## 왜 이렇게 됐나

역할 표를 먼저 그리고 규칙을 나중에 썼기 때문이다. 표에는 USER 칸이 있으니 뭔가 들어가야 할 것 같지만,
막상 기능을 하나씩 열 때마다 익명도 쓸 수 있게 만드는 편이 자연스러웠다. 게시판을 로그인 뒤로 숨길 이유가
없었고, 시나리오 실행은 보여 주려고 만든 것이라 더 그랬다.

그렇게 USER 칸은 비어 갔는데 표는 그대로 남아 있었다. 설계 문서가 코드보다 늦게 낡는다.

## 그래서 무엇을 했나

USER 역할을 위해 구글 계정의 이메일과 계정 식별자를 저장하고 있었다. 지키는 것이 없는 경계를 위해
남의 개인정보를 받고 있었던 셈이다. 2026년 8월 6일에 구글 로그인을 제거하고 그 두 컬럼을 드롭했다.

로컬 회원가입은 남겼다. 쓰임이 있어서가 아니라 개인정보 처리 시나리오를 만들 재료로 쓰려고 일부러 둔
것이다. 그 대신 위키용 개인정보 처리방침을 새로 써서 무엇을 받는지 적었다.

## 남은 경계는 ADMIN 하나뿐이고, 그 하나는 값을 한다

지금 남은 인증 경계는 ADMIN 하나다. 그리고 이 하나는 그대로 값을 한다.

관리자는 비밀번호를 알아도 애플리케이션이 검증하는 OTP 없이는 토큰을 받지 못한다. 관리자 계정 하나가
전체 콘텐츠와 서비스 제어 권한을 갖기 때문에, 비밀번호 유출 하나로 경계가 무너지지 않게 했다.
OTP 시도 횟수가 많으면 서버가 429로 막아 추측 공격도 제한한다.

브라우저에는 jw_token httpOnly 쿠키만 남고 role 판단은 서버가 한다. UI에서 버튼을 숨기는 것은 편의
기능일 뿐이고, 실제 보호는 Spring의 권한 검사와 BFF 경계에서 이뤄진다.

## 역할은 막는 요청이 있어야 존재한다

**역할을 몇 개 만들지보다, 각 역할이 실제로 막는 요청이 무엇인지가 먼저다.** 인가 규칙을 훑어서
그 역할로만 통과하는 줄을 못 찾으면 그 역할은 아직 없는 것이다. 이름만 있는 역할은 권한을 나누지 않고
개인정보 수집의 명분만 만든다.
