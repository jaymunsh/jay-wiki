
- 이 사이트가 어떤 묶음으로 나뉘고, 무엇이 어디까지 만들어져 있고, 어디부터 읽으면 되나?
- 첫 화면은 무엇을 눌러 볼지 정하는 자리로 두고, 구조를 통째로 읽는 자리는 이 글로 갈랐다.
- 아래 표는 [jay-wiki 한눈에 보기](/wiki/jaywiki-main-map)에 있던 것을 문장 하나 바꾸지 않고 옮긴 것이다.

첫 화면에 이 내용이 전부 붙어 있었다. 처음 오는 사람이 무엇을 눌러 볼지 정하기 전에
구조 설명 일곱 절을 먼저 지나야 했고, 그래서 첫 화면은 허브가 아니라 문서가 되어 있었다.
2026-08-23에 실행 화면으로 보내는 부분만 첫 화면에 남기고, 구조를 읽는 부분을 이 글로 옮겼다.

miniPC 위에는 k3s가 돈다. k3s는 여러 서비스를 한 대 안에 배치하고 죽으면 다시 띄워 주는
관리자, 즉 가볍게 만든 Kubernetes다. 바깥에서 오는 요청은 Cloudflare Tunnel을 지나 들어온다.
집 공유기에 포트를 여는 대신, 서버가 Cloudflare 쪽으로 먼저 연결을 만들어 두고 그 연결로만
요청을 받는 방식이라 집 IP로 직접 들어오는 길이 없다. 요청은 거기서 Traefik을 거쳐
Next.js로 들어온다.

첫 화면 아래의 오케스트레이션 지도가 그 경로를 그림으로 보여준다. 지도의 칸 하나하나가 무엇이고
지금 어떤 버전으로 도는지는 [오케스트레이션 지도를 한 칸씩 읽는 법](/wiki/orchestration-map-walkthrough)에
요청 경로 순서대로 적어 뒀다.

## 문서는 만들고, 운영하고, 고친 기록으로 나뉜다

글이 많아서 아무 데나 열면 길을 잃는다. 그래서 문서를 네 묶음으로 나눴다.
앞의 셋은 이 사이트 자체를 만들고 운영하고 개선한 기록이고,
마지막 하나는 이 사이트 밖에서 한 프로젝트와 실험이다. 마지막 묶음의 글은 위키가 아니라 블로그에 있다.

| 축 | 질문 | 이 사이트에서 확인하는 방법 |
|---|---|---|
| BUILD | 왜 이 구조와 기술을 선택했는가 | 인프라·백엔드·데이터·프론트엔드에서 설계 결정과 구현을 읽는다 |
| OPERATE | 실제로 배포하고 관측하며 복구할 수 있는가 | 운영·관측 · 시나리오·시연 · 보안 · 운영 검증에서 지표, 실행 이력과 검증 기록을 확인한다 |
| IMPROVE | 실패와 변경을 어떻게 다음 판단으로 연결했는가 | 프로세스·AI · 거버넌스 · 회고·로드맵에서 개선 근거를 읽는다 |
| LAB | 이 사이트 밖에서는 무엇을 만들고 측정했는가 | 글 여덟 편을 2026-08-10에 블로그(blog.leneu.cloud)로 옮겼다. 대분류 화면에서 LAB은 탭 카드가 아니라 블로그 링크로 나간다 |

보안을 IMPROVE가 아니라 OPERATE에 둔 이유가 있다. 이 프로젝트에서 보안은 나중에 개선할 항목이 아니라
공개 경계·인증·Secret처럼 운영하는 동안 계속 지켜야 하는 조건이기 때문이다.

## 화면에 보인다고 전부 같은 무게가 아니다

아래 표들을 읽기 전에 이 구분을 먼저 둔다. 이 사이트의 기능은 세 가지 무게로 나뉘고,
이 사이트는 화면에 보인다는 이유만으로 모든 기능을 운영 검증으로 주장하지 않는다.
정책 모델이란, 실제 외부 결제나 실제 부하를 걸어 본 것이 아니라 미리 정한 입력을 넣고
대응 방식끼리 비교해 보는 리허설이라는 뜻이다.

| 수준 | 의미 | 예시 |
|---|---|---|
| 구현 | 코드와 자동화 테스트로 동작을 확인했다 | 위키 revision, BFF 인증 경계, 검색 비교, 상태 전이 engine |
| 운영 검증 | miniPC 환경에서 실행 결과나 복구 기록을 남겼다 | 배포 rollout, TOTP 로그인, HPA 확장, trace 연결, 백업·복원 리허설 |
| 정책 모델 | 실제 외부 거래나 부하 대신 고정 입력으로 대응 방식을 비교한다 | 상품권, 주문, 쿠폰 경합, 정산 재실행, Connection Pool, JPA N+1 |

표에 나온 말을 풀면 이렇다. revision은 글을 고칠 때마다 남는 이전 판이고,
TOTP는 로그인할 때 30초마다 바뀌는 일회용 번호를 함께 요구하는 인증 방식이며,
HPA는 부하가 오르면 같은 서비스의 복제본 수를 자동으로 늘리는 Kubernetes 기능이고,
trace는 요청 하나가 어느 서비스를 얼마 만에 지나갔는지 한 줄로 이어 보여주는 기록이다.

정책 모델은 설계 판단을 설명하기 위한 리허설이다. 실제 Redis 동시성 시험, 정산 원장,
HikariCP metric이나 Hibernate query benchmark를 수행한 것처럼 표현하지 않는다.

## 브라우저는 Spring을 직접 보지 않는다

시스템이 어떻게 연결되는지는 이 한 가지 경계만 잡으면 나머지가 풀린다.
브라우저는 Next.js만 보고, Next.js가 BFF와 Server Action을 통해 클러스터 내부
Spring API를 호출한다.

| 계층 | 역할 | 연결 대상 |
|---|---|---|
| Browser | 공개 웹 화면과 사용자 조작 | Cloudflare Tunnel → Next.js web |
| Next.js | 화면 렌더링과 BFF 경계 | /api/bff 경로 → Spring Boot jaywiki |
| Spring Boot | 도메인 로직과 운영 API | PostgreSQL, Redis, OpenSearch, Kafka |
| FastAPI | 분리된 결제 참여자와 외부 API simulator | Saga 결제 승인·취소, 제휴 API 장애 리허설 |
| 데이터 서비스 | 영속화, 캐시, 검색, 이벤트와 이미지 자산 | PostgreSQL, Redis, OpenSearch, Kafka, MinIO |
| 관측 파이프라인 | metric, log, trace의 수집·저장·조회 | OTel Collector, Prometheus, Loki, Tempo, Grafana |

Spring은 업무 데이터 서비스의 중심이지만 관측 도구와 배포 파이프라인까지 Spring을 경유하지는 않는다.
브라우저에 공개되는 것은 Next.js의 화면과 제한된 BFF이며, Grafana 원본 화면과 내부 서비스 주소는 별도 접근 경계 뒤에 둔다.

## 지금 구현해 둔 범위는 여기까지다

기능별로 무엇이 만들어져 있고, 만든 것을 운영 화면 어디에서 다시 확인할 수 있는지를 짝지어 뒀다.
만든 것과 확인하는 방법이 짝을 이루지 않으면 이 표에 넣지 않았다.

| 축 | 구현 | 운영에서 확인하는 방법 |
|---|---|---|
| 위키 | DB 본문, 탭, revision, 관리자 편집 | 글을 수정하고 버전 이력을 다시 읽는다 |
| 인증과 권한 | local ADMIN, JWT와 TOTP | 관리자 OTP 경계와 공개 범위를 확인한다 |
| 게시판과 검색 | 10만 건 페이징, 익명·USER 글, 자동완성 | 세 검색 방식을 같은 쿼리로 비교한다 |
| Redis | 캐시, 조회수, 채팅 정원과 대기열 | 가상 사용자를 넣고 자동 승급을 본다 |
| Saga | Spring orchestration, FastAPI 결제 참여자 | 배송 실패 후 결제 취소와 재고 해제를 본다 |
| Kafka | Outbox, fan-out, retry, DLQ | 계속 실패 모드에서 격리된 이벤트를 확인한다 |
| 이미지 자산 | 위키 이미지 metadata와 MinIO 수명주기 경계 | 업로드, 같은 출처 조회와 삭제 조건을 확인한다 |
| 운영 | k3s, GHCR CI/CD, HPA, 백업, 관측 | 배포·metric·log·trace·복원 기록을 연결한다 |

이 표는 무엇을 만들었는지를 기능으로 묶은 것이다. 그것들이 각각 어느 서비스 위에서 도는지,
그 서비스가 지금 어떤 버전이고 메모리를 얼마나 쓰는지는
[오케스트레이션 지도를 한 칸씩 읽는 법](/wiki/orchestration-map-walkthrough)에 칸 하나씩 적어 뒀다.
PostgreSQL·Redis·Kafka·OpenSearch·MinIO부터 배포와 백업까지, 첫 화면 위 지도의 칸 순서 그대로다.

## 5분이면 한 바퀴를 돈다

1. [시나리오 허브](/scenarios)에서 관심 있는 운영 장면을 하나 고른다.
2. 기준 흐름과 실패 또는 지연 모드를 비교한다.
3. 처리 타임라인, 저장된 실행 결과와 관측 신호를 확인한다.
4. 관련 위키 문서에서 선택 이유와 실서비스 확장 조건을 읽는다.
5. 운영 검증과 회고에서 실제로 확인한 범위와 남은 한계를 구분한다.

## 보는 목적에 따라 입구가 다르다

무엇이 궁금해서 왔는지에 따라 먼저 볼 곳이 다르다. 자기 줄 하나만 찾으면 된다.

| 이 관점이라면 | 먼저 볼 곳 |
|---|---|
| 포트폴리오 전체를 빠르게 이해하고 싶다 | 이 글 → [시나리오 허브](/scenarios) → 회고 |
| 지금 무엇이 어떤 버전으로 돌고 있는지 궁금하다 | [오케스트레이션 지도를 한 칸씩 읽는 법](/wiki/orchestration-map-walkthrough) → 인프라 탭 |
| 백엔드 경계와 트랜잭션이 궁금하다 | 주문·상품권·외부 API 시나리오 → Saga → Kafka·Outbox 글 |
| 검색 설계가 궁금하다 | [검색 비교](/board/search) → OpenSearch 운영 글 |
| 데이터 모델과 테이블 경계가 궁금하다 | [전체 DB 스키마를 도메인별 ERD로 읽기](/wiki/db-schema-erd-map) → 데이터 탭 |
| 성능과 장애 대응이 궁금하다 | 트래픽·Connection Pool·N+1 시나리오 → 운영·관측 탭 |
| 배포와 복구가 궁금하다 | 운영·관측 탭 → 운영 검증 탭 → 백업·복원 runbook |
| 사용자 흐름과 권한 경계가 궁금하다 | 로그인 → 게시판 → TOTP 보안 글 |
| 이 사이트 밖의 결과물이 궁금하다 | 대분류의 LAB 링크 → 블로그(blog.leneu.cloud). 다른 프로젝트 글은 위키가 아니라 블로그에 있다 |

## 기능 하나마다 세 가지를 남긴다

기능을 붙이는 속도보다 이 세 가지가 갖춰졌는지를 먼저 본다.

| 기준 | 설명 |
|---|---|
| 구현 | 실제 코드와 테스트가 있어야 한다 |
| 운영 | miniPC k3s에서 재시작, 배포, 관측이 가능해야 한다 |
| 기록 | 왜 만들었고 어떤 실패가 있었는지 위키에 남긴다 |

그리고 아직 하지 않은 일을 한 것처럼 쓰지 않는다.
회고·로드맵 탭의 로드맵 항목에는 완료 조건이 함께 붙어 있고, 조건을 채우기 전에는 운영 글로 옮기지 않는다.

이 지도는 목차가 아니라, 어떤 기능을 실행하고 어떤 증거를 확인할지 결정하는 운영 중인 시스템의 지도다.
