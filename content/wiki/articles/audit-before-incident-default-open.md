
- 사고가 나기 전에 점검으로 찾은 구멍 네 개를, 왜 있다고 믿었던 방어가 실제로는 없었는지와 함께 기록한다.
- 가장 무거운 것은 관리자 조회가 인증 없이 열려 있던 것인데, 값이 아니라 SecurityConfig 의 규칙 순서가 잘못 서 있어서 앞으로 추가될 admin 조회까지 기본 공개가 되는 구조였다.
- 인증 없이 /api/bff/admin/services 를 실제로 호출해 401 이 아니라 컨트롤러 실행 뒤의 503 이 오는 것으로 확인했고, 수정을 되돌리면 실패하는 테스트 3개를 남겼다(294f61d, 기준선 198 → 201).

이 글은 사고 기록이 아니다. 운영에서 아무 일도 나지 않은 상태에서 저장소를 훑는 점검을 했고, 거기서 나온 것을 같은 날 커밋 294f61d 로 고쳤다. 그래서 postmortem 의 뼈대를 따르되 증상 자리에는 화면에 뜬 오류가 아니라 **점검이 실제 요청으로 확인한 상태**가 온다. 미리 적어 둘 한계가 하나 있다 — 실제로 악용된 흔적이 있는지는 확인하지 않았다. 본 것은 저장소와 로컬 요청뿐이고 운영 로그는 보지 않았다.

## 증상 — 인증 없는 요청이 관리자 컨트롤러까지 들어갔다

인증 쿠키 없이 /api/bff/admin/services 를 불렀다. 401 이 와야 하는 자리인데 503 이 왔다. 503 은 거절이 아니라 **컨트롤러가 실행된 뒤의 실패**다. 로컬에는 쿠버네티스 자격이 없어서 클러스터 조회가 실패했을 뿐이고, 운영 파드는 자격이 있으니 같은 요청에 200 과 함께 클러스터 구성이 나간다.

관리자 조회 하나만이 아니었다. 점검을 넓히자 성격이 같은 어긋남이 세 개 더 나왔다. 제한 없이 두드릴 수 있는 로그인, 클라이언트가 보낸 신원을 그대로 믿는 채팅, 그리고 조용히 꺼질 수 있는 2단계 인증이다.

## 잘못 짚은 원인 — 방어가 있다고 믿은 자리마다 실제로는 조건이 하나씩 빠져 있었다

점검 전에는 넷 다 막혀 있다고 믿었다. 믿음마다 근거가 있었는데, 근거가 조건 하나씩을 놓치고 있었다.

관리자 API 는 hasRole(ADMIN) 규칙이 있으니 닫혀 있다고 믿었다. 규칙은 실재했다. 그런데 SecurityConfig 는 **규칙 순서가 곧 정책**이다. GET /api/** 공개 규칙이 /api/admin/** ADMIN 규칙보다 먼저 평가되면, admin 의 모든 GET 은 공개 규칙에서 끝난다. 원래 코드에는 "아래의 GET 공개 규칙보다 먼저 와야 한다" 는 주석까지 있었다. **함정을 알고 있었는데, 선행 규칙을 /api/admin/blog/** 한 경로에만 줬다.** 나머지 admin 조회는 전부 공개였고, 앞으로 추가되는 admin 조회도 기본이 공개인 상태였다.

무차별 시도는 rate limit 인터셉터가 있으니 막혀 있다고 믿었다. 인터셉터는 실재했다. 그런데 걸린 곳이 /api/board/** 와 /api/blog/** 뿐이었고, 인증 없이 POST 할 수 있는 경로는 그보다 넓었다 — saga 주문, kafka 주문, 도메인 시나리오 실행, 채팅 초기화, 그리고 로그인. 가장 싼 공격은 채팅 초기화다. 정원 3명짜리 데모 방을 아무나 통째로 리셋한다. 가장 위험한 것은 로그인이다. 비밀번호 검증이 TOTP 검증보다 앞이라 응답이 "OTP 필요" 와 "아이디 또는 비밀번호가 올바르지 않습니다" 로 갈리고, **OTP 코드 없이도 비밀번호 정답 여부만 뽑아낼 수 있다.** TOTP 시도 제한 5회/5분은 있었지만 그것은 비밀번호를 맞힌 뒤의 이야기였다.

채팅은 프론트가 가리고 있으니 괜찮다고 믿기 쉬운 자리였는데, **이 경로는 BFF 를 안 거친다.** Ingress 가 WebSocket 을 Spring 으로 직결한다. 소켓은 쿼리스트링의 userId 를 그대로 신원으로 썼고, 그 값은 화면 상태 방송에 실려 접속자 전원에게 보인다. 남의 userId 로 붙으면 세션 맵이 덮여 상대에게 메시지가 안 가고, 공격자가 끊으면 상대가 방에서 나가진다. 오리진 제한도 패턴이 * 라 없는 것과 같았다.

2단계 인증은 운영에서 켜져 있으니 됐다고 믿었다. 지금은 켜져 있다. 그런데 TOTP 환경변수 두 개가 Secret 참조에서 optional 로 선언돼 있었다. Secret 에서 키가 빠지면 파드는 정상 기동하고 검증이 "비활성" 을 돌려주며 로그인이 통과된다. **비밀번호 한 겹으로 내려앉는데 아무도 안 알려준다.** JWT 키, IP salt, 콘텐츠 동기화 토큰은 optional 이 아니라 없으면 파드가 안 뜨는데, 2FA 만 fail-open 이었다. 게다가 다른 시크릿과 달리 이 키를 보장하는 스크립트도 없었다.

## 실제 원인 — 값이 아니라 구조가 틀려 있었다

넷을 관통하는 것은 하나다. 어느 것도 비밀번호가 약하거나 키가 새는 종류의 **값의 문제가 아니었다.** 규칙의 순서, 등록 목록의 범위, 신뢰 경계의 위치, 실패 방향 — 전부 구조가 틀려 있었고, 구조가 틀리면 그 위에 추가되는 것들이 기본으로 잘못된 쪽에 선다. admin 조회는 추가될 때마다 기본 공개였고, 인증 없는 POST 는 추가될 때마다 기본 무제한이었다.

그래서 고칠 때도 값이 아니라 구조를 고쳤다.

- 경로마다 예외를 더하는 대신 /api/admin/** 전체를 ADMIN 으로 닫았다. 새 admin 경로의 기본값이 공개에서 차단으로 바뀐다.
- 인증 없는 POST 경로를 전부 인터셉터에 등록하고, 인터셉터 안에 있던 경로 판단을 지웠다. **어디에 거는지는 등록 목록 한 곳에서만 정한다.** 판단이 두 곳이면 언젠가 어긋난다.
- 제한 통은 기능별로 나눴다. 하나로 합치면 데모를 눌러 본 사람이 로그인까지 막히고, 반대로 로그인을 두드려 통을 비우면 게시판이 함께 잠긴다.
- 채팅 userId 는 계속 받는다. 브라우저가 그 값을 저장했다가 재접속 시 대기열 자리를 유지하는 데 쓰기 때문에, 서버 발급으로 바꾸면 깔끔한 대신 기능이 깨진다. 대신 **이미 붙어 있는 id 로는 못 붙게** 막아 세션 탈취만 잘라냈고, 오리진을 공개 주소와 로컬로 좁혔다.
- TOTP 키의 optional 을 지워 다른 시크릿과 같은 fail-fast 로 만들었다. 이제 키가 없으면 파드가 안 뜬다. 배포가 죽을 수 있는 변경이라, 운영의 /api/auth/me 가 adminTotpEnabled 를 참으로 주는 것으로 키가 실재함을 먼저 확인하고 바꿨다.

곁가지로, /login 으로 리다이렉트만 하던 /admin/login 껍데기 페이지도 지웠다. 미들웨어가 인증 없는 /admin 요청을 바로 /login 으로 보낸다.

점검이 결함만 낸 것은 아니다. 마크다운은 raw HTML 이스케이프 뒤 허용목록 sanitize 를 한 번 더 타고, 애초에 마크다운을 쓸 수 있는 사람이 관리자뿐이다. SQL 문자열 조립이 없고 네이티브 쿼리도 전부 이름 붙은 파라미터다. 서버가 사용자 입력 주소를 부르는 곳이 없다. 업로드는 크기·MIME·매직바이트를 보고 확장자와 저장 경로를 서버가 만든다. 삭제 비밀번호의 평문 저장이 없고, 저장소에 진짜 운영 비밀값이 없다. BFF 프록시의 상위 경로 탈출도 실제로 시도해 봤는데, Next 라우터가 경로를 먼저 정규화해서 통하지 않았다.

## 남긴 방어 — 사람이 다시 밟을 자리를 테스트로 박았다

회귀 테스트 3개를 넣었다. 관리자 조회가 인증 없이 열리지 않는다, 로그인도 횟수 제한을 받는다, 기능마다 제한 통이 따로다. 넣고 끝내지 않고 **수정을 되돌려 실제로 실패하는 것까지 확인했다.** 통과하는 테스트가 진짜 무언가를 잡는지는 그렇게만 알 수 있다. 특히 첫 번째는 값이 아니라 규칙 순서라, 리팩터링에서 규칙 한 줄이 위아래로 움직이는 것만으로 조용히 다시 열린다. 주석이 한 번 실패한 자리라 주석을 더 쓰는 대신 테스트로 박았다. Spring 테스트 기준선은 198 에서 201 이 됐다.

## 남은 한계 — 악용 흔적은 확인하지 않았다

- 실제로 악용된 흔적은 확인하지 않았다. 저장소만 봤고 운영 로그는 안 봤다. "찾아서 막았다" 까지가 이 글이 말할 수 있는 전부다.
- 의존성 취약점 검사가 CI 에 없다. 지금 웹 의존성에 알려진 문제가 남아 있고 대부분 이 구성에서 경로가 닿지 않지만, 검사가 없다는 사실 자체가 구멍이다.
- 컨테이너가 전부 root 로 돈다(점검 당시 넷, shipping-api 가 붙은 지금은 다섯). 초기 침투 경로는 아니고 침투 후 확대 경로다.
- 클러스터 안에 네트워크 정책이 없고 Redis 에 인증이 없다. 같은 클러스터의 어떤 파드든 세션·제한 카운터·TOTP 재사용 방지 키가 든 Redis 에 붙을 수 있다.
  - 2026-08-17 부분 정정: pg-services 를 소유자만 받게 하는 NetworkPolicy 가 하나 생겼다. **Redis 는 그대로다** — 막는 정책이 아직 없다.
- 블로그 댓글의 IP 파생값에 보존기간이 없다. 방문자 집계는 24시간 TTL 을 거는데 댓글은 영구다.
