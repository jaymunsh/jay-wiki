
- 이 사이트의 프론트엔드 최적화를 무엇부터, 무엇을 근거로 했는지 적은 글이다.
- 가장 컸던 것은 코드 색칠이다. highlight.js 언어 정의를 192개에서 15개로 줄여 글 화면의 First Load JS 가 512kB 에서 228kB 가 됐다.
- 줄이기 전에 코드 블록 92개를 전후 설정으로 각각 렌더해 비교했고 92개 전부 같았다. 다만 화면이 실제로 얼마나 빨라졌는지는 아직 재지 않았다.

프론트엔드 최적화는 할 수 있는 일의 목록이 길다. 이미지를 줄이고, 번들을 쪼개고, 폰트를 손보고.
그 목록을 위에서부터 훑는 대신, 이 사이트가 실제로 내보내는 파일을 크기 순으로 늘어놓고
큰 것부터 손댔다. 이 글은 그 순서를 따라간다.

## 가장 큰 파일 하나가 코드 색칠이었다

운영 사이트가 보내는 청크를 크기 순으로 늘어놓자 하나가 눈에 띄었다.

~~~
/_next/static/chunks/8467-….js   1,156,028B  (gzip 372kB)
~~~

열어 보니 highlight.js 의 언어 정의가 통째로 들어 있었다. 통짜로 import 하면 언어 정의
**192개**가 전부 브라우저로 간다. Erlang, COBOL, Verilog 까지.

이 저장소의 글이 실제로 쓰는 언어를 세어 봤다. 여덟 종이다. bash 와 text 가 11블록씩으로
대부분이고, python 3, sql 2, markdown 2, js·ts·java·json 이 하나씩이다. 그래서 core 만
부르고 여유분을 포함해 15개만 등록하도록 바꿨다.

| | 이전 | 이후 |
|---|---:|---:|
| 글 화면이 처음 받는 JS | 512kB | **228kB** |
| 실리는 언어 정의 | 192개 | 15개 |

새 언어를 쓰려면 등록 목록에 한 줄이 늘어난다. 이 비용은 의도한 것이다 — 안 쓰는
언어를 모든 방문자에게 보내는 것보다, 쓸 때 한 줄을 적는 쪽이 싸다.

## 줄이기 전에 색칠 결과가 안 달라지는지부터 확인했다

언어를 안 적은 코드 블록은 자동 추측(highlightAuto)으로 갔다 — 같은 날 후속 커밋이 그 추측을 없애 지금은 plaintext 로 간다. 후보가 192개에서 15개로 줄면
추측의 답이 달라질 수 있다. 크기를 줄였는데 화면이 달라졌다면 최적화가 아니라 회귀다.

그래서 위키 시드와 블로그 초안의 코드 블록 **92개**를 전부 뽑아, 전후 설정으로 각각 렌더한
결과를 문자열로 비교했다. 표기가 없는 24개를 포함해 **92개 전부 바이트 단위로 같았다.**
그 블록들이 대부분 로그와 터미널 출력이라, 어느 언어로 추측하든 색칠할 것이 별로 없어서다.

## 이미지 지연 로딩은 글이 아니라 렌더러에 걸었다

이미지는 브라우저 표준 속성 loading="lazy" 하나로 됐다. 이 속성이 붙은 이미지는 화면에
들어오기 전까지 요청이 아예 나가지 않는다. 라이브러리도, 스크롤 감시 코드도 쓰지 않았다.

정한 것은 붙이는 위치다. 글마다 손으로 붙이면 언젠가 빠진다. 그래서 Markdown 렌더러의
이미지 처리에서 붙인다(web/src/lib/markdown.ts). 글에는 평범하게 이미지를 넣어도
결과 HTML 에는 항상 붙어 나온다. 빠질 자리가 없다.

효과는 글 아래쪽에서 난다. 위키 글은 길고 스크린샷은 대개 중간 아래에 있어서, 끝까지
안 읽는 사람은 그 이미지를 받지 않는다. 부작용도 하나 겪었다 — 헤드리스 브라우저로
이미지가 떴는지 쟀더니 naturalWidth 가 0 이라 깨진 줄 알았는데, 스크롤을 안 해서 브라우저가
요청을 안 한 것뿐이었다. 그 뒤로 지연 로딩을 건 화면은 **재는 쪽도 스크롤하고 나서 잰다.**

## mermaid 는 다이어그램이 있는 글에서만 내려받게 했다

mermaid 는 무겁다. 정적 import 를 걷어내고 다이어그램을 그리는 순간에 동적으로 가져오게
바꿨다(web/src/components/MermaidDiagrams.tsx). 다이어그램이 없는 글을 읽는 사람은
이 코드를 받지 않는다.

넓은 콘텐츠가 문서를 미는 문제도 여기서 같이 정리했다. 표는 렌더 단계에서 스크롤
컨테이너로 감싸고, 다이어그램도 페이지가 아니라 자기 프레임 안에서 가로 스크롤한다.
넓은 표 하나가 문서 전체를 가로로 밀지 않는다.

## 폰트와 썸네일은 자리 문제로 풀었다

폰트는 next/font/local 로 저장소에 두고 같은 서버에서 보낸다. 외부 요청이 없고,
폰트가 늦게 와서 글자가 한 번 바뀌는 일도 없다.

레이아웃 밀림(CLS)은 목록 썸네일에서 나기 쉽다. 컨테이너에 고정 크기(156×117 등)를 주고
이미지를 그 안에 맞췄다. 이미지가 늦게 떠도 자리가 이미 잡혀 있어 목록이 안 밀린다.
정적 분석 도구가 이 자리를 최적화 대상으로 지적했지만 고치지 않았다 — 크기가 이미
고정이면 할 일이 없다. **도구가 규칙을 보는 자리와 실제로 값이 나가는 자리는 다르다.**

## 자바스크립트가 늦게 와도 동작하게 만들었다

헤더 검색은 평범한 GET 폼으로 뒀다. 질의가 주소에만 살아서 공유와 뒤로가기가 그대로
되고, 스크립트가 아직 안 왔어도 검색이 동작한다.

첫 글은 서버에서 그려 HTML 로 온다. 브라우저가 글을 가져오는 것은 탭을 바꿀 때뿐이다.

## 보내는 비용만이 아니라 만드는 비용도 줄였다

Intl.DateTimeFormat 은 만드는 값이 비싸고 쓰는 값은 싸다. 그런데 호출할 때마다 새로
만드는 곳이 여덟 곳 있었고, 목록 한 화면이 날짜 수십 개를 그리니 그만큼 만들고 버리고
있었다. 모듈에서 한 번만 만들게 모았다.

## 여기서 멈췄고, 멈춘 이유가 있다

남은 228kB 에는 Markdown 파서와 sanitizer 가 들어 있다. 탭을 바꿀 때 본문을 브라우저에서
그리기 때문이다. 서버로 옮기면 더 줄지만 탭 전환이 서버 왕복이 된다.
**줄어드는 킬로바이트와 늘어나는 대기 시간을 같이 재기 전까지는 안 옮긴다.**

그리고 여기 적은 값은 전부 전송량이다. 실제 사용자 화면이 언제 그려지고 입력에 언제
반응하는지(LCP·INP)는 아직 재지 않았다. 그래서 이 글은 **무엇을 얼마나 줄였는지까지만**
말할 수 있고, 그래서 얼마나 빨라졌는지는 말하지 못한다.
