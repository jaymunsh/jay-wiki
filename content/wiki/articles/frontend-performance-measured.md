
- 프론트에서 무엇을 고칠지 무엇을 근거로 골랐나?
- 눈으로 의심한 두 가지는 둘 다 틀렸고, 실제 원인은 브라우저가 알아서 하는 스크롤 앵커링이었다.
- CDP 로 실제 마우스 이벤트를 보내 scrollY 가 500 에서 435, 370, 305 로 밀리는 것을 재현했고 고친 뒤 500 으로 고정됐다. 글 화면의 First Load JS 는 512kB 에서 228kB 가 됐다.

프론트 성능 이야기는 대부분 일반론으로 끝난다. 이미지를 줄이고, 번들을 쪼개고, 지연 로딩을 건다.
문제는 그 목록에 **이 사이트에서 실제로 값이 나가는 곳이 어디인지가 없다**는 것이다.
그래서 두 건을 골랐다. 하나는 사용자가 먼저 말해 준 증상이고, 하나는 재 보고 나서야 보인 것이다.

## 탭을 바꿀 때마다 화면이 조금씩 올라갔다

증상은 이랬다. 데스크톱에서 조금 스크롤한 뒤 탭을 바꾸면, 바꿀 때마다 화면이 조금씩 위로 밀렸다.
코드에는 스크롤을 옮기는 곳이 없었다. 탭 전환은 이미 scroll: false 로 라우팅하고 있었다.

먼저 재현부터 해야 했다. 헤드리스 크롬을 CDP 로 붙여 1440x900 으로 맞추고 탭을 눌러 봤는데
**아무 일도 일어나지 않았다.** 여기서 하나를 배웠다.

~~~
element.click()          → scrollY 500 → 500 → 500   (재현 안 됨)
Input.dispatchMouseEvent → scrollY 500 → 435 → 370   (재현)
~~~

자바스크립트로 부르는 click 은 이벤트만 만들고, 브라우저가 진짜 입력에 붙여 두는 처리는 건너뛴다.
UI 버그를 헤드리스로 쫓을 때 프로그램 클릭으로 안 나면 없는 게 아니라, **재는 방법이 틀린 것**일 수 있다.

## 두 번 잘못 짚었다

밀리는 값이 정확히 65px 이었다. 그리고 상단바 높이가 정확히 65px 이었다.

첫 번째 짐작은 sticky 헤더였다. 크롬은 포커스가 옮겨간 요소가 sticky 요소에 가려져 있으면
그것을 드러내려고 스크롤한다. 그럴듯했다. 상단바의 position 을 static 으로 바꿔 다시 쟀다.
**그대로 65px 씩 밀렸다.**

두 번째 짐작은 건너뛰기 링크였다. 라우팅 뒤 activeElement 를 찍어 보니 화면 밖에 숨겨 둔
skip link 가 잡혔고, 그 링크는 top: -100px 로 문서 위쪽에 놓여 있었다. 포커스가 거기로 가면
브라우저가 보이게 하려고 스크롤할 만하다. 숨기는 방식을 바꿔 다시 쟀다. **그대로였다.**

두 짐작 모두 65px 이라는 숫자 하나에 이야기를 맞춘 것이었다. 숫자가 맞아떨어지는 것은 단서지 증거가 아니다.

## 실제 원인은 브라우저의 스크롤 앵커링이었다

포기하고 스크롤을 옮기는 자바스크립트를 전부 가로챘다. window.scrollTo, Element.scrollIntoView,
scrollingElement.scrollTop 세터까지 감쌌다. **한 번도 안 불렸다.** 사람이 아니라 브라우저가 옮긴 것이다.

클릭 전후로 60ms 마다 값을 찍어 시간 순서를 봤다.

| 시각 | 문서 높이 | scrollY | 무슨 일 |
|---|---:|---:|---|
| 0ms | 13543 | 500 | 누르기 직전 |
| 24ms | 1187 | 287 | 본문이 사라져 높이가 무너지고 스크롤이 최대치로 깎였다 |
| 43ms | 2430 | 500 | 새 본문이 들어오고 스크롤이 되돌아왔다 |
| 112ms | 2424 | 435 | 여기서 65px 이 사라졌다 |

원인이 둘이었다.

**하나는 스크롤 앵커링이다.** 브라우저에는 보던 자리를 붙잡아 주는 기능이 있다. 화면 위쪽 내용의
높이가 바뀌면 보고 있던 요소가 제자리에 있도록 스크롤을 조용히 보정한다. 평소에는 고마운 기능이다.
그런데 이 화면은 탭을 바꿀 때 **문서를 통째로 갈아끼운다.** 붙잡을 것이 없는데도 브라우저는
무언가를 붙잡으려 하고, 그 결과가 매번 65px 이었다.

끄는 것은 CSS 한 줄인데, 어디에 주느냐가 중요했다.

~~~
.article        { overflow-anchor: none }   → 그대로 밀린다
.content-grid   { overflow-anchor: none }   → 그대로 밀린다
body            { overflow-anchor: none }   → 멈춘다
~~~

좁은 선택자로 주면 그 안이 앵커 후보에서 빠질 뿐, 브라우저가 **바깥에서 다른 앵커를 골라** 같은 일을 한다.
스크롤 컨테이너 쪽에서 꺼야 멈춘다.

**다른 하나는 불러오는 동안 본문을 지운 것이다.** 새 글을 가져오는 사이 본문 자리에 안내 문구만 두었는데,
그때 문서 높이가 13543 에서 1187 로 무너진다. 브라우저는 스크롤을 가능한 최대치까지 깎을 수밖에 없고,
본문이 돌아와도 깎인 값은 저절로 안 돌아온다. 앞 글을 그대로 두고 새 글로 갈아끼우게 바꿨다.
덤으로 탭을 누를 때마다 안내 문구가 한 번 깜빡이던 것도 없어졌다.

고친 뒤 같은 측정에서 scrollY 는 네 번을 눌러도 500 이었다.

## 코드 색칠 하나가 글 화면 JS 의 절반이었다

두 번째는 증상이 없었다. 그냥 운영 사이트가 실제로 받아 가는 파일을 크기 순으로 늘어놓아 봤다.

~~~
/_next/static/chunks/8467-….js   1,156,028B  (gzip 372kB)
~~~

이 하나가 글 화면이 받는 JS 의 대부분이었다. 안을 열어 보니 highlight.js 의 언어 정의가 통째로 들어 있었다.
통짜로 import 하면 **192개 언어**가 전부 실린다. Erlang, COBOL, Verilog 까지.

이 저장소의 글이 실제로 쓰는 언어를 세어 봤다.

| 표기 | 블록 수 |
|---|---:|
| mermaid (highlight.js 와 무관) | 35 |
| 표기 없음 | 24 |
| bash | 11 |
| text | 11 |
| python | 3 |
| sql | 2 |
| markdown | 2 |
| js, ts, java, json | 각 1 |

색칠에 쓰이는 언어는 여덟 종이다. 나머지 184개는 한 글자도 칠하지 않으면서 실려 왔다.
core 만 부르고 쓰는 언어만 등록하도록 바꿨다.

| | 이전 | 이후 |
|---|---:|---:|
| /wiki/[slug] First Load JS | 512kB | **228kB** |

## 색칠이 안 바뀐다는 것을 먼저 확인했다

언어를 줄이면 표기가 붙은 블록은 그대로다. 문제는 **표기 없는 24개 블록**이다.
그것들은 highlightAuto 로 가는데, 후보가 192개에서 15개로 줄면 다른 답이 나올 수 있다.

그래서 고치기 전에 확인했다. 위키 시드와 블로그 초안에서 코드 블록 92개를 전부 뽑아,
바꾸기 전 설정과 바꾼 뒤 설정으로 각각 렌더해 결과를 문자열로 비교했다.

~~~
블록 92 / 결과 동일 92 / 달라짐 0
~~~

표기 없는 24개도 전부 같았다. 그 블록들이 대부분 로그와 터미널 출력이라, 후보가 몇 개든
highlightAuto 가 같은 답을 내기 때문이다. **바뀌지 않는다는 것을 재고 나서 고쳤다.**

## 이미 되어 있던 것은 두고, 값이 있는 지적 하나만 고쳤다

재는 김에 나머지도 확인했다. 이미 되어 있던 것들이다.

| | |
|---|---|
| 웹폰트 | next/font/local 로 자체 호스팅한다. 외부 요청도, 글자가 늦게 바뀌는 것도 없다 |
| mermaid | 동적 import 라 다이어그램이 있는 글에서만 받는다 |
| 이미지 | loading 속성으로 지연 로딩한다 |
| 본문 | 첫 글은 서버에서 그려 HTML 에 담겨 온다 |

정적 분석 도구는 img 태그 세 곳을 지적했지만 고치지 않았다. 셋 다 컨테이너에 고정 크기가 이미 있어
이미지가 늦게 떠도 목록이 밀리지 않는다. **도구가 규칙을 보는 자리와 실제로 값이 나가는 자리는 다르다.**

대신 지적 중 실제로 값이 있는 것 하나는 고쳤다. 날짜 포매터를 호출할 때마다 새로 만들고 있었다.
만드는 값은 비싸고 쓰는 값은 싸다. 목록 한 화면이 날짜 수십 개를 그리므로 여덟 곳을 모듈에서 한 번만 만들게 했다.

## 한계 — 얼마나 빨라졌는지는 아직 말하지 못한다

Core Web Vitals 는 아직 재지 않았다. 여기 적은 것은 전부 특정 화면의 특정 값이고,
실제 사용자 환경에서 LCP 나 INP 가 얼마인지는 모른다. 그것을 재기 전까지 이 글은
**무엇을 얼마나 줄였다까지만 말할 수 있고, 그래서 얼마나 빨라졌다는 말은 하지 못한다.**

번들도 절반이 남았다. 228kB 중에는 여전히 마크다운 파서와 sanitizer 가 들어 있다.
탭을 바꿀 때 본문을 브라우저에서 그리기 때문인데, 이것을 서버로 옮기면 더 줄지만
탭 전환이 서버 왕복이 된다. 아직 그 값을 재 보지 않았다.
