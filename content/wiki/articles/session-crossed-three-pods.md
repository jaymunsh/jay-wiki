
- 파드를 상시 둘로 바꿨다. 그러면 「세션을 안 만든다」는 선택이 실제로 무엇을 피한 것인지 잴 수 있다.
- 잰 결과 둘이 예상과 달랐다 — 분배는 요청이 아니라 연결 단위였고, 세션은 내가 스위치를 켜기 전에 이미 Redis 에 있었다.
- 2026-08-19 운영에서 쟀다. BFF 경유 30회가 30:0 으로 한 파드에 몰렸고, 같은 쿠키가 파드 셋을 건너 hits 3·4·5 로 이어졌다.

이 사이트는 인증을 JWT 쿠키로 하고 세션을 안 만든다. 그래서 「세션 클러스터링이 필요 없다」고
말해 왔는데, 그 말은 **파드가 하나일 때는 확인할 방법이 없는 말**이다. 하나면 세션을 만들어도
안 깨진다. [파드를 상시 둘로 바꾸면서](/wiki/zero-downtime-on-one-machine) 비로소 잴 수 있게 됐다.

세션을 만드는 자리가 없어서 시연용 엔드포인트를 하나 뒀다. GET /api/session-demo 가 세션에
방문 수와 「처음 만난 파드」를 쌓고 그대로 돌려준다.

## 분배는 요청이 아니라 연결 단위다

먼저 로드밸런싱부터 봤다. 파드 둘에 같은 API 를 30번씩, 두 경로로 쳤다. 각 파드의
http_server_requests_seconds_count 증가분이다.

| 경로 | 파드 A | 파드 B |
|---|---:|---:|
| 공개 주소 → BFF → 백엔드, 30회 | 0 | 30 |
| 클러스터 안에서 매번 새 연결, 30회 | 9 | 21 |

**BFF 를 거친 30회가 전부 한 파드로 갔다.** Next.js 가 keep-alive 로 연결을 재사용하기 때문이다.
kube-proxy 는 연결이 만들어질 때 한 번 목적지를 고르고, 그 연결 위의 요청은 전부 같은 곳으로 간다.
매번 새 연결로 치면 9 대 21 로 갈린다 — 균등이 아니라 확률 분배다.

여기서 한 가지가 분명해진다. **이 구조에서는 세션이 있어도 잘 안 깨진다.** 브라우저가 백엔드에
직접 붙지 않고 BFF 한 곳을 거치니, 커넥션 풀이 sticky session 을 우연히 흉내 낸다.
안 깨지는 것이 아니라 **언제 깨질지 모르는 것**이다 — 연결이 끊기거나, web 파드가 늘거나,
배포로 파드가 갈리는 순간이 그때다.

## 같은 쿠키로 파드 셋을 쳤더니 세션이 이어졌다

공개 주소에서 쿠키를 하나 받고, 그 쿠키를 들고 클러스터 안에서 파드 셋의 IP 를 직접 쳤다.

~~~
파드 7wvvx  hits 3  firstPod twvhb  samePod false
파드 cxhtb  hits 4  firstPod twvhb  samePod false
파드 twvhb  hits 5  firstPod twvhb  samePod true
~~~

sessionId 가 셋 다 같고 hits 가 이어진다. **세션이 파드 밖에 있다는 뜻이다.** 그런데 이때
내가 만든 스위치(app.session.redis.enabled)는 꺼져 있었고, 응답의 store 필드는
「파드 메모리」라고 말하고 있었다.

## 스위치가 거짓말을 하고 있었다

Redis 를 열어 보니 세션 키가 그대로 있었다.

~~~
spring:session:sessions:bd5a7f3b-...
spring:session:sessions:3b2cbcab-...
~~~

원인은 의존성 하나다. **spring-session-data-redis 를 넣은 것만으로 Boot 자동설정이 세션
저장소를 Redis 로 옮긴다.** 내가 조건부로 붙이려던 @EnableRedisHttpSession 은 필요하지 않았다.
쿠키 이름이 JSESSIONID 에서 SESSION 으로 바뀐 것이 그 증거였는데, 그것도 나중에야 눈에 들어왔다.

**설정값을 읽어 「무엇을 쓰는지」를 보고하면 이런 거짓말이 난다.** 그래서 store 를 프로퍼티가
아니라 실제로 주입된 SessionRepository 빈으로 판정하게 고쳤다. 무엇을 쓰는지는 설정이 아니라
빈에게 묻는다.

## 끄고 다시 재니 그제서야 깨졌다

비교군을 만들려고 자동설정을 통째로 제외하고 다시 올렸다.

~~~
SPRING_AUTOCONFIGURE_EXCLUDE=org.springframework.boot.autoconfigure.session.SessionAutoConfiguration
~~~

쿠키가 JSESSIONID 로 돌아왔고, 같은 쿠키로 파드 둘을 치니 이렇게 나왔다.

| 친 파드 | 결과 |
|---|---|
| 세션을 모르는 파드 | **새 세션 발급. hits 1, sessionId 도 다른 값** |
| 세션을 가진 파드 | hits 3 으로 이어짐 |

이것이 세션 클러스터링이 푸는 문제의 실물이다. 로그인 상태라면 여기서 **로그아웃된 것처럼
보인다.** 잘못 짚기 쉬운 자리이기도 하다 — 사용자는 「가끔 로그인이 풀린다」고 말하고,
서버 로그에는 아무 오류가 없다.

## 그래서 무엇을 골랐나

세션 저장소는 Redis 로 둔다. 이미 떠 있는 것을 쓰고, 코드는 의존성 한 줄이다.
대신 대가를 적어 둔다.

| 방법 | 대가 |
|---|---|
| Traefik sticky cookie | 붙은 파드가 죽으면 그 사람들만 골라서 끊긴다. 부하도 안 고르게 갈린다 |
| Redis 세션 (고른 것) | **Redis 가 appendonly no · maxmemory 200mb · allkeys-lru 다.** 꽉 차면 세션이 evict 된다 |
| 세션을 안 만들기 | 서버가 기억할 것이 없다. 대신 발급한 토큰을 중간에 무효화하기 어렵다 |

지금 이 사이트의 인증은 여전히 JWT 쿠키이고 세션을 쓰지 않는다. 바뀐 것은 **「필요 없다」에서
「필요해지면 이미 받쳐져 있고, 그 대가가 무엇인지 안다」**로 옮겨 온 것이다.

**얼마나 안 쓰는지도 세어 봤다(2026-08-20).** 운영 Redis 의 키를 훑으니 전체 12개 중
spring:session 접두어가 **하나**였고, 그 하나가 방금 내가 시연 엔드포인트를 친 것이었다.
나머지는 blog:visitors 와 wiki:views 다.

~~~bash
kubectl -n data exec redis-master-0 -- redis-cli --scan --pattern "spring:session*"
~~~

즉 **실사용 세션은 0건**이다. 이 의존성은 지금 아무 요청도 안 받치고 있다. 그래도 두는 이유는
하나다 — 지우면 「파드를 건너 살아남는다」는 것을 다시 증명할 자리가 없어진다. **쓰이지 않는
것과 확인된 것은 다르고, 여기서는 확인된 쪽에 값을 매겼다.** 대가는 의존성 한 줄이다.

## 한계 — 파드가 둘인 이유는 세션이 아니다

- **파드가 둘인 이유는 세션이 아니다.** 순서가 반대다 — HPA 를 상시 2 로 올린 것은 자원 실측이
  근거였고, 세션은 그 전부터 이미 Redis 에 있었다. 파드가 둘이 되고 나서야 잴 자리가 생겼을 뿐이다
- sticky cookie 쪽은 재지 않았다. 표의 「대가」는 설정을 읽고 적은 것이지 실측이 아니다

### 더 재지 않기로 한 것 둘 (2026-08-20)

한때 여기 「다음에 잰다」로 둘이 있었다. 실사용이 0건이라는 것을 세고 나서 **안 하는 쪽으로
닫았다.**

- ~~세션에 로그인 상태를 실어 본 것은 아니다. 시연 엔드포인트의 방문 수 하나다~~
  → 로그인은 JWT 쿠키로 이미 돌고 있고, 그것을 세션으로 옮기는 것은 **없는 문제를 만들어
  푸는 일**이다. 지금 인증을 바꿀 이유가 없다
- ~~Redis 가 세션을 evict 하는 상황을 실제로 만들어 보지는 않았다. 200mb 를 채워야 나온다~~
  → 세션이 0건이라 채워도 evict 될 세션이 없다. 그럼 무엇이 밀리나 하고 나머지 키를 봤더니
  **잃을 것이 별로 없었다.** wiki:views 와 blog:visitors 는 데이터가 아니라 **중복 제거용
  표식**이다 — 조회수 본체는 PostgreSQL 에 있고, Redis 가 비면 같은 사람을 두 번 세지
  않으려던 창이 한 번 느슨해질 뿐이다. **밀려서 아픈 키가 지금은 없다.** 나중에 정말
  못 잃을 것을 Redis 에 넣게 되면 그때 다시 본다

**안 재기로 한 것을 「한계」에 남겨 두면 미룬 것처럼 읽힌다.** 미룬 것과 안 하기로 한 것은
다르고, 다른 자리에 적는다.
