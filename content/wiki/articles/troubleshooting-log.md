
- 이번 프로젝트에서 막힌 문제 12건이 기술 자체보다 상태, 환경, 경계에 대한 가정에서 나왔다는 회고다.
- 장애를 만나면 코드를 먼저 의심하지 않고 실행 중인 프로세스, 적용된 config, 열린 포트, 실제 이미지 태그와 적용된 Secret부터 보기로 판단했다.
- Flyway checksum mismatch부터 data·obs 네임스페이스 누락까지 실제로 겪은 문제 12건을 표로 놓고, 잘못된 가정이 상태·환경·경계 세 종류로 반복된다는 것을 확인했다.

이번 프로젝트에서 막힌 문제들은 대부분 기술 자체보다 상태를 잘못 가정한 데서 나왔다.

## 막힌 12건마다 잘못된 가정이 있었다

| 문제 | 잘못된 가정 | 교훈 |
|---|---|---|
| Flyway checksum mismatch | 적용된 migration을 고쳐도 된다고 봄 | 적용된 V 파일은 불변 |
| Spring DataSource 실패 | local profile이 켜졌다고 봄 | 실행 프로파일을 명시 |
| Next routes-manifest ENOENT | dev 서버가 켜진 채 .next 삭제 | 산출물 삭제 전 서버 종료 |
| Cloudflare Tunnel ingress | 대시보드에서 바뀐다고 봄 | locally configured tunnel은 config.yml 기준 |
| SSH miniPC 실패 | 같은 alias가 항상 같은 경로라고 봄 | 내부망과 외부망 경로를 분리해 이해 |
| OpenSearch nori | 기본 이미지에 analyzer가 있다고 봄 | plugin 포함 커스텀 이미지 필요 |
| pg_dump 버전 mismatch | 클라이언트가 서버보다 낮아도 된다고 봄 | 서버 major 이상 클라이언트 필요 |
| 시드 스크립트 ReferenceError | 문법 검사를 통과하면 실행된다고 봄 | 코드 안의 데이터는 코드 문법을 따른다 |
| 결제 서비스 지연 | 장애는 곧 연결 실패라고 봄 | 느린 의존은 죽은 의존보다 위험하다 |
| 결제 장애가 409로 응답 | 예외 클래스로 상태 코드를 정해도 된다고 봄 | 실패의 성격이 상태 코드를 정한다 |
| BFF 미처리 500 | 프록시는 요청만 옮긴다고 봄 | 경계는 실패도 옮긴다 |
| data, obs 네임스페이스 누락 | 잘 도는 클러스터는 재현 가능하다고 봄 | 손으로 만든 것은 매니페스트에 없다 |

## 세 가지 가정이 반복된다

위 표를 다시 보면 실패는 대체로 세 종류의 가정에서 나왔다.

| 가정 | 예 |
|---|---|
| 상태 | 지금 실행 중인 프로세스와 적용된 config 가 내가 편집한 파일과 같다 |
| 환경 | 로컬에서 되면 운영에서도 된다. 개발과 운영의 버전은 같다 |
| 경계 | 프록시, 예외 처리기, 네임스페이스 같은 경계는 그냥 통과시켜 준다 |

## 장애를 만나면 코드보다 상태를 먼저 본다

장애를 만났을 때 코드를 먼저 의심하지 않는다. 현재 실행 중인 프로세스, 적용된 config, 열린 포트,
실제 이미지 태그, 적용된 Secret을 먼저 본다.

## 문서에는 명령어만 적지 않는다

명령어만 적지 않는다. 증상, 원인, 해결, 재발 방지까지 같이 적어야 다음에 같은 문제를 빠르게 풀 수 있다.
