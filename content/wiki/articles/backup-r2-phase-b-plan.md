
- 로컬 PVC에만 있는 PostgreSQL 백업을 어디로, 어떻게 miniPC 밖에 복제할 것인가?
- 처음에 정한 목적지는 Cloudflare R2였지만 결제 수단 등록을 하지 않기로 하고 개발 머신으로 바꿔 실행했고, 2026-10-20에는 miniPC가 직접 Google Drive로 올리는 방식으로 다시 바꿨다.
- 2026-08-16에 첫 사본을 받아 그것만으로 복원 2.2초·오류 0을 확인했다. R2는 스크립트의 출력 경로만 바꾸면 되는 자리에 남겨 뒀다.

## 맥락 — 원본과 백업이 같은 디스크에 있다

PostgreSQL 백업 Phase A는 끝나 있다. pg_dump --format=custom으로 dump를 만들고, sha256을 생성하고,
임시 DB restore까지 스크립트 하나로 확인했다 — 그 기록은
[백업은 복원해보기 전까지 백업이 아니다](/wiki/postgres-backup-restore)에 있다.

다만 백업 파일은 miniPC 내부 PVC에 남는다. 실수로 데이터를 지웠을 때는 도움이 되지만, miniPC 디스크
자체가 죽으면 원본 DB와 백업이 같이 사라진다. 이 프로젝트는 단일 노드로 운영되므로 이 위험은 구조적으로
남아 있다.

## 후보와 기각 이유 — 새 인프라 0개인 개발 머신을 채택했다

| 후보 | 기각/채택 이유 |
|---|---|
| 개발 머신(맥북) 로컬 | **채택.** 계정도 토큰도 새 인프라도 0개다. miniPC 디스크 사망이라는 실제 위험을 막는다 |
| Cloudflare R2 | 보류. 용량은 문제가 아니다(30일치 72MB, 무료 한도 10GB의 0.7%). 걸린 것은 **결제 수단 등록** 하나였고, 지금 그것을 하지 않기로 했다 |
| AWS S3 | 기각. 새 클라우드 계정과 결제 경로가 추가로 필요하다 |
| Google Drive (rclone) | 기각. OAuth refresh token을 Secret에 넣어야 하고, 미검증 앱 토큰이 만료되면 백업이 **조용히 멈춘다.** 2.4MB를 옮기자고 질 짐이 아니다 |
| iCloud·Drive 동기 폴더 | 보류. 출력 경로만 바꾸면 언제든 켤 수 있다 |
| 다른 VPS로 rsync | 기각. 관리 대상 서버가 하나 더 늘어난다 |
| WAL 기반 PITR | 보류. 현재 규모에서는 하루 단위 dump와 수동 복구 리허설이 설명하기 쉽고 운영 복잡도도 낮다 |

## 결정 — 목적지를 R2에서 개발 머신으로 바꿨다

이 글은 원래 「목적지는 Cloudflare R2로 정했다」로 끝나 있었다. 실행하는 자리에서 바꿨다.
바꾼 이유는 기술이 아니라 **카드를 등록하지 않기로 한 것**이고, 그래서 R2가 막는 위험
(같은 장소의 화재·도난)은 지금도 안 막힌다. 그것까지 이 글에 적는다.

대신 **되돌리기 쉬운 모양으로 만들었다.** 사본을 만드는 스크립트는 파일 셋을 디렉터리에 만들 뿐이고,
그 디렉터리를 어디에 둘지는 부르는 쪽이 정한다. R2든 동기화 폴더든 **출력 경로만 바꾸면 된다.**

새 스케줄러도 만들지 않았다. 장치를 늘리면 그 장치의 실패를 감시할 장치가 또 필요해진다.
운영에 글을 쓰는 순간(반영)에 얹었다. 그 대가는 RPO가 시간이 아니라 행동이 된다는 것이고,
아래 「남은 한계」에 그대로 적었다.

| 대상 | 판단 | 이유 |
|---|---|---|
| PostgreSQL dump | 필수 | 위키 본문, revision, 게시판, 계정의 원본 |
| sha256 파일 | 필수 | 복구 전 무결성 확인 |
| Redis | 제외 | 캐시와 실시간 상태, 재생성 가능 |
| OpenSearch | 제외 | PostgreSQL에서 재색인 가능 |
| Kafka | 제외 | 데모 이벤트, 원본 데이터 아님 |
| MinIO wiki-assets | **필수로 바꿈** | 이미지 업로드가 켜져 있다. 지금 버킷에 사람이 올린 파일은 0개지만, 글 하나만 쓰면 재생성 불가능한 파일이 생긴다. 812K라 조건 분기보다 그냥 받는 쪽이 싸다 |
| Secret | 별도 | 지금은 k8s Secret과 로컬 env. 장기적으로 SOPS 후보 |

계획 단계의 그림은 PVC에서 R2로 가는 CronJob이었다. 실제로 선 것은 이 모양이다.

~~~mermaid
flowchart TB
    PG[(PostgreSQL)] --> DUMP[pg_dump CronJob 매일 03:17]
    DUMP --> PVC[(jaywiki-pg-backups PVC 7일)]
    SYNC[운영에 글을 반영하는 순간] --> PULL[pull-prod-backup.sh]
    PG --> PULL
    MINIO[(MinIO wiki-assets)] --> PULL
    PULL --> LOCAL[(개발 머신 사본 30일)]
    LOCAL --> DRILL[rehearse-local-restore.sh]
    DUMP --> ALERT[실패하면 텔레그램 45초]
~~~

목표로 잡았던 수치와 실제로 선 값을 나란히 둔다.

| 항목 | 계획 | 실제 |
|---|---|---|
| RPO | 하루 이내 | 위키·블로그는 반영 시점. **게시판·댓글은 마지막 반영 시점** |
| RTO | 수동 복구 30분 이내 | 복원 자체는 2.2초. 판단과 절차 시간이 나머지다 |
| miniPC 보관 | 7일 | 7일 |
| 밖 보관 | R2 30일 | 개발 머신 30일 (약 96MB) |
| 검증 | sha256 + 월 1회 리허설 | sha256 + pg_restore 목록 확인 + 사람이 부르는 리허설 |
| 알림 | 백업 실패, 복제 실패, 36시간 초과 | **백업 실패만.** 복제 실패와 낡음은 안 건다 |

마지막 줄이 이 결정의 값이자 대가다. 복제가 사람의 반영 행동에 붙어 있어서, 복제가 안 된 것을
기계가 알려 주지 않는다. 사본 디렉터리에 파일이 없다는 것 자체가 기록이라는 수준에서 멈췄다.

## 결과와 되돌리는 법 — 사본만으로 복원 오류 0을 확인했다

2026-08-16에 실행했다. 계획의 1~4번(R2 bucket·토큰·Secret·rclone CronJob)은 **하지 않았고**,
목적지를 바꾼 대신 5~8번에 해당하는 확인은 전부 했다.

| 확인 | 값 |
|---|---|
| 사본 받기 | 5.2초 (dump 2.4MB + sha256 + wiki-assets tar 812K) |
| 밖에 나온 사본만으로 복원 | 2.1~2.3초, 오류 0 |
| row 대조 | tb_article 70 · tb_revision 174 · tb_blog_post 18 · tb_post 100007 · tb_user 1 |
| 백업 실패 알림 | 일부러 실패시킨 Job → 텔레그램 45초 |

첫 리허설에서 오류 43건이 났고 전부 ALTER ... OWNER TO portfolio 였다. 임시 DB에 그 역할이
없어서다. 역할을 먼저 만드는 순서를 스크립트에 굳혔다.

되돌리는 법은 여전히 단순하다. **miniPC 쪽은 한 줄도 바뀌지 않았다** — 사본을 받는 동작은 전부
개발 머신에서 도는 읽기다. 스크립트를 지우고 호출 한 줄을 빼면 원래 상태다. 남는 것은 이미 받아 둔
파일뿐이고, 그것도 30일이면 스스로 지워진다.

## 남은 한계 — 같은 장소의 동시 손실은 못 막는다

**같은 장소의 동시 손실은 못 막는다.** 개발 머신과 miniPC가 한 집에 있어서 화재나 도난에는
둘 다 사라진다. 이것이 R2를 켰다면 사라졌을 위험이고, 카드를 등록하지 않는 대가로 남겨 둔 것이다.

**사본은 반영할 때만 늘어난다.** 게시판 글과 댓글은 반영과 무관하게 쌓이므로 개발 머신 사본은
그만큼 낡는다. 개발 머신이 오래 꺼져 있어도 마찬가지다.

**Secret은 여전히 백업 대상이 아니다.** 지금은 개발 머신의 로컬 파일 한 부뿐이다.
성격이 다른 문제(암호화와 보관 장소)라 이 결정에 섞지 않았다.

## 결말 — 2026-10-20, 사본은 miniPC 가 직접 Google Drive 로 보낸다

이 글의 결정은 그 뒤로 두 번 더 움직였다. 위 본문은 2026-08-16 시점 그대로 두고, 무엇이 바뀌었는지를 여기에 덧붙인다.

### 9월에 붙인 매일 사본은 41번 연속으로 시작도 못 했다

2026-09-10 에 「사본은 반영할 때만 늘어난다」는 한계를 메우려고 개발 머신에 매일 04:30 launchd 작업을 붙였다. run-offsite-backup.sh 가 DB 셋, MinIO 객체와 설정, 클러스터 설정을 끌어와 age 로 암호화해 두는 구성이었다. Secret 도 이때 처음 사본에 들어갔다. 설정하던 날 손으로 돌린 네 번은 모두 성공했다.

자동 실행은 한 번도 성공하지 못했다. macOS 개인정보 보호(TCC)가 launchd 의 /bin/bash 에 ~/Documents 접근을 주지 않아, 스크립트를 열기도 전에 Operation not permitted 로 끝났다(종료 코드 126). 9월 11일부터 10월 21일까지 41번 모두 그랬다.

실패 알림(osascript)과 last-attempt.json 기록은 스크립트 안에 있었다. 스크립트가 시작조차 못 하니 알림도 기록도 없었고, last-attempt.json 은 40일 동안 9월 10일의 success 를 가리켰다. 2026-10-19 에 다른 서버의 백업을 정리하다가 launchctl list 의 종료 코드를 보고서야 알았다.

### 백업은 서버에서 돌고, 끊기면 바깥이 알린다

고친 원칙은 둘이다. 첫째, 백업은 서버에서 돈다. 들고 다니고 덮여 있는 날이 있는 노트북이 켜져 있어야 도는 백업은 백업이 아니다. 둘째, 성공 보고가 끊기면 바깥이 알린다. 실패한 쪽 안에 있는 실패 알림은 같이 죽는다. 알림 경로에 쓰던 [클러스터 밖 판정자](/wiki/watchdog-outside-the-cluster)를 백업에도 건 것이다.

~~~mermaid
flowchart TB
    PG[(PostgreSQL 셋)] --> DUMP[pg_dump CronJob 매일 03:17]
    DUMP --> PVC[(jaywiki-pg-backups PVC 7일)]
    PVC --> TIMER[miniPC systemd 타이머 매일 05:00]
    MINIO[(MinIO 볼륨)] --> TIMER
    K8S[클러스터 설정 스냅숏] --> TIMER
    TIMER --> DRIVE[(Google Drive rclone crypt)]
    DRIVE --> PING[성공하면 healthchecks ping]
    PING --> HC[하루 2시간 넘게 끊기면 메일과 텔레그램]
~~~

| 항목 | 2026-08-16 | 2026-10-20 |
|---|---|---|
| 목적지 | 개발 머신 | Google Drive. 내용은 rclone crypt 로 암호화한다 |
| 누가 보내나 | 반영할 때 개발 머신이 끌어온다 | miniPC 의 root systemd 타이머가 직접 올린다 |
| 담는 것 | dump 와 wiki-assets | dump 셋, MinIO 볼륨 전체, Secret 을 포함한 클러스터 설정 |
| 보관 | 30일 | 매일 사본 3일, 매달 1일 사본은 계속 |
| 사본 쪽 알림 | 없음 | healthchecks jay-wiki-backup, 1일 + 2시간 침묵에서 울린다 |
| 같은 장소의 동시 손실 | 못 막는다 | 막는다 |

### Drive 를 기각했던 이유는 감시를 밖에 두면서 풀렸다

위 후보 표에서 Drive 를 기각한 이유는 「토큰이 만료되면 백업이 조용히 멈춘다」였다. 이번에는 그 「조용히」를 healthchecks 가 지운다. 토큰이 죽으면 ping 이 끊기고, 하루 두 시간 뒤 바깥이 알린다. 토큰은 k8s Secret 이 아니라 miniPC 의 /etc/leneu-backup 에 root 만 읽게 두었다.

같은 계정의 다른 서버가 이미 쓰던 rclone 설정을 복사해서, 새 계정도 결제 수단도 늘지 않았다. R2 를 막았던 카드 등록 문제도 여기서는 생기지 않는다.

### 사본만으로 되살아나는지 대조했다

2026-10-20 첫 업로드 뒤 Drive 에서 다시 받아 풀었다. dump 셋의 sha256 이 CronJob 이 남긴 원본 해시와 모두 같았고, MinIO 파일 205개와 클러스터 리소스 497개가 들어 있었다. 다음 날 05:09 에는 타이머가 스스로 돌아 37MB 를 올리고 ping 을 남겼다.

같은 날 Mac 의 launchd 작업은 내렸다. run-offsite-backup.sh 는 지우지 않고, 손으로 한 벌 받을 때만 쓴다.

### 남은 한계 — 공용 클라이언트와 공유한 토큰

- MinIO 볼륨은 쓰는 도중에 그대로 묶는다. 스냅샷이 아니고, 운영과 같은 MinIO 이미지로만 되살릴 수 있다
- RPO 는 하루다. 03:17 에 뜬 dump 를 05:00 에 올린다
- rclone 기본 클라이언트 ID 는 전 세계 사용자가 함께 쓴다. 붐비면 403 rateLimitExceeded 로 막히고, 2026-10-20 두 번째 수동 실행이 22분 재시도 끝에 30분 제한에 걸렸다. 자주 나면 자기 OAuth 클라이언트로 바꾼다
- Drive 토큰과 crypt 비밀번호를 다른 서버의 백업과 같이 쓴다. 한쪽 서버의 root 를 잃으면 다른 쪽 사본도 지울 수 있다
- 마지막 판정자는 healthchecks.io 무료 플랜 하나다
