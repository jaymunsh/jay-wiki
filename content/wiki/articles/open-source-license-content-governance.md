
- 폰트, 아이콘, 기술 로고, 의존성, 컨테이너와 위키 이미지가 어디서 왔고 어떤 조건으로 쓰는지 설명할 수 있는 상태를 어떻게 유지하는가?
- 폰트를 CDN 링크에서 저장소 자체 호스팅으로 바꾸는 순간 OFL 재배포 의무가 생기는 지점이라고 보고, 폰트 파일 옆에 라이선스 원문을 함께 두기로 판단했다.
- 폰트·아이콘·로고·패키지·컨테이너·위키 콘텐츠 여섯 대상을 표로 점검하고, Pretendard와 JetBrains Mono의 SIL OFL, Simple Icons의 공식 라이선스 문서를 직접 확인했다.

개인 포트폴리오이고 수익을 내지 않는다는 사실만으로 저작권 의무가 사라지지는 않는다.
jay-wiki는 코드 의존성뿐 아니라 폰트, 기술 로고, 컨테이너 이미지와 위키 첨부 이미지까지
**어디서 왔고 어떤 조건으로 사용하는지 설명할 수 있는 상태**를 목표로 한다.

이 글은 저장소를 기준으로 한 기술적 점검 기록이며 법률 자문은 아니다. 2026-07-15에 처음 점검했고, 이후
자체 호스팅으로 바뀐 폰트를 반영해 갱신했다.

## 무엇을 점검했는가

| 대상 | 현재 사용 방식 | 확인할 권리 |
|---|---|---|
| 웹 폰트 | Pretendard variable woff2와 JetBrains Mono woff2를 저장소에 포함해 자체 호스팅 | SIL OFL의 재배포 조건과 고지 의무 |
| UI 아이콘 | lucide-react 패키지를 앱에 포함 | ISC 라이선스 고지 |
| 기술 로고 | Simple Icons SVG를 MinIO에 저장해 기술 식별에 사용 | SVG 라이선스와 별개인 상표권 |
| 애플리케이션 패키지 | npm과 Python은 lockfile, Gradle은 Spring Boot BOM과 명시 버전으로 고정 | 직접·전이 의존성의 라이선스 |
| 컨테이너 | 앱 이미지와 PostgreSQL, Grafana, MinIO 등을 실행 | 이미지별 라이선스와 재배포 조건 |
| 위키 콘텐츠 | 직접 쓴 글, 화면 캡처와 업로드 이미지 | 작성자 권리, 인용 범위, 이미지 출처 |

## 폰트는 괜찮은가

실제로 내려받는 웹 폰트는 본문용 Pretendard와 코드용 JetBrains Mono 둘이다. 둘 다 SIL Open Font License로
배포하며 상업적 이용, 수정과 재배포를 허용한다고 명시한다.

처음에는 공식 문서가 안내하는 jsDelivr CDN 주소에 버전을 고정해 사용했다. 지금은 woff2 파일을
저장소에 넣고 Next.js의 local font로 자체 호스팅한다. 외부 CDN이 느려지거나 응답하지 않을 때 본문 글꼴이
fallback으로 흔들리는 것을 막기 위해서다.

이 변경은 편의 문제가 아니라 **라이선스 의무가 달라지는 지점**이다. CDN을 링크하는 것과 폰트 파일을
직접 배포하는 것은 다르다. OFL은 재배포 시 저작권 고지와 라이선스 원문을 함께 제공하도록 요구하므로,
폰트 파일 옆에 두 폰트의 라이선스 파일을 각각 같이 두었다. 폰트 이름을 바꾸거나 파생 폰트를 만들지 않고
원본 그대로 사용하므로 Reserved Font Name 조항에 걸리는 개명 의무는 발생하지 않는다.

**의무가 생기는 기준은 폰트 이름이 CSS에 적혀 있는지가 아니라 파일을 우리가 배포하는지다.**
CSS에 적힌 Apple SD Gothic Neo, Noto Sans KR, Menlo는 방문자의 장치에 이미 설치돼 있을 때 선택되는
fallback이라 재배포에 해당하지 않는다. 반대로 JetBrains Mono는 fallback 이름으로만 적혀 있다가
자체 호스팅으로 바뀌면서 Pretendard와 같은 고지 의무가 생겼다. 폰트를 하나 더 자체 호스팅할 때마다
라이선스 파일을 같이 넣는지 확인하는 일이 따라온다.

- [Pretendard 공식 문서와 라이선스](https://github.com/orioncactus/pretendard/blob/main/packages/pretendard/docs/en/README.md)
- [SIL Open Font License FAQ](https://software.sil.org/fonts/faq/)

## 라이브러리는 이름보다 배포 형태를 본다

Next.js, React, Spring Boot, FastAPI처럼 주요 직접 의존성은 대체로 MIT, Apache-2.0,
BSD 계열이다. 그러나 package.json 한 파일만 보고 전체를 단정할 수는 없다.

예를 들어 Next.js 이미지 처리 경로에는 LGPL인 libvips 바이너리가 선택적으로 포함될 수 있고,
브라우저 호환성 데이터에는 CC BY 조건이 붙을 수 있다. Grafana와 MinIO처럼 별도 서버로 실행하는
구성요소는 AGPL 계열 조건을 정확한 배포 버전과 함께 본다. 단순히 서비스를 내부에서
실행하는 경우와 바이너리를 수정하거나 이미지로 재배포하는 경우의 의무도 같지 않다.

따라서 이 프로젝트는 다음 세 층을 따로 기록한다.

1. 애플리케이션에 직접 추가한 패키지
2. lockfile과 빌드 결과에 들어온 전이 의존성
3. Kubernetes가 실행하는 외부 컨테이너와 직접 만든 컨테이너

보안 취약점 검사와 라이선스 검사는 목적이 다르다. npm audit이 통과해도 라이선스 검토가
끝난 것은 아니다.

## 기술 로고는 오픈소스 아이콘과 상표를 구분한다

오케스트레이션 맵은 Simple Icons에서 Cloudflare, GitHub, Kubernetes, PostgreSQL 등의 SVG를
받아 MinIO에 보관한다. Simple Icons의 SVG 데이터 라이선스와 해당 회사의 이름·로고에 대한
상표권은 별개다.

따라서 로고는 실제 사용 기술을 식별하는 크기와 문맥으로만 사용한다. 제휴나 공식 인증을
암시하지 않고, 임의로 형태를 왜곡하지 않으며, 각 브랜드의 사용 지침이 더 엄격하면 그 지침을
우선한다.

- [Simple Icons 라이선스](https://github.com/simple-icons/simple-icons/blob/develop/LICENSE.md)
- [Simple Icons 상표 면책 안내](https://github.com/simple-icons/simple-icons/blob/develop/DISCLAIMER.md)

## 글과 이미지는 출처를 수명주기에 포함한다

외부 문서는 원문 전체를 복제하지 않고 필요한 사실을 요약한 뒤 공식 링크와 확인일을 남긴다.
직접 촬영한 miniPC 사진과 직접 만든 다이어그램은 원본으로 관리한다. 제조사 제품 사진이나
다른 사람의 차트는 공개돼 있다는 이유만으로 다시 업로드하지 않는다.

위키 이미지 업로드 기능은 파일 형식, 크기, checksum과 MinIO 객체 수명주기를 관리하지만
권리까지 자동으로 검증하지는 못한다. 업로드 전 다음 정보를 함께 남기는 것을 운영 규칙으로 정했다.

| 필드 | 예시 |
|---|---|
| 제작자 | 본인 촬영, 직접 제작, 외부 저작자 |
| 원본 URL | 공식 문서나 원 게시물 |
| 라이선스·허가 | 직접 소유, CC BY 4.0, 사용 허가 |
| 확인일 | 2026-07-15 |
| 편집 내역 | crop, annotation, 색상 보정 |

AI로 생성한 자산도 도구, 생성일, prompt 요약과 후편집 여부를 기록한다. 특정 브랜드나 인물을
오인시키는 결과물은 생성 자산이라는 이유만으로 안전하다고 보지 않는다.

## 의존성은 여섯 단계를 거쳐 들여온다

1. 추가하려는 패키지와 대체재의 공식 라이선스를 확인한다.
2. 직접 의존성 버전과 다운로드 출처를 lockfile 또는 manifest에 고정한다.
3. 빌드 이미지별 SBOM을 SPDX나 CycloneDX 형식으로 생성한다.
4. 라이선스 원문 보존, 저작권 고지, 소스 제공 등 배포 조건을 release checklist에 연결한다.
5. 로고와 이미지에는 출처·라이선스·상표 사용 목적을 기록한다.
6. 주요 버전 변경과 분기별 점검 때 목록을 다시 생성해 차이를 검토한다.

## 현재 결론 — 막을 제한은 없지만 검토 완료는 아니다

현재 폰트와 주요 UI 라이브러리에서 사이트 운영을 막을 명백한 사용 제한은 발견하지 못했다.
다만 이것을 전체 법적 검토 완료로 표현해서는 안 된다.

- 저장소 자체에는 아직 LICENSE가 없다. 공개 소스의 재사용 허용 범위를 먼저 결정해야 한다.
- THIRD_PARTY_NOTICES는 현재 직접 사용 항목 중심의 초안이며 자동 생성된 완전한 SBOM이 아니다.
- 기술 로고별 상표 지침과 실제 배포 컨테이너 tag를 정기적으로 확인해야 한다.
- 위키 이미지 metadata에 출처와 라이선스 필드를 넣는 후속 개선이 필요하다.

중요한 것은 라이선스 이름을 외우는 일이 아니라, **새 요소를 추가할 때 출처와 조건을 함께
검토하고 배포 결과에서 다시 확인할 수 있는 절차**를 만드는 일이다.
