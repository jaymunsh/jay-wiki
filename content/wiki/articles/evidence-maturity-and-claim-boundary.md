
- 시뮬레이션, 로컬 실측과 운영 검증을 같은 성과처럼 말하지 않기 위한 증거 수준과 표현의 기준이다.
- 주장의 크기를 증거의 크기에 맞추기로 하고, 설계부터 반복 운영 증거까지 일곱 수준마다 쓸 수 있는 표현과 부족한 표현을 나눴다.
- 10만 건 Excel 실측, 결정론적 시나리오 모델, GitOps 동기화 같은 실제 사례를 수준별로 재분류했고, GitOps 동기화는 배포 workflow가 backup과 공개 smoke까지 실제로 돈 뒤에야 로컬 구현에서 운영 검증으로 올렸다.

포트폴리오에는 구현한 화면, 정책을 비교하는 시나리오, 실제 데이터 처리와 운영 지표가 함께 있다. 모두 의미가 있지만 같은 증거는 아니다.
고정 숫자를 보여주는 시뮬레이션을 실제 부하 시험처럼 설명하거나, 로컬 MVP를 운영 서비스처럼 쓰면 문서 전체의 신뢰도가 낮아진다.
그래서 기능을 적게 보이게 만드는 것이 아니라, **주장의 크기를 증거의 크기에 맞추는 기준**을 만들었다.

## 증거를 일곱 수준으로 나누고 표현을 갈랐다

| 수준 | 의미 | 사용할 수 있는 표현 | 부족한 표현 |
|---|---|---|---|
| 설계·계획 | 구조와 완료 조건을 정함 | 설계했다, 검토 중이다 | 구축했다, 검증했다 |
| 결정론적 모델 | 같은 입력에 정책 차이를 재현 | 정책 결과를 비교한다 | 실제 성능이 향상됐다 |
| Mock 연동 | API 계약과 UI 흐름을 확인 | 요청·응답 흐름을 구현했다 | 외부 provider 장애를 검증했다 |
| 로컬 구현 | 실제 코드와 로컬 저장소로 동작 | 로컬에서 저장·복구를 확인했다 | 운영 완료, 대규모 처리 |
| 제한된 benchmark | 환경·입력·반복 횟수를 고정해 측정 | 이 조건에서 수치를 측정했다 | 항상 빠르다, 일반적으로 우수하다 |
| 운영 검증 | 배포 환경과 공개 경로에서 확인 | 운영에서 SHA·HTTP·지표를 확인했다 | 고가용성·대규모 운영을 보장한다 |
| 반복 운영 증거 | 시간에 걸쳐 장애·복구·회전을 반복 | 운영 절차의 반복 가능성을 확인했다 | 모든 장애에 안전하다 |

## 이 프로젝트의 사례를 수준별로 재분류했다

### 도메인 시나리오

쿠폰 동시성, 트래픽 폭주와 이미지 최적화 일부는 고정 입력으로 정책 차이를 보여주는 결정론적 모델이다. 실행 이력을 PostgreSQL에 저장해도
실제 수만 개 동시 요청이나 image decoder를 사용한 benchmark가 되지는 않는다. 화면과 글에 정책 모델임을 표시하고 실제 검증 조건을 남긴다.

### 대용량 Excel

Excel 사례는 10만 건 PostgreSQL 데이터를 fetch size와 SXSSFWorkbook으로 실제 파일 생성했다. 따라서 단순 모델보다 증거 수준이 높다.
하지만 단일 miniPC의 한 번 실행 결과를 모든 운영 환경의 처리량으로 일반화하지 않고 row 수, 파일 크기와 실행 환경을 함께 쓴다.

### 로컬 LLM runtime 비교

같은 model family라도 quantization과 runtime이 완전히 같지 않다. 그래서 승자를 선언하기보다 hardware, version, prompt, thinking, cache miss·hit,
warmup과 반복 횟수를 공개하고 TTFT와 token/s, 정확도 관찰을 분리했다. raw JSON과 checksum을 함께 제공하지만 공식 benchmark라고 주장하지 않는다.

### GitOps 콘텐츠 동기화

로컬에서는 token 오류 404, 정상 upsert, 관리자 로그인 없는 복구와 no-op을 확인했고, 그때는 로컬 구현 완료로만 기록했다.
2026-07-22에 배포 workflow에 backup → content sync → 공개 smoke가 들어가 운영에서 실제로 돈 뒤에야 운영 검증으로 올렸다.
push와 코드 존재만으로 운영 사실을 만들지 않는다는 규칙은 지금도 같다 — 예를 들어 배포 롤백은 스크립트와 자동 복구
경로가 있지만 실제로 되돌린 기록이 없어, rehearsed가 아니라 구현으로만 기록한다.

## 숫자에는 조건을 붙인다

성능 수치를 쓸 때 최소한 다음 정보를 함께 남긴다.

- hardware와 OS, runtime·library version
- 데이터 크기와 입력 생성 방식
- cold·warm, cache hit·miss 조건
- warmup과 반복 횟수, 순차·동시 실행 여부
- 평균만이 아니라 분산이나 p95 등 목적에 맞는 통계
- 오류·중단·제외한 표본과 측정 도구의 한계

조건을 복원할 수 없는 오래된 수치는 참고 관찰로 낮추고, 정밀한 비교처럼 다시 사용하지 않는다.

## 상태 문구를 완료 조건과 연결한다

| 상태 | 완료 조건 |
|---|---|
| planned | 요구와 검증 방법이 문서에 있음 |
| implemented locally | 코드·테스트와 로컬 실행 증거가 있음 |
| deployed | immutable image와 rollout이 확인됨 |
| verified | 공개 경로 또는 목표 환경에서 핵심 동작을 확인함 |
| rehearsed | 실패·복구나 회전을 의도적으로 실행하고 기록함 |

문서의 현재 상태가 바뀌면 요약, 본문, current project status와 진행상황을 함께 갱신한다. 오래된 “예정”이나 검증하지 않은 “완료”가 남지 않게
dry-run, export와 공개 HTTP를 마지막에 다시 확인한다.

## 이 기준은 방어 규칙이 아니라 개발 backlog 다

확실한 증거가 없는 수치를 크게 말할 필요는 없다. 어떤 것은 실제 운영했고, 어떤 것은 제한된 실험이며, 무엇을 더 측정하면 판단이 달라질 수 있는지
구분하는 태도 자체가 운영 판단의 증거다.

이 기준은 포트폴리오를 방어적으로 쓰기 위한 규칙이 아니다. 다음 실험에서 무엇을 추가해야 한 단계 높은 주장을 할 수 있는지 보여주는 개발 backlog다.
