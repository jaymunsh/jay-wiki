
- 문서를 오갈 때 선택 상태가 흔들리지 않고 좁은 화면에서도 본문과 다이어그램이 읽히게 하려면 무엇을 고쳐야 했나?
- 탐색 상태를 컴포넌트가 아니라 URL로 올려 /wiki/[slug]를 정본 경로로 삼고, 늦게 끝난 요청은 정리 함수로 상태 반영을 막으며, 넓은 콘텐츠는 페이지가 아니라 자기 프레임 안에서만 스크롤하게 만들기로 판단했다.
- 390px, 768px, 1280px에서 페이지 가로 overflow가 없고 390px의 Mermaid가 프레임 안에서만 스크롤하며 딥링크가 올바른 탭과 문서를 여는 것을 확인했다.

문서가 많아질수록 첫 화면의 화려함보다, 원하는 글을 빠르게 열고 다시 찾아갈 수 있는지가 더 중요해진다.

이번 개선은 네트워크 전송량을 줄였다고 주장하는 작업이 아니다. 사용자가 여러 문서를 오가도 선택 상태가
흔들리지 않고, 좁은 화면에서도 본문과 다이어그램을 읽을 수 있게 만든 탐색 안정성 작업이다.

## 문제가 된 장면 — 선택과 화면이 어긋나고 폭이 밀렸다

| 장면 | 이전 위험 | 사용자가 느끼는 문제 |
|---|---|---|
| 문서 A를 누른 뒤 곧바로 B를 누름 | 늦게 끝난 A 요청이 B보다 나중에 화면을 덮을 수 있음 | 선택한 글과 본문이 다르게 보임 |
| 새로고침 또는 링크 공유 | 탭 내부 상태만 알고 URL은 모름 | 같은 글을 다시 열 수 없음 |
| 390px 화면의 Mermaid | SVG가 페이지 폭을 밀어냄 | 페이지 전체가 가로로 움직임 |
| 긴 탭과 표 | 화면 폭보다 넓은 콘텐츠가 바깥으로 나감 | 문서 레이아웃이 흔들림 |

## 탐색 상태를 URL로 올렸다

처음에는 탭과 문서 선택이 컴포넌트 상태에만 있었다. 화면은 정상으로 보여도 새로고침하면 첫 문서로
돌아갔고, 링크를 공유해도 상대는 다른 글을 봤다. 그래서 선택을 URL로 올렸다.

이 결정은 두 단계로 진행됐다. 먼저 article query parameter로 현재 문서를 표현했고, 이후 문서마다
고유한 경로를 갖도록 /wiki/[slug]를 정본 URL로 바꿨다. query parameter는 문서가 홈의 부속 상태처럼
보였지만, 경로는 문서 자체가 독립된 리소스임을 드러낸다.

| 시점 | 문서 URL | 한계 또는 이점 |
|---|---|---|
| 초기 | 컴포넌트 상태만 | 새로고침과 공유에서 선택이 사라짐 |
| 1차 | 홈 경로에 article query parameter | 공유와 뒤로 가기는 가능하나 문서가 홈의 부속으로 보임 |
| 현재 | /wiki/[slug] | 문서마다 고유 경로. 탭·문서 선택은 이 경로를 push한다 |

이미 공유된 옛 링크를 깨뜨리지 않는 것도 조건이었다. 그래서 홈으로 들어온 article query parameter는
같은 문서의 정본 경로로 permanent redirect한다. 주소 체계를 바꾸되 바깥에 나가 있는 링크는 살려 둔다.

선택 직후에는 화면 상태도 바로 바꾸고, 서버에서 받은 초기 문서는 다시 내려받지 않는다. 이 방식은 사용자가
클릭했을 때의 반응을 유지하면서 직접 링크의 첫 화면도 안정적으로 만든다.

## 늦게 도착한 요청이 화면을 덮지 못하게 했다

문서를 가져오는 effect에 정리 함수를 두어, 더 최신 선택이 생긴 뒤 끝난 이전 요청은 상태를 바꾸지 못하게 했다.
실패한 요청도 현재 선택과 일치할 때만 화면에 반영한다.

본문 렌더링은 메모화해 탭 주변 상태가 바뀌어도 이미 그려진 Mermaid를 불필요하게 다시 초기화하지 않는다.
여기서의 성과는 벤치마크 수치가 아니라, 빠른 연속 클릭에도 마지막 선택이 화면의 진실로 남는다는 동작 보장이다.

다만 ignore flag는 늦은 응답의 **상태 반영만 차단**한다. 이미 시작한 HTTP 요청 자체를 취소하지는 않으므로,
요청 비용은 그대로 남는다. AbortController나 경로 prefetch는 아직 적용하지 않았다.

## 넓은 콘텐츠의 책임을 컴포넌트 안으로 옮겼다

모바일에서 모든 것을 축소하면 기술 다이어그램의 라벨을 읽을 수 없다. 그래서 페이지 전체를 가로로 밀지 않고,
넓어야 하는 요소만 자신의 프레임에서 가로 스크롤한다.

| 요소 | 처리 | 이유 |
|---|---|---|
| 1차 탭 | 탭 레일 내부 스크롤 | 긴 카테고리 이름을 자르지 않는다 |
| 표 | 표 컨테이너 내부 스크롤 | 열의 의미를 유지한다 |
| Mermaid | 읽을 수 있는 최소 SVG 폭과 다이어그램 내부 스크롤 | 라벨을 축소해 흐리게 만들지 않는다 |
| 본문 | 줄바꿈과 폭 제한 | 페이지 자체의 가로 overflow를 막는다 |

## 390px, 768px, 1280px에서 눈으로 검증했다

- 390px, 768px, 1280px에서 페이지 가로 overflow가 없는지 확인했다.
- 390px에서 Mermaid의 최소 SVG 폭은 유지하되 다이어그램 프레임 안에서만 가로 스크롤하는지 확인했다.
- 탭은 좁은 화면에서 스크롤할 수 있고, 문서 제목과 한글 타임스탬프가 잘리지 않는지 확인했다.
- 딥링크가 올바른 활성 탭과 문서를 선택하고, Mermaid 오류 문구가 보이지 않는지 확인했다.

## 이 작업은 CSS가 아니라 탐색 계약을 고친 것이다

이 개선은 반응형 CSS를 덧붙인 작업이 아니다. URL, 비동기 요청, 렌더링 비용, 화면 폭의 책임을 각각 분리해,
운영 문서가 데스크톱과 모바일에서 같은 탐색 계약을 지키게 만든 작업이다.

아직 Lighthouse 기반 속도 점수나 대규모 사용자 데이터는 없다. 다음 성능 작업은 effect 기반 fetch와 상태 파생을
정리하고, 실제 배포 환경에서 Web Vitals와 문서 전환 지표를 측정하는 것이다.
