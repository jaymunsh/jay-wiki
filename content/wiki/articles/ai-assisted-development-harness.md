
- AI 에이전트를 제품 기능이 아니라 개발 도구로 쓰면서 결과를 어떤 규칙과 증거로 통제했는가?
- 조사, 구현, 테스트와 브라우저 QA는 AI에 맡기되 아키텍처, 보안, 디자인, 운영 배포처럼 되돌리기 어려운 결정의 소유자는 사람으로 유지하기로 판단했다.
- 테스트 통과만으로 완료로 보지 않고 실제 브라우저 확인과 GitHub Actions, image SHA, Kubernetes 상태로 운영 반영을 다시 확인했으며, 가독성이 떨어진 시안은 Git commit 기준으로 롤백했다.

이 글은 jay-wiki에 AI 제품 기능이 구현됐다고 주장하지 않는다. Claude와 Codex 같은 AI 에이전트를
개발 도구로 사용하면서, 결과를 어떤 규칙과 증거로 통제했는지를 정리한다.

## 맥락 유지 비용이 커서 조사와 구현을 AI에 맡겼다

jay-wiki는 Next.js, Spring Boot, FastAPI, PostgreSQL, Redis, Kafka, OpenSearch, k3s와 관측 도구를 함께 다룬다.
구현뿐 아니라 배포, 운영 확인과 문서화까지 반복해야 하므로 긴 작업의 맥락을 유지하는 비용이 컸다.

AI 에이전트에는 기존 코드와 운영 상태 조사, 변경 범위 정리, 코드와 테스트 작성, 브라우저 및 운영 환경 검증,
변경 이유 문서화를 맡겼다. 아키텍처 우선순위, 공개할 운영 정보의 범위, 디자인 승인, 비밀번호와 배포 같은
결정은 사람이 유지했다.

## 요청 하나를 여덟 단계 순서로 반복했다

한 번의 요청을 바로 코드 변경으로 끝내지 않고 다음 순서를 반복했다.

1. 저장소와 현재 실행 상태를 확인한다.
2. 구현 사실과 계획을 구분한다.
3. 변경 범위를 작게 나누고 롤백 기준을 만든다.
4. 코드와 직접 관련된 테스트를 함께 수정한다.
5. 타입 검사, 테스트와 production build를 실행한다.
6. UI는 실제 브라우저에서 desktop과 mobile을 확인한다.
7. miniPC 반영은 GitHub Actions, image SHA와 Kubernetes 상태로 다시 확인한다.
8. 결정과 실패를 상태 문서, 진행 기록과 위키에 남긴다.

테스트 통과는 완료의 한 조건일 뿐이다. 화면이 의도와 다르거나 운영 상태가 검증되지 않으면 완료로 보지 않았다.

## 되돌리기 어려운 결정은 사람이 소유했다

| 영역 | 사람이 결정한 내용 |
|---|---|
| 제품 경계 | 무엇을 실제 기능으로 만들고 무엇을 로드맵에 둘지 |
| 아키텍처 | Next.js BFF, Spring 내부 서비스, PostgreSQL Source of Truth 같은 핵심 선택 |
| 보안 | 외부에 공개할 지표, 관리자 인증과 Secret 처리 범위 |
| 디자인 | 정보 구조, 시각적 우선순위, 유지하거나 롤백할 시안 |
| 운영 | 운영 배포 시점, 데이터 시드, 비밀번호와 TOTP 등록 |

AI는 선택지를 만들고 근거를 조사했지만, 되돌리기 어려운 결정의 소유자는 사람이었다.

## 틀린 결과를 작게 되돌릴 수 있는 구조를 유지했다

- 카테고리 정보를 한 화면에 과도하게 넣어 가독성이 떨어진 시안을 Git commit 기준으로 롤백했다.
- 로컬과 운영 화면이 달라진 문제를 CSS 오류로 단정하지 않고 Next.js 배포 버전 혼합까지 조사했다.
- HPA의 잦은 확장을 트래픽 추측으로 고치지 않고 Prometheus CPU 분포와 resource request를 비교했다.
- 문서 seed 실패를 문법 검사 통과로 끝내지 않고 실제 실행 경로와 입력 제약을 추가했다.

중요한 것은 AI가 항상 맞았다는 사실이 아니라, 틀린 결과를 발견하고 작게 되돌릴 수 있는 구조를 유지한 것이다.

## 프로젝트 기억은 대화가 아니라 문서와 Git에 뒀다

대화 기록만을 프로젝트 기억으로 사용하지 않았다.

| 기준 자료 | 역할 |
|---|---|
| docs/current-project-status.md | 현재 구현 및 운영 상태 |
| docs/wiki-editorial-plan.md | 발행할 문서와 근거 |
| docs/interview/ | 면접 설명을 위한 선택과 증거 |
| 진행상황.md | 시간순 변경과 검증 기록 |
| posts/jay-wiki | 운영 DB 문서의 Markdown snapshot |
| Git commit | 코드와 문서 변경의 rollback 경계 |

새 세션은 이 자료를 기준으로 현재 상태를 다시 확인한다. 대화 내용과 코드가 다르면 코드, 테스트와 운영 증거를 우선한다.

## 한계 — 생산성 향상 수치는 주장하지 않는다

- AI 에이전트가 생성한 모든 판단을 자동으로 평가하지는 못한다.
- 시각적 완성도와 문서의 설득력은 여전히 사람의 검토가 필요하다.
- 사용량, 시간 절감과 결함률을 체계적으로 측정하지 않아 생산성 향상 수치를 주장하지 않는다.

## 결론 — AI 활용은 기능이 아니라 개발 방식이다

jay-wiki에서 AI 활용은 제품 기능이 아니라 개발 방식이다. AI 에이전트를 코드 생성기로만 사용하지 않고 조사, 구현, 테스트, 브라우저 QA, 운영 검증과 문서화를 연결하는
하네스 안에서 사용했다. 최종 판단과 운영 승인은 사람이 맡고, 결과는 테스트와 실행 증거, Git 이력으로 남겼다.
