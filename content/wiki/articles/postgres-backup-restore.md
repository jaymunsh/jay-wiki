
- PostgreSQL 백업을 매일 만들고, 그 파일이 정말 복원되는지, 그 기계가 죽어도 남는지 어떻게 확인하나?
- 백업 대상은 재생성 불가능한 것만으로 좁혔고(PostgreSQL과 MinIO 이미지 버킷), 사본을 운영에 글을 반영하는 순간마다 개발 머신으로 내보내기로 했다.
- 밖으로 나온 사본만으로 복원이 2.2초에 오류 0으로 끝났고(tb_article 70·tb_post 100007), 백업 실패 알림은 일부러 실패시킨 Job으로 45초 만에 텔레그램에 도착하는 것을 확인했다.

백업 파일이 생겼다는 사실만으로는 충분하지 않다.

정말 복구할 수 있는지 확인해야 백업이라고 말할 수 있다.

## 백업 대상은 재생성 불가능한 것으로 좁혔다

| 대상 | 결정 | 이유 |
|---|---|---|
| PostgreSQL | 백업 필수 | 위키, 게시판, 계정, revision의 원본 |
| Redis | 제외 | 캐시와 일시 상태 중심 |
| OpenSearch | 제외 | PostgreSQL에서 재색인 가능 |
| GitHub | 코드 백업 | repo가 원본 |

## 처음에는 pg_dump 클라이언트 버전에 막혔다

처음에는 pg_dump 16 클라이언트로 PostgreSQL 18.4 서버를 dump하려다 실패했다.
pg_dump 는 서버보다 낮은 major 버전으로는 덤프할 수 없다.

클라이언트를 postgres:18-alpine 이미지로 올려 서버 버전에 맞췄다.

그런데 이 사건에는 뒷이야기가 있다. 로컬 개발용 docker-compose 는 그대로 postgres 16 이었고,
주석에는 miniPC 와 동일 메이저 버전을 맞춰 로컬에서 되면 prod 에서도 된다고 적혀 있었다.
같은 버전 불일치가 백업 이미지에서는 드러났지만 개발 환경에는 남아 있었다.
지금은 로컬도 18 로 올렸다.

**교훈**: 버전 불일치를 한 곳에서 고친 뒤, 같은 불일치가 다른 곳에 남아 있는지 찾아 로컬 개발 환경도 18 로 함께 올렸다.

## 복원을 명령 하나로 만들었다

복원 절차가 문서에만 있으면, 급할 때 그 문서를 읽을 사람은 없다.
그래서 scripts/rehearse-postgres-restore.sh 가 무결성 검증부터 임시 DB 복원과 정리까지 한 번에 처리한다.

이 리허설에서 지킨 규칙은 두 가지다. **원본 DB 는 읽기만 한다.** 복원은 항상 timestamp 가 붙은 별도
임시 DB 로만 하고, 끝나면 지운다. 그리고 **성공 판정을 pg_restore 의 종료 코드에 맡기지 않는다.**
핵심 테이블의 row count 를 원본과 비교해 하나라도 다르면 실패로 끝낸다.

각 단계와 왜 row count 를 비교하는지는
[백업 파일이 아니라 복원 결과를 확인하는 방법](/wiki/postgres-restore-drill-1)에 자세히 적었다.
이 글은 무엇을 백업 대상으로 정했고 어디까지가 아직 안전하지 않은지에 집중한다.

## 박스 밖으로 내보냈다

이 글은 오래 「복원은 해봤고, 박스 밖으로 내보내는 일이 남았다」로 끝나 있었다.
2026-08-16 에 그 문장을 지웠다.

백업 PVC 는 애플리케이션과 **같은 miniPC 디스크** 위에 있다. 실수로 지운 데이터는 되살리지만
디스크가 죽으면 백업도 함께 죽는다. 그래서 사본을 개발 머신으로 한 벌 내보낸다.

**새 스케줄러를 만들지 않았다.** 장치를 늘리면 그 장치가 죽은 것을 감시할 장치가 또 필요해진다.
대신 이미 코드에 있던 「운영에 글을 쓰는 순간」에 얹었다 — 반영 직전 운영 글 사본을 받는
snapshotProduction 이 그 자리다. 배포는 miniPC 러너에서 돌아 개발 머신에 아무것도 안 남기므로
배포 후 한 번은 사람이 같은 스크립트를 부른다.

| 받는 것 | 크기 |
|---|---|
| PostgreSQL dump (custom format) | 2.4MB (DB 88MB) |
| sha256 | 81B |
| MinIO wiki-assets tar | 812K |

한 벌 받는 데 5.2초다. 30일 보관하면 약 96MB 다.

## 되살아나는 것까지 확인했다

밖으로 나온 사본만으로 miniPC 없이 되살아나는지 봐야 의미가 있다.
scripts/rehearse-local-restore.sh 가 docker 임시 PostgreSQL 에 부어 row 수를 확인하고 지운다.

| | |
|---|---|
| 복원 시간 | 2.1~2.3초, 오류 0 |
| tb_article | 70 |
| tb_revision | 174 |
| tb_blog_post | 18 |
| tb_post | 100007 |
| tb_user | 1 |

**첫 리허설은 오류 43건으로 끝났다.** 전부 ALTER ... OWNER TO portfolio 였고, 임시 DB 에
portfolio 역할이 없어서였다. 데이터는 다 들어갔지만 되살아난 것과 깨끗하게 되살아난 것은 다르다 —
진짜 사고 때 저 43줄을 보면서 이게 정상인지 판단해야 했을 것이다. 역할을 먼저 만드는 순서를
스크립트에 굳혔다. 리허설은 이런 것을 잡으려고 한다.

## 실패를 알아채는지도 일부러 실패시켜 봤다

백업이 조용히 멈추면 사본이 있어도 소용없다. JaywikiBackupJobFailed 규칙은 있었지만
**한 번도 울린 적이 없었다.** 즉시 실패하는 Job 을 data 네임스페이스에 띄워 경로 전체를 쟀다.

| 시각 | |
|---|---|
| 19:51:21 | Job 실패 |
| 19:52:02 | Prometheus 규칙 firing (41초) |
| 19:52 | 텔레그램 도착 (45초) |
| 19:57 | Job 삭제 후 해제. 해제 통은 오지 않았다 |

규칙 파일에 쓴 한글 문구가 Alertmanager 템플릿을 타고 그대로 도착하는 것도 이때 처음 확인했다.
해제 통이 안 오는 것은 send_resolved 를 false 로 둔 설계대로다.

## R2 복제와 PITR 은 알고도 하지 않았다

| 안 한 것 | 왜 |
|---|---|
| Cloudflare R2 외부 복제 | 결제 수단 등록이 필요하다. 스크립트가 목적지만 바꾸면 되게 짜 뒀다 |
| 자동 스케줄 복제 | 감시할 장치가 하나 더 생긴다. 반영 시점으로 갈음하고 한계를 적는다 |
| WAL 기반 PITR | 하루 단위 dump 로 충분한 규모다 |
| Redis·OpenSearch·Kafka | 재생성된다. 백업하면 복구 시간만 늘어난다 |
| Prometheus·Loki·Tempo | 되살릴 수 없지만 관측 데이터다. 잃어도 서비스가 안 깨진다 |

## 남은 한계 — 사본은 반영할 때만 늘어난다

**사본은 반영할 때만 늘어난다.** 위키·블로그는 반영이 곧 변경이라 잘 맞지만, 게시판 글과 댓글은
반영과 무관하게 늘어나므로 개발 머신 사본은 마지막 반영 시점만큼 낡는다. 그쪽은 하루 한 번 도는
CronJob 이 잡고, 그것은 miniPC 안에 있다.

| 데이터 | miniPC 안 | 개발 머신 사본 |
|---|---|---|
| 위키·블로그 본문 | 24시간 | 마지막 반영 시점 (사실상 같다) |
| 게시판·댓글·계정 | 24시간 | 마지막 반영 시점. 며칠일 수 있다 |

그리고 개발 머신과 miniPC 는 같은 장소에 있다. 화재나 도난은 못 막는다. 그것까지 막으려면
목적지를 오브젝트 스토리지로 바꿔야 하고, 그 판단은
[백업을 miniPC 밖으로 복제하는 계획](/wiki/backup-r2-phase-b-plan)에 적었다.

wiki-assets tar 는 파일 그대로가 아니라 MinIO 내부 레이아웃이다. 같은 MinIO 로만 되돌릴 수 있다.
