
- 위키 본문, revision, 이미지와 권리 정보가 서로 다른 속도로 사라져 설명할 수 없는 상태가 되지 않게 무엇을 원본으로 보고 언제 보존·삭제하는가?
- 현재 본문에서 빠진 이미지라도 과거 revision이 참조하면 ATTACHED로 보아 삭제를 차단하고, 삭제 요청은 현재 문서뿐 아니라 모든 revision 참조를 검사하기로 판단했다.
- 현재 구현이 checksum·MIME·크기·상태와 문서 참조를 관리하는 것과 제작자·출처·라이선스 필드가 아직 스키마에 없는 것을 확인해, 없는 필드는 운영 규칙으로 먼저 적용하고 후속 migration 대상으로 남겼다.

위키 글은 본문만 저장한다고 끝나지 않는다. 누가 만들었는지, 어떤 이미지와 연결되는지,
수정 전 상태를 언제까지 보존할지와 삭제할 권한까지 이 글에서 함께 정했다.

jay-wiki는 PostgreSQL 문서 revision과 MinIO 이미지 객체를 별도로 관리한다. 이 글은 구현 구조를
다시 설명하기보다 **무엇을 원본으로 보고 언제 보존하거나 삭제하는가**를 정한다.

## 관리 대상마다 기준 원본을 하나씩 정했다

| 대상 | 기준 원본 | 이유 |
|---|---|---|
| 공개 문서 본문 | PostgreSQL tb_article | 운영 화면이 읽는 현재 상태 |
| 문서 변경 이력 | PostgreSQL tb_revision | 이전 본문과 변경 시점 보존 |
| 이미지 metadata | PostgreSQL tb_article_asset | 소유자, checksum, 상태와 문서 연결 |
| 이미지 binary | 환경별 MinIO bucket | DB 크기와 object storage 책임 분리 |
| 재구축 기준 문서 | seed와 Markdown export | 검토된 기준 콘텐츠의 재현·면접용 snapshot |

seed와 운영 DB가 모두 존재하지만 같은 역할은 아니다. 운영 중 관리자 편집의 원본은 PostgreSQL이고,
seed는 검토된 기준 문서를 재구축하는 수단이다. 두 내용이 다르면 자동 덮어쓰기 전에 dry-run으로
차이를 먼저 확인한다.

## 편집 권한과 게시 권리는 다르다

문서를 편집할 수 있다는 사실과 외부 콘텐츠를 게시할 권리가 있다는 사실은 다르다.

| 역할 | 할 수 있는 일 | 책임 |
|---|---|---|
| ADMIN | 문서 작성·수정, 이미지 업로드, revision 확인 | 출처·권리 확인, 비밀정보 제거, 변경 사유 기록 |
| USER | 공개 문서 열람, 허용된 사용자 기능 | 위키 기준 콘텐츠 변경 불가 |
| 시스템 | revision 생성, checksum 검증, 참조 중 삭제 차단 | 권리 판단을 대신하지 않음 |

현재는 개인 운영자 한 명이 ADMIN이지만 정책을 생략하지 않는다. 역할이 늘어나도 같은 승인 경계를
유지할 수 있어야 하고, 설명할 때도 단순한 UI 숨김이 아니라 서버 권한과 데이터 이력으로 말한다.

## 이미지가 문서보다 먼저 사라지지 않게 한다

이미지는 TEMP, ATTACHED, UNUSED 상태를 가진다.

| 상태 | 의미 | 삭제 기준 |
|---|---|---|
| TEMP | 업로드됐지만 문서에 저장되지 않음 | 유예 시간 뒤 정리 가능 |
| ATTACHED | 현재 본문 또는 revision이 참조 | 삭제 금지 |
| UNUSED | 현재 본문에서 빠졌고 revision 참조도 없음 | 보존 기간 뒤 관리자 정리 가능 |

현재 글에서 이미지를 지웠더라도 과거 revision이 참조하면 ATTACHED다. 이 규칙이 없으면 변경 이력의
본문은 남아도 이미지가 깨져 revision을 증거로 사용할 수 없다. 따라서 삭제 요청은 현재 문서뿐 아니라
모든 revision 참조를 검사한다.

## 보존 기간은 데이터 종류마다 다르다

| 데이터 | 기본 기준 | 예외 |
|---|---|---|
| 현재 공개 본문 | 문서가 폐기될 때까지 | 개인정보·Secret 노출 시 즉시 비공개·정정 |
| revision | 원칙적으로 계속 보존 | 민감정보가 들어간 revision은 별도 폐기 절차 필요 |
| ATTACHED 이미지 | 참조가 존재하는 동안 | 권리 침해나 개인정보 신고 시 우선 차단 |
| TEMP 이미지 | 짧은 유예 후 삭제 | 저장 중 실패 복구 시간을 고려 |
| backup | 정해진 세대·기간만 보존 | restore rehearsal 증거는 별도 기록 |

**revision은 무조건 불변**이라는 규칙도 절대적이지 않다. 비밀번호, OTP secret, 개인정보나 권리 침해
자산이 들어가면 공개 화면에서 숨기는 것만으로 부족하다. 원본 revision, MinIO 객체, backup과 로그까지
영향 범위를 확인하고 삭제 사실 자체는 감사 기록으로 남긴다.

## 출처 정보는 binary와 함께 움직인다

파일 checksum은 같은 파일인지 증명하지만 사용 권리를 증명하지는 않는다. 이미지 metadata에는
다음 정보를 함께 관리하는 것이 목표다.

1. 제작자 또는 촬영자
2. 원본 URL과 확인일
3. 라이선스 또는 별도 허가
4. crop, annotation 같은 편집 내역
5. 사용 중인 문서와 revision

현재 구현은 checksum, MIME, 크기, 상태와 문서 참조를 관리한다. 제작자·출처·라이선스 필드는 아직
스키마에 없으므로 운영 규칙으로 먼저 적용하고 후속 migration 대상으로 남긴다.

## 본문에는 환경 독립적인 asset URL 만 저장한다

로컬과 운영 MinIO는 분리한다. 로컬에서 작성한 Markdown이 로컬 객체 주소를 직접 포함하면 운영 이식
때 본문을 고쳐야 하므로, 본문에는 환경에 독립적인 same-origin asset URL만 저장한다.

운영 반영 순서는 다음과 같다.

1. 로컬 글과 이미지를 검토하고 민감정보·출처를 확인한다.
2. 운영에서 이미지를 다시 업로드해 운영 assetId를 발급받는다.
3. 운영용 asset URL로 본문을 확정한다.
4. seed dry-run과 DB backup 후 문서를 반영한다.
5. 공개 URL, checksum과 revision 조회를 확인한다.

환경을 분리하는 목적은 불편을 만드는 것이 아니라 로컬 실수가 운영 자산 삭제나 오염으로 이어지는
범위를 줄이는 데 있다.

## 완료 기준 — 삭제 차단부터 backup 범위까지 다섯이다

- 본문과 revision이 참조하는 이미지 삭제가 서버에서 차단된다.
- MinIO 내부 주소와 credential이 Markdown에 노출되지 않는다.
- 운영 반영 전에 문서 차이와 이미지 출처를 검토한다.
- 출처가 확인되지 않은 외부 이미지는 업로드하지 않는다.
- 민감정보 삭제는 현재 화면이 아니라 revision, object, backup 범위까지 확인한다.

거버넌스의 목적은 문서를 오래 보관하는 것 자체가 아니다. **현재 글, 과거 이력, 이미지와 권리 정보가
서로 다른 속도로 사라져 설명할 수 없는 상태가 되는 것을 막는 것**이다.
