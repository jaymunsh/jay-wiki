
- 기능이 늘며 흐려진 화면을 어떤 기준으로 다시 묶었나?
- 화면마다 하나의 질문을 맡기고 19개 소분류를 같은 높이에 두는 대신 BUILD·OPERATE·IMPROVE·LAB 네 흐름으로 묶었으며, 개편의 목표를 장식이 아니라 정보의 위계와 다음 행동으로 정했다.
- 2026-08-02 기준 npm run lint가 exit code 0이지만 허용치 8개 경고를 전부 쓰고 그중 WikiShell에 2개가 남아 있음을 확인했고, Core Web Vitals 개선은 측정 전이라 주장하지 않는다.

기능을 붙일 때마다 메뉴와 탭을 하나씩 늘리자, 방문자는 기술 이름은 많이 보지만 어디부터 읽고 무엇을 직접
실행해야 하는지는 알기 어려워졌다. 위키, 게시판, 검색, 관리자, 시나리오와 모니터링을 한 화면에 모두 강조한 것이 문제였다.

그래서 프론트 개편의 목표를 장식이 아니라 **정보의 위계와 다음 행동을 분명히 만드는 것**으로 정했다.

## 화면마다 하나의 질문을 맡겼다

| 화면 | 답해야 하는 질문 | 대표 행동 |
|---|---|---|
| 대시보드 | 이 프로젝트는 어떤 구조로 운영되는가 | 오케스트레이션 맵의 영역을 선택한다 |
| 위키 | 왜 이 기술과 구조를 선택했는가 | BUILD·OPERATE·IMPROVE·LAB 순서로 근거를 읽는다 |
| 시나리오 | 실제 업무 문제를 어떻게 재현하고 판단했는가 | 사례를 선택해 상태 변화와 코드를 확인한다 |
| 모니터링 | 지금 서비스와 miniPC는 어떤 상태인가 | 공개 집계 신호를 보고 깊은 분석은 Grafana로 이동한다 |
| 자유게시판 | 검색과 사용자 콘텐츠 기능이 실제로 동작하는가 | 게시글을 읽고 10만 건 검색 방식을 비교한다 |

## 문서 탭을 4개 흐름으로 다시 묶었다

19개 소분류를 모두 같은 높이의 대분류로 놓지 않았다. 대시보드는 별도 진입점으로 두고, 나머지는 방문자의 질문에 따라
네 흐름으로 묶었다. 이때(2026-08-02) 소분류 이름은 아래와 같았다.

| 대분류 | 포함하는 내용 | 읽는 관점 |
|---|---|---|
| BUILD | 인프라·백엔드·데이터·프론트엔드 | 무엇을 어떻게 만들었는가 |
| OPERATE | 관측·운영·시나리오·보안·운영 검증 | 배포 뒤 어떻게 확인하고 대응하는가 |
| IMPROVE | 개발 프로세스·AI 활용·거버넌스·회고·로드맵 | 어떤 증거로 개선했는가 |
| LAB | 개인·팀 프로젝트·기술 실험·도구 | jay-wiki 밖에서 무엇을 실험했는가 |

대분류를 선택하면 그 안의 소분류만 두 번째 레일에 보인다. 문서 목록은 현재 카테고리만 우측 패널에 남겨,
전체 위치와 현재 글의 이웃을 동시에 알 수 있게 했다.

## 권한과 화면 상태도 같은 구조에 넣었다

- 관리자와 일반 사용자의 로그인 진입점은 하나로 통합했다.
- 비로그인·USER·ADMIN 상태는 같은 프로필 메뉴 안에서 구분한다.
- 모바일 헤더는 검색을 유지하고 나머지 명령을 2열 메뉴로 옮긴다.
- 편집·이력·탭 관리 명령은 ADMIN에게만 보이지만, 실제 권한 검사는 Spring에서 다시 수행한다.
- 테마 기본값은 light이며 사용자가 고른 light·dark 값은 localStorage에서 복원한다.

## 프로젝트 맵은 목록이 아니라 흐름이다

홈의 오케스트레이션 맵은 기술 로고를 나열하지 않는다.
Public edge에서 k3s로, 다시 workload와 data와 observability로, 마지막에 delivery로 이어지는 흐름을 보여주고,
영역을 고르면 그 영역이 실제로 무엇을 책임지는지 펼친다.

로고는 MinIO 버킷에 두고 same-origin asset route로 내보낸다.
자산을 못 불러와도 텍스트 라벨은 남기 때문에, 스토리지 장애가 화면을 비우지 않는다.

desktop과 mobile에서 라벨과 선택 상세가 영역 밖으로 나가지 않는지 확인한다. 넓은 맵을 억지로 축소하지 않고,
mobile에서는 세 열을 세로로 쌓되 Public Edge → k3s → Delivery 순서로 두어 요청이 흐르는 방향을 유지한다.

## 화면 구조를 코드 경계로 옮겼다

- 대분류 정의와 소분류 매핑은 wikiCategories 모듈에서 관리하고, WikiShell은 선택과 렌더링을 담당한다.
- 시나리오 설명 데이터는 scenarios 모듈로 분리해 화면 컴포넌트가 거대한 정적 데이터 파일이 되지 않게 했다.
- 내부 Spring 주소는 server-only backend 모듈, 공개 site·Grafana 주소는 siteConfig에서 관리한다.
- ESLint flat config와 npm lint 명령을 두고 CI와 배포 workflow에서 같은 검사를 실행한다.
- Mermaid는 동적 import하고 strict 보안 수준으로 parse한 뒤 렌더링한다. 실패한 원문과 오류 문구를 방문자에게 노출하지 않는다.

## 아직 남은 비용 — force-dynamic 렌더링과 lint debt다

위키 페이지는 최신 DB 본문을 보여주기 위해 force-dynamic으로 렌더링하고, 첫 요청에서 전체 탭 트리와 현재 글을 읽는다.
콘텐츠 규모에는 충분하지만 문서가 더 늘면 탭 tree payload, 서버 응답 캐시와 문서 전환 prefetch를 실제 수치로 다시 판단할 일로 남겨 뒀다.

또한 현재 개선은 탐색 안정성과 반응형 동작을 확인한 것이지, Core Web Vitals가 좋아졌다는 증거는 아니다.
다음 성능 개선은 운영 환경의 LCP·INP·CLS와 문서 전환 시간을 먼저 측정한 뒤 진행한다.

2026-08-02 기준 npm run lint는 exit code 0이지만 허용치인 8개 경고를 모두 사용한다. 이 중 WikiShell에는
initialArticle 동기화와 빈 slug 처리에서 effect 안의 동기 setState 경고가 2개 남아 있다. lint 도입과 lint debt 해소를
같은 완료 상태로 쓰지 않고, 상태를 props·URL에서 파생하도록 정리한 뒤 warning budget을 낮추는 작업을 남겨 둔다.
