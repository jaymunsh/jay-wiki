
- 같은 10만 건 코퍼스에서 LIKE, tsvector, OpenSearch nori가 각각 무엇을 찾고, 얼마나 걸리나?
- 결과 품질은 운영 smoke로, 응답 시간은 로컬 반복 실측(10회 중앙값)으로 나눠 재고, 특정 엔진을 영구적인 승자로 적는 대신 측정 조건을 수치 옆에 남기기로 판단했다.
- 희귀 단어에서 LIKE 155.2ms 대 nori 7.3ms(약 21배), 활용형 질의에서 tsvector 0건 대 nori 1건 — 2026-08-11 로컬 실측과 2026-07-08 운영 smoke로 확인했다.

## 성격이 다른 두 측정을 같은 10만 건에서 했다

게시판은 generate series로 만든 10만 건 코퍼스를 사용한다. OpenSearch index에는 추가 데이터까지
포함해 100007건이 색인돼 있다.

| 방식 | 역할 |
|---|---|
| LIKE | 가장 단순한 substring baseline. 인덱스 없는 순차 스캔 |
| PostgreSQL tsvector와 GIN | DB 안에서 가능한 토큰 기반 전문검색 |
| OpenSearch와 nori | 한국어 형태소 분석, 관련도 점수, highlight, title 자동완성 |

측정은 성격이 다른 두 번을 했다.

| 측정 | 언제·어디서 | 무엇을 보나 |
|---|---|---|
| 운영 smoke | 2026-07-08, 운영 공개 URL, 1회 | 세 경로가 실데이터에서 동작하는가, 무엇을 찾고 놓치는가 |
| 로컬 반복 실측 | 2026-08-11, 로컬 개발 장비, warm 상태, 질의당 10회 중앙값 | 같은 질의의 응답 시간 분포 |

## 결과 품질 — 운영 smoke

한 페이지 최대 20건 조건에서 같은 query를 세 방식에 동시에 넣었다.

| query | LIKE | tsvector | OpenSearch nori |
|---|---:|---:|---:|
| 게시글 | 20건 | 20건 | 20건 |
| 실험 | 1건 | 0건 | 1건 |

게시글처럼 흔한 단어는 세 방식 모두 페이지 상한인 20건을 채웠다. 즉 이 행은 성능이 아니라
**세 경로가 모두 정상 동작한다는 것만** 말해 준다. 차이가 드러난 것은 두 번째 행이다.
본문에 실험했었다만 있는 문서를 실험으로 찾을 때, LIKE는 substring이 포함되므로 찾았고
simple tokenizer를 쓴 tsvector는 실험했었다를 하나의 토큰으로 잘라 놓아 찾지 못했다.
nori는 형태소로 분석해 찾았고, LIKE와 nori 결과 snippet에서 실험 부분의 highlight도 확인했다.

이 결과는 tsvector가 열등하다는 뜻이 아니다. 한국어 형태소 사전 없이 simple tokenizer로 세운 비교군이
어떤 질의에서 무엇을 놓치는지 보여줄 뿐이다. 형태소 분석이 필요 없는 검색이라면 별도 검색 클러스터
없이 tsvector로 충분하다.

## 응답 시간 — 로컬 반복 실측

로컬 개발 장비에서 reindex로 100007건을 색인한 뒤, 같은 질의를 방식마다 10회 실행해 중앙값을 남겼다.
warm 상태이고, 시간은 Spring이 각 방식의 조회 구간만 잰 값이다(2026-08-11).

| 질의 | LIKE 순차 스캔 | tsvector GIN | OpenSearch nori |
|---|---:|---:|---:|
| 게시글 (흔한 단어) | 2.1ms · 20건 | 1.1ms · 20건 | 11.4ms · 20건 |
| 실험 (희귀 단어) | 155.2ms · 1건 | 13.5ms · 0건 | 7.3ms · 1건 |
| 복구 (없는 단어) | 153.7ms · 0건 | 13.4ms · 0건 | 5.1ms · 0건 |

### LIKE의 2ms는 운이고, 150ms가 실력이다

두 경우의 실행 계획이 아예 다르다. EXPLAIN ANALYZE로 확인했다.

| 질의 | 실행 계획 | 읽은 행 | 읽은 페이지 |
|---|---|---:|---:|
| 게시글 (흔한 단어) | idx_post_id_desc 역방향 Index Scan | 27 | 5 |
| 복구 (없는 단어) | Seq Scan | 100007 | 7700 |

이 쿼리는 order by id desc limit 20이다. id에 인덱스가 있으므로 PostgreSQL은 최신 id부터
거꾸로 훑다가 조건에 맞는 20건을 채우면 **그 자리에서 멈춘다.** 흔한 단어는 27행만 읽고 끝났다.
반대로 없는 단어는 멈출 조건이 영영 안 채워져 10만 건 전체를 훑고, 그때의 150ms가 LIKE의
실제 비용 상한이다. **결과가 없을수록 오래 걸리는 검색**은 오타·신조어·조합 질의가 섞이는
실사용에서 그대로 병목이 된다.

### 흔한 단어는 데이터가 늘어도 LIKE가 빠른가 — 조건부로 그렇다

맞다. 그리고 이게 이 비교에서 가장 오해하기 쉬운 지점이다.

조기 중단은 전체 행 수를 보지 않는다. 정렬 순서 앞쪽에서 20건을 얼마나 빨리 만나느냐,
즉 **매치 밀도**만 본다. 밀도가 그대로인 채 코퍼스가 100만 건이 되어도 읽는 행은 여전히 수십 개다.
그러니 "10만 건에서 2ms였으니 100만 건에서는 20ms"는 틀린 추론이다.

문제는 조기 중단이 성립하는 조건이 좁고, **실제 검색 화면이 그 조건을 전부 깬다**는 것이다.

| 조기 중단이 사는 조건 | 실제 검색이 요구하는 것 | 결과 |
|---|---|---|
| 인덱스가 있는 컬럼으로 정렬(id desc) | 관련도 순 정렬 | 점수를 매기려면 후보 전체를 봐야 하므로 전체 스캔 |
| 첫 페이지 20건만 | 2페이지, 10페이지 | offset만큼 더 깊이 훑는다 |
| 총 건수를 세지 않음 | 약 1,234건 표시 | count는 멈출 수 없다 |

마지막 줄은 같은 흔한 단어로 재 봤다. limit 20은 27행만 읽고 0.07ms였지만,
같은 조건의 count는 10만 건을 전부 훑어 **64.8ms**가 걸렸다. 조기 중단이 사라진 것이다.

밀도 자체가 떨어지는 경우도 있다. 특정 단어의 절대 등장 횟수는 그대로인데 코퍼스만 커지면
밀도가 낮아지고, 20건을 채우기까지 훑는 깊이는 그만큼 늘어난다. 신조어나 최근에만 쓰이는 말이
그렇다.

정리하면 — **"최신순 아무거나 20건"에는 LIKE가 규모와 무관하게 빠르다. 그런데 그건 검색이 아니라
표본 추출이다.** 관련도 순서, 총 건수, 깊은 페이지 중 하나라도 필요해지는 순간 조기 중단은 사라지고
150ms 쪽 비용이 기본값이 된다.

### 그럼 흔한 단어만 LIKE로 보내면 되지 않나

안 된다. 이 라우팅이 성립하려면 질의가 들어온 순간 그 단어가 코퍼스에 얼마나 흔한지 알아야 하는데,
그 단어별 빈도 통계를 미리 만들어 두는 것이 바로 역색인이다. 즉 LIKE로 보낼지 판단하는 비용이
역색인 조회 비용과 같아져 복합 라우팅의 이득이 사라진다. 그래서 실무 구성은 빈도로 가르지 않고
**전부 검색엔진으로 보내고, LIKE는 검색엔진 장애 시의 fallback으로만** 둔다. 이 프로젝트의
위키 검색이 정확히 이 구조다.

### 데이터가 커지면 격차는 벌어진다

조기 중단이 없는 경로, 즉 실제 검색이 걷는 경로에서 순차 스캔 비용은 행 수에 비례한다.
10만 건에서 150ms였다면 100만 건에서는 초 단위로 늘어난다. 역색인 조회는 매치한 문서 수와
사전 크기에 좌우되고 전체 행 수에는 훨씬 둔감하다.

OpenSearch가 흔한 단어에서 tsvector보다 느린 것(11.4ms 대 1.1ms)은 HTTP 왕복과 점수 계산이라는
**고정 비용** 때문인데, 이 비용은 데이터가 늘어도 거의 그대로다. 즉 지금 규모에서는 tsvector가
밀리초를 이기지만, 규모가 커질수록 상대적 비중이 줄어드는 쪽은 OpenSearch의 고정 비용이다.
10만 건은 이 프로젝트가 실측할 수 있는 규모의 상한이라, 그 너머는 비용 구조의 추론으로만 적는다.

## 속도만이 아니라 highlight와 자동완성이 갈린다

- OpenSearch는 title과 content highlight를 사용해 검색어 주변을 보여준다.
- LIKE와 tsvector 결과는 서버가 본문 문맥 snippet을 만들어 같은 화면에 표시한다.
- title 자동완성은 OpenSearch match phrase prefix를 먼저 사용한다.
- OpenSearch가 꺼져 있거나 nori가 없으면 자동완성은 PostgreSQL title prefix fallback으로 내려간다.

## 같은 측정을 운영에서 다시 했다 — 순위는 그대로, 값은 1.5배에서 3.5배

로컬 수치만 있는 것이 이 글의 빈칸이었다. 2026-08-19 에 공개 주소로 같은 질의를 방식마다
10회씩 쳐서 중앙값을 냈다. 조건은 로컬과 맞췄다 — 같은 질의, 같은 횟수, warm 상태,
시간은 Spring 이 조회 구간만 잰 값이라 네트워크는 안 들어간다.

| 질의 | 방식 | 로컬(2026-08-11) | 운영(2026-08-19) | 배수 |
|---|---|---:|---:|---:|
| 게시글 (흔한 단어) | LIKE | 2.1ms | 3.6ms | 1.7배 |
| | tsvector | 1.1ms | 2.6ms | 2.4배 |
| | OpenSearch | 11.4ms | 40.2ms | 3.5배 |
| 실험 (희귀 단어) | LIKE | 155.2ms | 177.9ms | 1.1배 |
| | tsvector | 13.5ms | 24.1ms | 1.8배 |
| | OpenSearch | 7.3ms | 16.0ms | 2.2배 |
| 복구 (없는 단어) | LIKE | 153.7ms | 187.6ms | 1.2배 |
| | tsvector | 13.4ms | 23.5ms | 1.8배 |
| | OpenSearch | 5.1ms | 11.8ms | 2.3배 |

**결론의 순서는 하나도 안 바뀌었다.** 흔한 단어에서는 PostgreSQL 쪽이 빠르고, 희귀·없는 단어에서
LIKE 가 무너지고, OpenSearch 는 질의 종류에 덜 흔들린다. 바뀐 것은 **모든 값이 함께 느려진 것**뿐이다.

느려진 폭이 방식마다 다른 것은 눈여겨볼 만하다. LIKE 는 1.1~1.7배인데 OpenSearch 는 2.2~3.5배다.
디스크를 순차로 읽는 일보다 JVM 위에서 도는 일이 장비 차이를 더 크게 받는다 — miniPC 의
4700U 와 heap 512m 고정이 그 자리다.

**최댓값도 같이 적어 둔다.** OpenSearch 는 10회 중 한 번씩 튀었다(게시글 93.3ms, 실험 177.4ms).
중앙값만 보면 안 보이는 값이고, warm 이라고 적었지만 완전히 데워진 상태는 아니라는 뜻이다.

## 수치에는 측정 조건을 옆에 붙였다

응답 시간은 로컬과 운영, 첫 요청과 cache가 데워진 뒤 요청이 다르다. 그래서 이 글의 수치에는
데이터 수, query, 실행 횟수, 환경, warm 여부를 옆에 붙였고, 조건이 다른 두 측정(운영 smoke와
로컬 실측)을 한 표에 섞지 않았다. 특정 밀리초를 영구적인 승자처럼 읽지 않기를 바란다.

## 세 방식 모두 남긴 이유가 있다

LIKE는 비교 기준으로 남긴다. PostgreSQL 전문검색은 별도 검색 클러스터 없이 가능한 선택지다.
OpenSearch nori는 한국어 분석과 highlight, 자동완성이 필요한 경우의 선택지다. 세 방식을 같이 둔 이유는
도구 이름을 늘리기 위해서가 아니라 이 트레이드오프를 직접 보이기 위해서다.
